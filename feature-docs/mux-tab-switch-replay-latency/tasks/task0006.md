# Task Plan: task0006 — tabs.rs pending-switch/redispatch: fix target-dims mismatch (FR7), decode dedup (FR8), and live-output loss/duplication introduced by round-1's fix

<!-- Rework task synthesized by the orchestrator from review round 1 residual findings (batch mode, no planner involved). Findings reproduced verbatim below per batch-mode.md "Rework task synthesis". -->

## Goal

Redesign the `pending_switch` / `pending_redispatch` state machine in `src-tauri/src/tabs.rs` so that: (1) a grid resize racing an in-flight switch does not leave the bypass split defeated by a segments-dims-vs-target mismatch (FR7), (2) a duplicate snapshot for the same pane is not decoded/fetched twice (FR8), and (3) live PTY output arriving in the window between a same-pane coalesce and the eventual poll is neither lost nor duplicated (a defect exposed by review round 1's own auto-fix for the original duplicate-application bug).

## Requirements

FR7, FR8

## Findings to resolve (verbatim from review round 1)

### Finding 64baa639d71792f9 (spec, high)

**Title**: FR7: resize 競合時、旧 target のセグメント dims のまま新 target へ replay し bypass が依然defeatされる

**File**: `src-tauri/src/tabs.rs:3455`

**Description**: task0003's coalescing reduces redundant WORKER SPAWNS, but the segments-dims-vs-replay-target mismatch (SPEC Root Cause 3) is untouched: a resize supersedes an in-flight switch, `dispatch_offthread_replay` reads the NEW core size as target, but the `ReplaySegment` dims were recorded by the daemon at the PRE-resize size. `stable_target_suffix_start(new_cols, new_rows, segments)` still finds no matching trailing run, so bypass is defeated for the one build that DOES complete. Round 1's two auto-fixes (tabs.rs:979/3463) changed WHICH already-recorded payload is replayed, not the relationship between that payload's segment dims and the replay-time target — this finding is unaffected by them.

**Suggestion**: Address the mismatch directly. Either (a) re-request the snapshot from the daemon at the new grid when a resize supersedes an in-flight switch (a round-trip, but segments then match the replay target); or (b) when the trailing run's dims equal the DISPATCH-time target, normalize/rewrite them to the replay-time target before computing `stable_target_suffix_start`, so a pure GUI-side resize does not synthesize a spurious divergence (this must be done carefully — only safe when the actual PIXEL content is unaffected by the dims relabeling, i.e. the segment's real content didn't depend on the old dims); or (c) let the worker build the core at the OLD target and then resize it in-process to the new one after replay, instead of rebuilding from scratch. Whichever route, add a test that performs a resize during an in-flight switch and asserts bypass engages (or the replay otherwise completes in the unraced baseline's latency order) for the POST-resize target.

### Finding fabff23130d04812 (spec, medium)

**Title**: FR8: 同一 pane の重複 snapshot は decode/fetch レベルでは依然 2 回行われる

**File**: `src-tauri/src/tabs.rs:1471`

**Description**: The coalesce sits strictly downstream of both fetch and decode. Every `Snapshot`/`SnapshotRestore` frame still runs `decode_snapshot_payload_typed` and the full segments/content conversion before `dispatch_offthread_replay` is reached; a repeat switch still sends a second `RequestPaneSnapshot` and the daemon still builds/ships a second snapshot. Only the replay BUILD is deduplicated.

**Suggestion**: Either (a) suppress a redundant snapshot request for a pane whose switch is already in flight, and/or short-circuit decode when a frame for the same pane is already coalesced in `pending_redispatch`; or (b) if replay-level dedup is judged sufficient for this feature's latency goal, amend SPEC FR8/US3's acceptance criterion to say "do not replay/rebuild the snapshot twice" and record that decision explicitly (do not leave the requirement and the test silently disagreeing about what is claimed).

### Finding 7ed0ba7335376c20 (comprehensive, high — regression introduced by round 1's own auto-fix)

**Title**: 同一ペインの新スナップショット到着後に届いたライブ出力が poll 時に丸ごと破棄される

**File**: `src-tauri/src/tabs.rs:993`

**Description**: Round 1's fix for the original duplicate-live-output bug (`old.payload == payload` guard in `poll_pending_switch`) left `pending_switch` (the OLD, superseded request) alive and still accepting queued live output for every pump cycle between the coalesce and the eventual poll — a window that did NOT exist before task0003's coalescing was introduced (previously, a new same-pane snapshot replaced `pending_switch` — and its `live_queue` — IMMEDIATELY, synchronously, in the same call that decoded it). Any live output arriving in this NEW window is queued against the stale `pending_switch` and then discarded wholesale at poll time by the very guard that fixed the original bug. The orchestrator independently verified (by reading `dispatch_offthread_replay`'s same-pane branch and the `PtyOutput` queueing arm) that this extended queuing window is new: pre-coalesce, a same-pane snapshot's arrival and the queue replacement were atomic within one call; post-coalesce, they are split across an unbounded number of pump cycles.

**Suggestion**: Move the discard/keep decision from POLL time to COALESCE time. In `dispatch_offthread_replay`'s same-pane branch (where `pending_redispatch` is set), immediately decide whether the CURRENT `pending_switch.live_queue` should be cleared (new payload differs — its content is not guaranteed to already include this queue) or kept (this is a resize-driven re-dispatch of the identical payload). If cleared at coalesce time, any live output arriving AFTER that point continues accumulating correctly against the (unmodified) `pending_switch`, and `poll_pending_switch` can simply always inherit `pending_switch.live_queue` without any payload comparison (removing the O(n) byte comparison the round-1 fix introduced, see 5b1878c41d3e02d6 below). Verify this handles more than one chained coalesce correctly (e.g. P1 → P2 coalesced → P3 coalesces again before poll) — each new coalesce must re-evaluate whether to clear the (potentially already-cleared-then-refilled) queue.

### Finding ebc9de26bb15fcb1 (comprehensive, medium — sibling of the above)

**Title**: live-queue オーバーフロー時の同期フォールバックが「別 payload + 旧キュー」を適用して二重適用する

**File**: `src-tauri/src/tabs.rs:1674`

**Description**: The `OFFTHREAD_LIVE_QUEUE_CAP_BYTES` overflow fallback resets the frame with `pending_redispatch`'s payload and then unconditionally applies `pending.live_queue` as ordinary output — the same bug family as 7ed0ba7335376c20, at a sibling call site.

**Suggestion**: Resolved automatically once 7ed0ba7335376c20's coalesce-time clear is implemented (this site's `pending.live_queue` will then already be correctly scoped to "output since the last coalesce/clear"). If a different design is chosen for 7ed0ba7335376c20, this site needs the same payload-aware decision.

### Finding 34a708465d04f983 (performance, medium)

**Title**: resize のたびに snapshot payload 全体を複製している（coalesce 済みでも複製 → 即破棄）

**File**: `src-tauri/src/tabs.rs:3463`

**Description**: `Tab::resize`'s redispatch branch clones `pending.payload`/`.segments` (or the `pending_redispatch` equivalent) EVERY resize event, even when the same-pane coalesce is about to discard that clone immediately. During a resize storm with an in-flight multi-MiB switch, this is a wasted multi-MiB alloc+memcpy per event on the UI thread, multiplied across tabs by `App::set_grid_size`'s per-tab loop.

**Suggestion**: Skip the clone entirely when a same-pane coalesce is already pending (check `self.pending_redispatch`'s target pane before cloning) — see the finding's own suggested diff for the exact structure. A `Arc<Vec<u8>>`/`Arc<[ReplaySegment]>` representation for `PendingSwitch::payload`/`.segments` and the resize path would eliminate this class of clone entirely and is worth considering as part of this task's redesign (it would also make FR7's fix and the live-queue coalesce-time decision cheaper to reason about).

### Finding 5b1878c41d3e02d6 (performance, medium — introduced by round-1's auto-fix)

**Title**: coalesce 解決時に最大数 MiB の payload を毎回フルバイト比較している

**File**: `src-tauri/src/tabs.rs:993`

**Description**: The round-1 auto-fix's `old.payload == payload` comparison performs an O(n) byte comparison (up to ~2 MiB) on every `poll_pending_switch` call during a resize storm, when the same information ("is this a resize-driven re-dispatch of the identical payload, or a genuinely new snapshot") is already known in O(1) at coalesce time.

**Suggestion**: Resolved by 7ed0ba7335376c20's redesign (move the decision to coalesce time) — `poll_pending_switch` should not need this comparison at all once the discard/keep decision happens earlier. If `Arc`-based payloads are adopted (per 34a708465d04f983), an `Arc::ptr_eq` check is also O(1) and available as a fallback discriminator.

## Design

Address FR7 (target-dims mismatch) and the live-queue lifecycle (7ed0ba7335376c20/ebc9de26bb15fcb1/5b1878c41d3e02d6) as the primary redesign — they are the two correctness-critical concerns. FR8's decode-level dedup and the wasteful-clone finding (34a708465d04f983) can be addressed as part of the same redesign since they touch the same call sites, but are secondary in priority (medium severity) if time/complexity forces a choice — in that case, resolve them by amending the requirement's acceptance criterion per the finding's own fallback suggestion (record the narrower scope explicitly) rather than leaving the test and the requirement silently disagreeing.

This is genuinely a design-level fix, not a mechanical patch — the review round that surfaced these findings explicitly noted that two independent reviewer perspectives (architecture vs. comprehensive) reached DIFFERENT conclusions about whether the live-queue-loss behavior was a regression, because the correct answer depends on precisely when in the pending_switch/pending_redispatch lifecycle a decision is made. Resolve this ambiguity with a clear, single point of decision (coalesce time, not poll time, per 7ed0ba7335376c20's suggestion) and write tests that pin the decision.
