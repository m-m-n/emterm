# Task Plan: task0002 — Suppress all-pane resize broadcast before the status bar settles

## Goal

Stop the GUI from broadcasting a `Resize` control frame to every
daemon-side pane in the mux group while the status bar's visible row
count is still settling at startup/reattach, which is the upstream cause
of resize markers accumulating in scrollback (the shape task0001 has to
tolerate downstream).

## Requirements

FR6

## Scope

### Files to Create
- (none)

### Files to Modify
- `src-tauri/src/window_host.rs` — `refresh_status_bar_insets` (and/or its
  caller, `apply_pending_resize`) — where a status-bar-height-driven inset
  change currently sets `pending_resize = true` unconditionally on every
  detected change
- `src-tauri/src/tabs.rs` — `Tab::resize`'s group-wide
  `MessageType::Resize` broadcast site (the loop over
  `self.mux_group.as_ref().pane_ids()`), only if the settling detection
  needs a signal from this call site rather than being fully containable
  in `window_host.rs`

## Design

### Observed mechanism (from measurement, see SPEC.md References)

`panel_height_logical = ROW_HEIGHT (22.0) × visible_row_count`
(`src-tauri/src/ui/status_bar.rs`). At startup/reattach,
`visible_row_count` (driven by OSC/App-line content becoming available
asynchronously as the mux session's panes/windows are seeded) transitions
through 0 and 1 — and was observed oscillating between two states 24
times within an 11 KB scrollback window before settling. Each transition
that changes `status_bar_bot_inset_logical`
(`window_host.rs::refresh_status_bar_insets`) sets `pending_resize = true`
unconditionally, which — once applied
(`window_host.rs::apply_pending_resize` → `app.set_grid_size` →
`Tab::resize`) — broadcasts a `Resize` control frame to EVERY pane in the
mux group (`src-tauri/src/tabs.rs`, the loop calling `self.send_control`
with `MessageType::Resize` for each `pane_id` in
`self.mux_group.pane_ids()`), and each of those panes'
`ScrollbackRingBuffer::attribute_write` then records a new resize marker
because the received dims differ from what it last recorded.

A separate, deliberate one-time seed already exists (pushing the current
grid's dims to every newly-seeded pane once, right after mux attach,
`src-tauri/src/tabs.rs` around the mux-session seeding path) — that seed
is correct and out of scope; this task targets the SUBSEQUENT broadcasts
caused by the status bar still settling in later frames.

### What must change

The GUI must not treat each individual status-bar-height change during
the settling window as an independent, immediately-broadcast resize.
Design a settling condition (e.g., requiring the computed grid size to
stay unchanged for some number of consecutive frames, or scoping
suppression to a bounded grace window right after mux attach) such that:
- transient oscillation during startup/reattach does not reach
  `Tab::resize`'s broadcast at all, or reaches it at most once for the
  FINAL settled size
- an ordinary, single, deliberate resize (user resizing the window, or
  status bar content genuinely and stably changing after startup) still
  reaches `Tab::resize` and broadcasts normally, with no added perceptible
  delay

Record the chosen settling mechanism and its rationale as a doc comment
at the point it's implemented (per IMPLEMENTATION.md's Conventions
section) — this is a single-task decision (IMPLEMENTATION.md D3), not a
cross-task one.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A test reproducing the startup/reattach `visible_row_count`
  0 → 1 (and back) oscillation sequence asserts that `Tab::resize`'s
  group-wide `Resize` broadcast is NOT invoked once per transient
  transition — at most once, for the final settled grid size.
- [ ] AC-2: The same test (or a paired one) asserts that, after settling,
  every pane in the mux group ends up informed of the FINAL correct grid
  size (no pane is left at a stale size because a broadcast was
  suppressed and never re-sent).
- [ ] AC-3: A test for an ordinary post-startup resize (e.g. the user
  resizing the window once, well after settling) asserts the broadcast
  still fires exactly as before this change (no regression to normal
  interactive resize).
- [ ] AC-4: A test confirms the existing one-time mux-attach seed (that
  pushes the current grid dims to every newly-seeded pane right after
  attach) is unaffected by this change — it still fires on attach.
- [ ] AC-5: After this fix, a scenario replaying the startup/reattach
  sequence produces a scrollback with NO new resize markers beyond the
  one (if any) the settled final size legitimately requires — i.e. the
  upstream cause of task0001's reproduced marker-cluster shape no longer
  occurs from this trigger.

## Test Notes

- AC-1/AC-5 need a way to simulate the `visible_row_count` transition
  sequence without a real GUI window — drive `StatusBarViewModel`/
  `refresh_status_bar_insets`-equivalent inputs directly in a unit test
  if the existing test setup allows constructing `WindowHost`-level state
  headlessly; otherwise isolate the settling-decision logic into a
  testable unit that takes a sequence of computed grid sizes and returns
  which ones should reach `Tab::resize`.
- AC-3 should reuse or extend whatever existing resize-path test already
  covers ordinary interactive resize, to catch a regression at the same
  granularity that existing coverage does.
- Follow the tdd-testing skill: write AC-1 as a failing test first
  (asserting the CURRENT code broadcasts once per transition), then
  implement the settling logic until it and the rest pass.

## Out of Scope

- The bypass split gate itself and its thresholds (task0001) — this task
  reduces how often the marker-dense shape occurs, but existing
  scrollback that already accumulated markers before this fix is not
  cleaned up by this task (per REQUIREMENTS.md 10.1, that's why task0001
  exists independently).
- Switch-time races (target mismatch during an in-flight switch,
  duplicate snapshot fetch) — task0003.
- Any resize storm involving `cols` changes (out of scope per
  SPEC.md/REQUIREMENTS.md).
