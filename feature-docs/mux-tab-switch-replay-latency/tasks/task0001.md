# Task Plan: task0001 — Bypass split gate resilience for a resize-marker-dense scrollback tail

## Goal

Make the snapshot replay bypass split gate engage (or otherwise complete
within the same latency order as when it engages) for a pane whose
scrollback has a cluster of resize markers with dims different from the
switch target near its tail, without reintroducing the double non-bypass
replay cost the gate's existing thresholds guard against.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1

## Scope

### Files to Create
- (none — this task extends existing files only)

### Files to Modify
- `crates/term_core/src/terminal_core.rs` — the bypass split gate
  (`stable_target_suffix_start`, the `k`/`split_at`/`suffix_len`/
  `bypass_split`/`bypass_engaged` computation in
  `TerminalCore::build_from_snapshot_inner`, and the constants
  `BYPASS_PREFIX_MAX_SEGMENTS`/`BYPASS_PREFIX_MAX_BYTES`/
  `BYPASS_SUFFIX_MIN_BYTES` if the fix changes their values or adds a new
  one)
- `crates/term_core/src/bench.rs` — add a new bench/regression test next
  to the existing `snapshot_replay_bench_2mib_seq` (around line 169)

## Design

### Reproduced shape (from measurement, see SPEC.md References)

A payload of ~2.1 MB / 31 replay segments, where the tail ~24-27 segments
are a dense cluster of resize markers (dims oscillating away from and
back to the switch target within a small byte window), leaving:
- `k` (the count of segments from the point where dims last diverge from
  target, per `stable_target_suffix_start`) around 27 — above
  `BYPASS_PREFIX_MAX_SEGMENTS` (24)
- `split_at` (prefix byte length) around 2,096,654 — far above
  `BYPASS_PREFIX_MAX_BYTES` (64 KiB)
- `suffix_len` around 7,395 — below `split_at`, failing
  `suffix_len >= split_at`

All three of the existing gates fail simultaneously, forcing a full
non-bypass drain of the ~2.1 MB payload (measured 782.8–977.6 ms), versus
9.3–9.5 ms for the same pane when bypass engages.

### What must change

The gate must distinguish this shape — a dense cluster of *small,
resize-only* segments near the tail whose own replay cost is cheap
per-segment even though their combined byte span is large — from the
shape the existing thresholds were designed to reject (a genuinely large,
content-heavy prefix whose non-bypass replay is itself expensive, per
`BYPASS_PREFIX_MAX_BYTES`'s doc comment history in
`terminal_core.rs`). The prefix in the reproduced shape is large in BYTES
but its *actual replay cost* is small (it's almost entirely dead
resize-marker segments with negligible content between them) — the
existing gate conflates "prefix is large" with "prefix is expensive,"
which is the false assumption to correct.

Any new threshold or condition introduced here must keep citing its
review-history-style rationale in a doc comment, per IMPLEMENTATION.md's
Conventions section, and must satisfy the NFR1 constraint below.

### Constraint (NFR1, MANDATORY — see IMPLEMENTATION.md D2)

The fix must NOT simply relax `BYPASS_PREFIX_MAX_BYTES` /
`suffix_len >= split_at` without another change that keeps a genuinely
expensive large prefix (the shape those two gates were added to reject —
see the `BYPASS_PREFIX_MAX_BYTES` doc comment's round-7/round-8 history)
from engaging the split and paying its non-bypass cost twice (once in the
split's own prefix replay, once in the 2nd-pass worker's
`build_scrollback_only_from_snapshot`). AC-6 below is the regression test
for this constraint.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A new bench/regression test reproduces the measured shape (2
  MiB payload, ~31 segments with a dense resize-marker cluster near the
  tail whose dims differ from the switch target, small final suffix) and
  asserts an end-to-end `build_from_snapshot` latency ceiling in the
  tens-of-ms order (matching the bypass-engaged baseline for a payload of
  this size, not the ~800-1000 ms non-bypass baseline).
- [ ] AC-2: The existing `snapshot_replay_bench_2mib_seq` bench
  (`crates/term_core/src/bench.rs:169`) still passes unmodified in its
  assertion (its own payload shape, with no resize markers, is
  unaffected).
- [ ] AC-3: An existing or new test/bench for the "ordinary switch" shape
  (small `k`, small `split_at`, large dominating suffix — the shape the
  gate already handled correctly) shows unregressed latency versus the
  pre-fix baseline (reference: 1.57 ms order for that shape).
- [ ] AC-4: A test asserts bypass equivalence for the reproduced shape
  from AC-1: the resulting viewport contents and cursor position match
  what a full non-bypass replay of the same payload produces, and
  `scrollback_populated`'s value has the same meaning as for any other
  bypass-engaged replay (i.e. this fix does not special-case AC-1's shape
  into a different, non-equivalent fast path).
- [ ] AC-5: A test for a shape at/near the `BYPASS_PREFIX_MAX_SEGMENTS`
  (24) boundary confirms the existing ordinary-shape behavior at that
  boundary is preserved (no accidental widening beyond what AC-1's
  specific marker-cluster case requires).
- [ ] AC-6 (NFR1 regression guard): a test constructs a genuinely large,
  content-heavy prefix (not a resize-marker cluster — real scrollback
  content) paired with a small qualifying suffix, and asserts the split
  still does NOT engage for it (or, if it does engage under the new
  logic, asserts the 2nd-pass worker path is not invoked a second time
  for that same prefix) — i.e. the double-cost scenario the existing
  gates prevent stays prevented.

## Test Notes

- AC-1/AC-6 need synthetic payloads with explicit `ReplaySegment` dims
  sequences (not just uniform `seq 1 N` text like the existing bench) to
  reproduce a marker cluster vs. a genuinely large content prefix
  respectively — construct both via `TerminalCore::build_from_snapshot`'s
  existing segments parameter, following the pattern of the file's
  existing `..._marker` fixtures referenced in the surrounding doc
  comments.
- AC-4's equivalence check should reuse whatever comparison helper the
  existing `bypass_split_matches_reference_viewport_and_cursor_for_ordinary_switch`-style
  test (referenced in the surrounding code's comments) already uses,
  applied to AC-1's shape instead of the ordinary-switch shape.
- Follow the tdd-testing skill: write AC-1/AC-6 as failing tests first
  (reproducing the current 800-1000 ms latency / confirming the current
  gate rejects AC-1's shape), then implement the gate change until they
  pass.
