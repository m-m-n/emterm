# Task Plan: task0005 — ResizeSettler: fix render-driven debounce blind spots and missing self-wake

<!-- Rework task synthesized by the orchestrator from review round 1 residual findings (batch mode, no planner involved). Findings reproduced verbatim below per batch-mode.md "Rework task synthesis". -->

## Goal

Fix task0002's `ResizeSettler` (`src-tauri/src/window_host.rs`) so its debounce is driven by actual status-bar state changes rather than by render cadence, so it does not misjudge a genuine oscillation as settled, and so it does not depend on an unrelated event to wake the loop and apply the finally-settled size.

FR6

## Findings to resolve (verbatim from review round 1)

### Finding 12cac263b7dab24b (spec, high)

**Title**: FR6: ResizeSettler がレンダー回数でデバウンスするため最初の遷移がそのまま broadcast される

**File**: `src-tauri/src/window_host.rs:2803`

**Description**: `ResizeSettler::observe` forwards once the same candidate has been observed `RESIZE_SETTLE_QUIET_OBSERVATIONS` (2) times in a row, but observations only happen inside `refresh_status_bar_insets`, called at the head of every `render()` — NOT once per `visible_row_count` change. Render frequency and status-bar-transition frequency are independent, so the storm's very first transient candidate is typically observed twice within ~2 frames and gets forwarded — exactly what FR6 forbids. Worse, forwarding permanently sets `observations_left = None`, closing the settling window until the next mux attach, so every REMAINING transition of the storm is then forwarded immediately (the pre-fix behavior), leaving the marker accumulation FR6 targets fully intact. The existing unit tests feed a value stream that changes on every call — the one regime where the debounce happens to work — so they do not catch this.

**Suggestion**: Debounce on a signal independent of render cadence: (a) wall-clock quiescence (forward only after the candidate has been unchanged for a settling duration, using the render loop's existing real-time clock), or (b) count only observations where the candidate actually CHANGED (track transitions; require N frames/ms with zero transitions), or (c) drive the settler from the status-bar view-model UPDATE site rather than from `render()`, so one observation == one `visible_row_count` change. Add a test that feeds the REAL render-driven shape (A,A,A,B,B,A,A,... — the same value repeated across multiple renders between transitions) and asserts nothing forwards mid-storm.

### Finding 02546e5e10deb500-c (comprehensive, high)

**Title**: ResizeSettler の静穏検出が呼び出し側フィルタで無効化され、計測された 0↔1 振動を吸収できない

**File**: `src-tauri/src/window_host.rs:1252`

**Description**: `refresh_status_bar_insets` only calls `observe(candidate)` when the computed inset DIFFERS from the currently-applied one (window_host.rs:1249 `if` condition). Since the applied value only updates when the settler forwards, one side of a 2-state oscillation (whichever matches the still-applied value) is NEVER observed — the settler is fed a biased stream consisting only of "the other state," repeated. This combines with the finding above (render-count-based debounce) to guarantee early false-settle detection specifically for the SPEC's measured 2-state storm shape. FR6/US2's AC-1 and AC-5 are not met.

**Suggestion**: Feed the settler an observation on every render regardless of whether the candidate differs from the applied value; let the settler itself decide when to forward (which will naturally no-op when the candidate already matches the applied value). Alternatively, pass the applied value into the settler and have it treat "candidate == applied" as a state that resets/holds the repeat counter rather than being skipped upstream. Add a regression test with the call-site's actual input pattern (not an idealized `observe()`-only unit test): a value stream where one state equals the currently-applied inset.

### Finding 02546e5e10deb500 (architecture, medium) + 5b1878c41d3e02d6-perf-P2 (performance, medium; same site, same root cause)

**Title**: ResizeSettler が反復観測を要求する一方、その観測を生む再描画を誰も要求しない（wait ループで確定 resize が宙吊りになる）

**File**: `src-tauri/src/window_host.rs:1248`

**Description**: When `observe` returns `None` (still debouncing), nothing schedules the next render: `pending_resize` is not set and `request_redraw()` is not called. The event loop (post task0004 D4) returns `ControlFlow::Wait` when no blink/bell/toast/sidebar-dim deadline is pending, and `about_to_wait` only requests a redraw for ime/pty/search/blink/bell/toast/mux_sidebar_dim — none of which cover "settler is mid-debounce." If the window becomes idle (unfocused, blink disabled, no PTY output) right after a status-bar height change, the settler's second confirming observation never arrives until an unrelated event wakes the loop, leaving the grid/PTY size stale (bottom row hidden behind the panel) for an unbounded time.

**Suggestion**: Either (a) call `self.window().request_redraw()` (or set an existing redraw-request flag) whenever `observe` returns `None`, so the settler drives its own next observation until it decides; or (b) give the settler a deadline that feeds into `control_flow_for`'s `next_wait_deadline` alongside blink/bell/toast, so the loop wakes itself. Document in `ResizeSettler`'s doc comment whose responsibility it is to schedule the next frame after a withheld observation, so this contract is not silently left to the caller again.

## Scope

### Files to Modify

## Design

Resolve the two independent defects together since they compound: (1) the call-site's "only observe when different from applied" filter starves the settler of the oscillating-back state, and (2) the debounce unit itself (render count) is the wrong signal. A wall-clock-quiescence redesign (per 12cac263b7dab24b's suggestion (a)) likely resolves both at once — feed every computed candidate on every render (removing the call-site filter), and forward only after the candidate has been stable for a real-time duration, independent of how many renders that spans. Whichever design is chosen, it must also close the "no self-wake" gap (02546e5e10deb500) so a pending, not-yet-settled candidate does not stall indefinitely in a fully idle window.
