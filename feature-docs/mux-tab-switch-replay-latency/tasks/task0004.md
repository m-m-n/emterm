### Finding b21749c5f2bd1006 (spec, high)

**Title**: FR1: D7 rescue gate が実測形状の振動方向（rows > target）を拒否する

**File**: `crates/term_core/src/terminal_core.rs:1957`

**Description**: `middle_is_row_bounded` only admits middle segments with `r <= target_rows` — a one-directional gate. SPEC's own root cause (§Implementation Approach 1) is the status bar's `visible_row_count` 0 → 1 oscillation, which changes the grid by 2 rows via `panel_height_logical = ROW_HEIGHT * visible_row_count`. When `visible_row_count == 0` (no bottom inset) the grid is LARGER; `== 1` it is smaller. During the storm the pane is recorded alternately at N and N-2 rows. When the settled target is the smaller (status-bar-visible) state, roughly half the cluster's markers carry `rows = N > target_rows`, `middle_is_row_bounded` returns false, `head_fold_safe` is false, `bypass_split` stays false, and the payload takes the same ~800-1000 ms full non-bypass drain the SPEC set out to eliminate. The new tests (`head_plus_marker_cluster_engages_the_split_and_matches_reference`, the bench) only construct clusters with rows BELOW target (24/26 vs 30) — the above-target direction is entirely unverified.

**Suggestion**: Either (a) extend the safety argument to above-target rows — ending the HEAD one segment earlier (or capping it at the last position from which every subsequent middle row-count stays recoverable) so `resize_full_reflow`/`resize_same_width`'s grow branch can still read real scrollback; or (b) keep the conservative gate but explicitly document (in SPEC/VERIFICATION) that FR1 is satisfied only for below-target clusters, AFTER confirming which direction the real measured markers in this bug actually take (the task's own investigation environment is no longer available to re-measure directly — reason from the code: `visible_row_count` 0→1 SHRINKS the grid, so the settled/target state is the smaller one, meaning the pre-settling markers ARE the above-target direction — i.e. option (a) is almost certainly required, not optional).

### Finding 6a02ed7e1b606588 (comprehensive, high)

**Title**: head_fold_safe を bypass_split のハードゲートにしたため、D7 以前は分割できた形状が全ドレインに退行する

**File**: `crates/term_core/src/terminal_core.rs:1178`

**Description**: `head_fold_safe = h == 0 || middle_is_row_bounded(...)` is ANDed directly into `bypass_split`. When `h > 0` and the MIDDLE contains a column change (or an above-target row count), the split does not merely skip folding the HEAD — it abandons the split ENTIRELY, falling back to a full non-bypass drain of the whole payload. This regresses shapes that engaged the split BEFORE D7 was introduced (e.g. `segments = [target(10 KiB), col-change(20 KiB), target(remaining 2 MiB)]`: pre-D7 gates `k=2<=24`, `split_at=30KiB<=64KiB`, `suffix>=split_at`, `suffix>=4096` were all satisfied and the split engaged; post-D7, `h=1` makes `middle_is_row_bounded` false, so it no longer does). The correct fallback when the HEAD cannot be safely folded is "behave exactly like pre-D7" (treat `h` as 0), not "abandon the split."

**Suggestion**:
```
let h = if bypass && k > 0 {
    let candidate = leading_target_run_len(cols, rows, &segments[..k]);
    if candidate > 0 && !middle_is_row_bounded(cols, rows, &segments[candidate..k]) {
        0 // HEAD not foldable -> degrade to the pre-D7 computation exactly
    } else {
        candidate
    }
} else {
    0
};
```
Then remove `&& head_fold_safe` from `bypass_split`'s condition entirely (with `h == 0`, `middle_len == split_at` and `middle_segment_count == k`, making the computation byte-identical to pre-D7).

### Finding b11143cfa2abef3b (spec, medium)

**Title**: FR2: 新規 bench の上限が緩く、tens-of-ms ceiling を担保しない

**File**: `crates/term_core/src/bench.rs:391`

**Description**: `marker_cluster_tail_bench_2mib_matches_bypass_engaged_cost` asserts `t_marker_cluster < t_free * 5.0 + 50ms`. With this task's own recorded baseline (~76.9 ms segment-free), the effective bound is ~434 ms — an order of magnitude above "tens of ms," and only ~2x below the 782.8-977.6 ms pre-fix regression it exists to catch. The file's own pre-existing companion bench uses a tighter `3.0x + 20ms` (bench.rs:999). Secondary: the fixture is 26 segments (`k=25`), not the SPEC-cited 31 segments / `k=27`.

**Suggestion**: Tighten to match the file's own precedent (e.g. `t_free * 2.0 + 20ms`, or an explicit absolute tens-of-ms ceiling with documented machine-variance margin). Align the fixture's segment/cluster count with the SPEC-cited shape (31 segments, `k=27`) where practical, or document why the smaller reproduction is equivalent.

### Finding 0e3a7dee5f50d788 (architecture, medium)

**Title**: bypass 状態機械の第 3 遷移（suspend）が名前付き API を持たずフィールド直書きで表現されている

**File**: `crates/term_core/src/terminal_core.rs:1255`

**Description**: D7's HEAD→MIDDLE transition is expressed as a direct `core.scrollback_bypass = false;` field assignment rather than a named method alongside `enable_snapshot_bypass`/`disable_snapshot_bypass`. This leaves the bypass state machine's third transition invisible to anyone reading only the two named methods, and any future field added to the bypass-lifecycle (as `capture_bypass_b_marks` was in round-7) risks being forgotten at this call site since it isn't discoverable by reading `disable_snapshot_bypass`.

**Suggestion**: Add a named `suspend_snapshot_bypass(&mut self)` method next to the other two (doc: what it preserves vs. `disable_snapshot_bypass`, precondition `debug_assert!(self.scrollback_slim.is_empty())`), and replace the direct field assignment in `build_from_snapshot_inner` with a call to it.
