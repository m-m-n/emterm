# Task Plan: task0003 — Pane-switch race resilience: target-mismatch bypass drop and duplicate snapshot fetch

## Goal

Ensure a pane switch keeps using the bypass-eligible replay path when a
grid resize lands concurrently with the switch, and ensure consecutive
switches to the same pane do not decode/replay the snapshot twice.

## Requirements

FR7, FR8

## Scope

### Files to Create
- (none)

### Files to Modify
- `src-tauri/src/tabs.rs` — `Tab::apply_mux_message`'s
  `MessageType::Snapshot`/`SnapshotRestore` handling (decode entry
  point), `Tab::dispatch_offthread_replay` (target/segments capture at
  dispatch time), and `Tab::resize`'s `pending_switch` re-dispatch branch
  (the block that re-invokes `dispatch_offthread_replay` when a resize's
  new `(cols, rows)` differs from the in-flight switch's captured
  `(cols, rows)`)

## Design

### FR7 — target-mismatch bypass drop during a resize race

Observed (see SPEC.md References): when a grid resize lands between a
snapshot's decode (which reads the CURRENT core size as the initial
target) and the eventual replay, the segments' tail dims (recorded
relative to the decode-time target) can mismatch the replay-time target
if a second resize supersedes the in-flight switch before it completes.
`stable_target_suffix_start` then correctly reports no matching tail run
against the NEW target — `k` becomes the full segment count, `split_at`
becomes the whole payload, `suffix_len` becomes 0 — defeating bypass.
Measured: 21.0 ms (raced) vs. 9.5 ms (unraced) for the same ~50 KB pane —
a real but smaller-magnitude regression than task0001's marker-cluster
case.

This is a genuine target change, not a data-integrity bug — the fix
should ensure the re-dispatch path (in `Tab::resize`'s
`pending_switch`-supersede branch) captures/derives target dims in a way
that keeps the segments' recorded tail consistent with whatever target is
actually used for the FINAL replay, rather than letting an intermediate,
already-superseded target's mismatch force a full non-bypass drain for
the final, correct target.

### FR8 — duplicate snapshot fetch for the same pane

Observed: two `Snapshot`/`SnapshotRestore` frames for the same pane can
be decoded ~1 ms apart (segment count differing by one between them),
with the first decode's replay result entirely discarded when the second
supersedes it before completing. Both decodes' work is wasted; only the
second's outcome matters.

Design a way to recognize that a newly-arrived frame for the same pane
supersedes an immediately-prior, not-yet-applied one for that pane
(whether still being synchronously processed or still in flight
off-thread) and skip doing the discarded work — e.g. detecting the
already-in-flight/just-applied state for that pane before starting a new
decode+dispatch, analogous to the existing off-thread
supersede-and-cancel logic in `dispatch_offthread_replay`, but covering
the case where the FIRST of the two frames would otherwise be fully
decoded and replayed before the second one arrives and supersedes it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A test reproducing a grid resize landing between a switch's
  dispatch and its completion (mirroring the measured decode
  target=207x51 → replay target=207x49 sequence) asserts the FINAL
  replay for the new target still engages bypass (or otherwise completes
  within the unraced baseline's order, ~9-10 ms class, not the ~21 ms
  raced-today class) when the segments' shape would otherwise support it
  at the new target.
- [ ] AC-2: A test confirms that when NO resize races the switch, behavior
  is unchanged from before this task (no regression to the already-fast
  unraced case).
- [ ] AC-3: A test reproducing two `Snapshot`/`SnapshotRestore` frames for
  the SAME pane arriving in immediate succession (before the first's
  replay would complete) asserts only one decode+replay actually runs to
  completion — the discarded one's work does not happen (verified by a
  counter/side-effect the test can observe, not by timing alone).
- [ ] AC-4: A test confirms two switches to DIFFERENT panes arriving in
  immediate succession are NOT deduplicated against each other — each
  pane's own switch completes normally (the dedup in AC-3 is scoped to
  same-pane frames only).
- [ ] AC-5: A test confirms a switch to the same pane that arrives well
  AFTER the previous one has already completed and been displayed (not a
  near-simultaneous race) is NOT dropped — i.e. AC-3's dedup does not
  turn into "ignore all repeat switches to a pane."

## Test Notes

- AC-1 can reuse/extend whatever existing test drives
  `Tab::resize`/`dispatch_offthread_replay`'s pending-switch-supersede
  branch (see the existing FR5 doc comments in `tabs.rs` around that
  branch) with a target-dims sequence that reproduces the mismatch.
- AC-3/AC-4/AC-5 need a way to count actual decode/replay invocations
  (not just observe final displayed state) to distinguish "deduplicated
  before doing the work" from "did the work twice but the result looks
  the same" — expose or reuse a test-only counter analogous to the
  existing `test_coalesce_parse_passes` pattern in `tabs.rs`.
- Follow the tdd-testing skill: write AC-1 and AC-3 as failing tests
  first (reproducing today's mismatch-triggered non-bypass fallback and
  today's double-decode respectively), then implement until all five
  criteria pass.
