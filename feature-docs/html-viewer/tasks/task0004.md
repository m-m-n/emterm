# Task Plan: task0004 — child HTML viewer window (serving + security policy)

## Goal

The `--html-viewer` child process opens a wry WebView window that renders the payload's HTML as the root document of a dedicated custom scheme, with JavaScript enabled, network blocked by CSP, basedir resources served through the resolver, http(s) links/popups delegated to the external browser, and no in-WebView navigation away from the document.

## Requirements

FR2, FR3, FR4, FR6, NFR1, NFR2

## Scope

### Files to Create
- `src-tauri/src/viewer/html_window.rs` — child window: payload read/delete, custom-protocol handler (document + resolver-backed resources + CSP header), navigation gate, popup delegation, WebViewHost setup

### Files to Modify
- `src-tauri/src/main.rs` — `--html-viewer` flag detection and child entry (mirrors the `--viewer` entry)
- `src-tauri/src/viewer/mod.rs` — module roster entries for `html_window` and `html_resolver` (task0003 ships the resolver file unregistered)
- `src-tauri/src/webview_host/mod.rs` — optional new-window (popup) handler on the host config
- `src-tauri/src/webview_host/linux.rs` — GTK/WebKitGTK wiring of the new-window handler
- `src-tauri/src/webview_host/windows.rs` — WebView2 wiring of the new-window handler

## Design

- Child entry mirrors the markdown viewer's: read the payload JSON (document + basedir), delete the temp file, build the WebViewHost pointed at the dedicated scheme's root URL (Decision D1/D2).
- Custom-protocol handler: the root path returns the payload HTML verbatim (no wrapper, no injected styles) with a CSP header per Decision D3 — sources restricted to the viewer scheme (both the native form and the WebView2 `*.localhost` rewritten form), inline script/style, and `data:`; no remote/connect sources. All other paths go through the task0003 resolver against basedir; denials return 403; responses carry nosniff.
- Navigation gate mirrors the existing viewer's predicate: allow only the viewer scheme (both platform forms); everything else is cancelled, and http(s) targets are handed to the safe external-open helper. In-page anchors do not trigger the gate (fragment-only changes).
- New-window handler (webview_host extension): a popup/new-window request never opens a WebView window; http(s) targets are delegated to the safe external-open helper. The hook is optional in the host config so existing viewer/settings windows are unaffected.
- JavaScript stays enabled (engine default); no sanitization of the document (Decision D3 — isolation is enforced at network/navigation/filesystem layers).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The `--html-viewer` flag with a payload path runs the HTML viewer entry; a missing/unreadable payload logs an error and exits without panicking.
- [ ] AC-2: The protocol handler serves the payload HTML verbatim at the root path with a CSP header whose source list contains only the viewer scheme forms, inline allowances, and `data:` — verified by unit tests on the response builder (header content and body identity).
- [ ] AC-3: Resource-path requests are answered through the resolver; a traversal path yields 403; an allowed CSS/image path under basedir yields 200 with the resolver's MIME.
- [ ] AC-4: The navigation predicate allows both platform forms of the viewer scheme and denies http(s)/file/javascript/data targets; the handler reports http(s) targets for external opening and denies in-WebView navigation (unit-tested at the predicate/decision seam, same style as the existing viewer's navigation tests).
- [ ] AC-5: The new-window decision path never allows an in-WebView popup and marks http(s) targets for external delegation (unit-tested at the decision seam; platform wiring compiles on Linux and cross-checks for Windows).
- [ ] AC-6: `viewer/mod.rs` module roster registers `html_resolver` and `html_window` under the GUI feature gate; the full test suite (`--lib`) passes.

## Test Notes

- AC-2/AC-3/AC-4/AC-5 are unit tests on pure decision/builder functions — keep the request handler, CSP builder, navigation predicate, and popup decision as side-effect-free functions so they are testable without a WebView (the existing `navigation_allowed` tests are the model).
- AC-1 is an integration-style test only if the existing `--viewer` entry has one; otherwise cover the payload-read failure path at unit level and note the manual scenario in VERIFICATION.md.
- Actual rendering / JS execution / Windows behavior are manual scenarios (VERIFICATION.md) — not TDD targets.

## Out of Scope

- CLI side (task0001), ingest/spawn (task0002), resolver internals (task0003 — consumed as-is).
- Windows cross-build execution (compile-correctness via cfg-gated code review; runtime check is a manual scenario).
- Any styling, toolbar, or viewer chrome — the document renders bare.
