# Task Plan: task0001 — `emterm html` CLI subcommand

## Goal

`emterm html <file>` validates the input file and emits a well-formed OSC 777 `html` display sequence (base64 chunked, basedir-tagged, tmux passthrough) to stdout, in both the GUI and CLI-only builds.

## Requirements

FR1, NFR2

## Scope

### Files to Create
- `src-tauri/src/cli/html.rs` — subcommand handler: read / canonicalize / validate / encode / emit (mirrors the responsibilities of the markdown handler)
- `src-tauri/tests/fixtures/html/sample.html` — integration-test fixture

### Files to Modify
- `src-tauri/src/cli/mod.rs` — module roster, clap subcommand registration, dispatch arm for `html`
- `src-tauri/src/cli/encoding/osc.rs` — OSC 777 frame generator for the `html` kind (begin with basedir / seq-numbered chunks / end)
- `src-tauri/src/cli/messages.rs` — bilingual (En/Ja) about/argument strings for the subcommand
- `src-tauri/src/cli/validation/file.rs` — extension-check helper if not kept local to the handler
- `src-tauri/tests/cli_subcommands.rs` — integration tests for the new subcommand

## Design

- Processing flow: canonicalize path → verify regular file → verify extension is `.html` or `.htm` case-insensitively → verify size ≤ 10MB → read bytes → base64-encode → split into 128KB chunks → compute basedir (canonical parent directory) → build OSC 777 frames (kind `html`) → wrap in tmux DCS passthrough when inside tmux → write to stdout.
- Validation failures map to the existing `CommandError` variants (file-not-found / not-a-file / too-large / read-error); the extension failure uses an appropriate existing variant or a new one following the same pattern, printed bilingually to stderr with non-zero exit.
- Frame grammar and parameter sanitization follow the shared-component contract in IMPLEMENTATION.md (same verb grammar as the markdown kind).
- Everything in this task must compile under `--no-default-features` (CLI layer depends only on always-built code).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The OSC generator produces frames for single-chunk, multi-chunk, with-basedir, and without-basedir inputs whose kind field is `html` and whose verb sequence is begin → chunks (seq-ordered) → end; basedir values containing semicolons or control characters are sanitized.
- [ ] AC-2: Extension validation accepts `.html`, `.htm`, `.HTML`, `.HtM` and rejects other extensions (including no extension) with a non-zero exit and a stderr message.
- [ ] AC-3: A file of exactly 10MB is accepted; a file one byte over is rejected with the size error.
- [ ] AC-4: A missing path and a directory path produce the corresponding error variants (non-zero exit, stderr message).
- [ ] AC-5: Integration tests (`tests/cli_subcommands.rs`): a valid `.html` fixture emits the sequence to stdout and exits 0; missing-file and directory inputs exit non-zero — mirroring the existing markdown test trio.
- [ ] AC-6: `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features` passes.

## Test Notes

- AC-1..AC-4 are unit tests inside the new handler / generator modules (same style as the existing markdown/osc unit tests).
- AC-5 reuses the integration-test patterns already present for markdown (spawn the binary, assert exit code and stream contents).
- Boundary file for AC-3 can be generated at test time (temp file); do not commit a 10MB fixture.

## Out of Scope

- GUI-side reception, routing, rendering (task0002 / task0004).
- Any change to the markdown/json/yaml/image subcommands.
- Interactive stdin loop (the markdown one is also intentionally non-interactive).
