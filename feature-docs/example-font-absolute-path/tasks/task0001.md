## Design

### 1. フォント取得元の実行時解決 (FR1, FR2, NFR2)

現在は 2 ファイル・計 3 箇所で、開発者マシン固有の絶対パス文字列をそのままファイル読み込みへ
渡している。これを IMPLEMENTATION.md「フォント取得元の解決規約」に従って置き換える。

- 前提条件: `scripts/fetch-fonts.sh` が `src-tauri/assets/fonts/` に
  `Inconsolata-Regular.otf` / `Inconsolata-Bold.otf` を配置済みであること (A1)。
- 事後条件: probe は crate マニフェストディレクトリ起点で解決した位置からフォントを読む。
  読めなかったときに即座に落ちる挙動と、成功時の診断出力の書式は変わらない。
- パス組み立ては結合 API に委ね、区切り文字を直書きしない (NFR2)。Linux / Windows 双方で
  同じソースが成立すること。
- `font_select_probe.rs` はシステムフォント列挙のみでフォントファイルを直接読まないため、
  この節の対象外 (A4)。

### 2. 実行手順コメントの更新 (FR3, FR4)

2 ファイルのファイル先頭コメントに残る実行手順を、プロジェクトルートから実行する現行形へ
書き換える。probe が何をするかを説明している部分は変更しない。

- `bold_raster_probe.rs` の実行手順:
  `CARGO_TARGET_DIR=src-tauri/target cargo run --manifest-path src-tauri/Cargo.toml --example bold_raster_probe`
- `font_select_probe.rs` の実行手順:
  `CARGO_TARGET_DIR=src-tauri/target cargo run --manifest-path src-tauri/Cargo.toml --example font_select_probe -- Inconsolata`
- `m_placement_probe.rs` は現在ファイル先頭コメントを持たない。ここへコメントを新設しない (FR2)。

### 3. ソース走査統合テスト (FR5, NFR1)

`src-tauri/tests/examples_source_hygiene.rs` を追加する。

- 入力: `src-tauri/examples/` ディレクトリ配下の Rust ソース群。ディレクトリ位置はテスト実行時に
  crate マニフェストディレクトリ起点で解決する（区切り文字を直書きしない点は 1. と同じ規約）。
- 処理フロー:
  1. examples ディレクトリのエントリを列挙し、拡張子が Rust ソースのものを集める
  2. 集まった件数が 0 なら失敗させる（走査先の解決ミスや対象消失を緑と報告しない）
  3. 各ファイルをテキストとして読む
  4. 絶対パス指標 `/home/` を含むファイルを違反として集める
  5. 旧レイアウト指標 `native-poc/` を含むファイルを違反として集める
  6. 違反があれば、どのファイルのどの行かが分かる形で失敗させる
- 検証は独立した 2 ケースに分ける（絶対パス = TS1、`native-poc/` = TS2）。どちらが壊れたかを
  単体で切り分けられるようにする。
- フォントファイルの存在確認、example の実行、ネットワーク取得のいずれも行わない (NFR1)。
- 走査対象は examples 配下のみ。判定文字列そのものを保持する本テスト自身は対象に含めない
  （IMPLEMENTATION.md「走査スコープ」）。

### 4. 触らない範囲 (FR6, NFR3, NFR4)

`src-tauri/src/render/font/resolver.rs` のコンパイル時埋め込み、`scripts/fetch-fonts.sh`、
`src-tauri/Cargo.toml` の `[[example]]` 定義と feature 構成はいずれも変更しない。
新規依存クレートを追加しない。3 つの probe の診断出力の書式と意味を変えない。

## Test Notes

- AC-4 / AC-5 は新規統合テストそのものが検証手段。TDD の順序としてこのテストを先に書き、
  examples が未修正の状態で赤になることを確認してから examples を是正して緑にする。
- AC-1 / AC-3 の大部分はこの走査テストが機械的にカバーする。個別 probe に対する追加のユニット
  テストは作らない（probe は診断用の実行バイナリで、出力の目視が本来の使い道のため）。
- AC-2 の「コメント新設なし」と AC-1 の「取得元がマニフェスト起点であること」はテキスト走査では
  表現しにくいため、差分レビューで確認する項目として残す。
- AC-6 はビルドと既存テスト実行で確認する。AC-7 は実フォントの取得が要るため、機械テスト化せず
  VERIFICATION.md の手動項目 (TS5) に載せる。
- 走査テストは自身を対象に含めないため、テスト内に判定文字列を持っていても自己検出で赤にならない。
  この性質はテスト設計時に意識して保つ。
