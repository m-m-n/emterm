# Task Plan: task0001 — term_core retroactive merge of zero-width characters

## Goal

Standalone-arriving zero-width characters (VARIATION SELECTOR / COMBINING)
merge into the previously written grid cell instead of overwriting the cursor
cell, with VS16-driven retroactive width-2 expansion — fixing both keycap
clusters (5️⃣) and general combining characters (é).

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2

## Scope

### Files to Create

(none)

### Files to Modify

- `crates/term_core/src/print_handler.rs` — the slow-path handling of
  width-0 characters; retroactive merge, widening, drop logic; unit tests
- `crates/term_core/src/terminal_core.rs` — state needed to track the
  "most recently written cell" and its invalidation
- `crates/term_core/src/cell.rs` — cell content append support if the
  existing set/overflow API is insufficient for appending codepoints

## Design

### Current behavior (defect)

`write_grapheme_to_grid` treats a width-0 character like any other: it
overwrites the cell at the cursor without advancing, so the next printed
character destroys it. `handle_print`'s grapheme buffer only starts on
Extended_Pictographic / Regional Indicator bases, so digit-based keycap
clusters never enter the buffered path.

### Target behavior

1. **Merge (FR1)**: when a width-0 character (classified VARIATION_SEL or
   COMBINING by the term_core width tables) arrives and the grapheme buffer
   is empty, append its codepoint to the string content of the most recently
   written cell. Cursor, colors, flags of that cell are untouched; the row is
   marked dirty. The cursor does not move (except case 2).
2. **Widen on VS16 (FR2)**: if after the merge the cell's cluster contains
   VS16 (U+FE0F) and the cell is width 1, retroactively expand it to width 2:
   the following cell becomes a spacer (same shape the existing wide-char
   write produces), and the cursor advances by 1. If the base cell is at the
   last column, apply the same wrap semantics the existing wide-char path
   uses at end of line (the base cell relocates via wrap; state must stay
   consistent). Without VS16, width stays 1.
3. **Spacer traversal (FR3)**: if the most recently written cell position
   holds a wide-cell spacer, the merge target is its base cell (one column
   left).
4. **Drop (FR4)**: if there is no valid merge target — nothing written yet on
   this screen, or the tracked position was invalidated — discard the
   character entirely: no grid write, no cursor movement.

### Most-recently-written-cell tracking

A tracked grid position (updated on every successful cell write in the print
path). Invalidation rules — tracking resets to "none" on: explicit cursor
movement operations, scrolling that displaces the tracked row, screen/line
erase covering the tracked cell, resize/reflow, and alternate-screen or
viewport switches. When invalid, FR4 applies. (Conservative invalidation is
acceptable: a dropped combining char is strictly better than corrupting an
unrelated cell.)

### Interaction with the existing grapheme buffer

The buffered path (ExtPict base) keeps priority: the continuation conditions
in `handle_print` are evaluated first, unchanged. Retroactive merge applies
only to width-0 characters that today fall through to the standalone slow
path. `flush_grapheme_buffer` and its width rules are untouched (NFR1).

### Storage constraint

Appending may push the cell string past the inline cell capacity; the
existing overflow mechanism (overflow map + index) must be kept consistent
when content grows (both directions: inline → overflow).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Input `5 FE0F 20E3` followed by text yields one base cell whose
      content is the full 3-codepoint cluster, `width == 2`, a spacer cell to
      its right, and the following text starting after the spacer.
- [ ] AC-2: Input `5 20E3` followed by text yields one base cell containing
      both codepoints with `width == 1`, and the following text in the next
      column.
- [ ] AC-3: Input `e 0301` followed by text yields one cell containing both
      codepoints; the accent survives subsequent writes.
- [ ] AC-4: A width-0 character arriving with no valid merge target (start of
      screen / invalidated tracking) leaves the grid unchanged and does not
      move the cursor.
- [ ] AC-5: A width-0 character arriving after a wide (width-2) character
      merges into the wide base cell, not the spacer.
- [ ] AC-6: VS16 merge onto a base cell in the last column produces a
      consistent grid per the existing wide-char end-of-line semantics
      (no spacer orphaned across the line boundary, cursor state valid).
- [ ] AC-7: All pre-existing term_core tests pass unchanged (grapheme buffer
      / ZWJ / ExtPict paths).
- [ ] AC-8: A run of multiple combining characters on one base cell stays
      consistent with the cell overflow mechanism (content readable back).

## Test Notes

- All criteria are unit-testable by driving TerminalCore with byte input and
  asserting grid cell content / width / cursor position (existing test style
  in print_handler.rs).
- AC-6 needs both auto-wrap on and off variants.
- AC-7 is the regression gate: run the full term_core lib test suite.
- NFR2 has no automated benchmark: keep the ASCII fast path untouched;
  reviewers verify by inspection.

## Out of Scope

- Renderer-side changes (VS16 stripping is task0002).
- Any change to `flush_grapheme_buffer` or the ExtPict grapheme-buffer path.
- Width configuration knobs (`unicode_version` equivalent).
- Overflow/oversize glyph drawing.
