# Task Plan: task0001 — Close the ac8 allowlist use-line and terminator gaps

## Goal

The ac8 allowlist checker in `src-tauri/src/program_status/tests.rs`
recognizes the use-line forms it currently misses (whitespace variants,
zero-whitespace `pub(...)use`, a bare `use` line, a leading attribute on the
same line) and allows `super::agent_status` only before an explicit
terminator set. Each closed form has a rejection self-test, and the existing
allowed set and the ac8 module test keep passing.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
None.

### Files to Modify
- `src-tauri/src/program_status/tests.rs` — the use-line recognizer
  (`ac8_use_path`), the judgement that follows `super::agent_status`
  (currently `ac8_continues_identifier`), the line scan in
  `ac8_check_allowlist`, the doc comments describing Rule A / Rule B, and new
  checker self-tests.

## Design

All components are test-only helpers inside `tests.rs`. `ac8_violation` and
the Rule B root list (`std`, `base64`, `self`, `super`) are unchanged.

### Components

| Component | Responsibility | Contract |
|---|---|---|
| Use-line recognizer (`ac8_use_path`) | Decide whether one trimmed line is a use line, and yield what follows the `use` keyword | Pre: a line with leading and trailing whitespace removed. Post: exactly one of three outcomes — (a) not a use line; (b) a use line, with the text after `use`; (c) a bare use line (nothing follows `use`). Comment lines, lines without a `use` keyword, and lines where `use` only begins a longer identifier (e.g. a field named `user` or `useful` after `pub`) are outcome (a). |
| Leading-attribute skip | For a line that starts with `#[`, expose the text after that attribute to the recognizer | The attribute ends at the `]` that closes the opening `#[`, with square brackets nested inside the attribute balanced (parentheses inside it, as in `cfg(all(...))`, do not end it). The remainder, with leading whitespace skipped, is what the recognizer examines. A line whose opening `#[` has no closing bracket on the same line is outcome (a). |
| Terminator judgement (replaces `ac8_continues_identifier`) | Decide whether one occurrence of `super::agent_status` is allowed | Allowed exactly when the text right after the path, on the same scanned line, is empty, or begins with `::`, `;` or `,`. Every other following character is a violation — whitespace, `)`, a single `:`, U+0301 and any other non-ASCII character included (FR5). The identifier-continuation helper is removed; no unused helper remains. |
| Line scan (`ac8_check_allowlist`) | Apply Rule B to every recognized use line and Rule A to every line, returning violations in source order | Carries one piece of state across lines: a pending bare use. See the flow below. |

### Use-line recognition rules

Whitespace means any character SPEC FR1 classifies as whitespace (space,
tab and every other Unicode whitespace character).

1. Visibility (optional): the `pub` keyword, followed by either a
   parenthesized qualifier `(...)` directly, or one or more whitespace
   characters optionally followed by a parenthesized qualifier. The
   qualifier ends at its first `)`, as today. `pub` followed directly by
   any other character is not a visibility keyword (outcome (a)).
2. After `pub` plus whitespace, or after the closing `)` of a qualifier,
   zero or more whitespace characters may precede `use` (FR1, FR2).
3. The `use` keyword is followed either by the end of the line (outcome
   (c), FR3) or by one or more whitespace characters (outcome (b), FR1).
   `use` followed by any other character is outcome (a).
4. When the line starts with `#[`, rules 1-3 apply to the remainder after
   the leading-attribute skip instead of the whole line (FR4).

### Line scan flow (per line, in source order)

1. Trim the line.
2. When a bare use is pending and the trimmed line is blank, the bare use
   stays pending.
3. When a bare use is pending and the trimmed line is non-blank, the first
   path segment of that line is the use root. Rule B is applied to it with
   this line as the offending line, and the pending state is cleared.
4. Otherwise the recognizer runs on the trimmed line. Outcome (b): Rule B
   is applied to the first path segment of the text after `use` (leading
   whitespace skipped), with the whole trimmed line — leading attribute
   included — as the offending line. Outcome (c): a bare use becomes
   pending.
5. Rule A runs on every line as today, with the terminator judgement above
   deciding each `super::agent_status` occurrence.

Within one line, a Rule B violation precedes Rule A violations (current
order). A bare use's Rule B violation is reported at its root line, so
source order holds.

### Violation text (NFR3)

Every violation for the newly closed forms is built with `ac8_violation`.
The offending line text it carries is the whole trimmed line (for FR1, FR2,
FR4 and FR5 inputs), or the trimmed root line (for FR3 bare-use inputs).

### Documentation and existing tests

- The doc comments of the recognizer and of `ac8_check_allowlist` describe
  the recognized forms and the terminator set; no wording about
  identifier continuation or a path-segment boundary remains.
- Existing ac8 and `ac8_allowlist_*` tests keep their names and expected
  outcomes. A comment inside them that describes the old
  identifier-continuation judgement is updated to the terminator wording.
  No existing test is renamed, so no record outside this file needs an
  update (NFR1).

## Test Notes

- Notation in the criteria above: `<TAB>` is U+0009, `<LF>` is a line feed
  (U+000A), `<U+0301>` is the combining acute accent. The test sources
  write them with the language's string escapes, as SPEC's Test Scenarios
  do.
- AC-1 to AC-5 are unit tests that feed synthetic sources to
  `ac8_check_allowlist`, reusing `ac8_assert_allowed` /
  `ac8_assert_rejected` and the existing test-attribute style (NFR2).
- Naming: new tests use the prefix `ac8_gaps_acN_`, where N is the AC
  number in this plan, under a new section comment naming this feature,
  matching the existing per-feature section comments.
- RED confirmation: every rejected input of AC-1 to AC-4 currently yields
  no violation, so each new rejection test fails before the change. AC-6
  is a regression guard and is green before and after.
- AC-5 runs over the same rejected inputs as AC-1 to AC-4. The bare-use
  inputs of AC-2 span several lines, so they cannot follow the shape of
  `ac8_allowlist_ac6_every_violation_states_the_gui_feature_invariant`,
  which compares each violation against the whole trimmed snippet; they
  assert against their root line instead.
- AC-7's file and dependency conditions are checked on the task branch
  diff; its test command is the project's approved test command.
- `tests.rs` is never a scan target of the ac8 test, so `crate::` /
  `super::` text inside new snippets does not reach
  `ac8_the_module_uses_only_always_built_crates`.

## Out of Scope

- Any change to a file other than `src-tauri/src/program_status/tests.rs`
