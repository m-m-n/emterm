# Task Plan: task0001 — The tracker follows RIS and compound DECSET in a mismatched state

## Goal

`AltSpanTracker` follows term_core's screen through a RIS, through an `ESC c`
in a designator slot, and, while its two screens disagree, through a DEC
private mode set or reset that carries 47, 1047 or 1049 in a form outside the
six switch patterns. This holds in one read and across any read boundary. As
a result, a mux pane ends in the plain tab's OSC 7501 table and OSC 777 state
for every SC-1y row and every delivery that the row lists.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5

## Design

### §1 Terms and what stays

- **Client rule**: term_core's view of the screen, which the extraction and
  the feed scanner's RIS tracking also follow. A recognized switch pattern
  switches screens, except when its `ESC` sits in the designator slot right
  after `ESC (` or `ESC )`.
- **Shadow rule**: the shadow parser's view of the screen. Every `ESC` aborts
  what came before it, so a pattern in a designator slot also switches. Only
  ?1049 and ?47 switch.
- **Mismatched state**: the tracker's client-rule screen differs from its
  shadow-rule screen.
- **Live ESC**: an `ESC` that the scan reaches outside a designator slot.

The per-read structure of `advance` stays:

1. Adopt the parser's state when it differs from the shadow-rule screen that
   the last read ended on.
2. Resolve the carried item against the read's first bytes.
3. Scan the rest of the read.
4. Record the new carried item.
5. Cross-check the shadow-rule screen with the parser's state after the read.

The signature of `advance`, its caller in `pty_reader_loop`, and its result
contract stay the same. The result contract is: read-relative spans,
ascending, non-overlapping, non-empty, and within the read.

### §2 RIS (FR1, FR2, FR3)

1. **RIS under the client rule (FR1).** A live `ESC` immediately followed by
   `c` is a RIS. At the `c`:
   - Both screens become the main screen.
   - Every carried item is cleared: the partial switch, the designator wait
     and the CSI parse state.
   - If the client-rule screen was the main screen, the open live run
     continues, so the `ESC c` bytes stay live and match the bulk walk of
     the stream.
   - If the client-rule screen was the alternate screen, the live run opens
     right after the `c`.
2. **RIS split by a read boundary (FR2):**
   - A carried lone live `ESC` followed by a read that starts with `c` is
     rule 1 at the read's first byte.
   - A carried partial of two or more bytes (for example `ESC [`) followed
     by `c` is not a RIS. This is the current divergence path.
   - When a carried partial diverges at a read that starts with `ESC c`,
     that `ESC c` is rule 1. For example, `ESC [?10 | ESC c`.
3. **`ESC c` in a designator slot (FR3).** The `ESC` sits in the designator
   slot in one read, across `ESC ( | ESC c`, or across `ESC ( ESC | c`.
   - Under the client rule this is not a RIS: the client-rule screen and the
     live run do not change.
   - Under the shadow rule it is a RIS: the shadow-rule screen becomes the
     main screen, and any CSI parse state is discarded.
   - When the parser agrees, no adoption follows.
4. **Agreement with the scanner.** For any stream and any delivery, rule 1
   fires exactly at the positions where `AgentStatusFeedScanner`'s RIS
   tracking emits its reset item.

### §3 DEC private CSI parse (FR5)

1. **Start.** A parse starts at a live `ESC` followed by `[` and `?`, when
   the bytes from that `ESC` do not complete one of the six switch patterns.
   Those patterns keep their current handling.
2. **Carried fields (O(1), NFR1):**
   - whether `ESC [ ?` has been seen
   - the value of the parameter being read
   - whether an earlier finished parameter was 47, 1047 or 1049

   The value saturates at a cap no lower than term_core's own parameter cap
   (9999), so a saturated value is never 47, 1047 or 1049. Digit runs of any
   length cannot overflow.
3. **Bytes:**
   - Digits and `;` are parameter bytes. An empty parameter is 0, and
     leading zeros do not change the value.
   - `h` and `l` are the terminators.
   - Any other byte discards the parse without detection: `ESC`, CAN, SUB,
     `:`, an intermediate byte, a private marker, or any final byte other
     than `h` and `l`. An `ESC` then goes on to its own handling (RIS,
     designator slot, switch pattern, or a new parse).
4. **Continuing from a diverging partial.** A carried live partial can
   diverge while its held bytes are a prefix of a DEC private CSI: `ESC`,
   `ESC [`, `ESC [ ?`, or `ESC [ ?` followed by digits. The parse then
   continues as if the held bytes came right before the read's first byte.
   Examples: `ESC [?104 | 9;1h`, `ESC [?1049 | ;1h`, `ESC | [?1;1049h`. A
   designator partial never starts a parse, because its CSI is text for the
   client (SPEC A7).
5. **A read that ends inside a parse** carries the parse state. The parse
   never changes a span by itself: the CSI bytes are live exactly when they
   would be live today. A read without a detection therefore gets exactly
   today's spans.
6. **Clearing.** The parse state is cleared at a RIS, at every adoption
   (including the start-of-read adoption after a parser rebuild), and at a
   detection.

### §4 Compound detection and the end of a detection read (FR4)

1. **Detection.** A parse can reach `h` or `l` with 47, 1047 or 1049 among
   its finished parameters. If the tracker is in a mismatched state at that
   point, the read is a detection read. The client-rule screen then takes
   the terminator's direction: `h` means the alternate screen and `l` means
   the main screen. This follows term_core, which sets the alternate-screen
   mode for every 47, 1047 or 1049 parameter. The scan continues with that
   client-rule screen, so a later switch pattern or RIS in the same read
   still applies.
2. **End of a detection read:**
   - The read's spans are the A3 fallback, judged on the client-rule screen
     at the read's end. If that screen is the main screen, the spans are the
     whole read. Otherwise there are none.
   - The shadow-rule screen takes the parser's state after the read.
   - The client-rule screen keeps the state the scan ended in.
   - Every carried item is cleared.
   - The test-visible adoption counter counts one adoption.
   - The ordinary post-read cross-check is not applied to that read.
3. **Matched state.** No detection happens (SPEC A2, FR8). Today's behavior
   stays, including the existing cross-check fallback for a compound that
   moves the shadow parser.
4. **Designator-slot CSI.** A designator-slot CSI (SPEC A7) is never parsed.
   The existing cross-check handles it as today.

### §5 Why not FR4's literal adoption (recorded deviation)

FR4's literal reading is "adopt the parser's state after the read for both
screens; fall back on the screen before and after the read". It disagrees
with the plain tab in three AC5 combinations:

| Mismatch before the compound | Compound | term_core after | Parser after | Literal reading | This design |
|---|---|---|---|---|---|
| client alternate, shadow main (M1) | `?1;1047h` | alternate | main | client becomes main, so a later mark counts | client stays alternate |
| client main, shadow alternate (M2) | `?1;1047l` | main | alternate | client becomes alternate, so a later mark is dropped | client stays main |
| client main, shadow alternate (M2) | `?1;1049l`, mark in the same read | main | main | the fallback is empty because the parser started on the alternate screen, so the mark is dropped | whole read, so the mark is live |

In a mismatched state, each rule's screen before the read is the main screen
under one rule and the alternate screen under the other. Judging "before" by
either rule alone empties the read of a leave whose mark follows in the same
read. The client-rule screen at the read's end is the screen the mark that
follows the compound is shown on. The other seven AC5 combinations give the
same result as the literal reading. Marks before the compound in the same
read stay inexact, as SPEC A3 accepts.

### §6 Unchanged (FR8, A4)

The following stay unchanged:

- the main-buffer extraction
- the switch-pattern list and the next-live-toggle walk that the extraction
  shares with the tracker. RIS and compounds are added to the tracker's own
  scan only, never to that list or that walk.
- `to_write`, `cuts`, and the fallback write of nothing
- `ScrollbackWriteFilter`
- `AgentStatusFeedScanner`, including its RIS tracking and its cut-liveness
  and tail-liveness rules
- `pty_reader_loop`
- term_core

## Acceptance Criteria (MANDATORY)

Notation (E(P), L(P), A, DS, DC, R, CC, C1h, C1l, Crh, C7h, C7l, C0h, Ceh,
M1, M2) follows IMPLEMENTATION.md, Parity corpus extension (SC-1y).

- [ ] AC-1 (FR1; TM-2): RIS in one read.
  - Starting states:
    - the main screen
    - an alternate screen where both rules agree (after E(1049))
    - the client rule on the alternate screen and the shadow rule on the
      main screen (after M1, and after E(1049) DS L(1049))
    - the client rule on the main screen and the shadow rule on the
      alternate screen (after M2)
  - In each case, a read of R followed by A BEL gives a live mark. A mark
    in a later read is live, and no adoption occurs.
  - On the main screen, the live run is not interrupted at R: the read's
    spans equal the oracle (Test Notes).
- [ ] AC-2 (FR2; TM-2): split RIS.
  - Deliveries: each AC-1 stream with every single cut, every pair of cuts
    and one byte per read.
  - Each read's spans equal the oracle, with no adoption.
  - A cut between `ESC` and `c` still gives a RIS.
  - M1 CC A BEL cut at `ESC [ | c` gives no RIS: the mark stays not live,
    and a mark in a later read is not live either.
  - `ESC [?10 | ESC c` and `ESC [?1;10 | ESC c`, each after M1, give a RIS:
    the mark after it is live.
- [ ] AC-3 (FR3; TM-2): an `ESC c` in a designator slot.
  - Streams: E(1049) DS R A BEL and E(1049) DC R A BEL, in one read and with
    every single cut (including `ESC ( | ESC c` and `ESC ( ESC | c`).
  - The mark is not live, a mark in a later read is not live, and no
    adoption occurs.
  - The real shadow parser (vt100) ends on the main screen after E(1049)
    DS R (pin for SPEC A1).
- [ ] AC-4 (FR4; TM-2): a compound in one read. Each compound is delivered
  as three reads: the setup, then a read holding the compound and A BEL,
  then a read holding A BEL.
  - Mismatched setups (M1, M2), with compounds C1h, C1l, Crh, C7h, C7l, C0h
    and Ceh:
    - The second read's spans are the whole read for a final `l` and none
      for a final `h`.
    - Exactly one adoption is counted.
    - The third read's mark is live exactly when the final byte is `l`.
  - Matched setup (E(1049)), with the same compounds:
    - C1l gives the existing fallback (no span) with one adoption, and the
      third read's mark is live.
    - Every other compound gives no span, no adoption, and a third-read mark
      that is not live.
  - Designator-slot compounds (DS C1h and DS C1l, after M1 and after M2):
    - No detection occurs.
    - Exactly one adoption is counted when the shadow parser changes screen
      (M1 then DS C1h, and M2 then DS C1l). Otherwise none is counted.
    - The third read's mark is live exactly after M2.
  - The real shadow parser follows C1h and ignores C7h (pin for SPEC A1 and
    TS3).
- [ ] AC-5 (FR5; TM-2): a split compound.
  - Stream: each mismatched AC-4 case as one stream: M1 or M2, then the
    compound, then A BEL, then A BEL.
  - Deliveries: every single cut, every pair of cuts and one byte per read.
  - In each delivery:
    - Exactly one adoption is counted.
    - The read that holds the compound's final byte gives the whole read
      for a final `l` and no span for a final `h`.
    - Every mark completed in a later read is live exactly when the final
      byte is `l`.
  - `ESC [?104 | 9;1h` and `ESC [?1049 | ;1h` are among the detected cuts.
  - After M1 and after M2, no detection and no adoption occur, and every
    read's spans equal those of the tracker without the CSI parse, for
    these inputs:
    - `ESC [?1;10` followed by CAN, by SUB, or by `ESC [0m`, and then `49h`
    - `ESC [?1049$p`
    - `ESC [?1;1049m`
- [ ] AC-6 (NFR1; TM-1): robustness. Inputs, run in a matched state and in
  both mismatched directions:
  - every prefix of C1h, Crh, C7l, C0h and Ceh, followed by a read holding

  - a parameter of more than 20 digits
  - parameters whose decimal value is 1049 plus a multiple of 65536 or of

## Test Notes

- **Where the tests go**: the tracker tests go into
  `tests/altscreen_split_read.rs` beside the existing ones. They reuse its
  rig (a tracker beside a real shadow parser), its `deliveries` and its
  well-formedness check. AC-7 goes into `daemon/tests.rs`, next to the
  K16-K37 list.
- **Oracle for AC-1 and AC-2**: `extract_main_buffer` does not handle RIS,
  so the expected spans come from a test-side walk of the whole stream
  under the client rule. The walk follows the extraction's rules, with RIS
  as a return to the main screen whose own bytes keep the liveness of the
  screen before it. It is restricted to each read, without the read's
  undecided tail, following the existing oracle convention. Literal
  expectations are equally acceptable for short cases.
- **Expectations for AC-4 and AC-5**: state them explicitly per case:
  - the detection read is the whole read or nothing
  - the reads before it keep today's spans
  - the reads after it follow the client-rule screen that the final byte set
- **TDD order**: write the AC-7 rows for K38 (reproduction 1) and K49 cut at
  10 (reproduction 2) first. Both must fail on the unmodified tracker: K38
  ends with root `working`, and K49 ends empty.
- **Edge cases worth naming**:
  - K41 (`ESC [ | c`)
  - `ESC ) ESC c`
  - Crh cut inside `?1049`
  - a compound followed by a switch pattern in the same read
  - a detection read that ends with a partial switch, which is cleared
    (IMPLEMENTATION.md Open Questions)
- **Plan deviation**: report a failing existing test as a plan deviation.
  Do not edit it. This also applies when the random differential test's
  compared count falls to 2000 or below.
