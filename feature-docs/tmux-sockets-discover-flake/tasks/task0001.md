## Design

### レースの機序（防御対象）

1. 現行テストは stale 側の listener を bind した直後に in-process で drop する（`src-tauri/src/tmux_sockets.rs:555`）。
2. 並行テストスレッドの `Command::spawn` は、clone から exec までの窓の間、親プロセスの fd テーブルのコピーを一時的に保持する（close-on-exec は exec 時に働くため、この窓の中では効かない）。
3. clone が drop より前・probe が exec より前という順序になると、drop 済み listener の fd コピーが子プロセス側に生存し、カーネルは当該ソケットを listen 中として扱い続ける。
4. その結果 `probe_unix_socket`（`src-tauri/src/tmux_sockets.rs:105`）の connect が ECONNREFUSED にならず成功し、stale が live と誤判定されてアサーションが失敗する。

### 決定: fd 寿命に依存しない stale fixture

stale の「listen していない」という性質を、テストプロセス内の fd 寿命ではなく、ソケットのカーネル状態そのものに持たせる。

- stale 用のソケットファイルは、**アドレスに束縛するだけで一度も listen 状態に入れない**方法で作る。stream 型の Unix ドメインソケットは listen 状態に入らない限り接続要求を常に拒否するため、fd のコピーが clone-to-exec 窓に何個生存していても connect は成功しない。probe の判定は決定的に「stale」になる。
- fixture 構築に使った fd は構築後に閉じる。閉じた後もソケットファイルはディスク上に残り（close は unlink しない）、socket 型のまま接続不能である。すなわち「tmux サーバーが socket ファイルを残して死んだ」状態の観測的定義（ディスク上の socket 型ファイル + listener 不在）を従来どおり満たす。
- 既存アサーション（stale ファイルがディスク上に残ること、`discover_in` の結果が live のみであること）は維持または強化し、弱めない（FR2）。
- fixture 構築部に、fork 窓レースの機序と「bind 後に listener を drop する」パターンへ戻してはいけない理由を説明するコメントを残す（将来の巻き戻り防止）。既存の「tmux サーバーが socket を残して死んだ状態のモデル」という説明意図も引き継ぐ。

fixture の契約（事前条件 / 事後条件）:

- 事前条件: テスト用一時ディレクトリが存在し、対象パスに既存エントリがない。
- 事後条件: 指定パスに socket 型ファイルが存在し、そのソケットへの接続試行はどの時点・どのプロセス状態でも拒否される。テストプロセスの fd テーブルに、当該ソケットを listen 状態にしうる fd が一度も存在しない。

### 不採用の代替案（理由つき）

- 完全に終了した子プロセス内で listener を bind → drop → exit する: 決定的だが、ソケットを bind できる外部ヘルパーの導入が必要で複雑。
- probe が失敗に転じるまで再試行する: 別の並行 spawn が新しい clone-to-exec 窓を開くと再び connect が成功しうるため、非決定性が残る。
- スイート全体の逐次化（`--test-threads=1`）: NFR1 が明示的に禁止。なお、レースの相手はモジュール外のテストの spawn でもあるため、モジュール内テストのみの直列化では解消しない。
