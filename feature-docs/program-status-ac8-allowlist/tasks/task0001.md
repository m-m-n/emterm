# Task Plan: task0001 — ac8 guard: explicit allowlist checker for project-module paths

## Goal

The ac8 guard in the program_status unit tests decides allowed project-module
paths through a test-side checker with the explicit allowlist
`super::agent_status`, instead of a `crate::` substring check, and its failure
message states the invariant it protects: program_status builds without the
`gui` feature.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `src-tauri/src/program_status/tests.rs` — add the checker function and its self-tests to the AC-8 section, and rewrite the body of the ac8 dependency test to apply the checker.

## Design

### Placement

Everything lives in the AC-8 section of tests.rs (the block under the existing
"AC-8: build" divider), next to `ac8_the_module_is_declared_without_a_gui_gate`.
The checker is test-only code. Production files are not touched (NFR1). Only
std facilities are used and no crate is added (NFR3).

### Checker contract

| Item | Contract |
|---|---|
| Input | One source text: the full text of a Rust source file, or a synthetic snippet of one or more lines |
| Output | The list of violations found, in source order. An empty list means the source satisfies every rule |
| Violation | A human-readable description (see "Violation description" below). One offending line may yield more than one violation; for example a `use crate::...` line breaks both rule A and rule B |
| Purity | No I/O, no logging, no panic for any input text: empty text, text without a trailing newline, and non-ASCII text included |

### Rule A — project-module path occurrences (FR1, FR2)

1. Every occurrence of the text `crate::` and every occurrence of the text
   `super::` anywhere in the source is examined: use lines, other code lines,
   comments and string literals alike. Occurrences are found as plain text,
   with no boundary requirement before them (fail-closed).
2. A `crate::` occurrence is always a violation.
3. A `super::` occurrence is allowed only when the text right after it is
   `agent_status` and that path segment ends there: either the source text
   ends, or the next character cannot continue an identifier. Letters, digits
   and `_` continue an identifier, non-ASCII letters and digits included.
   A following `::` satisfies this. Every other `super::` occurrence is a
   violation, including:
   - `super::agent_status_exit_latch` (a prefix match only),
   - `super::{...}` (a grouped import, rejected fail-closed per SPEC A5),
   - `super::super::...`,
   - `super::` followed by any other module name.

### Rule B — external roots on use lines (FR3)

1. A use line is a line whose text, with leading and trailing whitespace
   removed, starts with `use ` or with a visibility qualifier followed by
   `use `. The qualifier is `pub` alone or `pub` with a parenthesized
   restriction, so `pub use ` and `pub(crate) use ` lines are use lines. A
   line that starts with a comment marker is not a use line; its occurrences
   are still examined by rule A.
2. The root of a use line is the text after the `use ` keyword up to the
   first `::`, or the whole remaining text when there is no `::`. The root
   must be exactly one of `std`, `base64`, `self`, `super`. Any other root is
   a violation. The root rule is unchanged apart from the `super::`
   restriction of rule A (SPEC A6).
3. A use line rooted at `super` passes rule B and is then decided by rule A
   for its `super::` occurrence.
4. Rule B looks only at the line that carries the `use` keyword. Continuation
   lines of a multi-line use statement are covered by rule A only.

### Violation description (FR4)

Each violation description:

- contains the offending line's trimmed text, which carries the offending
  path;
- names the allowlist `super::agent_status`; a rule B violation also names
  the external-root list (`std`, `base64`, `self`, `super`);
- states the invariant that program_status must stay buildable without the
  `gui` feature, and contains the fragment ``without the `gui` feature``;
- does not contain the old phrase "must not reach into other project modules".

### ac8 test (FR5, FR7)

`ac8_the_module_uses_only_always_built_crates` keeps its name. It applies the
checker to the text of `src-tauri/src/program_status.rs` that the test already
embeds at compile time (the `include_str!("../program_status.rs")` read named
in SPEC FR1), and asserts that the violation list is empty. Its assertion
failure message carries every violation description. The previous per-line
root assertion and the `crate::` substring assertion with its old message are
removed; their behavior now lives in the checker.

tests.rs itself is not a scan target (FR1). The synthetic snippets of the
self-tests therefore never reach the ac8 test.

### Self-tests (FR6)

New tests feed synthetic sources to the checker. Their names start with
`ac8_allowlist_` followed by the label of the Acceptance Criterion below that
they prove (for example `ac8_allowlist_ac3_...`), following the file's
convention that a test name carries the criterion it proves. Each case is
asserted on its own, with the snippet in the assertion message, so a failing
case is identifiable.

## Test Notes

- AC-1 to AC-6 are unit tests in tests.rs. AC-7 is the integrated run of the
  workflow.yaml commands (the src-tauri `test_command` and the src-tauri-cli
  `build_command`) plus a check of the task's diff. Use the commands exactly
  as workflow.yaml `project.components` declares them.
- Red phase: the self-tests fail to compile until the checker exists. The
  rejected cases in AC-3 (prefix match, grouped import), the `pub use` and
  `pub(crate) use` cases in AC-4, and the non-use `super::` case in AC-5 are
  the cases the current guard lets through, so they show the gap the checker
  closes.
- Worth covering beyond the listed snippets: a snippet without a trailing
  newline, and a `super::agent_status` occurrence at the very end of the text
  (allowed, because the path ends there).
- The snippets contain `crate::` and `super::` text. This is harmless because
  tests.rs is not a scan target. The existing
  `parse_received_ac7_rejecting_or_ignoring_input_logs_nothing` test scans
  program_status.rs only, so the checker's text in tests.rs does not affect it.

## Out of Scope

- Any change to `src-tauri/src/program_status.rs`, `src-tauri/src/lib.rs`,
  `src-tauri/src/agent_status.rs`, or any Cargo manifest or lock file (NFR1,
  NFR3).
- Checking that agent_status itself is declared without a gui gate (SPEC A4).
  The CLI-only build check catches gating regressions.
- Token-level Rust parsing: whitespace inside a path (such as `super :: x`)
  and paths produced by macros get no special handling.
- Extending the external-root list (SPEC A6).
- Renaming existing tests, or updating the test-docs records of other
  features (FR7, SPEC A2).
