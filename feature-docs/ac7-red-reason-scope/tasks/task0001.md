## Design

### What the record currently says, and what is wrong with it

The AC-7 entry's `red_reason` records an invariant guard: before the edit the change set was
empty and a repository-wide fixed-string search for a described identifier already returned
zero contiguous occurrences, so there was no observable pre-state to fail. Its post-edit
re-verification sentence then reports, of the WHOLE change set, that `git status --porcelain`
lists a single path — the record that task edited. The task's commit in fact contained two
paths: that record, plus the per-task test record the implement phase always generates for the
feature. The scalar therefore asserts a state nobody inspected, which is the defect class
these records exist to avoid.

### Processing flow

1. **Establish the observation first.** Read the described task's commit and take its actual
   path list (IMPLEMENTATION.md D1). The expectation is two paths —
   `test-docs/ac7-red-confirmed-unobserved/task0001.tests.yaml` (the record that task edited)
   and `test-docs/ac2-red-reason-accuracy/task0001.tests.yaml` (that task's own generated
   per-task test record). This expectation comes from the task description and from the
   sibling record `test-docs/ac7-red-confirmed-unobserved/task0001.tests.yaml`, whose AC-6
   entry already uses the correct multi-path phrasing for the analogous situation; it has not
   been confirmed against git during planning.
   - If the observed list differs from that expectation, the replacement text follows the
     OBSERVATION, and the divergence is reported as a plan deviation. Writing the expected
     list without having observed it would reproduce the very defect being repaired (NFR4).
2. **Locate the entry by content**: the `acceptance_tests` mapping's `AC-7` key, never by the
   line number the task description quotes (IMPLEMENTATION.md D2).
3. **Rewrite that one folded scalar** so that it:
   - names the observed change set by its members, rather than reporting a single-member
     listing for the whole change set (FR1, FR4);
   - identifies the second path as the workflow-generated per-task test record that the
     implement phase always produces, and ties it to the SPEC's Declared Change Set entry
     `test-docs/{feature}/**`, so that its presence reads as expected rather than as a
     containment violation (FR2);
   - keeps the original finding that the listed change set contains no Rust file and no
     TypeScript file (FR3);
   - keeps the rest of the justification unchanged in substance: the invariant-guard
     classification, the statement that the pre-edit change set was empty so there was no
     observable pre-state to fail, and the fixed-string identifier search (assembled from the
     described record's own header-comment fragments) returning zero contiguous occurrences
     before and after the edit (FR5).
4. **Keep the form**: the scalar stays introduced by the folded `>-` indicator at its existing
   indentation, wraps like the file's other folded scalars, and stays in English
   (NFR1–NFR3).
5. **Confine the change**: nothing else in the file moves (FR6). The `notes` block stays
   byte-identical even though it carries similar single-file wording about the file that task
   edited; if that wording looks like a second instance of the same defect, report it as a
   plan deviation instead of editing it (IMPLEMENTATION.md D3, A-5).
6. **Describe this task's own change set correctly** wherever this task records it — the
   per-task test record it produces, its commit message, and any deviation report. It is
   expected to contain the edited record plus this feature's own generated
   `test-docs/ac7-red-reason-scope/task0001.tests.yaml`; it is never described as a single
   file (IMPLEMENTATION.md D4, NFR6).

## Test Notes

- **Assert on parsed values, never raw lines.** A folded scalar re-wraps when rewritten, so
  raw-line assertions are unstable. AC-1 through AC-5 are checked by loading the record with
  PyYAML and asserting on the parsed justification string, the parsed verdict boolean and the
  parsed `tests` value.
- **Red/green shape.** AC-1, AC-2 and AC-4 have a genuine observable pre-state: before the
  edit the parsed scalar carries the single-member listing claim and names one path only, so
  the checks fail first and pass after. AC-3, AC-5, AC-6, AC-7 are invariant guards — the
  properties they assert already hold before the edit — and are recorded as such with their
  pre-state stated honestly rather than dressed up as red→green. AC-8 becomes observable only
  once this task's own change set exists.
- **Format and shape (AC-7)** need one raw-text inspection that does not depend on wrapping:
  the `red_reason: >-` introducer and its indentation, and the order of the top-level keys.
  Entry count and key set come from the parsed mapping.
- **Containment (AC-6)** is a diff against the base revision: assert that hunks fall inside
  the AC-7 justification scalar, and compare the untouched regions for byte identity.
- **Self-consistency (AC-8)** is checked two ways: enumerate this task's change set from git
  and assert no Rust and no TypeScript path is present and that its membership is the expected
  two paths; and search the text this task writes — the per-task test record above all — for
  any statement that scopes the whole change set to one file, expecting none.
- **Project commands** are not required to exercise this change (it touches no Rust and no
  TypeScript source). `bun test` and `bun run typecheck` may still be run as a no-regression
  check, as the previous feature did (A-6); record the outcome in the per-task test record.
