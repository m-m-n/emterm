## Design

### D1'''''' — Raise the cap (6082de4e619d7f51)

The round-8 reviewer swept 216 shapes and established three things: the
current implementation is never worse than not fixing at all (0/216), it is
identical to not fixing in 86/216 (all with two or more evictions), and full
uncapped attribution mixes nothing in all 216. The sole cause of the residual
is the cap introduced by this feature.

The reviewer then swept the cap itself: at 24 the failing shapes mix 3/3/3
rows; at 32, 0/0/3; at 48, 0/0/3; at **62, 0/0/0**. Sixty-two is the wire
budget's ceiling — the decoder's segment maximum minus one for a synthesized
head and one for the trailing screen segment.

Critically, the same review measured that the ordinary window switch (1.57 ms
against a segment-free 8.23 ms) does not depend on the cap at all; the
prefix/suffix split is what makes it fast. The cap only affects the storm
path (234 ms at 6 segments, 338 ms at 24). So raising it trades storm-path
latency for correctness, and leaves the common case untouched.

Raise the cap to the wire ceiling. Then re-derive the producer's per-segment
cell budget, which is the cumulative ceiling divided by the maximum segment
count — a larger count means a smaller per-segment budget (roughly 125,000
cells at 64 segments). Verify that real terminal dimensions still fit
comfortably; if they do not, raise the cumulative ceiling instead, deriving it
from the producer's maximum rather than leaving the two to drift.

Measure the storm-path latency at the new cap rather than extrapolating, and
record it in VERIFICATION.md so the verify phase can accept or reject it
against NFR1 with real numbers.

If raising the cap turns out not to reproduce the reviewer's 0/0/0 result,
report that rather than working around it — the measurement is the reason for
this change.

### D2'''''' — Correct the doc (6eeccc889cb15d87)

The comment explaining the head-attribution policy claims a measurement showed
it matches full uncapped attribution in every tested case. It does not: with
two or more evictions it mixes rows that full attribution does not, which the
sibling test's documentation states correctly. Two places in the same
repository currently assert opposite things. Fix the wrong one, and state the
actual guarantee: exact match at one eviction, bounded-but-nonzero divergence
beyond it, never worse than no attribution at all.

If D1'''''' closes the divergence entirely at the new cap, say that instead —
but only if measured.

### D3'''''' — One client-side clamp (1e7e069001cf22dc)

The shared clamp is applied in one client method, so the paths that create a
tab's core and that publish dimensions to the daemon bypass it, and the app's
own grid record keeps the unclamped value while the core holds the clamped
one. Apply the clamp wherever the client decides or publishes dimensions, and
keep the app's record in agreement with the core it drives.

Consider whether a clamp derived from the mux wire protocol should constrain a
tab with no mux connection at all; if not, scope it to the mux path rather
than to every terminal.

### D4'''''' — Construction must not lie (7be271b2ead1bf07)

When pane construction clamps dimensions and the subsequent PTY resize fails,
the code logs and then records the clamped values anyway — so every byte the
child produces is attributed to a size the PTY never had. The sibling resize
path rolls back on the same failure. Make construction consistent: either fail
the construction, or record what the PTY actually has.

### D5'''''' — Test the real producer shape (45033eaafbdf8e25)

The budget's denominator is checked by building a segment list from the
constant itself, which cannot detect the constant drifting from what the
producer emits — and D1'''''' changes exactly that number. Add a test that
drives the real path (ring → snapshot assembly → encode → decode) at the
largest shape the daemon can produce, with the cap saturated and a trailing
screen segment present, and asserts the decode succeeds.

### D6'''''' — Verification runs what it claims (ba7953c458050780)

The documented test command covers one crate, so the twenty-one tests this
feature added to the terminal core never run in the verification gate. Include
them. Also state the seven pre-existing failures plainly, with the fact that
they reproduce on the base commit, so "all pass" stops being a claim the run
contradicts.
