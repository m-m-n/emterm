## Design

### D1 — Side-channel authority (findings a6ab9b340119beed, 15c54fb74bb91ec7)

Today a marker is a byte sequence in the scrollback ring, so every code path
that can put bytes in the ring is a forgery path. Two such paths survived the
previous rework: the write filter's pending-overflow escape hatch, and a
marker nested inside a sequence the OSC-granular stripper keeps (non-SIXEL
DCS). Filtering more paths is whack-a-mole.

Instead: the ring's existing `dim_markers` side channel becomes the single
authority for "which dimensions were in effect for this byte offset". PTY
bytes never contribute to it. Snapshot assembly emits marker bytes into the
replay stream from the side channel, so the replay stream still carries
in-band markers (the replay-side interpretation stays as-is), but their
provenance is structural rather than filtered. Correspondingly, the PTY write
path strips `resize` on EVERY path including the overflow hatch, because a
marker in PTY bytes now carries no meaning at all and must not survive into
the ring where it could be mistaken for an emitted one.

The invariant to state and test: no sequence of child-process output can
change the dimensions a replay applies.

### D2 — Shared marker contract (finding 602e685494248cbb)

The encoder currently accepts any `u16` while the decoder rejects zero and
anything above 2000, so a legitimate resize outside that range silently loses
its marker and the drift returns. Give the byte format and its accepted
dimension range one owner, used by both sides. Validate a resize against that
range where the resize is applied, rather than discovering the mismatch at
replay.

### D3 — Pane routing for Snapshot framing (findings 200b2c8beeb68fe4, 87ba3cc2911d104e)

The previous rework changed reattach and visibility-resume to send per-pane
`Snapshot` / `SnapshotRestore` frames, but the client's Snapshot arm resets
and replays the tab's single core without checking `pane_id` — the filter
exists only on the `PtyOutput` arm. With more than one mux window, the last
frame to arrive wins and the wrong window's content is displayed. Restore the
routing contract: a frame that replaces the tab's core is applied only when it
belongs to the pane that tab is showing.

### D4 — Marker accumulation cost (findings 5d1a4e9509365517, 0b0c18ff4ab911f4)

Coalescing only collapses markers with no bytes between them, but a real
drag-resize interleaves redraw bytes, so markers accumulate and each one costs
a full scrollback reflow on every later replay. Bound this at the recording
side: a dimension change that supersedes a previous one with only negligible
output between them replaces it rather than appending. Also make side-channel
pruning linear rather than quadratic.

### D5 — Ordering (finding 0bebe3e6f7b416dd)

Holding the scrollback lock across the PTY-visible resize only orders
post-resize bytes after the marker; bytes already read before the resize can
still land after it. With D1 the natural fix is to attribute bytes to the
dimensions in effect when they were read, so ordering follows from
attribution instead of from lock scope.

### D6 — Bypass divergence (finding 893241823258fce3)

A mid-drain resize under snapshot bypass reflows against an intentionally
empty scrollback, so row-count growth diverges from the synchronous path in
both history and cursor position. Either make the bypass path agree with the
synchronous path, or make row-growth markers not take the bypass path.

### D7 — Snapshot identity vs framing (finding 98eec9bbef67704a)

Above the chunking threshold the same logical snapshot degrades to
marker-blind live-output framing, so large snapshots replay incorrectly.
Snapshot identity must not depend on payload size.

### D8 — Test corrections (finding c9773adeab150890)

The width-varying test cannot fail: its rows are identical across phases so
the drift mechanism never fires, and its taint detector looks for a substring
the synthesized content no longer contains. Replace detector-style assertions
with the live-feed fingerprint comparison used by the round-trip test, vary
both dimensions, and include lines that wrap at the narrower width. Every new
or corrected test in this task must be demonstrated to fail with the fix
disabled before it is accepted.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: No child-process output can change the dimensions a replay
      applies — tests cover at least: a bare forged marker, a forged marker
      arriving through the pending-overflow escape hatch (unterminated
      introducer + padding past the cap + marker), and a forged marker nested
      inside a non-SIXEL DCS body.
- [ ] AC-2: A legitimate resize outside the previously-hardcoded decoder range
      still produces a marker the replay honors (encoder and decoder agree on
      the accepted range).
- [ ] AC-3: With two or more mux windows, reattach applies only the displayed
      pane's snapshot to the tab core — a test asserts a non-active pane's
      snapshot does not overwrite it.
- [ ] AC-4: Same as AC-3 for visibility-resume (`SetVisibility(true)` with
      multiple panes).
- [ ] AC-5: A snapshot above the chunking threshold replays with markers
      honored, exactly as a smaller one does.
- [ ] AC-6: A drag-resize-shaped sequence (many dimension changes with redraw
      bytes between them) does not leave one full-scrollback reflow per change
      in later replays — asserted via the reflow counter already present.
- [ ] AC-7: Side-channel pruning is linear — a test with a large marker count
      completes without the quadratic blowup (assert on operation count or
      structure, not wall-clock).
- [ ] AC-8: Bytes read before a resize are replayed under the dimensions they
      were produced for, including when the reader thread is contending with
      the resize path.
- [ ] AC-9: A row-count-growing marker inside a bypass-path (≥ 64 KiB)
      snapshot produces the same viewport fingerprint as the synchronous path.
- [ ] AC-10: The width-varying test compares against a live-feed fingerprint,
      varies both rows and columns, includes lines that wrap at the narrower
      width, and is demonstrated to fail when marker interpretation is
      disabled.
- [ ] AC-11: Existing Rust `--lib` tests pass single-threaded apart from the 7
      failures already present on base commit
      a8d4bed2df5e2f41f524bd0c1ff59fb07f76f025; CLI-only feature check passes.
