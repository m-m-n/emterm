# Task Plan: task0010 — Stop re-wrapping scrollback on intermediate segment resizes

## Goal

Replaying a snapshot with many dimension changes costs about what replaying
one with none costs, so neither the marker cap nor the bypass split has to
trade correctness against latency any more.

## Requirements

FR2, FR3, NFR1, NFR2, NFR3

## Scope

### Files to Modify

- `crates/term_core/src/terminal_core.rs` — the replay-time resize path
- `crates/term_core/src/reflow.rs` — a resize that establishes the coordinate
  system without re-wrapping retained scrollback
- `crates/term_core/src/bench.rs` — restore the latency assertions this
  change should make satisfiable again
- `src-tauri/src/mux/scrollback_buffer.rs` — revisit the marker cap once cost
  no longer forces it
- `feature-docs/mux-render-corruption/VERIFICATION.md` — re-measure and record

## Design

### D1 — The cost that was never actually removed

Round 4's review proposed making intermediate segment resizes cheap: a
mid-replay resize only needs to establish the coordinate system for the bytes
that follow it, because the next resize — and ultimately the restore to the
caller's target size — re-wraps everything again. Only the final state has to
be fully consistent.

Round 6 implemented something adjacent but different: a prefix/suffix *split*,
where the trailing run of segments already at the target size replays under
the fast bypass. That made the ordinary window switch fast (1.54 ms) and it is
worth keeping. It did nothing for the storm shape, where dimensions keep
changing and there is no stable trailing run — and the storm shape is exactly
what the marker cap exists to bound.

Measured, at the shipping scrollback default with a 0.95 MiB payload:

| segments | latency |
|---|---|
| 0 (baseline) | ~8-10 ms |
| 15 | ~235 ms |
| 24 | ~330 ms |
| 32 | ~2.5 s |
| 48 | ~3.7 s |
| 62 | ~4.6 s |

The curve is superlinear past ~24 because each intermediate resize performs a
full content-preserving reflow of everything accumulated so far, so the work
grows with both the segment count and the scrollback that has built up.

Implement the original proposal: during segment replay, an intermediate resize
changes the grid's dimensions without re-wrapping retained scrollback. The
final restore to the caller's target size performs the one real reflow.

Equivalence is the gate, not an assumption. The resulting grid, cursor,
eviction total, and prompt/fold marks must match what the current
reflow-per-segment path produces for the same input, across the existing
resize-spanning fixtures. Where a case cannot match, prefer correctness, state
the exception explicitly, and do not fold it into "accepted precision loss"
silently.

### D2 — Re-examine the cap once cost is flat

`MAX_DIM_MARKERS` is currently 62 — chosen in round 9 purely to make FR2's
mixing go to zero, at the cost of the storm latency above. Round 8's sweep
showed correctness improves monotonically with a larger cap and that full
uncapped attribution mixes nothing at all.

If D1 flattens the curve, the cap's latency justification disappears. Re-derive
it from what actually still constrains it — the wire segment budget — and say
so in the constant's documentation. Do not leave a value whose comment
explains a tradeoff that no longer exists.

### D3 — Restore the latency gate

Round 9 downgraded the bench's hard latency assertions to informational
reporting because they had begun failing by design. That removed the only
automated guard on this axis. If D1 works, those assertions should hold again:
restore them with bounds derived from the new measurements, and keep them
running in the normal verification flow rather than behind an ignore.

If D1 does not bring the storm shape under the old bounds, report the measured
numbers and leave the assertions calibrated to what is actually achieved,
stating the gap — do not re-downgrade them to informational.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Replay latency for a storm-shaped snapshot at the daemon's marker
      cap is within a stated small multiple of the segment-free baseline, and
      the measured table is recorded in VERIFICATION.md.

      cheap-intermediate-resize replay match the reflow-per-segment result

      constrains it after D1.

## Test Notes

- Read `feature-docs/mux-render-corruption/reviews/round8.yaml` (the sweep and
  cap data) and VERIFICATION.md's NFR1 section (the round-9 measurements) before
  starting.
- Every test written or changed must be demonstrated to fail without its fix,
  with the demonstration noted in its comment.
- Do not assert `core.cols()`/`core.rows()` after replay — replay restores the
  caller's target size regardless.
- The 7 pre-existing failures are out of scope; confirm unchanged. Run both
  `cargo test --manifest-path src-tauri/Cargo.toml --lib` and
  `cargo test --manifest-path crates/term_core/Cargo.toml --lib`.
- The worktree needs the gitignored bundled fonts under
  `src-tauri/assets/fonts/`.
- Replay tests run with `--test-threads=1`.
- Run tests synchronously in the foreground with a long timeout.
- If D1 turns out to be infeasible — if intermediate resizes genuinely cannot
  skip the re-wrap without changing the final grid — report that with the
  evidence rather than implementing a partial workaround. That answer is worth
  more than an approximation, because it settles whether the cap tradeoff is
  fundamental.
