# Task Plan: task0002 — Harden the resize-marker protocol (review round 1 rework)

## Goal

The resize-marker mechanism introduced by task0001 is trustworthy and complete:
a marker can only originate from the daemon, the earliest retained scrollback
segment always has known dimensions, markers are ordered against PTY output,
every replay consumer interprets them, and replaying them is not quadratic.

## Design

### Finding 0c18ff55032328ab (critical) — marker forgery

A child process can emit the marker byte sequence itself. Today the same
strip function serves the PTY write path and snapshot assembly, and it keeps
the `resize` kind on both. Separate the two so the write path strips `resize`
(PTY-originated markers never enter the ring) while snapshot assembly keeps it
(daemon-written markers survive to replay). Daemon markers bypass the filter
already, so this separation alone establishes the invariant "every marker the
replay trusts was written by the daemon". The decoder's dimension clamp
(applied in review loop 1) stays as defense in depth.

### Findings 81947e02402b5ace / ee93d8be8823e5d7 (high) — ring wraparound

The 2 MiB ring evicts the initial marker on any long-lived pane, leaving the
earliest retained segment without known dimensions. Track the dimensions in
effect at the oldest retained byte and make snapshot assembly emit a
head-dimension marker so the invariant "the earliest retained segment is
preceded by a marker" holds regardless of wraparound. Also ensure a marker
truncated by the eviction point cannot surface as visible text.

### Finding 83bed291fb779f52 (high) — ordering

`MuxPane::resize` signals the child before recording the marker, so the
reader thread can interleave post-SIGWINCH bytes ahead of it. Establish a
single ordering owner for the recorded stream: the marker must be recorded
before any byte the resize causes can be appended.

### Finding 6ff208bbc674189c (high) — reflow per marker

Consecutive markers with no bytes between them each trigger a full
content-preserving reflow. Defer the resize until bytes are actually about to
be fed, so a drag-resize run collapses into one reflow; also avoid the final
restore reflow when the pending dimensions already match the target.

### Finding 20b2bed0aaf48f94 (medium, correctness-relevant) — consumer coverage

Only the window-switch snapshot path interprets markers. The reattach and
visibility-resume paths deliver history through the live output path, which
discards markers, so the reported symptom persists on detach → resize →
reattach. Make those paths marker-aware (routing them through the same replay
entry point is preferred over duplicating interpretation).

### Finding 1698d9b52a89e241 (medium) — bypass invariant

A mid-drain resize during snapshot bypass populates the slim scrollback the
bypass assumes stays empty, which the second pass then treats as live-drain
content. Restore the invariant (or make the reflow bypass-aware), and guard it
so a future in-drain mutation path fails loudly instead of silently.

### Finding 4005fe364386682d (medium) — byte contract SSOT

Encoder and decoder hold independent literals for the marker bytes. Give the
contract one owner, or add an explicit round-trip drift-guard test.

### Findings 7aef70ff81703b90 / abeda9cc206cf018 (medium) — test gaps

SPEC FR3 names a differing-terminal-width scenario that no test covers, and
the SPEC test list's grid round-trip equality check is absent. Both are
required by FR3.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A marker emitted by PTY output (not by the daemon) never reaches
      the replay stage — a test feeds the marker byte sequence as ordinary
      child output and asserts the replay core's dimensions are unchanged.
- [ ] AC-2: A test drives the scrollback ring past wraparound so the initial
      marker is evicted, then replays a resize-spanning recording and asserts
      zero cross-line content mixing in the earliest retained segment.
- [ ] AC-3: A marker truncated by ring eviction never renders as visible cells.
- [ ] AC-4: Recording a resize orders the marker ahead of any byte the resize
      causes — verified by a test that exercises the resize path concurrently
      with reader-thread appends.
- [ ] AC-5: A recording with N consecutive markers and no bytes between them
      performs one reflow, not N — verified by an observable counter or by
      asserting the resulting grid equals the single-final-dimension case
      while the intermediate dimensions leave no trace.
- [ ] AC-6: The reattach path (and visibility-resume path) interprets resize
      markers — a test replays a resize-spanning recording through that path
      and asserts no cross-line mixing.
- [ ] AC-7: A snapshot ≥ 64 KiB containing a row-count-shrinking marker,
      taken through the bypass path and the second-pass merge, produces no
      duplicated or out-of-order scrollback rows and reports consistent
      eviction bookkeeping.
- [ ] AC-8: A round-trip test asserts the grid fingerprint (line text +
      cursor) of a core fed the recording live equals that of a core replayed
      from the assembled snapshot, for both resize-spanning and resize-free
      recordings.
- [ ] AC-9: A test covers a recording whose lines were produced at differing
      terminal WIDTHS (including lines longer than the narrower width), with
      zero cross-line mixing after replay.
- [ ] AC-10: A drift-guard test round-trips the encoder's output through the
      decoder (or the contract has a single owner making drift impossible).
- [ ] AC-11: The existing Rust `--lib` suite passes single-threaded apart from
      the 7 failures already present on base commit
      a8d4bed2df5e2f41f524bd0c1ff59fb07f76f025, and the CLI-only feature check
      passes.
