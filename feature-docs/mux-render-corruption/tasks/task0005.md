# Task Plan: task0005 — Validate, bound, and version the segment protocol (round 4 rework)

## Goal

The out-of-band segment design from task0004 is production-safe: dimensions
arriving over the wire are validated where they are consumed, replay cost is
bounded so window switching stays responsive, the protocol version reflects
the incompatible payload change, and the bypass predicate covers every resize
that triggers a reflow.

## Requirements

FR2, FR3, NFR1, NFR2, NFR3

## Scope

### Files to Modify

- `crates/mux_ipc/src/protocol.rs` — version bump; decode-side validation and
  bounds; typed decode outcome
- `crates/term_core/src/terminal_core.rs` — clamp at the replay boundary;
  bypass predicate; bound the reflow cost of a segment run
- `src-tauri/src/mux/ipc/handlers.rs` — frame-size enforcement at every
  snapshot producer

## Design

### D1'' — Validate dimensions where they are consumed (da834d05f3f18af4)

`clamp_resize_dims` currently guards only the producer. A decoded segment goes
straight to `TerminalCore::resize`, which allocates
`(scrollback_capacity + rows) * cols` cells and debug-asserts non-zero
dimensions. Apply the same domain at the replay boundary, and reject
out-of-domain segments at decode. Keep the producer clamp as defense in depth.

### D2'' — Bound the wire (1cd7b5e593f3b901, 5299d50f586b8cb8)

Segment count is unbounded; `count.min(4096)` limits only the initial
allocation. Define and enforce a maximum, verify the table length with checked
arithmetic, and distinguish three decode outcomes — legacy (no magic),
structured, malformed (magic present but table invalid) — so a corrupt frame
is not replayed as terminal text.

### D3'' — Bound replay cost (6c650908ea8e95e9, b1de83542bfe60bc)

Measured: 0.95 MiB snapshot at the shipping scrollback default replays in
134 ms with no segments, 2.1 s at 30 segments, 3.3 s at 50, 5.4 s at 80.
Segments accumulate because resize messages are sent per grid-size change with
no debounce and coalescing now only merges adjacent markers. This violates
NFR1 as measured, so the round-3 deferral no longer holds.

Reduce the total reflow work rather than only the marker count. Options the
reviewers raised, in rough order of leverage:

- A mid-drain resize only needs the coordinate system for the bytes about to
  be fed; the intermediate scrollback re-wrap is overwritten by the final
  restore-to-target reflow. If intermediate segments can resize the viewport
  without re-wrapping scrollback, cost becomes near-linear and cheap.
- Bound the recorded segment count K, merging the oldest boundary into its
  successor when exceeded. Unlike the byte-threshold coalescing reverted in
  round 4, this keeps recent attribution exact and only loses precision in the
  oldest span, so it does not reintroduce ab54fae335086db3.
- Debounce resize dispatch so one drag does not emit dozens of messages.

Also make the synchronous-vs-off-thread dispatch account for segment count,
not payload bytes alone.

### D4'' — Protocol version (fdfd391ba97167de)

The Snapshot / SnapshotRestore payload format changed incompatibly while
`PROTOCOL_VERSION` stayed at 2, so a new daemon and an old GUI handshake
successfully and the old GUI renders the envelope header as terminal content.
The project already has a legacy-daemon recovery path gated on this constant,
and its doc states there is no silent compatibility shim between versions.
Bump the version and let the existing recovery mechanism engage, or — if not
bumping — record the justification in that doc so the constant and the
implementation stop contradicting each other.

### D5'' — Bypass predicate covers every reflow (697d8dc2b88dcddc)

The downgrade fires only on row growth, but the reflow drains scrollback for
column changes too, so a columns-only resize under bypass reflows against an
intentionally empty scrollback and diverges from the synchronous path. Base
the predicate on "does replay resize at all" rather than on row growth. The
existing test asserts only `scrollback_count() == 0`; replace it with the
grid-fingerprint comparison the other bypass tests use.

### D6'' — Producer-side frame policy (1d4a0c96821da0ef)

Snapshot producers disagree about the frame-size limit: some enqueue without
checking (an oversize snapshot then tears down the connection), while reattach
falls back to raw output framing and drops all segments, returning to
dimension-blind replay. Give the size policy one owner that every producer
goes through, and keep segments attached on the oversize path.

### D7'' — Attribution correctness gaps

- **Resize failure (ef9ab1689853785c)**: when the PTY resize fails, published
  dimensions must not stay advanced — otherwise every later chunk is attributed
  to a size the PTY never had.
- **Filter carry-over (0e3f8378913e1f4a)**: bytes held in the write filter's
  pending buffer belong to the read that produced them, not the read that
  flushed them.
- **Trailing screen dump (5ba2063e993baf6c)**: the screen dump appended to a
  snapshot is produced at the pane's current dimensions but inherits the last
  scrollback segment's, which can differ after a correction.

### D8'' — Contract hygiene (03c11d98f82dfa1c, cefa30b5ebd33f5c)

Make the "first segment starts at offset 0" precondition explicit and enforced
rather than emergent, and replace the anonymous `(usize, u16, u16)` that
crosses eight signatures with a named type, converting at the wire boundary
once. This matters because the codebase already has inconsistent cols/rows
argument order, so a positional swap would compile and pass same-size tests.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A snapshot whose segments carry zero or out-of-domain dimensions
      neither panics nor allocates beyond the shared domain — replay clamps or
      the frame is rejected.
- [ ] AC-2: A snapshot declaring an excessive segment count is rejected before
      allocation; a magic-bearing frame with an invalid table is reported as
      malformed rather than replayed as terminal text.
- [ ] AC-3: Replay of a segment-bearing snapshot stays within a stated latency
      bound as segment count grows — a test asserts total reflow work does not
      grow linearly with segment count at the shipping scrollback default.
      State the bound in the test.
- [ ] AC-4: A drag-resize-shaped sequence produces a bounded number of
      recorded segments regardless of how many bytes each redraw emits.
- [ ] AC-5: The synchronous-vs-off-thread dispatch sends a small-payload,
      many-segment snapshot off-thread.
- [ ] AC-6: `PROTOCOL_VERSION` reflects the payload change (or its doc records
      why not), and the version constant test is updated accordingly.
- [ ] AC-7: A columns-only resize segment in a payload above the off-thread
      threshold yields the same grid fingerprint as the synchronous path.
- [ ] AC-8: Every snapshot producer enforces the same frame-size policy; the
      oversize path keeps segments rather than degrading to dimension-blind
      replay.
- [ ] AC-9: A failed PTY resize leaves published dimensions unchanged, and a
      subsequent chunk is attributed to the dimensions the PTY actually has.
- [ ] AC-10: Bytes carried across reads in the write filter's pending buffer
      are attributed to the dimensions in effect when they were produced.
- [ ] AC-11: A snapshot's trailing screen dump replays at the dimensions it
      was produced at, including after an attribution correction changed the
      last scrollback segment.
- [ ] AC-12: The first-segment-at-offset-0 precondition is enforced, not
      assumed.
- [ ] AC-13: Existing Rust `--lib` tests pass single-threaded apart from the 7
      failures already present on base commit
      a8d4bed2df5e2f41f524bd0c1ff59fb07f76f025; CLI-only check passes.
- [ ] AC-14: VERIFICATION.md's manual section includes a drag-resize-then-
      switch scenario.
