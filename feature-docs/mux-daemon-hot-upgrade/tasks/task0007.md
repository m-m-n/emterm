# Task Plan: task0007 — Process-id based child reaping for restored panes

## Goal

Let the daemon reap pane children whose owned process handle did not survive
the process replacement, so restored panes still exit cleanly instead of
leaving zombies.

## Requirements

FR18, NFR2

## Scope

### Files to Modify
- `src-tauri/src/mux/session/child_reaper.rs` — add a process-id based reaping
  path alongside the existing handle-based one.
- `src-tauri/src/mux/session/pane.rs` — let a pane hold a child process id in
  place of an owned child handle, and route its exit handling to the new path.

## Design

The PTY library's child handle cannot be rebuilt after the process image is
replaced, but the daemon remains the parent of every pane child, so the
platform's child-status collection still works by process id
(IMPLEMENTATION.md D6).

**New reaping path.** Accepts a raw process id and applies the same policy the
existing handle-based reaper applies: poll for exit for a bounded grace period,
then terminate and collect. Reuse the existing timing constants rather than
introducing new ones, so both paths behave identically from the outside.

**Pane changes.** A pane's child is now either an owned handle (freshly
spawned pane) or a bare process id (pane restored from a handoff). The pane's
exit handling picks the matching reaping path. Everything else about pane exit
— marking the pane exited, releasing the writer and master, notifying the
exit channel — stays as it is today, so a restored pane and a spawned pane are
indistinguishable to the rest of the daemon.

Guard the process-id path to Unix; the handle-based path stays available on
all platforms so non-Unix builds are unaffected.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Given a child process that exits on its own, the process-id path
      collects it within the grace period and reports the exit.
- [ ] AC-2: Given a child process that ignores the graceful signal, the
      process-id path terminates and collects it after the grace period.
- [ ] AC-3: The process-id path returns promptly and without error for a
      process id that has already been collected.
- [ ] AC-4: A pane holding a process id, when marked exited, is reaped through
      the process-id path and ends in the same observable state as a pane
      holding an owned handle.
- [ ] AC-5: A pane holding an owned handle continues to be reaped through the
      existing path, unchanged.
- [ ] AC-6: Both paths use the same grace and poll timing constants.

## Test Notes

Spawn short-lived and signal-ignoring helper processes the way the existing
reaper tests construct their doubles. AC-3 covers the already-collected case
so the restored-pane path cannot hang on a child the reaper already handled.
AC-4 and AC-5 assert on observable pane state rather than internal fields.
Keep the process-id tests Unix-gated.

## Out of Scope

- Capturing the process id into the handoff document (task0003).
- Restoring panes (task0003).
- Any change to how freshly spawned panes obtain their child handle.
