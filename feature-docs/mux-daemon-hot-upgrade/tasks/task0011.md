# Task Plan: task0011 — Make the inherited-PTY negative-path tests safe under parallel execution

## Goal

Stop the library test suite from intermittently aborting the whole test
process. The suite must complete every run, so that real failures are
distinguishable from a crash.

This is a **rework task** synthesized from the verify phase's failure VF-1.

## Requirements

NFR4

## Scope

### Files to Modify
- `src-tauri/src/mux/inherited_pty.rs` — the negative-path tests that pass a
  closed or non-terminal descriptor number.

## Design

### The failure

`CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`
aborts the entire test process with:

```
fatal runtime error: IO Safety violation: owned file descriptor already closed, aborting
```

Measured during verification: **2 aborts in 12 runs** on this feature branch,
**0 aborts in 6 runs** on the base commit `9c9db29`. Every captured abort
occurred while `mux::inherited_pty::tests` was running — the last tests to
complete before the abort were consistently that module's negative-path cases
(`construction_fails_over_a_closed_descriptor`,
`construction_fails_over_an_ordinary_file_descriptor`, and neighbours).

Running `--test-threads=1` never aborts. Running only `mux::` in parallel
never aborted in 5 runs. The abort needs the full suite's thread count.

### Why it happens

The descriptor table is process-wide and shared by every test thread. A test
that closes a descriptor and then keeps using its *number* is racing every
other thread: between the close and the use, an unrelated test can open
something that lands on the same number. When that number is then treated as
owned and closed a second time — or when the standard library's I/O-safety
check observes an already-closed owned descriptor — the runtime aborts the
whole process rather than failing one test.

This is the same hazard class the task0002 implementer already hit and worked
around for one assertion (comparing device identity instead of descriptor
validity). The negative-path cases were not covered by that workaround.

The defect is in the **tests**, not in production code: nothing here shows the
adapter mishandling descriptors at runtime. But an intermittently aborting
suite is not an acceptable state to ship — it destroys the signal every other
test provides.

### Approach

Make each negative-path case reason about a descriptor identity that cannot be
recycled underneath it, rather than about a bare number. Options that fit the
existing conventions in this file:

- Keep a descriptor of the intended kind open for the whole assertion so its
  number cannot be reused, and assert on the adapter's rejection of *that*
  descriptor.
- Where the case genuinely needs a closed descriptor, obtain a number that the
  process will not hand out again for the duration of the assertion, or
  serialize just these cases against each other with a module-local guard.

Do not weaken the criteria the cases exist for: construction over a closed
descriptor and over a non-terminal descriptor must still be shown to fail
without taking ownership. Do not mark the tests `#[ignore]`, and do not move
them behind a single-threaded-only path — the suite must stay correct under
its default parallel execution.

While here, check the rest of this module's tests for the same pattern (using
a descriptor number after its owner may have released it) and apply the same
treatment.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `cargo test --lib` (default parallelism) completes without
      aborting the process across 15 consecutive runs.
- [ ] AC-2: Construction over a closed descriptor is still asserted to fail
      without taking ownership.
- [ ] AC-3: Construction over a non-terminal descriptor is still asserted to
      fail without taking ownership.
- [ ] AC-4: No test in this module is newly `#[ignore]`d, skipped, or
      restricted to single-threaded execution.
- [ ] AC-5: The module's remaining tests still pass under both default
      parallelism and `--test-threads=1`.

## Test Notes

AC-1 is the criterion that matters and needs repetition to be meaningful — a
single green run proves nothing for a defect that reproduces roughly one run
in six. Run it enough times to be confident, and report the observed count.

The `tabs::tests` off-thread-replay failures seen in the same suite are **not**
in scope: they reproduce identically on the base commit (15-17 failures in
every one of 6 baseline runs) and are unrelated to this feature.

## Out of Scope

- The `tabs::tests` flakiness (pre-existing, unrelated).
- The 7 residual review findings deferred in review round 2 — those are
