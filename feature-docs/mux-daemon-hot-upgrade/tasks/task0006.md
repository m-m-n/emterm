# Task Plan: task0006 — Client reconnect after an upgrade announcement

## Goal

Make an attached client survive the daemon replacing itself: after receiving
the upgrade announcement, reconnect and re-attach instead of exiting, so the
user's panes reappear without them relaunching anything.

## Requirements

FR12, NFR3

## Scope

### Files to Modify
- `src-tauri/src/mux/bridge.rs` — recognise the announcement, arm a bounded
  reconnect loop around the connect-and-handshake path, and re-attach after a
  successful reconnect.

## Design

Today the bridge connects once, and any socket read failure ends the loop and
the process, which hands the terminal back to the shell that ran the attach
command. That behaviour is correct for an ordinary shutdown and must stay
(IMPLEMENTATION.md D2).

The change is to make the disconnect's meaning depend on whether the
announcement arrived first:

- **Announcement received, then the socket drops** — enter a reconnect loop:
  retry connect-and-handshake with a bounded number of attempts spread over a
  bounded window, using a backoff rather than a tight spin. On success,
  re-attach to the same session the bridge was attached to and resume normal
  operation, letting the daemon's existing reattach machinery repaint the
  panes. Reset the armed state so a later ordinary disconnect exits as usual.
- **Announcement not received, socket drops** — today's behaviour, unchanged.
- **Reconnect window exhausted** — exit with today's behaviour, after logging
  the reason.

The announcement carries no payload; its arrival is the entire signal. It must
not be forwarded to the terminal as pane output.

Because the daemon keeps its listen socket open across the replacement, a
reconnect attempt made during the handoff blocks in the kernel backlog rather
than failing, so the loop must tolerate a connect that takes noticeably longer
than usual (IMPLEMENTATION.md D4).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Receiving the announcement does not emit any bytes to the
      terminal output path.
- [ ] AC-2: After the announcement, a socket drop causes a reconnect attempt
      rather than an immediate exit.
- [ ] AC-3: Without the announcement, a socket drop ends the bridge exactly as
      it does today.
- [ ] AC-4: A reconnect that succeeds re-attaches to the same session the
      bridge was previously attached to.
- [ ] AC-5: Reconnect attempts are bounded: after the window is exhausted the
      bridge exits and logs the reason, rather than retrying forever.
- [ ] AC-6: Retries use a backoff — asserted by observing that the attempts
      are not issued back-to-back without delay.
- [ ] AC-7: After a successful reconnect, a subsequent socket drop with no new
      announcement exits as in AC-3.

## Test Notes

Use a stand-in daemon in a plain thread, following the pattern the existing
daemon tests use: it completes the handshake, optionally sends the
announcement frame, then closes the connection, and on a later connection
completes the handshake again. Assert reconnect behaviour through observable
effects (a second handshake arriving at the stand-in, the attach message being
re-sent) rather than through internal state. Keep timings short enough that
the suite stays fast, and Unix-gate anything that binds a socket path.

## Out of Scope

- The announcement message type itself (task0001).
- Broadcasting the announcement (task0004).
- Any change to the daemon's reattach machinery.
