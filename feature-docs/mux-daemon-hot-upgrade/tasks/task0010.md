# Task Plan: task0010 — Keep stdin across bridge reconnects

## Goal

Stop the bridge from discarding the user's keystrokes and stranding a blocking
read every time it reconnects after an upgrade.

This is a **rework task** synthesized from review round 1.

## Requirements

FR12, NFR3

## Scope

### Files to Modify
- `src-tauri/src/mux/bridge.rs` — own the stdin handle across reconnects
  instead of creating a new one per connection attempt.

## Design

### Finding this task resolves

Two reviewers independently flagged the same site (round 1, performance and
comprehensive; see `reviews/round1.yaml`). The forwarding loop creates a fresh
stdin handle on every call. When the connection drops after an upgrade
announcement, the in-flight read is dropped mid-flight. Reading from stdin is
not cancellation-safe, so bytes already pulled from the real descriptor are
discarded with the handle, and the blocking read that was abandoned keeps
occupying a pool thread until the user happens to press a key.

Before this feature, the forwarding loop ran exactly once and the process
exited afterwards, so neither consequence could occur. The reconnect loop is
what makes it reachable — and it makes it recur once per upgrade.

Two observable symptoms: keystrokes typed during the replacement vanish
silently, and each upgrade strands one more blocking read while two handles
contend for the same input.

### Approach

Give the stdin handle a lifetime that spans reconnects — created once by the
caller that owns the reconnect loop and lent to each connection — or move stdin
reading into its own long-lived task that survives connection churn and feeds
the forwarding loop through a channel. Either removes the per-reconnect handle;
pick the one that fits the existing structure with the smaller change.

Keep the platform split as it is today.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A reconnect does not create a second stdin handle — the same handle
      (or the same long-lived reader) serves every connection in one bridge
      run.
- [ ] AC-2: Bytes read from stdin while a connection is dropping are delivered
      to the daemon after the reconnect rather than discarded.
- [ ] AC-3: After a reconnect, no abandoned blocking read remains outstanding
      against stdin.
- [ ] AC-4: Behaviour without a preceding upgrade announcement is unchanged:
      the bridge still exits on a normal disconnect.
- [ ] AC-5: The existing bridge reconnect tests still pass unmodified.

## Test Notes

AC-2 is the criterion worth the most care: drive input through the stand-in
daemon pattern the existing bridge tests already use, drop the connection while
input is pending, and assert the byte arrives after the reconnect. If AC-3
cannot be asserted directly in this test harness, say so and assert the
structural property instead (the handle is created once), rather than dropping
the criterion.

## Out of Scope

- The upgrade path itself (task0009 owns daemon.rs, upgrade.rs and cli.rs).
- Any change to the reconnect policy, backoff, or the announcement contract.
