# Task Plan: task0008 — End-to-end hot-upgrade integration test

## Goal

Prove, against a real daemon and a real shell, that an in-place upgrade keeps
the pane's shell process alive and its state intact — the single claim this
whole feature exists to make.

## Requirements

FR7, FR9, FR10, FR11, NFR2

## Scope

### Files to Create
- `src-tauri/tests/mux_hot_upgrade.rs` — the integration test and its helpers.

### Files to Modify
- `test/README.md` — document the new integration test and how to run it.

## Design

Follow the existing mux integration test's structure: an isolated runtime
directory so the test never touches the user's daemon, a daemon spawned as a
child process with that environment, a readiness poll on the socket, raw frame
helpers speaking the mux protocol directly, and a cleanup guard that stops the
daemon and removes the directory even when the test fails.

### Main scenario

1. Start a daemon in an isolated runtime directory and create a pane running a
   plain shell.
2. Drive the shell to record its own process id and to create a marker file
   whose name the test chose.
3. Trigger the upgrade and wait for the daemon to answer again.
4. Drive the same pane to report its shell's process id again and to report
   whether the marker file exists, reading the answers back through the pane's
   output.
5. Assert that the process id is unchanged and the marker is reported present.

Reading a shell's answers out of pane output is inherently timing-sensitive.
Use unambiguous, uniquely-marked output the test can scan for, and poll with a
bounded timeout rather than a fixed sleep, so the test fails with a clear
message instead of flaking.

### Additional scenarios

- **Handoff logging**: after the upgrade, the daemon's log contains the
  handoff-start marker and the adopted pane count (FR11).
- **Zero panes**: upgrading a daemon with no panes succeeds and leaves it
  serving.
- **Incompatible schema**: an upgrade whose probe answer does not cover the
  document version aborts, and the original daemon still answers a handshake
  with its panes intact.

### Test command

The test runs under the integration-test command already recorded in
workflow.yaml. Because it spawns real processes and real terminals, it runs
single-threaded, and every wait is bounded by an explicit timeout.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: After an upgrade, the shell running in a pane reports the same
      process id it reported before the upgrade.
- [ ] AC-2: After an upgrade, that same shell can still observe a file it
      created before the upgrade.
- [ ] AC-3: After an upgrade, the daemon's log contains a handoff-start entry
      including the adopted pane count.
- [ ] AC-4: Upgrading a daemon with no panes succeeds and the daemon still
      answers a handshake afterwards.
- [ ] AC-5: An upgrade rejected by the schema probe leaves the original daemon
      answering handshakes with its pane still live.
- [ ] AC-6: Every scenario runs against an isolated runtime directory and
      leaves no daemon process or temporary directory behind, including when
      an assertion fails.
- [ ] AC-7: No scenario waits without a bounded timeout; a stuck step fails
      with a message naming the step.
- [ ] AC-8: `test/README.md` documents the new test file and its run command.

## Test Notes

This task's deliverable is the tests themselves, so the usual test-first
ordering means writing each scenario before the assertions it needs are
satisfiable. Where a scenario depends on behaviour another task delivers, the
scenario is still written first and is expected to fail until the integration
branch carries that behaviour — do not weaken or delete a scenario to make it
pass. The Unix-only gate matches the rest of the feature.

## Out of Scope

- Any production-code change: this task adds tests and documentation only. A
  defect this test exposes is reported, not fixed here.
- Performance measurement.
