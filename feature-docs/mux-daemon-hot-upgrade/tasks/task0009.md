# Task Plan: task0009 — Wire the upgrade path and make descriptor inheritance actually work

## Goal

Make the hot-upgrade path functional end to end: connect the daemon to the
real snapshot/restore implementation, keep the inherited descriptors alive and
correctly flagged across the process replacement, validate what is adopted, and
make the announcement reach clients before the runtime dies.

This is a **rework task** synthesized from review round 1 (residual
critical/high findings). It deliberately owns all three files of the upgrade
path in one task: round 1's critical defect was caused by splitting these
interlocking changes across parallel tasks, so that the wiring between them
belonged to nobody.

## Requirements

FR3, FR4, FR5, FR6, FR7, FR8, FR9, FR10, FR11, FR13, FR14, FR17, FR18, FR19,
NFR1, NFR2, NFR4, NFR5

### Descriptor lifetime (the core of this task)

The invariant to establish and test: **every descriptor recorded in the handoff
document is (a) close-on-exec cleared and (b) still open at the moment the
process image is replaced**, and after a handoff start **every adopted
descriptor has close-on-exec set again** so it never reaches a pane child.

Today neither half holds: the wired snapshot clears nothing, and the listener
plus the whole session manager are dropped when the accept loop returns. Note
that the second half is currently masked — the upgrade refuses to proceed while
any pane is live — so fixing only the wiring turns a "refuses to work" bug into
a "kills every shell" bug. Both halves must land together.

Deliberately keeping a descriptor open past the end of its owner's scope is the
crux; choose an approach that makes the ownership transfer explicit rather than
relying on a value happening to stay alive.

### Adoption validation

Adopting the listener must be as defensive as adopting a pane master already
is: check that the recorded number refers to a live, listening Unix-domain
socket *before* taking ownership, and on failure take no ownership at all (so
the failure path cannot close a descriptor belonging to someone else) and fall
back to a fresh bind. This matters most on the in-process re-entry after a
failed replacement, where the recorded number is very likely to have been
reused by the new runtime's own internals.

### Announcement delivery

The announcement must be observably written to connected clients before the
runtime is torn down. Queueing it on a broadcast channel is not delivery.
Establish a synchronization point that the daemon waits on (bounded), and make
the test assert on what reached the socket rather than what entered the queue.

### Single ownership

One owner for the handoff file's whole lifetime (path, creation with its
hardening, read, removal), and one source for the supported schema range. The
duplicates are what let the wired and unwired halves disagree in round 1.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: An upgrade requested while panes are live proceeds — it is no
      longer refused — and the resulting handoff document contains those panes
      with their descriptors, child process ids, identifier counters and the
      original incarnation token.
- [ ] AC-2: Every descriptor recorded in the handoff document has close-on-exec
      cleared at the moment the run outcome is returned, asserted by querying
      descriptor flags.
- [ ] AC-3: Every descriptor recorded in the handoff document is still open at
      the moment the run outcome is returned — neither the listener nor any
      pane master has been closed by a drop.
- [ ] AC-4: After a handoff start, every adopted descriptor (listener and each
      pane master) has close-on-exec set, and a pane child spawned afterwards
      does not inherit the listener or any other pane's master.
- [ ] AC-5: A handoff start restores the session tree, identifier counters and
      incarnation token from the document rather than falling back to a fresh
      session manager.
- [ ] AC-6: Adopting a recorded listen descriptor that is not a live listening
      Unix socket fails without taking ownership of it (the descriptor is still
      open and unchanged afterwards) and the daemon falls back to a fresh bind.
- [ ] AC-7: The upgrade announcement is written to a connected client's socket
      before the run outcome is returned, asserted by reading it from the
      client side rather than from the broadcast queue.
- [ ] AC-8: The handoff file's path, creation, read and removal have exactly
      one implementation, the file is created with owner-only permission and
      without following an existing symlink, and it is removed after a
      successful read, a failed read, and an aborted snapshot.
- [ ] AC-9: The probe subcommand's output is derived from the canonical
      supported-schema-version range; a test fails if the two ever diverge.
- [ ] AC-10: `mux upgrade` exits non-zero and reports the daemon's reason when
      the daemon refuses the upgrade, and reports success only after observing
      evidence that the replacement actually happened.
- [ ] AC-11: A descriptor that fails adoption during restore is closed, not
      leaked.
- [ ] AC-12: The `--no-default-features` build still compiles.

## Test Notes

AC-2, AC-3, AC-6 and AC-11 are descriptor-state assertions — query the flags
and liveness directly rather than inferring from behaviour, following the
existing close-on-exec tests. AC-4 needs a real spawned child to inspect what
it inherited. AC-7 needs a stand-in client that reads from its socket, not a
subscriber that polls the queue. AC-1 and AC-5 can run in-process (snapshot
then restore) against a real PTY pair without an actual process replacement;
the full replacement is covered by the existing integration test, which should
be re-run and is expected to pass once this task lands.

Where a criterion cannot be expressed as an automated test, say so explicitly
rather than weakening the criterion.
