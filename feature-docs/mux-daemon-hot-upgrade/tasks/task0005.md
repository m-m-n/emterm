# Task Plan: task0005 — CLI surface: upgrade command, schema probe, and the replacement

## Goal

Give users and the recovery path a way to trigger an in-place upgrade, give a
running daemon a way to ask a candidate binary what it can restore, and
perform the process replacement at the one place where it is safe.

## Requirements

FR7, FR13, FR14, FR15, FR16, NFR4

## Scope

### Files to Modify
- `src-tauri/src/mux/cli.rs` — the `upgrade` subcommand, the handoff probe
  subcommand, their usage text, and the daemon entry point that performs the
  replacement after the async runtime has been shut down.
- `src-tauri/src/mux/daemon.rs` — change the legacy-recovery path to attempt an
  upgrade before falling back to the existing shutdown-then-respawn, and widen
  the visibility of the connect/handshake helpers the new CLI paths need.

## Design

### `upgrade` subcommand

Slots into the existing mux subcommand dispatch table and its usage text.
Behaviour:

1. Resolve the socket; report clearly when no daemon is running.
2. Connect and complete the handshake, tolerating a daemon one protocol
   version behind exactly as the existing recovery helper does, so a
   mismatched daemon can still be asked to upgrade.
3. Send the upgrade request message.
4. Poll until a daemon answering the current protocol version is reachable
   again, bounded by a timeout, and report success or timeout.

On non-Unix targets the subcommand reports that in-place upgrade is not
supported and exits with a non-success status, leaving today's behaviour
untouched (IMPLEMENTATION.md, Conventions).

### Handoff probe subcommand

A mux subcommand that prints the inclusive range of handoff schema versions
this binary can restore and exits successfully. It must not touch the socket,
must not read or write daemon state, and must produce output a caller can
parse unambiguously. This is the answer side of IMPLEMENTATION.md D3; the
asking side lives in task0004.

### Performing the replacement

The synchronous daemon entry point currently creates an async runtime and
blocks on the daemon. It now inspects the daemon's run outcome
(IMPLEMENTATION.md Shared Components, daemon run outcome):

- normal termination → today's behaviour;
- upgrade requested → fully shut the async runtime down first, then replace
  the process image with the target binary, argument vector and environment
  addition the outcome carries (IMPLEMENTATION.md D1).

If the replacement fails, log at error level and re-enter service in this same
process by starting the daemon in handoff mode over the document that was just
written (task0004's contract, SPEC.md A14) rather than exiting.

### Recovery path

The legacy-recovery helper currently shuts a mismatched daemon down, which
kills every pane. It now attempts an upgrade first: send the upgrade request,
wait a bounded time for a daemon answering the current protocol version, and
only on timeout fall back to the existing shutdown-then-respawn path. A daemon
built before this feature does not recognise the request and silently discards
the frame, so the timeout is the expected route for those and must not be
treated as an error.

Keep the helper's existing shape of taking its respawn action as a substitutable
parameter so the fallback remains unit-testable.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `upgrade` appears in the subcommand dispatch table and in the
      usage text, and an unknown subcommand still reports usage as today.
- [ ] AC-2: Against a stand-in daemon that accepts the handshake, the
      subcommand sends the upgrade request message and reports success once
      the stand-in becomes reachable at the current protocol version.
- [ ] AC-3: Against a stand-in daemon that never becomes reachable, the
      subcommand reports a timeout with a non-success exit status and does not
      hang indefinitely.
- [ ] AC-4: With no daemon running, the subcommand reports that clearly
      without creating a socket or spawning a daemon.
- [ ] AC-5: The probe subcommand prints a parsable schema version range and
      exits successfully, without connecting to a socket.
- [ ] AC-6: The recovery helper attempts an upgrade before any shutdown —
      asserted against a stand-in that ignores the upgrade request, where the
      helper is observed to fall back to its respawn action only after the
      upgrade attempt.
- [ ] AC-7: The recovery helper does not fall back when the stand-in becomes
      reachable at the current protocol version after the upgrade request.
- [ ] AC-8: On a non-Unix build the subcommand reports unsupported, and the
      crate still compiles with default features and with no default features.

## Test Notes

Follow the existing daemon unit tests' stand-in-daemon pattern: a listener in
a plain thread that speaks the handshake and reads frames, with a temporary
directory for isolation. AC-6 and AC-7 exercise the recovery helper with its
substitutable respawn action so no real daemon is spawned. AC-8's non-Unix
half is a compilation concern — verify with the CLI-only check command from
workflow.yaml rather than a runtime test.

## Out of Scope

- The daemon-side upgrade branch and handoff startup (task0004).
- Snapshot/restore internals (task0003).
- Client reconnect after the announcement (task0006).
