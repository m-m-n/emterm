# Task Plan: task0001 — Handoff wire types and schema version in mux_ipc

## Goal

Add the upgrade control messages and the versioned handoff document type to
the mux IPC crate, so the daemon and CLI have a shared, version-checked
vocabulary for an in-place upgrade.

## Requirements

FR1, FR2, FR4, FR14, NFR6

## Scope

### Files to Create
- `crates/mux_ipc/src/handoff.rs` — handoff schema version constant, the
  handoff document type and its nested session/window/pane entries, and the
  version-checked decode entry point.

### Files to Modify
- `crates/mux_ipc/src/protocol.rs` — add the two new message types to the
  message-type enumeration and its byte conversion, keeping the protocol
  version constant unchanged.
- `crates/mux_ipc/src/lib.rs` — expose the new module.

## Design

### Message types

Two new control message types are added, both mirroring the existing shutdown
message's wire shape (type byte, pane id zero, empty payload):

- an upgrade request, sent client → daemon;
- an upgrade announcement, sent daemon → client immediately before the
  process is replaced.

Choose type byte values that do not collide with any existing or retired
value in the enumeration. Adding types must not change any existing structure,
so the protocol version constant stays as it is (IMPLEMENTATION.md D7). The
existing frame decoder already discards frames whose type byte it does not
recognise; the new types must inherit that behaviour rather than introducing
a new failure mode.

### Handoff document

A serde-encodable document describing everything a successor process needs.
Its shape is pinned in IMPLEMENTATION.md's Shared Components table — implement
exactly those fields, using the same encoding mechanism the crate already
applies to control-message payloads.

Two version-related items live here:

1. A schema version constant, versioned independently of the protocol version.
2. The inclusive range of schema versions this build can restore. Today that
   range contains only the current value; the range exists so that a future
   build can accept its predecessor's format.

Decoding is version-checked: a document whose version falls outside the
supported range fails with an error distinguishable from a malformed-bytes
error, and nothing is partially applied.

The document is a plain data type. It must not depend on any daemon-side type
(no PTY handles, no channels, no session-manager types) — the crate sits below
the daemon in the layer structure.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Both new message types round-trip through the crate's frame
      encode/decode helpers, preserving type, pane id, and empty payload.
- [ ] AC-2: A frame carrying a type byte that the decoder does not recognise
      is reported as "not a known message", not as an error that would tear a
      connection down — asserted for a byte value adjacent to the new ones.
- [ ] AC-3: The two new type byte values collide with no existing or retired
      value in the enumeration.
- [ ] AC-4: The handoff document round-trips through encode → decode with the
      session/window/pane tree, ID counters, incarnation token, descriptor
      numbers, child process ids and scrollback bytes all preserved
      byte-for-byte.
- [ ] AC-5: Decoding a document whose schema version is outside the supported
      range fails with a version-specific error, and that error is
      distinguishable from a malformed-payload error.
- [ ] AC-6: The protocol version constant is unchanged, asserted by a test.
- [ ] AC-7: A document containing zero sessions round-trips successfully.

## Test Notes

All criteria are unit-testable inside the crate with no daemon, no PTY and no
socket. Cover an empty document, a multi-session document, a pane recorded as
exited (no descriptor to adopt), and scrollback containing arbitrary bytes
including zero bytes and invalid UTF-8. Mirror the existing protocol tests'
style, including the existing test that pins the protocol version value.

## Out of Scope

- Producing or consuming the document from live daemon state (task0003).
- Sending or handling the new messages (task0004, task0005, task0006).
- Any descriptor manipulation.
