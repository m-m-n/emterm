# Task Plan: task0004 — Daemon upgrade branch, handoff startup and fallback

## Goal

Make the daemon act on an upgrade request: announce it, snapshot state, hand
the replacement over to its synchronous caller, and — when started in handoff
mode — resume from the handed-over state instead of binding a fresh socket.

## Requirements

FR2, FR3, FR7, FR8, FR11, FR13, FR17, NFR2, NFR5

## Scope

### Files to Modify
- `src-tauri/src/mux/ipc/connection.rs` — handle the upgrade request message
  next to the existing shutdown handling, and broadcast the upgrade
  announcement to connected clients.
- `src-tauri/src/mux/daemon.rs` — upgrade signalling channel, the accept
  loop's upgrade branch, handoff-mode startup, and the run outcome the
  synchronous caller acts on.

## Design

### Request handling

The connection layer gains an arm for the upgrade request message alongside
the existing shutdown arm. It signals an upgrade watch channel rather than the
shutdown watch channel, so the two paths cannot be confused. Errors detected
during the subsequent preparation are reported back over the requesting
client's still-open connection.

### Accept-loop upgrade branch

When the upgrade signal fires, the accept loop leaves its select and takes a
branch that:

1. Asks the candidate binary which handoff schema versions it can restore
   (task0005's probe contract) and aborts the upgrade if the answer does not
   cover the version about to be written (IMPLEMENTATION.md D3).
2. Takes the session-manager lock and snapshots state to a handoff file
   (task0003's contract), which also clears close-on-exec on the listen
   descriptor and every live pane's master descriptor.
3. Broadcasts the upgrade announcement to every connected client, so clients
   arm their reconnect path (IMPLEMENTATION.md D2).
4. Returns the "upgrade requested" outcome carrying the target binary path,
   the argument vector, the environment addition naming the handoff file, and
   the handoff file path.

This branch must **not** call the existing pane-killing shutdown helper and
must **not** remove the socket file — both are what today's recovery path does
and both are exactly what this feature exists to avoid. The listen descriptor
also stays open, so connection attempts arriving mid-upgrade stay queued in
the kernel backlog (IMPLEMENTATION.md D4).

Any failure in steps 1–2 aborts: the daemon reports the reason to the
requesting client, logs it at a level that survives release filtering, removes
any partial handoff file, and returns to the accept loop unchanged.

### Handoff-mode startup

At daemon start, the presence of the handoff environment variable
(IMPLEMENTATION.md Shared Components) selects handoff startup:

- The normal socket bind and stale-socket cleanup are skipped.
- The listen descriptor recorded in the document is adopted as the daemon's
  listener.
- The session tree is restored (task0003's contract).
- The handoff file is removed.
- A log line distinguishable from a normal start records that this is a
  handoff start, together with the number of panes and descriptors adopted.
- The environment variable is cleared so it is not inherited by pane children
  spawned afterwards.

If restoring fails, the failure is logged at error level, the handoff file is
still removed, and the daemon continues as best it can rather than exiting
silently.

### Replacement failure recovery

The synchronous caller performs the replacement (task0005). If it fails, the
process re-enters service in the same process by restoring from the handoff
document it just wrote (IMPLEMENTATION.md D1, SPEC.md A14). This task owns the
entry point that makes that possible: handoff-mode startup must be callable
for a document the current process itself produced, not only for one produced
by a predecessor.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: An upgrade request received on a client connection triggers the
      upgrade branch, not the shutdown branch — asserted by observing that the
      pane-killing shutdown helper is not invoked and no pane is marked
      exited.
- [ ] AC-2: The upgrade branch does not remove the socket file.
- [ ] AC-3: When the schema probe reports an incompatible range, the upgrade
      aborts, no handoff file remains, and the accept loop continues serving.
- [ ] AC-4: When snapshotting fails, the upgrade aborts, an error is reported
      to the requesting client, no handoff file remains, and the accept loop
      continues serving.
- [ ] AC-5: On a successful preparation, the upgrade announcement is
      broadcast to every connected client before the run outcome is returned.
- [ ] AC-6: The returned run outcome carries the target binary path, argument
      vector, environment addition and handoff file path.
- [ ] AC-7: With the handoff environment variable set to a valid document, the
      daemon start path skips socket bind, adopts the recorded listener,
      restores the session tree, removes the handoff file, and emits a log
      line identifying the start as a handoff start including pane and
      descriptor counts.
- [ ] AC-8: With the handoff environment variable absent, the daemon start
      path behaves exactly as today (binds the socket, no handoff logging).
- [ ] AC-9: The handoff environment variable is not visible to a pane child
      spawned after a handoff start.

## Test Notes

AC-1 through AC-6 are testable against a session manager built with the
existing test-only pane constructor plus a substitutable probe, following the
existing daemon tests that assert on shutdown behaviour. AC-7 through AC-9 use
a document produced by the snapshot path over a real PTY pair and a listener
bound in the test, so no second process is needed. The end-to-end replacement
is covered by task0008. Keep tests Unix-gated.

## Out of Scope

- The `upgrade` subcommand, the probe subcommand, and performing the
  replacement itself (task0005).
- Client-side reconnect (task0006).
- Snapshot/restore internals (task0003).
- The message types themselves (task0001).
