# Task Plan: task0003 — Persist shift_enter_behavior through the settings-window boundary (rework)

## Goal

The settings window's load/save boundary carries `shift_enter_behavior`
end-to-end, so all three values persist and display through the panel; a
present-but-null new key resolves per FR5.

## Requirements

FR1, FR5, FR6

## Scope

### Files to Create

- (none)

### Files to Modify

- `crates/app_settings/src/settings.rs` — add `shift_enter_behavior` to the
  shared settings schema (wire values per the IMPLEMENTATION.md contract,
  default `alt_enter`); fold the legacy boolean into it during the schema's
  migration step (true → `alt_enter`, false → `none`); stop serializing the
  legacy key.
- `src-tauri/src/settings_window/commands.rs` — tests driving the real
  load/save command round-trip proving `none` and `kitty_csi_u` survive.
- `src-tauri/src/settings.rs` — FR5 null-precedence fix: track presence of
  the new key separately from its nullable value so a present `null`
  resolves to the default and wins over the legacy key.
- `src-tauri/src/settings_store.rs` — extend/adjust round-trip coverage to
  the production boundary (not only a hand-built patch).

## Design

Review round 1 findings driving this task (reviews/round1.yaml):
`rd1-app-settings-schema` (critical), `rd1-store-legacy-retained` (high),
`rd1-null-legacy-precedence` (medium).

- The child settings window round-trips the full settings object through
  the shared schema in `crates/app_settings`; today that schema drops the
  new key on load and save. Adding the field with the wire contract's
  values and default closes the gap; the schema's serialization no longer
  emits the legacy boolean.
- Migration lives in both deserialization paths consistently: legacy key
  only → mapped value; new key present (including null) → new key
  semantics win; neither → default.
- Null-precedence: distinguish "key absent" from "key present with null".
  Present null → default (`alt_enter`), and the legacy key is ignored.
