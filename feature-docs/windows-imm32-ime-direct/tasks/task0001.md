# Task Plan: task0001 — IMM32-direct cursor area on Windows + deferred IME detach

## Goal

Eliminate the Windows + CorvusSKK "not responding" freeze: the Windows
cursor-area IME notification bypasses winit's mutex-holding request path by
calling IMM32 directly from the bridge's Windows window sink, and the IME
detach is deferred until the composition has ended. Non-Windows targets and
the CLI-only build keep their current behavior.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3

## Scope

### Files to Create

- none

### Files to Modify

- `src-tauri/src/ime/winit_bridge.rs` — Windows-only IMM32-direct
  cursor-area sink in the production `BridgeWindow` implementation;
  composition-aliveness tracking and detach-hold behavior in the bridge's
  flush; new unit tests for the deferred detach; module-docs update
  describing the new routing.
- `src-tauri/Cargo.toml` — add the `Win32_UI_Input_Ime` feature to the
  existing `windows-sys` dependency under
  `[target.'cfg(windows)'.dependencies]`.

## Design

The integration seam is the existing `BridgeWindow` abstraction: bridge
state (recording, dedup, deferred flush from `about_to_wait`) above, the
platform window sink below. Both stay in place; this task changes what the
Windows sink does for the cursor area, and adds one hold rule to the flush.

### 1. Split point (FR1 / FR4 / FR5)

- The production window sink splits ONLY the cursor-area delivery by compile
  target: on Windows it performs the IMM32 recipe below; on every other
  target it keeps the current winit-routed delivery, byte-for-byte
  unchanged.
- The allow-state delivery stays winit-routed on ALL targets. Enable must
  keep flowing through winit because winit gates all WM_IME_* processing on
  its own IME-capabilities state (FR4); bypassing Enable would stop
  `WindowEvent::Ime` delivery entirely.
- Testability rule (feature convention, see IMPLEMENTATION.md): every
  DECISION — when to hold, when to deliver — lives in platform-neutral
  bridge state exercised by host-run unit tests; the `#[cfg(windows)]` sink
  is a thin, decision-free executor of the recipe, verified by the windows
  cross-target compile gate plus the feature-level real-device manual gate.

### 2. Windows IMM32 recipe — external-interface contract (FR2 / FR6 / NFR3)

Executed entirely inside the flush that `window_host` runs from
`about_to_wait`, i.e. on the event-loop thread — this satisfies IMM32's
calling-thread requirement with no new threading machinery (NFR3). The sink
must not be callable from any other path.

1. Obtain the Win32 window handle (HWND) from the winit window through the
   raw-window-handle trait (`rwh_06::HasWindowHandle`; the dependency
   already exists). If the handle is unavailable or is not a Win32 handle,
   return without doing anything (same silent no-op posture as the
   null-context case).
2. Acquire the window's input-method context (`ImmGetContext`).
3. If the context is null, return without any further IMM32 call (no-op —
   FR2's defined error case).
4. Set the composition window: style `CFS_POINT`, current position
   `(x, y + height)`, area rectangle `(x, y, x + width, y + height)`.
5. Set the candidate window: style `CFS_EXCLUDE`, current position `(x, y)`,
   area rectangle `(x, y, x + width, y + height)`.
6. Release the context (`ImmReleaseContext`) — always paired with a
   successful acquisition, regardless of the outcome of steps 4-5.

| Call | Style | Current position | Area rectangle |
|------|-------|------------------|----------------|
| composition window | `CFS_POINT` | `(x, y + height)` | `(x, y, x + width, y + height)` |
| candidate window | `CFS_EXCLUDE` | `(x, y)` | `(x, y, x + width, y + height)` |

`x` / `y` / `width` / `height` are physical pixels, passed through without
conversion. The recipe never touches winit's request path, so no
winit-internal lock is held during these calls — that lock being held across
them is the settled root cause of the freeze.

### 3. Deferred detach (FR3)

New bridge-level composition-aliveness state:

- Opens when the bridge observes the winit Enabled event; closes ONLY when
  the bridge observes the winit Disabled event.
- The existing `ime_enabled` flag is NOT this tracker: `notify_focus(false)`
  clears `ime_enabled` immediately for key-suppression reasons (the FR10
  gate-release from the earlier feature), which would make the composition
  look dead before the flush runs. The aliveness state must survive focus
  loss until Disabled actually arrives.

Flush behavior around the held detach:

- Pending allow-state is a detach AND a composition is alive → the flush
  leaves it pending: not delivered, not dropped. A held detach does NOT
  block cursor-area delivery — a pending cursor area still flushes in that
  same turn.
- Pending allow-state is an enable → never held; delivered as today.
- No composition alive → a pending detach is delivered on that flush,
  exactly as today.
- After Disabled is observed, the next flush delivers the held detach
  exactly once (delivery consumes the pending state, so a further flush
  delivers nothing).
- `pending_allow` stays last-writer-wins: a focus-in recorded while a detach
  is held overwrites it, and the detach is then never delivered.
- Accepted failure mode (SPEC-settled): if Disabled never arrives, the
  detach stays held — the IM server remains attached to an unfocused window
  until the next focus-in overwrites the pending state. No timeout
  machinery.
- Drop path: unchanged (immediate direct detach, pending state discarded) —
  the mid-composition bridge-swap hole is a known residual, out of scope.

The deferral is platform-neutral (it lives in the bridge, above the sink),
matching the SPEC architecture diagram. FR5 is protected by AC-4 below plus
the feature-level Linux manual spot check (VERIFICATION TS6, verify phase).

### 4. Manifest change (FR6 / NFR1)

The existing `windows-sys` 0.59 dependency gains the `Win32_UI_Input_Ime`
feature. The point/rect types the IMM32 structures need come from the
already-enabled `Win32_Foundation` feature. No new crate, no version change,
no change to the pinned winit dependency, no `[patch.crates-io]`.

      Disabled not yet), focus loss followed by a flush delivers no detach
      call to the mock window; after Disabled arrives, the next flush
      delivers the detach exactly once, and a further flush delivers
      nothing.

## Test Notes

- AC-1, AC-2, AC-3, AC-5 → unit tests in the existing `winit_bridge.rs`
  test module, using the established mock-window pattern (shared mock with
  snapshot-based assertions; assert on snapshots, never across a held lock —
  the existing mutex-poisoning caveat in that module applies to new tests
  too).
- Existing tests discharge the constructor's recorded initial enable with a
  first flush before asserting; new tests follow the same convention.
- Composition aliveness is driven through the bridge's winit-event entry
  (Enabled / Disabled) and focus through the backend's focus notification —
  all host-runnable; no Windows host is needed for any FR3 test.
- Edge worth covering: Enabled → Disabled → focus loss → flush delivers the
  detach immediately (composition already closed when focus was lost).
- AC-4 is verified by running the full existing suite via gate 1 of AC-6;
  the criterion is green WITHOUT edits to any pre-existing test.
- The `#[cfg(windows)]` sink has no host-executable test by design; its
  gates are the windows cross-target check (AC-6 gate 3) and the
  feature-level real-device manual scenario (VERIFICATION TS5 — verify
  phase, not this task).

## Out of Scope

- Forking or patching winit (`[patch.crates-io]` included); filing an
  upstream winit issue or PR.
- Deferring the `Drop`-path detach (known residual hole, deliberately kept).
- Any change to `app.rs` / `window_host.rs` call sites (the flush wiring
  already exists) or to the key-suppression gate semantics.
- The unrelated Wayland DnD issue.
- Real-device Windows verification (feature-level manual gate in
  VERIFICATION.md, executed in the verify phase by the user).
