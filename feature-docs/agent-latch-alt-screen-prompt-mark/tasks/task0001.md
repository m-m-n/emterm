# Task Plan: task0001 — Exclude alternate-screen OSC 133 candidates from the agent-status latch feed

## Goal

When one processing unit (one `process_combined` call on a plain tab) mixes
alternate-screen OSC 133 marks, an alternate-screen exit, OSC 777
agent-status reports (Set / Clear) and main-screen OSC 133 marks, the tab's
inferred-clear latch receives only the main-screen marks, each at its true
position relative to the reports, so the latch clears on the main-screen `A`
that follows the report.

## Design

### Why the walk misassigns marks today

Each pump, the plain-tab output pipeline drains two lists for the same bytes:
the latch feed (OSC 777 Set / Clear and OSC 133 mark candidates, in callback
order) and term_core's live marks (OSC 133 marks dispatched on the main screen
only). `reconcile_latch_feed` walks the feed once from the front, matching
each mark candidate against the next unconsumed live mark by kind alone.

The latch feed currently receives one candidate per recognized OSC 133 on
either screen. An alternate-screen candidate whose kind equals the next live
mark therefore consumes that live mark: the mark is emitted at the
alternate-screen candidate's position (ahead of the report), and the real
main-screen candidate after the report finds the live list exhausted and is
dropped.

### Candidate source rule (FR1)

The OSC 133 branch of the native callbacks receives the alternate-screen flag
term_core read at dispatch (the screen-aware notification). The branch adds a
latch-feed mark candidate only when that flag says the main screen — the same
rule it already applies to the OSC 7501 feed.

| Notification | Recognized kind (A / B / C / D) | Latch feed | OSC 7501 feed |
|---|---|---|---|
| screen-aware, alternate screen | yes | nothing | nothing (unchanged) |
| screen-aware, main screen | yes | one candidate of that kind | one candidate (unchanged) |
| screen-less (existing notification) | yes | one candidate (counts as main screen) | one candidate (unchanged) |
| any | no | nothing (unchanged) | nothing (unchanged) |

OSC 777 agent-status Set / Clear keep entering the latch feed on either
screen, in call order, at their own position (unchanged: they reach the feed
through the existing notification path, to which the screen-aware
notification forwards every non-OSC-133 action).

### Reconciliation (FR2)

`reconcile_latch_feed` keeps its signature, its contract and its single
forward walk. With every mark candidate in the feed now a main-screen
candidate, the feed's mark candidates and the same pump's live marks describe
the same marks in the same order, so the walk emits each live main-screen mark
at its own candidate's position relative to Set / Clear. Nothing in the
pipeline or the model re-derives alternate-screen state.

Contract after the change:

- Precondition: every mark candidate in one pump's latch feed was dispatched
  on the main screen (or arrived through the screen-less notification);
  Set / Clear entries are in call order.
- Postcondition: the resolved inputs hold every Set / Clear in original order
  and each candidate the pump's live marks confirm (front to back, kind match)
  at its own position; an unconfirmed candidate is dropped without consuming
  a live mark.
- Cost (NFR1): one pass over the feed, no blocking, no I/O (unchanged).

### Unchanged behavior (FR3, NFR2)

- Latch transitions: Set arms; a live main-screen D then a live main-screen A
  while armed applies the inferred clear through the existing Clear path; an
  A without a preceding D after Set does not clear; an explicit Clear disarms.
- Mux-attached pumps discard the latch feed.
- The OSC 7501 feed rule and its reconciliation.
- Every non-OSC-133 action delivered through the screen-aware notification
  leaves the same callback state as the screen-less notification, on either
  screen.

## Acceptance Criteria (MANDATORY)

Notation: `ESC[?1049h` / `ESC[?1049l` enter / leave the alternate screen
(likewise `?1047` and `?47`); `D` = OSC 133 `D;0` and `A` = OSC 133 `A`, both
BEL-terminated; `Set` = OSC 777 `emterm;agent-status;v=1;state=working`;
`Clear` = OSC 777 `emterm;agent-status;clear`; "main" / "alt" = emitted on
the main / alternate screen. "Latch inputs" = the tab's pending resolved latch
inputs after one `process_combined` call.

- [ ] AC-1 (FR1, FR2): A plain tab given `ESC[?1049h`, alt `D`, alt `A`,
  `ESC[?1049l`, `Set`, main `D`, main `A` in one `process_combined` call has
  latch inputs exactly [Set, Mark(CommandEnd), Mark(PromptStart)]. Applying
  the tab's pending agent-status events and latch inputs to a fresh
  agent-status model in batch-apply order (each Set / Clear input applies the
  next pending event, then records the latch Set / Clear; each Mark records a
  live prompt mark) leaves the tab's OSC 777 state cleared.
- [ ] AC-2 (FR1): AC-1 with the alternate-screen switch done through `?1047`
  and, separately, through `?47` gives the same latch inputs and the same
  cleared state.
- [ ] AC-3 (FR1, FR2): One call with `Set`, main `D`, `ESC[?1049h`, alt `A`,
  `ESC[?1049l`, `Clear`, main `A` gives latch inputs [Set, Mark(CommandEnd),
  Clear, Mark(PromptStart)]; the same with a second `Set` in place of `Clear`
  gives [Set, Mark(CommandEnd), Set, Mark(PromptStart)].
- [ ] AC-4 (FR1, FR2): Only main-screen marks reach the latch inputs, in
  order, when (a) the main marks precede the alternate-screen marks — `Set`,
  main `D`, main `A`, `ESC[?1049h`, alt `D`, alt `A`, `ESC[?1049l` gives
  [Set, Mark(CommandEnd), Mark(PromptStart)] — and when (b) several
  alternate-screen marks precede the main marks — `ESC[?1049h`, alt `D`,
  alt `A`, alt `D`, alt `A`, `ESC[?1049l`, `Set`, main `D`, main `A` gives
  [Set, Mark(CommandEnd), Mark(PromptStart)].
- [ ] AC-5 (FR1, FR3): At callback level, an OSC 133 of each recognized kind
  (A, B, C, D) delivered through the screen-aware notification with the
  alternate screen active adds nothing to the latch feed and nothing to the
  OSC 7501 feed; with the main screen active, and through the screen-less
  notification, it adds exactly one candidate of that kind to each feed; an
  unrecognized kind adds nothing to either feed on either screen; a
  screen-aware alt `A` followed by a screen-aware main `A` leaves exactly one
  latch-feed candidate.
- [ ] AC-6 (FR3, NFR2): The test whose name states the superseded behavior is
  renamed as in Design; `test-docs/osc7501-alt-screen-prompt-mark/task0001.tests.yaml`
  lists the new name under AC-3, carries a supersede note naming this
  feature's SPEC FR1, and keeps `red_reason` unchanged; every test name in
  that record appears in the `--lib` test listing; every other existing test
  named in Design keeps its name and passes.
- [ ] AC-7 (FR1, FR2, FR3, NFR1, NFR2): The `--lib` suite
  (`CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`)
  passes, including the existing agent-exit-after-icon latch tests (ac1..ac7,
  `reconcile_latch_feed_*`), the osc7501 / program_status_feed tests, the mux
  latch-feed discard tests and the screen-aware callback tests; `cargo check`
  passes with default features and with `--no-default-features` (commands in
  VERIFICATION.md).

## Test Notes

- AC-1 to AC-4 are end-to-end tests through the plain-tab output pipeline
  (the tab test harness's process-combined entry and its pending latch-input /
  agent-status-event drains), placed beside the existing
  `latch_feed_end_to_end_*` tests. AC-1, AC-2, AC-3 and AC-4 (b) fail before
  the change (the alternate-screen candidate consumes the live mark, so the
  real main-screen mark lands ahead of the report or is dropped). AC-4 (a)
  passes before the change; it pins that the existing order stays intact.
- Each new test asserts the full latch-input list, not only its length, so a
  reordering is caught.
- The AC-1 / AC-2 model application follows the batch-apply order stated in
  AC-1. The output-pipeline test module already holds a helper with this
  logic (it resolves a tab's OSC 777 state from its events and latch inputs);
  reuse it where its visibility allows, otherwise apply the same order in the
  new tests.
- AC-5 is covered by the callback tests listed in Design (updated) plus the
  unchanged main-screen / screen-less tests; their alternate-screen
  latch-feed assertions fail before the change.
- AC-6 resolution check: `.claude/rules/test-docs-records.md` names the
  `--lib` listing command. When that listing command is not permitted in the
  session, the approved `--lib` run output, which prints each executed test by
  name, serves the same check.
- Known non-deterministic failures under parallel load (tabs replay tests,
  tmux_sockets discover tests) go to the record's `baseline_failures` /
  `final_failures`; a failure outside that set is a real failure.
