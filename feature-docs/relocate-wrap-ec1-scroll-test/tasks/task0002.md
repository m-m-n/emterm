## Design

### 1. The three drift sites

Line numbers are as rustfmt reported them at the rework base; the enclosing
item is the durable identifier, since the reported line is the start of a
diff hunk and can shift.

| # | File | Reported line | Enclosing item | Shape of the drift |
|---|------|---------------|----------------|--------------------|
| 1 | `crates/term_core/src/print_handler/tests.rs` | 1131 | `test_write_grapheme_column_shifted_redraw_blanks_all_orphan_partners` (fn at line 1056) — the `expected: &[(u16, &str, u8)]` array literal | manual column alignment of the trailing `//` comments on the array's element lines; rustfmt normalizes the run of spaces before each comment |
| 2 | `crates/term_core/src/terminal_dispatch.rs` | 517 | `process_pty_data_pure_ascii_fast_path_matches_direct_handle_print` (fn at line 503) — the multi-line `assert_eq!` comparing `get_cell_char` | rustfmt re-wraps the macro call's argument layout |
| 3 | `crates/term_core/src/terminal_dispatch.rs` | 565 | `process_pty_data_ascii_overwrites_width0_without_wide_left_neighbor_leaves_it_untouched` (fn at line 568, its `{` on line 569) | same shape as site 2 |

Both `terminal_dispatch.rs` sites sit well inside the module opened by
`#[cfg(test)]` / `mod tests {` at lines 379-380, so neither is a production
line. The whole of `print_handler/tests.rs` is a `#[cfg(test)]` child module
(`print_handler.rs:673-674` declares `#[cfg(test)] mod tests;`), so site 1 is
not a production line either. FR8 / SPEC AC-5 therefore survive the fix; this
is the fact that makes the fix legitimate rather than a scope breach.

`crates/term_core/src/terminal_dispatch.rs` is not listed in SPEC.md's "File
Structure" block. That block describes the create-plan-phase edit set under
"Implementation Approach"; SPEC's normative freezes are its Constraints
section (production code, TS1, the two out-of-scope paths), and a
`#[cfg(test)]` module of `terminal_dispatch.rs` is in none of them. NFR5
("the touched Rust files pass the format check") stays satisfied because the
file becomes a touched file that passes.

### 2. How the reformat is produced

Run rustfmt per file, on exactly the two files above:

- Invoke `rustfmt` directly on each path (not `cargo fmt`), passing
  `--edition 2024` explicitly: bare rustfmt defaults to edition 2015 while
  the crate is edition 2024, and the repo-root `rustfmt.toml`
  (`style_edition = "2024"`, everything else at stable defaults) is picked up
  from the path's ancestry either way.
- A crate-wide `cargo fmt --manifest-path crates/term_core/Cargo.toml`
  (write mode) is prohibited: the project's standing rule is that crate-wide
  formatting pollutes unrelated files with unrelated diff noise. Only the
  `--check` form of that command is used, and only as the verification in
  AC-1.
- rustfmt's default child-module traversal reaches no additional file here:
  `print_handler/tests.rs` declares no `mod` item at all, and
  `terminal_dispatch.rs`'s only `mod` item is its inline `mod tests`.

The edit is whatever rustfmt writes — no hand-shaping of the result, and no
edit that changes a token. Assertion arguments, literal values, expected
values and comment text stay as they are; only whitespace and line breaking
move.

### 3. What must not move

- Every non-`#[cfg(test)]` line of the crate. The production diff against
  `workflow[implement].base_commit` (`2ccadc78`) must stay empty, exactly as
  verify observed it.
- The frozen tests of this feature:
  `test_relocate_widened_base_via_wrap_removes_stale_overflow_entries_on_target_row`,
  `test_relocate_widened_base_via_wrap_no_panic_when_column_one_does_not_exist`
  and `test_relocate_widened_base_via_wrap_scrolls_without_panic`. None of the
  three drift sites lies inside any of them (they start at lines 1454, 1590
  and 1564; the only `print_handler/tests.rs` site is at 1131, inside the test
  that starts at 1056 and ends before 1185).
- `crates/term_core/src/ring_buffer/tests.rs` and both test-docs records —
  untouched, so TS-2, TS-6 and SPEC AC-7 keep the verify-phase state they were
  confirmed in.

## Test Notes

- **Coverage is TS-4**, the existing VERIFICATION.md scenario ("full
  `term_core` lib suite plus the format check"). This task adds no test: the
  failed item is a gate the existing scenario already runs, and adding a
  scenario for "rustfmt is clean" would duplicate TS-4's format leg.
- **The red state already exists and is recorded.** `cargo fmt --check`
  exiting 1 at the rework base with those three drifts is the red observation;
  it is captured verbatim in `workflow.yaml`
  `workflow[verify].failed_items[0].note`. Re-run the check once before
  editing to confirm the same three sites are still reported, then once after
  for green. No production mutation is involved anywhere in this task.
- **Verify AC-3 by inspecting the diff, not by memory.** The drift sites in
  `terminal_dispatch.rs` are only ~140 lines below that file's production
  code; the check that matters is that the changed line numbers all exceed the
  `#[cfg(test)]` line (379 at the rework base).
- **A widening diff is a stop signal.** If rustfmt rewrites anything beyond
  the three sites described above, stop and report it as a plan deviation
  rather than committing the wider diff — the premise of this task is that the
  crate's only drift is those three sites.
