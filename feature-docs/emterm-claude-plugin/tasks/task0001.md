# Task Plan: task0001 — Marketplace and plugin manifests

## Goal

Create the marketplace catalog at the repository root and the plugin metadata file, along with the empty directory scaffold required for the plugin to load. Nothing else — no hook wiring, no skills, no README. This task exists so Claude Code can *see* the marketplace and plugin, even before any behavior is attached.

## Requirements

FR1, FR2, NFR3, NFR4.

## Scope

### Files to Create

- `.claude-plugin/marketplace.json` — marketplace catalog. Names the marketplace `emterm-plugins`, owner `{ "name": "m-m-n" }`, points `metadata.pluginRoot` at `./plugins`, and lists one plugin entry `{ "name": "emterm", "source": "emterm", "description": "...", "version": "0.1.0" }`. See SPEC.md §Implementation Approach for the skeleton.
- `plugins/emterm/.claude-plugin/plugin.json` — plugin metadata (name / version / description) that is internally consistent with the marketplace entry (same name and version).

### Files to Modify

None.

## Design

- Both files are minimal JSON: keys as specified in SPEC.md skeletons; no fields beyond what SPEC.md requires (YAGNI).
- Every JSON file is UTF-8, no BOM, terminated with a trailing newline.
- Nothing in either file uses an absolute path or a path escaping the plugin directory. This is a hard rule enforced by NFR3 — validated by task0002's static integration test.

## Acceptance Criteria

- [ ] AC-1: `.claude-plugin/marketplace.json` exists, parses as valid JSON, and contains exactly the fields SPEC.md FR1 requires (name, owner, description, metadata.pluginRoot, plugins[0].{name,source,description,version}).
- [ ] AC-2: The single `plugins[0]` entry uses `name: "emterm"`, `source: "emterm"`, `version: "0.1.0"`.
- [ ] AC-3: `plugins/emterm/.claude-plugin/plugin.json` exists, parses as valid JSON, and its `name` and `version` match the marketplace entry exactly.
- [ ] AC-4: `plugins/emterm/.claude-plugin/plugin.json` contains a non-empty `description`.
- [ ] AC-5: A `bun test` run passes (no existing tests broken; the manifest static checks in task0002 will validate this task's outputs as a side effect).

## Test Notes

This task ships no runtime code, so it has no dedicated unit tests. The static integration tests in task0002 (JSON validity, marketplace ↔ plugin consistency) cover its outputs. That's the intended coverage split: manifests are declarative and are best tested by the same static checks the hook wiring task owns.

If task0002's tests happen not to land in the same round (they will, but hypothetically), this task can add its own JSON-parse smoke test to prevent an unnoticed typo.

## Out of Scope

- Hook configuration or scripts (task0002).
- Any SKILL.md files (task0003).
- README (task0004).
- Making `emterm` actually installable via `/plugin install` end-to-end (verify phase POC).
