# Task Plan: task0003 — Display and mux skills

## Goal

Ship the seven SKILL.md files that expose `emterm`'s rich-display CLI (markdown/json/yaml/image) and mux API (read/send/wait) as Claude Code skills. All skills are thin wrappers: their body tells the model to invoke the matching `emterm` subcommand on the arguments the user supplies.

## Requirements

FR5, FR6, NFR3.

## Scope

### Files to Create

- `plugins/emterm/skills/display-markdown/SKILL.md`
- `plugins/emterm/skills/display-json/SKILL.md`
- `plugins/emterm/skills/display-yaml/SKILL.md`
- `plugins/emterm/skills/display-image/SKILL.md`
- `plugins/emterm/skills/mux-read/SKILL.md`
- `plugins/emterm/skills/mux-send/SKILL.md`
- `plugins/emterm/skills/mux-wait/SKILL.md`

### Files to Modify

None.

## Design

### SKILL.md shape

Each file:

- YAML frontmatter with `name` (kebab-case, matching the directory name) and a `description` in English. `description` must state (a) what the skill does and (b) *when* Claude should auto-invoke it — Claude Code's skill selector reads this line, so a vague description equals a skill that never fires.
- Body (Markdown): one short section that instructs the model to run the corresponding `emterm` subcommand on the file/argument the user gave. Include the exact CLI form.
- No trigger words in the description that would cause false-positive activation (e.g. "any file" is too broad).

### Per-skill invocation mapping

| Skill directory | Invocation the body must direct |
|-----------------|---------------------------------|
| `display-markdown` | `emterm markdown <file>` |
| `display-json` | `emterm json <file>` |
| `display-yaml` | `emterm yaml <file>` |
| `display-image` | `emterm image <file> [--protocol kitty|sixel]` — document the optional `--protocol` argument |
| `mux-read` | `emterm mux read ...` — arguments passed through; delegate pane resolution to the CLI |
| `mux-send` | `emterm mux send ...` |
| `mux-wait` | `emterm mux wait ...` |

### Assumptions the skill body should make explicit

- `emterm` is expected on PATH. If missing, the user sees the shell's not-found error (skills, unlike hooks, do surface errors — this is intended so users know to install `emterm`).
- Pane resolution for mux skills uses the eMterm CLI's existing `EMTERM_PANE_ID` mechanism; the skill body should not re-explain it.

## Acceptance Criteria

- [ ] AC-1: All seven SKILL.md files exist at the paths above.
- [ ] AC-2: Each SKILL.md's `name` frontmatter matches its directory name exactly.
- [ ] AC-3: Each SKILL.md's `description` is a non-empty English single sentence stating the trigger condition.
- [ ] AC-4: Each SKILL.md body instructs the model to invoke the exact `emterm` subcommand from the mapping table above.
- [ ] AC-5: `display-image`'s body documents the optional `--protocol kitty|sixel` argument.
- [ ] AC-6: No SKILL.md references an absolute path or a path outside `plugins/emterm/`.

## Test Notes

Skill content is prose; automated tests are limited to a static scan (frontmatter present, `name` matches directory, `description` non-empty). Keep the scan in a single Bun test file (`plugins/emterm/skills/skills.test.ts`) that walks the seven directories — or fold it into task0002's test file if that's cleaner. If added, this file is a modification the implementer may make; note the deviation in the completion report.

Meaningful verification of skill behavior (does Claude actually pick the right skill for a given prompt?) is human-judgment and lives in the verify phase manual scenarios.

## Out of Scope

- Runtime testing of the skills against a live Claude Code session (verify phase).
- Documenting install / prerequisites (task0004 / README).
