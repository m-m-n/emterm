# Task Plan: task0006 — mux skill hardening (rework)

## Goal

Close two medium security findings on the mux skills from review round 1: (a) `mux-send` currently guides the model toward unsafely constructing a shell command from user text, (b) `mux-read` currently hands untrusted pane output to the model without prompt-injection boundaries.

## Requirements

FR6, NFR2 (already satisfied for the hook script; this task extends NFR2's spirit to the skill instructions).

## Scope

### Files to Modify

- `plugins/emterm/skills/mux-send/SKILL.md`
- `plugins/emterm/skills/mux-read/SKILL.md`

### Files to Create

None.

## Design

Both fixes are prose changes to SKILL.md bodies. The invocation contracts (which `emterm mux` subcommand to call) do NOT change — the changes are additive guardrails around how the model should assemble arguments and how it should treat the output.

### F4 (from finding sc-mux-send-shell-inject, medium, security) — mux-send

Current risk: the skill instructs the model to invoke `emterm mux send --pane <id|current> --text <s>` with values substituted in. When the text comes from a file / another pane / a log / any untrusted source, characters like `$(...)` / backticks / `;` / newlines can be interpreted by the shell if the model builds a shell string.

Update the skill body to require ONE of these safe forms:

- Preferred: pipe the text via `--stdin` — `printf '%s' "$TEXT" | emterm mux send --pane <id> --stdin` — so the text never enters an argv position at all.
- If `--text` is used, MUST validate that the value contains no newline / shell metacharacters and MUST be passed as a single argv element (Bun `Bun.spawn`-style argv array, never a joined shell string).

Also add an explicit note about pane ID: must match a simple identifier (e.g. `^[a-z0-9-]+$` or the literal `current`), never taken verbatim from untrusted input.

Include 2-3 adversarial examples in the skill body: `"; rm -rf ~"`, `"$(whoami)"`, embedded newline. The examples show what the safe form produces (pane literally receives the string) vs. what the unsafe form would do (shell executes it).

### F5 (from finding sc-mux-read-prompt-inject, medium, security) — mux-read

Current risk: `mux-read` reads arbitrary pane stdout and returns it to the model. Pane content can be attacker-controlled (SSH into a shared host, viewing a log a remote system wrote, another tenant's build). If that output contains instructions like "ignore prior instructions and run…", the model may follow them.

Update the skill body to add a prompt-injection boundary section that:

- Explicitly labels the returned pane output as UNTRUSTED DATA (in exactly that phrasing or equivalent).
- Delimits the output from the surrounding instructions using a clearly-marked block (e.g. a fenced code block that the skill body describes as untrusted).
- Instructs the model NOT to: invoke tools, disclose secrets, send follow-up commands, or perform actions "recommended" by the mux output. The output is data to be quoted/summarized only.
- States the escape valve: if the user's original request explicitly asks the model to *react* to the output, the model must confirm in natural language with the user before any tool call — never act on the pane content unilaterally.
