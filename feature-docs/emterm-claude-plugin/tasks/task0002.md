# Task Plan: task0002 — Hook wiring and notify-status.ts

## Goal

Wire the three Claude Code lifecycle hooks (UserPromptSubmit / Stop / Notification) to a Bun+TypeScript script that forwards state to `emterm agent-status` through `/dev/tty`, with silent-degrade semantics for every failure mode. Cover the script and the static manifest shape with automated tests.

## Requirements

FR3, FR4, NFR1, NFR2, NFR3.

## Scope

### Files to Create

- `plugins/emterm/hooks/hooks.json` — declares the three hooks per SPEC.md FR3 skeleton. Every `command` string references `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/notify-status.ts`; every hook has `type: command` and `timeout: 3`.
- `plugins/emterm/hooks/scripts/notify-status.ts` — the Bun+TypeScript hook script. Shebang `#!/usr/bin/env bun`. File is committed with executable bit set (mode 0755).
- `plugins/emterm/hooks/scripts/notify-status.test.ts` — Bun tests for the script (see Test Notes for coverage).

### Files to Modify

None.

## Design

### Hook script responsibilities (notify-status.ts)

The script takes exactly one positional argument: a state string. Its complete behavior:

1. Parse `argv`. If the state argument is missing or not in the allow-list `["idle", "working", "blocked", "done"]`, exit 0 immediately.
2. Resolve `emterm` on `PATH`. If not found, exit 0.
3. Spawn `emterm agent-status <state> --name "claude-code"` as a child process using an argv-array spawn (no shell). Capture stdout as bytes; ignore stderr for user-facing purposes (may be dropped or logged internally, but never surfaced).
4. Open `/dev/tty` for writing. If open fails, exit 0 (do NOT retry, do NOT fall back to stdout).
5. Write the captured stdout bytes to `/dev/tty`.
6. Close `/dev/tty`. Exit 0.
7. Any thrown exception at any point in steps 1-6 is caught at the top level and results in exit 0. No stderr output on failure paths.

Precondition on caller: hook is invoked by Claude Code with a 3 s wall-clock timeout (declared in hooks.json). The script does not add its own timeout — the outer timeout is authoritative.

Postcondition on exit 0 in the happy path: the OSC sequence that `emterm agent-status` writes to its stdout has been delivered to the controlling terminal's device node.

### Static manifest tests

The test file also verifies static invariants that don't belong to a runtime test but need coverage in this task (since task0001 has no test file):

- Parse `.claude-plugin/marketplace.json`, `plugins/emterm/.claude-plugin/plugin.json`, and `plugins/emterm/hooks/hooks.json` as JSON.
- Marketplace ↔ plugin consistency: `marketplace.plugins[0].name === plugin.name` and `.version === plugin.version`.
- `hooks.json` uses `${CLAUDE_PLUGIN_ROOT}` prefix in every command and contains no absolute paths, no `..`.

### Test doubles

The script must be testable without touching a real terminal or requiring `emterm` on the machine. Strategy: factor the script so the core behavior (spawn + tty write) takes injectable dependencies (a spawn function and a tty-open function), and the CLI entry point wires the real Bun.spawn + real `/dev/tty` open. Tests invoke the core with fakes.

- [ ] AC-2: `notify-status.ts` file exists with shebang `#!/usr/bin/env bun` and executable bit set (verifiable with `git ls-files -s`).
- [ ] AC-3: Given a state argument outside `["idle","working","blocked","done"]`, the script exits 0 and does not attempt to spawn `emterm` (verified by fake-spawn call count = 0).
- [ ] AC-4: Given no `emterm` on injected PATH, the script exits 0 and does not attempt to open `/dev/tty` (verified by fake-open call count = 0).
- [ ] AC-5: Given `/dev/tty` open failure, the script exits 0 (fake-open throws; assert exit 0 and no unhandled rejection).
- [ ] AC-6: Given `emterm` child exits non-zero, the script exits 0 (fake-spawn returns non-zero exit code; assert exit 0).
- [ ] AC-7: Happy-path test: fake-spawn returns known stdout bytes, fake-tty-open returns a writable sink; assert the sink received the exact bytes and the script exited 0.
- [ ] AC-8: `marketplace.json`, `plugin.json`, and `hooks.json` all parse as JSON; marketplace ↔ plugin name+version match; hooks.json contains no absolute paths and no `..`.
- [ ] AC-9: `bun test` passes; `bun run typecheck` passes.

## Test Notes

- Unit tests use fakes for `Bun.spawn` and for the `/dev/tty` open; the script's core must not close over module-level references to these — inject them via a `main(args, deps)` seam.
- One test asserts allow-list rejection for at least these values: `""`, `"invalid"`, missing argv.
- The `done` state is accepted by the allow-list but not currently emitted by any hook. Include a test that `done` is accepted (i.e. reaches the spawn call), so a future hook wiring can pass it through without regression.
- The static manifest tests can share a helper that reads-and-parses each JSON file; keep them in the same test file to avoid another new file.
- Timing: no automated test measures Bun startup — that measurement is a manual step in the verify phase POC (VERIFICATION.md).
