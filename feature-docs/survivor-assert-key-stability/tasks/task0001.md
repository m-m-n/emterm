# Task Plan: task0001 — survivor row key-stability and content observations

## Goal

The blank-push row-scope test observes both that the survivor row's ring slot
key is still the key that backs viewport row 0 after the scroll, and that the
survivor row's own content survived — so a regression confined to the blank-push
routine's Step 3 fill target turns the test red instead of passing.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4

### Files to Create

None. This task creates no files.

### Files to Modify

- `crates/term_core/src/ring_buffer/tests.rs` — the only permanent change: two additive observations inserted into the post-scroll survival block of the blank-push row-scope test, alongside the assertions already there
- `crates/term_core/src/ring_buffer.rs` — transient only: a deliberate mutation is introduced here for the red-check and then fully restored, so this file must carry no diff when the task finishes (see Acceptance Criteria AC-6 and Out of Scope)

## Design

### What the test currently observes, and what it misses

The test drives a terminal core through a fixture that prints one base character
carrying a run of combining marks into a row, captures that row's ring slot key
before scrolling, issues a line feed, and then asserts that the captured key is
still present in the overflow table and in the overflow reverse index.

Presence of the key is all it checks. It never checks that the key still
resolves to the survivor row, and never checks that the survivor row still holds
anything. A defect that blanks the survivor row while leaving the overflow-side
clear pointed at the correct row therefore leaves every existing assertion
satisfied, which is precisely the orphan-entry retention this task exists to
catch.

### The two observations to insert

Both go into the same post-scroll survival block, after the line feed, next to
the existing presence assertions.

1. **Key stability.** Assert that resolving viewport row 0 to its absolute ring
   slot key yields the key captured before the scroll, narrowed to the key's own
   numeric type. This is the observation the block's comment already claims to
   make. Precondition: the key was captured before the line feed. Postcondition
   on success: the viewport shifted, and the survivor row's slot identity did
   not.

2. **Content survival.** Read the leading cell of viewport row 0 through the
   cell grapheme accessor (column first, then row — the argument order the
   full-screen-scroll test in the same file already uses) and assert it equals
   the grapheme the fixture printed: the base character followed by its combining
   marks, in the fixture's own order. Postcondition on success: the row was not
   blanked. A blanked row yields an emptied cell, which stops reporting itself as
   an overflow cell and therefore reads back as a halfwidth space — that is the
   difference this observation detects.

Derive the expected grapheme from the fixture's own mark sequence inside the
test rather than transcribing a literal from this document
(IMPLEMENTATION.md decision D3).

### Processing flow of the enlarged test

1. Construct a terminal core explicitly, as the test already does.
2. Fixture prints the base character and applies its combining marks; the row is
   captured together with its ring slot key.
3. Existing pre-scroll anti-vacuity assertions run — retained unchanged.
4. Line feed: the blank-push routine rotates the ring and fills its Step 3
   target rows.
5. Survival block:
   a. existing overflow-table and reverse-index presence assertions — retained;
   b. new key stability observation;
   c. new content survival observation.
6. Existing recycled-row removal post-assertions run — retained unchanged.

### The red-check procedure

This is a local verification procedure, not part of the deliverable
(IMPLEMENTATION.md decision D2). Run it after the two observations are in place.

1. In the blank-push routine's Step 3, corrupt **only** the fill target's slice
   index — for example by deriving the fill base from the ring head as it stands
   *after* the rotation — while leaving the bottom-most absolute row value handed
   to the overflow clear and reverse-index clear routines correct. Keeping the
   overflow side correct is what makes the check meaningful: it is the shape of
   defect the existing assertions cannot see.
2. Run the crate's unit-test command and confirm the blank-push row-scope test
   is now red, and that it is the content observation that reports the failure.
3. Restore the production file to its original content.
4. Re-run the unit-test command and confirm the whole suite is green again.
5. Confirm the production file shows no diff.

If step 2 stays green, the observations are not positioned where the defect is
visible — treat that as the task being incomplete, not as the check passing.

## Test Notes

- **Where the TDD cycle lives.** The deliverable *is* test code, so the usual
  "write the test first" loop is inverted: the red phase is the red-check
  procedure above. Add the two observations, then prove they can fail by
  injecting the Step 3 mutation, then restore and confirm green. An observation
  that was never seen to fail has not been shown to observe anything, so
  treat AC-4 as the gate on AC-1 and AC-2 rather than as an afterthought.
- **Expect the key observation to stay green under the mutation.** The mutation
  leaves the overflow-clear side pointed at the correct row, so AC-1's assertion
  and all pre-existing assertions pass through it unaffected. Only AC-2's content
  observation turns red. This is expected and is the reason the content
  observation is mandatory; do not "fix" it by strengthening the key observation
  instead.
- **Determinism.** The additions read only the test's own terminal core. They
  introduce no global state, no filesystem access, no clock read, no process
  spawn and no sleep, so the test stays deterministic under the suite's parallel
  execution and adds no measurable runtime (NFR3, NFR4).
- **Suite scope.** Run the crate's unit-test command, not a workspace-wide run —
  the change cannot affect anything outside this crate, and the crate-scoped run
  is the one the requirements name.
- **Edge case worth a moment's thought.** A blanked survivor row is not an
  absent row: it reads back as a halfwidth space rather than failing to read.
  The content observation must compare against the expected grapheme, not merely
  check for non-emptiness, or the blanked case slips through again.

## Out of Scope

- Changing any production behaviour, including the blank-push routine's fill
  target. The mutation is transient verification only and must not survive the
  task.
- Adding, removing, renaming or restructuring any other test in the crate.
- Rewriting or "improving" the assertions that already exist in this test — the
  change is strictly additive.
- Changing the visibility of any accessor. The lookup the key observation uses is
  crate-internal and the test is in the same crate, so it is already reachable.
- Adding a test crate, dependency, helper module, shared fixture or coverage
  tool.
- Broadening the test to cover scroll regions, alternate screens, or resize
  behaviour. This test pins the lifetime and scope of the overflow-side tables
  and nothing else.
