# Task Plan: task0001 — Distinguish notification-worker loss from queue saturation in NotifyQueue::try_submit

## Goal

`NotifyQueue::try_submit` reports the loss of the notification worker (the
receiving side of the queue has been dropped) as its own outcome, with a
dedicated error-level log record emitted once per queue and never suppressed by
the saturation-episode flag. Queue-saturation behavior stays exactly as it is.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/callbacks.rs` — split the send-result handling of NotifyQueue::try_submit into accepted / full / disconnected branches; add the two worker-gone outcomes to SubmitOutcome, the LOG_NOTIFY_WORKER_DEAD constant, and the independent worker-gone suppression flag on NotifyQueue.
- `src-tauri/src/callbacks/tests.rs` — add the worker-gone unit tests to the worker_thread module.

## Design

### Send-result branches in `try_submit`

The non-blocking send into the bounded channel has three outcomes. Each is
handled by its own branch; no catch-all error branch remains.

| Outcome | Saturation flag (`armed`) | Worker-gone flag | Log record | Returned `SubmitOutcome` |
|---|---|---|---|---|
| accepted | set back to armed (unchanged) | not read, not written | none | the existing accepted outcome (unchanged) |
| full (receiver alive) | existing atomic check-and-disarm (unchanged) | not read, not written | warn `LOG_NOTIFY_QUEUE_SATURATED` at episode start only (unchanged) | `DroppedEpisodeStart` / `DroppedAlreadyWarned` (unchanged) |
| disconnected (receiver dropped) | not read, not written | atomic check-and-set | error `LOG_NOTIFY_WORKER_DEAD`, only when this call set the flag | `WorkerGoneReported` when this call set the flag, otherwise `WorkerGoneAlreadyReported` |

### New `SubmitOutcome` variants

- `WorkerGoneReported` — the receiving side is gone, the notification was
  dropped, and this call emitted the worker-gone error record.
- `WorkerGoneAlreadyReported` — the receiving side is gone, the notification
  was dropped, and no record was emitted because an earlier call on the same
  queue already emitted it.

The pair mirrors `DroppedEpisodeStart` / `DroppedAlreadyWarned`: whether a
record was emitted is decidable from the return value alone. Existing variants
keep their names and meanings.

### Worker-gone suppression flag

- A new atomic boolean field on `NotifyQueue`, separate from `armed`.
  `NotifyQueue::new` initializes it to "not yet reported"; the constructor's
  signature and return shape do not change.
- Only the disconnected branch touches it, through a single atomic operation
  that sets it and yields the previous value. A previous value of "not yet
  reported" makes this call the reporter.
- It is never cleared while the queue lives. The accepted branch's re-arm of
  `armed` does not reset it.
- Invariant: for one `NotifyQueue`, across any number of concurrent producers,
  exactly one call returns `WorkerGoneReported` and at most one worker-gone
  error record is emitted.
- The flag guards only the log emission and publishes no other data; the same
  memory-ordering discipline as `armed` is sufficient.

### Log constant and record

- `LOG_NOTIFY_WORKER_DEAD` is a public string constant placed in the same log
  constant section as `LOG_NOTIFY_QUEUE_SATURATED`. Its text states that the
  notification worker is gone and the notification was dropped, and differs
  from the saturation text.
- The record is emitted at error level in the same shape as the saturation
  warn: the constant, then `: `, then the output of `redact_notification` for
  the dropped notification's title and body (length and diag_id only). The
  notification's title and body text never appear in the record.

### Boundaries kept

- The `NotificationSink` trait signature (`send(&self, title: &str, body: &str)`,
  `Send + Sync`) and the `NotifyRustSink::send` contract toward its callers do
  not change; `NotifyRustSink::send` keeps discarding the outcome.
- `try_submit` performs no blocking operation and nothing that depends on the
  notification daemon, in any branch.
- Neither the change nor the new tests sit behind a platform gate (no
  `cfg(unix)` / `cfg(windows)`).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: For a queue built with `NotifyQueue::new(NOTIFY_QUEUE_CAPACITY)` whose receiving side has been dropped, the first `try_submit` returns `WorkerGoneReported`, and neither `DroppedEpisodeStart` nor `DroppedAlreadyWarned`.
- [ ] AC-2: After the receiving side is dropped, repeated `try_submit` calls on the same queue return `WorkerGoneReported` on the first call only and `WorkerGoneAlreadyReported` on every later call; no call returns a saturation variant.
- [ ] AC-3: With the receiving side held and not drained, submitting until `try_submit` returns `DroppedEpisodeStart` (saturation flag disarmed), then dropping the receiving side, makes the next `try_submit` return `WorkerGoneReported`.
- [ ] AC-4: With the receiving side dropped and the queue shared across several threads that call `try_submit` concurrently, exactly one of all returned outcomes is `WorkerGoneReported` and every other one is `WorkerGoneAlreadyReported`.
- [ ] AC-5: `LOG_NOTIFY_WORKER_DEAD` is a public constant whose text differs from `LOG_NOTIFY_QUEUE_SATURATED`.
- [ ] AC-6: The existing tests `queue_drops_the_ninth_submission_without_blocking_when_receiver_is_idle`, `saturation_episode_warns_exactly_once_then_rearms_after_a_successful_submission` and `concurrent_saturated_drops_produce_exactly_one_episode_start_warning` pass without modification.
- [ ] AC-7: The tests for AC-1 to AC-5 are in the worker_thread module of `src-tauri/src/callbacks/tests.rs` (not platform-gated), use neither `NotifyRustSink` nor notify-rust / D-Bus, and `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib` passes.

## Test Notes

- AC-1 to AC-4 are unit tests in the worker_thread module, one per criterion
  (SPEC.md TS1 to TS4). They follow the module's existing approach: build the
  queue with `NotifyQueue::new`, act on the receiving side obtained at
  construction directly, and judge outcomes by return value only, without
  capturing logs.
- AC-3 reuses the saturation setup of the existing tests (submit capacity + 1
  while holding the receiving side) and asserts `DroppedEpisodeStart` before
  dropping the receiving side, so the "saturation flag disarmed" precondition
  is proven inside the test.
- AC-4 mirrors `concurrent_saturated_drops_produce_exactly_one_episode_start_warning`:
  share the queue across threads, release them together to raise contention,
  collect every outcome, and count.
- AC-5 is a single assertion comparing the two constants.
- AC-6 and AC-7 are satisfied by running the full `--lib` suite; no existing
  test is edited.
- The redaction rule (NFR3) and the unchanged `NotificationSink` boundary
  (NFR1) are not observable without log capture or are structural; they are
  checked in review against the Design section.
- SPEC.md assumption A1: once the receiving side is dropped, the channel
  reports "disconnected" even when it is full. If a test shows otherwise,
  report it as a plan deviation instead of working around it.

## Out of Scope

- Restarting the worker after it dies.
- Changing when notifications fire, or the rate limit.
- Changing the saturation-episode semantics, the `NotificationSink` trait, or
  `NotifyRustSink`.
- Adding log-capture test infrastructure.
