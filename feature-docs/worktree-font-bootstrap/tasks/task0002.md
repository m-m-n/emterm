# Task Plan: task0002 — Bootstrap-verification script

## Goal

A single command reproduces the reported situation end to end: it builds from an
isolated, un-fetched tree with no cache restore, runs the reported command, and
fails when the library test suite does not execute — while also covering the
fetch-failure and already-fetched paths.

## Requirements

FR6

## Scope

### Files to Create

- `scripts/verify-font-bootstrap.sh` — the bootstrap-verification entry point:
  isolates a tree per scenario, runs the three scenarios, reports each
  scenario's outcome under a stable identifier, and aggregates them into one
  exit status.

### Files to Modify

None.

## Design

Read IMPLEMENTATION.md first. The Shared Components table pins the four
contracts this script observes and must not re-derive: the acquisition script's
invocation contract, the opt-out switch's name and semantics, the actionable
message's two literal lines, and this script's own entry-point contract
(invocation form, argument-free, exit-code meaning). D6 pins the isolation
requirement, D8 pins the failure shapes, and the Conventions section pins the
single-acquisition-path rule that constrains how failure may be induced.

**The build-script change this script verifies is implemented by a different
task and is therefore absent from this task's own worktree.** That is expected
and is exploited by AC-5: in a tree without the bootstrap, the un-fetched
scenario must be reported as failing. Write every assertion against the pinned
contracts above, never against the current contents of the build script.

### Scenario responsibilities

| Scenario id | Starting state | What it does | Passes when |
|-------------|----------------|--------------|-------------|
| un-fetched | An isolated tree whose font directory is empty, obtained with no cache restore and no font bytes copied in | Runs the reported command — the library-test command from the project's `main` component, with the project's designated quick-check target directory | The command completes and the run reports a non-zero count of executed tests |
| fetch-failure | The same isolated, empty-font starting state, plus an environment in which the acquisition path cannot succeed | Runs a GUI build | The build stops, its output carries both lines of the actionable message verbatim and identifies D8's shape 3, and the tree's font directory still holds no partial or unverified file |
| already-fetched | An isolated tree whose fonts have been populated through the acquisition path itself | Runs a GUI build | The build performs no download — the acquisition path either is not invoked or reports every file as already up to date — and no font file is rewritten |

### Reporting contract

- Every scenario reports exactly one outcome line carrying its stable
  identifier and a pass/fail verdict, using the `verify_font_bootstrap.`
  diagnostic prefix established in IMPLEMENTATION.md Conventions.
- A failing scenario also emits enough of the observed output to diagnose the
  failure without re-running the script.
- Scenarios run to completion independently: one failing scenario does not
  prevent the others from running, so a single run reports the full picture.
- The script's exit status is zero if and only if every scenario passed.

### Isolation and cleanup

- Each scenario gets its own tree. The repository's primary checkout is never
  used as a scenario's build tree, and its font directory is never populated or
  emptied by this script.
- Whatever a scenario creates — trees, build output, scratch directories — is
  removed when the script finishes, including when a scenario fails. Nothing is
  left behind that a later run would inherit.
- The script never requires elevated privileges and writes nothing outside the
  repository's ignored paths and its own scratch area.

### Inducing the fetch failure

Per the single-acquisition-path rule, failure is induced **by environment
manipulation only** — for example by giving the build a `PATH` in which the
acquisition path's required tooling cannot be resolved. Substituting, stubbing,
shadowing or copying the acquisition script is prohibited: it would create the
second acquisition mechanism FR5 forbids, and it would make the scenario stop
testing the real path.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `scripts/verify-font-bootstrap.sh` exists and satisfies its pinned
      entry-point contract: invoked from the repository root with no arguments
      and no required environment variables, it runs to completion and exits
      zero if and only if every scenario it ran passed.
- [ ] AC-2: The un-fetched scenario starts from an isolated tree whose font
      directory is empty, with no cache restore and no font bytes copied in,
      runs the reported library-test command, and treats both "the build script
      stopped the build" and "zero tests executed" as failures of that
      scenario.
- [ ] AC-3: The fetch-failure scenario induces failure by environment
      manipulation only, and requires all three of: the build stopping, both
      lines of the actionable message appearing verbatim, and the font
      directory containing no partial or unverified file afterwards. It does
      not pass on a bare non-zero exit alone.
- [ ] AC-4: The already-fetched scenario populates the fonts through the
      acquisition path and then requires that the measured build performs no
      download and rewrites no font file.
- [ ] AC-5: Each scenario's outcome is reported on its own line under a stable
      identifier, and the aggregate exit status is non-zero when any scenario
      fails. Demonstrated concretely in this task's own worktree, where the
      build-script bootstrap is absent: the run exits non-zero and names the
      un-fetched scenario as the failing one, while the fetch-failure and
      already-fetched scenarios still report their own verdicts.
- [ ] AC-6: A completed run — passing or failing — leaves the repository's
      primary checkout unchanged: no font file added or removed there, no
      scenario tree, scratch directory or build output left behind, and no
      write outside the repository's ignored paths and the script's own scratch
      area.

## Test Notes

- The script is itself the test vehicle, so the TDD cycle is inverted in a
  useful way: write each scenario so that it fails first against the current
  tree, then confirm the failure reason is the one intended. AC-5 makes that
  first failure a permanent, checkable property rather than a transient state.
- AC-6 is verified by capturing the state of the primary checkout's font
  directory and of the scratch area before and after a run, in both the passing
  and failing directions, and comparing.
- The un-fetched scenario needs real network access and a real toolchain. Guard
  against a false pass caused by an environment problem: a scenario that could
  not start (no toolchain, no network at all) reports as a failure with a
  distinguishable reason rather than being skipped silently.
- Scenario runs are slow — each performs a real build. Keep them sequential and
  independent rather than introducing parallelism, which would make the
  isolation guarantee of AC-6 harder to hold.
- "No download occurred" in the already-fetched scenario is asserted from the
  acquisition path's own reported behavior (every file up to date, no download
  line), which is the strongest signal available without a network-isolation
  facility; IMPLEMENTATION.md records this limitation.
