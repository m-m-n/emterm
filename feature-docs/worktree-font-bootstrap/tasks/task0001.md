# Task Plan: task0001 — GUI build-time font bootstrap in the build script

## Goal

The GUI build script, on finding any bundled font missing, bootstraps the whole
set once through the project's single acquisition path into the building
worktree's own font directory — or, when the explicit opt-out is engaged or the
attempt does not succeed, stops the build with a diagnostic that names the
failure shape followed by today's actionable message.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR8, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6, NFR7

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/build.rs` — the bundled-font check becomes a bootstrap gate: it
  keeps the GUI feature gate and the seven-path set, adds the opt-out read, the
  single acquisition invocation with a pinned destination, the four
  distinguishable failure shapes, and the deliberate rerun-condition
  declarations.

## Design

Read IMPLEMENTATION.md first — D1 (destination pinning), D2 (exactly one
attempt), D3 (opt-out semantics), D4 (attempt on every host), D5 (rerun
conditions) and D8 (four failure shapes) are the binding cross-task decisions
for this task, and the Shared Components table pins the acquisition script's
invocation contract, the opt-out switch and the actionable message. This
section adds only what is local to this task.

### Responsibilities inside the build script

| Element | Responsibility |
|---------|----------------|
| Feature gate | Unchanged: nothing in this task runs unless the GUI feature is enabled. The CLI-only path still returns before the font check is reached. |
| Presence check | Evaluates all seven relative font paths (the set is fixed by FR1 and is not edited) against the building worktree's font directory, and reports which of them are absent. |
| Bootstrap decision | Given "at least one absent" and the opt-out's state, decides between: stop immediately (opt-out engaged), or attempt once then re-check. |
| Acquisition invocation | Launches the acquisition script exactly once, per the Shared Components contract: interpreter resolved from `PATH`, script passed as an argument, working directory set to the worktree root, destination supplied absolutely and overriding any inherited value. |
| Failure reporting | Classifies the outcome into one of D8's four shapes, emits that shape's diagnostic context, then the actionable message verbatim, then (shape 1 only) the bash-availability line, and stops the build. |
| Rerun declarations | Declares the seven font paths and the opt-out switch as cargo rerun inputs, per D5. |

### Processing flow

1. The feature gate decides whether this logic runs at all; the CLI-only build
   returns beforehand, exactly as today.
2. Declare the rerun inputs: the seven font paths and the opt-out switch. These
   declarations do not depend on how far the check subsequently gets.
3. Evaluate the seven paths against the destination derived from the manifest
   location. If all seven are present, the gate is satisfied and the build
   continues — with no invocation, no environment inspection beyond step 2, and
   no network access.
4. At least one is absent. If the opt-out is engaged, stop now: emit the
   opt-out diagnostic context, then the actionable message, naming one absent
   path. Nothing that could reach the network is prepared on this path.
5. Otherwise attempt the acquisition exactly once. Classify the outcome:
   - launch failed because the interpreter is unavailable → shape 1;
   - launch failed for another reason → shape 2;
   - ran and exited non-zero → shape 3, carrying the exit status and the
     script's own error output;
   - exited zero → continue to step 6.
6. Re-evaluate all seven paths. All present ⇒ the build continues. Any still
   absent ⇒ shape 4, naming a still-absent path.
7. Every shape from steps 4–6 ends the build; none is downgraded to a warning,
   and no further attempt is made.

### Invariants this task must not break

- The seven relative paths and the position of the GUI feature gate are
  unchanged (FR1).
- The acquisition script is not modified, not copied, not wrapped, and not
  replaced; no second way of obtaining font bytes is added (FR5).
- The handling of `viewer/dist`, `settings/dist` and the Windows icon resource
  inside the build script is untouched (FR8).
- Writes reach only the building worktree's own font directory and whatever
  staging location the acquisition script already uses (NFR4).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With the GUI feature disabled, a build performs no font check, no
      acquisition invocation and no network access; and with it enabled, the
      checked path set is exactly the seven paths named in FR1. The build
      script's handling of `viewer/dist`, `settings/dist` and the Windows icon
      resource is unchanged by this task's diff. (FR1, FR8, NFR5)
- [ ] AC-2: With the GUI feature enabled, at least one font absent, and the
      opt-out not engaged, the acquisition script is invoked exactly once per
      build-script execution, with its destination resolved to the building
      worktree's own font directory derived from the manifest location; the
      same result holds when the build is driven from an arbitrary working
      directory and when an unrelated destination value is already present in
      the environment. No font byte is written outside that directory. (FR2,
      FR5, NFR4)
- [ ] AC-3: With the opt-out engaged and at least one font absent, zero
      acquisition attempts occur on any host, no network access takes place,
      and the build stops with both lines of the actionable message present
      verbatim in its output. With the opt-out engaged and all seven fonts
      present, the build succeeds normally. (FR3, FR4, NFR7)
- [ ] AC-4: Each of D8's four failure shapes is distinguishable in the build's
      output and carries its own cause — the launch error for shapes 1 and 2,
      the exit status together with the acquisition script's preserved error
      output for shape 3, and the still-absent path for shape 4. Both lines of
      the actionable message appear verbatim on all four shapes, and shape 1 —
      and only shape 1 — additionally states that bash must be made available
      first, because re-running the suggested command cannot remedy the absence
      of the interpreter it needs. (FR4)
- [ ] AC-5: After any failing attempt, the building worktree's font directory
      contains no partial, unverified or leftover staging file. (NFR3)
- [ ] AC-6: With all seven fonts present and hash-matching, the build makes no
      acquisition invocation at all and performs no network access and no
      re-download. (NFR2)
- [ ] AC-7: In a tree where the fonts were fetched during a build, running the
      same cargo command again with no source change does not re-run the build
      script and does not start another acquisition; and changing the opt-out
      switch's value does cause the build script to re-run. (NFR6)

## Test Notes

- The build script is not reachable from the crate's own test harness, so the
  acceptance criteria are verified behaviorally, by driving builds under
  controlled conditions and asserting on the build's output, on the contents of
  the font directory, and on whether the build script re-ran. The implementer
  writes those scenario checks first (they are the failing tests of the TDD
  cycle) and then implements until they pass.
- Recommended scenario set, each a fresh tree whose font directory is empty:
  (a) fonts absent, opt-out unset, network available → build proceeds, seven
  fonts land in this tree; (b) fonts absent, opt-out engaged → shape "opt-out",
  message present, directory still empty; (c) fonts absent, the acquisition
  script's required tooling removed from the child's `PATH` → shape 3, exit
  status and preserved error output present, directory still empty; (d) all
  seven present → no invocation and no network; (e) build twice with no source
  change → the second run does not re-run the build script.
- Shape 1 is awkward to produce on a Linux development host, where the
  interpreter is always present. Cover it by driving the gate with an
  environment whose `PATH` cannot resolve the interpreter at all, which is the
  same condition a bash-less Windows host presents.
- Shapes 2 and 4 are also awkward: shape 2 can be produced by making the script
  path unreadable; shape 4 by leaving the destination unwritable so the script
  can exit zero on a no-op path while the fonts remain absent. If either proves
  impractical to stage, assert on the classification logic's decision table
  instead of on a staged build, and record which criterion was covered that way.
- The steady-state and convergence checks (AC-6, AC-7) must run in a tree that
  has just fetched, not in one that was pre-populated, because the point of
  AC-7 is the interaction between the write and cargo's change tracking.
- Do not leave a scenario's fetched fonts in the repository's primary checkout;
  every scenario runs in its own tree.
