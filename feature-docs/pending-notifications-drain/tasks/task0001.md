# Task Plan: task0001 — Remove the never-drained OSC 9 notification buffer

## Goal

Delete the pending OSC 9 notification buffer from the shared native callback
state — the field, the push site in the OSC 9 handler, and the doc comment
describing a drain contract that does not exist — and re-point the two tests
that observed that buffer at the notification sink's receive log, leaving
notification behaviour bit-for-bit identical.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/callbacks.rs` — remove the pending-notification buffer field
  and its doc comment from the shared callback-state struct; remove the push
  into that buffer from the OSC 9 handler's emit branch, leaving the inline
  synchronous sink delivery as the sole statement of that branch.
- `src-tauri/src/callbacks/tests.rs` — rewrite the two assertions that read the
  removed field so they assert on the test sink's receive log instead.

## Design

See IMPLEMENTATION.md for the cross-task decisions this task implements (D1
single-task rationale, D2 remove-don't-replace, D3 inline delivery retained,
D4 sibling fields untouched, D5 static verification of the absence property).
They are not restated here.

### Production change (callback layer)

1. The shared callback-state struct loses exactly one field: the pending OSC 9
   notification buffer holding raw `(title, body)` pairs. Every sibling field
   of that struct — including all the other pending/queue/counter fields —
   keeps its declaration, its type and its doc comment untouched.
2. The doc comment attached to that field is deleted together with it. Nothing
   else in the file may lose a comment; sibling comments that describe a
   tab-side drain are accurate and stay.
3. In the OSC 9 handler, the emit branch (the branch taken when the rate
   limiter permits delivery) loses the statement that locks the shared state
   and appends the pair to the buffer. Its remaining content is the existing
   inline synchronous sink delivery, with the same arguments in the same order.
4. The suppression branch — the redacted warn line under the existing marker
   constant — is not touched, and neither is the title-fallback parsing that
   precedes the rate-limiter decision.

Contract of the handler after the change:

- Precondition: an OSC 9 payload string, plus whatever title the preceding
  OSC 0/2 events left in the shared state (used only as the fallback title).
- Postcondition (emit path): exactly one synchronous sink delivery with the
  parsed title and body; no process-local structure holds a reference to
  either string after the call returns.
- Postcondition (suppressed path): no delivery, one redacted warn line;
  unchanged from today.
- Invariant: delivery target, delivery count, delivery ordering and delivery
  timing are identical before and after this task.

### Test change (callback layer test module)

5. The single-OSC-9 emit test drops the assertion that reads the removed
   buffer's length. Its existing assertions on the sink's receive log — one
   entry, expected title, expected body — become the sole evidence of the
   emit, and must remain as strong as they are today.
6. The OSC 133 no-op test replaces its assertion that the removed buffer is
   empty with an assertion that the test sink received nothing at all. Its
   other assertions (that the title and the viewer-request queue are
   untouched) stay exactly as they are, so the test keeps its meaning: OSC 133
   mutates no native callback state and triggers no notification.
7. No other test in the file changes. In particular the fallback-title test
   and the three rate-limiter tests keep their bodies verbatim.

## Test Notes

- **This task is behaviour-preserving, so a classic red→green cycle is not
  available for most criteria — do not manufacture an artificial failing
  test.** The honest sequence is: (1) adjust the two test assertions onto the
  sink receive log first and confirm they pass against the current,
  still-buffering code (characterization step — this proves the new assertions
  really observe the emit); (2) perform the production removal; (3) confirm the
  same assertions still pass and the crate compiles; (4) run the static
  absence checks for AC-1/AC-3. Step (1) failing would mean the sink-based
  assertions do not actually observe the behaviour, which is exactly the signal
  worth having before the removal.
- AC-1 and AC-3 are absence properties: verify them by searching the two files
  rather than by a unit test (IMPLEMENTATION.md D5). AC-3's search must be
  narrow enough not to flag the sibling fields' legitimate drain comments.
- AC-2 is verified by the compiler (the field is gone) plus a read of the
  final diff (no new field, no new collection). No runtime memory-inspection
  test is expected or wanted.
- Unit tests are in the library target; a test run scoped to the binary target
  reports zero tests and proves nothing.
- The OSC 133 test currently holds a guard on the shared state while
  asserting. The new sink assertion reads a different lock — keep the two
  acquisitions non-overlapping rather than nesting them, so the file does not
  establish a lock-ordering precedent between the callback state and the sink.
- Edge cases already covered and to be kept green: OSC 9 without a separator
  falling back to the preceding OSC 2 title; identical pairs within the
  one-second window being suppressed; distinct pairs never being deduped.
