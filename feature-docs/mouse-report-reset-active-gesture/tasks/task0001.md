# Task Plan: task0001 — Decision layer: reset preserves held gestures, left release always completes the local drag

## Goal

A reset raised because mouse tracking is inactive no longer erases the
gesture-ownership slot of a physically-held button, and a left release that is
not report-owned always names the local selection-completion arm, so an
interleaved wheel notch or second button press can no longer strand the drag
flag.

## Requirements

FR1, FR2, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5

## Design

Read IMPLEMENTATION.md first: D1 (reset trigger distinction), D2 (the
exclusion lives in the application step), D3 (the no-owner release gate), D6
(the invariance perimeter), and the Shared Components contracts for
`apply_outcome_with_held` and the local-drag-in-flight signal. This section
adds only what is specific to this task.

### 1. Reset narrowing (FR1, FR6)

The application step currently answers one reset flag by resetting the
cell-change cache and clearing every gesture slot. It becomes:

1. Reset the cell-change cache whenever either reset trigger fired —
   unconditional, unchanged from today.
2. When the tab-change trigger fired, clear every gesture slot, held or not.
3. Otherwise, when the tracking-inactive trigger fired, clear only the slots
   of buttons the supplied held-button value reports as NOT held.
4. The "no button" identity never occupies a slot, so the exclusion must not
   give it one.

The pre-existing entry point delegates with an all-released held-button
value, which reduces step 3 to "clear every slot" — its present behaviour for
the roughly thirty existing inline test call sites.

### 2. The drag-in-flight input (FR2, FR5)

The button-decision input bundle gains one plain boolean field,
`local_drag_in_flight`, filled by the routing layer from the definition
IMPLEMENTATION.md pins. Only the release half reads it, and only in its
no-owner branch; the press half ignores it entirely.

Release decision table after the change:

| Recorded owner | Button | Drag in flight | Disposition | Record updates |
|---|---|---|---|---|
| report-owned | any | — | unchanged from today (a report when some tracking mode is active, otherwise nothing) | clear this button's slot (unchanged) |
| locally owned | left | — | the selection-completion arm (unchanged) | clear this button's slot (unchanged) |
| locally owned | middle / right | — | nothing (unchanged) | clear this button's slot (unchanged) |
| none | left | true | the selection-completion arm (**new**) | today's reset observations, unchanged |
| none | left | false | nothing (unchanged) | today's reset observations, unchanged |
| none | middle / right | — | nothing (unchanged) | today's reset observations, unchanged |

### 3. What must not change (FR4, NFR5)

Button-code composition, byte encoding, the release targeting the tab its
press recorded, the motion gate, the cell-change filter, the wheel-consumer
matrix, the guard-rejected press and wheel dispositions, and the bounded
wheel-report duplication cap. The reset narrowing changes only which gesture
slots survive an already-raised reset; it must never cause a reset to be
raised where one is not raised today, and never cause a report to be emitted
where none is emitted today.

### 4. Window-freedom and purity (NFR1, NFR2)

Every new or changed signature in the decision layer takes plain values only.
The decision functions continue to return their record updates for the
application step to apply exactly once; nothing in the decision path mutates
the records it was handed.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With no tracking mode active, a left press over the grid followed
      by a wheel notch over the grid leaves the left gesture slot recorded as
      locally owned, and the following left release names the
      selection-completion arm.
- [ ] AC-2: The same sequence with a middle press, and again with a right
      press, substituted for the wheel notch produces the identical left
      release outcome; the middle or right slot is recorded at its own press
      and cleared at its own release, independently of the left slot.
- [ ] AC-3: A left release whose left slot is empty names the
      selection-completion arm when the gathered drag-in-flight input is true,
      and names "nothing" when it is false; a chrome-position press (which
      records no owner and starts no drag) followed by its release therefore
      names no arm.
- [ ] AC-4: An outcome carrying a tracking-inactive reset, applied through the
      companion entry point with left held, resets the cell-change cache and
      leaves the left slot recorded; the same outcome applied with a middle
      slot recorded but middle not held clears the middle slot.
- [ ] AC-5: An outcome carrying a tab-change reset clears every gesture slot,
      including the slot of a currently-held button.
- [ ] AC-6: Every pre-existing test in the decision layer's inline test module
      and in the `window_host` module test file passes; no report byte
      sequence, release tab target, guard-rejected disposition or wheel-matrix
      outcome changes; the structural delegate list names the companion entry
      point and its assertion passes; the bounded wheel-report duplication cap
      and its constant are untouched.
- [ ] AC-7: No signature in the decision layer takes or returns a winit type,
      an egui handle, a GPU surface, a PTY or a `term_core` mode type; every
      new test is a bare test constructing no window; each decision function
      leaves the records value it was handed unmodified; the crate still
      compiles with default features off.

## Test Notes

- **Regression evidence**: the tests behind AC-1, AC-2 and AC-3 must fail
  against the revision this task starts from and pass afterwards. Confirm the
  failure before implementing (they are the task's TDD contract).
- **Fixture defaults**: the existing input-builder helpers in the decision
  layer's inline test module default to mouse tracking ON. Every repro test
  here needs tracking explicitly off, otherwise the press records report
  ownership and the scenario does not reproduce.
- **Threading a sequence**: AC-1/AC-2 need one records value threaded through
  the whole press → interleaved event → release sequence via the application
  step, not three independent decisions against fresh records — the bug only
  appears in the threaded form.
- **AC-4/AC-5 are application-step tests**, not decision tests: construct the
  outcome directly, apply it with a chosen held-button value, then inspect the
  slots and the cell-change cache.
- **AC-7's purity check**: copy the records value before the decision and
  compare after; the records type is a plain copyable value, so this needs no
  fixture.
- **AC-6** is satisfied by running the whole suite, not by new assertions; run
  the library tests single-threaded, as the project's test conventions
  require.
- **Edge cases worth a test**: tracking turning on mid-drag (the left slot
  says locally owned while tracking is active — the release must still
  complete the drag, not emit a report); tracking off with a report-owned
  button held (the release must stay "nothing", not become a spurious
  report); the "no button" identity never gaining a slot through the
  exclusion.
