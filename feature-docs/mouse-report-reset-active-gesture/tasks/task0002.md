# Task Plan: task0002 — Focus loss terminates a live local drag

## Goal

A left selection drag that is in flight when the window loses focus is
terminated under the same publish rules a left release applies, so the drag
flag can never survive a focus transition and the pointer-state-gated
features resume on the next pointer motion.

## Requirements

FR3, NFR1, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/window_host/pointer_routing.rs` — extract the publish half of
  the release terminator into one module-visible step; add the pure
  applicability predicate; leave the release path's observable behaviour
  identical.
- `src-tauri/src/window_host/event_loop.rs` — the focus-loss arm consults the
  predicate and runs the terminator, alongside the gesture/held record clear
  it already performs.
- `src-tauri/src/window_host/tests.rs` — tests for the predicate and for the
  focus-loss expectations at the level the existing focus-loss test already
  works at.
- `src-tauri/src/app.rs` — only if consuming the pending selection anchor from
  the new call path needs a change there; no change is expected.

## Design

Read IMPLEMENTATION.md first: D4 (focus loss shares the publish half, not the
fold toggle), D5 (the drag lifecycle invariant), D6 (the invariance
perimeter), and the Shared Components contracts for the local drag terminator
and the local-drag-in-flight signal. This section adds only what is specific
to this task.

### 1. Extracting the terminator (FR3)

The release path's local arm today performs, in order: clear the drag flag;
consume the pending selection anchor; if the consumed anchor was present, no
selection exists and the control modifier is not held, attempt a fold toggle
and, when it succeeds, stop without publishing; otherwise publish any existing
selection to PRIMARY and, when the copy-on-select setting is on and the text
is non-empty, to CLIPBOARD.

Split this into two named steps:

- the **publish half** — clear the drag flag, consume the pending anchor,
  publish an existing selection — made module-visible under the pinned name;
- the **fold-toggle branch** — unchanged, still reached only from the release
  path and still short-circuiting the publish exactly as today.

The release path composes the two so that its externally observable behaviour
(which destinations are written, in what circumstances, and when the fold
toggle wins) is bit-for-bit what it is today. The focus-loss path calls the
publish half only.

### 2. The applicability predicate (FR3, NFR1)

A pure function of plain booleans — the drag flag and whether a pending
selection anchor is present — answers whether the focus-loss arm must run the
terminator. It reads no host, app, window or terminal state, so it is
exercisable from a bare test with nothing constructed. Its answer is the
local-drag-in-flight signal IMPLEMENTATION.md pins; task0001 derives the same
signal independently for the release decision, and the two definitions must
agree.

### 3. Wiring the focus-loss arm (FR3)

The focus-loss arm keeps everything it does today — dropping modifiers,
zeroing the button-down count, clearing the gesture-ownership and held-button
records, refreshing the link cursor, forcing a full redraw. The terminator
call is added to that list, guarded by the predicate, and ordered so it runs
while the drag state it inspects is still intact (that is, before the record
clear is allowed to influence anything it reads). With the predicate false,
the arm's behaviour is unchanged in every respect.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The publish half of the release terminator exists as one
      module-visible step, and the release path's observable behaviour is
      unchanged: the drag flag is cleared, the pending anchor is consumed, a
      successful fold toggle still suppresses the publish, and the PRIMARY /
      CLIPBOARD writes happen under exactly the conditions they do today.
- [ ] AC-2: A pure predicate over plain booleans answers whether focus loss
      must terminate a drag; it is exercised by bare tests that construct no
      window, no GPU surface and no PTY, and it answers true exactly when the
      drag flag is set or a pending selection anchor is present.
- [ ] AC-3: With a live drag and a materialized selection, the focus-loss path
      leaves the drag flag false, the pending anchor consumed, and the
      selection's text published to PRIMARY — and additionally to CLIPBOARD
      when the copy-on-select setting is on.
- [ ] AC-4: With no drag in flight, the focus-loss path writes neither PRIMARY
      nor CLIPBOARD and leaves selection state untouched; the gesture and
      held-button record clear still runs in both cases, so a decision taken
      after focus loss starts from empty records.
- [ ] AC-5: The focus-loss path never runs the fold-click toggle, for any
      combination of pending anchor, selection and modifier state.
- [ ] AC-6: After a focus loss that terminated a drag, no subsequent pointer
      motion extends the selection, and the pointer-state-gated work (the
      resize hint refresh and the link-hover refresh) runs again on the next
      motion.
- [ ] AC-7: Every pre-existing test in the `window_host` module test file
      passes, including the existing focus-loss record-level test, and the
      crate still compiles with default features off.

## Test Notes

- **AC-2 is the window-free unit**: the predicate is a plain function, so its
  truth table is covered exhaustively by bare tests — all four combinations of
  the two booleans.
- **AC-3/AC-4/AC-5 at the record level**: the focus-loss arm itself cannot be
  driven without a winit window. Follow the precedent already set by the
  existing focus-loss test in the module test file — pin the properties the
  call is required to have (which state ends up cleared, which destination is
  written, which branch is never taken) at the level that is reachable, and
  keep the arm's body a straight-line composition of the predicate and the
  terminator so nothing untestable is hidden inside it.
- **AC-6 is a consequence, not a separate mechanism**: it holds because the
  drag flag is false; assert the flag rather than re-testing the gated
  features.
- **AC-1 is a no-regression criterion**: the strongest evidence is the
  existing suite passing plus a reading of the composed release path against
  the order described in Design section 1. Add a test only where the split
  introduced a branch that did not exist before.
- Run the library tests single-threaded, as the project's test conventions
  require. New tests are named `<subject>_<scenario>_<expected>` and construct
  their own state per test.

- Any change to the DEC mouse-report protocol surface or to what the existing
