# Task Plan: task0001 — Core inferred-clear latch (OSC 133 D→A state machine)

## Goal

Provide a single, build-agnostic, side-agnostic core component implementing
the SPEC.md FR1 state machine: given a pane's `Set`/explicit-`Clear`
OSC 777 events and live OSC 133 marks, decide when an inferred `Clear`
should fire.

## Requirements

FR1, NFR2

## Scope

### Files to Create
- `src-tauri/src/agent_status_exit_latch.rs` — the core inferred-clear
  latch: per-pane state (armed / command-ended / generation) and the
  operations to record a `Set`, record an explicit `Clear`, and record a
  live OSC 133 mark (returning whether an inferred `Clear` should now
  fire).

### Files to Modify
- `src-tauri/src/lib.rs` — register the new module (build-agnostic, no
  `gui` cfg gate — mirrors how `agent_status.rs` is registered).

## Design

**Component**: one latch instance covers one pane/tab's lifecycle. Its
state is exactly: `armed: bool`, `command_ended: bool`, `generation:
u64`.

**Operation — record `Set`**: increments `generation`, sets `armed =
true`, `command_ended = false`. Idempotent under repeated `Set` calls
(each call starts a fresh generation per SPEC.md FR1 step 5 — a
re-report while already armed simply re-arms with a new generation, so a
`D` observed against the OLD generation can never combine with an `A`
observed against the NEW generation).

**Operation — record explicit `Clear`**: sets `armed = false`,
`command_ended = false`. Never itself produces an inferred-clear signal
(that would double up with the explicit clear the caller is already
applying).

**Operation — record a live OSC 133 mark**: takes the mark's kind
(`PromptMarkKind`, reused from `prompts.rs` — see IMPLEMENTATION.md
Conventions) and the generation tag the caller associates with "the
current live stream position" is NOT required as an input; the latch's
OWN `generation` counter is authoritative, and only `D`/`A` are
meaningful (all other kinds are a no-op):
- `D` while `armed && !command_ended`: sets `command_ended = true`.
  `D` while `!armed` or already `command_ended`: no-op (this correctly
  absorbs repeated `D`s from multiple commands run before the matching
  `A` — only the state, not a count, is tracked).
- `A` while `armed && command_ended`: returns "fire inferred clear",
  then resets to `armed = false`, `command_ended = false` (same terminal
  state as an explicit `Clear`).
- `A` while `armed && !command_ended`, or while `!armed`: no-op, returns
  "no signal."

This exactly implements the Shared Components contract in
IMPLEMENTATION.md — do not add fields or operations beyond what that
contract and this design describe (e.g. no timeout, no text inspection —
those are explicitly out of scope per SPEC.md).

**Caller contract (documented in this module, enforced by task0002 /
task0003, not by this task)**: only live, main-screen-observed marks may
be passed to the mark-recording operation, in true arrival order
alongside that pane's `Set`/`Clear` calls (SPEC.md FR4, FR5).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `Set` → live `D` → live `A` → the mark-recording operation
  for the `A` call reports "fire inferred clear" exactly once (TS-1).
- [ ] AC-2: `Set` → live `A` (no prior `D`) → no inferred-clear signal is
  ever reported (TS-2).
- [ ] AC-3: `Set` → explicit `Clear` → live `D` → live `A` → no
  inferred-clear signal is reported for the `D` or the `A` (TS-3).
- [ ] AC-4: `Set` → live `D` → `Set` again (new generation) → live `A` →
  no inferred-clear signal is reported (the `D` belonged to the
  invalidated generation) (TS-4).
- [ ] AC-5: No `Set` ever recorded → live `D` → live `A` → no
  inferred-clear signal is reported (TS-5).
- [ ] AC-6: `Set` → live `D` → live `D` again (repeated) → live `A` →
  exactly one inferred-clear signal is reported (repeated `D` before the
  matching `A` does not produce multiple fires or otherwise break the
  state machine) (TS-12).
- [ ] AC-7: After an inferred-clear signal fires, the latch's state is
  observably equivalent to having just received an explicit `Clear`
  (i.e. a subsequent live `D`/`A` pair with no intervening `Set` produces
  no further signal).

## Test Notes

All criteria are unit-testable in isolation (pure state machine, no I/O,
no `gui` feature dependency). Cover the full transition table from the
Design section, including kinds other than `D`/`A` being no-ops.

## Out of Scope

- Deciding whether a mark is "live" vs. replay-derived, or main-screen
  vs. alt-screen (that is the caller's responsibility per
  IMPLEMENTATION.md D2 — task0002 / task0003).
- Applying the inferred-clear signal to any `agent_status`/UI/revision
  state (task0002 / task0003 own that, through the existing explicit
  `Clear` application path per FR2).
- Any per-generation bound on how long "command_ended" may persist before
  an `A` arrives (no timeout — SPEC.md explicitly excludes this).
