### title

mux 接続中も GUI ローカルのタブ status が作られ、daemon の推論 Clear では消えない

### description (finding 原文)

While mux-attached, this block discards only `pending_latch_feed`; previously
parsed `agent_status_events` are still queued and later applied as
`PaneKey::Tab` events. Thus an inner OSC 777 `Set` creates both a daemon-owned
mux-pane status and a GUI-local tab status, but the subsequent daemon D→A
inferred clear clears only the mux-pane entry. Because the tab badge aggregates
both keys, the GUI-local Set can keep the icon visible indefinitely. SPEC FR3
states that `AgentStatusModel` is for plain tabs and `MuxPane.agent_status` is
authoritative for mux panes, and explicitly says applying mux clearing only in
the GUI is unacceptable; the inverse split here likewise desynchronizes the
visible badge from the daemon.

### suggestion (finding 原文)

Do not enqueue/apply GUI-local `pending_agent_status` events for mux-owned PTY
output. Discard or prevent both the plain status events and latch feed while
mux-attached, relying exclusively on daemon `AgentStatusUpdate` messages for
mux panes.

  `pending_latch_feed.clear()` がフレーム適用ループより前に走るため、
  detach したポンプだけ mux inner 由来の候補が tail 再ルートに混入する。
  クリアをフレーム適用ループ直後 (tail 再ルート前) へ移し、判定は
  「このポンプの開始時点で mux だったか」で行う。
- `5cd6f305dcdeceb7` (spec, tabs.rs:2495): `pending_agent_status` の drain
  (`Tab::pump` 2642 行付近) と `pending_latch_feed` の drain
  (`process_outer_via_core` 2495 行) が別地点にあり、detach テール再ルートでは
  両者が別ポンプに分かれるため、`App::pump_all` のタブ単位ペアリングが前提とする
  「両者が同一ポンプで drain される」が崩れる。

## Acceptance Criteria

1. mux 接続中に mux pane の inner OSC 777 `Set` が流れても、GUI ローカルの
   `AgentStatusModel` に `PaneKey::Tab` のステータスが作られない。
   daemon からの `AgentStatusUpdate` 経由の mux-pane ステータスのみが
   タブバッジに反映される。

   plain-tab latch に混入しない。
