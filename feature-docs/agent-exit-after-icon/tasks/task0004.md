# Task Plan: task0004 — Hot-upgrade latch preservation

## Goal

Ensure the mux daemon's per-pane inferred-clear latch state (added by
task0003) survives a daemon hot-upgrade (in-place binary replacement), so
an upgrade occurring between a live `D` and its matching `A` does not
silently drop the pending inferred clear.

## Requirements

FR6

## Scope

### Files to Modify
- `src-tauri/src/mux/upgrade.rs` — extend the existing pane-state
  transfer performed during a hot-upgrade to also carry task0003's new
  latch field(s) across the upgrade boundary.

## Design

**Read task0003's actual field additions at implementation time.** This
task's file overlap with task0003 is None by file path (only
`mux/upgrade.rs` is modified here), but its correctness depends on
matching whatever field(s) task0003 actually adds to the pane's
agent-status state (IMPLEMENTATION.md D3). Since both tasks run in
parallel, do not assume a specific field name in advance — read the
merged/current state of the pane type before wiring the transfer, and if
task0003's fields are not yet present in this task's worktree because of
parallel timing, that is a normal cross-task integration point resolved
at merge time (per the project's parent-side-adoption protocol for
overlapping/dependent changes), not a blocker to be worked around by
guessing the shape.

**Transfer semantics**: the existing hot-upgrade pane-state transfer
already copies fields the new process needs to resume serving that pane
without observable disruption (per the existing `agent_state: None`
entries visible in `mux/upgrade.rs` for unrelated fields). Add the
latch's state (armed / command-ended / generation, or whatever task0003
actually named them) to that same transfer, preserving their values
exactly (no reset, no re-derivation) — a pane mid-"command_ended" before
an upgrade must still be mid-"command_ended" immediately after.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A pane whose latch is `armed` (Set observed, no D/A yet) at
  the moment of a hot-upgrade remains `armed` with the same generation
  immediately after the upgrade completes (TS-10, partial coverage).
- [ ] AC-2: A pane whose latch has recorded `command_ended` (Set → D
  observed, no A yet) at the moment of a hot-upgrade still fires exactly
  one inferred clear when its matching `A` arrives after the upgrade
  (TS-10).
- [ ] AC-3: A pane whose latch is disarmed (no `Set` since the last
  clear) at the moment of a hot-upgrade remains disarmed after the
  upgrade (no spurious clear or false arm introduced by the transfer
  itself).

## Test Notes

These are integration tests exercised against the existing
`mux_hot_upgrade` test conventions/fixtures (per
`references/workflow-schema.md` mentioning an existing approved test
command targeting that test file) rather than a new test harness —
extend that existing coverage with the latch-state assertions above.

## Out of Scope

- Any change to when/how the latch fires at runtime (task0003's
  responsibility) — this task only concerns state SURVIVAL across the
  upgrade boundary.
- Any change to plain-tab behavior (plain tabs run entirely inside the
  GUI process and are not subject to daemon hot-upgrade).
