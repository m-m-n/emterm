### title

hot-upgrade の snapshot がライブ順序イベントストリームのカットになっていない

### description (finding 原文)

The snapshot records the current latch state, but pane reader threads and the
daemon agent-status channel are not quiesced or drained at the snapshot
boundary. A D or A can therefore be read/queued or processed after this state
is captured and before `exec`, after which the old queue and reader scanner
disappear. For example, an A processed after a command-ended snapshot clears
the old pane, but restore reinstates the pre-clear Set and pending latch with
no remaining A to consume. SPEC FR6 explicitly requires latch state to survive
so an upgrade between live D and its matching A does not silently drop the
pending inferred clear.

### suggestion (finding 原文)

Establish an upgrade barrier that stops pane readers at a defined byte
boundary, drains all ordered agent-status feed items through the daemon,
snapshots afterward, and prevents further consumption until exec;
alternatively transfer the in-flight scanner/channel state as part of the
handoff.

## 判断が割れている点 (実装前に確認すること)

`claude:spec` は同じ経路を「snapshot は `SessionManager` ロック下で走るため
torn read は成立せず、FR6 の往復は verbatim で保たれている」と判定しており、
`codex:spec` の指摘と結論が異なる。両者は別のレベルを見ている:

- claude: snapshot 取得そのものの原子性 (ロック下で一貫している)
- codex: snapshot 取得から `exec` までの間に、静止していない reader スレッドと
  agent-status チャネルがイベントを消費し得ること

したがって最初にやることは、`prepare_upgrade` 系の実際の制御フローを読み、
「snapshot 後 exec 前に latch を変え得る消費経路が実在するか」を確定させること。

- 実在する場合: 上記 suggestion のいずれかで塞ぎ、回帰テストを追加する。
- 実在しない場合 (claude の判定が正しい場合): 修正せず、なぜ安全なのかを
  `upgrade.rs` のコメントとして残し、その根拠を実装レポートに書く。
  この finding は `declined` として扱えるようにすること。
