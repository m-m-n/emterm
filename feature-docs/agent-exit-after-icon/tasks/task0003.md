# Task Plan: task0003 — Mux daemon (pane) inferred-clear wiring

## Goal

Wire the core inferred-clear latch (task0001) into the mux daemon's
per-pane agent-status handling, so a Ctrl+C/crash/`exit` out of Claude
Code inside a mux pane on an OSC-133-capable shell clears a stale icon,
with the daemon remaining the authoritative owner of the resulting state
change.

## Requirements

FR2, FR3, FR4, FR5, NFR1

## Scope

### Files to Modify
- `src-tauri/src/mux/session/pane.rs` — add a latch instance field to the
  pane's agent-status state; when the latch reports "fire inferred
  clear," apply it through the exact same path
  `apply_agent_status_event` already uses for an explicit `Clear` (FR2)
  — same revision increment, same downstream broadcast, no parallel
  logic.
- `src-tauri/src/mux/daemon.rs` — daemon-side live PTY OSC 133 capture
  and OSC 777 report dispatch for a pane: feed both into that pane's
  latch in original relative order (FR4); ensure only live, main-screen
  marks reach the latch (FR5) — the daemon's existing snapshot
  construction / replay path (`strip_replayable_rich_content` and
  friends) must never be a source for the latch.

## Design

**Per-pane latch lifetime**: one latch instance per `MuxPane`, alongside
the pane's existing `agent_status` field and `agent_waiters`. Created
with the pane; discarded when the pane is discarded (mirrors existing
pane-lifecycle handling — no special-case needed since the whole
agent-status entry already goes away with the pane).

**Feed ordering (FR4)**: the daemon's OSC 777 report application
(`apply_agent_status_report`, called from the daemon's PTY-reader path)
and the daemon's live OSC 133 capture for the same pane must be
processed through one ordered per-pane path. Do not introduce a
separate async task/queue for OSC 133 handling that could race the
existing synchronous(-per-pane) OSC 777 application — SPEC.md FR4
explicitly forbids `Set` and `D`/`A` reordering within a batch.

**Live-only feed (FR5)**: the daemon reconstructs snapshots (for
reattach/detach) and replays scrollback content through paths that are
NOT the live PTY stream (per the investigation's findings on daemon
snapshot assembly). The latch must only ever see marks captured on the
live, currently-executing PTY-reader path for that pane — never marks
produced or replayed as part of snapshot assembly, reattachment, or
scrollback backfill. Alt-screen-suppressed marks must not reach the latch
either, mirroring `term_core`'s existing suppression.

**Applying the inferred clear (FR2, FR3)**: when the latch signals a
fire, apply it through the exact same effects `apply_agent_status_event`
already produces for `AgentStatusEvent::Clear` on that pane: mutate
`pane.agent_status` to `None`, increment the pane's revision, call
`reevaluate_agent_waiters` so any pending `WaitAgentState` request
unblocks correctly, and let the existing `AgentStatusUpdate` broadcast
push `state: None` to the GUI. Do not clear the GUI-displayed badge
directly and independently of this daemon-side state change (FR3 — the
daemon stays authoritative; a GUI-only clear would desync daemon
queries, waiters, detached-pane state, and reattachment replay from the
visible badge, per the design consultation record in REQUIREMENTS.md
§14.1).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: On a mux pane, `Set` (via OSC 777) followed by live OSC 133
  `D` then `A` results in `pane.agent_status` becoming `None`, the pane's
  revision incrementing, any matching `WaitAgentState` waiter resolving,
  and an `AgentStatusUpdate(state: None)` being produced for the GUI
  (TS-7).
- [ ] AC-2: On a mux pane, `Set` followed only by live OSC 133 `A` (no
  `D`) leaves `pane.agent_status` unchanged (TS-2, daemon-side
  integration).
- [ ] AC-3: On a mux pane, an explicit `Clear` followed by live `D`/`A`
  does not produce a second/duplicate clear application or a second
  revision increment (TS-3, daemon-side integration).
- [ ] AC-4: OSC 133 marks sourced from the daemon's snapshot/reattach
  replay path do not drive the latch to fire (TS-8, daemon-side).
- [ ] AC-5: OSC 133 marks captured while the pane is on the alternate
  screen do not drive the latch to fire (TS-9, daemon-side).
- [ ] AC-6: A mux pane whose shell never emits OSC 133 behaves exactly as
  today — an unresolved `Set` with no explicit `Clear` leaves the icon
  showing indefinitely (NFR3 regression guard, daemon-side).
- [ ] AC-7: The new latch field(s) added to the pane's agent-status state
  are named/shaped so task0004 (hot-upgrade) can locate and carry them
  across an upgrade boundary without needing to read this task's plan
  (per IMPLEMENTATION.md D3 — task0004 reads the actual code, not this
  plan, to stay in sync).

## Test Notes

AC-1 through AC-3 are integration tests exercising the actual daemon path
(`apply_agent_status_report` / OSC 133 dispatch → latch →
`apply_agent_status_event`-equivalent effects), not just the latch in
isolation. AC-4 in particular should reuse or mirror the daemon's
existing snapshot-construction test fixtures so the "not from replay"
guarantee is checked against the real code path, not a hand-rolled
substitute. AC-6 is a regression test guarding NFR3 on the daemon side.

## Out of Scope

- Any change to plain-tab behavior (task0002's responsibility).
- Hot-upgrade state transfer itself (task0004's responsibility) — this
  task only needs to leave the new field(s) in a shape task0004 can
  carry across.
- Any change to the OSC 777 wire format or `agent_status.rs` parsing.
- Text-pattern-based detection or timeouts (excluded features, see
  SPEC.md).
