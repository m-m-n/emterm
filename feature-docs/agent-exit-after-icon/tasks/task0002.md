# Task Plan: task0002 — Plain-tab (GUI-local) inferred-clear wiring

## Goal

Wire the core inferred-clear latch (task0001) into the GUI-local plain-tab
agent-status path, so a Ctrl+C/crash/`exit` out of Claude Code on an
OSC-133-capable shell clears a stale icon on plain (non-mux) tabs.

## Requirements

FR2, FR3, FR4, FR5, NFR1, NFR3

## Scope

### Files to Modify
- `src-tauri/src/callbacks.rs` — OSC dispatch for plain tabs: feed live
  OSC 133 marks and OSC 777 `Set`/`Clear` events for a given tab into that
  tab's latch instance, in original relative order (FR4); ensure only
  live, main-screen marks reach the latch (FR5) — do not source marks
  from `PromptTracker`'s retained storage or any snapshot/replay path.
- `src-tauri/src/agent_status_model.rs` — host one latch instance per
  `PaneKey::Tab`; when the latch reports "fire inferred clear," apply it
  through the exact same code path `AgentStatusEvent::Clear` already uses
  (FR2) — no parallel/duplicate clear application logic. Discard the
  latch instance when its tab's `AgentStatusModel` entry is discarded
  (mirrors existing entry-discard handling).

## Design

**Per-tab latch lifetime**: one latch instance keyed the same way
`AgentStatusModel` already keys plain-tab entries (`PaneKey::Tab`).
Created alongside (or lazily on first `Set` for) that key; discarded
together with the existing entry-discard path (tab closed).

**Feed ordering (FR4)**: the plain-tab OSC 777 report path
(`callbacks.rs`'s existing `OSC_EMTERM_EXTENSION` handling that produces
`pending_agent_status` entries) and the live OSC 133 capture path must
both route through the latch for the SAME tab in the order `term_core`
actually delivered them for that tab's PTY stream — this task must not
introduce two independently-scheduled queues that could reorder a `Set`
relative to a `D`/`A` pair from the same read.

**Live-only feed (FR5)**: only OSC 133 marks captured from the tab's live,
currently-processing PTY stream feed the latch. Marks that exist solely
for `PromptTracker`'s prompt-jump navigation (backfilled, pruned, or
otherwise historical) must never be re-used as latch input — the latch
must not, even indirectly, read from `PromptTracker`'s stored marks.
Marks `term_core` already suppresses on the alternate screen must not
reach the latch either (this should fall out naturally if this task taps
the same live capture point `term_core` uses, rather than re-deriving
"main screen" from scratch).

**Applying the inferred clear (FR2)**: when the latch signals a fire,
construct the exact same transition `AgentStatusModel` would apply for an
explicit `AgentStatusEvent::Clear` on that key (no new UI-facing state,
no new notification path — this must flow through the existing
Set/Clear transition and notification-suppression logic already covering
`new_state: None`).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: On a plain tab, `Set` (via OSC 777) followed by live OSC 133
  `D` then `A` results in that tab's `AgentStatusModel` entry becoming
  `state: None`, through the existing Clear transition path (TS-6).
- [ ] AC-2: On a plain tab, `Set` followed only by live OSC 133 `A` (no
  `D`) leaves the tab's state unchanged (TS-2, GUI-side integration).
- [ ] AC-3: On a plain tab, an explicit `Clear` followed by live `D`/`A`
  does not produce a second/duplicate clear transition (TS-3, GUI-side
  integration).
- [ ] AC-4: OSC 133 marks sourced from a scenario equivalent to
  snapshot/replay (not the tab's live, currently-processing PTY stream)
  do not drive the latch to fire (TS-8).
- [ ] AC-5: OSC 133 marks captured while the tab is on the alternate
  screen do not drive the latch to fire (TS-9).
- [ ] AC-6: Closing a tab discards its latch instance along with its
  existing `AgentStatusModel` entry (no leak, no stale latch keyed to a
  closed tab).
- [ ] AC-7: A tab whose shell never emits OSC 133 behaves exactly as
  today — an unresolved `Set` with no explicit `Clear` leaves the icon
  showing indefinitely (NFR3 regression guard).

## Test Notes

AC-1 through AC-3 are integration tests exercising the actual
`callbacks.rs` → latch → `AgentStatusModel` path (not just the latch in
isolation, which task0001 already covers). AC-4/AC-5 require constructing
test input that plausibly represents replay/alt-screen-suppressed marks
per however `term_core` currently distinguishes them — consult the
existing suppression logic referenced by the investigation
(`term_core`'s existing alt-screen OSC 133 suppression) rather than
re-inventing a new distinction. AC-7 is a regression test, not new
behavior — write it to fail loudly if a future change accidentally makes
OSC-133-absent tabs start clearing anyway.

## Out of Scope

- Any change to mux-pane behavior (task0003's responsibility).
- Any change to the OSC 777 wire format or `agent_status.rs` parsing.
- Text-pattern-based detection or timeouts (excluded features, see
  SPEC.md).
