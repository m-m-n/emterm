# Task Plan: task0001 — Thread CPU-time helper and CPU budget for the strip_concat alternations test

## Goal

`strip_concat_alternations_and_chains_finish_within_the_budget` judges its 10 s budget on the thread CPU time of the measured strip, snapshot-strip and write-filter calls only, through a new test-side thread CPU-time helper. The helper's own tests show that it ignores sleep and other threads, counts its own thread, panics on clock failure, and that its budget judgment rejects a quadratic surrogate.

## Design

### Thread CPU-time reading (FR3, FR4, NFR3)

Contract of "read the calling thread's CPU time":

- **Precondition**: none; callable from any thread.
- **Postcondition**: returns the total CPU time (user + kernel) the calling thread has consumed so far, as a duration. Two readings on the same thread never decrease. CPU time consumed by any other thread — including tests libtest runs in parallel — is never included. Time the calling thread spends sleeping or blocked adds nothing.
- **Source per platform** (selected at compile time; nothing else in the module is platform-specific):
  - Unix targets (Linux is the supported one): the POSIX per-thread CPU-time clock, through the existing libc dependency.
  - Windows: the Win32 thread-times query on the current thread, summing kernel time and user time and converting from 100 ns units, through the existing windows-sys dependency with the feature added by this task.
- **Failure (FR4)**: interpreting the OS-reported status is a separate step that takes the reported status and the OS error detail, so a test can drive it with a failure status without making the OS call fail. On a failure status the step panics with a message naming the clock API and the OS-reported error (Unix: the last OS error; Windows: the last error code). It never returns zero, never falls back to a wall-clock reading and never retries.
- The module reads no wall clock except in the two helper tests that contrast against it (TS-1, TS-3).

### CPU budget meter and judgment (FR2, FR8)

One meter and one judgment, used both by the FR2 test and by the FR8 control, so the control demonstrates the very judgment the FR2 test relies on.

- **Meter**: a per-test accumulator of thread CPU time, owned by one thread.
  - "Measure a call": read the thread CPU time, run the call, read again, add the difference to the running total, and hand back the call's result unchanged.
  - Precondition: every measured call runs on the thread that owns the meter; the meter is not shared between threads.
  - Postcondition: the total grows by exactly the CPU time of the calls passed through the meter. Work outside measured calls — building inputs, comparisons, concatenation, releasing returned values — is not counted, because the result is handed back out of the measured region.
- **Judgment**: "is the total within the budget" — within exactly when the total is strictly less than the budget, otherwise over. The verdict carries the total and the budget so assertion messages can show both.

### The FR2 test (strip_concat_query.rs)

Changes inside `strip_concat_alternations_and_chains_finish_within_the_budget`:

1. The wall-clock start and the elapsed assertion are removed.
2. A meter is created at the start of the test.
3. Measured calls, each passed through the meter individually:
   - per target and per shape (open CSI, lone ESC): the write strip on the whole input; the snapshot strip on the whole input; the one-call feed (the overflow flush); every feed of the unit-aligned reads; every feed of the unaligned 64 KiB reads;
   - per target, the ESC chain: the write strip; the one-call feed; every feed of the 16 KiB reads.
4. Not measured: building units, inputs and expected outputs (the repetition and concatenation helpers), the context strings, filter construction, chunk iteration, every equality / prefix / suffix / emptiness comparison, the CSI-phase checks, and the test-side extension of the collected output with each feed's result (SPEC EC5).
5. At the end the test asserts, through the judgment, that the total is within the module's existing `BUDGET` (10 s); the failure message shows the total and the budget.
6. Every correctness assertion keeps its condition and its message. The test keeps its name; its doc comment states that the budget is the thread CPU time of the measured calls.
7. The rest of the file is unchanged: the other tests (including their wall-clock budget checks), the `BUDGET` constant and the time imports stay, since those tests still use them.

### The helper's own tests (in the helper module; regular, non-ignored tests)

Every threshold compares CPU time with CPU time or with a sleep length, so the tests stay valid under load; the one comparison against wall time (TS-3) is a low floor. Durations are long enough that Windows tick granularity cannot decide an outcome (SPEC EC4): roughly 50 ms or more of CPU time or sleep in every comparison.

- **TS-1, sleep (FR6)**: read, sleep for a fixed duration between 200 ms and 500 ms, read. The CPU delta is less than half the sleep duration. The same test also checks that the wall-clock elapsed time over that interval does not meet that bound, showing that a wall-clock helper fails this case.
- **TS-2, another thread (FR6, NFR3)**: a spawned thread consumes a fixed amount of its own CPU time (at least 200 ms, judged with the helper on that thread), with a wall-clock safety cap so a defective helper cannot hang the test; the measuring thread waits in join. The test asserts that the spawned thread reached its amount, and that the measuring thread's delta is less than half of that amount.
- **TS-3, own thread (FR7)**: CPU work kept opaque to the optimizer, in two sizes on the measuring thread; the smaller takes roughly 50 ms or more of CPU on an unloaded debug build, the larger is several times the smaller. Both deltas are positive, the larger work's delta exceeds the smaller's, and the smaller work's delta is at least 1% of that work's wall-clock duration.
- **TS-4, quadratic control (FR8, NFR4)**: a short budget (on the order of 100 ms); a linear and a quadratic surrogate workload of the same input size, both opaque to the optimizer, each measured through a fresh meter and judged by the same judgment. Sizes are chosen so that on an unloaded debug build the linear one uses at most a fifth of the budget and the quadratic one at least five times the budget, keeping the quadratic one to about a second or two of CPU. The quadratic one is judged over, the linear one within.
- **TS-9, clock failure (FR4)**: the status-interpretation step of the platform being built is driven with a failure status; the test expects a panic whose message names the clock API.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR3, FR7; TS-3): CPU work done on the measuring thread yields a positive delta from the helper; a larger amount of work yields a strictly larger delta than a smaller amount; the smaller work's delta is at least 1% of that work's wall-clock duration.
- [ ] AC-2 (FR6; TS-1): across a sleep of a fixed duration between 200 ms and 500 ms, the helper's delta is less than half the sleep duration, and the same test shows that the wall-clock elapsed time over that interval does not meet that bound.

- [ ] AC-4 (FR4; TS-9): the status-interpretation step, given a failure status, panics with a message naming the clock API and the OS-reported error (should-panic test on the platform being built); no code path of the helper returns zero or a wall-clock reading on failure (review).
- [ ] AC-5 (FR8, NFR4; TS-4): a regular, non-ignored test applies the same judgment the FR2 test uses, with a short budget, to a quadratic and a linear surrogate of the same input size: the quadratic one is judged over the budget and the linear one within it.
- [ ] AC-6 (FR2, FR9; TS-6): `strip_concat_alternations_and_chains_finish_within_the_budget` reads no wall clock, sums through the meter exactly the measured calls listed in Design (write strip, snapshot strip, every write-filter feed), asserts through the judgment that the total is under the 10 s `BUDGET`, and passes; every correctness assertion is unchanged; the test name is unchanged; no other test in `strip_concat_query.rs` changes.
- [ ] AC-7 (FR5, NFR1, NFR2; TS-10): the Windows windows-sys dependency in `src-tauri/Cargo.toml` lists the Win32_System_Threading feature and no crate is added; the default build check, the `--no-default-features` check and the `--lib` test build compile with no new warning from the changed files; the check of the test code for the Windows target compiles where the cross toolchain is available.

## Test Notes

- AC-1 to AC-5 are unit tests in the helper module; run them with the `--lib` test command filtered to the helper module name. They must also pass inside the full parallel `--lib` run and under the TS-7 synthetic load.
- AC-6: the test run proves the budget and the correctness assertions; that only the listed calls are counted is a structural property checked by reviewing the diff. TDD-awkward: under no load there is no deterministic red state for the rewrite of an existing passing test; the helper tests supply the red phase (they fail before the helper exists), and the rewrite is recorded as a structural change.
- AC-4: the should-panic test covers the platform being built; the other platform's step is covered by the Windows cross check (compilation) and by review.
- SPEC EC4: on Windows each measured feed's delta is quantized to the scheduler tick; the FR2 total sums many short calls, so the quantization averages out over the sum, and the 10 s budget leaves ample margin over the unloaded total.
- The Windows branch compiles only when the tests are built for the Windows target; on Linux only the unix branch runs.
- No external process is started by these tests; only TS-2 spawns a thread, and it always joins it.
