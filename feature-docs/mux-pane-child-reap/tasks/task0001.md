# Task Plan: task0001 — Retain pane child handle and reap it on teardown

## Goal

The mux daemon keeps the shell child-process handle from spawn through the
pane's lifetime and reaps the process on every pane-teardown path, so a
long-running daemon accumulates no zombie shells and no teardown path ever
blocks on a child's exit.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

- `src-tauri/src/mux/session/child_reaper.rs` — standalone reap procedure
  (bounded exit-poll loop → kill escalation → blocking reap) plus a
  background-handoff entry that runs it on a detached OS thread. Includes
  the module's unit tests (TS-4, TS-5, TS-6, TS-11).

### Files to Modify

- `src-tauri/src/mux/session/mod.rs` — register the new module.
- `src-tauri/src/mux/ipc/pty_spawn.rs` — `SpawnedPty` gains a field holding
  the child handle returned by the spawn call (currently discarded at the
  spawn site, around lines 109–111); `spawn_pty` stores it;
  `register_pane_and_start_reader` passes it into `MuxPane::new`. The
  end-to-end integration/regression tests (TS-7, TS-8, TS-9) live in this
  file's test module.
- `src-tauri/src/mux/session/pane.rs` — `MuxPane` holds the child handle as
  an optional private field; `MuxPane::new` gains a parameter for it;
  `mark_exited` takes the handle out and hands it to the reaper; test
  constructors (`new_test`, `new_test_with_writer`) construct with no child.
  Pane-level tests (TS-1, TS-2, TS-3, TS-10) and updates to the existing
  direct `MuxPane::new` test call sites.

## Design

### D1 — Child handle retention (FR1, FR2)

- `SpawnedPty` carries the child handle — the boxed, thread-transferable
  (`Send + Sync`) trait object the slave's spawn call returns — alongside
  its existing master/writer/reader fields. The spawn site stops discarding
  the spawn call's return value.
- `MuxPane` stores the handle as an optional private field. `MuxPane::new`
  gains one optional-handle parameter and records it. The single production
  caller (`register_pane_and_start_reader`) passes the spawned handle; the
  direct test call sites in pane.rs's test module (which open a PTY but
  spawn no command) pass no handle. `new_test` / `new_test_with_writer`
  keep their signatures and construct with no child (SPEC A3), so their
  ~10 existing call sites stay unchanged.

### D2 — Teardown handoff (FR3, FR4, NFR1)

`mark_exited` keeps its signature and its existing postconditions: the
exited flag is set, and the writer and master handles are cleared (dropping
the master is what delivers the hangup to the shell). In addition it:

1. Removes the child handle from the pane, leaving nothing behind — this
   removal is the multi-call gate: a second `mark_exited` (concurrent
   teardown paths, e.g. destroy-pane racing graceful-shutdown, or the
   PTY-EOF reap racing an explicit destroy) finds no handle and starts no
   second reap.
2. When a handle was present, hands it — together with the pane ID for log
   context — to the reaper's background-handoff entry.
3. Returns immediately. It performs no waiting of any kind; its runtime is
   independent of the child's exit behavior (NFR1). Callers holding the
   `SessionManager` tokio mutex (`handle_destroy_pane`,
   `handle_destroy_window`, `graceful_shutdown`) are never blocked on
   process exit.

Ordering: writer/master are cleared before the handoff so the hangup
reaches the shell no later than the start of the grace-period polling.

### D3 — Reap procedure (`child_reaper` module; FR5, FR6, FR7)

Two public entry points:

1. **Blocking reap procedure** (the unit-testable core, FR6).
   - Inputs: pane ID (log context only), owned child handle, grace period,
     poll interval.
   - Flow:
     1. Poll the child's non-blocking exit check at the poll interval.
     2. Exit observed → the child is reaped by that observation; return
        without any kill.
     3. Non-blocking check errors → log at warn and escalate immediately
        (SPEC error table: "cannot determine" → kill + wait).
     4. Grace period elapses with the child still alive → escalate.
     5. Escalation: send the kill; a kill error is ignored (child already
        gone) and the procedure proceeds.
     6. Blocking reap. An error here (e.g. already reaped elsewhere) is
        logged at warn with the pane ID and error, and ends the procedure.
   - Postconditions: never panics on any path; never propagates an error;
     no unbounded wait before the kill escalation — after the kill, the
     blocking reap returns promptly because the child is dead.
2. **Background-handoff entry.**
   - Inputs: pane ID, owned child handle.
   - Spawns one detached OS thread per exit (named for diagnosability)
     that runs the blocking procedure with the default timing constants,
     and returns immediately. Per-exit threads (SPEC A1): pane exits occur
     at human rates, so thread churn is negligible and no new plumbing
     through pane creation is needed. Reaper threads are not joined at
     daemon shutdown — an unfinished reap's child re-parents to init,
     which reaps it (SPEC edge case).

Timing defaults (SPEC A2, planner decision): **grace period 500 ms, poll
interval 50 ms**, defined as named constants in the module. Rationale: a
normally exiting shell (hangup delivered by the master drop) exits well
within 500 ms, so the kill escalation stays exceptional; a wedged shell
holds its thread for ≲ 1 s. The blocking procedure takes both values as
parameters so tests can shrink them.

### D4 — Teardown-path coverage (FR8)

All four teardown paths already converge on `mark_exited`:
`handle_destroy_pane` (handlers.rs:193 — also driven by
`run_pane_exit_task` on PTY EOF), `handle_destroy_window`
(handlers.rs:360), and `graceful_shutdown` (daemon.rs:1143). `mark_exited`
keeps its signature, so **no caller changes** — FR8 is satisfied by
construction and verified by the integration tests (TS-8/TS-9 exercise the
shared `mark_exited` gate) plus review inspection of the call sites.

### D5 — Platform and feature-gate posture (NFR5)

No platform divergence in the reap logic (SPEC A5): the portable-pty child
contract is cross-platform, and the handle is retained and reaped on
Windows too even though the zombie symptom is Unix-only. The mux subsystem
builds in every feature configuration, so the new module needs no feature
gate and the CLI-only build is unaffected. Zombie-state observations in
tests are Unix-only and gated accordingly (SPEC A4).

### D6 — Security posture (NFR2)

No new API accepts a numeric PID from outside the daemon. The reaper's only
inputs are an owned handle obtained from the daemon's own spawn call plus
timing values; there is no path from external input to the kill.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `SpawnedPty` carries the child handle returned by the spawn
      call (no longer discarded), and `register_pane_and_start_reader`
      passes it into the pane, which stores it. (TS-7)
- [ ] AC-2: `MuxPane` holds the child handle as an optional field; test
      constructors build with no child; `mark_exited` on a child-less pane
      starts no reap and does not panic. (TS-1)
- [ ] AC-3: `mark_exited` removes the child handle from the pane, preserves
      its existing postconditions (exited set, writer/master cleared), and
      returns without waiting on the child; a second call finds no handle
      and starts no second reap. (TS-2, TS-3, TS-10)
- [ ] AC-4: The reap procedure is a standalone function in the new module,
      parameterized by grace period and poll interval; a promptly exiting
      child is reaped without any kill being sent. (TS-4)
- [ ] AC-5: A child still alive when the grace period elapses is killed and
      then reaped; the procedure has no unbounded wait before the kill
      escalation. (TS-5)
- [ ] AC-6: Failure handling matches the SPEC error table: a kill error is
      ignored and the procedure proceeds to the blocking reap; a blocking-
      reap or exit-poll error is logged at warn (never below) and the
      procedure returns without panicking. (TS-6, TS-11)
- [ ] AC-7: Regression: repeatedly opening and tearing down panes through
      the real spawn path leaves no child in zombie state (Unix-gated;
      skips cleanly when the environment cannot open a PTY). (TS-8, TS-9)

## Test Notes

TS-n IDs refer to VERIFICATION.md.

- **Error paths (TS-6, TS-11)** — use a scripted in-test double
  implementing the portable-pty child + child-killer traits, returning
  preprogrammed results (blocking reap fails; kill fails while the
  subsequent reap succeeds). No real process needed. The tests assert the
  behavioral half (returns, no panic, kill error does not abort); the
  "logged at warn or above" half is verified by inspection of the log call
  sites if capturing logger output is impractical in this harness — note
  that in the test comments.
- **Real-child paths (TS-4, TS-5)** — wrap a standard-library child
  process in a small test adapter implementing the portable-pty child
  contract (its exit-status type has a plain exit-code constructor, so the
  adapter is a thin translation). Prompt exit: a command that terminates
  immediately. Kill escalation: a command that sleeps far longer than a
  shrunken grace period; assert the procedure returns within a deadline
  and the process is reaped. This keeps the module's unit tests free of
  any PTY dependency (FR6). Gate on Unix anything that observes /proc.
- **End-to-end (TS-7, TS-8, TS-9)** — in pty_spawn.rs's test module: use
  the real spawn path, record the child's process ID from the handle
  before constructing the pane, tear down via `mark_exited`, then poll the
  process table (via /proc, with a deadline) until the PID is gone or
  observed in a non-zombie state. TS-9 repeats open/close for a small N
  (e.g. 5) and asserts no test-owned PID remains in state Z. Unix-gated
  (`cfg(all(test, unix))`); when PTY creation fails, skip cleanly with an
  early return and a note (SPEC A4).
- **TS-10 (no-wait guarantee)** — pane holding a deliberately long-lived
  child; assert `mark_exited` returns within a generous bound that is far
  below the child's natural lifetime (avoid tight timing assertions; use
  wide margins to stay CI-safe).
- **Existing behavior (TS-3)** — the existing test
  `test_mark_exited_clears_writer_and_master` (pane.rs) must keep passing
  with its assertions substantively unchanged.
- **Parallel safety** — every process-table assertion is keyed on specific
  PIDs owned by the test, so the suite stays parallel-safe; do not add any
  test-thread restriction.
- Run tests with the approved command:
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml`.

## Out of Scope

- No changes to the teardown call sites (`handle_destroy_pane`,
  `handle_destroy_window`, `run_pane_exit_task`, `graceful_shutdown`) —
  `mark_exited` keeps its signature (D4).
- No retroactive cleanup of already-accumulated zombies (REQUIREMENTS 1.3:
  a daemon restart clears them).
- No joining/synchronization of reaper threads at daemon shutdown (D3).
- No platform-specific divergence in the reap logic; no change to spawn
  behavior beyond retaining the handle.
- No configuration surface (settings/UI) for the grace period or poll
  interval — they are internal constants.
