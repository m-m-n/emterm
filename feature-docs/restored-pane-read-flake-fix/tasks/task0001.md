# Task Plan: task0001 — Bounded read-until-marker check for the restored-pane echo test

## Goal

`from_restored_pane_can_write_and_read_through_its_adopted_master` no longer
fails when the PTY echo arrives in pieces. It keeps reading until the marker
`restored-write` is complete or a 5-second deadline passes, and any failure
shows the bytes it collected. Deterministic scripted-reader tests catch a
return to the single-read shape.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Modify

## Design

Cross-task decisions D1 (helper thread plus channel receive timeout) and D2
(5-second deadline) and the Shared Components contract of the target test's
read-back check are in `IMPLEMENTATION.md`. They are applied here and not
restated.

### Current state (for orientation)

The target test sits at `src-tauri/src/mux/session/pane/tests.rs` lines
3246-3291, under a unix gate. It opens a PTY pair with the file's existing
PTY-pair helper. It clones a reader from the master before handing the
master to the restored pane, and writes `restored-write` followed by a
newline through the pane. It then performs ONE read of up to 64 bytes and
asserts that the marker is in it. The kernel's default termios (ICANON,
ECHO, ONLCR) echo `restored-write` followed by a carriage return and a
newline, 16 bytes in all (SPEC A7). When the first read returns only
1-13 bytes, the assert fails, and its message does not show the bytes.

### Component: read-until-marker helper (new, test-only)

Suggested name: `read_echo_until_marker`.

- **Inputs**: a reader it takes exclusive ownership of (it must be movable to
  another thread), the marker byte sequence, and a deadline duration.
- **Behavior**:
  1. Record the absolute deadline (start time plus the duration) once.
  2. Start a reading thread that owns the reader. The thread repeatedly reads
     into a small buffer and sends each non-empty chunk to the waiting side.
     On end of data it sends an end-of-data signal and stops. On a read error
     it sends the error's description and stops. When a send fails because
     the waiting side is gone, it stops silently. It never panics.
  3. The waiting side receives with a timeout equal to the time left before
     the absolute deadline. It appends each chunk to the collected bytes and
     then searches ALL collected bytes for the marker, so a marker that
     straddles chunk boundaries is found.
  4. It returns as soon as the marker is present. It does not wait for the
     deadline or for more data.
- **Outcome** (returned, never panicked): either "marker found", carrying the
  collected bytes, or "marker missing", carrying a reason (deadline passed,
  end of data, or read error with its description) and every byte collected
  so far. A reading thread that disappears without a signal counts as end of
  data.
- **Postconditions**: total waiting never exceeds the deadline by more than
  scheduling slack, however many chunks arrive. The reading thread is not
  joined; it ends by itself (see `IMPLEMENTATION.md` Risk Assessment).
- **Platform**: uses no unix-only API, so it carries no platform gate.

### Component: failure-message renderer (new, test-only)

Suggested name: `describe_missing_echo`. It turns a "marker missing" outcome
into the failure text. The text contains:

- the meaning of the current message: bytes written through the adopted
  master's writer must be readable back through the adopted master, echoed by
  the PTY line discipline;
- the reason (deadline with its duration, end of data, or the read error's
  description);
- every collected byte, decoded as lossy UTF-8 and shown in debug-escaped
  form (quoted, control characters such as carriage return and newline
  escaped), as SPEC FR3 describes.

### Component: scripted test reader (new, test-only)

A reader built from a list of chunks: each read returns the next chunk.
After the chunks run out, it does one of these four things, chosen per test:

- return end of data;
- return an error;
- withhold data until the test releases it, then return end of data;
- keep returning one non-marker byte at a short interval until the test
  releases it.

It is defined locally in the pane test module. The `ScriptedReader` in
`src-tauri/src/pty/mod.rs` is private to that module's tests and is only a
style precedent.

### Target test after the change

The target test keeps its name, its unix gate, its PTY-pair setup, the
reader clone taken before hand-off, and the write of `restored-write` plus a
newline. Its single read and assert are replaced by a call to the helper with
the cloned reader, the marker `restored-write` and a 5-second deadline. A
"marker missing" outcome fails the test with the renderer's text. A "marker
found" outcome passes.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR4; TS-1): when a scripted reader returns `rest` and then
  the rest of the echo (`ored-write` followed by a carriage return and a
  newline), the helper returns "marker found", and the collected bytes equal
  the full 16-byte echo. A single-read implementation fails this test,
  because its only read sees `rest`.
- [ ] AC-2 (FR1, FR4; TS-1): when the echo is split into three or more
  chunks, the helper returns "marker found". This holds for a first chunk of
  one byte and for a split where the marker straddles at least two chunk
  boundaries.
- [ ] AC-3 (FR3; TS-2, TS-7): when a scripted reader returns a strict prefix
  of the marker and then end of data, the helper returns "marker missing"
  with reason end of data and the prefix as collected bytes. The same holds
  for a prefix followed by a read error, with reason read error. In both
  cases the rendered text contains the debug-escaped collected bytes, the
  reason, and the meaning of the current message.
- [ ] AC-4 (FR2, FR3; TS-8): when a scripted reader returns a prefix and
  then withholds data, the helper is called with a short deadline (at most a
  few hundred milliseconds). It returns "marker missing" with reason deadline
  and the prefix as collected bytes, within a generous upper bound of the
  deadline (several seconds), and the rendered text contains the
  debug-escaped prefix. The same result holds when the reader keeps
  trickling non-marker bytes instead of withholding them. Then the
  collected bytes start with the prefix and the call still returns within
  the bound, which shows that the deadline is absolute.
- [ ] AC-5 (NFR4; TS-9): when a scripted reader returns the complete echo
  and then withholds data, a call with a long deadline (at least
  5 seconds) returns "marker found" in clearly less time than the deadline.
  The test releases the reader after the call returns.
- [ ] AC-6 (FR1, FR2, FR3; TS-3): `from_restored_pane_can_write_and_read_through_its_adopted_master`
  keeps its name and unix gate, uses the helper with the marker
  `restored-write` and a 5-second deadline against the real PTY pair, fails
  with the renderer's text on "marker missing", and passes in a
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`
  run.
- [ ] AC-7 (NFR1, NFR2, NFR3; TS-5, TS-10): the only source file changed
  under `src-tauri/` is `src-tauri/src/mux/session/pane/tests.rs`;
  `Cargo.toml` and `Cargo.lock` are unchanged. Both
  `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml`
  and its `--no-default-features` variant compile, and the new helpers use
  no unix-only API.

## Test Notes

- AC-1 to AC-5 are unit tests of the helper and renderer, driven by the
  scripted reader. They are deterministic and platform-neutral. Write AC-1
  first and confirm it fails against the old single-read shape: one read,
  then a check for the marker. This is the FR4 red check.
- Suggested names: `read_echo_until_marker_finds_the_marker_after_a_prefix_only_first_read`
  (AC-1), `read_echo_until_marker_finds_the_marker_across_three_or_more_chunks`
  (AC-2), `read_echo_until_marker_reports_end_of_data_and_read_errors_with_the_collected_bytes`
  (AC-3), `read_echo_until_marker_reports_the_deadline_with_the_collected_bytes`
  (AC-4), `read_echo_until_marker_returns_as_soon_as_the_marker_is_complete`
  (AC-5). The implementer may adjust them and records the final names in
  the test record.
- Timing checks (AC-4, AC-5) assert only generous upper bounds. Never assert a
  tight lower bound.
- Every scripted reader that withholds or trickles data is released by its
  test after the helper returns. This lets its reading thread end and keeps
  threads from outliving the test.
- AC-6 is the existing real-PTY test. Under normal load it cannot force a
  short first read, which is why AC-1 and AC-2 exist. The load reproduction
  (TS-4) is run by the verify phase, not inside this task.
- AC-7 is checked by the build commands and by reading the diff.
