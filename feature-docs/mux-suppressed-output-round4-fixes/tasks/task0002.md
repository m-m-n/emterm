# Task Plan: task0002 — Awaiting designator at a cut writes the consumed ESC

## Goal

When the write filter closes at a cut while the client is waiting for a
charset designator, it writes one ESC byte to the ring after the bytes
already written. That ESC stands for the switch ESC the live client
consumed as the designator, so replay can no longer take a later byte as
the designator and fabricate a query (finding 48caec6f5b0b5810).

## Design

Follow IMPLEMENTATION.md D2 (this task owns the ESC in step 2 and clearing
the awaiting flag in step 3) and the write filter feed contract. Round3
SPEC as-02 and EC-2, which wrote the waiting `ESC (` with nothing after it,
are superseded. The round3 SPEC itself is not edited.

### When the client is awaiting a designator at a cut

The client is awaiting a designator at a cut when either holds:

- the run before the cut ends in `ESC (` / `ESC )` outside any string;
- the flag was carried in with an empty `pending`, and nothing has consumed
  the designator byte yet.

In that case the filter appends exactly one ESC (0x1B) after the bytes it
emits for that run, then clears the flag. It applies the same rule on every
path:

1. a cut inside the same call;
2. a cut at an empty segment, where an earlier read left the wait with an
   empty `pending` (fed range empty or not);
3. a cut that follows an overflow flush in its segment. Here the end-of-run
   wait is computed for the flushed run even though it is not the last
   segment. That computation runs on the overflow path only;
4. the reader's fallback closing, which reaches the filter as an empty fed
   range with a cut at 0.

When no designator is awaited, nothing extra is written:

- a complete designation such as `ESC ( A`;
- a carried designator consumed by the segment's first byte;
- a run that ends in an open string, which task0001 drops per D2 step 1.

The appended ESC never starts a strip target, because it is written after
the strip, and it is part of the bytes attributed to the outcome's dims.
