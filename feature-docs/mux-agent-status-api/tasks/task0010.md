# Task Plan: task0010 — safe PROTOCOL_VERSION upgrade path (v1 daemon survives)

## Goal

Upgrading an eMterm client from PROTOCOL_VERSION 1 to 2 must not strand a
long-lived v1 daemon that already owns user sessions. Either the v2 client
can talk enough of v1 to gracefully hand off, or daemon discovery detects
the version mismatch and offers a safe restart — but `mux kill` in
particular MUST work against a v1 daemon from a v2 client.

## Requirements

NFR2 (compatibility)

## Scope

### Files to Modify
- `crates/mux_ipc/src/protocol.rs` — the version handshake behavior. Add
  whichever of these fits the chosen strategy: dual-version accept,
  version-in-handshake with negotiated fallback, or making Shutdown
  always version-tolerant.
- `src-tauri/src/mux/cli.rs` and/or `src-tauri/src/mux/daemon.rs` — the
  discovery / handshake / handoff flow (`ensure_daemon_running`,
  connect path). Restricted to what's needed to implement the chosen
  strategy.

## Rework context (verbatim from review round 1)

> **stable_id: protocol_v1_v2_break — severity high, category architecture**
> The hard version bump makes every new client reject an existing v1
> daemon, but daemon discovery remains presence-based:
> `ensure_daemon_running` treats an existing Unix socket or connectable
> pipe as sufficient and never probes protocol compatibility. After
> upgrading eMterm, bridges and all mux CLI commands therefore fail
> against the long-lived old daemon. Even the new `mux kill` cannot
> recover it because the old server rejects the v2 Hello before
> processing Shutdown, leaving existing sessions inaccessible without
> manual process intervention.
>
> Suggestion: Add an upgrade strategy before enforcing the version
> boundary: either continue accepting v1 and capability-gate v2 pushes,
> or make daemon discovery perform a version handshake and provide a
> safe restart/handoff path. Ensure shutdown remains usable across
> adjacent protocol versions.

## Design

Pick ONE of these strategies (implementer's judgment, recorded in a
short design note in the commit body):

- **A: dual-version accept on the daemon side + capability gate for
  v2-only messages.** The daemon accepts both v1 and v2 Hellos. v1
  clients see the v1 message set; v2 clients see the v2 message set.
  This is the least user-disruptive path but doubles the compatibility
  matrix for the added messages (AgentStatusUpdate, ReadPane, SendText,
  WaitAgentState, AgentApiError).
- **B: version-probing discovery + graceful handoff on the client
  side.** `ensure_daemon_running` (or an equivalent pre-check) opens a
  short connection to probe the running daemon's PROTOCOL_VERSION. If
  it's older than the client's minimum, send a Shutdown request (which
  MUST work across adjacent versions — see below), wait for the
  daemon's exit, then relaunch a fresh v2 daemon. Session state IS
  lost — but that is the exact same outcome as a manual restart, and
  it becomes automatic and one-command instead of manual pkill +
  re-attach.
- **C: minimal-compat Shutdown-tolerant server.** The v2 server can
  parse a v1 Shutdown request even when the Hello's version field is
  wrong, so a v2 client that sees a version mismatch can at least send
  Shutdown to a v1 daemon and let the OS reclaim the socket. Recovery
  is manual after that (user runs the v2 daemon), but the "stranded"
  state is broken.

Strategy B is the smallest viable fix and probably the right default
for this codebase (sessions are per-daemon-lifetime already — see
FR3's "state is not persisted"). Strategy A is friendlier but broader.
The implementer records the choice in the commit body / PR description.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A test (integration or unit against the socket layer)
      demonstrates that a v2 client can gracefully recover from
      encountering a running v1 daemon: either the client speaks v1
      enough to continue (strategy A), or the client detects the
      mismatch and successfully performs handoff / Shutdown (strategies
      B / C).
- [ ] AC-2: `emterm mux kill` (or equivalent Shutdown path) succeeds
      against a v1 daemon from a v2 client, regardless of chosen
      strategy.
- [ ] AC-3: Under strategy B or C, the client's error message (or the
      handoff flow's user-facing output) explains what happened —
      users must not see an opaque bincode/decode error.
- [ ] AC-4: Existing v2 ↔ v2 handshake tests still pass; no regression
      in normal operation.

## Test Notes

Simulate a v1 server by forcing PROTOCOL_VERSION to 1 in a scoped test
harness (either a test-only const override or by manually crafting the
handshake bytes). The point of the test is to exercise the
mismatch-recovery path, not to keep v1 alive as a supported target.

## Out of Scope

- Making v1 clients able to talk to a v2 daemon (backward-compat).
- Any of the medium-severity findings in `handlers.rs` (task0011).
