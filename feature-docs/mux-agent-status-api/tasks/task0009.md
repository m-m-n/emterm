# Task Plan: task0009 — wire agent-status transition drain into notification pipeline

## Goal

`App::pump_all` drains `AgentStatusModel::transitions` and routes each real
transition through `App::maybe_notify_agent_transition`, so blocked/done OS
notifications actually fire per FR9 / US2. Closed panes discard their
notification-rate-limit state.

## Requirements

FR9, FR6, NFR3 (bounded transition queue)

## Scope

### Files to Modify
- `src-tauri/src/app.rs` — call `agent_status.drain_transitions()` in
  `pump_all` after applying reports; iterate and dispatch qualifying
  transitions to `maybe_notify_agent_transition`; call
  `discard_agent_notification_state` alongside every `agent_status.discard`
  site (close_tab, reap-exited-tabs, `pump_all`'s closed-pane loop)

Optionally (implementer's judgment, kept within the same task):

  model's `Transition` structure if the current `Option`/non-Option
  mismatch forces awkward conversion at the wire-up site (see task0004
  review finding `agent_state_type_duplication` medium; medium is out of
  auto-fix scope, but if trivial to align here it removes churn)
- `src-tauri/src/agent_status_model.rs` — expose whatever helper the
  wire-up needs (e.g. a Transition → AgentTransition converter or a
  filter predicate for Set-only transitions), if the wiring benefits from

## Design

Contract in `IMPLEMENTATION.md` (Shared Components / AgentStatusModel and
`App::maybe_notify_agent_transition`) is authoritative — the wiring code
CONSUMES that contract, does not restate it.

The pump-side loop, at a high level:

1. After applying agent-status events/updates and BEFORE `mark_seen`,
   `let transitions = self.agent_status.drain_transitions();`.
2. For each `Transition { pane, old_state, new_state, name }`:
   - Skip Clear transitions (`new_state.is_none()`) — only Set into
     blocked/done is notification-eligible per
     `is_qualifying_agent_state`.
   - Resolve `pane_visible`: `self.window_focused` AND the pane is
     currently displayed. `PaneKey::Tab(tab_id)` → active tab is that tab.
     `PaneKey::MuxPane(pane_id)` → active tab's `mux_group` contains
     `pane_id`.
   - Resolve `rate_limit_key`: for MuxPane, prefer
     `self.mux_public_pane_id(pane_id)`; for Tab, use the tab's stable
     string id. This key must be STABLE across the pane's lifetime and
     UNIQUE across concurrent panes (so the rate limiter is per-pane).
   - Resolve `tab_title` from the transition's pane by locating its
     containing tab.
   - Build the `AgentTransition` for the notification layer. If the
     `old_state`/`new_state` optionality mismatch or wire/core enum
     mismatch is awkward, address it in `notifications.rs` /
     `agent_status_model.rs` — see the optional scope above.
   - Call `self.maybe_notify_agent_transition(pane_key, pane_visible,
     &transition, &tab_title)`. Rate limiting and settings gating are
     the notification layer's job — do not reimplement them here.
3. Then continue with `mark_seen` and the rest of `pump_all`.
4. At every `agent_status.discard(pane_key)` call site (close_tab,
   reap-exited-tabs, `pump_all`'s closed-pane loop), also call
   `self.discard_agent_notification_state(&rate_limit_key)` for each pane
   being removed.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A production-path test (integration or `pump_all`-level unit
      test) demonstrates that a real Set-transition to blocked/done on a
      non-visible pane triggers exactly one call into the notification
      sink; a transition on the visible pane triggers zero.
- [ ] AC-2: A production-path test shows that repeated same-state reports
      trigger no notification, and Clear (new_state None) triggers no
      notification.
- [ ] AC-3: After every `pump_all` invocation,
      `AgentStatusModel::transitions` is empty (the drain runs
      unconditionally, even when the setting is off — the queue must not
      grow while the setting is toggled off).
- [ ] AC-4: A test demonstrates that closing a tab / pane discards both
      `AgentStatusModel` state AND the notification rate-limiter state
      for that pane's key.
- [ ] AC-5: Snapshot / replay-derived updates (`replay_derived: true`) do
      not enqueue transitions, so drain sees zero of them — verify the
      round-trip test for reattach still passes with no notifications.
- [ ] AC-6: All previously-passing tests still pass (nothing regressed in
      `agent_status_model`, `notifications`, `app`).

## Test Notes

Fault line is the visibility computation and PaneKey→(rate_limit_key,
tab_title) resolution — write those as pure helpers on `App` (or free
functions) so they can be tested without a full render loop. The
integration into `pump_all` itself is thin and reads as glue.
