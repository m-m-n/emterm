# Task Plan: task0012 — per-pane stateful OSC scanner (agent-status reports survive chunk boundaries)

## Goal

`scan_agent_status_reports` becomes per-pane stateful so a valid OSC
`agent-status` sequence that spans multiple PTY reads is detected and
delivered exactly once. FR1's "valid sequence" and FR3's "accepted
reports advance revision" hold regardless of how the transport chunks
the byte stream.

## Requirements

FR1 (OSC sequence validity), FR3 (revision semantics), NFR2, NFR3

## Scope

### Files to Modify
- `src-tauri/src/mux/scrollback_filter.rs` — turn the stateless scanner
  into a per-pane stateful decoder that retains partial OSC sequences
  across reader chunks.
- `src-tauri/src/mux/ipc/pty_spawn.rs` — hold the per-pane scanner
  state alongside the PTY reader; feed each chunk through it.

Optional, kept within this task if useful:
- `src-tauri/src/mux/session/pane.rs` — if the per-pane scanner state
  is naturally owned by the pane rather than the reader thread.

## Rework context (verbatim from review round 1)

> **stable_id: osc_split_lost — severity high, category spec (+ architecture)**
> SPEC FR1 defines each valid OSC agent-status sequence as a report;
> SPEC FR3 requires accepted reports to update pane state and revision.
> The scanner is explicitly stateless and documents that a report
> crossing an arbitrary PTY read boundary is not detected. Even a short
> sequence can be split at any byte boundary, so valid reports can
> disappear and waits can time out against stale state.
>
> Complete reports are also forwarded with a best-effort `try_send` in
> `pty_spawn.rs:624`, so channel pressure silently drops them
> (see stable_id `try_send_drops_reports`, medium — same file, related
> concern; consider addressing here if the fix naturally extends).
>
> Suggestion: Use a per-pane stateful OSC decoder that retains partial
> sequences across reads, preferably sharing the existing stream-scanner
> abstraction.

## Design

Model the scanner as a per-pane `OscScanner` (or similar):

- Owns a small carry-over buffer (a few KiB is plenty — the sequences
  are short) plus a decode state (Idle / SeenEsc / InsideOsc).
- `feed(chunk: &[u8]) -> Vec<AgentStatusEvent>` returns fully-decoded
  events and stashes any incomplete tail bytes to be resumed on the
  next `feed()`.
- The carry-over MUST have an upper bound (reject / reset when
  exceeding a fixed cap, e.g. 8 KiB — a legitimate `agent-status`
  payload is far smaller). This bounds attacker DoS via infinite
  unterminated OSC sequences.
- The scanner MUST also handle both OSC terminators (BEL `\x07` and
  ST `\x1b\\`), unterminated ESC recovery, and OSC types other than
  the emterm namespace (pass them through as "not our concern").

Integrate into the PTY reader:

- Each pane's reader thread owns one `OscScanner` instance across
  reader iterations.
- Every chunk is passed through the scanner AND through the existing
  strip logic (strip must also honor cross-chunk sequences so the
  bytes never enter scrollback — this is the same statefulness).

Optional (address `try_send_drops_reports` medium): once the scanner is
per-pane and stateful, switching from `try_send` to a
backpressure-friendly send (blocking send outside locks, or a
bounded send with an explicit "drop-count / retry" policy) is
naturally in-scope — SPEC FR3 requires accepted reports to advance
revision, and silently dropping them is a spec bug.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A test where a valid `agent-status` OSC sequence is fed
      to the scanner as two adjacent chunks (split at every possible
      byte boundary in a short parametric test) results in exactly one
      decoded event.
- [ ] AC-2: A test where multiple back-to-back OSC sequences arrive in
      one chunk still produces one event each, in order.
- [ ] AC-3: A test where an unterminated OSC prefix is followed by a
      much larger burst of non-OSC bytes still bounds the carry-over
      to the cap — no unbounded memory growth.
- [ ] AC-4: A test where the carry-over cap is exceeded results in the
      partial sequence being DROPPED (or reset) rather than producing
      a garbage event; the scanner recovers cleanly on the next real
      sequence.
- [ ] AC-5: Strip semantics are preserved: no `agent-status` byte
      makes it into scrollback even when split across chunks.
- [ ] AC-6: If the implementer chose to also fix `try_send_drops`, a
      test demonstrates that a full channel does not silently drop an
      accepted report.
- [ ] AC-7: Existing scan tests and PTY reader tests still pass.

## Test Notes

Parametric byte-boundary tests are the most efficient way to cover
AC-1 — one test parameterized over a small enum of realistic
sequences, chunked at every split point.
