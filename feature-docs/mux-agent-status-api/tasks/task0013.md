# Task Plan: task0013 — post-snapshot replay must synchronize cleared states

## Goal

`sync_agent_status_after_snapshot` (and the per-pane variant) emit a
replay-derived `AgentStatusUpdate` for every pane whose GUI state may
need to change — including panes whose current state is None but was
previously non-empty. After a reattach, no stale badge / summary is
shown for a pane that was cleared while the GUI was detached.

## Requirements

FR4 (post-snapshot state sync), FR5 (AgentStatusUpdate carries
state=None on clear), NFR2

## Scope

### Files to Modify
- `src-tauri/src/mux/daemon.rs` — `sync_agent_status_after_snapshot`
  (and `_after_pane_snapshot` if present): stop skipping panes whose
  state is None; emit a replay-derived AgentStatusUpdate for panes
  whose GUI might have stale state.

Optional, kept within this task if useful:
- `src-tauri/src/mux/session/pane.rs` — a "has ever been reported"
  flag or a nonzero revision counter to distinguish "clean pane
  never reported" from "cleared explicitly" (avoids emitting a
  no-op update for a fresh pane that never had state).

## Rework context (verbatim from review round 1)

> **stable_id: replay_clear_lost — severity high, category spec**
> SPEC FR4 says current states are synchronized after a snapshot
> through replay-derived FR5 messages, and SPEC FR5 explicitly allows
> the message state to be none/cleared. The synchronization loop
> skips every pane whose current state is None. If the GUI previously
> knew a non-empty state but missed a clear while detached, reattach
> cannot clear the stale badge or summary.
>
> Suggestion: Emit replay-derived updates for panes with an accepted
> clear (for example, revision > 0), carrying state/name as None;
> ensure synchronization covers every pane whose GUI state may need
> replacement.

## Design

Two decisions the implementer makes and records in the commit body:

1. **Which panes to emit updates for.** Options:
   - (a) Every pane, unconditionally — simplest; small extra network
     cost, but predictable. The GUI's `apply_daemon_update` is
     idempotent for no-op cases.
   - (b) Every pane whose revision > 0 — assumes revision starts at 0
     and increments only on accepted reports (per FR3 as designed
     in task0003). This is the "ever reported" filter without an
     extra flag.
   - (c) An explicit "ever reported" bit on the pane's AgentStatus —
     more precise but adds state.
   
   Recommended: (b), because task0003 already establishes
   revision-monotonicity.

2. **Ordering with existing sync messages.** The replay updates should
   be emitted alongside (in the same "sync burst") as the existing
   pane-name / window-name sync — so the GUI receives a coherent
   view of all pane state, not a partial one.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A test where a pane transitions blocked → cleared while
      the GUI is detached, followed by reattach, results in the GUI
      receiving a replay-derived AgentStatusUpdate with state=None
      for that pane (so the badge clears).
- [ ] AC-2: A test where a pane has never reported any state and the
      GUI reattaches: no unnecessary state=None update is delivered
      (the choice of option (b) above makes this pass automatically;
      option (a) would need a filter here).
- [ ] AC-3: A test where a pane's most recent report is a non-None
      state (working / blocked / done) still produces the correct
      replay-derived update on reattach — no regression to task0003's
      existing behavior.
- [ ] AC-4: replay-derived updates never trigger notifications (the
      GUI model's replay_derived flag already handles this; verify no
      change).
- [ ] AC-5: Snapshot payload format is unchanged (state is delivered
      via FR5 messages, not embedded in the snapshot bytes).
