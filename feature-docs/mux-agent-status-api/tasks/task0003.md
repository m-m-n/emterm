# Task Plan: task0003 — daemon agent-state store, OSC intercept, replay strip, broadcast

## Goal

The mux daemon owns per-pane agent state: it detects agent-status OSC in
pane output, updates {state, name, revision}, strips the sequences from
scrollback/snapshot replay, broadcasts AgentStatusUpdate to GUI clients,
and syncs state after snapshots with the replay_derived flag.

## Requirements

FR3, FR4, FR5 (daemon send side), NFR2 (snapshot format unchanged), NFR3

## Scope

### Files to Modify
- `src-tauri/src/mux/session/pane.rs` — per-pane agent status storage
  {state, name, revision}; lifecycle discard
- `src-tauri/src/mux/session/session.rs` — pane iteration/lookup helpers
  as needed
- `src-tauri/src/mux/session/manager.rs` — incarnation token generation at
  daemon start; access for public-ID minting
- `src-tauri/src/mux/scrollback_filter.rs` — extend the strip mechanism to
  remove agent-status OSC from replayable content
- `src-tauri/src/mux/daemon.rs` — OSC detection on pane output path;
  broadcast of AgentStatusUpdate on accepted reports
- `src-tauri/src/mux/ipc/handlers.rs` — post-snapshot state sync
  (replay_derived updates after snapshot delivery); PtyExited discard
- `src-tauri/src/mux/snapshot.rs` — hook point for post-snapshot sync if
  snapshot assembly lives here (verify; keep Snapshot payload unchanged)

## Design

- Use the shared `agent_status` core parser (contract in
  IMPLEMENTATION.md) — never a second parser.
- Accepted report (set/clear/same-state re-report) → revision += 1 →
  broadcast one AgentStatusUpdate (replay_derived=false) to attached GUI
  clients.
- Rejected sequences change nothing and broadcast nothing.
- Strip: agent-status OSC bytes never enter scrollback storage nor any
  snapshot/replay byte stream (extend the existing
  strip_replayable_rich_content-style filtering).
- After a client receives a snapshot (attach/window switch), send one
  AgentStatusUpdate per pane that currently has state, with
  replay_derived=true.
- Pane destroy / PtyExited discards the pane's status (no update message
  needed beyond existing pane-lifecycle messages; GUI drops state on pane
  removal).
- State is in-memory only.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A set report in pane output updates that pane's state/name and
      increments revision; a clear report empties state and increments
      revision.
- [ ] AC-2: Same-state re-report increments revision (and is broadcast);
      rejected sequences leave state and revision untouched.
- [ ] AC-3: Agent-status OSC bytes are absent from stored scrollback and
      from snapshot replay bytes; all other bytes pass through unchanged.
- [ ] AC-4: Accepted reports produce exactly one AgentStatusUpdate with
      replay_derived=false and the correct public pane ID.
- [ ] AC-5: After snapshot delivery, each stateful pane produces one
      AgentStatusUpdate with replay_derived=true; stateless panes produce
      none.
- [ ] AC-6: PtyExited/pane destroy discards the pane's agent status.
- [ ] AC-7: The incarnation token is generated once per daemon start and
      all public IDs minted in this run share it.
- [ ] AC-8: Existing snapshot/replay tests pass unchanged (snapshot payload
      format untouched).
