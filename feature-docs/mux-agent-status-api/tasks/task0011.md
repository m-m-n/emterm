# Task Plan: task0011 — mux read returns rendered rows; send_text drops the manager lock

## Goal

`mux read` returns the tail N RENDERED rows (not ANSI-stripped raw
scrollback) with the byte cap keeping the newest suffix, per FR10.
`handle_send_text` releases the session-manager lock before performing
the synchronous PTY write, so other mux API tasks and the Tokio worker
are not blocked by a stalled child.

## Requirements

FR10 (mux read rendered rows), FR11 (send_text watermark still returned),
NFR3 (event-driven; no polling; capped responses)

## Scope

### Files to Modify
- `src-tauri/src/mux/ipc/handlers.rs` — `handle_read_pane` render
  reconstruction and byte-cap suffix retention;
  `handle_send_text` lock hygiene (clone Arcs under the manager lock,
  release, then write).
- `src-tauri/src/mux/session/pane.rs` — if the pane needs to expose a
  cloneable PTY-writer handle for `handle_send_text` to use without
  holding the manager lock, add it here (mirror the pattern
  `handle_read_pane` uses for `pane.shadow_parser.clone()` /
  `pane.scrollback.clone()`).

## Rework context (verbatim from review round 1)

> **stable_id: mux_read_render_missing — severity high, category spec**
> SPEC FR10 requires the tail N rendered rows from current screen plus
> scrollback. The scrollback path merely removes escape bytes and calls
> `str::lines()`, so terminal wrapping, carriage returns, cursor
> movement, erasure, and overwritten cells are not rendered.
> Additionally, when the byte cap is exceeded, `truncate` keeps the
> oldest prefix and removes the newest suffix, so the result is no
> longer the tail.
>
> Suggestion: Maintain or reconstruct scrollback as rendered terminal
> rows, select the final N rows, and enforce the byte cap by retaining
> the UTF-8-safe suffix containing the newest output.

> **stable_id: send_text_lock_held — severity high, category performance**
> `handle_send_text` keeps the `session_manager` mutex guard alive
> while `pane.write_input` performs synchronous `write_all` + `flush`.
> A 1 MiB payload against a non-consuming child can block; during that
> time every task needing the manager stalls (ReadPane,
> WaitAgentState, pane creation/destruction, snapshots, status
> updates), while a Tokio worker is also blocked. `handle_read_pane`
> already drops the lock before scrollback work — SendText should
> follow the same pattern. (Two reviewers agreed: claude+codex
> performance.)
>
> Suggestion: Clone per-pane writer/status handles under the manager
> lock, then release it. Serialize writes through a bounded per-pane
> writer task/channel, or at minimum use `spawn_blocking` after
> dropping the manager guard; obtain the revision watermark within the
> same per-pane serialized operation.

## Design

### mux read rendered rows

The current screen is already rendered by the pane's `ShadowParser`
(or equivalent VT parser). For scrollback, either (a) render on the
fly by feeding scrollback bytes through a scratch VT parser and reading
the resulting rows, or (b) if the pane keeps a rendered-row scrollback
representation, read from it directly. Option (a) is more general;
(b) is faster if the representation already exists.

Cap semantics: the response is the LAST N rendered rows subject to a
total byte cap. If the byte cap is smaller than the last N rows,
retain the newest suffix (drop leading rows / bytes, never trailing),
splitting at UTF-8 code-point boundaries.

### send_text lock hygiene

Mirror `handle_read_pane`'s pattern:

1. Acquire `session_manager.lock().await`.
2. Resolve the pane; clone the specific Arcs the write needs (the
   PTY-writer handle and the `AgentStatus` for the watermark).
3. Drop the manager guard (scope out).
4. Take the revision watermark from the AgentStatus lock (a brief
   `std::sync::Mutex` lock, no I/O).
5. Perform the PTY write via the cloned writer handle. If necessary,
   guard the write with a per-pane `tokio::sync::Mutex` on the pane's
   writer (or a small serializer task) to preserve atomic-per-request
   semantics.

      write (SPEC FR11 semantics unchanged).
- [ ] AC-5: `handle_send_text` still writes bytes atomically per

      task, or Tokio-side single-writer invariant).
- [ ] AC-6: Existing handler tests still pass.

## Test Notes

The lock-hygiene test needs concurrent tasks and a stalled writer to
observe the blocking behavior. A test harness with a
`tokio::sync::mpsc` write sink whose consumer is paused is the
straightforward approach. For rendered-rows, a fixture scrollback with
`\r`-overwrites is enough to distinguish the two implementations.
