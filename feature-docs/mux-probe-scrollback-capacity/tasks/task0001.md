# Task Plan: task0001 — Client-capacity message: protocol, GUI report, bridge relay

## Goal

The client-capacity control message exists in the mux protocol. A GUI tab sends
its own scrollback capacity as the first control frame of each attach. The bridge
forwards the message and, after an upgrade reconnect, re-sends the latest one before
the stored Attach.

## Requirements

FR1, FR2, FR3, NFR1, NFR2, NFR3, NFR4, NFR5

## Design

### Protocol (owner of the shared definition)

- Add the variant, the `from_u8` arm and the payload type with the names,
  discriminant, payload rule and placement pinned in IMPLEMENTATION.md Shared
  Components (D3). The variant's doc comment states the following: direction
  client to daemon, pane id 0, a 4-byte little-endian capacity, no response, and
  an older daemon drops the message through the existing unknown-type path.
- Four existing tests pin 0x27 as the first unmapped byte: the message-type round
  trip, the agent-API round trip, the upgrade round trip, and the "byte adjacent
  to the upgrade types" frame-body test. Each moves its boundary to 0x28 and keeps
  its intent. No other existing assertion changes.

### GUI tab

- Precondition: the Welcome is accepted, a session is present, and it is the first
  Welcome of this attach (the existing first-Welcome guard). The capacity message
  is then the first control frame the Welcome handler sends. It goes before Attach,
  before the Resize seeding and RequestPaneSnapshot, and on the fresh-start path
  before CreateWindow.
- Value: the tab's own core scrollback capacity, read when the message is sent. It
  is fixed when the core is built (SPEC A-5). The tab never reads the global
  setting and never clamps the value (IMPLEMENTATION.md D1, D2).
- A duplicate Welcome in the same attach sends no further capacity message; the
  existing guard already covers it.
- The message goes out through the existing control send path, so the transport
  (APC on Linux, EMUX plaintext on Windows) is chosen exactly as for every other
  control message.
- Test observer: a `cfg(test)` record of type, pane id and payload for every
  control frame the send path handles. The existing payload-only outbound record
  keeps its current meaning, because other tests depend on it.

### Bridge

- Stored state: for the lifetime of the bridge process, the bridge keeps the
  latest capacity frame body next to the latest Attach frame body. Both survive
  reconnects, the same way the existing Attach slot does.
- Forwarding: the bridge forwards the capacity message to the daemon unchanged,
  like any other message, and its frame body replaces the stored capacity. Other
  message types never change the stored capacity. Attach capture is unchanged.
- Reconnect flow (Unix only), after the reconnect handshake succeeds:
  1. If a capacity frame is stored, write it.
  2. If an Attach frame is stored, write it.
  3. Return the connection. With nothing stored, nothing is written, which is
     today's behaviour.

  A failed write of the capacity frame is logged at warn. It does not stop the
  Attach attempt.
- Windows: the bridge forwards and records the message but has no re-send path.
  The Windows main loop gets only the mechanical change it needs to own the slot.
- The bridge never interprets the value (IMPLEMENTATION.md D1).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, NFR1): `from_u8(0x27)` returns the new variant. A message with pane id 0 and a 4-byte payload round-trips unchanged through the frame body, APC, OSC 9999 and EMUX plaintext encodings. Every pre-existing discriminant maps as before, and PROTOCOL_VERSION is 3.
- [ ] AC-2 (FR1, NFR2, TM-2): The payload decoder returns the value for exactly-4-byte little-endian inputs of 0, 50, 10,000, 10,001 and u32::MAX. It returns nothing for inputs of 0, 3, 5 and 8 bytes, and never panics. The encoder emits exactly 4 little-endian bytes, and each listed value round-trips.
- [ ] AC-3 (NFR1): Byte 0x28 is unmapped: both `from_u8` and `from_frame_body` report it as unknown. The daemon codec discards a raw 0x28 frame without an error and returns the next valid frame. The four existing boundary assertions now pin 0x28 instead of 0x27.
- [ ] AC-4 (FR2): On the first accepted Welcome whose session has panes and windows, the tab's first control frame is the capacity message. It has pane id 0 and carries the tab core's scrollback capacity. Attach follows, then the Resize frames and RequestPaneSnapshot. Tests cover a tab built at capacity 0 and a tab built at a small non-default capacity.
- [ ] AC-5 (FR2): On the first accepted Welcome whose session has no panes, the capacity message comes before CreateWindow. A second Welcome in the same attach sends no further capacity message.
- [ ] AC-6 (FR3): The bridge forwards a capacity message to the daemon socket unchanged and stores its frame body. A later capacity message replaces the stored one. A non-capacity message leaves the stored capacity unchanged. Attach capture behaves as before.
- [ ] AC-7 (FR3): After an upgrade reconnect on Unix, the first frames the stand-in daemon receives after the handshake are the stored capacity frame and then the stored Attach frame. With no stored capacity it receives only the Attach, as today. With a stored capacity and no stored Attach it receives only the capacity frame.
- [ ] AC-8 (NFR3, NFR4, NFR5): The default-feature lib tests, the mux_ipc crate tests and the CLI-only check pass. Any new diagnostic is at warn or higher. Only the files listed in this plan are formatted.

## Test Notes

- AC-1 to AC-3 are unit tests in the protocol test module and the codec test
  module. For the plaintext round trip, follow the existing plaintext tests that
  mirror the bridge parser: strip the prefix and the terminator, then decode through
  the APC decoder with the APC prefix. The codec test follows the existing
  unknown-frame test that uses the removed 0x11 type.
- AC-4 and AC-5 use the existing Welcome message helper in the tab tests. They build
  tabs through the tab constructor's scrollback argument (0, and a small value such
  as 7). They read the new control-frame record to check order and value.
- AC-6 and AC-7 follow the existing Attach-capture test and the reconnect test that
  uses a stand-in daemon on a plain thread. The forwarding test may feed the frame
  in EMUX plaintext form, so the bridge parser's plaintext path is exercised as well.
- The verification commands do not compile Windows-only code. Keep `cfg(windows)`
  edits mechanical and point them out in the task report.

## Out of Scope

- How the daemon handles, stores and uses the reported value.
- Re-sending the capacity after a settings change. A tab's capacity is fixed per core (SPEC A-5).
- Any Windows reconnect behaviour.
- The probe's `scroll_region_scrollback_enabled` divergence (SPEC A-8).
