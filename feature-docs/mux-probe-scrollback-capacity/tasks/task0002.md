# Task Plan: task0002 — Daemon per-connection capacity drives the wrap-restore probe

## Goal

The daemon records each connection's reported client capacity. Every wrap-aware
snapshot it sends to that connection runs the replay-state probe at
`min(reported, 10,000)`, or at 10,000 when nothing was reported. At 10,000 the
output is byte-identical to today's, and regression tests show that small client
capacities combined with a grow-resize now restore continued output to the correct
row.

## Design

### Probe capacity resolution (single source of truth in the snapshot-bytes module)

- **Cap**: 10,000 lines. This is the existing probe constant with its value
  unchanged. Its documentation is rewritten to cover three points:
  - (a) For client capacities above 10,000, a residual cursor-row mismatch after a
    grow-resize remains.
  - (b) In mixed old/new GUI, bridge or daemon combinations the connection keeps
    working, but the fix is not guaranteed and the legacy 10,000 applies.
  - The cap limits load amplification only and does not change lock-hold time
    (follow-up `3b5bbd839c74d67b`).

  The current text says 10,000 was chosen to match the test suite's oracle depth.
  It is replaced, because the probe now follows the client's capacity.
- **Resolution function**, visible within `crate::mux`. Input: an optional reported
  u32. Output: a u32 probe capacity. Unreported gives 10,000. A reported value r
  gives `min(r, 10,000)`. The function is pure and allocates nothing.
- **Probe**: builds its scratch terminal at the smaller of the value it receives
  and the cap. No caller can make it exceed the cap, even by bypassing the
  resolution function (TM-1).
- **Builders**: both wrap-aware builders, the reattach/on-demand one and the resume
  one, gain a probe-capacity argument. They pass it through the shared dump-block
  tail to the composer and the probe. Nothing else in byte assembly changes: the
  layout, the segments and the composition order are identical (FR7). The plain,
  non-ring builders are untouched.
- **Layering**: the snapshot-bytes module and its dump-block child still import
  nothing from `mux::ipc` or `mux::session` (IMPLEMENTATION.md Layer Structure).

### Per-connection state and intake (FR1, FR4)

- The connection loop owns one reported-capacity value per connection. It starts
  as "unreported", which is a separate state from a reported 0 (IMPLEMENTATION.md
  D2). The value is not stored on the session or the pane, is not part of the
  hot-upgrade handoff, and ends with the connection. Only the connection's own task
  reads or writes it, because every handler that needs it runs on that task.
- Router arm for the new message:
  1. Decode the payload with the shared payload decoder.
  2. If a payload is decoded, store it, replacing any earlier report.
  3. If nothing is decoded (malformed payload), log at warn with the message type
     and payload length only, leave the stored value unchanged, and return
     normally so the connection stays open.
  4. Send no reply in either case.

  The arm allocates nothing whose size depends on the payload.
- The single-shot CLI-client path is unchanged. Real CLI clients never send this
  message, and its existing unsupported-message reply stays.

### Reaching the four assembly sites (FR5)

The connection's value is resolved at the moment each snapshot is assembled, and
the resulting u32 is passed down:

1. **Attach**: the attach handler passes it to reattach collection, which passes it to the reattach builder.
2. **RequestPaneSnapshot**: the on-demand handler passes it to the shadow-parser ring builder.
3. **SetVisibility(true)**: the resolve-and-resume path passes it to the visibility resume. A resume deferred on the connection's deferred-output queue gets the connection's value at flush time, on both the ordinary flush and the fair-permit path. The queue is per connection, so this is always the requesting connection's value.
4. **Evaluate-output-target**: the resume branch builds with the value passed in. The production caller on the hidden edge passes it too, although that branch is not reached in production today.

### Observing which capacity a site used

Tests use a wrapped-ring fixture with a grow-resize for which a capacity-0 probe
and a 10,000 probe restore different cursor rows. A site's snapshot must equal the
builder output at the expected capacity and differ from the output at the other
capacity.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR5): The probe is run at capacity C, for C in {0, a small non-zero value, 10,000}, on a wrapped main-buffer pane. The pre-dump payload has one of three shapes: a rows-only grow segment, a rows+cols grow segment, or a current_dims larger than the last segment. For each C and each shape, the probe reports the same scroll region, origin mode, cursor row/col, SGR and pending-wrap state as an oracle terminal built at capacity C that replays the same payload through the same replay entry point.
- [ ] AC-2 (FR4, FR5, FR6, NFR1, NFR2, TM-1): The resolution maps unreported to 10,000, 0 to 0, 50 to 50, 10,000 to 10,000, 10,001 to 10,000, and u32::MAX to 10,000. For a reported value above 10,000, the wrapped snapshot still carries the dump block and equals the output at 10,000. Whatever value it is passed, the probe never builds a scratch terminal deeper than 10,000 lines.
- [ ] AC-3 (FR7): At probe capacity 10,000, both wrap-aware builders produce payloads and segments that are byte-identical to the pre-change implementation for the existing wrapped fixtures, pinned by golden output captured before the change. All pre-existing wrap-restore, dump-block, pty_spawn and pane snapshot tests pass, changed only by the added capacity argument.
- [ ] AC-4 (FR9): Builder-level regression tests combine a wrapped ring with each of the three grow shapes and a client capacity C in {0, a small non-zero value}. Each test builds the snapshot at probe capacity C, replays it on a client terminal of capacity C through both the reset-and-replay-segments path and the off-thread build-from-snapshot path, and then feeds a continuation (a CR LF followed by a marker). The cursor row/col, and the row holding the marker, must equal those of an oracle of capacity C that replays the delegated pre-dump payload plus the same continuation. With the probe forced to a fixed 10,000, at least one case fails, and the test record says which.
- [ ] AC-5 (FR1, FR4, NFR2, TM-2): A valid capacity message sets the connection's value. A capacity message whose payload is not exactly 4 bytes leaves the value unchanged, sends no frame to the client and does not end the connection. No reply is sent for a valid message either. An explicit 0 and no report give different probe capacities (0 versus 10,000). Two connections that reported different values each get snapshots built at their own value.
- [ ] AC-6 (FR5): Each of the following snapshots is built with the requesting connection's resolved probe capacity: the visible reattach; the on-demand RequestPaneSnapshot; the visibility resume, both on the immediate path and when deferred through the connection's deferred-output queue and flushed later by the ordinary flush or by the fair-permit path; and the evaluate-output-target resume branch.
- [ ] AC-7 (FR8, NFR4): The cap constant's documentation states both known limits (the residual mismatch above 10,000, and the legacy fallback for mixed versions) and states that the cap does not change lock-hold time. Every new diagnostic is at warn or higher.
- [ ] AC-8 (NFR3, NFR5): The default-feature lib tests (single-threaded), the mux_ipc crate tests, the CLI-only check and the CLI-only lib tests pass. Only the files listed in this plan are formatted.

## Test Notes

- **Red first (AC-4)**: write the regression tests before changing the probe. Show
  red by running them with the probe at a fixed 10,000 and record the failing case
  in the test record. The existing grow-resize test comment in the dump-block
  module notes that the shape with current_dims larger than the last segment
  diverges between capacity 0 and capacity 10,000 (row 23 versus row 39). C = 0
  with that shape is therefore the expected red case.
- **Small non-zero C**: pick a value smaller than the number of rows the grow adds,
  for example 5 against a 24-to-40 grow, so that it can diverge from 10,000.
- **Golden output (AC-3)**: capture it before editing the builders. A wrapped
  fixture with a grow-resize and one without both qualify.
- **Site-reach tests (AC-6)**: use the distinguishable-capacity fixture described
  in Design. Visibility tests cover the immediate path and a deferred item flushed
  by each of the two flush paths.
- **Router-level tests (AC-5)**: send the new message with a 3-byte payload, then
  check three things: the handler result is normal, no frame was admitted, and a
  following snapshot still uses the earlier value.
- **Test threads**: replay-related tests are order-sensitive under parallel runs.
  The workflow test command already runs single-threaded.
