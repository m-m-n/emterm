# Task Plan: task0001 — Split-aware live spans for the mux feed scanner

## Goal

The mux reader carries the partial state of an alternate-screen switch
sequence from one read to the next, and the feed scanner receives, for every
read, the live spans the bulk extraction of the same bytes would give, so a
mux pane ends in the plain tab's OSC 7501 table and OSC 777 state however the
switch sequences are split. The scrollback write path is unchanged.

## Design

### Terms

- **Switch pattern**: one of the alternate-screen switch sequences the
  extraction recognizes (?1049 / ?1047 / ?47, `h` / `l`), at most 8 bytes.
- **Client rule**: term_core's rule, which the main-buffer extraction already
  follows: every recognized switch pattern changes the screen, except one
  whose `ESC` sits in the charset-designator slot (the byte right after
  `ESC (` / `ESC )`), which is the designator plus printed text.
- **Shadow rule**: the shadow parser's (vt100 0.16) rule: every `ESC` aborts
  what came before it, so a switch whose `ESC` sits in a designator slot does
  switch; and only ?1049 and ?47 switch — vt100 0.16 ignores ?1047.
- **Bulk extraction**: the main-buffer extraction run once over the whole
  stream, from the main screen with the designator slot at ground. Its spans
  never include a completed switch pattern's bytes, whichever screen the
  switch leaves.

### Component: split-aware live-span tracker (`write_filter.rs`)

Responsibility: given each read in order, together with the shadow parser's
alternate-screen state before and after that read, return the read's live
spans for the feed scanner (read-relative byte ranges, ascending,
non-overlapping, in the same form as the extraction's spans).

Carried state, constant size:

- the screen under the client rule;
- the screen under the shadow rule (used only for the cross-checks below);
- the designator-slot state (same meaning as the reader's existing
  `DesignatorSlot`);
- a partial switch pattern: the at most 7 bytes of a proper prefix of a switch
  pattern that the last read ended in, and its kind — **live** (its `ESC` is
  a live `ESC` under the client rule) or **designator** (its `ESC` is a
  designator, so under the client rule it is printed text, while under the
  shadow rule it may still complete a switch).

Per-read flow:

1. **Start check.** If the shadow parser's state before the read differs from
   the tracker's shadow-rule screen, adopt the parser's state for both
   screens and drop the partial. (This covers anything that changed the
   shadow parser between reads, such as the reader rebuilding it after a
   panic.)
2. **Continue the partial.** If a partial is carried, the read's leading
   bytes either complete its pattern, extend it (the whole read is still a
   proper prefix), or diverge from it.
   - On completion of a live partial, both screens follow the switch under
     their own rule at the completing byte; the pattern's bytes are not live.
   - On completion of a designator partial, only the shadow-rule screen
     follows (if the pattern is one vt100 acts on); its bytes are printed
     text, live when the client-rule screen is main.
   - On divergence, the partial's bytes were ordinary bytes after all, and
     the read is scanned from the diverging byte on exactly as one buffer
     holding the partial and the read would be scanned — a lone carried
     `ESC` followed by `(` / `)` opens a designator slot, and a diverging
     `ESC` may start a new pattern.
3. **Scan** the rest of the read with the extraction's existing rules
   (live switches, designator slot), moving the client-rule screen on each
   live switch and the shadow-rule screen on each switch the shadow rule
   counts. Bytes on the main screen under the client rule are live; switch
   patterns are not.
4. **Record the new partial.** If the read ends inside a proper prefix of a
   switch pattern, carry it with its kind. The bytes of a live partial that
   lies on the main screen are the read's **undecided tail**: they are not
   live. The bytes of a designator partial are decided (printed text) and are
   live when the client-rule screen is main.
5. **End check.** If the tracker's shadow-rule screen differs from the shadow
   parser's state after the read, the read gets today's fallback spans (the
   whole read when the parser was on the main screen before and after it, no
   live span otherwise), and the tracker adopts the parser's state for both
   screens and drops the partial.

Contract (postcondition): for any input, the returned spans lie inside the
read, and the carried partial is at most 7 bytes. When neither check
disagrees, the spans equal the bulk extraction's spans restricted to the
read, except that undecided-tail bytes are not live.

Why the undecided tail is safe: a partial is a prefix of a switch pattern —
it starts with `ESC` and holds no `BEL` or `\` — and the scanner decides
liveness only at a `BEL` / `\` that commits a string, at the byte before an
in-body `ESC`, and at a read's last byte while it is inside an OSC body. None
of these can fall on an undecided-tail byte, so the scanner's items do not
depend on that choice (AC-2). IMPLEMENTATION.md Open Questions records this
reading of FR1.

The main-buffer extraction keeps its signature and results (existing tests
call it). The tracker may reuse its private scanning helpers; it may not
change their behavior for the extraction.

### Reader wiring (`mod.rs`)

- One tracker per reader loop, created next to the scanner and the
  designator slot the loop already carries.
- Inside the capture step, after the shadow update, the tracker is advanced
  with the read and the shadow parser's states before and after it — on
  every read the shadow parser processes, in order, whether or not the read
  takes the fallback and whether or not it is later suppressed.
- The step returns the tracker's spans next to the values it returns today.
  The scanner is fed the read with the tracker's spans.
- Unchanged (FR5): the bytes to write, the cuts, the fallback's empty write
  with its single cut, the scrollback write filter, and the `live_spans`
  value handed to the suppressed-chunk pipeline as the ring-written ranges.
  Update the comment at the scanner call so it names the tracker's spans as
  the scanner's input and `live_spans` as the ring-written ranges.

### Doc comments in `write_filter.rs`

Existing tests read `write_filter.rs` as text. New or edited doc comments in
that file must not contain the phrases "counts a string body as ground",
"a string body counts as", "at most one of the two", "writes at most one
closure" or "or ends an APC / DCS body at it", and must keep the phrases
"STRING_BODY_CLOSING", "open string body" and "`ESC` + CAN" present.
