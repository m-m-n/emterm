# Task Plan: task0001 — Bound the wheel-report path with a dedicated notch cap

## Goal

One wheel event can no longer request an unbounded allocation or an unbounded
PTY write: a report-path-only notch cap is enforced both where the wheel delta
becomes a notch count and where the single-notch report payload is duplicated,
with the duplication step extracted into a pure, unit-testable function.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Scope

### Files to Create

None. Every change lands in existing files.

### Files to Modify

- `src-tauri/src/window_host/input_translate.rs` — add the report-path cap
  constant; make the wheel-delta → notch conversion saturate against it ahead of
  the integer conversion; document the new postcondition on that function. The
  alternate-scroll constant and the alternate-scroll byte-producing function in
  this same file are NOT touched.
- `src-tauri/src/window_host/pointer_routing.rs` — extract the inline
  duplication step of the wheel-report branch into a pure bounded helper that
  re-applies the same cap, and rewire that branch to call it instead of
  allocating and repeating inline.
- `src-tauri/src/window_host/tests.rs` — add unit tests for the conversion's
  boundary, pathological and invariant behaviour, and for the bounded
  duplication helper. The three existing wheel-conversion tests and the existing
  alternate-scroll clamp test stay in place with their assertions unedited.

## Design

Contracts for the cap constant, the conversion function and the bounded
duplication helper are pinned in IMPLEMENTATION.md ("Shared Components"); the
rationale for the two clamp layers, the dedicated constant, the pre-conversion
saturation, the single capped value and the preserved write granularity is in
IMPLEMENTATION.md decisions D2–D6. Do not restate or renegotiate them here —
implement against them.

Task-local flow, end to end for one wheel event on the report path:

1. The wheel delta arrives as a line count in floating point.
2. The conversion rejects non-finite input by yielding zero.
3. The conversion takes the magnitude's floor, then saturates that magnitude at
   the cap **while it is still a floating-point value** (IMPLEMENTATION.md D4).
4. The saturated magnitude is converted to a signed integer and the sign of the
   original delta is applied. The result's absolute value is at most the cap for
   every possible input.
5. The routing branch, which already holds the single-notch report payload and
   the destination tab, obtains the notch count from step 4 and, when it is
   non-zero, calls the bounded duplication helper with the payload and the
   count's magnitude.
6. The helper caps the requested count at the same constant, computes that
   capped value once, and uses it both to size the preallocation and to bound
   the repetition (IMPLEMENTATION.md D5). It reads no host state.
7. The routing branch performs exactly one PTY write with the returned buffer.
   A zero notch count writes nothing at all (IMPLEMENTATION.md D6).

Placement notes:

- The cap constant lives in the translation module beside the conversion it
  guards, because both clamp layers reference the same definition and the
  routing layer already depends on the translation layer.
- The duplication helper lives in the routing module, next to the branch that
  uses it, because it produces routing-layer output; it takes only a payload
  slice and a requested count, so it is testable without any host state.
- Nothing introduced here is visible beyond the `window_host` module tree, and
  the conversion function's existing visible signature is unchanged.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, NFR5): A report-path-only cap constant exists in the
      translation module, equals 100, and is referenced by both clamp layers.
      The alternate-scroll cap constant and the alternate-scroll byte-producing
      function are byte-identical to their pre-task state, and neither constant
      is defined in terms of the other.
- [ ] AC-2 (FR2, NFR1, NFR2): For every `f32` input — including non-finite
      values, the largest and smallest finite values, and values just above the
      cap — the conversion returns a value whose absolute value is at most the
      cap, and the saturation happens before the float-to-integer conversion so
      no saturated integer extreme is ever produced as an intermediate value.
- [ ] AC-3 (FR3, NFR3): Below the cap the conversion's behaviour is unchanged:
      non-finite → 0, magnitude below one whole line → 0, sign follows the input
      delta, magnitude is the floor of the absolute value. The three existing
      wheel-conversion tests pass with their assertions unedited.
- [ ] AC-4 (FR4): The duplication step is a standalone function taking only a
      payload byte slice and a requested repeat count, returning the duplicated
      buffer. It references no application, tab, host or terminal state, and its
      tests call it directly without constructing any host state.
- [ ] AC-5 (FR5, NFR1): The helper caps the requested count at the same
      constant, computes the capped value once, and derives both the
      preallocation size and the repetition bound from that one value. For any
      requested count up to the largest unsigned 32-bit value, the returned
      buffer's length is at most the payload length × the cap.
- [ ] AC-6 (FR6): The wheel-report branch no longer allocates or repeats
      inline — it calls the helper. Observable behaviour is otherwise unchanged:
      a zero notch count produces no PTY write, and a non-zero notch count
      produces exactly one PTY write per wheel event carrying the whole
      duplicated buffer.
- [ ] AC-7 (FR7, FR8, NFR6): New unit tests covering TS1–TS7 exist in the
      module's existing test file, in the existing inline style with
      `<subject>_<scenario>_<expected>` names and standard-library assertions
      only, and they pass. No new test framework dependency is added.
- [ ] AC-8 (NFR4): Both project build commands succeed after the change — the
      default-feature library test build and the no-default-features check
      build. No crate dependency is added, and nothing introduced by this task
      is visible beyond the `window_host` module tree.

## Test Notes

Write the tests first, then implement until they pass. Every test in this task
is a unit test; the feature has no integration or E2E surface.

| Scenario | Covers | Notes |
|----------|--------|-------|
| TS1 boundary conversion | AC-2, AC-3 | 99.999 → 99, 100.0 → 100, 100.999 → 100, 101.0 → 100, and each negated input yields the negated result |
| TS2 pathological conversion | AC-2 | NaN → 0, both infinities → 0, the largest finite value → the cap, the smallest (most negative) finite value → the negated cap |
| TS3 near-zero and sub-notch conversion | AC-3 | both signed zeros → 0, ±0.999 → 0, 1.999 → 1, -1.999 → -1 |
| TS4 conversion invariant sweep | AC-2 | a fixed set of finite inputs — small, boundary, large, extreme, both signs — each asserted to have magnitude at most the cap. A hand-written input list, not a property-testing crate (NFR6) |
| TS5 helper degenerate cases | AC-4, AC-5 | requested count 0 → empty buffer; requested count 1 → byte-for-byte identical to the payload |
| TS6 helper around the cap | AC-5 | requested count 100 → exactly 100 concatenations; requested counts 101 and the largest unsigned 32-bit value → exactly 100 each |
| TS7 helper length invariant | AC-5 | representative payloads (including an empty payload and a realistic single-notch report payload) × requested counts {0, 1, 99, 100, 101, largest unsigned 32-bit value}: the returned length never exceeds payload length × the cap |
| TS8 existing conversion regression guard | AC-3 | the three existing tests must remain untouched; if one needs editing to pass, the below-cap semantics were changed and the implementation is wrong |
| TS9 alternate-scroll regression guard | AC-1 | the existing alternate-scroll clamp test must remain untouched and pass |

TDD-awkward item, with its planned handling: **AC-6's call-site behaviour** (no
write at zero notches; exactly one write otherwise) cannot be asserted by a unit
test — the branch needs application and tab state the existing suite does not
construct, and the SPEC deliberately declares no integration test for it. The
planned handling is: (a) keep the change to that branch strictly a substitution
of the inline allocation/repetition by the helper call, leaving the surrounding
guard and the write call untouched; (b) record the code-inspection result
against VERIFICATION.md's manual item. Do not build a new host-state harness for
this — that is a larger change than the fix and is out of scope.

Realistic-payload note for TS7: use a byte sequence shaped like a single-notch
report (about ten bytes), taken as test data. It does not need to be produced by
the encoder under test; the invariant is about length arithmetic.

## Out of Scope

- The alternate-scroll path: its cap constant and its byte-producing function
  stay byte-identical. Do not unify, rename, re-tune or share them (NFR5).
- Restructuring write granularity: no per-notch writes, no batching change, no
  change to when the branch decides to write (IMPLEMENTATION.md D6).
- Any change to the conversion function's visible signature or to the visibility
  level of anything in the `window_host` module tree (NFR4).
- New crate dependencies of any kind, including property-testing and
  benchmarking crates (NFR4, NFR6).
- Any UI, rendering, design-token, egui or child-WebView change — this feature
  has no UI surface.
- Building a host-state test harness for the routing branch, or reworking
  neighbouring pointer-routing logic that the wheel-report branch does not need.
