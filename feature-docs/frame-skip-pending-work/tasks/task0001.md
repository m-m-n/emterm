## Design

### 1. Non-consuming restart peek (FR1, NFR1)

- `restart_pending() -> bool` in `self_exec`. Postcondition: returns the
  current value of the restart flag and leaves it unchanged — any number of
  consecutive peeks observe the same value.
- `restart_required()` keeps its swap-reset contract: the first read after a
  failure returns true, subsequent reads return false (arms the toast
  exactly once).
- The flag itself is target-neutral (only its setters are Linux-gated), so
  the peek follows the module's existing structure without new target
  gating; on non-Linux targets the flag is simply never raised.

### 2. `App::frame_work_pending(&self) -> bool` (FR2, NFR3)

True iff any of the following holds:

1. a toast is already up (the existing toast predicate), OR
2. the SFTP progress channel is non-empty, OR
3. the SFTP duplicate-check result channel is non-empty, OR
4. the restart peek reports true.

Contract: evaluation consumes nothing — no channel drain, no flag swap, no
state mutation. Cost is one atomic read plus two constant-time channel
emptiness checks plus the existing toast check; it takes no lock the App
does not already hold.

### 3. Call-site rewiring (FR3, FR4)

- `render_surface`: in the `overlay_work` expression, ONLY the toast term
  changes to the new predicate. The other skip-gate terms (dirty rows,
  status bar, bell, search, sidebar, egui input) are out of scope.
- `event_loop`: the read feeding `toast_redraw_due` supplies the new
  predicate. The pure pacing helper keeps its shape (a boolean plus
  rate-limit inputs); the meaning of that boolean widens from "toast up" to
  "toast up or pre-toast pending work", reflected in comments / parameter
  naming, not logic.

### 4. Wait deadline (FR5 — resolved per IMPLEMENTATION.md D1)

`next_toast_deadline()` gates on the new predicate: it returns a
poll-cadence-bounded deadline while any pending work exists (toast up OR
pre-toast work) and nothing when fully idle. This closes the rate-limit
race described in D1 — do not keep the old toast-only gate here.

### 5. Documentation (FR6)

- `pump_toasts` doc: the known-limitation paragraph ("a pending SFTP event
  with no toast up yet … relies on another redraw trigger") is rewritten to
  state the new guarantee: pre-toast pending work now keeps frames alive
  through the new predicate.
- `toast_pending` doc: its claim that the redraw pacing / skip veto /
  deadline all call it directly is corrected — those three now call the new
  predicate, which includes it as one term.

### 6. Test seams (FR7)

- The SFTP channel senders are private to the service; add a
  `cfg(test)`-gated way to make each receiver non-empty from tests
  (synthetic-event push or equivalent). The production channel layout and
  public API are unchanged.
- The restart flag is module-private; add a `cfg(test)`-gated, crate-visible
  setter so App-level predicate tests can raise it. Every test that raises
  it restores clear state before returning.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `restart_pending()` peeks without clearing: after raising the
      flag, two consecutive peeks both report true, and a subsequent
      `restart_required()` still returns true exactly once and false
      afterward (consume semantics unchanged). (TS-4, TS-5)
- [ ] AC-2: On a freshly constructed App with empty SFTP channels and a
      clear restart flag, `frame_work_pending()` is false. (TS-1)
- [ ] AC-3: `frame_work_pending()` is true for each pending source
      independently — progress channel non-empty, result channel non-empty,
      restart flag raised — and evaluating it consumes nothing: the queued
      event is still receivable and the raised flag still observable
      afterward. (TS-2, TS-3, TS-4)
- [ ] AC-4: The `overlay_work` toast term (render_surface) and the pacing
      read feeding `toast_redraw_due` (event_loop) both read
      `frame_work_pending()`; neither site reads `toast_pending()` directly
      any more. (wiring — verified by inspection in review, behavior by
      TS-7 manual)
- [ ] AC-5: `next_toast_deadline()` returns a bounded deadline while
      pre-toast pending work exists (e.g. a queued progress event with no
      toast up) and nothing when fully idle; the existing deadline tests
      stay green. (TS-6)
- [ ] AC-6: The `pump_toasts` known-limitation paragraph and the stale
      `toast_pending` doc cross-references describe the new gating — no
      remaining claim that pre-toast pending work relies on another redraw

- [ ] AC-7: The full `--lib` suite passes single-threaded; all three check
      configurations (Linux GUI, no-default-features, Windows cross) and
      the format check complete with zero warnings. (TS-9)
