# Task Plan: task0002 — Bridge: move stdout writes off the tokio runtime thread

## Goal

The mux bridge's daemon→stdout direction no longer executes synchronous
stdout syscalls on the tokio runtime thread: a full GUI-side PTY buffer can
stall, at most, the daemon→stdout forwarding once its bounded buffer fills —
never the stdin→daemon direction and never the runtime thread — while frame
order, error semantics, and the exit sequence stay as today.

## Requirements

FR2, FR3, FR4, NFR1, NFR3

## Scope

### Files to Create

- (none)

### Files to Modify

- `src-tauri/src/mux/bridge.rs` — `forward_loop`'s `daemon_to_stdout`
  block (currently a synchronous stdout lock + write inside the async
  block, ~594-621); the new stdout writer component and its bounded
  admission channel; inline tests.

## Design

### Problem (current shape)

`daemon_to_stdout` reads a frame from the daemon socket, then writes the
encoded bytes to the process's stdout with a synchronous lock + write
inside the async block. When the GUI's PTY buffer is full, that syscall
blocks the OS thread running the tokio runtime — stalling not just this
future but the concurrently-selected `stdin_to_daemon` direction too. This
is the chain origin for the connection-level freeze (the daemon's socket
then backs up into FR1's site).

### Target shape (contracts, not mechanics)

- **Stdout writer**: a dedicated blocking-capable writer context (its own
  OS-thread-backed execution, not the async runtime thread) becomes the
  only place forwarded frames are written to stdout. It consumes a bounded
  FIFO channel and writes in dequeue order.
- **Forwarding future**: `daemon_to_stdout` keeps reading/classifying
  frames from the socket (`decide_daemon_frame_effect` unchanged) but,
  for `Forward` frames, only admits them to the writer's channel via an
  asynchronous, yielding wait — it never performs a stdout syscall itself.
  `Announced` / `Ignored` handling stays on the async side unchanged.

Invariants (each maps to an AC):

1. **No sync stdout on the runtime (FR2)**: in the forwarding path, every
   stdout syscall happens in the writer context. A stalled stdout consumer
   therefore suspends (not blocks) only the daemon→stdout future once the
   channel fills; `stdin_to_daemon` — a sibling future on the same
   runtime — keeps forwarding keystrokes throughout.
2. **Bounded progress independence (FR2/FR4)**: while stdout is stalled,
   the socket-drain direction keeps reading frames until the bounded
   channel fills, then exerts backpressure toward the daemon (socket fills
   upstream). Memory growth is capped by the channel bound (explicit named
   capacity constant with rationale).
3. **FIFO (FR3)**: forwarded frames reach stdout in socket order — single
   admission channel, single writer, no reordering.
4. **Transport parity**: the encoding decision (undetected → both OSC and
   APC; otherwise the detected transport's encoding) observes the shared
   transport state at write time in the writer context — the same
   per-frame resolution point as today.
5. **Error parity**: a stdout write error terminates the forwarding —
   observable to the async side so `daemon_to_stdout` ends and
   `forward_loop` returns, exactly as today's break-on-write-error. A
   socket read error likewise ends the loop as today, with the writer
   given a bounded opportunity to drain already-admitted frames.
6. **Exit-sequence parity**: `finish_bridge_exit`'s synthetic Detached
   must remain the last bytes written to stdout. Before the caller
   proceeds to `finish_bridge_exit`, the writer for the ended
   `forward_loop` call is quiesced (drained within a bound, then stopped)
   so no queued frame can interleave with or follow the synthetic
   Detached. `finish_bridge_exit` itself is unchanged (the runtime is done
   at that point; its direct stdout use stays).
7. **Reconnect compatibility**: `forward_loop` is called repeatedly across
   the Unix reconnect loop; the writer's lifecycle is contained within (or
   correctly spans) those calls such that each call observes a working
   writer and quiesced predecessors — no stranded writer keeps stdout
   after its call returns.
8. **Platform neutrality (NFR3)**: `forward_loop` is shared by
   `bridge_main_loop` (Unix) and `bridge_main_loop_windows`. The change
   must be platform-neutral in compilation and must not modify
   `bridge_main_loop_windows` itself; Windows-specific validation and any
   Windows-only blocking sites are out of scope — Unix establishes the
   pattern.

### Testability seam

Real process stdout cannot be captured in tests. Factor the writer pump so
its output sink is injectable (the production caller supplies process
stdout; tests supply a controllable sink that can block until released,
fail on demand, and record write order). Keep the seam minimal — the pump's
contract (invariants 1-6) is what tests target, mirroring how
`decide_daemon_frame_effect` was already extracted pure for testability.
Helpers that need PTY/pipe APIs are gated `#[cfg(all(test, unix))]`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR2): with the injected sink blocked, admitted frames
  accumulate only up to the channel bound and the admitting side remains
  responsive (admissions up to the bound complete without waiting on the
  sink; the next admission suspends rather than blocking a thread) —
  asserted with named bounded timeouts.
- [ ] AC-2 (FR2): while the pump's sink is blocked (and even once its
  channel is full), the sibling stdin→daemon direction continues to make
  progress: a stdin-fed mux message still reaches the daemon-side
  transport within the named timeout — driven through `forward_loop` with
  in-memory transports and the injected sink. Honest-TDD note: this
  criterion cannot be observed red against the CURRENT code, because the
  current block writes to the real process stdout, which a test cannot
  stall; the implementer records it as verified against the reworked
  structure (per-invariant pump tests plus this `forward_loop`-level
  test), not as red-then-green.
- [ ] AC-3 (FR3): after a blocked sink is released, the sink has received
  exactly the admitted frames in admission order (no loss, no reorder).
- [ ] AC-4 (FR4): the writer channel's capacity is a named constant; a
  test demonstrates admissions up to the bound succeed while the sink is
  blocked and the next admission suspends until the writer drains one —
  boundedness observable, no unbounded fallback path.
- [ ] AC-5: a sink write error ends the forwarding: the async side
  observes termination and `daemon_to_stdout`/`forward_loop` conclude as
  today (same `ConnectionEnded` semantics; `Announced` classification
  unaffected).
- [ ] AC-6 (NFR3): `bridge_main_loop_windows` is textually untouched, and
  both `cargo check` variants (default features and
  `--no-default-features`) pass, demonstrating the shared change is
  platform-neutral in compilation.

## Test Notes

- AC-1/AC-3/AC-4/AC-5 target the extracted pump with the injected sink —
  unit-scale, deterministic, no real stdout. Use a sink that parks on a
  gate the test releases; record order; every wait bounded by a named
  timeout constant (5 s per IMPLEMENTATION.md Convention 5).
- AC-2 builds on the existing `forward_loop` test style (in-memory duplex
  transports, stand-in daemon side) already present in `bridge.rs`'s
  inline tests.
- Transport parity (invariant 4) can be pinned by asserting the
  both-encodings behavior for an undetected transport through the pump.
- Commands (exact strings, from the project root):
  `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml`,
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`,
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib -- --test-threads=1`,
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --test mux_throughput`,
  `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features`.
