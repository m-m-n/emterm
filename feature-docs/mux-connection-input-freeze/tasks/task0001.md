# Task Plan: task0001 — Connection task: decouple socket sends from the select! loop

## Goal

The daemon connection task keeps polling client input (`framed.next()`)
within a bounded delay even while the socket send buffer is full, by moving
all client-bound socket writes out of the `select!` arm bodies into a
single, bounded, independently-draining outbound path — without changing
same-pane frame ordering, backpressure, PTY-exit reap semantics, or the
Upgrading-ack contract.

## Requirements

FR1, FR3, FR4, FR5, NFR1, NFR4

- `src-tauri/src/mux/ipc/handlers.rs` — `route_message` and the handlers it

- `src-tauri/src/mux/ipc/mod.rs` — only if the implementer factors the

  untouched.

## Design

### Problem (current shape)

`handle_connection`'s GUI loop owns one framed transport for both
directions. The PTY-batch drain arm feeds and flushes that transport at a
point position inside its arm body (connection.rs ~665-671): when the
socket send buffer is full, those awaits park the entire task, so
`framed.next()` (SwitchWindow, key input) stops being polled — the residual
freeze this feature closes. The notification arm and `route_message`'s
reply sends share the same shape one level down.

### Target shape (contracts, not mechanics)

Once the GUI message loop starts (after handshake/Welcome; the CLI-client
path `handle_cli_client` returns before the loop and may keep today's
undivided transport):

- **Outbound writer**: exactly one component owns the socket's write side
  and is the only place socket write/flush occurs. It consumes a bounded
  FIFO admission queue and writes frames in dequeue order. It drains
  independently of the connection loop — its progress depends only on the
  socket, never on the connection loop's scheduling.
- **Admission path**: every client-bound frame produced inside the GUI loop
  (drain-arm PTY/snapshot frames, PtyExited frames, `route_message`
  replies, reattach frames, notification forwards, the kick arm's
  Detached) enters this one queue. Wire order = admission order; there is
  no second route to the socket.
- **Read side**: the connection loop keeps sole ownership of the socket's
  read side and continues to poll it as the client-message arm.

Invariants (each maps to an AC):

1. **Drain-arm non-blocking admission (FR1)**: the drain arm never awaits
   outbound capacity at a point position. When it cannot admit everything
   it consumed, it holds the unsent remainder in loop-owned, bounded state,
   stops consuming `pane_output_rx`, and resumes via a capacity-acquisition
   future polled as its own `select!` arm — mirroring the existing
   fair-reservation pattern (`arm_pending_deferred_reserve` /
   `pending_deferred_reserve`), including that pattern's documented
   placement rule (the capacity arm must be listed before the drain arm
   under `biased`). While the remainder is held, every other arm — the
   client-message arm above all — keeps being polled.
   `route_message`'s reply sends MAY await admission (request-response
   traffic was capacity-dependent before this task too, and the writer now
   drains independently, so this is no longer a self-block); the drain arm
   MUST NOT.
2. **FIFO (FR3)**: chunks consumed from `pane_output_rx` are admitted in
   consumption order; a held remainder is admitted before any newer chunk.
   Same-pane Snapshot and PtyOutput frames therefore reach the wire in
   channel order, exactly as today.
3. **Deferred-output consistency (FR3)**: the drain arm remains the only
   consumer of `pane_output_rx`, so the deferred-output machinery's
   capacity-freeing point is unchanged: `flush_deferred_output` and the
   fair reservation still resolve when the drain arm consumes. The chain
   "outbound capacity frees → drain consumes → pane channel capacity
   frees → deferred work progresses" must hold; the rework must not add a
   second capacity-freeing point nor remove this one.
4. **Boundedness (FR4)**: the outbound queue and any held-remainder state
   have explicit named capacity bounds with rationale comments. Worst-case
   transient memory stays in the same order of magnitude as today's drain
   batch bound (`DRAIN_BATCH_LIMIT`'s documented ~4 MB). No unbounded
   channel anywhere.
5. **Reap at consumption (NFR4)**: an empty-data PtyOutput chunk (PTY
   exit) triggers the pane-reap path exactly once at the moment the drain
   arm consumes it — independent of whether the corresponding PtyExited
   frame is ever successfully written to the client. This preserves
   "reap regardless of delivery success" now that delivery outcome is no
   longer synchronously observable in the arm.
6. **Ack after flush (NFR4)**: the Upgrading-frame ack fires only after
   the Upgrading frame has been written and flushed to the socket —
   delivery, not queueing. The admission path therefore supports a
   per-frame post-flush notification for designated frames (used only by
   the Upgrading forward today).
7. **Failure and teardown parity**: a socket write/flush failure in the
   writer is observable to the connection loop and terminates it (same
   break-and-detach outcome as today's `send_err`/`flush_failed`
   handling). On loop exit (kick, client EOF, error), already-admitted
   frames — including the kick arm's Detached — get a bounded,
   best-effort flush before the connection tears down, equivalent to
   today's best-effort sends.

### Reworked drain-arm flow

1. Receive first chunk from `pane_output_rx` (arm fires only when the loop
   is not already holding an unsent remainder).
2. Drain up to the batch limit non-blocking; merge consecutive same-pane
   chunks (existing behavior).
3. For each merged chunk, classify (Snapshot / PtyOutput / PTY-exit) as
   today; run the reap path now for exit chunks (invariant 5).
4. Admit resulting frames to the outbound queue without blocking; on
   queue-full, store the remainder as held state and arm the
   capacity-acquisition future (invariant 1).
5. Run `flush_deferred_output`, then `arm_pending_deferred_reserve`
   (existing sequence, unchanged trigger point — invariant 3).

### Starvation-guard interaction

The existing G2/G4 guard (`allow_client_message_arm` /
`has_unforwarded_pane_output` / `next_client_msg_starvation_count`)
protects queued output from a continuously-ready client. Its "pending
output" signal must be extended to also count a held unsent remainder and
armed outbound-capacity acquisition as outstanding output work, so the
guard's bounded-progress guarantee covers the new state. The guard's
quota semantics themselves do not change.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1/FR5): a connection-level test drives the real
  `handle_connection` loop over an in-memory duplex transport whose
  server→client capacity is small, floods a pane's output channel until
  the socket side is saturated (client deliberately not reading), then
  sends a client message (input for a different pane) — and asserts the
  message is processed (observable at that pane's captured writer) within
  the named 5-second timeout constant. This test fails against the current
  code (drain arm parked in flush) and passes after the rework.
- [ ] AC-2 (FR3): same-pane Snapshot and PtyOutput frames are observed by
  the client in channel order through the reworked path, including when a
  held remainder / deferred retry is exercised; the existing
  connection-level saturation test
  (`connection_level_deferred_snapshot_survives_sustained_saturation_and_input_keeps_flowing`)
  passes unmodified in its assertions (harness adaptation allowed).
- [ ] AC-3 (FR4): every queue/holding structure added by this task has an
  explicit named capacity bound; a test (or existing-test assertion)
  demonstrates that when the outbound path is full the connection stops
  consuming `pane_output_rx` (upstream backpressure observable) instead of
  buffering without bound.
- [ ] AC-4 (NFR4): a test demonstrates that a PTY-exit chunk consumed
  while frame delivery to the client cannot succeed still reaps the pane
  (reap independent of delivery outcome).
- [ ] AC-5 (NFR4): a test demonstrates the Upgrading ack does not fire
  while the Upgrading frame is queued behind a saturated socket, and fires
  once the frame has been written and flushed (socket drained).
- [ ] AC-6: a socket write failure terminates the connection loop with
  today's outcome (loop exits; panes detach via the existing teardown
  path) — covered by a test with a transport that fails writes, or by
  existing tests remaining green if they already pin this.

  (duplex transport, `MuxPane::new_test*`, CapturingWriter, background
  producer threads using the same blocking-send shape as the PTY reader).
  Key lever: a small duplex buffer plus a client that stops reading makes
  the socket genuinely saturated; the named timeout constant is 5 s per
  IMPLEMENTATION.md Convention 5. Observe red before implementing (TDD).
- AC-2 reuses/adapts the existing saturation test (VERIFICATION TS2); add
  an explicit ordering assertion if the existing one does not already pin
  same-pane order across the new admission path.

  ack-designation logic should be factored so they are testable without a
