# Task Plan: task0003 — Outbound admission path: restore bounded remainder, single ordered admission, and teardown delivery

## Goal

Restore the three invariants of the GUI connection's outbound admission
path that review round 1 found broken after the auto-fix loops: the held
`outbound_remainder` is bounded by construction again (no producer can grow
it in proportion to notification or client-message traffic), every
client-bound frame producer admits through one shared, FIFO-preserving
admission path (reply / reattach frames can no longer overtake a held
remainder), and frames still held at loop exit — including the kick arm's
Detached — get a bounded best-effort delivery at teardown instead of being
silently dropped.

## Design

### Problem (state after review round 1's auto-fix)

task0001 introduced the single-writer outbound path; the review round's
auto-fix loop 3 then rerouted the notify and kick producers through
`outbound_remainder` to fix frame overtaking — but only the drain arm
carries the `outbound_remainder`-empty gate. Three contract breaks result:

1. **Boundedness broken (FR4)**: the notify arm appends to a held
   remainder unconditionally. While the client stalls its reads the
   remainder's drain rate is zero (the fair-reservation arm resolves only
   when the client reads), so RenameWindow / AgentStatusUpdate / Notify
   traffic grows the remainder without bound, and a broadcast Lagged
   resync amplifies this by all sessions × all windows per lag. The
   `outbound_remainder` declaration comment and the
   `OUTBOUND_QUEUE_CAPACITY` memory accounting both still claim the old
   bound and are now false. Secondary effects: a never-empty remainder
   permanently closes the drain arm (PTY output starves — FR1), and
   head-of-line blocking can push the Upgrading ack past
   `UPGRADE_PREPARE_TIMEOUT` (NFR4-adjacent).
2. **Single ordered path broken (FR3)**: `route_message` replies
   (handle_create_window / handle_upgrade_request / the Detach reply),
   `handle_attach`'s error reply, and `send_reattach_data`'s PaneCreated /
   SnapshotRestore still admit directly into the queue, bypassing a held
   remainder — later frames overtake older held PtyOutput. Worst case is
   reattach: a same-pane SnapshotRestore overtaking older held PtyOutput
   makes the client apply stale output on top of the snapshot. The
   correct admission procedure exists only as copies inside
   `handle_connection`'s arm bodies, and the one abstraction the module
   exports (`OutboundHandle`) is a bypassing producer.
3. **Teardown delivery broken**: the kick arm appends Detached to the
   remainder and breaks, but teardown only flushes frames already admitted
   into the queue — the remainder is dropped, so a kicked client with a
   held remainder never receives Detached (protocol contract regression:
   eviction degrades to a bare socket EOF).

### Target contracts (invariants; each maps to an AC)

1. **One admission component (closes the architecture drift)**: the
   outbound admission state — the bounded queue sender, the held
   remainder, and the in-flight fair reservation — is owned by a single
   component (natural home: `outbound.rs`), and every producer on the GUI
   loop admits only through it: the drain arm, the notify arm (single
   forward and Lagged resync), the kick arm's Detached, `route_message`
   replies (including via `ReplySink`), `handle_attach`, and
   `send_reattach_data`. The raw queue sender is not reachable from
   handlers or reattach code; the only consumers of the queue's receive
   side remain the dedicated writer task. The component exposes an
   "is holding a remainder" predicate for the loop's gates and
   starvation-guard bookkeeping, and its remainder-draining machinery
   keeps the existing fair-reservation placement contract (polled ahead of
   the drain arm under `biased`).
2. **FIFO (FR3)**: for every frame the component accepts, wire order =
   acceptance order. A held remainder always reaches the wire before any
   frame accepted later, regardless of which producer supplied it. In
   particular, same-pane SnapshotRestore / PaneCreated / reply frames
   admitted while a PtyOutput remainder is held are delivered after those
   held frames.
3. **Bounded-by-construction remainder (FR4, FR1)**: while a remainder is
   held, no producer may add frames in proportion to notification or
   client-message arrival counts. Per-producer resolution:
   - *Drain arm*: keeps its existing remainder-empty gate.
   - *Notify arm*: gated off while a remainder is held (same gate shape as
     the drain arm). Notifications then wait in the broadcast channel
     (fixed capacity); overflow takes the existing Lagged resync path once
     the arm resumes — notification semantics are preserved by that
     existing recovery mechanism, and a resync starting from an empty
     remainder contributes at most the current window count. With the
     gate in place, the "append to non-empty remainder" branch of the
     single-forward path becomes unreachable and is removed rather than
     left as dead code.
   - *Kick arm*: may append its single Detached to a held remainder (it
     breaks the loop immediately, so the contribution is one frame).
   - *Reply / reattach producers* (`route_message` path): these run only
     when the client-message arm processes a message, and they were
     capacity-awaiting before this feature, so they MAY await delivery
     progress (task0001 invariant 1's existing carve-out). They must
     admit through the component in a way that both preserves invariant 2
     (no overtaking) and leaves the remainder no larger than before the
     call completed — e.g. an ordered blocking admission that first
     drains the held remainder into the queue and then admits its own
     frames, serialized with the fair-reservation arm so exactly one
     mechanism drains the remainder at a time (the component owns that
     serialization; the two must not race or duplicate sends). The net
     effect: client-message-driven production cannot accumulate frames in
     the remainder across messages.
   The resulting worst-case remainder bound (one drain batch's frames, or
   one resync's window count, plus the single kick Detached) is stated in
   the updated `outbound_remainder` declaration comment and reconciled
   with the `OUTBOUND_QUEUE_CAPACITY` doc's memory accounting.
4. **Teardown delivery**: on loop exit without a writer failure, teardown
   first performs a bounded best-effort FIFO admission of the still-held
   remainder into the queue (within the existing named teardown-flush
   budget), then drops the senders so the writer drains and exits as
   today. A kicked client that resumes reading therefore receives the
   held frames followed by Detached; a client that never reads still
   tears down within the existing bounded budget. Frames that do not fit
   within the budget are dropped exactly as today's already-admitted-only
   flush would have dropped them — the guarantee is best-effort and
   bounded, not absolute.
5. **Unchanged contracts (NFR1, NFR4)**: no change to `crates/mux_ipc`,
   the codec, or any wire message shape. Reap-at-consumption and
   ack-after-flush keep their task0001 contracts (the ack still fires in
   the writer after feed+flush; restoring remainder boundedness is what
   removes the new head-of-line threat to the ack's timeliness).

### Starvation-guard interaction

The G2/G4 guard already counts a held remainder and an armed outbound
reservation as pending output (`has_pending_output`) while excluding the
remainder from `excludable_work` (a held remainder must not exclude the
client arm — finding 9537da352469bc68's rule). Consolidating the state
into the admission component must preserve exactly these signals (the
component's "is holding" predicate feeds them); the quota semantics do not
change. Gating the notify arm adds no new starvation class: the arm
resumes as soon as the remainder empties, which requires client reads —
the same condition that already gates the drain arm.

  the drain arm.
- [ ] AC-3 (FR3 — findings 79d48554f94fd3df / ebb33f43f48f612a): with a
  PtyOutput remainder held, frames produced by the reply / reattach path
  (at minimum a same-pane SnapshotRestore + PaneCreated, plus one
  `route_message` reply) are observed by the client strictly after every
  held remainder frame — no overtaking; same-pane SnapshotRestore never
  precedes older held PtyOutput.

  outbound queue sender is owned by the admission component; handlers and
  reattach code receive the admission context (signature-level), and

  the writer wiring. The component's remainder machinery is exercised by
  unit tests independent of a live connection (mirroring the module's

  `outbound_remainder` declaration comment and the

  does not enforce), and `outbound.rs`'s module / `OutboundHandle` docs
  describe the single admission path as implemented.
- [ ] AC-7 (regression): the full `--lib` suite and the `mux_throughput`
  integration test pass with no new failures; the existing
  connection-level saturation and ordering tests keep their assertions
