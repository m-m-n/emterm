# Task Plan: task0001 — Namespace the learned public pane id in the notification rate-limit key

## Goal

A mux daemon's `public_pane_id` can no longer reach another pane's or tab's
agent-notification rate-limit bucket, because the learned-id branch of the key
derivation wraps the daemon string in a code-owned namespace instead of
returning it verbatim — and the two doc comments in that region describe what
the code actually does.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None. This task modifies existing files only.

### Files to Modify

- `src-tauri/src/app/agent_status.rs` — the learned-id branch of the rate-limit key derivation now returns the namespaced form; the derivation's doc comment is corrected; the ingest path, the public-id accessor and the two call sites in this file stay behaviourally unchanged
- `src-tauri/src/app/mod.rs` — the field doc on the agent-notification rate limiter stops describing a mux key as a pane's public id and describes it as a key produced by the shared derivation
- `src-tauri/src/app/tests/agent_status.rs` — one existing unit scenario and one existing end-to-end scenario are updated to the new expected key; three new scenarios are added
- `src-tauri/src/app/tab_lifecycle.rs` — expected to stay unchanged; it is listed because it is the fourth call site and part of the verification surface, so a correction there is not a plan deviation

## Design

This task implements the whole feature. The cross-task contracts it works
against — the derivation's pre/postconditions, the key namespace convention,
the single-derivation-point rule and its ordering obligation — are pinned in
IMPLEMENTATION.md (Shared Components, Conventions, CD-1 through CD-3) and are
not restated here.

### What changes

Exactly one behavioural change: in the pane-key branch that handles a mux pane
whose public id HAS been learned, the derivation stops returning the learned
string and instead returns the namespaced form — the literal namespace prefix
for learned ids, then the connection scope's numeric value, then a colon, then
the learned string embedded verbatim. Nothing about the string is inspected,
validated, escaped or truncated on the way in.

The other two branches are untouched: the unlearned mux pane keeps the
scope-qualified fallback form and the plain tab keeps the tab form, both byte
for byte as today.

### What must not change

1. Ingest keeps storing the daemon-supplied public pane id verbatim. No
   protocol-level parse call and no rejection path is added.
2. The public-id accessor keeps returning that stored string unchanged, so the
   mux sidebar and every other reader observes exactly today's value.
3. The five existing fixtures whose public ids would fail the mux protocol's
   own parse stay exactly as they are. Rewriting them into parseable forms
   would silently delete the coverage that proves point 2.
4. All four call sites keep obtaining the key from the shared derivation, and
   the two sites that remove a pane's learned-id entry keep deriving the key
   BEFORE that removal.
5. Badge aggregation, tab-title resolution and visibility resolution keep
   their current results — this task changes no behaviour outside the key
   derivation.

### Derivation flow (unchanged in shape)

1. The caller passes the learned-id map and the pane key.
2. Plain tab → the tab form.
3. Mux pane with a learned entry → the namespaced learned form.
4. Mux pane with no learned entry → the scope-qualified fallback form.
5. There is no fifth outcome: no failure path, no panic, and an empty learned
   string still takes step 3.

### Doc comments

Both corrected comments must state the post-change truth: all three produced
forms are mutually disjoint by construction because each begins with its own
code-owned prefix before any daemon-controlled bytes appear, and the learned
daemon string is never returned unwrapped. Neither comment may retain the
claim that the mux prefix is what protects the learned-id branch.

## Acceptance Criteria (MANDATORY)

AC-1 through AC-7 use the SPEC.md acceptance-criteria numbering, so an
identifier means the same thing in both documents. AC-8 is task-local.

- [ ] AC-1: For a mux pane whose public id has been learned, the derived key
      is the learned-id namespace prefix, the connection scope's numeric
      value, a colon, and then the learned string verbatim; it never equals
      the learned string on its own. In the same scenario, an unlearned mux
      pane still derives the scope-qualified fallback form and a plain tab
      still derives the tab form, both unchanged from today. (TS-1)
- [ ] AC-2: A daemon that supplies a learned id equal to a plain tab's key
      cannot reach that tab: the derived key carries the learned-id namespace
      prefix and differs from the key that tab derives. The comparison is made
      against a key obtained from the derivation itself, not against a
      hand-written string. (TS-2)
- [ ] AC-3: A daemon that supplies a learned id equal to an unlearned pane's
      fallback key cannot reach that pane: the derived key differs from the
      key that unlearned pane derives, so the reserved fallback form is
      unreachable from a daemon string. (TS-3)
- [ ] AC-4: Two connections that each learn a public id for their own pane
      derive different keys, because the scope component differs; and repeated
      derivation for the same scope and pane is stable, so the per-pane rate
      limit still suppresses a second notification inside the window. Driven
      end-to-end through the real message path, with expected strings built
      from ids observed at runtime rather than hard-coded. (TS-4)
- [ ] AC-5: Arm and discard agree through the real call sites: after a mux
      pane with a learned public id fires a blocked transition, an immediate
      second transition is suppressed; after that pane closes, the next
      transition fires again. The scenario asserts no literal key string. (TS-5)
- [ ] AC-6: The public-id accessor still returns the raw learned string for
      every pane, including ids that fail the mux protocol's own parse; no
      parse call and no rejection path exists on the ingest path, and the five
      existing unparseable fixtures are still present and still unparseable. (TS-6)
- [ ] AC-7: Both doc comments — the one on the derivation and the field doc on
      the rate limiter — describe the post-change behaviour, and neither still
      claims that the mux prefix protects the learned-id branch. (TS-7,
      verified in review)
- [ ] AC-8: Both build configurations are green: the default-feature test
      command passes with no scenario outside this task's own updates newly
      failing, and the CLI-only feature check still compiles.

## Test Notes

TDD order — each new or updated assertion is written before the derivation
change, and must fail against today's code for the right reason:

1. **AC-1 (TS-1)**: extend the existing derivation unit scenario. It builds
   the learned-id map by hand and needs no application instance. Only the
   learned-pane expectation changes; the fallback and tab expectations stay
   as they are and act as the regression guard for FR2 and FR3.
2. **AC-2 and AC-3 (TS-2, TS-3)**: two new unit scenarios in the same
   hand-built-map style, one per reserved form. Compare derived key against
   derived key so the scenarios keep their meaning if the forms are ever
   reshaped.
3. **AC-4 (TS-4)**: update the existing scoped end-to-end scenario that drives
   two connections. Stable ids are allocation-order dependent, so build the
   expected strings from the ids the scenario itself observes; hard-coded
   numbers here are the known flakiness source. Keep both the
   two-keys-differ assertion and the bare-public-id assertions.
4. **AC-5 (TS-5)**: a new scenario in the style of the existing discard
   scenarios. This is the only scenario that exercises the arm site and a
   discard site together, so it is what actually protects the derive-before-
   removal ordering. It must not name a key string.
5. **AC-6 (TS-6)**: assert the accessor's output for an unparseable id after
   ingest. Existing fixtures already supply suitable values.
6. **AC-7 is not test-translatable.** No doc-drift test covers these two
   comments, and adding one is out of scope. It is verified in review as TS-7
   — write the corrected comments as part of the same change and call them out
   in the completion report so the review perspective can check them.
7. **AC-8** is a command outcome, not a scenario: run the default-feature test
   command and the CLI-only check. The touched module sits behind the GUI
   feature gate, so the CLI-only build should be entirely unaffected — a
   failure there means something leaked out of the gate.

Edge cases worth an explicit assertion or a deliberate note: an empty learned
string still takes the learned branch (no fallthrough, no panic); a learned
string containing colons or arbitrary Unicode is embedded as-is and stays
harmless because the key is only ever compared for equality.

## Out of Scope

- Ingest-time validation of the daemon-supplied public id, and any rejection,
  drop or normalization path for it.
- Rewriting the five existing fixtures whose public ids fail the protocol
  parse into parseable forms.
- Bounding how many buckets a daemon can create for its OWN panes by minting a
  fresh public id per update — a separate, pre-existing exposure.
- Any change to the mux wire protocol, to persisted state, or to a
  user-visible identifier, including the sidebar's displayed public id.
- Touching the plain-tab form or the unlearned-pane fallback form.
- Adding a dependency, a doc-drift test, an E2E harness, or a performance
  benchmark.
- Reformatting or renaming unrelated tests in the touched test file.
