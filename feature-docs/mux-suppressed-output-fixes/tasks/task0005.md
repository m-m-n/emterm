## Design

### FR11: pause ordering

In `split_osc9_across_two_suppressed_chunks_never_fires_more_than_once`, arm the P2 pause for chunk_b before sending the release for chunk_a. Everything else stays the same: the boundaries, the assertions, and the order in which chunks are fed.

Arming while the reader is paused is safe. The pause hook takes its armed state before it blocks, so a new arm only affects the next hit.

### FR12: concurrent snapshot paths (TS-14)

**Setup.**
- A session pane driven by the production reader loop over a scripted reader that yields a long, bounded stream of chunks: text lines with occasional CSI device queries.
- One destination channel, standing for one client connection, drained continuously so backpressure never stalls the reader.

**Concurrent loops.** Each loop runs a bounded number of iterations:
- the pane resize, alternating between two sizes;
- `collect_reattach_data` with visible = true, targeting the destination;
- `handle_request_pane_snapshot`, targeting the destination;
- hide via `evaluate_output_target` with visible = false, then `resume_pane_with_permit` with a reserved permit on the destination.

**Pass criteria.**
- Everything finishes within a fixed time budget; failing to join within it counts as a deadlock.
- No panic.
- Every Snapshot-kind chunk received decodes.
- Each of the three snapshot paths completed at least one successful delivery.

**Constraints.**
- The test uses no real PTY and no platform-specific process control, so it runs on Linux and Windows alike.
- The test itself must not hold the output-target lock while waiting on a channel (NFR2).
