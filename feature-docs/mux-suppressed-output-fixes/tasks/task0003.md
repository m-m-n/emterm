# Task Plan: task0003 — Visibility-resume snapshot restores the screen mode

## Goal

After a visibility resume (`resume_pane_with_permit`), the client shows the same screen (main or alternate) as the shadow parser had when the snapshot was read. An alternate-screen pane shows the shadow screen on the alternate screen. A main-screen pane keeps today's exact display, including an apt-style progress bar.

## Design

### Step 1: establish the client behavior (IMPLEMENTATION.md D5) before changing anything

Find this in the GUI's Snapshot-kind apply path (the arm that performs core reset plus segment replay) and in term_core's reset and replay:
- **(i)** Whether applying a Snapshot starts from the main screen with a ground parser, whatever screen the client showed before.
- **(ii)** Whether an alternate-screen switch in the middle of the payload takes effect mid-replay, with the later payload bytes drawn on the alternate screen. term_core stops processing at a 47/1047/1049 switch and the caller performs the switch.

Record both findings in the completion report. Extend the test-side client model so it mirrors exactly the behavior found (IMPLEMENTATION.md "Test-side client model").

### Step 2: choose the layout

The requirement: after the client model applies the resume Snapshot, its screen mode and visible content equal the shadow parser's.

The layout choice must satisfy these rules:
- Everything travels in the single Snapshot-kind chunk the resume path already sends. No additional chunk and no wire change (NFR1).
- The main-pane resume payload stays byte-identical to today's if (i) holds. If (i) does not hold, a leave-alternate-screen normalization at the start of the main payload is allowed, and every existing test it changes is listed (AC-8).
- Expected layout when (ii) holds: the alternate-pane payload is the resume clear prefix, then the stripped main history, then the enter-alternate-screen switch, then the shadow screen dump. The main history then stays on the main screen for when the program leaves the alternate screen.
- Never append a trailing switch after the main replay that would disturb the cursor or scroll region the replay established.
- Reattach and on-demand layouts do not change (NFR1). The wrap-aware resume variant keeps its main-pane dump-block behavior.
- If no single-chunk layout can meet the requirement under the established client behavior, stop and report a plan deviation. Do not change the client.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR8; TS-9): A chunk containing ESC [ ? 1 0 4 9 h is suppressed by a visibility resume that runs while the reader is paused on it. After the client model applies the resume Snapshot, the replacement and the next chunk, it is on the alternate screen, and its visible rows and cursor equal the shadow parser's (test visibility_resume_restores_alt_screen_mode_and_content).
- [ ] AC-2 (FR8; TS-9): A pane is hidden while on the alternate screen, receives ESC [ ? 1 0 4 9 l while hidden, and is then resumed. The client model was on the alternate screen before the apply; after it, the model is on the main screen, with main history and visible rows equal to the reference (test visibility_resume_after_hidden_alt_exit_shows_main_screen).
- [ ] AC-3 (FR8; TS-9): A pane stays on the alternate screen through hide and resume. After the apply, the client model is on the alternate screen with the shadow parser's visible rows. This case is also covered in visibility_resume_restores_alt_screen_mode_and_content.
- [ ] AC-4 (FR8; TS-10): A main-screen pane shows an apt-style progress bar, drawn with a scroll region and cursor save/restore. After hide then show, the cursor position, scroll region and visible rows equal those before the hide. The main-pane resume payload is byte-identical to the pre-change layout, unless finding (i) forced the documented normalization (test visibility_resume_keeps_main_pane_progress_bar_layout).
- [ ] AC-5 (NFR1): The existing reattach and on-demand snapshot layout tests pass unmodified. The mux wire format is untouched. The only layout change is in the visibility-resume payload, and it is documented in the builder's documentation.
- [ ] AC-6 (NFR6, AC-8 of SPEC): `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib` and `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features` both pass. Every existing test whose expectation changed is listed with its reason (at least the resume-layout unit test in snapshot_bytes.rs), and all other existing tests pass unmodified.

## Test Notes

- **Unit level.** The builder's layout test compares the payload for main and alternate panes against the chosen layout.
- **Integration level (pane/tests.rs).** Go through the production `resume_pane_with_permit`, with a paused reader where the case needs a suppressed chunk. Mirror the existing paused-reader resume test. Compare the client model against the shadow parser's screen, or against a reference fed the raw stream once.
- **Reader inputs.** Use only inputs covered by the IMPLEMENTATION.md "Suppressed-chunk delivery contract", so these tests do not depend on the parallel change to the replacement builder.
- **Oracle.** Screen mode is compared through the client model's own alternate-screen flag and the shadow parser's.
