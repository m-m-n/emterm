# Task Plan: task0001 — Derive ProgramState::rank from AgentState::compose_rank and pin their agreement

## Goal

The in-pane state order blocked > working > error > done > idle is written as
rank values only inside `AgentState::compose_rank`; `ProgramState::rank`
obtains its value from it through an exhaustive ProgramState -> AgentState
correspondence, a unit test pins that the two agree for all five states, and
the doc comments of both functions describe this relationship accurately.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `src-tauri/src/program_status.rs` — the ProgramState rank function derives its value through a new exhaustive correspondence to AgentState; its doc comment points to the single definition (FR1, FR2, FR5).
- `src-tauri/src/agent_status.rs` — doc comment of the AgentState compose-rank function only; no behavior change (FR4).
- `src-tauri/src/program_status/tests.rs` — new agreement and correspondence tests appended; existing tests untouched (FR3, NFR3).

## Design

### Dependency direction

`program_status` gains a dependency on `agent_status` (it refers to
`AgentState` and its `compose_rank`). `agent_status` gains no dependency on
`program_status`. Both modules are always built (declared outside the `gui`
feature gate in `src-tauri/src/lib.rs`), and neither gains a dependency on a
`gui`-gated module (NFR2).

### ProgramState -> AgentState correspondence (FR2)

A new conversion owned by `ProgramState` in `src-tauri/src/program_status.rs`.

| Aspect | Contract |
|--------|----------|
| Input | any `ProgramState` value |
| Output | exactly one `AgentState` value — never optional, never a fallback |
| Mapping | `Idle` -> `Idle`, `Working` -> `Working`, `Done` -> `Done`, `Blocked` -> `Blocked`, `Error` -> `Error` (same-named variant) |
| Postcondition | the output's display word equals the input's protocol word |
| Form | an exhaustive match over the five `ProgramState` variants with no wildcard arm, so a future `ProgramState` variant fails to compile until it is mapped |
| Not allowed | going through protocol words (the existing word-based conversion on the `AgentState` side returns an optional value, which would need a fallback and would defeat exhaustiveness) |
| Visibility | module-level access is sufficient: the only required consumers are the rank function and the module's own test module. Exposing it outside the crate is not required by this task |

### ProgramState rank (FR1)

- Signature stays as it is: public, takes the state by value, returns `u8`.
- Flow: (1) map the receiver to its `AgentState` through the correspondence;
  (2) return that `AgentState`'s compose rank.
- The function contains no rank numeric literal of its own. The numeric
  values it returns are therefore identical to today's (0..4), so
  `Table::summary`'s rank comparison and its recency tie-break are unaffected
  (NFR1). `Table::summary` itself is not edited.

### Doc comment of AgentState compose_rank (FR4)

The doc comment states all of the following:

1. It is the single definition of the in-pane order
   blocked > working > error > done > idle (higher rank is stronger), and the
   order is read-flag free.
2. `ProgramState::rank` takes its value from it, and `Table::summary` uses
   `ProgramState::rank` to pick the deciding record.
3. `agent_status_model`'s `priority_rank` is a separately defined,
   unseen-aware cross-pane order and does not derive its values from
   `compose_rank`. This replaces the current statement that the GUI's
   cross-pane aggregation "adds the unseen distinction on top of it", which
   does not match the code.

Mentioning that `agent_status::compose` (and the GUI's composite-name
decision) use this rank directly is allowed; no other doc in the crate is
edited.

### Doc comment of ProgramState rank (FR5)

States that the value comes from `AgentState::compose_rank` through the
correspondence. If the order is restated for readability it is attributed to
`compose_rank`; the comment does not present the order as an independent
definition.

## Test Notes

- AC-1, AC-2, AC-3 are unit tests appended to `program_status`'s test module
  (the child test module can reach a module-private correspondence). They may
  be one or several test functions; each AC must be traceable to a named
  test. New test names must not collide with or rename any existing test.
- Red phase: the values already agree today, so the red state for AC-1..AC-3
  is the correspondence not existing yet (the tests do not compile until it
  is added). Record that as the red reason.
- The "no wildcard arm", "no rank literal in program_status.rs" and
  dependency-direction parts of AC-1 / AC-2 / AC-7 are structural properties:
  checked by inspection of the diff (and, for exhaustiveness, by the compiler
  itself), not by a runtime test.
- AC-4 / AC-5 are documentation criteria, checked by reading the two doc
  comments against the listed statements.
- AC-6 is the regression guard for NFR1: the existing `ac5_*` summary tests
  pin the recency tie-break and "higher rank beats recency", and the
  `compose_*` tests pin the OSC 7501-side tie-break. The diff of
  `src-tauri/src/program_status/tests.rs` consists of additions only, and the
  test module inside `src-tauri/src/agent_status.rs` has no changed lines.
- Edge case: `Error` is not part of the OSC 777 grammar but has a rank (2).
  Iterate over `ProgramState::ALL` (five members) on the ProgramState side;
  `AgentState::ALL` has four members and excludes `Error`, so it is not the
  iteration source for these tests.
