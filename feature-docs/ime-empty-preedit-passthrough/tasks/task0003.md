# Task Plan: task0003 — Host-testable gate predicate + focus-loss reset

## Goal

The key-suppression decision becomes a platform-parameterized pure predicate
that unit tests can drive for either platform on any host, and losing window
focus clears the bridge's gate states so a Windows composition cannot latch the
gate open and swallow every subsequent key.

## Requirements

FR10, FR11, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/ime/winit_bridge.rs` — extract the gate predicate, route
  `dispatch_key_event` through it, clear both states on focus loss, and convert
  the target-gated Windows tests into host-running ones.

## Background: the two findings this closes

Both were reported in review round 1 and left unresolved because the auto-fix
candidate gate admits only critical/high severities. They are recorded in
`feature-docs/ime-empty-preedit-passthrough/reviews/round1.yaml`.

### `5b461e782d6f18bc` — the Windows branch has no executable test

The gate selection is fixed at compile time, so on a Linux host the Windows
branch is never evaluated at run time. The six Windows acceptance tests are
gated to that target, and the project's only Windows workflow is a build/check,
which does not execute test code. The dangerous half of the gate — the one that
suppresses keys — therefore has no executed coverage anywhere.

### `9f9664d463b1f618` — focus loss does not clear the gate

The Windows gate is now the lifecycle state, and its only clearing event is the
disable event. winit-win32's disable request returns without emitting one,
while winit-wayland synthesizes one for the same request. A composition
interrupted by focus loss on Windows can therefore leave the gate latched, and
because the commit event deliberately no longer clears the lifecycle state
there is no second escape route.

## Design

### Predicate extraction (FR11)

Introduce a pure predicate over three booleans — whether a preedit is currently
present, whether the IME lifecycle is open, and which platform's rule to apply
— returning whether the key is suppressed. Its contract:

- Precondition: none; total over all eight input combinations.
- Postcondition: when the platform selector is true the result equals the
  lifecycle state alone; when false it equals the preedit-present state alone.
  The unselected state never influences the result.

`dispatch_key_event` becomes a call to this predicate with the bridge's two
states and the compile-time target as the selector. It must remain a
constant-time boolean computation with no allocation and no locking (NFR1).

Give the predicate a name that says what it decides, not how it is wired, and
document that the selector exists so tests can drive both platform rules from
one host.

### Focus-loss reset (FR10)

On focus loss, clear both states before delegating to the window's IME-allowed
toggle. On focus gain, change neither state. Record in a comment why this is
not redundant with the disable event: the asymmetry between winit's Windows and
Wayland disable paths, cited to the winit sub-crates as the module docs already
do for the platform split.

Do not queue any additional neutral event from this path. The existing focus
handling in the app layer is out of scope, and on Wayland/X11 the synthesized
disable event still produces the focus-out event as before.

### Test conversion (NFR3)

The six tests currently gated to the Windows target assert the Windows rule.
Rewrite them to assert through the predicate with the platform selector set to
true, so they run on the development host. Keep their scenarios intact — each
one's event sequence and expectation must survive the conversion unchanged;
only the mechanism by which the expectation is read changes.

Where a scenario needs the bridge's states to be driven by real events (rather
than passed as literals), drive them through the bridge's event entry point as
today and then read the answer through the predicate.

Tests that assert the non-Windows rule may keep their current form or move to
the same mechanism; do not weaken any of them.

## Test Notes

it pins AC-1 before any call site moves.

For AC-4, note that the focus-loss entry point is on the backend trait, so the
test drives it the same way the existing focus test does. Assert through the
predicate rather than through the dispatch entry point, since dispatch alone can
only ever show the host platform's rule.

attributable.
