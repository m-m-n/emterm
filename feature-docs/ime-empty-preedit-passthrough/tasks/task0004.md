# Task Plan: task0004 — Restore dispatch-level Windows coverage

## Goal

The Windows scenarios are asserted both through the parameterized predicate
(which runs on any host) and through the real dispatch entry point under the
Windows target, so that a miswired platform selector in `dispatch_key_event`
cannot silently revert Windows to the preedit-derived gate this feature
replaced.

## Requirements

FR7, FR11, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/ime/winit_bridge.rs` — add Windows-target tests that assert
  through the dispatch entry point, alongside the existing predicate-level ones.

## Background: the finding this closes

Reported by the spec review perspective (Codex) in round 2.

The previous task converted the Windows scenarios from `#[cfg(windows)]` tests
that called the dispatch entry point into unconditional tests that call the
predicate directly. That made the Windows RULE executable on a Linux host, which
was the goal, but it removed the last test that exercises the dispatch entry
point under the Windows rule.

The consequence is a silent-failure path. If the platform selector that
`dispatch_key_event` passes to the predicate were replaced by a hardcoded
"not Windows" value, every test would still pass — the predicate tests pass
their own literal selector, and the non-Windows dispatch tests want exactly that
value anyway. Windows would quietly return to gating on preedit emptiness, which
is the original bug.

The predicate-level tests are correct and stay. What is missing is a test whose
subject is the WIRING rather than the rule.

## Design

Add Windows-target tests that replay the same two scenarios the predicate-level
Windows tests cover, but read their answer from the dispatch entry point instead
of the predicate:

1. Lifecycle opened, then an empty preedit — the dispatch answer is "suppressed";
   then the lifecycle closes — the dispatch answer is "not suppressed".
2. Lifecycle opened, a non-empty preedit, an empty preedit, then a commit — the
   dispatch answer is still "suppressed"; then the lifecycle closes — "not
   suppressed".

These are gated to the Windows target because their expectation only holds
there. They will not execute on the development host; the available local
evidence is that the Windows target compiles with test code included. Their
value is (a) catching a miswired selector on a Windows host and (b) keeping the
wiring's intent written down where the target-specific expectation lives.

Name them so their subject is evident: they test the dispatch path, not the
rule. Cross-reference the predicate-level counterparts in a comment so a future
reader does not mistake either pair for redundant duplication of the other, and
state explicitly which one guards the rule and which one guards the wiring.

Leave the predicate-level Windows tests, the non-Windows tests, and every other
existing test exactly as they are.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A Windows-target test asserts, through the dispatch entry point,
      that an empty preedit inside an open lifecycle is suppressed and that
      closing the lifecycle releases it.
- [ ] AC-2: A Windows-target test asserts, through the dispatch entry point,
      that a commit inside an open lifecycle does not release suppression and
      that closing the lifecycle does.
- [ ] AC-3: The predicate-level Windows tests covering the same two scenarios
      remain present and unmodified.
- [ ] AC-4: Each new test carries a comment naming what it guards (the wiring of
      the compile-time selector) and pointing at its predicate-level counterpart.
- [ ] AC-5: No existing test is deleted or weakened, and the count of tests that
      execute on the development host does not decrease.
- [ ] AC-6: The crate compiles for the Windows target with test code included,
      and the host test run for the IME bridge module stays fully green.
