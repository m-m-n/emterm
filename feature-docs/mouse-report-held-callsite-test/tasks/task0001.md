## Design

Cross-task decisions (production freeze, the narrow NFR5 exception,
token-level-not-substring, naming and assertion-message conventions) are in
`IMPLEMENTATION.md`; they are referenced here, not restated.

### Element responsibilities and contracts

All four elements live inside the test module and are exercised both against the
embedded production source and against in-memory inputs. Being reusable against
in-memory inputs is a hard requirement, not a convenience: it is what lets TS-4
and TS-5 demonstrate the red conditions without ever mutating the real file.

**E1 — Lexical scanner**

- Input: a source string. Output: an ordered sequence of tokens, each addressable
  by its own text.
- Postconditions:
  - A line comment contributes nothing from the comment marker to the end of the
    line; a block comment contributes nothing, nests, and closes at its matching
    terminator.
  - A string literal, a raw string literal (with any number of hashes, closing
    only on the matching hash count), a byte string, a C string, and a character
    literal each become exactly **one** opaque token; the scanner never looks
    inside them for anything.
  - A lifetime marker is not mistaken for the opening quote of a character
    literal.
  - An escaped quote inside a literal does not terminate that literal.
  - Identifiers are whole tokens: one identifier is never matched as a prefix of
    a longer identifier.
  - The punctuation the later elements need — path separator, field access dot,
    parentheses, comma, braces — is individually addressable.
  - Whitespace and comments are equivalent: replacing any run of whitespace with
    a comment, or vice versa, yields the same token sequence.

**E2 — Body extractor**

- Input: a token sequence and the name of a top-level function. Output: the
  token subsequence forming that function's body, plus the set of the function's
  own parameter identifiers.
- Preconditions: the name refers to a function declared at the top level of the
  input (not nested in another item).
- Postconditions:
  - The body begins immediately after the brace that follows the parameter list
    and ends at that brace's match, located by brace depth; braces nested inside
    the body are included, and the body of any other function is excluded.
  - A name that cannot be located yields an explicit "not found" outcome that is
    distinguishable from an empty body, so a rename produces a clear red rather
    than a vacuous pass.
  - The result depends on neither line numbers, nor comment text, nor the
    position of the following item.

**E3 — Argument splitter**

- Input: a body token sequence and a callee path to locate. Output: the ordered
  list of argument token slices for that call.
- Postconditions:
  - Splits occur only at commas at nesting depth zero relative to the call's own
    parentheses; a comma inside a nested call, index, closure or brace group does
    not split.
  - A trailing comma before the closing parenthesis does not produce an extra,
    empty argument.
  - Zero occurrences, exactly one occurrence, and more than one occurrence of the
    callee are distinguishable outcomes.

**E4 — Judgment function**

- Input: a body token sequence, the enclosing function's parameter-identifier
  set, the callee path to check, the expected argument count, and the expected
  position of the held argument. Output: pass, or a failure carrying the reason.
- Rules, all of which must hold for a pass:
  1. The callee path occurs **exactly once** in the body (so a second, defaulted
     call added alongside the good one is also a failure).
  2. The call's argument count equals the expected count.
  3. The argument at the expected position is exactly a three-token sequence:
     an identifier, the field-access dot, and the held field name — with the
     leading identifier required to be a member of the enclosing function's own
     parameter-identifier set (never a hardcoded literal, NFR8), and with no
     extra tokens before or after within that argument.
  3b. That leading identifier must still denote the parameter at the call site:
     the body tokens from the start of the body up to the call must contain no
     re-binding of that identifier. The check is deliberately **conservative and
     syntactic** — it rejects on any `let` binding, closure parameter, or
     `match` / `if let` / `while let` pattern that introduces the same
     identifier, without attempting full Rust name resolution. A conservative
     rejection is a red, never a silent pass: shadowing the parameter and then
     passing the shadowed value is exactly the false-green this rule closes.
  4. The held-unaware apply path does not occur anywhere in the body. Because
     rule 4 compares whole identifier tokens, the held-aware name is a different
     identifier and never triggers it.

### Processing flow

1. Embed the production source at compile time from the same directory.
2. Run E1 over it to obtain tokens.
3. Run E2 twice — once for the button-path function, once for the wheel-path
   function — obtaining two bodies and two parameter-identifier sets.
4. Run E3/E4 on each body against its own callee, expected argument count and
   expected held-argument position.
5. Assert, with messages following the convention in `IMPLEMENTATION.md`.

### Scan scope boundary

The scan reads only the two named bodies. The third call to the held-aware entry
point — the one in the motion path — must be absent from both extracted bodies;
that exclusion is the entire difference from the existing whole-file needle and
is asserted directly (TS-6).

**TDD ordering — read this before starting.** The four file-backed tests
(TS-1, TS-2, TS-3, TS-6) are green from the first moment they compile, because
the production call sites are already correct (SPEC A1). The red-first
discipline is therefore carried by the in-memory tests: write TS-4 and TS-5
first, watch them fail against an absent or naive scanner, and build the scan
elements until they pass. TS-5 is what proves the red condition of TS-1, TS-2
and TS-3 without ever mutating the real file — a file-backed test that has never
been observed red is worth nothing, and TS-5 is how this task discharges that
obligation.

TS-5 must build its mutated inputs by rewriting the **real extracted bodies**
in memory (AC-6), not by hand-writing a body that merely resembles them.
Hand-written inputs can prove the judgment function correct while the body
extractor's wiring to the real file is wrong, and in that state TS-1/TS-2/TS-3
would pass vacuously and never catch the regression this feature exists to
catch. Asserting "unmutated passes / exactly one site changed / mutated fails"
for each mutation is what closes that gap.

Edge cases to cover in TS-4 (each one is a distinct input, not a single blended
input): nested block comments; a raw string containing text that looks like a
correct call; raw strings with differing hash counts; byte and C string
literals; a lifetime marker adjacent to a character literal; a trailing comma in
the argument list; the argument list re-wrapped across different line
boundaries; a comment inserted between the callee and its opening parenthesis;
a body in which the parameter identifier is re-bound by a `let`, a closure
parameter, or a `match` / `if let` pattern before the call (E4 rule 3b must
reject it).

Determinism: every test owns its input — either the compile-time embedded source
or a local string — and holds no shared or global fixture, so the suite needs no
single-thread flag (NFR4) and no `#[ignore]` gate (NFR6).
