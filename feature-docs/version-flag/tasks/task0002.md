# Task Plan: task0002 — release.yml sync-version job

## Goal

On tag push, the release workflow commits the tag's version into
`src-tauri/Cargo.toml` (and its lockfile entry) on the default branch before
the GitHub release is created.

## Requirements

FR3, NFR2

## Scope

### Files to Create

- (none)

### Files to Modify

- `.github/workflows/release.yml` — add the `sync-version` job; make
  `create-release` depend on it

## Design

Per IMPLEMENTATION.md D2. The new job, running on the same triggers the
workflow already has (`push: tags: v*` and `workflow_dispatch`):

1. Resolve the release version exactly like the existing `get-version`
   step: the `workflow_dispatch` `tag` input takes precedence, otherwise the
   pushed tag ref; strip the leading `v` for the numeric version.
2. Check out the default branch `main` (not the tag ref).
3. Rewrite the `[package]` version in `src-tauri/Cargo.toml` to the numeric
   version, using the same substitution approach the build jobs already use.
4. Bring `src-tauri/Cargo.lock`'s entry for this package to the same
   version so the committed lockfile stays consistent.
5. If the working tree has no diff after the rewrite, finish successfully
   without committing.
6. Otherwise commit with a bot identity and push to `main` using the
   workflow's `GITHUB_TOKEN` (workflow already declares
   `permissions: contents: write`).

Ordering: `create-release` gains `needs: sync-version`, so a failed push
blocks release creation. All existing jobs (including their build-time
version stamping) stay unchanged. The tag itself is never moved.

Tainted-input rule: tag/input values flow into scripts only via `env:`
indirection, matching the file's existing steps.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `release.yml` parses as valid workflow YAML.
- [ ] AC-2: A `sync-version` job exists; `create-release.needs` includes it;
  no other job's `needs` chain was weakened.
- [ ] AC-3: The job's version resolution matches `get-version` semantics
  (input tag precedence, `v` prefix stripped).
- [ ] AC-4: The job commits and pushes only when the rewrite produced a
  diff; an already-matching version yields a successful no-op.
- [ ] AC-5: Both `src-tauri/Cargo.toml` and `src-tauri/Cargo.lock` are
  covered by the rewrite step.
- [ ] AC-6: Tag/input values reach run scripts only through `env:`
  indirection.

## Test Notes

- CI jobs cannot execute locally; ACs are verified statically: YAML
  validation (AC-1) via a parser available in the repo toolchain, structural
  assertions (AC-2..AC-6) by inspecting the workflow document. A lightweight
  script-style test is acceptable but not required — a documented static
  check in the task report satisfies the criteria.
- TDD-awkward: acknowledged; treat the YAML-parse validation as the failing
  test written first (it fails while the job doesn't exist by asserting the
  expected structure).

## Out of Scope

- Changing the build jobs' existing version stamping.
- Re-pointing or recreating tags.
- Branch-protection configuration on the repository.
