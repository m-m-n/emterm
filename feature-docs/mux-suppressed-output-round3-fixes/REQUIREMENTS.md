# mux-suppressed-output-round3-fixes - 要件定義書

## 1. 概要

### 1.1 背景
mux-suppressed-output-round2-fixes（PR #111）のレビュー round 1 で、medium 指摘 8 件が `unresolved` のまま残った。

### 1.2 目的
- 重なったスナップショット取得（タブ切替 / 再アタッチ）で抑止されたチャンクの副作用を、そのチャンクが抑止されなかった場合にクライアントが到達したはずのパース状態へ、同じ順序で到達させる。
- 通常の（抑止されない）スクロールバック書き込み経路が OSC ごとに負担している余分なコピーと UTF-8 検証を取り除く。
- 上記 8 件の各指摘について、解決済みか変更不要かを判定し、根拠と対応する回帰テストを記録する。

### 1.3 スコープ
- 対象: FR1〜FR9（mux デーモン内の書き込みフィルター、スクロールバックの strip、境界記録、抑止チャンクの置換出力）。
- 対象外: `mux_ipc` のワイヤー形式、Snapshot / SnapshotRestore フレームの形（NFR1）。
- 対象外: `feature-docs/mux-suppressed-output-round2-fixes/reviews/round1.yaml` の変更（FR9）。

### 2.2 対象ユーザー

- クライアントのパーサーが制御シーケンスを開始しない位置から、照会やビューア起動が捏造されない（NFR4）。
- 通常の書き込み経路で、OSC ごとのコピーと UTF-8 検証が発生しない（FR8 / NFR3）。

### 4.2 機能詳細

#### FR1: 除去された画面切替で閉じられた構成要素をリングに書かない

**説明**:
書き込みフィルターが、カット位置で未完の OSC・DCS・APC 文字列、または保持中の単独 ESC を閉じるとき、その構成要素のバイトは開始 ESC 以降すべてスクロールバックリングに書き込まない。

**ビジネスルール**:
- カット位置は、メイン画面範囲の抽出で除去される画面切替シーケンス（47/1047/1049 h/l）の位置とする。
- 構成要素の開始 ESC より前の確定済みバイトは、従来どおり既存の strip を通して書き込む。
- 終端（ST その他）は付加しない。
- 前回の読み取りから `pending` に持ち越された構成要素にも、現在のセグメント内で開始した構成要素にも適用する。
- 帰結: メイン画面の可視性復元スナップショットを再生しても、クライアントが OSC の内部に留まらない。そのため、後続の読み取りに含まれる BEL がカラー照会を完了させない。
- 根拠: 回答 req.fr1-closed-construct-handling（選択肢 (a)）。

#### FR2: 共有 strip が指示子を消費し、書き込みフィルターが指示子待ち状態を渡す

**説明**:
共有 strip（`strip_rich_content_and_remap` と、その書き込み経路・スナップショット経路の入口）は、`ESC (` / `ESC )` の次のバイトを、それが ESC であっても無条件に指示子（designator）として消費する。これは term_core のエスケープ処理と同じ遷移とする。

**ビジネスルール**:
- strip は初期状態として指示子待ち状態を受け取る。
- 書き込みフィルターは、すべての経路（通常の drain、カット、オーバーフロー時のフラッシュ）で、各 strip 呼び出しの開始時点で有効な状態を渡す。
- 指示子バイトをまたいでも、バイトと位置の対応（再マップされたオフセット）を保つ。
- スナップショット側は初期状態なし（ground）で strip を呼ぶ。
- 帰結: 任意の分割位置、および 1 バイトずつの投入で、書き込みフィルターの出力バイトと `pending` は、同じ入力を 1 回で投入した場合と一致する。`ESC ( ESC [6n` と `ESC ( ESC ]777;emterm;markdown;x BEL` も含む。
- 根拠: 回答 req.fr2-fr3-shared-strip（選択肢 (a)）。

#### FR3: strip 側は指示子の ESC を導入子とみなさない

**説明**:
FR2 と同じ共有 strip の変更で満たす。`ESC (` / `ESC )` の後に指示子として消費された ESC は、strip 側で OSC・APC・DCS・CSI の候補の開始とみなさない。

**ビジネスルール**:
- `ESC ( ESC ]0777;emterm;markdown;begin;id=x BEL X` は、1 回で投入しても分割して投入しても、リング書き込みとスナップショットの strip の両方で表示バイトを保持する。
- 根拠: 回答 req.fr2-fr3-shared-strip（選択肢 (a)）。

#### FR4: 読み取り境界をまたぐフォールバック経路で、書き込みフィルターの保持分を閉じる

**説明**:
リーダーのフォールバック経路（メイン範囲抽出の最終 alt 状態が、シャドウパーサーのチャンク処理後の状態と食い違う場合。`pty_spawn/mod.rs` の 519〜529 行付近）で、`alt_before` または `alt_after` が true のとき、書き込みフィルターはカットと同じ方法で `pending` を閉じ、指示子待ち状態をクリアする（例: 投入範囲が空でカットが 1 つ）。

**ビジネスルール**:
- 閉じた構成要素は FR1 と同じく扱う。
- `!alt_before && !alt_after` のときのフォールバック（チャンク全体の投入）は変更しない。
- 帰結: 切替シーケンスが読み取り境界をまたぎ（例: 読み取りが `ESC` / `[?1049h` / `ESC` / `[?1049l` / `]11;? BEL`）、最後の読み取りが抑止された場合、持ち越し分の完了は報告されず、カラー照会も配送されない。

#### FR5: as-05 フォールバックは、判定できない末尾の `ESC (` をまたいで捏造しない

**説明**:
`derive_prefix_start` の as-05 フォールバック（保持ウィンドウが満杯で、判定可能な ESC を含まない場合）で、ウィンドウが `(` / `)` で終わり、そのバイトがウィンドウの先頭バイトであるか直前が ESC である場合、走査はチャンクの先頭バイトを、指示子として消費された可能性があるものとして扱う。

**ビジネスルール**:
- この場合、チャンクの先頭バイトから始まる構成要素からは、項目も末尾（tail）も抽出しない。
- この扱いは取りこぼしを生むだけで、捏造は生まない。
- 帰結: 先行する読み取りで `ESC (` が 129 回連続した後、抑止されたチャンク `ESC ]11;? BEL` は照会を配送せず、応答も生じない。

#### FR6: 送信時に世代を確認して末尾省略を判定する

**説明**:
宛先ごとの境界記録は世代（または同等の識別子）を持ち、同じ境界での再記録を含め、記録のたびに世代を進める。リーダーの covered 判定は、構成要素と一緒に世代を取得する。

**処理の流れ**:
1. 置換出力を送るとき、リーダーはまずすべての排他の外で送信スロットを確保する。
2. 次に `output_target`、続いて境界の排他を取り直し、宛先の記録を再確認する。
3. 末尾省略の判定には、その時点の記録を使う。その構成要素は、チャンク番号が記録された境界と等しい場合にだけ適用する。
4. リーダーはこの保持を `permit.send` まで続ける。

**ビジネスルール**:
- 走査と通知処理は排他の外に置く。
- 古い構成要素のもとで置換が空になる場合も再確認を行い、先の判定で省略した末尾を現在の記録が必要とするなら送る。
- 最終的な置換が空なら送らない。
- 抑止パイプラインの 2 つの呼び出し箇所（直接の Suppressed アームと、NeedsSlot 再確認アーム）の両方に適用する。
- 根拠: 回答 req.fr6-recheck-at-send（選択肢 (a)）。

#### FR7: 等しい境界では後の記録を採る

**説明**:
宛先の既存境界と等しい境界が記録されたとき、後の記録が構成要素を置き換える（なしへの置き換えも含む）。食い違う構成要素が、なしに潰れることはなくなる。

**ビジネスルール**:
- より大きい境界は、従来どおり両方の値を置き換える。
- より小さい境界は、従来どおりエントリを変更しない。
- いずれの記録も FR6 の世代を進める。
- 帰結: 同じ境界で、オンデマンドスナップショット（構成要素なし）の後に可視性復元スナップショット（`ESC (`）が記録されると `ESC (` が残り、置換出力は `ESC (` を再送しない。逆順ではなしが残り、末尾が再送される。

#### FR8: 通常の書き込み経路で、ヒープ確保なしに OSC を識別する

**説明**:
`crate::mux::osc_identify` に、OSC 本体のバイト列を受け取り、ヒープ確保を行わない識別の入口を追加する。

**ビジネスルール**:
- 番号は変更前と同じ規則で復元する。
    - 最初の `;` より前の数字は 10 進で累積する。
    - 最初の `;` より前の数字以外のバイトはデータとする。
    - 最初の `;` は捨てる。
    - u16 を超える累積値は識別しない。
- 番号が 777 でも 9999 でもなければ、直ちに NotIdentified を返す。
- それ以外は、借用したバイト列で、種別の判定に必要な接頭部だけを比較する。
- 結果は、あらゆる本体について `identify_osc(&recover_osc(body))` と等しい。
- strip の `is_replayable_osc_body` はこの入口を使う。
- `recover_osc` / `identify_osc` は、等価性テストの基準として、また配送側の呼び出し元のために残す。
- 根拠: 回答 req.fr8-regression-test（選択肢 (a)）。

## 5. 非機能要件

### 5.1 パフォーマンス要件

**NFR3: リーダーのホットパスの負荷**
- リーダーの通常経路に新しい走査を追加しない。
- 指示子の追跡は、strip の既存の 1 パスの中で行う。
- FR8 により、書き込み経路から OSC ごとのコピーと UTF-8 検証を取り除く。
- 世代は、記録ごと・covered 確認ごとに O(1) の処理を加える。
- 配送用の識別、項目の抽出、末尾の組み立ては、抑止されたチャンクに対してだけ行う。

### 5.2 セキュリティ要件

**NFR4: セキュリティ（TM-1, TM-3）**
- クライアントのパーサーが制御シーケンスを開始しない位置から、照会やビューア起動を捏造しない。FR1・FR2・FR4・FR5 は、この制約への違反を修正する。
- 置換出力は、覆っているスナップショットを受け取った宛先にだけ送る。
- 末尾省略に使う構成要素は、その宛先の現在の境界記録から得る。別の宛先の状態を読み直して決めない。

**NFR5: セキュリティ（TM-2）**
- strip、書き込みフィルターの境界走査、保持ウィンドウの再開位置の選択、置換の走査、新しい識別は、いずれも有界の 1 パスとし、panic しない。
- 空の置換を空の `PtyOutput` チャンクにしない。
- `pending` の上限 512 KiB と、上限超過時の strip 済みフラッシュは変更しない。

### 5.3 可用性要件
該当なし。

### 5.4 保守性要件

**NFR2: ロックの規律**
- ロック順序は `output_target` -> キャプチャ排他 -> リング / シャドウパーサー、および `output_target` -> 境界排他とする。
- `output_target` または境界排他を保持している間は、ブロックする待機（`reserve_owned`、`blocking_send`）を行わない。
- 既存の NeedsSlot 経路と同じく、保持中のブロックしない `permit.send` は許す。
- 置換の走査、末尾構成要素の判定、通知処理は、キャプチャ排他と境界排他の外で行う。

### 5.5 互換性要件

**NFR1: 互換性**
- `mux_ipc` のワイヤー形式と、Snapshot / SnapshotRestore フレームの形は変更しない。
- 可視性復元・再アタッチ・オンデマンドのスナップショットのバイト組み立て配置は変更しない。置換出力は引き続き通常の `PtyOutput` チャンクとして送る。
- リングとスナップショットの内容について、次の例外を定める。
    - (a) カット、または FR4 のフォールバックでの閉じ処理で閉じられた構成要素は、リングに書き込まなくなる（FR1 / FR4）。
    - (b) `ESC (` / `ESC )` の後に指示子として消費された ESC は strip 対象の開始とならなくなる。そのため、その位置で取り除かれていたバイトが残るようになる（FR2 / FR3）。

**NFR6: ビルドとプラットフォーム**
- `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features` が通る。
- `osc_identify` は `mux::ipc` にも `gui` フィーチャーにも依存しない。
- FR8 のテストで使う確保カウンターは、テストビルド（`cfg(test)`）にだけ存在する。
- Linux と Windows で動作が同じ。
