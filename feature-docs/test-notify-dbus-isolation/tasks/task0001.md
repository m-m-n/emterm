# Task Plan: task0001 — Test-build App uses a no-op notification sink

## Goal

In the lib's test build, every `App` (built through `App::new()` or
`App::with_settings`) holds a notification sink that does nothing, so no
App-constructing test can reach notify-rust. The non-test build keeps
building `NotifyRustSink::new()`. A regression test pins the test-build
behavior.

## Requirements

FR1, FR2, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `src-tauri/src/app/tests/notification_sink.rs` — regression tests for the sink the test-build App holds (TS-1, TS-2)

### Files to Modify
- `src-tauri/src/app/mod.rs` — build-configuration switch of the sink in App::with_settings, the test-build no-op sink, the NotifyRustSink import scoped to the non-test branch, and the notification_sink field documentation
- `src-tauri/src/app/tests.rs` — registers the new test module
- `src-tauri/src/callbacks.rs` — test-build-only sink identification on the NotificationSink trait (with a default), plus the NativeCallbacks::new documentation sentence that says App always builds the production sink
- `src-tauri/src/app/tests/agent_status.rs` — documentation wording only, where it describes the App's default sink as the production NotifyRustSink; no behavior change

## Design

Cross-task contracts used here: `NotificationSink` trait, `NotifyRustSink::new()`
and `NotifyRustSink` type identity (IMPLEMENTATION.md Shared Components);
build-configuration switch and warnings conventions (IMPLEMENTATION.md
Conventions).

### No-op sink (test build only)

- **Responsibility**: a `NotificationSink` implementation whose send accepts
  any title and body and returns immediately with no side effect — no thread,
  no I/O, no log record, no panic.
- **Placement**: exists only in the test build, private to the `app` module
  and its tests.

### Sink selection in `App::with_settings`

1. Test build: build the no-op sink and store it, in the shared handle form
   the field already uses, as `notification_sink`.
2. Non-test build: build `NotifyRustSink::new()` and store it exactly as
   today (FR2, NFR2).
3. Everything downstream is unchanged: the same handle is cloned into tabs
   and used by `App::notify`. `App::new()` delegates to `App::with_settings`,
   so it inherits the switch (FR1).

Tests that replace the sink after construction (`app_with_test_sink`,
`app_with_shell_less_tab` and similar helpers) keep working unchanged.

### Sink identification (test build only)

- **Purpose**: let a test decide, from the shared sink handle `App` holds,
  whether the concrete sink is a `NotifyRustSink` — without constructing a
  `NotifyRustSink`.
- **Contract**:
  - Exists only in the test build; the production `NotificationSink` surface
    is unchanged.
  - Lives on the `NotificationSink` abstraction with a default behavior
    derived from the implementing type, so no existing implementation needs
    editing.
  - The answer for a `NotifyRustSink` comes from `NotifyRustSink`'s own type
    identity; the test compares against that identity obtained without
    instantiating the type.

### Regression tests (new test file)

| Test | Flow | Expected |
|------|------|----------|
| TS-1 | Build `App::new()` in the test build → identify its `notification_sink` | Identified as not `NotifyRustSink` |
| TS-2 | Build `App::new()` → call `App::notify("t", "b")` | Returns without panicking |

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR6, TM-3; TS-1): In the test build, a test identifies the sink held by `App::new()` as not being a `NotifyRustSink`, and the test itself constructs no `NotifyRustSink`. The same test fails when `App::with_settings` builds `NotifyRustSink::new()` in the test build.
- [ ] AC-2 (FR1, TM-3; TS-2): In the test build, `App::notify("t", "b")` on `App::new()` returns without panicking, and the held sink's send performs no delivery (no worker thread, no notify-rust call, no log record).
- [ ] AC-3 (FR2, NFR2; TS-6): In the non-test build, `App::with_settings` builds the sink with `NotifyRustSink::new()` and stores it in `notification_sink` as before (confirmed by code review), and the default-features cargo check passes.
- [ ] AC-4 (FR1, NFR2): The sink identification exists only in the test build; the production `NotificationSink` surface is unchanged, and every existing implementation (`NotifyRustSink` and the test sinks in `callbacks/tests.rs`, `app/tests/agent_status.rs`, `tabs/tests.rs`) compiles without edits.
- [ ] AC-5 (NFR1, NFR3, NFR4; TS-6): The full `--lib` test command passes; the `--no-default-features` cargo check and the Windows-target check including tests pass; neither the test build nor the non-test build shows a new warning originating in `src-tauri/src/app/mod.rs` (in particular no unused import of `NotifyRustSink`).

## Test Notes

- AC-1 and AC-2 are unit tests in the new test file. Write AC-1 first: it is
  red against the current code, where the test-build `App` holds a
  `NotifyRustSink`.
- The "no delivery" half of AC-2 is structural (the no-op sink has no side
  effect to observe) and is confirmed by code review; the test asserts the
  return.
- AC-3 and AC-4 are confirmed by code review plus the build commands in
  VERIFICATION.md; they need no new test.
- Do not construct a `NotifyRustSink` in these tests: construction alone
  starts its worker thread.
- Existing app tests that build `App::new()` without replacing the sink now
  run on the no-op sink. None asserts on the production sink; the full
  `--lib` run confirms this.

## Out of Scope

- `NotifyRustSink` internals, worker injection points and the
  `worker_thread` tests.
- Integration tests under `src-tauri/tests/` (SPEC technical constraints).
- Any crate-wide detection mechanism (FR6).
- Replacing the existing test sinks (`TestSink`, `TestNotifySink`, the tabs
  test sink) with the new no-op sink.
