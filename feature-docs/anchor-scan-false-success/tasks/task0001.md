# Task Plan: task0001 — Close anchor_scan false-success paths (literal args, char/raw strings, fn depth gate)

## Goal

The test-only `anchor_scan::locate_call` in `src-tauri/src/window_host/tests.rs`
either returns the true call range or fails with an explicit `Err` when it meets
trailing literal arguments, char literals / raw strings, or a same-named function
nested inside an `impl` or block. It never returns a wrong range as `Ok`. Each
path is pinned by a unit test that fails against the pre-change implementation.

## Design

### Handling chosen per path (resolves SPEC A2)

| Path | Handling | Requirement |
|---|---|---|
| Numeric / string literal arguments, including the trailing position | Processed correctly: every literal becomes exactly one opaque token, so it counts as argument content | FR1 |
| Char literals, byte char literals, raw strings (`r` / `br` / `cr`, any `#` count), byte / C strings | Processed correctly as opaque spans; any form the scanner cannot close or classify → `Err` | FR2 |
| Same-named `fn` inside an `impl` or a nested block | Processed correctly: only brace-depth-0 definitions are candidates; more than one depth-0 candidate → `Err` | FR3 |
| Commas owned by generic arguments or closure parameters at the argument list's own top level (a residual FR4 path that paren / bracket / brace depth cannot see) | `Err` (fail-closed) | FR4 |

### Scanner (`scan`) — contract

- **Input**: the full source text.
- **Success**: an ordered token list with byte-offset spans, in these kinds:
  - identifier — unchanged; additionally a raw identifier such as `r#type` is
    one identifier token whose text includes the `r#` prefix;
  - single-character punctuation — unchanged;
  - opaque literal (new) — one token per literal, spanning the literal's full
    byte range;
  - lifetime / label marker (new) — one token per `'name` that is not a char
    literal.
- Opaque literals and lifetime / label markers are never identifiers (they can
  never match `fn_name` or the callee name) and never structural punctuation
  (they never change paren / bracket / brace depth and never act as a comma).
- Whitespace, line comments and nested block comments still contribute no
  tokens (behavior unchanged).
- **Failure**: an explicit failure carrying a human-readable reason — never a
  partial token list — when (a) a string-like literal has no closing
  delimiter, or (b) a `'` can be classified neither as a char literal nor as a
  lifetime / label marker.
- The scanner is private to the module; its signature may change to express
  the failure outcome. `locate_call` absorbs the change.

### Literal recognition rules (behavioral)

1. **Numeric literal**: same extent as today (starts with an ASCII digit,
   continues over alphanumerics, `_` and `.`), now emitting one opaque literal
   token.
2. **Plain string** (`"…"`): a backslash escapes the one character after it;
   the literal ends at the first unescaped `"`. No closing `"` → failure.
3. **Prefixed forms** are recognized only when the whole identifier run is
   exactly the prefix and is immediately followed by the delimiter:
   - `b` or `c` followed by `"` → byte / C string, plain-string escape rules;
   - `r`, `br` or `cr` followed by zero or more `#` and then `"` → raw string:
     no escapes; ends at the first `"` followed by the same number of `#` as
     the opening; no such closing → failure;
   - `b` followed by `'` → byte char literal (char literal rules below);
   - `r` followed by `#` and then an identifier-start character → raw
     identifier, never a raw string.
   - Any other identifier — including one that merely ends in `r`, `b` or `c`,
     such as `for` — stays an ordinary identifier.
4. **`'` — char literal vs lifetime / label**: after the opening `'`, take
   exactly one scalar: a single character, or an escape (a backslash plus one
   character; `\x` plus two characters; `\u{…}` through its closing `}`). If
   the next character is `'`, it is a char literal spanning through that
   closing `'`. Otherwise, if the character right after the opening `'` is an
   identifier-start character, it is a lifetime / label marker spanning that
   identifier run (`'a`, `'static`, `'outer`). Otherwise → failure.
5. Every token boundary is a character boundary: non-ASCII content (for
   example the char literal `'あ'`) never makes a later byte-range slice panic.

### Top-level argument counter — contract

- **Input**: the token range strictly between the call's own `(` and its
  matching `)`.
- **Output**: the number of top-level arguments, or "indeterminate".
- Depth counting is unchanged: `(` / `[` / `{` against `)` / `]` / `}`. A
  comma at depth 0 separates arguments; a non-empty final segment is one
  argument; a trailing comma adds none; an empty list is 0. Because every
  literal now yields a token, a literal-only segment — including the final
  one — is non-empty and counts.
- **Indeterminate**: a `<` or `|` punctuation token at depth 0 of the list.
  Commas there may belong to generic arguments (`::<A, B>`) or closure
  parameters (`|x, y|`), which this depth model does not nest. `locate_call`
  turns "indeterminate" into `Err`.

### `locate_call` step 1 (function search) — contract

- Tracks brace depth over the whole token list, counting only `{` and `}`
  tokens (SPEC A3; the same definition `call_site_scan::extract_function`
  uses).
- A candidate is an `fn` identifier token at brace depth 0 whose very next
  token is the identifier `fn_name`. A comment between the two does not stop
  it from being a candidate.
- Exactly one candidate is required: zero → `Err` (not found); two or more →
  `Err` (ambiguous — never a first-match guess).
- The single candidate must still pass the existing checks — a
  whitespace-only gap between `fn` and the name (predecessor EC-1) and
  locatable body braces — otherwise `Err`. There is no fallback to any other
  occurrence.
- Consequence: whenever step 1 succeeds, it has resolved the same definition
  that `call_site_scan::extract_function` resolves for the same source.

### `locate_call` overall

- Signature and `AnchoredCall` fields are unchanged (FR4).
- New `Err` sources: scanner failure, counter "indeterminate", zero or
  multiple depth-0 candidates. Each message follows the existing style: it
  names `fn_name` and / or the callee, states the reason, and states that this
  is an explicit failure rather than a silently wrong range.
- Steps 2–4 (single callee hit, paren-depth walk, argument-count check, range
  decomposition) keep their current behavior.

### Frozen / untouched

- `call_site_scan` — its tokenizer, private helpers and visibility — is
  read-only reference material. `anchor_scan` does not call its private
  helpers and keeps its own logic (NFR2, SPEC A1).
- `src-tauri/src/window_host/pointer_routing.rs` and `src-tauri/Cargo.toml`
  do not change (NFR1, NFR3).
- NFR4: only the literal / lifetime / raw-identifier forms above, the depth-0
  gate and the `<` / `|` guard are added. No further syntax support.

### Doc comments

The doc comments on the module, `scan`, the counter and `locate_call` currently
state that string contents contribute zero tokens and that step 1 walks every
token. Update them to describe the behavior above, citing
`anchor-scan-false-success`.
