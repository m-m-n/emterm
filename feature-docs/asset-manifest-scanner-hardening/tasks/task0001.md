# Task Plan: task0001 — Directory-only build-output exclusion and parenthesis-bounded macro-argument extraction

## Goal

The asset-manifest regression guard stops dropping ordinary source files whose
name begins with the build-output prefix, and stops searching for a macro
argument outside the macro call's own parentheses — with the guard's verdict on
the current tree unchanged.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/tests/asset_manifest.rs` — narrow the path-exclusion predicate to
  directory components, bound the byte-include argument extraction to the call's
  parenthesis region, and add the recurrence-detecting tests.

## Design

All three contracts this task implements against are pinned in IMPLEMENTATION.md
(Shared Components) and are not restated here. This section covers only what is
specific to carrying them out.

### Change 1 — Path-exclusion predicate (FR1, NFR3)

The predicate keeps two independent reasons to exclude a path, evaluated in this
order:

1. The path is the scanner's own source (equality against the self-path
   constant). Untouched by this task — it is what keeps the fixture text added
   below from being read as a real embedding.
2. The path's *directory portion* contains a build-output name. The build-output
   prefix rule is applied to every ordinary-name component except the final one.

The final component is therefore never examined by the prefix rule. A file whose
own name begins with the prefix stays in scope; a build-output directory
encountered as an entry of the walk still fails to be excluded here and is
stopped instead by the walk's directory-name check (IMPLEMENTATION.md D1). Do
not add a compensating check to the path predicate — the split is deliberate,
and duplicating it there would re-introduce the gap.

Paths with a single component are the boundary case this narrowing creates:
their only component is the final one, so the prefix rule never applies to them.

### Change 2 — Byte-include argument extraction (FR2, FR4, FR5)

Per call site, the flow is:

1. Find the next occurrence of the fixed opening substring (macro name,
   exclamation mark, opening parenthesis). No match ends the scan.
2. Determine the argument region by walking forward from just after that opening
   parenthesis, tracking nesting depth over the two parenthesis characters, and
   stopping at the parenthesis that returns the depth to zero. No such
   parenthesis in the remaining text ends the scan, returning what was collected.
3. Inside that region only, look for a string literal: an opening quote and a
   closing quote both within the region. Absent either, this call contributes
   nothing.
4. When a literal is found, take the final path segment of its contents and keep
   it when it ends in one of the configured font extensions (existing behaviour,
   including the case-insensitive extension comparison).
5. Resume the scan immediately after the region's closing parenthesis — never
   from a quote position, and never before that point.

Step 5 is the behavioural heart of FR2: the previous resumption point was just
past a quote that could lie outside the call. Step 3 is FR5: a region with no
literal must not end the scan.

The pass must stay forward-only, with no re-examination of text already passed
(NFR4), and must remain free of filesystem access (NFR1).

### Change 3 — Recurrence-detecting tests (FR6, NFR6)

Add tests covering TS1–TS5. Follow the file's existing naming convention
`<subject>_<scenario>_<expected>` and its existing construction style: synthetic
values for the pure predicates, and a temporary directory tree built with the
existing dev-dependency for the walk-level scenario. Add no dependency (NFR2).
Leave every existing test unmodified; they are the invariants this change is
measured against.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, TS1): The path-exclusion predicate reports *not excluded* for a
      path whose final component begins with the build-output prefix, both when
      the name merely starts with it and when the name equals it exactly, under a
      directory that is itself in scope.
- [ ] AC-2 (FR1, NFR3, TS2): The path-exclusion predicate still reports
      *excluded* for every path whose directory portion contains a build-output
      name — including the plain prefix, the two suffixed variants used by this
      project, and an arbitrary further suffix — and still reports *not excluded*
      for an ordinary source path. The scanner's own source path stays excluded
      and a sibling test file stays in scope.
- [ ] AC-3 (FR1, TS3): Over a temporary tree, the scan finds a font embedding
      written in a source file whose name begins with the build-output prefix,
      and finds nothing when the same embedding is placed inside a build-output
      directory.
- [ ] AC-4 (FR2, FR5, TS4): For text shaped like the generated-code site in the
      build script — a byte-include call whose argument is not a string literal,
      followed later in the text by an unrelated string literal — the extractor
      returns the empty set and does not reach the unrelated literal.
- [ ] AC-5 (FR2, FR5, TS5): For text where a call with a non-literal argument is
      immediately followed by a call embedding a real font path, the extractor
      returns exactly the one real font file name — the scan is neither cut short
      nor misaligned.
- [ ] AC-6 (FR3, FR6, TS6, TS7): On the unmodified repository the scan still
      yields exactly the seven documented font names, and the whole
      `asset_manifest` test target passes with every pre-existing test unchanged.
- [ ] AC-7 (NFR1, NFR2, NFR5): The diff touches only
      `src-tauri/tests/asset_manifest.rs`; the crate manifest's dependency and
      dev-dependency sets are unchanged; the changed functions remain free of
      filesystem access and of process-state dependence.

## Test Notes

- **Unit (pure, synthetic input)**: AC-1, AC-2, AC-4, AC-5. These need no
  filesystem at all — synthetic path values and synthetic source text.
- **Integration (temporary tree)**: AC-3, and the repository-facing half of AC-6.
  Build the tree under a temporary directory; never write into the repository.
- **Write the tests first.** AC-1, AC-3, AC-4 and AC-5 must each fail against the
  current implementation before the change and pass after it — that failure is
  the evidence the test actually detects the gap. AC-2 and AC-6 pass both before
  and after: they are the invariants, and they must stay green at every step.
- **Edge cases worth covering inside the AC tests**: a single-component path (the
  boundary the narrowing creates); a region whose closing parenthesis is absent
  (the scan must end without panicking rather than loop); a non-font extension
  inside a well-formed call (existing behaviour, already pinned).
- **TDD-awkward item**: AC-7 is inspection-based, not assertion-based (a diff and
  a manifest check). It is verified at review/verify time and is recorded in
  VERIFICATION.md rather than as a test.
- Run the focused target while iterating:
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --test asset_manifest`.

## Out of Scope

- Any change to production code, in particular the build script and the font
  resolver. The build-script call site is a reference instance of the shape being
  bounded, not a defect to repair (NFR5).
- Bracket and brace macro delimiter forms, and descending into a nested macro to
  assemble an argument (FR4, IMPLEMENTATION.md D3).
- Raw string literals and backslash-escaped quotes inside a macro argument, and
  argument literals containing an unbalanced parenthesis (accepted limitation,
  IMPLEMENTATION.md D2).
- Changing the documented seven-font set, the declaration sources, or the
  one-directional nature of the comparison.
- Restructuring, reformatting or renaming anything in the file beyond what the
  three changes above require.
