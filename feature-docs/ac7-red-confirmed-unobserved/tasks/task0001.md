### Naming, before anything else

Three unrelated things in this feature are numbered "AC-n", and two different
files are named `task0001.tests.yaml`. Throughout this plan:

- **record AC-n** — an entry of the `acceptance_tests` mapping inside
  `test-docs/stale-test-name-refs/task0001.tests.yaml`, the file being edited.
  This file belongs to a DIFFERENT feature's test-docs directory.
- **task AC-n** — a criterion in this plan's own Acceptance Criteria section.
- The record this task's implementer writes for its own work lives under this
  feature's own test-docs directory and is a third, separate file. It is not
  edited by this task; it is produced by the implement phase, and convention C2

### The three regions that change

The edit is located by content, never by line number (decision D4): find the
`acceptance_tests` mapping's AC-7 key, and the record's trailing `notes` key.

1. **The AC-7 entry's confirmation flag.** Its value becomes the boolean false.
   Nothing else about the entry's key set or key order changes.

2. **The AC-7 entry's reason text.** Rewritten so that it states, in the
   record's existing voice and inside its existing folded block scalar:

   - that record AC-7 is an invariant guard on writing discipline;
   - that it has no observable pre-state, because the task the record documents
     is the very thing that creates the record — so no red state could exist
     before it;
   - that it therefore receives the same treatment as record AC-6, which
     already records a criterion of this class with the confirmation flag
     false;
   - and it retains the linkage that explains why the record's own AC-2
     repository-wide count stands at 6 rather than 7. Removing that linkage
     would leave AC-2's count unexplained — a second record/reality gap of the
     same class this task exists to close.

   The rewritten text asserts no observed red and implies none. The factual
   after-state measurement currently cited there (that searching this file for
   the contiguous old identifier after writing it returned zero matches) MAY be
   kept, as verification evidence, provided it is not presented as a confirmed
   red observation (assumption A-1 in SPEC.md). Dropping it is equally
   acceptable.

3. **The trailing notes block.** Gains exactly one line, inside the existing
   folded block scalar and at the block's existing indentation, stating that
   record AC-7 is an unconfirmed red. This is one added line within the existing
   scalar — not a new top-level key and not a list of note entries (assumption
   A-2 in SPEC.md).

### What the rewrite must not disturb

The record's header comment (which declares the split `prefix + suffix` form for
the old identifier), the keys `task_id`, `baseline_failures` and

### The trap in this task

The text being rewritten is precisely the text that documents the
zero-contiguous-occurrence prohibition. Writing about the constraint is the most
likely way to violate it. Convention C1 applies literally: refer to the old
identifier descriptively, or in the split form the header comment declares, and
never assemble it into a written string. The count check below is what proves it.

## Test Notes

**Red observability, decided here rather than while writing the record**
(IMPLEMENTATION.md decision D2; this is the discipline the whole feature is
about). Before writing the per-task test record, classify each criterion above:

| Criterion | Fails before the change? | Record it as |
|---|---|---|
| AC-1 | Yes — the flag currently reads `true` | red confirmed, with the observed failure noted |
| AC-2 | Yes — the current text carries no invariant-guard rationale | red confirmed, with the observed failure noted |
| AC-3 | Yes — the `notes` block has no such line yet | red confirmed, with the observed failure noted |
| AC-4 | No — the file already parses and already has this shape | NOT red-confirmed: invariant guard, no observable pre-state |
| AC-5 | No — the count is already 0 in the base revision | NOT red-confirmed: invariant guard, no observable pre-state |
| AC-6 | No — the diff is empty before the change, so containment holds vacuously | NOT red-confirmed: invariant guard, no observable pre-state |
| AC-7 | No — the commit does not exist before the change | NOT red-confirmed: no observable pre-state |

Writing `true` for any of the bottom four would ship the exact defect this task
removes.

**How each criterion is checked.** AC-1, AC-2 and AC-3 are content assertions
made by reading the edited entry and the `notes` block, with AC-2 compared
against record AC-6's wording as the model. AC-4 is a parse of the file followed
by an inspection of the loaded key set, plus a read of the raw text to confirm
the block-scalar indicators and indentation survived. AC-5 is a fixed-string
count over the whole file, with the search string assembled from the header
comment at check time and never written into any file. AC-6 is a read of the
file's own diff plus a listing of the change set. AC-7 is a read of the commit
message.

**TDD shape.** The three red-confirmed criteria are the cycle: state each as a
concrete check against the file, observe it fail on the base revision, make the
edit, observe it pass. The four invariant guards are run before and after —
they must hold in both states — and are recorded as guards, not as red-to-green
transitions.

**Edge cases worth covering.** A rewrite that satisfies AC-2 but violates AC-5
is the single most likely failure; run the count check immediately after
rewriting the reason text, not only at the end. An added `notes` line at the
wrong indentation can still parse while folding into the neighbouring sentence —
after parsing, read the loaded `notes` value back and confirm the added line
reads as its own sentence rather than being welded to the previous one.

**TDD-awkward item.** AC-7 concerns a commit message, which cannot be asserted
before the commit exists. It is checked after committing, by reading the message
back; if it fails, amend the message rather than adding a second commit.
