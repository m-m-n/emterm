# ac7-red-confirmed-unobserved - 要件定義書

## 1. 概要

### 1.1 背景

PR #46 のレビュー round 1 において、comprehensive 観点が
`test-docs/stale-test-name-refs/task0001.tests.yaml` の AC-7 エントリに
欠陥を検出した（stable_id `41b6ef707d9d6692`、severity medium、
confidence 65）。自動修正ゲートは critical / high のみを対象とするため、
この指摘は `unresolved` のまま残された。

指摘内容は、AC-7 の `red_confirmed` が `true` になっている点である。
AC-7 は「書き方の規律に対する不変条件ガード」であり、この記録自体を
作成するタスクが対象であるため、観測可能な事前状態は存在しない。
すなわち赤（red）状態が観測されたことはない。同じクラスの基準である
AC-6 は `red_confirmed: false` として扱われており、単一の記録の中で
扱いが矛盾している。

### 1.2 目的

`test-docs/stale-test-name-refs/task0001.tests.yaml` の AC-7 エントリを、
観測されていない赤を主張しない記述に改める。あわせて、AC-6 と AC-7 の
扱いを一致させ、記録末尾の `notes` に AC-7 が未確認の赤である旨を残す。

### 1.3 スコープ

**対象**:
- `test-docs/stale-test-name-refs/task0001.tests.yaml` の AC-7 エントリ
  （`red_confirmed` および `red_reason`）
- 同ファイル末尾の `notes` ブロック

**対象外**:
- 同ファイルの AC-1 〜 AC-6、`task_id`、`baseline_failures`、
  `final_failures`、およびヘッダコメント（1〜4 行目）
- Rust / TypeScript のソースコード（一切変更しない）
- 記録の AC-2 / AC-6 が名指しする 3 つの除外対象ファイル
  （`feature-docs/relocate-wrap-cursor-clamp/` 配下の `SPEC.md`、
  `REQUIREMENTS.md`、`reviews/round1.yaml`）

## 2. ビジネス要件

### 2.1 ビジネス目標

| ID | 目標 |
|----|------|
| BO-1 | `taskNNNN.tests.yaml` の記録を真実に保ち、後続タスクがこの記録を読んで失敗要因を帰属させるときに、観測されていない赤状態を渡さないようにする |
| BO-2 | 単一記録内の矛盾（AC-6 は不変条件ガードを `red_confirmed: false` として扱う一方、AC-7 は同種の基準を `red_confirmed: true` として扱っている）を解消する |
| BO-3 | PR #46 自身が修正対象としているのと同じクラスの欠陥（記述が観測された現実から乖離し、静かに緑として読まれてしまう記録）を、新しい機械可読な記録として出荷しないようにする |

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| 後続タスクの実行者（人間 / エージェント） | この記録を読んで、テスト失敗の帰属や TDD サイクルの成立を判断する |
| レビュー担当（人間 / レビューエージェント） | 記録の内容と観測された事実の一致を検証する |

### 2.3 期待される効果

- 記録が主張する赤状態と、実際に観測された赤状態が一致する
- AC-6 と AC-7 で不変条件ガードの扱いが揃い、記録内の矛盾がなくなる
- 記録の欠陥が新規に混入することを防ぐ

### 3.2 ユースケース詳細

#### UC01: 記録から失敗要因を帰属させる

**アクター**: 後続タスクの実行者（人間 / エージェント）

**事前条件**:
- `test-docs/stale-test-name-refs/task0001.tests.yaml` が存在する

**基本フロー**:
1. 実行者が対象の `taskNNNN.tests.yaml` を読む
2. 各受け入れ基準の `red_confirmed` と `red_reason` を参照する
3. 赤が確認された基準と、確認されていない基準を区別して判断する

**代替フロー**:
- `red_confirmed: true` でありながら赤が観測されていない基準があると、
  実行者は誤った帰属を行う（本要件が解消する状態）

**事後条件**:
- 実行者が受け取る赤状態の主張が、観測された事実と一致している

### 4.2 機能詳細

#### FR1: AC-7 の `red_confirmed` を false にする

**説明**: `test-docs/stale-test-name-refs/task0001.tests.yaml` の AC-7
エントリの `red_confirmed` の値が `false` であること（現状は 81 行目で
`true`）。

**入力**:
- `test-docs/stale-test-name-refs/task0001.tests.yaml`: YAML ファイル -
  編集対象の記録

**出力**:
- 同ファイルの AC-7 エントリ: YAML マッピング - `red_confirmed: false`

**ビジネスルール**:
- 観測されていない赤を `true` として記録しない

#### FR2: AC-7 の `red_reason` に不変条件ガードの根拠を書く

**説明**: AC-7 の `red_reason`（現状 82〜88 行目）を書き換え、AC-7 が
書き方の規律に対する不変条件ガードであり、観測可能な事前状態を持たない
こと（この記録自体をタスクが作成するため、その前に赤状態が存在し得ない
こと）、そして AC-6 と同じ扱いを受けることを述べる。書き換え後の
テキストは、観測された赤を主張せず、また示唆もしない。

**入力**:
- AC-7 の `red_reason`: 折り畳みブロックスカラー（`>-`） - 現行テキスト
- AC-6 の `red_reason`（74〜78 行目）: 折り畳みブロックスカラー - 参照する
  書きぶり

**出力**:
- AC-7 の `red_reason`: 折り畳みブロックスカラー（`>-`） - 不変条件ガードの
  根拠を述べた新しいテキスト

**ビジネスルール**:
- AC-6 の `red_reason` と同じ形の説明にする
- 観測された赤の主張を含めない

#### FR3: `notes` に AC-7 が未確認の赤である旨を記す

**説明**: 記録末尾の `notes` ブロック（現状 89〜95 行目）に、AC-7 が
未確認の赤である旨を述べる 1 行を追加する。

**入力**:
- `notes`: 折り畳みブロックスカラー（`>-`） - 現行テキスト

**出力**:
- `notes`: 折り畳みブロックスカラー（`>-`） - 1 行が追加されたテキスト

**ビジネスルール**:
- 追加は既存の `notes` 折り畳みブロックスカラーの内部に対して行い、
  新しいトップレベルキーや新しい `notes` エントリのリストは作らない

#### FR4: 分割表記の規約を維持する

**説明**: 編集後、ファイル内に旧識別子の連続した出現が 0 件であること。
旧識別子への言及は、ファイル冒頭のヘッダコメント（1〜4 行目）が宣言する
`接頭辞 + 接尾辞` の分割形のままとし、ヘッダコメント自体はそのまま残す。

**バリデーション**:

| 項目 | ルール | エラーメッセージ |
|------|--------|------------------|
| 旧識別子の連続出現数 | 0 件であること | 旧識別子が連続した文字列として出現している |
| ヘッダコメント（1〜4 行目） | 変更しないこと | ヘッダコメントが変更されている |

**エラーケース**:

| エラー | 条件 | 対応 |
|--------|------|------|
| 旧識別子の連続出現 | 書き換えた `red_reason` や `notes` が旧識別子を連続表記した | 分割形に直す |

#### FR5: 他の受け入れエントリを変更しない

**説明**: AC-1 から AC-6 は現在の `red_confirmed` の値と `red_reason` の
テキストを変更しない。`task_id`、`baseline_failures`、`final_failures`
も同様に変更しない。

**ビジネスルール**:
- 変更は AC-7 エントリと `notes` ブロックの内部に限る
