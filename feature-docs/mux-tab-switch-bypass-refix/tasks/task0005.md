# Task Plan: task0005 — apply_pending_resize consumes only settler-forwarded grid sizes

## Goal

A `pending_resize` raised by a non-settler source during the settling
window never broadcasts a grid size computed from a not-yet-settled
status-bar inset: the size the PTYs receive is always the settler's
forwarded decision, and the settler's record of what it forwarded never
diverges from the size actually applied.

## Design

### Defect — grid computation reads a settler-unsettled inset

Change 2 of the merged task0002 decoupled which events SET
`pending_resize` from the settler, but not which inset value the eventual
resize CONSUMES. `grid_size()` still reads
`status_bar_bot_inset_logical`, which is now updated immediately on any
height change (correctly, for drawing and pointer routing — FR4), and
`apply_pending_resize` feeds that recomputed size into the app grid and
the group-wide `Resize` broadcast. So when `pending_resize` is raised by
something other than the settler's forward — the mux-sidebar inset
refresh on mux attach, or a compositor resize / scale-factor change — a
transient, not-yet-settled status-bar height reaches the PTYs, which is
the very path FR6's settle debounce exists to close. The concrete firing
order occurs within a single render pass on mux attach/reattach (exactly
when the settling storm happens): the status-bar inset refresh resets the
settler and writes the transient inset → the sidebar inset refresh raises
`pending_resize` → `apply_pending_resize` computes the grid from the
transient inset and broadcasts. Before the merged Change 2 the inset was
only written on the settler's forward, so this could not happen. It also
risks the settler's last-forwarded record diverging from the size actually
applied.

### Required change

Separate the drawing/pointer-routing inset from the grid-computation
input. Mechanism is the implementer's choice between (at least):

- keep `status_bar_top_inset_logical` / `status_bar_bot_inset_logical`
  immediate for drawing and hit-testing (FR4 behavior, unchanged), and
  have grid computation read a separate settled value updated only when
  the settler forwards; or
- have `apply_pending_resize` apply the settler's forwarded `(cols,
  rows)` directly instead of recomputing from the inset at apply time
  (deferring or reconciling non-settler resizes that arrive while a
  settle is pending).

Constraints in either mechanism:

1. **FR4 preserved**: an inset-only change (unchanged derived grid) still
   applies the drawing insets immediately and never sets `pending_resize`
   (merged task0002 behavior; IMPLEMENTATION.md D-D).
2. **FR6 closed, not narrowed**: during the settling window, no
   `pending_resize` source — settler reset, sidebar refresh, compositor
   `Resized` / scale change — can broadcast a size derived from a
   not-yet-settled status-bar inset.
3. **No stale lock-in**: once the settler forwards, subsequent legitimate
   resizes apply the new size normally; a fully idle window still ends up
   at the settled size.
4. **Record coherence**: the settler's last-forwarded size and the size
   actually applied/broadcast stay equal — no divergence between what the
   settler believes it forwarded and what the PTYs got.
5. **Predicate seam (IMPLEMENTATION.md D-E)**: this task does not modify
   the inset-change predicate's tolerance semantics or its tests —
   task0006 owns those; this task only consumes the predicate.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS10): a unit test reproduces the traced mux-attach firing
  order — settler reset + transient inset write, then a sidebar-driven
  `pending_resize`, then `apply_pending_resize` — and asserts the
  applied/broadcast grid size is NOT derived from the transient inset:
  it equals the settler's last forwarded size, or the resize is deferred
  until the settler forwards. The test is documented as failing against
  the pre-change code (fail-first evidence in its doc comment).
- [ ] AC-2 (TS10): a compositor-sourced `pending_resize`
  (`Resized` / scale-factor change) during the settling window likewise
  never applies a size computed from the not-yet-settled inset.
- [ ] AC-3 (TS10): after any sequence of settles and applies, the
  settler's recorded last-forwarded size equals the size actually applied
  (unit test asserts equality; no divergence path remains).
- [ ] AC-4 (TS5 / FR4): a status-bar height change with an unchanged
  derived grid-size candidate still applies the new drawing-inset values
  immediately and does not set `pending_resize` (merged behavior intact).
- [ ] AC-5 (TS5 / FR6): a frame where neither insets nor derived grid
  size change leaves insets untouched and never sets `pending_resize`;
  and once the settler has forwarded, a subsequent legitimate size change
  applies normally (no stale lock-in on an idle window).
- [ ] AC-6 (NFR3): all existing `ResizeSettler`, inset-application, and
  self-wake-predicate unit tests stay green with no assertion changes.
- [ ] AC-7: doc comments on the changed sites cite `0029db1c89ab226f` /
  `5b2f22c5a14f7364` and state the sharpened D-D boundary: drawing and
  pointer-routing insets are immediate; grid computation and the `Resize`
  broadcast consume only settler-forwarded values.
