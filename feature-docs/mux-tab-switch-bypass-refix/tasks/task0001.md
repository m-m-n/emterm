# Task Plan: task0001 — Bypass split gate admits the measured 26-segment MIDDLE

## Goal

The real measured scrollback shape — 2 MiB payload, 31 segments, `k = 27`,
`middle_segment_count = 26` after head fold — engages the bypass split and
replays in the tens-of-ms order (on par with bypass-engaged cost for the
same payload size), with the NFR1 double-cost protections intact and a new
release bench pinning the shape.

## Requirements

FR1, FR2, FR6, NFR1, NFR3

## Scope

### Files to Create

None.

- `crates/term_core/src/terminal_core.rs` — the segment-count treatment in
  the `bypass_split` gate (`middle_segment_count <=
  BYPASS_PREFIX_MAX_SEGMENTS`, currently 24, near the gate condition and
  the constant's definition), its doc comments, and new/updated unit tests

- `crates/term_core/src/bench.rs` — a new release bench reproducing the

## Design

### Current behavior (defect)

The split engages only when ALL hold: `middle_segment_count <=
BYPASS_PREFIX_MAX_SEGMENTS` (24), `middle_len <= BYPASS_PREFIX_MAX_BYTES`
(64 KiB), `suffix_len >= BYPASS_SUFFIX_MIN_BYTES` (4096), and `suffix_len
>= middle_len`. In the measured shape, adjacent scrollback-marker dims
always differ, so `leading_uniform_run_len` folds a HEAD of length 1 only,
leaving `middle_segment_count = 26 > 24` — the gate rejects the very shape
the prior feature targeted, and the switch pays the ~800–1000 ms full
non-bypass drain (finding `b6a60c440da70e79`).

### Required change

Change the segment-count treatment so the measured shape engages. The
mechanism is the implementer's choice (e.g. a raised bound with a measured
per-segment-cost justification, or a cost-aware bound that combines the
MIDDLE's segment count with its already-byte-bounded size), subject to all
of:

1. **NFR1 (see IMPLEMENTATION.md D-B)**: the byte bound, the suffix floor,
   and the suffix-dominates-middle condition stay in force; a genuinely
   expensive MIDDLE/prefix must still not engage. The rationale
   `BYPASS_PREFIX_MAX_SEGMENTS` was introduced for — each MIDDLE segment
   pays one reflow regardless of its byte size — must be answered
   explicitly in the new treatment's doc comment (why MIDDLE replay stays
   cheap at the admitted count).
2. **An enforced bound remains**: whatever the new treatment is, there is a
   mechanically-enforced boundary with tests at exactly-at (engages) and
   one-past (does not engage). The existing 24-boundary unit tests are
   updated to the new boundary while preserving their both-sides intent;
   they are not deleted.
3. **Shared contracts preserved (IMPLEMENTATION.md Shared Components)**:
   the caller-visible meaning of `bypass_engaged` is unchanged, and the
   `h == k` empty-MIDDLE degradation postcondition is untouched (task0003
   pins it in parallel; this task must not alter that semantics).
4. **Doc-comment convention (IMPLEMENTATION.md D-C)**: the changed
   condition/constant cites `b6a60c440da70e79` and its D1–D9 design
   lineage.

### New bench (FR2)

A new release bench in `bench.rs` reproduces the SPEC-cited shape: ~2 MiB
HEAD-dominant payload, 31 total segments, `k = 27`, a 26-segment MIDDLE
whose adjacent dims all differ and oscillate at-or-above the settled target
(the direction D8's fold admits — `visible_row_count` 0→1 shrinks the
grid, so pre-settling dims sit at the larger size), and a small qualifying
target-dims tail. The latency ceiling is asserted relative to the
same-host segment-free cost using the file's precedent bound style (the
`3.0x + 20 ms` class used by the existing marker-cluster bench), not an
absolute wall-clock constant. The existing 24-segment bench
`marker_cluster_tail_bench_2mib_matches_bypass_engaged_cost` remains green
and unchanged.
