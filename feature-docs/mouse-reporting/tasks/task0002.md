# Task Plan: task0002 — Mouse report encoding and routing-decision helpers

## Goal

A window-free decision layer that composes a mouse report's button code, encodes
it in either the X10 or the SGR form, decides whether a motion is reportable,
caps motion volume at cell granularity, and chooses which of the three wheel
consumers takes a notch — all as pure functions over plain values, with
byte-exact unit tests.

## Requirements

FR2, FR3, FR4, FR5, FR6, FR7, FR9, NFR1, NFR4, NFR5, NFR6, NFR7

## Scope

### Files to Create

- `src-tauri/src/window_host/mouse_report.rs` — button-code composition, report encoding, the motion gate, the cell-change filter, and their inline tests

### Files to Modify

- `src-tauri/src/window_host/mod.rs` — register the new module in the window_host module root
- `src-tauri/src/window_host/input_translate.rs` — add the wheel-consumer decision and its inline tests alongside the existing alternate-scroll helpers

## Design

This task owns shared components SC-2, SC-3, SC-4, SC-5 and SC-6 of
IMPLEMENTATION.md. Those contracts are authoritative and are not restated here;
implement exactly them, because another task compiles against them in parallel.

**Placement.** SC-2 through SC-5 live in the new module. SC-6 lives in the
existing translation module, next to the alternate-scroll helpers whose
selection it now governs, so the wheel-routing tests sit beside the
alternate-scroll tests that pin today's behaviour.

**Purity is the point.** Every unit here takes plain values and returns plain
values: no window handle, no GPU surface, no PTY, no reference to the core
crate's mode types and no winit type in a signature. The caller converts its
state into those plain values. A unit that cannot be called from a bare test
without constructing a window has missed this task's contract, regardless of
whether its output is correct.

**Encoding flow.** Event description → button code (SC-2) → optional byte
sequence (SC-3). The two stages stay separate so a coordinate that cannot be
expressed in the X10 form suppresses the whole report at the second stage
without the first stage knowing about coordinates.

**Suppression is a value, not an error.** The unencodable X10 coordinate (FR9)
is the single "no output" condition in this feature. It is represented as an
absent optional value: no error type, no log line, no clamping, no partial byte
sequence.

**Motion volume.** The motion gate (SC-5) answers "is a motion reportable at
all for the active tracking mode" and the cell-change filter (SC-4) answers "has
the cell actually changed". Both run before encoding, so a suppressed motion
costs no encoding work. The filter owns its cached cell and exposes a reset;
deciding when to reset is the caller's job (decision D7).

**Wheel decision.** SC-6 returns exactly one consumer for every input
combination, and it branches on tracking-active **first** — the two branches
share no rows, which is what makes the three consumers structurally exclusive
rather than exclusive by tie-break (decision D5).

- Tracking-active branch: Shift held yields scroll-scrollback; Shift not held
  yields report-to-application. Arrow translation is unreachable here — while an
  application is tracking the mouse, no wheel notch ever produces arrow bytes,
  on either screen.
- Tracking-inactive branch: today's matrix, reproduced exactly and without
  consulting Shift at all — arrow translation on the alternate screen when both
  the alternate-scroll mode bit and the alternate-scroll setting are on,
  scroll-scrollback otherwise.

Express this as one total decision, not as nested conditions at a call site, so
mutual exclusivity is a property of a single testable unit. A scroll-scrollback
outcome on a screen with no scrollback to move is a no-op; that is the existing
behaviour of that path and is not special-cased here.

**Gating and portability.** Everything here stays inside the existing
gui-feature module tree, and no platform-conditional branch is introduced.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The X10 encoding is byte-exact for press, release, motion and both
      wheel directions — including a left press at column 1 row 1 emitting the
      introducer, the letter M, then the bytes 32, 33, 33; its release emitting
      35, 33, 33; the release base being replaced by 3; motion adding 32; and
      wheel-up and wheel-down carrying 64 and 65.
- [ ] AC-2: The SGR encoding is byte-exact for press, release, motion and both
      wheel directions, with the final byte M for a press or motion and m for a
      release, the press base retained on release, and unbiased decimal
      coordinates.
- [ ] AC-3: Ctrl contributes the value 16 to the button code, Alt contributes 8,
      both together contribute 24, and no combination of inputs ever produces
      the value 4.
- [ ] AC-4: Under the X10 encoding, column 223 and row 223 encode normally,
      while column 224 or row 224 yields no bytes at all — not a clamped value
      and not a partial sequence; the same event under the SGR encoding carries
      the true coordinate.
- [ ] AC-5: The cell-change filter reports the first cell, suppresses a repeat
      of the same cell, reports again on crossing into a different cell, carries
      its cached cell across calls, and reports the next cell unconditionally
      after a reset.
- [ ] AC-6: The motion gate yields nothing when only mode 1000 is active,
      nothing when 1002 is the highest active tracking mode and no button is
      held, the held button when 1002 is active with a button held, and always a
      result under 1003 — the held button, or the "none" identity when no button
      is held. With several buttons held it yields the lowest-numbered one.
- [ ] AC-7: The wheel-consumer decision yields exactly one consumer for every
      input combination. While tracking is active it yields scroll-scrollback
      when Shift is held and report-to-application otherwise, and it never
      yields arrow translation in that branch — including the alternate-screen
      case with the alternate-scroll mode bit and setting both on. While
      tracking is inactive it reproduces today's choice between arrow
      translation and scrollback scroll exactly, without consulting Shift.
- [ ] AC-8: Every unit added by this task is exercised by a test that constructs
      no window, no GPU surface and no PTY; the main build command, the main
      test command and the CLI-only check all exit 0; and the change adds no
      platform-conditional branch.

## Test Notes

- All tests are inline next to the code under test, in the
  subject-scenario-expectation naming style, with each unit constructed
  explicitly per test and no shared fixture. No test crate is added.
- AC-1 and AC-2 realise scenarios TS-3 and TS-4 of VERIFICATION.md and are best
  written table-driven: a table of (button, event kind, column, row, modifiers,
  encoding) against the expected byte sequence, asserted byte-for-byte. Assert
  the full sequence including the introducer, not a substring.
- AC-3 realises TS-5; include a case that proves shift cannot reach the button
  code even when the caller passes a modifier state that has shift set, since
  that is the only mechanical guarantee behind AC10 of SPEC.md.
- AC-4 realises TS-6 and must test 223 and 224 on both the column and the row
  axis independently, plus the SGR counterpart of the 224 case.
- AC-5 realises TS-7: feed a sequence with repeats and assert the exact set of
  emitted cells, not just the count, so an off-by-one in the cache is visible.
- AC-6 realises TS-9. Include the multi-button case explicitly: with left and
  right both held the report carries left (decision D6).
- AC-7 realises TS-8. Enumerate the full input combination space rather than
  sampling it — five boolean inputs are small enough to cover exhaustively, and
  exhaustiveness is what proves mutual exclusivity. Two cells deserve a named
  test of their own because they are where the requirement documents appeared to
  disagree: tracking-active with Shift held on the alternate screen with the
  alternate-scroll mode bit and setting both on must yield scroll-scrollback
  (never arrow translation), while the same cell with tracking inactive must
  still yield arrow translation.
- TDD-awkward point: the byte sequences are the specification, so write the
  expected-byte tables from SPEC.md's encoding section first and let them fail
  before any encoder exists.

## Out of Scope

- Reading the core mode bits, collecting the modifier state, converting pointer
  pixels to cells, and writing anything to a PTY — all of that is the routing
  task's work. This task's units receive those values already resolved.
- Deciding when to reset the cell-change cache (the caller's job, decision D7).
- Any change to the existing alternate-scroll helpers' own behaviour: the new
  decision selects between them and the other consumers, it does not modify
  them.
- Any new setting, and any change to the core crate.
