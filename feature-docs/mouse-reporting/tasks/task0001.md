# Task Plan: task0001 — Core-side mouse-tracking mode state

## Goal

`term_core` holds DEC private modes 1000, 1002, 1003 and 1006 as mode bits that
the host can read, instead of accepting the request and dropping it through the
dead TS-fallback arm.

## Requirements

FR1, NFR3, NFR5

## Scope

### Files to Modify

- `crates/term_core/src/csi_modes.rs` — add the four mouse mode bits, move modes 1000, 1002, 1003 and 1006 off the TS-fallback arm onto them, and update the existing fallback test while adding the toggle test

## Design

Implements shared component SC-1 of IMPLEMENTATION.md; that table is the
authoritative contract and is not restated here. This task owns SC-1 and is the
only task that may change it.

**Responsibility.** The mode-set handler gains one arm per mouse mode. On a set
request it sets that mode's bit, on a reset request it clears it, and in both
cases it returns the "no host-side action" action value rather than the
TS-fallback value the four modes return today. The existing mode-query accessor
is what the host reads them back through — the same route the alternate-scroll
mode already uses, so no new accessor is introduced.

**Bit allocation.** The four new bits take currently free positions in the
existing mode bitfield. No existing bit is renumbered or reused: other code and
existing tests pin the current positions, and a renumbering would be an
invisible behavioural change in unrelated modes.

**Untouched neighbours.** Mode 1005 keeps its existing TS-fallback arm — it is
explicitly out of scope and its arm stays exactly as it is. Mode 1015 is
deliberately given no arm at all, so it continues to fall through the
unknown-mode arm as a silent no-op. Neither gains a bit, an accessor or a test.

**Flow.** A DEC private mode request arrives at the handler with the mode number
and a set/reset flag → the handler matches the mode number → for one of the four
mouse modes it updates the corresponding bit and returns the no-action value →
for every other mode the current behaviour is unchanged.

**Constraint.** This crate is compiled into the CLI-only build, so this change
introduces no dependency that is unavailable without the GUI feature, and adds
no conditional compilation of any kind.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: For each of the modes 1000, 1002, 1003 and 1006, a set request
      returns the no-host-action value and the mode-query accessor reports that
      mode active afterwards.
- [ ] AC-2: For each of the same four modes, a reset request returns the
      no-host-action value and the mode-query accessor reports that mode
      inactive afterwards.
- [ ] AC-3: The four mode bits are independent: setting exactly one of them
      leaves the other three inactive, and clearing one leaves the others
      untouched.
- [ ] AC-4: Mode 1005 still returns the TS-fallback action value, and mode 1015
      still returns the no-action value without owning a bit of its own.
- [ ] AC-5: The pre-existing fallback test no longer asserts the fallback value
      for 1000, 1002, 1003 or 1006; it asserts it only for the modes still on
      that arm, and the four moved modes are covered by positive bit assertions
      instead.
- [ ] AC-6: No existing mode's bit position changed, and the crate's own test
      command and the CLI-only check both exit 0.

## Test Notes

- All tests are inline in the module under test, in the
  subject-scenario-expectation naming style already dominant in this crate, with
  the unit under test constructed explicitly inside each test and no shared
  fixture.
- AC-1 through AC-3 realise scenario TS-1 of VERIFICATION.md; build them by
  mirroring the construction style of the existing alternate-scroll toggle test
  rather than inventing a new harness.
- AC-4 and AC-5 realise scenario TS-2: the existing fallback test is edited, not
  duplicated. It currently asserts the fallback value for a list that includes
  all four moved modes; narrowing that list is part of this task, and leaving it
  unchanged makes the suite fail.
- AC-6 is checked by running the crate test command and the CLI-only check from
  the project root.
- Edge case worth an explicit test: setting a mode twice, and clearing a mode
  that was never set, must both be no-ops that still return the no-action value.

## Out of Scope

- Any host-side behaviour: reading the bits, encoding reports, pointer routing
  and PTY emission all belong to other tasks.
- DECSET 1005 and 1015 support (decision D9).
- Any new accessor, any renaming of existing mode identifiers, and any change to
  the action-value vocabulary itself.
