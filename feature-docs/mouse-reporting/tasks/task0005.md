# Task Plan: task0005 — A window-free decision seam for the three pointer paths

## Provenance

- **source**: verify
- **source_ids**: TS-19, TS-20, TS-21
- **review_round**: n/a (verify-sourced)

All three failed items share one root cause. The reporting decisions were
extracted into units that ARE behaviourally tested, but the three real pointer
handlers take mutable references to the window host and to the application
object and cannot be constructed in a unit test, so the sequence in which those
units are consulted — the part TS-19, TS-20 and TS-21 are about — is pinned only
by assertions that read the routing source and compare substring positions. A
decision unit that is correct while its call site is miswired keeps those
assertions green, which is exactly what verify round 1 reported. One task,
because one seam makes all three observable.

## Goal

The decision each pointer path makes for one raw event — including the order in
which the grid-ownership test, the gesture-ownership record, the motion gate and
the cell-change filter are consulted, and what the event finally does — is one
value computed from plain inputs, and the effects of that value are applied to
plain state and a caller-supplied byte destination, so that "no bytes were
produced" and "the cached cell did not move" are assertable without a winit
window, a GPU surface or a live PTY.

## Design

This task adds shared components SC-10 and SC-11 and applies cross-task
decision D12 of IMPLEMENTATION.md. It changes the decision CONTENT of nothing:
SC-2 through SC-9 keep their contracts exactly, and this task's units consult
them. What it adds is a place from which that content is evaluated that a test
can reach.

### The sequence unit (SC-10)

One unit per pointer path — button, motion, wheel. Each takes only plain values
(IMPLEMENTATION.md SC-10 lists the input set in full) and returns one enumerated
outcome naming exactly one disposition plus the record updates it implies. The
three properties that matter for this task's criteria:

1. **The dispositions are named and disjoint.** "Emit a report" carries the
   exact bytes and the identifier of the tab they are destined for. "Take a
   local arm" names WHICH local arm — begin a selection drag, complete a
   selection and publish it to PRIMARY, open a hovered link, paste PRIMARY,
   scroll the scrollback, translate to arrow bytes. "Do nothing" is its own
   value. A test can therefore tell "nothing happened" apart from "the local arm
   ran", which a byte-absence assertion alone cannot.
2. **Ordering is inside the unit, not at the call site.** The grid-ownership
   answer is consulted first on all three paths, ahead of the motion gate, the
   cell-change filter and the tracking-active read. That is what makes the TS-21
   ordering assertion an assertion about a returned value rather than about
   source-text positions.
3. **The record updates travel in the outcome.** Nothing mutates a record
   during the decision; the outcome states which updates to apply, so a decision
   can be evaluated in a test without any state at all.

### The applier (SC-11)

Applies an outcome to the record pair as a plain value a test constructs
directly, appending report bytes to a caller-supplied byte destination together
with their target tab identifier. It never performs the named local arm — that
is returned to the caller — and it never touches a PTY, which is what keeps it
window-free. A separate clear-all operation empties the gesture-ownership record
and the held-button record together, for the host to invoke on focus loss.

### The four corrections the sequence contract carries

These are the wiring defects review round 1 recorded against the same call
sites; SC-10's postconditions state each as a contract so the sequence unit is
where they are decided and where they are tested:

- A release's disposition reads "at least one tracking mode is active", not
  merely which encoding is selected, so an application that clears its tracking
  modes between press and release gets no stray release report.
- A reported release carries the tab identifier its PRESS recorded, so a tab
  switch mid-gesture cannot deliver the release into a different tab.
- All three sequences carry the same two reset observations (no tracking mode
  active; the active tab differs from the one the records were built against),
  so a click or a wheel notch with no intervening motion is not decided from
  stale records.
- While a gesture is owned by the local side, motion stays local whatever the
  instantaneous shift flag has become, so releasing Shift mid Shift-drag does
  not start streaming drag reports for a button the application never saw
  pressed.

### Boundary

The handlers in `pointer_routing.rs` are NOT touched by this task — task0006
owns reducing them onto this seam. The units here are written so that a handler
can be reduced to gather / decide / apply / perform-local-arm, and their
contracts are IMPLEMENTATION.md SC-10 and SC-11, which both tasks implement
against (D3).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: One decision sequence unit exists per pointer path (button, motion,
      wheel). Each is constructed and called inside a test with no winit window,
      no GPU surface and no live PTY, takes only plain values, returns one
      enumerated outcome naming exactly one disposition, and mutates nothing
      itself — the record updates it implies travel in the returned outcome.
      "Emit a report" carries both the exact bytes and the target tab
      identifier; each local disposition names which local arm it is.
- [ ] AC-2: An applier takes an outcome, the record pair as a plain value the
      test constructs directly, and a caller-supplied byte destination; it
      appends report bytes there paired with their target tab identifier,
      applies the outcome's record updates exactly once, appends nothing for a
      do-nothing or local disposition, and performs no local arm itself. A
      clear-all operation empties the gesture-ownership record and the
      held-button record together.
- [ ] AC-3 (TS-19): A table over (chrome region × event kind × button identity)
      drives the sequence units and asserts that the byte destination stays
      empty for a left / middle / right press, a left / middle / right release,
      a motion and a wheel notch over the top strip, the status-bar bottom
      strip, the right-edge scrollbar overlay, the mux sidebar in both
      persistent and overlay placement and the CSD edge-resize hot zone, and
      over every position while the profile selector is visible — and that a
      position over the grid with no region claiming it is accepted and does
      produce bytes.
- [ ] AC-4 (TS-20, TS-24): Driven as a sequence against one persistent record
      pair: a press with Shift held, then Shift lifted, then release produces no
      bytes and returns the local disposition that completes the selection
      (drag flag cleared, pending anchor consumed, selection published to
      PRIMARY); a press without Shift, then Shift pressed, then release produces
      the matching release report whose button code does not carry the shift
      bit; motion between those two events follows the recorded owner and not
      the instantaneous shift flag; a press the grid-ownership answer rejects
      records no owner; a delivered release clears its record; a second button
      pressed mid-gesture is owned independently.
- [ ] AC-5 (TS-21): After a motion the grid-ownership answer rejects, the test
      reads the record pair directly and asserts the cached last-reported cell
      is unchanged — not merely that no bytes appeared — and a following motion
      over the grid at a different cell still produces bytes.
- [ ] AC-6 (TS-22, TS-23): A release whose gesture's tracking modes were all
      cleared between press and release produces no bytes; a release after an
      active-tab change carries the tab identifier the press recorded; a release
      with no recorded press produces no bytes; each of the three sequences
      carries both reset observations, asserted by reading the record pair after
      driving the button path and the wheel path with no intervening motion; the
      clear-all leaves both records empty.
- [ ] AC-7: Tests are inline modules next to the units, each unit constructed
      explicitly inside its own test with no shared global fixture and no new
      test crate or harness; no platform-conditional branch and no logging is
      added; and the main build command, the main test command, the core crate
      test command and the CLI-only check all exit 0.

## Test Notes

- Every criterion above is satisfied only by driving the unit and observing its
  result — the returned outcome, the byte destination, the record pair. An
  assertion that reads the routing source and compares substring positions
  satisfies none of them; that is the verdict verify round 1 returned against
  TS-19, TS-20 and TS-21.
- The byte destination is what turns "no report was produced" into an
  observation. Assert emptiness, not just the absence of a panic.
- TS-21's assertion subject is the record pair after the call, because a test
  that only checks byte emptiness passes even when the grid-ownership answer is
  consulted after the cell-change filter.
- Sequence-driven criteria (AC-4, AC-6) need the same record pair carried across
  the calls of one scenario; constructing a fresh pair per call hides exactly
  the defects they exist to catch.
- Worth an explicit case: a press inside the grid whose release arrives while
  the pointer sits over a guarded region — ownership decides, not the release
  position, so the reported gesture still gets its release report.
- Manual scenarios TS-11 and TS-12 remain integrated confirmation only; they are
  not a substitute for any criterion here.
