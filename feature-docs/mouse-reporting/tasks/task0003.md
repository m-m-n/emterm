# Task Plan: task0003 — Pointer routing integration and report emission

## Goal

Pointer presses, releases, motion and wheel notches reach the active tab's PTY
as mouse reports while an application is tracking the mouse, behind every
existing egui chrome guard and behind the Shift local override — and behave
exactly as they do today whenever no tracking mode is active.

## Requirements

FR2, FR3, FR4, FR7, FR8, FR10, FR11, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Modify

- `src-tauri/src/window_host/pointer_routing.rs` — insert the reporting decision after the existing chrome guards and after the Shift override, collect the values the decision layer needs, and emit reports through the active tab's input path
- `src-tauri/src/window_host/mouse_report.rs` — consume the button-code, encoder, motion-gate and cell-change-filter contracts; create this module to the pinned contract if it is absent in this worktree, and adopt the integration side on merge
- `src-tauri/src/window_host/input_translate.rs` — consume the wheel-consumer decision contract; same create-if-absent and adopt-on-merge rule
- `src-tauri/src/window_host/mod.rs` — module-root registration for the report module, when the module had to be created in this worktree
- `crates/term_core/src/csi_modes.rs` — consume the four mouse mode identifiers; same create-if-absent and adopt-on-merge rule

## Design

This task owns shared component SC-7 of IMPLEMENTATION.md and is the **consumer**
of SC-1 through SC-6. Decision D3 governs the consumption: implement against the
pinned contracts, create the minimum needed to compile when a producing task's
file is absent from this worktree, and adopt the integration side for those
files on merge. Never change a contract locally — a contract that does not fit
is a plan deviation to report.

This task is also the integration owner: after it merges, no placeholder remains
anywhere in the feature. Nothing is left "to be wired later".

**Precedence order.** Every pointer event is decided in exactly this order, and
the order itself is the requirement:

1. The existing egui chrome guards run first and unchanged — the profile-selector
   modal, the CSD title bar and tab bar top strip, the status-bar bottom strip,
   the right-edge scrollbar overlay, the mux sidebar in both its persistent and
   overlay placement, and the CSD edge-resize hot zone. An event any guard
   consumes is never reported and keeps its current local behaviour.
2. The Shift override runs second. While Shift is held the event is never
   reported and takes its local path: selection for a drag, link open for
   Ctrl+click, PRIMARY paste for a middle click, and eMterm's scrollback for a
   wheel notch (decision D5 — never the arrow translation while a tracking mode
   is active).
3. The tracking-active question runs third, read from the core mode bits (SC-1)
   on each event rather than from a host-side mirror (decision D2). When no
   tracking mode is active, every remaining step is skipped and today's
   behaviour stands untouched.
4. For motion only: the motion gate (SC-5) and then the cell-change filter
   (SC-4).
5. Encoding (SC-2 then SC-3), which may yield nothing for an unencodable X10
   coordinate.
6. Emission through SC-7.

Reporting is inserted into this chain — the guards and the local handlers are
not rewritten around it.

**Values the decision layer needs.** This task converts host state into the
plain values the decision layer takes: the pointer pixel position into a 1-based
column and row through the existing pixel-to-cell grid mapping (screen row, not
absolute buffer row); the current modifier state into the ctrl and alt flags,
with shift never forwarded because step 2 has already consumed it; the winit
button identity into the left / middle / right identity; and the scroll delta
into wheel-up or wheel-down notches.

**Wheel call site.** The wheel decision (SC-6) is taken once, ahead of both
existing wheel consumers, and its result selects exactly one of the three. Its
tracking-active branch already folds in the Shift override, so the call site
passes the shift-held flag straight into the decision rather than short-circuiting
the wheel path at step 2 — one decision, one selection, no second place where
Shift is interpreted for the wheel. When the decision is report-to-application
the scrollback offset is never touched and no alternate-scroll arrow bytes are
written; when it is scroll-scrollback nothing at all reaches the PTY, on either
screen.

**Ctrl+click and middle-click.** While tracking is active and Shift is not held,
a Ctrl+left press is reported with the ctrl modifier bit instead of invoking the
link-open path, and a middle press is reported as base 1 instead of performing
the PRIMARY paste. Both local paths stay exactly as they are for the
tracking-inactive case, and both remain reachable through the Shift override.

**Cache lifetime.** The host owns the cell-change cache and resets it whenever
it observes that no tracking mode is active, and on active-tab change (decision
D7).

**Constraints.** No setting is added anywhere — not in the settings crate, not
in the TypeScript mirror, not in the settings panel. No platform-conditional
branch is introduced. No logging is added on the pointer path. All of this code
stays inside the existing gui-feature module tree.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With a tracking mode active and Shift not held, a press over the
      terminal grid and its matching release are emitted through the active
      tab's existing PTY input path and drive no local selection; with no
      tracking mode active, the same press and release produce no report and
      select text exactly as today.
- [ ] AC-2: Motion is emitted only when the motion gate and the cell-change
      filter both allow it, and the host resets the cached cell when it observes
      that no tracking mode is active and on active-tab change, so the first
      motion of a new tracking session always reports.
- [ ] AC-3: With a tracking mode active and Shift not held, a wheel notch is
      reported on both the main and the alternate screen, the scrollback offset
      is unchanged and no alternate-scroll arrow bytes are written; with no
      tracking mode active, wheel behaviour is byte-for-byte what it is today,
      Shift included.
- [ ] AC-4: With a tracking mode active, holding Shift suppresses the report for
      press, release, motion and wheel alike. Shift+drag selects text,
      Shift+Ctrl+click opens the hovered link, Shift+middle-click pastes
      PRIMARY, and Shift+wheel moves eMterm's scrollback and writes nothing at
      all to the PTY — including on the alternate screen with the
      alternate-scroll mode bit and setting both on, where no arrow bytes are
      written either.
- [ ] AC-5: With a tracking mode active and Shift not held, a Ctrl+left press is
      reported with the ctrl modifier bit and does not open the hovered link,
      and a middle press is reported as base 1 and does not paste PRIMARY; both
      local behaviours are unchanged when no tracking mode is active.
- [ ] AC-6: An event consumed by any existing chrome guard — the profile
      selector, the title and tab strip, the status bar, the scrollbar overlay,
      the mux sidebar in either placement, or the CSD edge-resize zone — is
      never reported and retains its current local behaviour, for presses,
      releases, motion and wheel alike.
- [ ] AC-7: The change adds no settings field, no TypeScript settings mirror
      entry and no settings-panel row; it adds no platform-conditional branch;
      and the main build command, the main test command, the core crate test
      command and the CLI-only check all exit 0.

## Test Notes

- Automated coverage for this task is indirect by nature: the routing function
  runs inside a winit and egui context that cannot be constructed in a unit
  test, which is exactly why the decision logic was factored out into the pure
  layer. Do not build a windowed test harness for it.
- Where a routing step can be expressed as a pure value-to-value decision,
  express it that way and test it inline: the conversion from a winit button
  identity to the button identity the decision layer takes, and the conversion
  from a scroll delta to wheel notches, are both testable without a window and
  should be.
- AC-1, AC-2, AC-3 and AC-5 are confirmed end to end by manual scenarios TS-10
  and TS-11 of VERIFICATION.md; AC-4 by TS-11, whose alternate-screen Shift+wheel
  case is the one that pins decision D5 at the call site; AC-6 by TS-12; the mux
  half of AC-1 by TS-13. Record in the task's test file which criteria are
  covered manually rather than leaving them silently untested.
- AC-7's inspection half corresponds to TS-15 and TS-16, and its command half to
  TS-14 and TS-17.
- Edge case worth explicit attention while wiring: a press that starts inside
  the grid and releases outside it, and a release that arrives while the pointer
  sits over a chrome guard — in both cases the guard order above decides, and
  neither may leave a half-reported drag behind.
- Edge case: a tracking mode being cleared by the application while a button is
  still held. The next release must not report, and the cell cache must be reset
  on the same observation.
- Edge case: Shift being pressed or released mid-drag. Each event is decided on
  its own, so a drag can legitimately produce reported motion and then stop
  reporting; no state carries the drag's initial Shift decision forward.

## Out of Scope

- Changing any contract of SC-1 through SC-6; those belong to their owning
  tasks. A mismatch is reported as a plan deviation.
- Reimplementing or altering the existing chrome guards, the selection model,
  the link-open path, the PRIMARY paste path, or the alternate-scroll helpers —
  reporting is inserted ahead of them, not folded into them.
- The tracking-inactive half of the wheel matrix, including how it treats Shift:
  that is today's behaviour, preserved untouched (AC7).
- Any new user setting, any new transport channel, and any new logging on the
  pointer path.
- DECSET 1005 and 1015 (decision D9).
