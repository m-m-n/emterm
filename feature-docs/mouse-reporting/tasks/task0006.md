nothing else. The report bytes reach the tab the outcome names, the focus-loss
path clears the pointer records alongside the button-down record it already
zeroes, and every source-scanning assertion either pins that the handlers hold
no decision or has been replaced by a behavioural assertion.

## Design

This task applies cross-task decision D12 of IMPLEMENTATION.md and consumes
shared components SC-10 and SC-11 against their contracts there. It introduces
no decision of its own.

### The three-part handler

1. **Gather.** Read the plain values SC-10 takes out of the host, the
   application and the core mode state: the pointer position, the chrome-region
   geometry the host already hit-tests, whether the profile selector is visible,
   the modifier flags, the tracking-mode and encoding flags read at this event,
   the identifier of the currently active tab, the held buttons and the current
   record pair. This step holds NO branch that chooses between reporting and
   local handling, and mutates no record — that property is what makes the
   remaining untestable residue harmless.
2. **Decide.** Call the sequence unit for this path.
3. **Apply.** Call the applier with the outcome, the record pair and a byte
   destination.
4. **Perform.** Write whatever bytes the destination holds to the tab the
   outcome names, and run the local arm the outcome names through the existing
   local code paths, unchanged.

### What this resolves at the call sites

- The release path no longer reads the tracking state only for its encoding,
  and no longer writes to whichever tab happens to be active at release time:
  both come from the outcome, which SC-10 derives from the gesture's own press.
- The two reset observations are no longer motion-only: every path applies the
  outcome's record updates, so a click or a wheel notch with no intervening
  motion is decided from fresh records.
- The motion path no longer branches on the instantaneous shift flag; it has no
  branch at all.
- Focus loss clears the gesture-ownership and held-button records, matching the
  existing treatment of the pointer button-down record, so a button released
  outside the window strands no ownership.

### The source-scanning assertions

They were the only coverage the wiring had and verify round 1 rejected them as
such. They are not deleted blindly: for each one, either the property it pinned
is re-expressed as a behavioural assertion against the seam, or — for the single
property that is genuinely structural, that the handler body holds no decision —
it is kept and re-aimed at that subject. No assertion is removed leaving its
subject unpinned.

### Boundary

The existing chrome guards, the selection model, the link-open path, the PRIMARY
paste path, the alternate-scroll helpers and the tab input transport are not
rewritten — they are the inputs the gather step reads and the arms the perform
step runs. The left-press-only gating of the existing local side effects stays
exactly as it is.

## Test Notes

- The behavioural coverage for the decisions themselves lives with the seam
  (scenarios TS-19 through TS-24). What needs pinning HERE is that the handlers
  delegate to it: assert against the seam's observable surface — the byte
  destination and the record pair — wherever the handler's own inputs can be
  assembled without a window, and keep the structural assertion only for AC-1's
  subject.
- AC-3 is testable at the record level: drive the clear-all the focus-loss path
  invokes and assert both records are empty, then assert the next decision is
  taken from empty records.
- AC-4 is the regression guard: the tracking-inactive wheel matrix and the
  guarded regions' local behaviour are what the reduction most easily breaks.
  The existing tests for those paths must keep passing unmodified; changing one
  of them to accommodate the reduction is a plan deviation to report.
- Follow the inline convention (a test module next to the code under test, each
  unit constructed explicitly, no shared global fixture, no new test crate, no
  E2E harness) and keep every new test free of a winit window, a GPU surface and
  a live PTY.
- Manual scenarios TS-11, TS-12 and TS-13 are re-run as integrated confirmation
  after merge; they are not coverage for any criterion here.
