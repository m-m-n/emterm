# Task Plan: task0004 — One pointer-ownership decision for reporting

## Provenance

- **source**: review
- **source_ids**: 97676659aa15db37, a4377ac1f3430e7c, 5175da13ae0becec, c99335940bf23416
- **review_round**: 1

All four findings share one root cause: whether a pointer event belongs to the
terminal grid or to eMterm's local UI is decided independently, per event and
per handler, in the three pointer handlers of `pointer_routing.rs`. Three
findings are the spatial half of that split (a chrome region guarded on one
path is unguarded on another); the fourth is the temporal half (a press and its
matching release decided separately can be owned by two different paths). They
are one task because they are one decision that has to become one decision.

## Goal

Every pointer event that can produce a mouse report — button press, button
release, motion and wheel — answers "does this event belong to the terminal
grid?" through a single shared decision, and a button gesture is owned end to
end by whichever side took its press, so no chrome region leaks events to the
application and no gesture is left half-owned.

FR2, FR3, FR4, FR7, FR10, NFR1, NFR5, NFR6

## Design

This task adds shared components SC-8 and SC-9 and applies cross-task decisions
D10 and D11 of IMPLEMENTATION.md. It changes no contract of SC-1 through SC-7;
it changes only WHERE and HOW MANY TIMES the report-vs-local question is asked.

### The spatial half — one grid ownership test (SC-8, D11)

Today each handler asks its own question. The button handler runs a top-strip
test that is identity-independent, plus a bottom-strip / scrollbar-overlay /
sidebar test and a CSD edge-resize handoff that both apply only to a left
press; the motion handler runs no region test at all; the wheel handler runs
the sidebar and tab-band tests but no bottom-strip or scrollbar-overlay test.
The reporting block downstream of each of them accepts every button identity
the feature can encode, and the pixel-to-cell mapping clamps an out-of-grid
position to an edge cell rather than rejecting it, so an unguarded event
becomes a plausible-looking report of the wrong cell instead of nothing.

The replacement is one decision, stated once and consulted from all three
handlers:

1. The host collects the plain values the decision needs — the pointer
   position, the geometry of the top strip, the bottom strip, the right-edge
   scrollbar overlay, the mux sidebar in whichever placement is active and the
   CSD edge-resize hot zone, and whether the profile selector is visible.
2. The decision answers whether the position belongs to the terminal grid. It
   is independent of button identity, of press-versus-release, and of event
   kind: the same position gives the same answer for a left press, a right
   release, a motion and a wheel notch.
3. Each handler evaluates it BEFORE any reporting work — before the
   tracking-active read on the wheel path, and before the motion gate and the
   cell-change filter on the motion path, so a suppressed motion cannot advance
   the cached cell either.
4. A false answer means the event is never reported and keeps exactly its
   current local behaviour. The existing local side effects that genuinely are
   left-press-only keep their existing left-press-only gating; only the
   reporting question is made identity-independent.

The existing guards are not rewritten, reordered relative to each other, or
folded into the reporting path — their hit tests become the inputs of one
decision that now also covers the paths they never reached.

### The temporal half — gesture ownership (SC-9, D10)

A press and its matching release are one gesture (FR2 speaks of a press and its
*matching* release). Today the shift question is asked again at release time, so
one gesture can be owned by two different paths:

- Shift held at press: the press takes the local arm and starts a selection
  drag. Shift released before the button: the release satisfies the reporting
  condition, reports and returns, so the local release arm never runs — the
  drag flag stays set, the pending selection anchor is never taken, the
  selection is never copied to PRIMARY, and every later motion keeps extending
  a selection with no button held.
- Shift not held at press: the press reports. Shift pressed before the button
  is released: the release takes the local arm, which has no gesture to
  complete, so nothing is emitted and the application's button state stays
  down.

The fix records, at press time, which side took the gesture, keyed by button
identity, and routes the matching release to that same side regardless of the
shift state at release time. A press the grid ownership test rejects records no
ownership at all. The record is cleared when its release is delivered, and on
the same observations that already reset the cell cache (no tracking mode
active, active-tab change), so a mode cleared mid-gesture cannot strand it.

### Why this keeps FR7 intact

FR7 makes Shift the sole local override and states that holding Shift
suppresses reporting for that event. This task keeps Shift as the only thing
that can divert a gesture away from reporting, and keeps it consulted on the
press — nothing else, and no other modifier, key, setting or menu, suppresses
reporting. What changes is only the granularity at which that single override
is applied: it is applied once per gesture, at the gesture's start, rather than
re-asked per raw event.

That granularity is the SPEC's own. AC9 requires that with a tracking mode
active, Shift+drag "produces a text selection" — a selection is only produced
when its release completes it and updates PRIMARY, which a per-raw-event
reading cannot deliver once Shift is lifted mid-drag. The per-raw-event reading
is therefore the one that breaks AC9; per-gesture ownership is the reading
under which AC9, FR2's press/matching-release pairing and FR7 all hold at once.
AC10 is unaffected: the shift bit is still never set in any emitted report,
including a release emitted while Shift happens to be held.

### Constraint: the earlier attempt and why it was reverted

A bounded auto-fix for the gesture half was attempted during review (commit
b1244629) and reverted (ae47aa35). Its three failure modes are hard constraints
here:

1. It broke the committed source-scanning assertion at
   `src-tauri/src/window_host/tests.rs:1633`, which requires a literal negated
   shift condition to appear inside the mouse-reporting block. Any change to
   that condition updates that assertion in the same change (see AC-6).
2. It covered one direction only — the locally-owned gesture whose Shift is
   lifted — and left the reported gesture whose Shift arrives mid-drag still
   stranding the application's button state. Both directions are in scope.
3. It expressed the fix as an extra suppression condition on a release with no
   Shift held, which reads as a second local override alongside Shift and was
   judged to contradict FR7. Ownership is recorded at press time instead; no
   new suppression condition is added to the release path.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: One grid-ownership decision, expressed as a unit that takes plain
      values and runs with no winit window, answers whether a pointer position
      belongs to the terminal grid, and returns the same answer for a given
      position regardless of button identity, press-versus-release or event
      kind. It rejects the top strip, the bottom strip, the right-edge
      scrollbar overlay, the mux sidebar in both its persistent and overlay
      placement, and the CSD edge-resize hot zone, and rejects every position
      while the profile selector is visible; it accepts a position over the
      grid with no guard active.
- [ ] AC-2: A middle or right button press, and a middle or right button
      release, over each of the regions named in AC-1 produces no report — the
      guarded region's current local behaviour is unchanged, and the
      left-press-only gating of the existing local side effects is unchanged.
- [ ] AC-3: With a tracking mode active, pointer motion over each of the
      regions named in AC-1, and any motion while the profile selector is
      visible, produces no report AND leaves the cached last-reported cell
      unchanged, so a subsequent motion over the grid at a different cell still
      reports.
- [ ] AC-4: With a tracking mode active, a wheel notch over the status-bar
      bottom strip and over the right-edge scrollbar overlay produces no report
      and keeps its current local behaviour; the wheel notches over the mux
      sidebar and the tab-bar band that are already guarded stay guarded; a
      wheel notch over the grid is still reported and still leaves the
      scrollback offset untouched.
- [ ] AC-5: A button gesture is owned by whichever side takes its press, for
      both orderings: a press taken locally because Shift was held completes
      locally when the button is released after Shift is lifted — the drag flag
      is cleared, the pending selection anchor is consumed and the selection
      reaches PRIMARY, and no report is emitted; a press that was reported emits
      its matching release report when the button is released after Shift is
      pressed, with the shift bit not set. A press the AC-1 decision rejects
      records no ownership. The record is cleared when its release is delivered
      and on the observations that reset the cell cache.
- [ ] AC-6: The committed source-scanning assertions in
      `src-tauri/src/window_host/tests.rs` (the block-order assertions at
      1592-1690 and the literal shift-condition assertion at 1633) are updated
      in this same change to match the new structure and still pin that Shift
      is what diverts a gesture from reporting; no source-scanning assertion is
      deleted without a behavioural assertion replacing what it pinned.
- [ ] AC-7: No user setting, no TypeScript settings-mirror entry and no
      settings-panel row is added; no platform-conditional branch is added; no
      logging is added on the pointer path; and the main build command, the main
      test command, the core crate test command and the CLI-only check all exit
      0.

## Test Notes

- The existing routing tests at `src-tauri/src/window_host/tests.rs:1592-1690`
  are source-scanning tests: they assert the ORDER of blocks in the routing
  source, not behaviour, which is exactly why all four findings survived them.
  They are not coverage for any criterion above. Every criterion here needs a
  behavioural assertion.
- AC-1 and AC-2 map to the table-driven unit test of scenario TS-19: one row
  per (region, event kind, button identity) pair, asserting the decision and,
  where the wiring is expressible without a window, asserting that no bytes are
  produced.
- AC-5 maps to scenario TS-20, driven as a sequence of events against the
  ownership record rather than as a single call: press, then a shift-state
  change, then release, in both orderings, asserting the owner the release is
  routed to and the emitted bytes.
- AC-3 maps to scenario TS-21, whose point is ORDERING: the assertion is on the
  cache state after a suppressed motion, not only on the absence of bytes. A
  test that only checks "no bytes" passes even when the guard runs after the
  filter.
- Manual scenarios TS-11 (Shift override end to end) and TS-12 (chrome guards
  unaffected) are re-run as integrated confirmation; they are not a substitute
  for the automated scenarios above.
- Follow the inline test convention already used in these modules — a test
  module next to the code under test, each unit constructed explicitly inside
  its own test, no new test crate, no shared global fixture (NFR5), and no
  winit window, GPU surface or live PTY anywhere in the new tests (NFR6).
- Edge case worth an explicit test: a press inside the grid whose release
  arrives while the pointer sits over a guarded region. Ownership decides, not
  the release position, so the reported gesture still gets its release report.
- Edge case: a second button pressed mid-gesture. Ownership is per button
  identity, so the two gestures are owned independently.
