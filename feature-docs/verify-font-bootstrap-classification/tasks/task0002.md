# Task Plan: task0002 — Fail closed when the executed-test count cannot be derived

## Provenance

- `source`: review
- `source_ids`: [1f095aa46999c43d]
- `review_round`: 1

## Goal

The un-fetched verdict helper never reports a passed or warned outcome from a
value it could not derive: when the captured log cannot be read, or an
argument cannot be interpreted as a number, the classification is a failure
that names the cause instead of silently falling into the executed-greater-
than-zero branch.

## Requirements

FR2, FR4, FR5

## Scope

### Files to Create

None — both files already exist.

### Files to Modify
- `scripts/verify-font-bootstrap-verdict.sh` — check that the executed count was actually derived (and that the status argument is a number) before the classification branches; feed the captured log to the counting program in a way that cannot reinterpret the path as an option or an assignment
- `scripts/verify-font-bootstrap-verdict.test.ts` — add the cases that pin the new fail-closed behaviour and the unchanged counting behaviour

## Design

Read IMPLEMENTATION.md first: it owns the layer structure, the two component
contracts (Shared Components), the classification table — including the
derivation-failure row and decision D8 — and the conventions. This section adds
only what is specific to carrying them out.

### The defect being closed

The classification currently consumes the derived executed count without
checking either that the derivation succeeded or that what came back is a
number. When the count is not a number, the arithmetic comparison that selects
the zero-executed branch cannot answer and is treated as "not zero", so every
un-derivable run lands in the executed-greater-than-zero branch: a non-zero
status becomes a warning (which the script tallies as a pass) and a zero status
becomes a clean pass. That inverts both failure branches FR2 and FR4 into
passes, and the warning it emits states an empty count, which FR5 forbids. The
same defect class applies to the status argument, which is compared the same
way.

### The shape of the fix

Two guards, evaluated before the classification table is consulted:

1. The count must have been derived. The counting function signals whether it
   could read its log rather than leaving that to be inferred from its output,
   and the classification treats a derivation that did not produce a
   non-negative integer as a failure outcome naming the cause and the log path.
2. The status argument must be interpretable as an integer; one that is not is
   the same kind of failure, named as such.

Both guards produce the `fail` outcome token the script already maps onto its
existing failure reporting, so no change to `scripts/verify-font-bootstrap.sh`
is needed or permitted by this task's file set.

### The counting function's invocation

The log is handed to the counting program through its standard input rather
than as a positional argument, so a path that begins with `-` or contains `=`
cannot be taken for an option or a variable assignment. The counting program
itself — the text that decides which lines count and how they are summed — is
not edited; only how the bytes reach it, and whether an unreadable path is
reported, change. FR10's "counting rule unchanged" therefore still holds, and
AC-7 below is what pins it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Given a log path that names no existing file and a non-zero exit
      status, the classification yields the `fail` outcome, and its message
      names the log path and the fact that the executed count could not be
      derived. (FR2, FR5)
- [ ] AC-2: The AC-1 message contains neither the build-stop wording nor the
      executed-and-failed wording, and states no test count at all — in
      particular no empty count field where a number belongs. (FR5)
- [ ] AC-3: Given a log path that names no existing file and a zero exit
      status, the classification yields the `fail` outcome — never `pass`.
      (FR4, FR5)
- [ ] AC-4: AC-1 and AC-3 hold identically when the log file exists but is
      unreadable, as well as when it is absent. (FR2, FR4)
- [ ] AC-5: Given an exit-status argument that is not an integer, together with
      any log, the classification yields the `fail` outcome naming the
      uninterpretable status — never `pass` and never `warn`. (FR2, FR4)
- [ ] AC-6: The counting function reports failure to its caller, and prints no
      count on standard output, when its argument names an absent or unreadable
      path; for every readable log it reports success and prints exactly the
      integer it prints today. (FR5)
- [ ] AC-7: The derived counts are unchanged for every log shape already
      exercised: two `test result:` lines are summed, a log holding none yields
      zero, and a suite reporting zero passed and zero failed yields zero.
      (FR10 preserved)
- [ ] AC-8: A readable log whose path begins with `-`, and one whose path
      contains `=`, derive the same count as identical content at an ordinary
      path. (FR5)
- [ ] AC-9: The four already-specified outcomes are byte-for-byte unchanged:
      the same four (count, status) inputs used before still produce the same
      outcome tokens and the same messages. (FR2, FR4, FR5)
- [ ] AC-10: The helper still prints exactly one line on standard output whose
      first whitespace-delimited token is one of `pass`, `warn`, `fail`, and
      still returns success for every classified outcome including the new
      one, so the script's outcome-to-report mapping needs no change.

## Test Notes

Every criterion is exercised against the shipped helper as a real subprocess
with synthetic logs, exactly as the existing regression test already does — no
cargo, no network, no git worktree (NFR1 is unchanged by this task).

- AC-1 through AC-5: one case per assertion, so a failure names the branch that
  broke. Build the unreadable-file case by creating a file and removing its
  read permission, and skip that one case when the test runs as a user for whom
  permissions do not apply, rather than weakening the assertion.
- AC-6: drive the counting function directly and assert on both its reported
  success/failure and its standard output, since "prints nothing" and "reports
  failure" are two separate claims.
- AC-7 reuses the existing edge-case logs; it is a regression guard on the
  invocation change, not new behaviour.
- AC-8: create the log inside a temporary directory and address it by a
  relative name beginning with `-`, and separately by a name containing `=`.
- AC-9 is best expressed by leaving the existing cases untouched and letting
  them keep passing; add no duplicate of them.

TDD-awkward: none. Every criterion is a pure input/output claim about the
helper.

## Out of Scope

- Editing `scripts/verify-font-bootstrap.sh`. The new outcome uses the `fail`
  token the script already maps onto its failure reporting.
- Changing the counting program's text, or the counting rule it expresses
  (FR10).
- Changing the wording of the four already-specified outcomes (AC-9 pins them).
- Adding any cargo or test-harness flag to the reproduction command (FR7), and
  any edit to `.github/workflows/ci.yml` (FR8).
- Detecting a failed output redirection inside the script itself. An
  unwritable log is one of the ways the log becomes unreadable, and the helper
  now fails closed on all of them.
- Fixing the underlying flaky library tests.
