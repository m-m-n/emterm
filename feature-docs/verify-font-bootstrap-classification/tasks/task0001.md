# Task Plan: task0001 — Un-fetched verdict classification and its regression test

## Goal

The un-fetched scenario of the bootstrap-verification script reports what
actually happened — a build stop, an executed-but-failing suite, or a clean
pass — by classifying on the executed-test count first, and that behaviour is
pinned by an automated test that needs neither a Rust toolchain nor a network.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, FR10, NFR1, NFR2, NFR3, NFR4,
NFR5

## Scope

### Files to Create
- `scripts/verify-font-bootstrap-verdict.sh` — function definitions only: the executed-count derivation (relocated unchanged) and the new un-fetched classification decision
- `scripts/verify-font-bootstrap-verdict.test.ts` — the automated regression test, driving the shipped helper as a subprocess with synthetic logs

### Files to Modify
- `scripts/verify-font-bootstrap.sh` — load the verdict helper, drop the relocated counting function, replace the un-fetched scenario's verdict block with the outcome-to-report mapping

## Design

Read IMPLEMENTATION.md first: it owns the layer structure, the three
component contracts (Shared Components), the classification table, the
conventions and decisions D1–D7. This section adds only what is specific to
carrying them out.

### The verdict helper file

A new file holding function definitions and nothing else. Loading it performs
no work: it allocates nothing, spawns nothing, installs no exit-time hook,
reads no environment variable and requires no particular working directory.
That is the property the regression test and NFR1 depend on — the bun CI job
has no Rust toolchain and no repository-root assumption.

It holds exactly two functions:

1. The executed-count derivation, carried over from the script
   character-for-character (D6). Only its location changes.
2. The classification, whose contract and branch table are in
   IMPLEMENTATION.md. It derives the count by calling the first function,
   then selects its branch from that count before consulting the exit status.

### The script's side

Three edits, and no others:

1. Load the helper. The path is resolved relative to the script's own file
   location rather than the working directory, so the script behaves
   identically however it is invoked. A missing or unreadable helper is a
   usage-level error reported through the script's existing usage-failure
   path, not a silent continuation.
2. Remove the counting function's old definition (it now lives in the
   helper).
3. Replace the un-fetched scenario's verdict block. Where it currently tests
   the exit status and then the count, it now asks the helper for one outcome
   line and maps the outcome onto the reporting and tally helpers it already
   has, per IMPLEMENTATION.md's outcome-to-report mapping contract.

Everything else in the script stays as it is: the preconditions, the scratch
allocation, the exit-time cleanup, the isolated-tree helper, the pristine-font
check, the broken-tooling shims, the log-tail helper, the reporting and tally
helpers, the fetch-failure scenario, the already-fetched scenario, the
scenario invocation order, the summary line and the aggregate exit status.

### Comment to record the AC1 reading

The prior feature's SPEC is not edited (D5). The un-fetched scenario's comment
block is where the reading is recorded instead: that the pinned pass condition
is a non-zero executed-test count, and that a run which executed tests and
reported a failure therefore satisfies it while still being surfaced as a
warning. Keep the existing comment marking the literal reproduction command.

### The regression test

Writes synthetic captured logs to a temporary location, invokes the shipped
helper as a real subprocess with a chosen exit status and log path, and
asserts on the single outcome line. It follows the subprocess-driven
precedent already in this repository
(`plugins/emterm/hooks/scripts/notify-status.test.ts`) — see D7. It also
carries the static assertions that pin the reproduction command and the CI
call site (below), by reading the script and the workflow as text/data rather
than by executing them.

      the executed count derived from that log. (FR1, FR3)
- [ ] AC-2: The `warn` message does not contain the build-stop wording, so a
      run whose tests executed and failed is never reported as a stopped
      build. (FR3, AC1 of SPEC)
- [ ] AC-3: Given a captured log holding no `test result:` line and a non-zero
      exit status, the classification yields the `fail` outcome, and its

      FR2)

## Test Notes

**Unit-level (the bulk of the work, all against the shipped helper as a
subprocess with synthetic logs):** AC-1 through AC-7, AC-10 and AC-17. Build
each synthetic log as text in a temporary directory — a realistic cargo
summary line for the executed cases, a build-error-shaped log with no summary
line for the zero-executed cases. Drive one case per assertion so a failure
names the branch that broke.

Edge cases worth a case of their own:

- two `test result:` lines in one log (a library suite plus doctests) — the
  counts sum;
- a suite reporting zero passed and zero failed (every test ignored) — the
  derived count is zero, so the zero-executed branch applies even though the
  harness did run;
- an exit status that is not cargo's own failure status (a signal-derived
  status, for instance) together with a non-zero executed count — the
  test-failure branch still applies, and the message stays neutral about the
  cause;
- a log path holding a space or other shell-significant character — the
  helper handles it without splitting.

**Script-level (AC-8, AC-9, AC-13):** the reporting and tally behaviour can be
exercised without a build by asserting on the script's text — that the warned
branch routes through the script's own logging helper, adds to the passed
tally and emits the log tail — and by an end-to-end read of the un-fetched
verdict block. A real end-to-end run of all three scenarios needs cargo, a
network and several minutes; it belongs to the feature-wide verification
(VERIFICATION.md's manual section), not to this task's test suite.

**Static assertions (AC-11, AC-12, AC-14):** read the script as text and the
workflow as parsed data — the existing `ci-workflows.test.ts` demonstrates the
parse-as-data approach for workflow files. Assert on the reproduction command's
exact substring, on the absence of any test-thread flag anywhere in the script,
and on the CI step's exact run string. The prior feature's SPEC and the release
workflow being unmodified is a change-set observation for the verify phase; a
digest assertion on the release workflow already exists in
`ci-workflows.test.ts` and must keep passing rather than being duplicated.

**TDD-awkward:** AC-15's "no Rust toolchain on PATH" is a property of the
environment, not something the test can assert about itself without becoming
brittle. Handle it by construction — the test must not reference cargo at all
— and verify it at the feature level by the bun CI job passing.

**Test record:** the per-task test record under
`test-docs/verify-font-bootstrap-classification/` is produced by the implement
phase's standard flow; no separate authoring step is needed for FR9's record
clause.

## Out of Scope

- Adding any flag to the un-fetched scenario's cargo invocation, including a
  test-thread-count flag (FR7, D4). The known parallelism-dependent flakes are
  absorbed by the classification, not by changing the command.
- Editing `.github/workflows/ci.yml` in any way (FR8, D5).
- Editing `feature-docs/worktree-font-bootstrap/SPEC.md` (D5, assumption a7).
- Editing `.github/workflows/release.yml` (D5, assumption a5).
- Changing the fetch-failure scenario, the already-fetched scenario, the
  exit-time cleanup or the counting rule itself (FR10).
- Fixing the underlying flaky library tests. They are a separate concern; this
  task only stops them from being misreported as a font-bootstrap failure.
- Changing the summary line's shape or the aggregate exit status rule beyond
  counting a warned scenario as passed (assumption a6).
- Any change under `src-tauri/`.
