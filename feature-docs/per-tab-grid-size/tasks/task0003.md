# Task Plan: task0003 — Deferred activation reconcile against the incoming tab's display area, unified App-side resize invalidation, and observable pane Resize frames

## Provenance

- source: review
- review_round: 1
- source_ids: dbb7766a6212fb1a, 09f0e6096bbc36ee, a172de726b3cbc29,
  d39a6a9468ff892e, cfcbfae57964beb5

These five findings share one defect cluster: the activation reconcile
introduced by the merged implement pass (task0001) compares against — and
resizes to — dims computed for the OUTGOING tab, misses the App-side tracker
invalidation on two of its three call paths, and its FR4 guarantee is
asserted through a dims-only proxy that cannot observe frame emission.

## Goal

Tab activation reconciles the incoming tab exactly once, against dims
computed for the INCOMING tab's display area (after status-bar / sidebar
insets for the new active tab have settled), with the App-side reflow
invalidation applied on every path that issues a width-changing resize, and
with mux pane `Resize` frame emission directly observable in tests.

## Design

Cross-task contracts are pinned in IMPLEMENTATION.md (Shared Components:
corrected contract (d) with the enumerated frame-emission sites and the
frame-observation hook; the reconcile request/execute split; the App resize
application helper; corrected D2/D3). Implement against them; do not restate
or re-derive them.

### 1. Reconcile request/execute split (findings dbb7766a6212fb1a, 09f0e6096bbc36ee — FR3, NFR1)

Root cause: the reconcile currently runs synchronously inside the activation
paths, at a moment when `App::cell_size` still holds dims computed for the
outgoing tab. Because the persistent-sidebar inset depends on whether the
ACTIVE tab is mux-attached, a mux⇔local switch reconciles the incoming tab
to a wrong width, then the next frame's `set_grid_size` corrects it — two
resizes (and, for mux tabs, two pane `Resize` frame sets) where the
pre-feature behavior issued one.

Fix, per the finding's suggestion:

1. The three activation paths (explicit switch, close-tab fix-up, exited-tab
   reap fix-up) no longer resize anything. Each only records a pending
   reconcile request on App state.
2. A reconcile executor on App consumes the request: compare the now-active
   tab's core dims against the CURRENT `cell_size`; on mismatch, resize that
   tab through the App resize application helper (Design 2); on match, issue
   nothing and clear nothing (FR3's no-op guarantee is preserved).
3. The render pass in `window_host` invokes the executor at exactly one
   point: after the status-bar insets, the mux-sidebar inset, and any pending
   display-area resize have been applied for the frame — i.e. after
   `cell_size` has been recomputed for the NEW active tab. This is the only
   `window_host` change; the existing call convention into `set_grid_size`
   is otherwise untouched.
4. A request with no matching tab (e.g. all tabs closed) is dropped silently.
   Consecutive activations before a render pass collapse into one request —
   only the final active tab is reconciled.

Structural consequence (NFR1): the executor never runs before the inset
state for the incoming tab is settled, so correctness cannot depend on which
cell-area-affecting UI elements exist or their ON/OFF state.

### 2. App resize application helper (findings a172de726b3cbc29, d39a6a9468ff892e — FR6)

Root cause: after merge, App issues `Tab::resize` from two entry points
(`set_grid_size` and the reconcile), but the App-owned half of the D3
invalidation split (selection, pending selection anchor) is applied only in
`set_grid_size`. The close-tab and reap paths reach a width-changing resize
without any App-side clearing, and the reconcile helper's doc comment claims
a caller precondition that two of three callers do not meet.

Fix: one shared App-side application path used by BOTH `set_grid_size` and
the reconcile executor:

1. Read the target tab's pre-resize column count.
2. Invoke `Tab::resize` (which owns the clamp, the tab-side invalidation,
   and frame emission — contracts (a)-(e), untouched).
3. If the post-resize column count differs from the pre-resize count, clear
   the App-owned trackers (selection, pending selection anchor).

The reconcile executor therefore fulfils the App-side half on every
activation origin without depending on the caller having cleared anything.
Correct the helper's doc comment to describe this owned behavior instead of
the stale caller-precondition claim.

### 3. Observable pane `Resize` frames (finding cfcbfae57964beb5 — FR4)

Root cause: the "single emission site" premise cited by the current AC-5
test is false (emission also exists at mux attach/Welcome pane seeding and
at PaneCreated handling), and the test observes only core dims, so it cannot
detect frame emission at all.

Fix:

1. In tabs.rs, add a test-only (test-build-gated) observation hook that
   records every pane `Resize` control frame at the moment of emission —
   tab/pane identity plus the post-clamp dims — at ALL emission sites
   enumerated in the corrected contract (d). Release builds compile the hook
   away entirely; no behavior change outside tests.
2. Rewrite the FR4 app.rs assertion to observe recorded frames instead of
   core dims: a grid-size change with an inactive mux-flavored tab present
   records ZERO frames for that tab.
3. Add the activation-side frame assertion: a mux tab activation reconcile
   that changes dims records exactly ONE frame set (one frame per pane, at
   the incoming tab's post-clamp dims); no frame carrying outgoing-tab dims
   is ever recorded.

## Test Notes

- AC-1..AC-5 are app.rs unit tests. The reconcile executor is an App method
  the render pass calls, so tests drive it directly: request an activation
  (switch / close / reap through the public surface), settle the display
  area via `set_grid_size` with the incoming tab's dims, then invoke the
  executor and assert dims / tracker state / resize count. This mirrors the
  production ordering (activation happens inside the egui pass; the
  executor runs on the following render pass after insets settle) without
  needing a real winit window.
- AC-6 reads the tabs.rs observation hook from app.rs tests; seed the
  mux-flavored tab the same way the existing AC-5 test does. The hook is the
  ONLY new surface in tabs.rs — no production-path change there.
- Resize-count assertions ("exactly once", "no wrong-dims resize") observe
  the recorded frames for mux tabs and core-dims transitions for local
  tabs; where a direct count is impractical through the public surface, the
  frame hook is the authoritative counter.
- Updated existing tests (the AC-5 dims-proxy test and any reconcile test
  assuming synchronous activation-time resize) each carry a comment stating
  WHY the assertion moved (NFR2's "updated with justification").
- Run tests with the project command:
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib -- --test-threads=1`
  (the tabs.rs replay tests flake under parallel execution). Never `cd`
  into `src-tauri/`; never run a crate-wide `cargo fmt`.
