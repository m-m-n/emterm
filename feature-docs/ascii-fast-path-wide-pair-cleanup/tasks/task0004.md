# Task Plan: task0004 — Overflow cleanup gated on the overwritten cell, not on the table

## Goal

Restore the NFR1 per-byte budget of the ASCII write step: the overflow-table
cleanup added for FR2 must cost nothing on a byte that overwrites a cell with
no overflow content, instead of charging every printable ASCII byte an
absolute-row computation plus a hash-map probe for as long as any overflow
entry exists anywhere in the ring.

## Requirements

FR2, FR3, FR7, NFR1, NFR2

## Scope

### Files to Create

None.

### Files to Modify

- `crates/term_core/src/terminal_dispatch.rs` — the PTY-dispatch ASCII fast
  path's write step: the condition that guards its overflow-table cleanup, and
  the placement of the read that condition needs.
- `crates/term_core/src/print_handler.rs` — the print path's ASCII writer
  (`handle_print_ascii`): the same guard change, so the two ASCII writers keep
  the identical shape FR3's parity rests on.

## Design

### The defect

Both ASCII writers gate their overflow cleanup on "the overflow table is
non-empty". That predicate is a property of the whole ring, not of the cell
being overwritten. A single cluster longer than the inline cell capacity
anywhere in the scrollback keeps it true, and from then on every printable
ASCII byte pays an absolute-row computation and a hash-map lookup (a
`(column, absolute row)` key through the default SipHash hasher) before the
byte is written. NFR1 budgets the ASCII common case at one already-resident
field read plus one well-predicted branch; a per-byte hash probe is outside
that budget, and the fast path exists precisely to avoid work of this class.

### Target shape

The cleanup is gated on the overwritten cell itself, read from the cell record
the write step is about to write:

- Before the write, read the overwritten cell's overflow marker — the same
  marker the grapheme writer already tests when it decides whether to insert
  an entry, and the same cell record the pre-write width read (FR1) already
  touches, so no additional cache line is brought in.
- The absolute-row computation, the table removal and the reverse-index
  removal happen only when that marker was set. In every other case — the
  ASCII common case — the write step performs no table access and no
  absolute-row computation at all.
- Both ASCII writers use the same shape. Applying the change to only one of
  them leaves the two writers structurally divergent, which is the condition
  FR3's parity guarantee is supposed to exclude.

**Ordering constraint (the trap):** the marker must be read BEFORE the cell is
written. The ASCII write sets the cell's inline length to one byte, which
clears the marker — a marker read placed after the write is always false, the
cleanup then never runs, and FR2's regression test would be the only thing
standing between that and a silent leak of stale table entries. This is the
same ordering trap IMPLEMENTATION.md's risk table records for the pre-write
width read; both reads belong in the same pre-write step.

### Equivalence obligation

The change is behaviour-preserving only if an overflow-table entry can exist
at a position ONLY when that position's cell record carries the overflow
marker. Establish this before making the change, by checking every site that
inserts an entry and every site that relocates entries between positions
(the cell layer's grapheme write, the print path's grapheme writer, its
codepoint-merge step and its relocation-by-wrap step all insert only under
the marker; the reflow, scroll and snapshot paths move existing entries
together with the cells they belong to). If a path is found that can leave an
entry for a cell whose marker is clear, the entry-gated cleanup is NOT
equivalent: stop, leave the guard as it is, and report the finding as a plan
deviation rather than trading correctness for the budget.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR1): In both ASCII writers, the overflow-table access and the
      absolute-row computation are reachable only through the branch taken
      when the overwritten cell's own pre-write overflow marker is set; no
      table access and no absolute-row computation remains on the path a byte
      overwriting a non-overflow cell takes.
- [ ] AC-2 (FR2): A cell carrying an overflow entry that is overwritten by an
      ASCII byte through the dispatch fast path ends with no table entry and no
      reverse-index entry for its position — proving the marker read precedes
      the write. The same holds through the print path's ASCII writer.
- [ ] AC-3 (FR3, FR7): With the overflow table non-empty because of an
      unrelated cell, overwriting a non-overflow cell with ASCII leaves the
      unrelated entry and its reverse-index entry intact, and produces grid
      contents, per-cell widths and table state identical to the result of the
      same stream through the other ASCII writer.
- [ ] AC-4 (FR2, FR3): The equivalence obligation above is checked and its
      result recorded in the task's completion notes: every insertion site and
      every relocation site is listed, with the marker's state at that site, or
      the disqualifying path is named and the guard left unchanged.
- [ ] AC-5 (NFR2): The diff touches only the two files named in Scope plus
      their inline test modules; no crate manifest is edited, nothing publicly
      exported from term_core changes, and no new dependency is added.
- [ ] AC-6 (FR7, NFR2): The term_core library suite, the src-tauri library
      suite and the CLI-only check all pass, with no new warning.

## Test Notes

- AC-2 and AC-3 are unit tests in the inline module next to each writer,
  following the feature's existing convention: an explicitly constructed
  terminal core per test, input driven through the PTY-dispatch entry point,
  assertions on the observable contract (cell content, cell width, table and
  reverse-index state) rather than on internal bookkeeping.
- Reaching the fast path requires the ASCII bytes to arrive in their own
  dispatch call, at a chunk boundary with the parser ground-clean and no
  grapheme buffered — the same split-input discipline task0001's tests use.
  A test that unintentionally runs the slow path passes without proving
  anything about the fast path.
- Producing an overflow entry needs content longer than the inline cell
  capacity; producing the "unrelated entry" state for AC-3 needs that content
  at a position other than the one being overwritten.
- AC-1 is a code-shape criterion, not a behavioural one: no test can observe
  the absence of a hash probe. It is checked by reading the two write steps,
  the same way VERIFICATION.md's inspection item M2 checks the NFR1 budget.
- AC-2's ordering property is worth a deliberate check against a
  marker-read-after-write arrangement: that arrangement must fail AC-2's test.
