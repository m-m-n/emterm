# Task Plan: task0001 — ASCII fast-path wide-pair repair and overflow cleanup

## Goal

Make the PTY-dispatch ASCII fast path restore the D2 invariant on every cell
it overwrites — blanking the surviving half of a broken wide pair and
removing the overwritten cell's overflow-table entry — so its observable
result is identical to the slow ASCII print path, at no measurable cost to
the ASCII common case.

## Requirements

FR1, FR2, FR3, FR4, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `crates/term_core/src/terminal_dispatch.rs` — the ASCII fast path's
  per-byte write step gains the pre-write width read, the orphan-neighbour
  repair call and the overflow-entry removal; the NFR1 cost evaluation is
  recorded as a comment at that step; a new inline test module holds the
  scenarios below.
- `crates/term_core/src/print_handler.rs` — visibility of the orphan-neighbour
  repair entry point is raised to crate-internal, in place. No other change to
  this file: signature, body, doc comment and the three existing call sites
  stay as they are.

## Design

IMPLEMENTATION.md carries the contracts this task implements against: the
repair entry point's pre/postconditions and the in-place visibility rule
("Shared Components"), the D2 invariant, and decision D-1 (parity comes from
shared code, not duplicated logic). They are not restated here. Everything
below is specific to this task.

### What changes in the fast path

Only the branch that handles a printable ASCII byte changes, and only its
cell-write portion. The surrounding loop, the control-byte branches
(carriage return, line feed and friends, backspace, tab, bell), the
break-to-slow-path conditions and the cursor-advance/wrap logic are
untouched.

### Write-step ordering contract

The fast path's per-byte write step observes this order, which is the same
order the slow ASCII writer already observes:

1. Resolve the target cell for the current cursor position; when it does not
   resolve, do nothing (existing behaviour).
2. Read the target's current width.
3. When that width is not 1, invoke the orphan-neighbour repair entry point
   with it. When it is 1, skip the call entirely.
4. Write the ASCII byte, width 1, and the current attributes into the target.
5. Remove any overflow-table entry (and its reverse-index companion) for the
   target position, gated on the overflow table being non-empty — the same
   shape the slow ASCII writer uses.
6. Mark the row dirty and record the write as the retroactive-merge target
   (existing behaviour, unchanged).

Two properties of this order carry the correctness of the task:

- The repair decision is made from the target cell's width as it stands
  BEFORE the write, so steps 2-3 must precede step 4.
- The repair only ever mutates a neighbouring column, never the target
  column, so it cannot be clobbered by the write that follows it.

### Admission conditions stay as they are

The fix lives entirely inside the write step. The fast path's eligibility
conditions — charset state, placeholder state, the parser-ground and
empty-grapheme-buffer checks, and the per-byte classification — gain no
grid-state precondition such as "no wide cells present" (FR4). Narrowing
admission would silently move common input onto the slow path and defeat the
reason the fast path exists.

### NFR1 cost budget and where the evaluation is recorded

Budget for the ASCII common case (a width-1 cell overwritten by a width-1
character): at most one read of a field in the cell record already being
written (same cache line) plus one branch that is not taken. No allocation,
no additional pass over the input buffer, no additional per-byte call that
cannot be inlined, and no work added to the fast path's loop outside the
write step.

The evaluation itself is recorded as a comment at the fast path's write step,
mirroring the equivalent comment the slow ASCII writer already carries. It is
not written to a separate document, so it stays adjacent to the code it
describes and cannot drift out of review scope.

### Reaching the repair entry point

The repair entry point lives in the print layer and is module-private today,
so the dispatch layer cannot name it. Raising its visibility to
crate-internal is the whole of the print-layer change. Re-deriving the R1/R2
conditions inside the dispatch layer is explicitly rejected (IMPLEMENTATION.md
D-1) — the shared entry point is what makes fast/slow parity structural.

### Why the tests must split their input

The fast path is entered only at a point where the parser is in a clean
ground state and no grapheme is buffered. The slow path's parser consumes the
whole remainder of the buffer it is handed, so within a single dispatch call
that begins with non-ASCII content, every following byte — including plain
ASCII — is handled by the slow path. A test that hands the fullwidth
character and the overwriting ASCII byte to one dispatch call therefore
exercises the ALREADY-CORRECT slow path and passes without this fix.

Consequently every fast-path scenario below delivers its setup and its
overwriting ASCII byte in SEPARATE dispatch calls. This same mechanic is what
the parity scenario exploits: one dispatch call for the whole stream drives
the slow path, and the same bytes split at the boundary drive the fast path;
the two resulting grids must be indistinguishable.

The existing wide-pair tests in the print layer call the print entry point
directly and therefore never enter the dispatch fast path — they are not
evidence for any criterion of this task.

### Setups the scenarios need

- **Wide pair from a fullwidth character**: a CJK fullwidth character is
  written to the grid immediately, leaving no buffered grapheme, so the very
  next dispatch call is fast-path eligible.
- **Wide pair whose base content lives in the overflow table**: a multi-
  codepoint pictographic cluster buffers until something forces a flush.
  Delivering a control byte (or an explicit flush, as the existing print-layer
  tests do) in its own dispatch call both writes the cluster to the grid and
  empties the buffer, making the following call fast-path eligible.
- **Cursor placed on the spacer half**: the cursor-position escape sequence
  must be delivered in its own dispatch call, so that the ASCII byte that
  follows it starts a fast-path-eligible call.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR6 / TS1): After a fullwidth character is written at column
      0 by one dispatch call, a second dispatch call carrying a carriage
      return followed by an ASCII letter leaves column 0 holding that letter
      at width 1 and column 1 a blank cell at width 1 — no width-0 spacer
      remains anywhere in the row.
- [ ] AC-2 (FR1 / TS3): With a fullwidth character occupying columns 0-1 and
      the cursor positioned on column 1, a following dispatch call carrying an
      ASCII letter leaves column 1 holding that letter at width 1 and column 0
      a blank cell at width 1 — no width-2 base survives without its spacer.
- [ ] AC-3 (FR2 / TS4): When the cell the fast path overwrites carried an
      overflow-table entry, neither the overflow table nor its reverse index
      retains an entry for that position afterwards; the resulting state
      matches what the slow ASCII writer produces for the same overwrite.
- [ ] AC-4 (FR3 / TS2): For a byte stream containing a fullwidth character, a
      carriage return and an ASCII letter, a core fed the stream in one
      dispatch call and a core fed the same stream split so the ASCII tail
      begins a fast-path-eligible call end with identical grid contents,
      identical per-cell widths and identical overflow-table state.
- [ ] AC-5 (FR4, FR7, NFR1 / TS5): On a grid holding no wide cells, a
      pure-ASCII stream driven through the fast path produces the same grid as
      the same stream driven through the slow path, and every touched cell has
      width 1. The fast path's admission conditions are byte-for-byte the
      pre-change set — no grid-state precondition was added.
- [ ] AC-6 (NFR3 / TS6): Overwriting a width-0 cell at column 0 (no left
      neighbour), overwriting a width-2 base sitting in the last column of a
      row, and overwriting a width-0 cell whose left neighbour is not a
      width-2 base all complete without panic or out-of-range access, and none
      of them blanks a cell outside the overwritten cell's own row or a cell
      that is not the partner of a broken pair.
- [ ] AC-7 (NFR1): The fast path's write step carries a recorded evaluation of
      its added cost stating this task's budget — one read of a field in the
      cell record already being written plus one untaken branch on the common
      case, with no allocation, no extra pass over the input buffer and no
      non-inlinable per-byte call — and the implemented code matches that
      statement.
- [ ] AC-8 (FR7, NFR2 / TS7): The term_core library suite, the src-tauri
      library suite and the CLI-only check all pass, no crate manifest is
      modified, and nothing publicly exported from term_core changes.

## Test Notes

- All new tests are unit tests in a new inline test module in
  `terminal_dispatch.rs`, following `test/README.md`: one explicitly
  constructed terminal core per test, `<subject>_<scenario>_<expected>`
  naming, input driven through the dispatch entry point, assertions on the
  observable grid contract (cell content, cell width, overflow-table
  presence) rather than on internal-only bookkeeping.
- TDD order: AC-1's scenario is the reported break and must be written first
  and observed FAILING against the unmodified fast path — a test that passes
  before the change is exercising the slow path and is wrong (see Design,
  "Why the tests must split their input").
- AC-3's overflow setup mirrors the existing print-layer overflow tests
  (pictographic cluster whose content does not fit inline), differing only in
  that the overwriting byte is delivered through the dispatch fast path.
- AC-4 is written as a two-core comparison so parity is asserted on state, not
  on a hand-written expectation of what the state should be.
- AC-5's "no repair entered" aspect is a static property of the gating branch
  and is carried by AC-7's recorded evaluation plus review of the diff; the
  test asserts the observable equivalence rather than probing internal
  counters.
- AC-6 covers three adversarial shapes in one or more tests; the third shape
  (a width-0 cell that is combining-mark residue rather than a spacer) exists
  to prove the repair keys off the wide-pair relationship rather than width 0
  alone.
- AC-8 is a gate, not a new test: run the three commands from VERIFICATION.md.
  Re-run the term_core suite with a single test thread if unrelated
  replay/socket tests flake (`test/README.md`).
