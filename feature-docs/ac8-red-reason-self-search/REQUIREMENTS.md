# ac8-red-reason-self-search - 要件定義書

## 1. 概要

### 1.1 背景

`test-docs/ac7-red-reason-scope/task0001.tests.yaml` の AC-8 エントリの
`red_reason` は、その記録自身の本文を対象とした固定文字列検索の結果を、検索語を
本文中に引用したまま記録している。検索語が本文に含まれているため、コミット済みの
ファイルに対して同じ検索を再実行すると、記録された「一致しない」という結果は成立
しない。この記録は後続タスクが失敗を切り分けるために読む機械可読な証跡であり、
自己矛盾したまま残すと読み手を誤らせる。

### 1.2 目的

- AC-8 の `red_reason` から、再実行すると成立しない検査の記述を取り除く。
- 記録が独立に確認できた知見（2 パスの変更集合の列挙、Rust ファイル・TypeScript
  ファイルを含まないという判定）は、訂正後もそのまま残す。

### 1.3 スコープ

対象は `test-docs/ac7-red-reason-scope/task0001.tests.yaml` の AC-8 エントリの
`red_reason` スカラー 1 つのみ。同ファイルの他のキー、他のエントリ、末尾の
`notes` ブロックは変更しない。

## 2. ビジネス要件

### 2.1 ビジネス目標

| ID | 目標 |
|----|------|
| BO1 | 機械可読な証跡記録 `test-docs/ac7-red-reason-scope/task0001.tests.yaml` の AC-8 エントリが、再実行しても成立する検査だけを記録している状態にし、これを読んで失敗を切り分ける後続タスクが自己矛盾した記述に誤導されないようにする。 |
| BO2 | 記録が独立に確認した知見（2 パスの変更集合の列挙と、Rust なし・TypeScript なしの判定）を訂正によって失わない。 |

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| 後続タスク（証跡記録の読み手） | 失敗の帰属先を判断するために `test-docs/` 配下の証跡記録を読む。 |

### 2.3 期待される効果

- AC-8 の記述に、再実行すると覆る主張が残らない。
- 正確な記述は変更されずに残る。

## 3. ユースケース

本機能は生成済みの証跡記録の記述訂正であり、実行時のアクターとの相互作用を持たない
ため、ユースケースの記述は該当なし。

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 |
|----|--------|------|
| FR1 | 自己矛盾する検索記述の除去 | 記録自身の本文を検索した結果を報告する末尾の記述と、そこで引用されている検索語を取り除く。 |
| FR2 | 直接確認した性質のみの記述 | 置換後の記述は、変更集合から直接確認できる性質のみを述べる。 |
| FR3 | 2 パス列挙の保持 | 変更集合を構成する 2 つのパスの列挙を残す。 |
| FR4 | Rust なし・TypeScript なし判定の保持 | 変更集合に Rust ファイルと TypeScript ファイルが含まれないという判定を残す。 |
| FR5 | 事前観測不能の説明の保持 | 事前に変更集合を列挙できない理由と、コミット後に検証した旨を残す。 |
| FR6 | 編集範囲を AC-8 の red_reason に限定 | 変更を AC-8 エントリの `red_reason` スカラーのみに閉じる。 |
| FR7 | パース形状とスカラー形式の保持 | 編集後もファイルのキー構造と折り畳みブロックスカラーの形式を保つ。 |

### 4.2 機能詳細

#### FR1: 自己矛盾する検索記述の除去

**説明**: `test-docs/ac7-red-reason-scope/task0001.tests.yaml` の AC-8
`red_reason` の末尾の記述——記録自身の本文に対する単一ファイル表現の固定文字列検索
の結果を報告し、その検索語 2 つを本文中に引用しているもの——を取り除く。置換後の
本文は、記録自身の本文を検索した結果について何も主張しない。

#### FR2: 直接確認した性質のみの記述

**説明**: 置換後の記述は、タスクコミットの変更集合をマージベースと比較して
(`git diff --stat <merge-base>..HEAD`) 直接確認した性質のみを述べる。すなわち、
変更集合が列挙された 2 つのパスのみで構成され、Rust ファイルと TypeScript
ファイルを含まないこと。記録自身の本文では裏付けられない新しい主張は導入しない。

#### FR3: 2 パス列挙の保持

**説明**: 書き換え後の AC-8 `red_reason` は、
`test-docs/ac2-red-reason-accuracy/task0001.tests.yaml`（編集対象の記録）と
`test-docs/ac7-red-reason-scope/task0001.tests.yaml`（当該フィーチャー自身の
生成記録）の両方を引き続き名指しし、変更集合がちょうど 2 パスであることを述べる。

#### FR4: Rust なし・TypeScript なし判定の保持

**説明**: 書き換え後の AC-8 `red_reason` は、列挙された変更集合に Rust ファイルが
なく TypeScript ファイルもないことを引き続き述べる。

#### FR5: 事前観測不能の説明の保持

**説明**: AC-8 `red_reason` の冒頭——当該タスク自身のコミットはタスク実行前には
存在せず、その変更集合を事前に列挙できないこと、したがってコミット後にマージベース
と比較して検証したこと——を保持する。これにより `red_confirmed: false` と
`tests: []` が記述と整合したままになる。

#### FR6: 編集範囲を AC-8 の red_reason に限定

**説明**: 変更は AC-8 エントリの `red_reason` スカラーのみに触れる。`task_id`、
`baseline_failures`、`final_failures`、AC-1 から AC-7 までのエントリ、AC-8 の
`tests` と `red_confirmed` の値、末尾の `notes` ブロックはベースリビジョンと
バイト単位で同一。特に、43 行目と 47 行目にある `lists only` の 2 箇所は AC-4 の
`red_reason` に属し別の記録を説明しているため、変更しない。

#### FR7: パース形状とスカラー形式の保持

**説明**: 編集後もファイルは YAML パーサーでロードでき、トップレベルキーは
`task_id`、`baseline_failures`、`final_failures`、`acceptance_tests`、`notes` の
同じ順序で、`acceptance_tests` はちょうど 8 エントリ AC-1..AC-8 を持つ。AC-8 の
`red_reason` は、ファイル内の他の折り畳みスカラーと同じインデントで同じ折り畳み
ブロックスカラー導入子によって導入され、記述は英語のまま。

## 9. 制約条件

### 9.1 技術的制約

- 編集は AC-8 の `red_reason` スカラー 1 つに閉じる（FR6）。
- ファイル全体への一括置換は、43 行目と 47 行目の `lists only` を巻き込むため

  `tests: []` の根拠が失われる（EC5）。

- [ ] TS4（NFR1）: YAML のみの変更であるが、退行防止として `bun test` と
