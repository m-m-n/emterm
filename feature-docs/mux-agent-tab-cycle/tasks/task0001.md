# Task Plan: task0001 — next-agent-window mux action (native cycle behavior)

## Goal

Pressing the mux prefix followed by the configured key (default Ctrl+A)
switches the active mux window to the next window — in display order, with
wrap-around — among only the windows that have a reported agent status;
non-mux tabs and zero-qualifying situations are no-ops.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2

## Scope

### Files to Create

- (none — behavior is added to existing modules per IMPLEMENTATION.md

### Files to Modify

- `src-tauri/src/settings.rs` — add `next-agent-window` to the mux

- `src-tauri/src/agent_status_model.rs` — (if needed) read-only query:
  whether any of a given set of mux pane ids currently has a reported
  (uncleared) agent state.

## Design

The action identifier, default binding and settings contract are pinned in
IMPLEMENTATION.md (Shared Components); implement against them.

Dispatch flow, on the new action:

1. If the active GUI tab has no mux window group, stop — this is the
   existing dispatch guard; no new mechanism (FR4).
2. Obtain the group's windows in display order and, for each window,
   determine qualification: at least one of its panes has an agent-status
   entry with a reported state (Idle / Working / Blocked / Done). Cleared
   or never-reported panes do not qualify a window (FR6 assumption,
   IMPLEMENTATION.md).
3. If no window qualifies, stop (FR5).
4. Scan forward from the position after the current window, wrapping once
   through the full order with the current window considered last. Switch
   to the first qualifying window found. If that window is the current one,
   the active window stays as is (FR2 wrap rule; TS-4).

Constraints:

- Resolution is computed only at key-event time from in-memory state
  (window group order + agent-status model); no polling, timers, or cached
  qualify lists (NFR2).
- Express the resolution decision (ordered qualify flags + current index →
  optional target) in a form unit-testable without a GUI context —
  IMPLEMENTATION.md cross-task decision 2.
- Switching to the resolved target reuses the existing window-switch path
  (the same path the existing next/previous window actions use).
- All changes stay inside `gui`-gated modules (NFR1). No user-visible
  strings are expected; if one is added it follows the `crate::i18n` inline
  `t(ja, en)` convention.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The mux prefix followed by Ctrl+A triggers the new action by
      default, and the binding can be overridden through
      `settings.mux.keybinds["next-agent-window"]` like existing actions
      (FR1).
- [ ] AC-2: With several mux windows of which a subset qualifies, repeated
      invocations visit exactly the qualifying windows in display order,
      skipping non-qualifying ones (FR2, FR3 — TS-1, TS-2).
- [ ] AC-3: Invoking from the last qualifying window in display order lands
      on the first qualifying window (wrap-around, FR2 — TS-3).
- [ ] AC-4: With exactly one qualifying window, invocation lands on (or
      stays on) that window and never activates a non-qualifying window
      (TS-4).
- [ ] AC-5: With zero qualifying windows, the active window does not change
      (FR5 — TS-5).
- [ ] AC-6: With a non-mux GUI tab active, the key operation changes
      nothing (FR4 — TS-6).
- [ ] AC-7: Qualification follows the any-reported-state predicate — a
      window with at least one pane in state Idle / Working / Blocked /
      Done qualifies; a window whose panes are all cleared or unreported
      does not (FR6). The `--no-default-features` build still compiles and
      no polling is introduced (NFR1, NFR2).

## Test Notes

- TS-1 … TS-5 map to unit tests over the pure resolution decision plus the
  qualification predicate; run with the project's lib-test command
  (`CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path
  src-tauri/Cargo.toml --lib -- --test-threads=1`), tests inline in
  `#[cfg(test)] mod tests` of the touched modules.
- Predicate tests exercise the agent-status model directly: each reported
  state kind qualifies; cleared and never-reported do not; multi-pane
  windows qualify existentially.
- AC-6 (TS-6): cover at the dispatch-guard level if a test can reach it
  without a GUI context; otherwise rely on the existing guard plus the
  manual check in VERIFICATION.md (MT-2), and state that choice in the
  completion notes.
- AC-1's settings-override path: unit-test the binding lookup (default
  present when unset; user override wins). The full physical key-event
  path is covered manually (VERIFICATION.md MT-3).
