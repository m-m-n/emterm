## Design

### Fix 1: saturating first-param accumulation (high)

The first-param digit accumulation must mirror term_core's `ParamParser` semantics (`crates/term_core/src/parser_params.rs`): saturating multiply/add so an arbitrarily long digit run can never overflow. A saturated (huge) value never equals any target constant (5/6/14/16/18), so oversized parameters are preserved, never stripped, and never panic under overflow-checked builds.

### Fix 2: relax DA / DECRPM intermediates matching (medium/security)

term_core dispatches on the FIRST collected intermediate and truncates the collected intermediates at two (`MAX_CSI_INTERMEDIATES` in `crates/term_core/src/parser_types.rs`); trailing intermediate bytes never prevent a response. Mirror that exactly (verify against `csi_dispatch.rs` + the parser's intermediate collection before writing tests):

- final `c`: strip when there are no intermediates (bare DA1), or when the first intermediate is `?` or `>` regardless of trailing intermediates. First intermediate `<` or `=` (or any other) → keep.
- final `p`: strip when the first intermediate is `?` and the second is `$`, regardless of any further intermediate bytes in the raw sequence (term_core truncates to two, so it still answers). Any other shape → keep.
- finals `n` / `t`: unchanged (term_core requires no intermediates there; current behavior already matches).

The updated SPEC.md "Strip decision" table (already corrected) is the normative statement; the code cross-references `csi_dispatch.rs` as the SSOT.
