# Task Plan: task0002 — Report-path gate, tracking-session discard, and notch-rule deduplication

## Provenance

- source: `review`
- review_round: 1
- source_ids: `ae089e04bcb3fa0f`, `9d6f3c3e77ff8649`, `071c856f96b7b56d`,
  `b28097f0714fe6f1`, `56dfd61c2174fc9e`

All five findings sit on the same unit — the report-path wheel accumulator
as wired across the decision layer, the conversion layer and the wheel
handler. They share one root cause family (the accumulator's write-sites and
reset mechanism are not confined to the report path) and they defend the same
acceptance criteria (SPEC AC-7, AC-8, AC-9, AC-10), so they are one task.

## Goal

The report-path wheel accumulator is written only by events that actually
report, is discarded at the moment a tracking release is observed rather than
by a latch a later event can consume, and the whole-notch conversion rule
exists in exactly one place that the production path runs through — restoring
SPEC AC-7, AC-8, AC-9 and AC-10, which the merged implementation of task0001
satisfies only at the decide/apply seam and not on the production wiring.

## Requirements

FR1, FR4, FR5, FR6, FR7, NFR3, NFR4

None.

## Design

The cross-task contracts this task adds or amends — the gated report step, the
amended accumulator-store write rule, and the amended discard signal — are
pinned in `feature-docs/wheel-report-fraction-accum/IMPLEMENTATION.md`
(Shared Components, and decisions D9 / D10 / D11 which refine D1, D2 and D6).
This section adds only what is specific to carrying them out.

### 1. The accumulator is written only by a reporting event

Today the wheel handler folds the delta and stores the fraction back on every
event that reaches the wheel path, with no reference to what the outcome
decided. Two dispositions therefore corrupt the accumulator:

- a grid-rejected event, whose record updates are the default bundle
  precisely so that nothing changes (FR6 / AC-8);
- a local-arm event — in particular the scrollback arm taken on a
  tracking-active modifier wheel — whose whole point is that the report path
  did not consume it (FR7 / AC-10).

Required behaviour: the report accumulator is read, folded and written back
**only** when the applied outcome's disposition is a report. On every other
disposition the accumulator, and the per-gesture record value as a whole, are
left bit-identical and the notch count driving the write is zero. The
report-ness of the outcome is already fully determined by the decision layer;
the host reads it off the outcome (or off the outcome-application step's
output, which receives report bytes for exactly that disposition) and never
re-derives it from the modifiers, the tracking bits or the delta.

### 2. The step is a plain-value unit

NFR4 requires this to be assertable with no `WindowHost`, no winit event loop
and no GPU surface, and the review found that the decide/apply seam alone
cannot see the defect. So the per-event report step becomes its own unit over
plain values: given the applied outcome's report-ness, the current per-gesture
record value and the event's line delta, it yields the notch count to report
and the record value to store back. The wheel handler becomes a caller of that
unit and holds no branch of its own on this path.

Ordering inside the unit is load-bearing and unchanged from task0001: the
outcome's record updates are applied first, the delta is folded into the
resulting (possibly just-discarded) fraction second.

### 3. Discard on observing inactive, not on detecting reactivation

Today reactivation is detected by a `became_active` latch read from the stored
last-observed tracking state, and that latch is folded into the shared reset
expression. This is wrong twice over:

- the latch is consumed by any accepted pointer event that records a
  tracking-active observation, so an intervening motion or press between the
  release and the next wheel event swallows it and the stale remainder
  survives (SPEC AC-7);
- the shared reset expression also drives the cell-change cache reset and the
  gesture-ownership clear, so the extra term clears records the feature
  declared out of scope — a mid-drag reactivation drops a recorded report
  owner and the drag's release then reports nothing.

Required behaviour: the outcome-application step discards the report
accumulator at the point it records an observed tracking state of *inactive*.
No state needs to be carried to a later event, so no latch is read and the
shared reset expression returns to its two original observations (no tracking
mode active, or the active tab differs from the record's tab marker). The
stored last-observed-tracking-state field then has no remaining reader; do not
leave it in place as dead state.

This keeps the residual case VERIFICATION.md already accepts — a release and a
re-enable with zero intervening accepted pointer events — and no other case.
A grid-rejected event still records nothing and therefore still discards
nothing, which is what FR6 requires.

### 4. One implementation of the notch rule

The stateless whole-notch conversion currently restates the accumulating
unit's non-finite rejection, float-domain saturation, toward-zero truncation
and sign application, has no production caller, and carries a dead-code
allowance. The rule must exist once: the stateless conversion is expressed in
terms of the accumulating unit invoked from a zero carried fraction. Its
observable results are identical for every input, so the pre-feature
expectations that pin it pass unedited — and for the first time they exercise
the rule the production path actually runs.

Keep the stateless conversion's name and visibility: those expectations are
AC-9's regression evidence and re-pointing them is out of scope.

### 5. The cap-separation scan is bounded on both sides

The scan that proves the two accumulators reference only their own cap
constant closes the alternate-scroll region at a following function marker but
leaves the report-path region open to the end of the file, which pulls the
file's own test module into the scanned text. Close it the same way the
alternate-scroll side is closed: locate the next item definition after the
accumulating unit and end the region there, failing loudly if that marker is
absent.

### Points where this task must not drift

- The decision units stay pure functions of their plain inputs. The delta
  magnitude does not become visible to them, and no record is mutated inside
  them (NFR1). Widening the wheel decision's inputs to carry the delta is
  explicitly out of scope — SPEC NFR1 forbids it, and it would require a SPEC
  change, not a rework task.
- The rejected-event branch keeps returning the default record updates, and
  every field of the record updates keeps a default that means "change
  nothing".
- The two clamp layers stay two, referencing the same report cap constant,
  neither aliased to nor derived from the alternate-scroll cap. Collapsing the
  stateless conversion onto the accumulating unit is a deduplication of one
  layer's rule, not a removal of the second layer.
- The alternate-scroll accumulator, its screen-switch zeroing on both arms,
  its deliberate non-mutation on the tracking-active modifier branch, and its
  own cap constant are untouched.
- No new host state field is added; the per-gesture record round-trip in the
  host module is unchanged, which is why that module is absent from this
  task's file set.

## Acceptance Criteria (MANDATORY)

Each criterion names the SPEC acceptance criterion it restores. Every one is
assertable over plain values, with no `WindowHost`, winit event loop or GPU
surface.

- [ ] AC-1 (restores SPEC AC-8 / FR6): For a wheel event the grid-ownership
      gate rejects, the per-event report step yields a zero notch count and
      returns the per-gesture record value bit-identical — the report
      accumulator included — for a delta large enough that folding it would
      have crossed a notch boundary. Asserted over the per-event step unit,
      not only over the decision-and-apply pair.
- [ ] AC-2 (restores SPEC AC-10 / FR7): For a wheel event whose outcome names
      a local arm — both the scrollback arm reached with a tracking mode
      active and a modifier held, and the arrow-translation arm — the
      per-event report step yields a zero notch count and leaves the report
      accumulator bit-identical, for a delta large enough that folding it
      would have crossed a notch boundary. The alternate-scroll accumulator's
      own behaviour on those arms is unchanged.
- [ ] AC-3 (FR1, FR2 regression): For a wheel event whose outcome is a
      report, the delta is folded exactly once and the returned fraction is
      stored exactly once; the notch count the duplication step receives is
      the folded unit's output, and a run of sub-notch deltas still reports
      exactly at the crossing event.
- [ ] AC-4 (restores SPEC AC-7 / FR5): A remainder accumulated while tracking
      is active is discarded by the first accepted pointer event that observes
      tracking inactive, whatever kind of event that is, and stays discarded
      across any number of intervening accepted pointer events. In particular,
      the sequence "owner-recorded release observes tracking inactive →
      tracking re-enabled → an accepted motion or press → wheel event" leaves
      the wheel event accumulating from zero. The existing test that covers
      only "release immediately followed by a wheel event" is extended, not
      relied upon as sufficient.
- [ ] AC-5 (FR5 scope boundary): Discarding the report accumulator for a
      tracking-session boundary clears neither the cell-change cache nor any
      gesture-ownership slot. Concretely: a press that records a report owner,
      followed by tracking being toggled off and back on and observed by
      intervening events, still leaves that owner recorded, so the drag's
      release still produces its report.
- [ ] AC-6 (restores SPEC AC-9 / FR1, FR4, NFR3): The pre-feature
      notch-conversion expectations pass unedited, and the function they
      exercise produces its result through the same rule implementation the
      production wheel handler runs — there is exactly one place in the
      conversion layer that rejects a non-finite delta, saturates in the float
      domain, truncates toward zero and applies the sign. No dead-code
      allowance remains on that function.
- [ ] AC-7 (restores SPEC AC-10): The cap-separation source scan bounds its
      report-path region at a located following-item marker and fails with a
      clear message if that marker is absent, exactly as the alternate-scroll
      region already does; the scanned report-path region does not contain the
      scanned file's test-module marker.

## Test Notes

- Write the tests first. Each of AC-1, AC-2, AC-4, AC-5 and AC-7 must fail
  against the current merged implementation before any production change —
  if one of them passes unchanged, the test is not yet pointed at the defect
  the review found.
- Unit level — AC-3, AC-6, AC-7. AC-6 is satisfied by the existing
  expectations continuing to pass plus the structural single-implementation
  property; do not add a parallel copy of those expectations against the
  accumulating unit.
- Step level — AC-1, AC-2. These need the per-event report step to be callable
  over plain values (Design §2). Build the record value directly, construct
  the rejected and local-arm outcomes through the decision layer so the test
  keeps exercising the real dispositions, and assert the *whole* record value
  is unchanged, not only the accumulator field.
- Sequence level — AC-4, AC-5. These are multi-event sequences over a record
  value carried by hand across calls. For AC-4 assert the intervening-event
  ordering explicitly, with at least one accepted non-wheel event between the
  release and the wheel event. For AC-5 assert the gesture owner survives and
  that the release still reports — asserting only "the owner slot is
  non-empty" understates it.
- Re-point, do not delete, the existing reactivation test: the behaviour it
  named is still required, but it is now delivered by the discard at the
  inactive observation rather than by a reset flag on the later wheel event,
  so its assertions move from the outcome's reset flag to the accumulator's
  value.
- Edge cases worth covering beyond the criteria: a rejected event arriving
  mid-run of sub-notch deltas (the run must resume exactly where it was, not
  restart and not skip); a local-arm event arriving mid-run (same); a tab
  change and a tracking release observed by the same event (one discard, not
  a double-discard that loses the event's own delta).
- The task is done when the project's build command and its full library test
  command both pass, with no pre-existing test edited except by addition or by
  the re-pointing named above.

## Out of Scope

- Making the delta magnitude visible to the decision layer, or otherwise
  moving the fold inside the decide/apply seam. SPEC NFR1 fixes the wheel
  decision's inputs to the event kind; changing that needs a SPEC change, not
  a rework task.
- Any behavioural change to the alternate-scroll path, its accumulator, its
  screen-switch zeroing or its cap constant.
- Collapsing the two clamp layers into one, or sharing a constant between the
  report path and the alternate-scroll path.
- Closing the accepted residual case of SPEC AC-7 (a tracking release and
  re-enable with zero intervening accepted pointer events) — VERIFICATION.md
  accepts it and it remains accepted.
- Mirroring the alternate-screen reset onto the report accumulator (SPEC
  assumption A-5, IMPLEMENTATION.md D7).
- Adding a host state field, changing the per-gesture record round-trip, or
  touching any file outside this task's file set.
- Tuning sensitivity or normalization of the pixel-delta to line conversion;
  adding logging, metrics or settings for the wheel path.
