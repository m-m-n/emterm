# Task Plan: task0001 — Report-path wheel fraction accumulator

## Goal

Sub-notch wheel deltas on the mouse-report path accumulate across events until a
whole notch is available and are then reported, instead of being floored to zero
and discarded — with the carried fraction confined to its tab and tracking
session, and the existing two-layer notch cap preserved.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/window_host/input_translate.rs` — add the report-path
  accumulate-and-consume unit (non-finite rejection, sign-preserving whole-notch
  consumption, float-domain saturation at the report cap); leave the existing
  notch conversion, the alternate-scroll helper and both cap constants
  behaviourally unchanged
- `src-tauri/src/window_host/mouse_report.rs` — carry the report accumulator in
  the per-gesture mouse-report records, zero it in the existing reset branch of
  the outcome-application step, and make the tracking-active observation
  reportable through the outcome so an inactive-to-active transition is visible;
  the decision units stay pure and the rejected-event branch keeps returning the
  default record updates
- `src-tauri/src/window_host/mod.rs` — extend the host-side round-trip of the
  mouse-report records so the new field survives it; do not add a second
  free-standing accumulator field and do not touch the alternate-scroll
  accumulator
- `src-tauri/src/window_host/pointer_routing.rs` — wire the wheel handler to the
  accumulate-and-consume unit: read the stored fraction, fold the delta, write
  the fraction back, drive the report from the consumed notch count and derive
  the report direction from its sign; leave the duplication cap and all three
  alternate-scroll arms unchanged
- `src-tauri/src/window_host/tests.rs` — add the accumulation, guard, cap,
  reset and invariance tests; keep the existing notch-conversion expectations
  passing unmodified

## Design

Cross-task contracts (the accumulate-and-consume unit, the accumulator store,
the reset signal) and the decisions D1–D8 are pinned in
`feature-docs/wheel-report-fraction-accum/IMPLEMENTATION.md`. This section adds
only what is specific to carrying them out.

### Per-event flow on the report path

1. The host samples the tracking-mode bits from the active tab, as it already
   does on every pointer event.
2. The decision layer decides the event: whether it reports, which tab it
   reports for, and whether the per-gesture records must be reset. It does not
   see the delta magnitude and mutates nothing.
3. The host applies the outcome. In the branch that already resets the
   per-gesture state, the report accumulator is zeroed too.
4. The host reads the (possibly just-zeroed) carried fraction and calls the
   accumulate-and-consume unit with it and the event's line delta.
5. A non-finite delta returns zero notches and the carried fraction unchanged;
   the host stores nothing and writes nothing to the PTY.
6. Otherwise the host stores the returned fraction back and, when the returned
   notch count is non-zero, emits that many repetitions of the report payload
   for the direction matching the count's sign, through the existing duplication
   step with its own independent cap.

Step 3 must precede step 4 — the resetting event's own delta belongs to the new
session, not the old one. The existing call order already gives this; keep it.

### Points where this task must not drift

- The decision layer stays a pure function of its plain inputs: no record is
  mutated inside it, and anything the host must change travels back in the
  outcome. Widening its inputs to include the delta magnitude is out of scope
  and would break that property.
- The rejected-event branch keeps emitting the default record updates. Any new
  field added to the record updates must have a default that means "change
  nothing", so that branch stays byte-invariant without extra code.
- The duplication step keeps deriving both its preallocation size and its
  repetition bound from the same capped value, so the two cannot diverge.
- The alternate-scroll accumulator, its screen-switch zeroing on both arms, its
  deliberate non-mutation on the tracking-active modifier branch, and its own
  cap constant are all untouched.

### Observing a tracking-session boundary

Zeroing on an event that observes tracking inactive covers the release. To also
cover a release-and-re-enable whose inactive phase was observed by some pointer
event but not by a wheel event, the last observed tracking-active state is kept
beside the record's tab marker and an inactive-to-active transition triggers the
same reset. The state is written only by the outcome-application step, never by
the decision units and never directly by the host (IMPLEMENTATION.md D2). A
release and re-enable with no intervening pointer event at all is not observable
and is out of scope — see IMPLEMENTATION.md Open Questions.

## Acceptance Criteria (MANDATORY)

The numbering matches the SPEC's acceptance criteria one-to-one.

- [ ] AC-1: A run of same-direction sub-notch deltas whose running sum reaches
      one notch produces exactly one notch of report bytes at the crossing
      event, and no PTY write at any earlier event in the run.
- [ ] AC-2: The leftover fraction is retained across events and is
      sign-preserving; after a delta that consumes one notch and leaves a
      remainder, an opposite-direction delta nets against that remainder instead
      of restarting from zero, and the emitted direction matches the sign of the
      notch count consumed.
- [ ] AC-3: A non-finite delta (not-a-number, positive infinity, negative
      infinity) produces no report and leaves the accumulator bit-identical; a
      following finite delta behaves exactly as if the non-finite event had
      never arrived — in particular a positive infinity followed by a negative
      infinity does not silence the report path.
- [ ] AC-4: For every delta value tested, including the floating-point extremes
      and an accumulator pre-loaded near the cap, the notch count handed to the
      duplication step has magnitude at most the report cap, saturated while
      still a floating-point value ahead of the conversion to an integer count.
- [ ] AC-5: The duplication step still caps independently: asked for a count far
      above the cap it emits exactly the cap's worth of repetitions and
      allocates for no more.
- [ ] AC-6: A remainder accumulated while one tab is active contributes nothing
      to any report emitted after the active tab changes; the first wheel event
      on the new tab reports exactly what it would have reported from a zero
      accumulator.
- [ ] AC-7: A remainder accumulated while tracking is active is discarded once
      tracking is released, and re-enabling tracking starts accumulation from
      zero — the first wheel event of the new tracking session reports exactly
      what it would have reported from a zero accumulator.
- [ ] AC-8: A wheel event rejected by the grid-ownership gate advances nothing
      and resets nothing: the accumulator and the whole per-gesture record value
      are unchanged across the event, and the outcome's record updates equal the
      default value.
- [ ] AC-9: Whole-notch report behaviour is unchanged — the existing
      notch-conversion expectations (signed whole counts, sub-notch zero,
      non-finite zero, cap boundaries, cap sweep) still hold without editing
      them.
- [ ] AC-10: The alternate-scroll path is unchanged: its accumulator keeps its
      screen-switch zeroing, keeps being left untouched on the tracking-active
      modifier branch, and keeps its own cap constant, which is neither aliased
      to nor derived from the report cap.

## Test Notes

- Every criterion is reachable as a plain-value test: no window, no event loop,
  no GPU surface. Write the tests first; a criterion with no failing test before
  the change is not yet under contract.
- Unit level — AC-1, AC-2, AC-3, AC-4, AC-5, AC-9, AC-10. These exercise the
  accumulate-and-consume unit and the duplication step directly over values.
- Seam level — AC-6, AC-7, AC-8. These exercise the decision layer's outcome and
  the outcome-application step over constructed record values; they need no
  host. For AC-6 assert both halves: that the outcome carries the reset and the
  new tab marker, and that applying it zeroes the accumulator. For AC-8 assert
  the record value is unchanged as a whole, not just the accumulator field.
- Edge cases worth covering beyond the criteria as written: a delta that lands
  exactly on a notch boundary (the remainder must be zero, not a denormal
  leftover); an accumulator holding a near-one magnitude when a same-direction
  delta arrives; a long run of alternating sign at sub-notch magnitude, which
  must never emit anything.
- AC-4 is the awkward one for a plain example-based test: cover it as a sweep
  over a fixed list of extreme and near-cap deltas with the cap asserted as a
  post-condition of every case, rather than as one hand-picked value.
- The task is done when the project's build command and its full library test
  command both pass with no pre-existing test edited except by addition.

## Out of Scope

- Any behavioural change to the alternate-scroll path or to the
  tracking-disabled scrollback path.
- Mirroring the alternate-screen reset onto the report accumulator (SPEC
  assumption A-5).
- Collapsing the two clamp layers into one, or sharing a constant between the
  report path and the alternate-scroll path.
- Making the delta magnitude visible to the decision layer.
- Tuning the sensitivity or normalization of the pixel-delta to line conversion.
- Adding logging, metrics or settings for the wheel path.
