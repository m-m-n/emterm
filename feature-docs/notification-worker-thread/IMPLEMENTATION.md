# Implementation Plan: notification-worker-thread

## Overview

デスクトップ通知の同期 D-Bus ラウンドトリップ 2 件を、winit/egui のイベントループ
スレッドからシンクが所有する専用ワーカースレッドへ移す。`NotificationSink` トレイト
境界とプロデューサ呼び出し箇所は不変のまま、本番シンク `NotifyRustSink` の内部だけを
境界付きキュー + ワーカーの構成に置き換える。

## Technology Stack

- **Language**: Rust（既存の `src-tauri` クレート内に閉じる。新規クレート・新規モジュール
  ファイルを作らない）
- **crossbeam-channel 0.5** — 境界付きキュー。`src-tauri/Cargo.toml` の
  「CLI-shared dependencies（常時ビルド）」ブロックに既に存在する。標準ライブラリの
  同期チャネルでも要件を満たせるため、実装者はどちらを採ってもよい
- **notify-rust 4** — 通知送出（Linux は D-Bus、Windows はトースト）。既存の
  `gui` フィーチャー配下のオプション依存
- **std のスレッド API** — ワーカーの起動と join ハンドル

### 依存ライセンス（新規依存の有無）

**本フィーチャーは新規依存を 1 件も追加しない。** 使用するのはすべて
`src-tauri/Cargo.toml` に既存のもの。参考として既存分のライセンスを記録する
（プロジェクトは MIT）。

| 依存 | ライセンス | 新規か |
|------|-----------|--------|
| crossbeam-channel 0.5 | MIT OR Apache-2.0 | 既存（追加なし） |
| notify-rust 4 | MIT OR Apache-2.0 | 既存（追加なし） |

## Layer Structure

```
プロデューサ層（無変更）
  App::notify / NativeCallbacks の OSC 9 / タブ活動 /
  maybe_notify_agent_transition / リンク処理
        │  呼び出しスレッド = winit/egui イベントループ
        ▼
NotificationSink トレイト境界（宣言はバイト単位で不変）
        ▼
NotifyRustSink 投入側（send）
        │  ノンブロッキング投入のみ。ここから先は別スレッド
        ▼
境界付きキュー（容量 8・満杯時ドロップ・ドロップ観測）
        ▼
ワーカースレッド 送出側
  redaction → capability 照会 → エスケープ → 送出 → ログ
        ▼
notify-rust（Linux: D-Bus / Windows: トースト）
```

依存方向は上から下の一方向のみ。ワーカー側は `App` もプロデューサ層も参照しない。
`callbacks` モジュールは `src-tauri/src/lib.rs` で `#[cfg(feature = "gui")]` 配下に
あるため、この構成は CLI 専用ビルドには一切含まれない（NFR5 はこの既存の配置に
乗ることで満たされる。新しいフィーチャーゲートを足さない）。

## Shared Components

本フィーチャーは task0001 の 1 タスクで構成される。下表は複数タスク間の共有ではなく、
**review / verify フェーズが照合する境界の定義**として置く。

| Component | Responsibility | Contract (pre/postcondition) | Used by tasks |
|-----------|----------------|------------------------------|---------------|
| `NotificationSink` トレイト | OS 通知面の抽象 | 宣言は `src-tauri/src/callbacks.rs:191-193` の現行のままバイト単位で不変。受け手を借用し、タイトルと本文の 2 つの文字列参照を受け取り、値を返さない。実装は複数スレッドから共有可能であること。事後条件: 呼び出しスレッドをブロックしない（本フィーチャーで本番実装が満たすようになる性質であり、宣言そのものは変えない） | task0001（不変性の維持のみ） |
| `NotifyRustSink` | 本番シンク | 事前条件: なし。構築後は必ずワーカーが 1 本起動済み（遅延起動しない）。事後条件: 送信側とワーカーの join ハンドルを所有し、ドロップ時に境界付きシャットダウンを行う。プロセスグローバルな状態を持たない | task0001 |
| 境界付き投入コンポーネント | 容量 8 の投入とドロップ観測 | 事前条件: なし。事後条件: 空きがあれば投入して成功を返す。満杯なら投入せずドロップして失敗を返す。いずれの場合もブロックしない。ドロップ時は D1 の武装状態に従い、エピソード先頭でのみ警告を 1 件出す。notify-rust の型に依存せず、D-Bus 接続なしで単体検証できること（NFR4） | task0001 |
| ワーカー本体 | 送出ループ | 事前条件: 受領した (タイトル, 本文) の組。事後条件: 受領値に対する redaction → capability 照会 → エスケープ判定 → 送出 → 成功/失敗いずれか 1 件のログ、をこの順で 1 通知につき 1 回行う。送信側がすべてドロップされたらループを抜けてスレッドを終える | task0001 |

## Conventions

- **配置**: 新規モジュールファイルを作らず、変更は `src-tauri/src/callbacks.rs` の中に
  閉じる。テストは `src-tauri/src/callbacks/tests.rs`。これは実 D-Bus 接続なしで
  検証できるよう `escape_for_send` を同ファイル内の私有関数として切り出した既存の
  前例（`src-tauri/src/callbacks.rs:263-277`）に合わせたもの。
- **ログ**: 既存 2 記録のリテラル接頭辞（`notify-rust dispatched: ` /
  `notify-rust failed: `）は一切変えない。新設するドロップ観測は `log::warn!` で出す
  — `.claude/rules/debugging-constraints.md` の通り、リリースビルドに残る最下位
  レベルが `warn` であるため。
- **エラー方針**: 送出失敗は呼び出し元に伝播しない。シンクの外に出るのはログのみで、
  戻り値の形は変わらない。いかなる失敗経路でもパニックさせない。
- **定数**: キュー容量とシャットダウン期限は、意味の分かる名前を付けた定数として置く
  （呼び出し位置に数値を直接書かない）。どちらも調整可能な値であり、構造上の
  確定事項ではない。
- **cfg の範囲**: 既存の `#[cfg(unix)]` ゲートは capability 照会とエスケープ判定に
  限定したまま据え置く。投入・受信・送出というディスパッチ経路そのものには cfg 分岐を
  置かない（FR9）。

## Cross-task Design Decisions

### D1: 飽和エピソードと警告の武装

「飽和エピソード」をキューが満杯になってから再び投入が成功するまでの一区間と定義し、
警告の出力可否を表す**武装状態**を 1 つ持つ。

1. 初期状態は武装済み。
2. ドロップが起き、かつ武装済みなら、警告を 1 件出して武装を解除する。
3. ドロップが起き、武装が解除されているなら、何も出さない。
4. 投入が成功したら武装し直す（エピソードの終了）。

**複数プロデューサが同時にドロップしても、エピソード先頭の警告はちょうど 1 件**で
なければならない（AC5）。武装状態の確認と解除は不可分に行う必要がある。プロデューサは
OSC 9・タブ活動・エージェント状態・リンク処理から来るため、同一スレッドとは限らない。

**理由**: キューが捌けない停滞ではドロップが連続する。ドロップごとに警告を出すと
`emterm.log` が埋まる。エピソード単位に落とすと、停滞の開始は必ず記録に残りつつ、
記録量は停滞回数に比例するだけになる。

### D2: シャットダウンの境界付き期限

`Drop` は送信側を落としてからワーカーの終了を待つが、待つ時間には上限を置く。
**期限は 200 ms 以下の名前付き定数**とし、超過したら join を諦めてスレッドを
デタッチする。

**理由**: 通常の終了ではワーカーは受信待ちで止まっているため即座に join できる。
D-Bus 呼び出しで固まっている場合、待ち続けるとプロセス終了がハングする。SPEC は
「短い境界付き待機」としか定めていないため、本計画で検証可能な数値に確定させた
（調整可能）。テスト側の判定は CI のばらつきを踏まえて余裕を持った上限で行う
（VERIFICATION.md TS4 / TS8 参照）。

### D3: capability 照会の位置と鮮度

capability 照会はワーカー本体で行い、**通知ごとにちょうど 1 回**、キャッシュせずに
実行する。その単一の結果がタイトルと本文双方のエスケープ判定を駆動する
（fail-closed の意味論は現行のまま）。

**理由**: 照会もラウンドトリップであり、これを呼び出しスレッドに残すと目的を
達しない。一方でキャッシュすると、通知デーモンの再起動で capability が変わった際に
古い判断でエスケープを省く経路ができてしまう。送出ごとの鮮度は維持する（FR3）。

### D4: redaction のタイミング

redaction は**受領したままの値**に対して、ワーカー本体の先頭で行う。エスケープ後の
値から導出してはならない。

**理由**: エスケープゲートが値を差し替えた後に redact すると、同じ通知に対する
ディスパッチ記録と後続のレートリミット抑止記録とで別々の診断 ID が付き、
実行内の相関が壊れる（既存コードのコメントが述べている不変条件）。

### D5: テスト時に起動される本番ワーカー

実 `App` を構築するテストは、本番シンクを構築するため本番ワーカーを 1 本起動し、
テスト終了時に即座にドロップする（`src-tauri/src/app/tests/agent_status.rs:49` が
テストシンクで差し替えるのは `App` 構築の**後**であるため）。D2 の境界付き join が
あるので挙動上は無害だが、**ドロップ経路が `cargo test` 下で健全であり続けること**
自体が要件である（SPEC A9）。テストで通知が 1 件も送られない場合でも、構築直後の
ドロップが期限内に戻ることを明示的に検証する。

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| ワーカーが D-Bus 呼び出しで固まりプロセス終了がハングする | 中 | 高 | D2 の境界付き join と期限超過時のデタッチ。TS4 / TS8 で期限内復帰を検証 |
| 武装状態の確認と解除が分割され、同時ドロップで警告が 2 件以上出る | 中 | 中 | D1 で不可分性を契約として明記。TS3 で単一エピソードの記録件数を検証 |
| redaction をエスケープ後の値から導出してしまう回帰 | 中 | 中 | D4 を明記し、既存の redaction テスト（TS5）を無変更で通す |
| capability 照会をワーカー側でキャッシュしてしまう最適化 | 低 | 高（セキュリティ） | D3 を明記。既存 fail-closed テスト（TS5）を無変更で通す |
| 容量 8 のキューでバースト時に通知が落ちる | 中 | 低 | 仕様上の許容（FR5）。エピソード単位の警告で可観測にする（FR6） |
| テストごとに本番ワーカースレッドが起動し `cargo test` が不安定化する | 低 | 中 | D5 / TS8 でドロップ経路の健全性を検証。ワーカーは受信待ちのみで D-Bus に触れない |

## Open Questions

- [ ] D2 の期限値（200 ms 以下）は SPEC が数値を定めていないため本計画で置いた値。
      実機でのアプリ終了に体感できる遅延が出るなら短縮する。
- [ ] 容量 8（SPEC A3）は調整可能な定数という前提。運用でドロップ警告が頻出するなら
      見直す。本フィーチャーでは 8 のまま実装する。
