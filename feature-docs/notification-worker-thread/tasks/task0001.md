# Task Plan: task0001 — 通知シンクのワーカースレッド化

## Goal

`NotifyRustSink` を、容量 8 の境界付きキューと専用ワーカースレッドを所有する構造に
置き換え、`send` がイベントループスレッド上で D-Bus I/O を一切行わずに戻るようにする。
`NotificationSink` トレイト境界とプロデューサ呼び出し箇所は変えない。

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, FR10, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

なし。

### Files to Modify

- `src-tauri/src/callbacks.rs` — 本タスクの主たる変更先。NotifyRustSink をユニット
  構造体から「境界付きキューの送信側 + ワーカーの join ハンドル」を所有する構造体へ
  変える。構築時にワーカーを起動するコンストラクタ、投入のみを行う送信メソッド、
  境界付き join によるドロップ処理、ワーカー本体の送出ループ、D-Bus 非依存で
  検証できる投入コンポーネントを置く。NotificationSink トレイト宣言（:191-193）と
  redact_notification / escape_for_send / escape_body_markup /
  body_markup_absence_confirmed の各関数の中身は変えない。
- `src-tauri/src/callbacks/tests.rs` — 投入・ドロップ・警告の武装・シャットダウンの
  ユニットテストを追加する。既存テスト（TestSink 定義、レートリミット、redaction、
  escape_for_send / fail-closed capability の各テスト）は一切書き換えない。
- `src-tauri/src/app/mod.rs` — :574 の本番シンク構築を、ユニット構造体のリテラルから
  コンストラクタ呼び出しへ変える 1 箇所のみ。App::notify（:836）、
  notification_sink フィールドの型と宣言（:402-407）、:646 の構造体リテラルへの
  移動は変えない。

## Design

### 構成要素と責務

| 要素 | 責務 |
|------|------|
| 投入コンポーネント | 容量 8 の境界付きキューへのノンブロッキング投入、満杯時のドロップ、ドロップ警告の武装管理。notify-rust の型に依存せず単体で検証できること |
| `NotifyRustSink` | 投入コンポーネントとワーカーの join ハンドルを所有する。構築でワーカーを起動し、`send` は投入へ委譲し、ドロップで境界付きシャットダウンを行う |
| ワーカー本体 | 受信ループ。1 通知ごとに redaction → capability 照会 → エスケープ判定 → 送出 → ログを行う |

契約（事前条件・事後条件・武装状態の規則・シャットダウン期限）は IMPLEMENTATION.md の
Shared Components と D1 / D2 / D3 / D4 / D5 に定義済み。ここでは再掲しない。

### 送出経路（ワーカースレッド上）

1. キューから (タイトル, 本文) を 1 件受け取る。
2. **受領したままの値**に対して redaction を行い、結果を保持する（D4）。
3. capability を 1 回照会する（キャッシュしない、D3）。
4. その単一の結果でタイトルと本文双方のエスケープ判定を駆動する。既存の
   fail-closed 判定ロジックをそのまま使う（新しい判定を書かない）。
5. 通知を送出する。
6. 成功なら `notify-rust dispatched: ` にステップ 2 の redaction 結果を続けて
   `log::debug!` で、失敗なら `notify-rust failed: ` にエラーを続けて `log::warn!` で
   出す。接頭辞のリテラルは既存のまま。
7. 1 に戻る。送信側がすべて落ちていたらループを抜けてスレッドを終える。

ステップ 3-4 は既存どおり `#[cfg(unix)]` の配下に置く。ステップ 1・5・7 には
cfg 分岐を置かない（FR9）。

### 投入経路（呼び出しスレッド上）

1. 受け取った 2 つの文字列参照から、キューに載せる所有値の組を作る。
2. 空きがあれば投入して戻る。このとき武装状態を武装済みに戻す。
3. 満杯なら投入せずに破棄し、武装済みであれば警告を 1 件出して武装を解除する。
   武装が解除済みなら何も出さない（D1）。
4. どちらの分岐でも、外部デーモンに起因してブロックしうる処理は行わない。

### シャットダウン経路

1. 送信側を落とし、ワーカーの受信ループを終了させる。
2. 名前付き定数の期限内でワーカーの終了を待つ。
3. 期限内に終わったら回収する。期限を超えたら待つのをやめ、スレッドをデタッチして
   ドロップ処理から戻る（D2）。

シャットダウンはシンクのドロップ処理に置く。`App` のティアダウンで最後の共有参照が
解放された時点で発火する。

### 変えてはならないもの

- `src-tauri/src/callbacks.rs:191-193` のトレイト宣言（バイト単位で不変）。
- 既存のテストシンク 3 種の定義: `src-tauri/src/callbacks/tests.rs:22` /
  `src-tauri/src/app/tests/agent_status.rs:22` / `src-tauri/src/tabs/tests.rs:12`。
- プロデューサ呼び出し箇所: `App::notify`、`NativeCallbacks` の OSC 9 経路、
  タブ活動、`src-tauri/src/app/agent_status.rs:187` の
  `maybe_notify_agent_transition`、リンク処理。
- シンクの共有クローンを受け渡している箇所（`src-tauri/src/app/tab_lifecycle.rs`、
  `src-tauri/src/tabs/mod.rs`）。型は共有参照のままなので変更不要。
- プロセスグローバルな状態を新設しないこと。ワーカーの寿命はシンクの寿命に
  結び付けるのであって、静的な一度きりの初期化に結び付けない（FR10）。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `send` の本体に capability 照会と通知送出の呼び出しが現れず、両者は
      ワーカー本体にのみ現れる。ワーカーを占有した状態で投入しても、投入側は
      ブロックせずに戻る。（SPEC AC1 / FR1 / NFR1）
- [ ] AC-2: `NotificationSink` トレイト宣言が変更前とバイト単位で同一であり、既存の
      テストシンク 3 種と全プロデューサ呼び出し箇所が無変更でコンパイル・通過する。
      本番側で変わるのは `src-tauri/src/app/mod.rs:574` の構築 1 箇所のみ。
      （SPEC AC2 / AC3 / FR2）
- [ ] AC-3: 容量 8 のキューが満杯のとき、9 件目以降の投入はブロックせずドロップされ、
      キューは無制限に伸びない。ドロップは呼び出し元に観測可能な形で報告される。
      （SPEC AC4 / FR5 / NFR3）
- [ ] AC-4: 飽和エピソードの最初のドロップがちょうど 1 件の警告記録を生み、同一
      エピソード内の以降のドロップは記録を生まない。投入が成功して再武装された後の
      新たなドロップは再び記録を生む。（SPEC AC5 / FR6）
- [ ] AC-5: redaction が受領したままの値から導出され、2 つのログ記録のリテラル接頭辞が
      不変であり、capability 照会が通知ごとに 1 回だけ行われ、その単一の結果が
      タイトルと本文双方のエスケープ判定を駆動する。（SPEC AC6 / AC7 / FR3 / FR4）
- [ ] AC-6: シンクのドロップで送信側が落ちてワーカーの受信ループが終了し、境界付き
      join が期限内に戻る。通知を 1 件も送らずに構築直後にドロップした場合も同様に
      期限内に戻る。期限超過時はデタッチして戻り、ハングしない。
      （SPEC AC8 / FR7 / FR8 / NFR2 / A9）
- [ ] AC-7: `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path
      src-tauri/Cargo.toml` が通り、`CARGO_TARGET_DIR=src-tauri/target cargo check
      --manifest-path src-tauri/Cargo.toml --no-default-features` が通る。投入・受信・
      送出のディスパッチ経路に cfg 分岐がなく、プロセスグローバルな一度きりの初期化を
      新設していない。（SPEC AC9 / FR9 / FR10 / NFR5）

## Test Notes

- **すべてヘッドレスで走ること**（NFR4）。投入コンポーネントを notify-rust の型から
  切り離し、実 D-Bus 接続なしに直接検証する。既存の `escape_for_send` を私有関数として
  切り出しユニットテストしている前例（`src-tauri/src/callbacks.rs:263-277` と
  `src-tauri/src/callbacks/tests.rs:691-860`）に合わせる。
- **AC-3 のテストは消費側を動かさない**こと。ワーカーが動いていると 1 件が取り出し
  済みになり、ドロップが始まる件数が 8 件目ではなく 9 件目にずれてテストが不安定に
  なる。投入コンポーネント単体に対して、受信側を動かさずに 8 件投入 → 9 件目が
  ドロップ、を検証する。
- **AC-4 は記録件数で判定する**。実ログ出力の捕捉に依存させず、警告を出したか否かを
  投入結果から観測できる形にして、エピソード先頭 1 件・以降 0 件・再武装後 1 件の
  3 段を 1 本のテストで通す。
- **AC-6 は 2 本に分ける**。(a) 何件か投入した後のドロップ、(b) 1 件も送らずに構築
  直後のドロップ（D5 / SPEC A9 の経路）。判定は経過時間の上限で行うが、CI の
  ばらつきを踏まえて D2 の期限より十分大きい上限で判定し、フレーキーにしない。
- **既存テストは書き換えない**。既存の `escape_for_send` / fail-closed capability /
  レートリミット / redaction / エージェント状態通知の各テストが無変更で通ることが
  AC-2 / AC-5 の主たる根拠になる。テストが落ちたら、テストではなく実装を直す。
- **TDD で進める**。投入とドロップの検証（AC-3 / AC-4）は実装より先に書ける。
  ワーカー本体の送出ステップ（AC-5）は実 D-Bus に触れるため直接のユニット検証が
  難しい部分が残る。ここは既存テストの無変更通過とレビュー時のコード検査で担保し、
  新しいテストダブルを足してまで検証しようとしない（トレイト境界を変えないため)。

## Out of Scope

- 通知本文のサニタイズ（別フィーチャー）。
- 通知の発火条件とレートリミットの変更。
- `NotificationSink` トレイトへのメソッド追加・シグネチャ変更。
- capability 照会結果のキャッシュ導入。
- 新しいモジュールファイル・新しいフィーチャーゲート・新しい外部依存の追加。
- キュー容量やシャットダウン期限の設定ファイルからの可変化。
