# Task Plan: task0003 — Integration tests for binary-update detection (mux_hot_upgrade.rs extension)

## Goal

End-to-end proof, against a real daemon process and a real shell, that a
rename-replaced daemon binary triggers an in-place upgrade from both CLI
entry points with the shell PID preserved and the new image running — and
that no upgrade fires when the binary is unchanged or the identity
information is absent.

## Requirements

FR1, FR2, FR3, FR4, FR7

## Scope

### Files to Create
(none)

### Files to Modify
- `src-tauri/tests/mux_hot_upgrade.rs` — add the TS-3 / TS-4 / TS-5 /
  TS-7 scenarios (TS-8's notice assertion folded into TS-3/TS-5) and any
  new shared helpers they need. Existing scenarios stay untouched.

## Design

Follow the file's own established pattern exactly: isolated
`XDG_RUNTIME_DIR` per scenario, real daemon child process, bounded
named-step waits, RAII cleanup guard, raw frame helpers. Reuse the
existing helpers (`copy_daemon_binary`, the rename-replacement technique
documented at `poison_binary_at`, `socket_path_for`, `log_path_for`).

These scenarios are written against the IMPLEMENTATION.md contracts that
task0001/task0002 build to in parallel (the file's header documents this
exact precedent from the hot-upgrade feature): they are expected to fail
by timing out at a clearly-named bounded wait until the sibling tasks land
on the integration branch, and must not be weakened to pass early.

**Cross-task contract surface consumed (black-box only):**
- Identity file name/location: `mux-identity.txt` next to the daemon
  socket (needed only to DELETE it in TS-7).
- The pinned notice line `Mux daemon upgraded in place to the newly
  installed binary` on the attaching/starting client's standard error.
- Firing sites: `emterm mux attach` and the `ensure_daemon_running` path.

**New helper**: replace the daemon's start binary with a VALID new copy —
write a fresh copy of the built test binary to a temporary name in the
same directory, then rename it over the daemon's private binary path
(same rename-replacement semantics as a package manager; the running
daemon keeps the old inode, and its own executable-path resolution starts
reporting "(deleted)"). This is the "compatible candidate" counterpart of
the existing incompatible `poison_binary_at`.

**Scenario outlines:**
- **TS-3 (attach path; AC-1/2/3/6/8 main line)**: copy the binary to a
  private path; start the daemon from it; create a pane with a real shell
  and record the shell PID; rename-replace the binary with a valid new
  copy; run `<new binary> mux attach` as a child process with piped
  standard error against the isolated runtime dir; wait (bounded) for the
  pinned notice line on its standard error; then assert — shell PID
  unchanged and alive; daemon log contains the handoff-start marker; the
  daemon process's executable link no longer reports "(deleted)" (new
  image running, AC-6). Terminate the attach child during cleanup.
- **TS-4 (no churn; AC-4)**: same setup WITHOUT replacing the binary;
  attach (or run the mux-start vehicle); hold a raw-frame observer
  connection and assert, within a bounded observation window, that no
  Upgrading broadcast arrives and the daemon log contains no
  handoff-start marker.
- **TS-5 (mux-start path)**: same replacement setup as TS-3, but drive
  the `ensure_daemon_running` probe via `<new binary> mux script` (it
  runs the same probe, prints the socket path, and exits — no
  long-running bridge to manage); assert the upgrade fired (handoff-start
  marker; executable link no longer "(deleted)") and the notice line
  appeared on the child's standard error.
- **TS-7 (pre-feature generation; AC-7)**: same replacement setup as
  TS-3, but DELETE `mux-identity.txt` after the daemon is up (simulating
  a daemon generation that never wrote one); attach; assert no upgrade
  fires (as TS-4's absence assertions) and the attach still works.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A TS-3 scenario exists and asserts all four outcomes — upgrade
      fired, shell PID unchanged and alive, daemon running the new image
      (handoff-start marker + non-"(deleted)" executable link), and the
      pinned notice line on the attach client's standard error (FR1, FR2,
      FR4; SPEC AC-1/2/3/6/8).
- [ ] AC-2: A TS-4 scenario exists and asserts, within a bounded window,
      that an unchanged binary produces no Upgrading broadcast and no
      handoff-start log entry (FR3; SPEC AC-4).
- [ ] AC-3: A TS-5 scenario exists proving the `ensure_daemon_running`
      path fires identically after a binary replacement, including the
      notice line (FR2; SPEC AC-8).
- [ ] AC-4: A TS-7 scenario exists proving a missing identity file causes
      no misfire even with a replaced binary, and the attach proceeds as
      before (FR7; SPEC AC-7).
- [ ] AC-5: Every new wait is bounded and panics naming the stuck step;
      every scenario uses an isolated runtime dir and RAII cleanup that
      also terminates any spawned attach/script child on failure (the
      file's existing cross-cutting conventions).
- [ ] AC-6: All pre-existing scenarios in the file are textually untouched
      and still pass (FR6 regression — the schema-gate abort and
      exec-failure behaviors keep their existing coverage).

## Test Notes

- Run command (from workflow.yaml):
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --test mux_hot_upgrade -- --test-threads=1`.
- The attach child in TS-3 is long-running (bridge); read its standard
  error incrementally with a bounded deadline, then kill it via the
  cleanup guard. TS-5's `mux script` child exits on its own — prefer it
  wherever a scenario does not specifically need the attach path.
- Absence assertions (TS-4/TS-7) must use a fixed observation window
  generous enough for a real fire to have happened (calibrate against
  TS-3's observed fire latency) but short enough to keep the suite fast.
- Expected-to-fail-before-merge: document this in each scenario's comment
  per the file's header convention; do not mark them ignored.
