# Task Plan: task0002 — Update-detection trigger in the shared recovery probe (client side)

## Goal

The shared recovery probe fires the existing hot-upgrade path when the
daemon's binary was replaced — even when the protocol is compatible — with
a one-line notice to the client, and warns the user before the legacy
shutdown→respawn fallback destroys panes. Both CLI entry points (`emterm
mux attach` and `emterm mux` / `emterm mux script`) get this behavior from
the single shared probe.

FR1, FR2, FR3, FR5, FR6, FR7, NFR1, NFR2, NFR3

## Design

Implements IMPLEMENTATION.md decisions D1, D5, D6. The `mux::identity`
check API and both pinned message lines are Shared Components — consume
them exactly as pinned; do not restate or vary them.

**Compatible-arm flow (D5)** — inside `recover_from_legacy_daemon`, after
the current-version handshake is accepted:
1. Obtain the identity verdict for the socket path via the pinned check
   API (production wiring; tests inject the verdict).
2. Unchanged or Undecidable → return Compatible exactly as today. No
   Upgrade frame is sent, so no Upgrading broadcast can occur (FR3, FR7).
3. Updated → send the existing bare Upgrade frame on the
   already-handshaked probe connection (no second connection, no payload —
   the client never transmits a path, NFR3), then read the daemon's reply
   via the existing response reader:
   - Rejected(reason) → print a warning to standard error that includes
     the daemon's reason, log at warn, return Compatible (the original
     daemon keeps serving with panes intact — FR6).
   - Proceeded/unknown → drop the connection and poll the existing
     bounded reachability wait:
     - reachable → print the pinned notice line
       (`Mux daemon upgraded in place to the newly installed binary`) to
       standard error, log at warn, return Compatible (AC-8).
     - timeout → print a warning to standard error, log at warn, return
       Compatible (the client proceeds; a truly dead daemon surfaces
       through the existing downstream connection error).
4. The probe fires at most once per invocation and never converts a
   detection or upgrade failure into an attach / mux-start failure.

**Legacy-arm change (D6)**: at the single point where the legacy path
commits to the shutdown→respawn fallback (reached both when the Upgrade
frame was silently ignored until the reachability timeout and when the
send itself failed), print the pinned FR5 warning line
(`The running mux daemon predates in-place upgrade support; panes cannot
be preserved and will be recreated.`) to standard error and log at warn.
The fallback behavior itself is unchanged.

**Testability**: keep the existing public shape
(`recover_from_legacy_daemon(socket path)`) and add an internal
parameterized variant — the established pattern of
`resolve_attach_socket_with` and `execute_upgrade_at` — injecting (a) the
identity-verdict provider and (b) a user-message sink, so unit tests can
drive every verdict and assert emitted lines without real files or a real
terminal. Production wires the real check API and standard error.

**Entry-point coverage (D1)**: no caller changes. Because the flow lives
in the shared probe, `resolve_attach_socket_with` (cli.rs:494) and
`ensure_daemon_running` (daemon.rs:219) both get it. Do not duplicate any
detection logic in the callers.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Against a current-protocol fake daemon, with an injected
      Updated verdict, the probe sends exactly one Upgrade frame and — once
      the daemon is reachable again — emits exactly the pinned notice line
      once, and returns success (FR2, TS-8).
- [ ] AC-2: With an injected Unchanged verdict, no Upgrade frame is sent,
      no notice is emitted, and behavior is byte-identical to the
      pre-feature Compatible path (FR3).
- [ ] AC-3: With an injected Undecidable verdict, behavior equals AC-2's
      (no fire, no notice) (FR7).
- [ ] AC-4: When the daemon replies with a rejection to the fired Upgrade,
      the emitted warning contains the daemon's reason, the probe still
      returns success, and the fake daemon observes no shutdown request
      (FR6).
- [ ] AC-5: When the fired Upgrade is followed by a reachability timeout,
      a warning is emitted and the probe still returns success (D5
      outcome 3).
- [ ] AC-6: Against a previous-protocol fake daemon that silently ignores
      the Upgrade frame, the pinned FR5 warning line is emitted before the
      existing shutdown→respawn fallback runs, and the fallback outcome is
      unchanged from today's tests (FR5, TS-6).
- [ ] AC-7: The production call site obtains its verdict through the
      pinned `mux::identity` check API (D2 wiring ownership), detection
      code exists only inside the shared probe (no duplication in either
      caller), and Windows / CLI-only builds compile with zero behavior
      change (NFR2).

## Test Notes

- AC-1/AC-2/AC-3/AC-4/AC-5: extend the fake-daemon fixture family in
  daemon.rs / cli.rs test modules with a current-protocol stand-in that
  accepts the handshake, records whether an Upgrade frame arrived, and can
  be configured to (a) reply with a rejection, (b) go silent, or (c)
  "become upgraded" (keep serving handshakes so the reachability wait
  succeeds). Existing fixtures `spawn_fake_legacy_daemon` and
  `spawn_fake_legacy_daemon_with_upgrade` are the pattern to follow.
- AC-6: reuse `spawn_fake_legacy_daemon_with_upgrade`'s ignored-upgrade
  configuration; assert the message sink received the pinned FR5 line and
  the existing fallback assertions still hold.
- Message assertions go through the injected message sink, not by
  capturing the process's real standard error.
- Timing: the reachability wait is already bounded (~2s); keep fake-daemon
  tests within the existing test-time envelope of the current
  recover_from_legacy_daemon tests.
- TDD-awkward: none — every branch is drivable via injection.
