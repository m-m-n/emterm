# Task Plan: task0001 — Identity mechanism and exec-target resolution (daemon side)

## Goal

The mux daemon records its start-binary identity (executable path +
(device, inode)) to a hardened identity file at every startup, exposes a
client-side comparison verdict, and resolves the hot-upgrade exec target
exclusively from that recorded identity — never from fresh executable-path
resolution, which returns a "(deleted)" path after a rename replacement.

## Requirements

FR1, FR3, FR4, FR6, FR7, NFR1, NFR2, NFR3

## Scope

### Files to Create
- `src-tauri/src/mux/identity.rs` — the `mux::identity` module: identity
  file path derivation, daemon-side record-or-invalidate, client-side
  check verdict, comparison predicate, file format, hardening, unit tests.

### Files to Modify
- `src-tauri/src/mux/mod.rs` — declare the new module, Unix-gated
  (matching the existing `upgrade` / `inherited_pty` precedent).
- `src-tauri/src/mux/daemon.rs` — (a) daemon startup: invoke
  record-or-invalidate and keep the recorded identity in process state;
  (b) upgrade branch: resolve the exec candidate from the recorded
  identity instead of `self_exec::self_exe_path`, refusing with a reason
  when no identity was recorded.

## Design

This task implements the `mux::identity` Shared Components contract in
IMPLEMENTATION.md verbatim (path derivation, record-or-invalidate, check
verdict, recorded-identity value) plus the daemon-side wiring of decisions
D3 (exec target) and D4 (lifecycle). Do not re-derive those contracts —
they are pinned there because task0002 builds against them in parallel.

**Identity file** (`mux-identity.txt`, sibling of the daemon socket):
- Content: a format-version marker plus the three recorded fields
  (executable path, device, inode). Exact serialization is this task's
  choice, but it must reject truncated or trailing-garbage content into
  the Undecidable verdict, and the path field must round-trip arbitrary
  valid Unix paths (including whitespace).
- Hardening (NFR3, following the handoff-file precedent in
  `mux::upgrade`): file mode 0o600, never follow a symlink at the
  destination or at any temporary path used, directory is the existing
  owner-only 0o700 socket directory.
- Replacement must be atomic with respect to concurrent readers (a
  client probing mid-write must read either the old complete content or
  the new complete content, never a torn write; the rename-into-place
  pattern used elsewhere in the codebase satisfies this).

**Record-or-invalidate (D4)** — called once per daemon startup, on every
startup route (fresh bind, post-execve handoff start, failed-exec
re-entry), after the socket parent directory is ensured:
1. Resolve the running process's executable path and stat it.
2. Stats cleanly → persist path + (device, inode); return the recorded
   identity for in-process use.
3. Resolution or stat fails (notably: the post-rename "(deleted)" state
   during a failed-exec re-entry) → remove any existing identity file,
   record nothing. This is the fire-loop breaker — see IMPLEMENTATION.md
   D4 rationale.
4. A persistence failure itself must not abort daemon startup (best-effort
   policy): log at warn, attempt to remove a possibly-stale file, and
   continue with no recorded identity.

**Comparison predicate** (client side, pure, table-testable in the style
of the `is_missing` test group in `self_exec.rs`):
- recorded (dev, ino) equals current stat of recorded path → Unchanged
- differs → Updated (carrying the recorded path)
- recorded path not found → Updated
- any other stat error → Undecidable
- identity file missing / unreadable / malformed / truncated → Undecidable
Cost bound (NFR1): one small-file read + one stat, nothing else.

**Upgrade-branch wiring (D3)** — in `run_daemon`'s upgrade-signal branch
(the site currently calling `self_exec::self_exe_path`, daemon.rs:1355):
- Candidate := the recorded identity's clean path (in-process value
  captured at startup — the same value persisted to the file).
- No recorded identity → reply with a clear refusal reason through the
  existing per-request reply channel (same route the schema-gate refusal
  uses) and continue serving. No fallback to fresh executable-path
  resolution exists on this path.
- Everything downstream (schema-range probe, snapshot, execve,
  failed-exec re-entry) is untouched (FR6).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: After daemon startup with a cleanly stat-able executable path,
      the identity file exists next to the socket with mode 0o600 and
      round-trips the recorded path, device and inode through the
      client-side check (TS-2).
- [ ] AC-2: When the startup capture cannot stat the resolved executable
      path, any pre-existing identity file is removed and no identity is
      recorded; daemon startup still succeeds (D4, FR7).
- [ ] AC-3: The comparison predicate satisfies the full TS-1 table:
      match → Unchanged; (dev, ino) mismatch → Updated; recorded path
      not-found → Updated; other stat error → Undecidable — and never
      reports Updated from a parse failure (FR1, FR3, FR7).
- [ ] AC-4: Missing, truncated and malformed identity files each yield
      Undecidable (TS-2, FR7).
- [ ] AC-5: A symlink pre-placed at the identity file path (or at the
      temporary path used during atomic replacement) is refused — the
      write fails without following it (TS-2 security, NFR3).
- [ ] AC-6: The upgrade branch resolves its exec candidate from the
      recorded identity path; with no recorded identity the upgrade
      request is refused with a human-readable reason via the existing
      refusal reply, and the daemon keeps running (FR4, FR6, NFR3).
- [ ] AC-7: `self_exec::self_exe_path` is no longer referenced by the
      upgrade-signal branch, and Windows / CLI-only builds compile with
      zero behavior change (the new module and all call sites are
      Unix-gated) (FR4, NFR2).

## Test Notes

- AC-3/AC-4: pure predicate table tests plus file-content tests against a
  temp directory — mirror the `is_missing` test group's style (TS-1) and
  add write/read round-trip, truncation, garbage, and permission-bit
  assertions (TS-2).
- AC-5: pre-place a symlink and assert refusal (same technique the
  handoff-file hardening precedent implies).
- AC-2: simulate a non-stat-able capture by exercising the
  record-or-invalidate routine against a recorded path that does not
  exist (parameterize capture input rather than manipulating /proc).
- AC-6: `run_daemon`'s branch is hard to unit-test whole; keep the
  candidate-resolution decision ("recorded identity or refusal reason")
  in a small pure helper and table-test it; the end-to-end proof is
  task0003's TS-3 (not this task's responsibility).
- TDD-awkward: none of the above needs a live daemon.
