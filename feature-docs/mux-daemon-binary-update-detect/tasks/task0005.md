# Task Plan: task0005 — Positive replacement proof before the upgraded notice (client side)

## Goal

The automatic trigger claims "Mux daemon upgraded in place" only on
positive evidence that the daemon was actually replaced — a
post-reachability identity re-check reporting Unchanged — never on
reachability alone, which cannot distinguish a genuinely replaced daemon
from the original one that refused or ignored the upgrade and kept serving
(SPEC FR2 / AC-6 / AC-8).

## Design

**Evidence chain — why a re-check verdict of Unchanged is proof.** Every
daemon start records-or-invalidates its OWN image's identity before its
accept loop answers any handshake (the shipped D4 lifecycle plus the
startup ordering: identity recording precedes the accept loop, and
mid-upgrade connections queue in the kernel backlog until the loop runs).
Therefore, once a post-upgrade handshake succeeds, the answering daemon has
already re-recorded the identity of its own image:

- Replacement genuinely took → the answering (new) daemon recorded the
  newly installed file → re-check reports **Unchanged**.
- The original daemon kept serving (refusal lost in the reply race, or the
  request was ignored) → its recorded identity still names the old image,
  which no longer matches the file installed at the recorded path →
  re-check reports **Updated**.
- Identity unavailable (e.g. a failed exec re-entry invalidated it) →
  **Undecidable** — not proof, so no success claim.

This reuses the existing identity-recording invariant as the positive
evidence source: no protocol change, no new connection type, no new frame.

**Flow change — proceeded/unknown arm only:**

1. Reachability wait fails → behavior unchanged: existing timeout warning,
   success return, and NO re-check is performed.
2. Reachability wait succeeds → obtain a second verdict from the SAME
   injected identity-check provider the firing decision used (the
   trigger's existing injected-check parameter; no signature change):
   - **Unchanged** → emit the pinned replacement notice exactly as today
     (`Mux daemon upgraded in place to the newly installed binary`), log at
     warn, return success.
   - **Updated** or **Undecidable** → do NOT emit the notice. Emit exactly
     this pinned line instead, and log it at warn:
     `Warning: mux daemon is reachable but the binary replacement could not be confirmed; continuing with the existing daemon`
     Then return success — an unproven upgrade never becomes an attach /
     mux-start failure.

**Cost (NFR1):** one extra identity-file read plus one stat, incurred only
on the fired-upgrade path (never on the ordinary attach path, whose single
pre-fire check is unchanged) — within the lightweight-check budget.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With an injected provider scripted Updated (pre-fire) then
      Unchanged (post-fire) and a fake daemon that stays reachable, the
      trigger emits exactly one pinned replacement-notice line and returns
      success — the shipped TS-8 behavior is preserved (FR2, TS-13).
- [ ] AC-2: With the provider scripted Updated then Updated (replacement
      did not take), no replacement notice is emitted; exactly one pinned
      unconfirmed-replacement warning line is emitted; the trigger still
      returns success (FR2, TS-13).
- [ ] AC-3: With the provider scripted Updated then Undecidable, behavior
      equals AC-2's — undecidable evidence is never claimed as success
      (FR2, TS-13).
- [ ] AC-4: On a reachability timeout, the provider is invoked exactly
      once (pre-fire only — no re-check), the existing timeout warning is
      emitted, and the trigger returns success (TS-13).
- [ ] AC-5: The production call site performs the re-check through the
      same real identity check API as the firing decision; no new frame,
      connection, or protocol element is introduced; Unchanged/Undecidable
      pre-fire verdicts still send no Upgrade frame at all; Windows /
      CLI-only builds compile with zero behavior change (NFR1, NFR2).

## Test Notes

- Drive every criterion through the trigger's existing injection points
  (identity-check provider + message sink), following the shipped trigger
  tests' fake-daemon pattern; use a stateful scripted provider returning a
  sequence of verdicts, with a call counter distinguishing the pre-fire
  and post-fire invocations (AC-4's exactly-once assertion).

  process's real standard error.
- Keep fake-daemon tests inside the existing trigger tests' time envelope
  (the reachability wait is already bounded).
