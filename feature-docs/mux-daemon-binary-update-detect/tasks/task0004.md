# Task Plan: task0004 — Upgrade-candidate validation and repeat-refusal suppression (daemon side)

## Goal

The daemon never probes or execs an upgrade candidate whose current on-disk
state is not owner-controlled (SPEC NFR3: "a path writable by others … is
never exec'd unverified"), and a candidate that was refused or failed once
is not re-probed on every subsequent client attach — the repeat is
suppressed daemon-side, keyed by the candidate's (device, inode), until a
different candidate appears or the daemon restarts.

## Requirements

FR2, FR6, NFR1, NFR3

## Provenance

- source: review (round 1)
- source_ids: `sid-upgrade-candidate-exec-without-validation`,
  `sid-failed-upgrade-not-suppressed`
- Grouping rationale: both findings live on the daemon's upgrade refusal
  path and compound each other — adding the ownership/writability gate
  creates a new class of structurally repeating refusals, and the
  suppression fix must key on exactly the refusals that gate produces, so
  the two are one contract implemented and tested together.

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/mux/identity.rs` — candidate-validation helpers: a pure,
  table-testable decision over captured file attributes, plus a thin
  capture wrapper that reads the candidate's and its parent directory's
  metadata without following a symlink at the inspected path; unit tests.
- `src-tauri/src/mux/daemon.rs` — (a) upgrade-signal branch of the daemon
  run loop: validate the resolved candidate before the handoff schema
  probe; hold run-loop-scoped "last refused candidate" state; fast-reject a
  repeat attempt with a pinned suppression-marker reason without spawning
  the probe; (b) client-side trigger (`trigger_binary_update_if_detected`),
  rejected-reply arm only: suppress the user-facing warning when the
  daemon's reason carries the suppression marker; unit tests.
- `src-tauri/src/mux/cli.rs` — replacement routine
  (`perform_upgrade_replacement`): re-validate the candidate immediately
  before the process-image replacement attempt; on refusal, skip the
  replacement attempt and take the existing re-entry path so the daemon
  keeps serving.
- `src-tauri/tests/mux_hot_upgrade.rs` — integration proof for the
  validation refusal (TS-11 live half).

## Design

Consumes the existing `mux::identity` contracts (recorded identity,
`resolve_upgrade_candidate`) and the existing refusal reply channel
unchanged. Both halves of the new suppression-marker data contract (daemon
producer, trigger consumer) are owned by this task.

**Candidate validation (NFR3).** Two layers:

1. A pure decision function over captured attributes — inspected-entry
   kind, owner uid, permission bits, and the daemon's own effective uid —
   returning either "accepted" or a human-readable refusal reason naming
   the failed rule. Being pure, it is table-testable without privileged
   fixtures (foreign-owner and root-owner rows are parameterized, never
   created on disk).
2. A capture wrapper that inspects the candidate path and its parent
   directory. Every metadata read refuses to follow a symlink at the
   inspected path itself (the check must describe the entry at that path,
   not a symlink target).

Rules — ALL must hold, applied to the candidate file AND to its parent
directory:

- The candidate is a regular file (a symlink, directory, or special file is
  refused); the parent is a directory and not a symlink.
- The owner uid equals the daemon's effective uid, or is root.
- No group-write and no world-write permission bits are set.

Call sites (both required — recorded-path resolution is necessarily stale
relative to exec time, so the check runs at the last responsible moment on
each side):

1. **Before the handoff schema probe**, in the upgrade-signal branch, after
   candidate resolution succeeds. A refusal replies through the existing
   per-request refusal channel — the same route the schema-gate rejection
   uses today — and the daemon keeps serving with panes intact (FR6
   refuse-and-keep-serving).
2. **Immediately before the exec attempt**, in the replacement routine
   (after the run loop has exited). A refusal here logs at error level,
   skips the replacement attempt entirely, and re-enters service through
   the existing handoff-mode re-entry — the same pane-preserving path an
   exec failure takes today. Keep the "attempt or re-enter" decision in a
   small helper parameterized on the validation outcome so it is
   table-testable.

**Repeat-refusal suppression (NFR1).**

- Run-loop-scoped mutable state (alongside the other run-loop state, e.g.
  the pending-upgrade slot): the most recently refused candidate identity
  as (device, inode), plus the refusal reason it produced. In-memory only —
  a daemon restart naturally clears it (the lifetime the finding chose).
- On each Upgrade signal: resolve the candidate; capture its current
  (device, inode) with one metadata read (not following a symlink). If it
  equals the recorded refused identity → reply with a rejection whose
  reason is the pinned suppression form (below), spawning NO probe
  subprocess, taking NO snapshot, and logging at debug level only. If it
  differs, or the capture fails → clear the state and proceed through
  validation and the probe normally.
- Recording: whenever the branch refuses the candidate — validation
  failure, probe spawn failure, probe timeout, or the schema-range gate
  rejection — record that candidate's (device, inode) and the reason. A
  resolution failure (no recorded identity) is NOT recorded: it has no
  (device, inode) to key on and is already cheap.
- Pinned suppression reason (data contract, both ends in this task): the
  rejection reason starts with the exact marker `upgrade-suppressed: `,
  followed by a human-readable sentence containing the original refusal
  reason and the recovery hint that installing a new binary or restarting
  the daemon re-enables the attempt.

**Trigger-side warning suppression.** In
`trigger_binary_update_if_detected`'s rejected-reply arm only: a reason
starting with the pinned marker emits NO user-facing line and is logged at
debug level; any other reason behaves exactly as today (visible warning,
warn-level log). The return value is unchanged in both cases (success —
never converts to an attach failure). Net user experience: the FIRST
refusal of a given candidate is visible with its real reason; repeats are
silent.

**Manual-upgrade note.** The daemon cannot distinguish an automatic
request from a manual upgrade-command request (same frame — deliberately no
protocol change), so a manual retry against an unchanged refused candidate
also receives the fast marker rejection; the manual command path prints the
daemon's reason as it does today, so a user retrying by hand still sees why
and how to recover.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The validation decision table holds: an owner-or-root-owned
      regular file without group/world-write bits, in a conforming parent
      directory, is accepted; each of {symlink candidate, non-regular
      candidate, group-writable, world-writable, foreign-owner (neither
      effective uid nor root)} — and the analogous parent-directory rows —
      is refused with a reason naming the failed rule (NFR3, TS-11).
- [ ] AC-2: The upgrade-signal branch refuses a validation-failing
      candidate through the existing refusal reply BEFORE any probe
      subprocess is spawned, and the daemon keeps serving; the TS-11
      integration case (candidate at the recorded path made group/world
      writable, then attach) shows a visible refusal warning, no upgrade,
      and an unchanged live shell PID (NFR3, FR6).
- [ ] AC-3: The replacement routine re-validates immediately before the
      exec attempt; on refusal no exec is attempted and the existing
      re-entry path keeps the daemon serving — the attempt-or-reenter
      decision helper is table-tested across accepted/refused outcomes
      (NFR3, FR6).
- [ ] AC-4: After a refused attempt, a second Upgrade signal for a
      candidate with the same (device, inode) is rejected without spawning
      the schema probe (an injected counting probe records exactly one
      spawn across the two signals), and the reply reason starts with the
      pinned `upgrade-suppressed: ` marker (NFR1, TS-12).
- [ ] AC-5: After a refusal, a candidate whose (device, inode) differs
      clears the suppression state and is validated and probed normally
      (TS-12).
- [ ] AC-6: The automatic trigger emits no user-facing line for a
      marker-prefixed rejection (debug-level log only) and still returns
      success; a rejection without the marker still emits the existing
      visible warning (FR2, NFR1, TS-12).
- [ ] AC-7: The pre-existing hot-upgrade regression suite passes
      unmodified (TS-9), and Windows / CLI-only builds compile with zero
      behavior change — every new item is Unix-gated (NFR2).

## Test Notes

- AC-1/AC-3: pure decision-helper table tests in the style of the existing
  identity predicate tables — no privileged fixtures; foreign-uid and
  root-owner rows are parameterized attribute values.
- AC-2 (unit half): extract the branch's "validate → suppress → probe"
  sequencing into a parameterized helper (the run-loop `select!` body is
  not unit-testable whole) injecting the probe function and the refusal
  sink; AC-2 (integration half): extend `mux_hot_upgrade.rs` — replace the
  binary as TS-3 does, then loosen the new copy's permission bits to a
  group/world-writable mode before attaching, and assert refusal + pane
  survival.
- AC-4/AC-5: same parameterized helper with an injected counting probe and
  two sequential signals.
- AC-6: task0002-style injected message-sink tests on
  `trigger_binary_update_if_detected` with a fake daemon replying a
  marker-prefixed vs plain rejection.
- TDD-awkward: the final pre-exec site (replacement routine) cannot be
  end-to-end tested without a real exec; its decision helper's table tests
  plus TS-9 regression are the planned coverage.

## Out of Scope

- Any IPC protocol change, including distinguishing manual from automatic
  Upgrade requests or advertising suppression state in the handshake.
- Persistent (on-disk) suppression state — daemon restart clears it by
  design.
- Changes to when the success notice is emitted on the proceeded/reachable
  path (a separate round-1 rework concern; this task touches only the
  rejected-reply arm of the trigger).
- Validation of the identity FILE itself (already hardened by the shipped
  identity mechanism) or changes to identity recording/comparison.
