# Task Plan: task0001 — Scope mux agent-status state by connection identity

## Goal

Make the GUI keep one agent-status entry per (mux connection, wire `pane_id`)
instead of one per wire `pane_id`, and carry that scope through every consumer
of the key, so panes on two different mux daemons never share state, a badge, a
notification title, a rate-limit key, or a discard.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Design

Read IMPLEMENTATION.md first: it pins the six contracts this task implements
(scoped mux pane key, connection scope value, tagged mux drain, scoped
public-pane-id lookup, rate-limit key derivation, scoped tab resolution) and the
decisions D1..D6. This section states only what is specific to carrying them out.

### The one shape change, and why everything else follows

Exactly one thing changes shape: the model's mux pane key stops being the bare
wire `pane_id` and becomes the pair (connection scope, wire `pane_id`). Every
other edit in this task is a consequence — either a caller that must now supply
the scope, or a lookup that must now be built from the scoped pair. Nothing
in the plain-tab path changes shape at all (NFR3).

### Flow, end to end

1. A daemon sends a status update for its own pane over one tab's mux attach
   stream. The tab extracts the frame and latches it in that tab's pending
   queue. Unchanged.
2. A pane exit on that daemon latches the wire `pane_id` in that tab's pending
   closed-pane list. Unchanged.
3. The per-frame drain takes both latches. **This is the change point for FR1**:
   today both are flattened into untagged collections, unlike the plain-tab
   events drained beside them, which already carry their tab's stable id. Both
   mux drains must carry the originating tab's stable id in the same way, so the
   batch apply receives (scope, item) pairs rather than bare items.
4. The batch apply derives every key from the pair it was given: the model key,
   the public-pane-id map key, and the rate-limit key. It must have no path left
   that constructs a key from a wire `pane_id` alone.
5. The read paths build keys from the querying tab's own scope:
   - the per-tab key set pairs each of that tab's group pane ids with that tab's
     scope, so two tabs holding identical pane ids yield disjoint key sets;
   - the per-tab badge aggregates only that set;
   - the per-sidebar-entry badge takes the sidebar's owning tab scope alongside
     the wire `pane_id`;
   - the "any pane has reported state" query matches within the acting tab's
     scope only.
6. Discard follows the same rule: the closed-pane loop removes the scoped model
   entry, the scoped map entry and the scoped rate-limit bookkeeping, and
   nothing else. The two whole-tab discard paths already iterate the per-tab key
   set, so they inherit the scope from step 5 — confirm they gained no other way
   to reach a key outside the closing tab.

### Notification resolution (FR5)

Both the title resolution and the visibility decision currently answer "which
tab holds this wire `pane_id`", which with two daemons can answer with the wrong
tab. They must answer "which tab's connection reported this", i.e. resolve
through the transition's own scope. When that tab no longer exists, the answer
stays "no tab" and the caller keeps its existing empty-title fallback (EC-4) —
never a different tab that happens to hold the same wire `pane_id`.

### Cost shape (NFR2)

The per-frame badge reads and the key-event-time cycle must remain keyed
lookups. Do not introduce a search over all tabs to discover a pane's owner, and
do not add per-frame allocation beyond the key-set build that already happens.
The scope is available at every one of these call sites from the tab already in
hand, so no lookup is needed to obtain it.

### Documentation (NFR4)

Two doc comments state the pre-fix contract and must state the new one instead:
the mux pane key's "keyed by the wire `pane_id`" note, and the rate-limit key's
"unique across concurrent panes" claim. Rewriting them is part of the task, not
a cleanup afterthought.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): Two model entries created under different connection scopes
      with the same wire `pane_id` are fully independent — applying a daemon
      update to one leaves the other's state, name, revision and unseen flag
      untouched, and aggregating over one scope's key set never observes the
      other's state. Verified by TS-1.
- [ ] AC-2 (FR1): Both mux drains carry the originating tab's scope into the
      batch apply, and the batch apply derives every key from that scope. Feeding
      one batch containing items tagged for two different scopes but carrying the
      same wire `pane_id` produces two independent sets of state, with no
      overwrite in either direction. Verified by TS-7 and TS-8.
- [ ] AC-3 (FR2, NFR2): All four read paths are scope-qualified — the per-tab key
      set is disjoint between two tabs whose groups hold identical pane ids; the
      per-tab badge and the per-sidebar-entry badge each return their own tab's
      value when the two tabs' panes are in different states; and the "any pane
      has reported state" query does not qualify another scope's same-numbered
      pane. Each of these remains a keyed lookup with no scan across other tabs
      and no new per-frame allocation. Verified by TS-3, TS-4, TS-9 (and VC-2 for
      the cost half).
- [ ] AC-4 (FR3, FR4): The public-pane-id map is scoped and the rate-limit key
      derives from it — learning a public id for one scope's pane 1 neither
      overwrites nor removes the other scope's pane 1, each scope's key resolves
      to its own daemon's public pane id string, the two keys differ, and they
      still differ on the never-learned fallback path. All four rate-limit call
      sites derive the same key for the same pane. Verified by TS-5 and TS-7.
- [ ] AC-5 (FR5): Notification tab-title resolution and pane visibility resolve
      by the transition's scope — with two tabs whose groups both contain wire
      `pane_id` 1, each scoped key resolves to its own tab's title, a non-active
      tab's pane is not reported visible merely because the active tab holds the
      same wire `pane_id`, and a transition whose owning tab is gone still
      resolves to no tab. Verified by TS-6.
- [ ] AC-6 (FR6): A close for one scope's pane discards that scope's model
      entry, its public-pane-id entry and its rate-limit bookkeeping, and leaves
      the other scope's same-numbered pane entries fully intact; the two
      whole-tab discard paths discard nothing outside the closing tab's own
      scope. Verified by TS-2 and TS-8.
- [ ] AC-7 (NFR1, NFR3, NFR4): `crates/mux_ipc` and the daemon-side pane-id
      allocator are unmodified; every existing plain-tab test passes with its
      original expectations unchanged; and the two doc comments named in the
      Design section describe the new scoping rule. Verified by TS-10, VC-1 and
      VC-3.

## Test Notes

- **Test level**: unit only (SPEC assumption A3). Ten scenarios, all inline
  `#[cfg(test)]`: TS-1, TS-2, TS-3 and the model half of TS-10 in the model's
  test module; TS-4 .. TS-9 and the application half of TS-10 in the
  application-level test module. No integration or E2E test is added.
- **TDD order**: write TS-1 first (it forces the key shape), then TS-4 (it forces
  the per-tab key derivation), then TS-8 (the primary regression scenario), then
  the rest. Each new test must fail for a semantic reason before the fix, not
  only because a signature changed.
- **AC-7 regression bar**: TS-8 is the primary regression test. Its assertions
  must fail if any consumer derives its key from the wire `pane_id` alone —
  compiling against a new signature is not the assertion. Write it so that
  dropping the scope from any single derivation (model key, map key, or
  rate-limit key) breaks it.
- **Plain-tab expectations are frozen** (NFR3): if an existing plain-tab test
  needs its expectation changed to pass, that is a defect in the change, not a
  test to update. Set/clear, unseen preservation, replay-derived silence,
  latch-driven inferred clear and discard-on-close must all keep their current
  expectations.
- **Edge cases to keep in mind while writing the tests**:
  - EC-1: two tabs attached to the same daemon pane become two entries. That is
    accepted duplication; do not add de-duplication. The model's global count is
    the only reader affected and it has no non-test caller.
  - EC-2: detach then re-attach in the same tab keeps the same scope. No
    detach-time discard is added (IMPLEMENTATION.md D3) — do not add one, and do
    not write a test that asserts a discard at detach.
  - EC-3: a mux tab whose daemon never installs a window group contributes no
    mux keys at all and must keep behaving exactly like a plain tab.
  - EC-4: a transition whose owning tab closed before the drain resolves to no
    tab and the caller falls back to an empty title. Cover this in TS-6.
  - EC-5: a daemon restart mints new public pane ids for reused wire pane ids.
    The scope is independent of that; the refresh path already overwrites on
    every update, so no extra handling is needed.
- **Running the tests**: unit tests live under the library target — running the
  binary target alone yields zero tests. The replay tests in the tabs module are
  non-deterministic under parallelism; a replay-test failure must be re-run with
  a single test thread before it is attributed to this change. Both commands are
  recorded in VERIFICATION.md.
- **Feature gates**: the touched modules are GUI-only, so the CLI-only build must
  still compile unchanged — verify it, do not assume it.
