# Task Plan: task0003 — Theme: scheme mirrors and correct OSC 110 / 111 / 104 resets

## Goal

After OSC 110, 111 or 104, the theme holds — and the renderer therefore
shows — the active color scheme's values rather than built-in fallback
constants or leftover OSC-set colors, so that a query issued after a reset
can only report a value the renderer is actually using.

## Requirements

FR7, FR8, FR9

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/render/theme.rs` — add the foreground, background and
  16-color-array scheme mirrors; seed them at theme construction; update them
  where a color scheme is applied; restore from them in the OSC 110 / 111 /
  104 paths; correct the change reporting of the palette reset; update the
  existing reset tests to the new semantics and drop the stale comment that
  deferred palette restoration to the caller.

## Design

Implements SC-5 of IMPLEMENTATION.md and relies on SC-6 for its post-reset
assertions; those contracts are normative and are not restated here. The
query side of the theme's OSC entry is task0002's and is not touched here.

**Mirrors.** Three fields join the existing cursor-color mirror: one for the
foreground, one for the background, and one mirroring the 16-color array.
They follow the existing mirror exactly, including its update rule
(IMPLEMENTATION.md D4 explains why a mirror is the only available mechanism):

- seeded at theme construction from the same constants that seed the
  corresponding live fields;
- updated unconditionally in the preset-scheme branch, alongside the live
  fields;
- updated in the user-scheme branch only under the same parse guard that
  gates the live field's update — a spec that fails to parse updates neither
  the live field nor the mirror, so both keep the construction seed;
- the 16-color mirror is updated per index, under that same guard;
- never written by any OSC set sequence.

**Foreground / background reset.** The two reset codes restore the live
fields from their mirrors instead of from the built-in constants. The
constants remain in place as the construction seed. This is visible on
screen: under a non-default scheme the reset now redraws in the scheme's
colors instead of the fallback bright green / black.

**Palette reset.** With an empty payload: the whole sparse overlay is cleared
AND the 16-color array is restored from its mirror. With an explicit index
list: for each listed index the overlay slot is cleared, and when the index
is below 16 that entry of the 16-color array is restored from the mirror.
Indices outside the valid range, and unparseable entries, change nothing.

**Change reporting.** The reset reports a change when either the overlay or
the 16-color array actually changed — including the newly covered case where
only the array changed — so that the newly covered case still marks the
render dirty. When nothing changed it still reports no change.

**Why this matters beyond queries**: a set of a palette index below 16 writes
both the overlay and the 16-color array, so before this change a reset left
that index rendering in the OSC-set color forever.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A freshly constructed theme's three new mirrors equal the same
      constants that seed the corresponding live fields.
- [ ] AC-2: Applying a preset scheme updates all three mirrors alongside the
      live fields; applying a user scheme updates a mirror only when the
      corresponding spec parses, per index for the 16-color mirror; no OSC set
      sequence (4, 10, 11, 12) ever changes a mirror.
- [ ] AC-3: Under an active preset scheme, the foreground and background reset
      codes restore the live fields from the mirrors rather than from the
      built-in constants (TS-6).
- [ ] AC-4: Under a user scheme whose foreground / background spec fails to
      parse, the same reset codes leave the construction seed in place
      (TS-7).
- [ ] AC-5: After a palette set, an empty-payload palette reset clears the
      overlay and restores the 16-color array from its mirror; an
      explicit-index palette reset restores only the listed indices, leaving
      other set indices intact (TS-8).
- [ ] AC-6: The palette reset reports a change when only the 16-color array
      changed, and reports no change when neither the overlay nor the array
      changed (TS-9).
- [ ] AC-7: The existing reset tests are updated to these semantics rather
      than deleted, the stale comment deferring palette restoration to the
      caller is gone, and — per SC-6 — the resolved value for indices 0-15
      after a reset equals the active scheme's palette value while 16-255
      still resolve by the xterm cube / grayscale rule (TS-10, FR7).

## Test Notes

- Every criterion is a theme-level unit test; no pipeline, no term_core seam,
  no GUI event loop is involved.
- Build the "active preset scheme" and "user scheme with an unparseable spec"
  states through the same scheme-application path production uses, not by
  writing fields directly — the parse guard is exactly what AC-4 checks.
- The existing cursor-color reset test is the closest model for AC-3 and
  AC-4; mirror its structure.
- AC-7's resolution assertion is written against SC-6's rule, so it stays
  valid whether or not task0002's query entry has landed in this worktree.
- Edge cases worth covering: a palette reset whose index list contains an
  index of 16 or above (overlay slot cleared, array untouched); a palette
  reset with nothing to clear (no change reported); the no-active-scheme case,
  where every mirror still holds the construction seed and the resets restore
  those seeds.

## Out of Scope

- Producing any response bytes, recognizing query tokens, or touching the
  theme entry's response output — task0002.
- The cursor-color reset path, which already behaves correctly and must keep
  behaving identically.
- Anything under `crates/term_core/` or `src-tauri/src/tabs/`.
- Re-reading settings at reset time (the theme holds no settings handle).
