# Task Plan: task0005 — Color responder survives the off-thread history swap

## Provenance

- source: review
- source_ids: [4d2f818d6a5b35f9, 3712df9238833233]
- review_round: 1

Both findings report one defect from two sides: the off-thread swap site and
the responder's single registration site. They share a root cause and one
Acceptance Criterion set, so they are one task.

## Goal

A tab that has gone through an off-thread history swap answers color queries
and applies color sets exactly as a tab that never swapped: the registered
color responder is part of the state carried across the core replacement, not
state that is silently dropped by it.

## Requirements

FR1, FR2, FR4, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/tabs/replay.rs` — the off-thread swap that replaces the live
  core wholesale: carry the registered responder across the replacement with
  the rest of the transplanted state, inside the same critical section and
  before the replacement becomes live; correct the doc comment whose
  behavioral-equivalence claim this task makes true again.
- `src-tauri/src/tabs/mod.rs` — the responder's single registration site:
  record the lifecycle expectation (a registered responder outlives any core
  replacement) at the registration point, so a future replacement path is not
  written without carrying it.
- `src-tauri/src/tabs/tests/replay.rs` — regression coverage beside the
  existing transplant test for the callbacks instance.

## Design

Normative background is IMPLEMENTATION.md SC-2 (host color-responder seam,
including its lifecycle postcondition), SC-3 (pending-response accumulation)
and D2 (responses travel by return value into the existing buffer). Those are
not restated here.

**The lost state.** A core rebuilt from a snapshot starts with no registered
responder — snapshot construction has no way to know about one. The swap
replaces the live core with that rebuilt core and transplants a fixed set of
live-side state onto it. The responder is not in that set, so after any swap
the live core holds none and the consult step short-circuits permanently for
that tab.

**Why the blast radius exceeds the new feature.** The theme's handling of the
color OSC codes is reached only through the responder now; the callbacks
route for those codes is inert. Because callbacks *are* transplanted and the
responder is not, a swapped tab keeps the inert route and loses the live one,
so color **set** — behavior that predates this feature — stops working along
with color query. The task's criteria therefore assert both directions.

**Where the carry-over belongs.** Inside the swap, with the rest of the
transplanted state, under the same lock, before the replaced core is
observable by the output path. Re-registering from the registration site
after the fact is not equivalent: it would leave a window in which a parse
pass sees a responder-less core, and it would duplicate the registration
rule in two places.

**What must not change.** The swap path also discards pending device
responses so that a query baked into snapshot bytes by a dead program cannot
be answered into a live shell (NFR3). Carrying the responder over does not
relax that: the responder is the thing that *produces* an answer, the discard
governs what is *delivered*, and the existing discard assertions stay intact
and unmodified.

**Synchronous path.** The synchronous replay path does not exhibit the defect
and is not modified; it is covered only as a regression.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: After a payload large enough to take the off-thread swap path, a
      subsequent OSC 11 query on the live core yields exactly one response,
      terminated with the form the request used, delivered through the
      existing device-response route (no new route, no second delivery).
- [ ] AC-2: After the same swap, an OSC 4 set mutates theme state and a
      following OSC 4 query for that index reports the value just set.
- [ ] AC-3: The responder answering after the swap is the same registered
      instance that answered before it — a test-local responder carrying a
      distinguishing marker proves identity, so a fix that re-registers a
      fresh responder instead of carrying the live one fails.
- [ ] AC-4: A swapped core and a never-swapped core, given the same color
      query and the same color set, produce identical responses and identical
      resulting theme state.
- [ ] AC-5: The pre-existing regression that pins discard of stale device
      responses across the swap passes **unmodified**; a color-query payload
      embedded in replayed snapshot bytes still produces no delivery (NFR3).
- [ ] AC-6: The synchronous replay path's existing behavior is unchanged, and
      a test fails if the carry-over is later removed from the off-thread
      path.

## Test Notes

- Unit/integration tests live in the tabs test module next to the existing
  transplant test. Drive the swap with a payload above the threshold that
  selects the off-thread path rather than calling the swap helper directly,
  so the test covers the production route.
- Use a test-local responder conforming to SC-2 that returns marker bytes for
  the query assertions (AC-1, AC-3) and the real theme-backed path only where
  the assertion is about theme state (AC-2, AC-4).
- AC-5 is a "do not touch" criterion: the existing assertions must appear
  byte-identical in the diff. Extending them with an additional payload case
  is allowed; weakening or rewriting them is the failure this criterion
  guards.
- Replay tests in this module have a history of order sensitivity; keep new
  tests free of shared mutable state (the crate's test command already pins
  single-threaded execution).
- Edge cases worth covering: a swap on a tab whose responder was never
  registered (must stay a no-op, no panic); two consecutive swaps (the
  responder survives both).

## Out of Scope

- Any change to which side of the mux bridge answers a query (settled by
  task0004).
- Any change to the response fan-out budget (task0006).
- Any relaxation of the replay / off-thread-swap discard behavior.
- Re-introducing color-code routing into the callbacks path — the responder
  is the single route by design (SC-2, D1).
- Changing the snapshot constructors so they carry a responder; the snapshot
  layer has no access to the GUI theme (NFR4).
