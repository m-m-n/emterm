# Task Plan: task0001 — term_core: terminator carriage and the color-response seam

## Goal

`crates/term_core` carries the string terminator that ended an OSC sequence
all the way to the OSC dispatch boundary, and offers a registration seam
through which the embedding layer can answer an OSC dispatch with response
bytes that land in the existing single-slot response buffer — without
`term_core` gaining any knowledge of the GUI theme.

## Requirements

FR5, NFR1, NFR4, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify

- `crates/term_core/src/osc_handler.rs` — the OSC dispatch boundary: accept
  and forward the terminator kind; consult the registered responder.
- `crates/term_core/src/color_spec.rs` — extend the existing response
  formatter's inline tests with boundary components (no second formatter).
- `crates/term_core/src/lib.rs` — export the seam's registration point and
  the terminator-kind value so the embedding layer can use them.
- `crates/term_core/src/parser.rs` — **predicted name** for the OSC parsing
  module: retain the terminator form observed at the end of an OSC string.
- `crates/term_core/src/terminal.rs` — **predicted name** for the core
  terminal module that owns the response buffer: registration storage and the
  accumulation behavior.

The last two names are predictions made without filesystem discovery
(IMPLEMENTATION.md D8). If the actual modules inside `crates/term_core/src/`
are named differently, the equivalent modules in that directory are the
intended scope; report the name difference as a plan deviation. Do not widen
the change outside `crates/term_core/`.

## Design

Implements SC-1, SC-2 and SC-3 of IMPLEMENTATION.md; those contracts are
normative and are not restated here.

Processing flow for one OSC string:

1. The parser recognizes the end of an OSC string and records which
   terminator form ended it (BEL form or ST form). A string ended by anything
   else (buffer flush, truncation) is classified deterministically, and that
   choice is documented where the value is defined.
2. The OSC dispatch boundary receives the numeric code, the raw payload and
   the terminator kind, and keeps its existing behavior for every code it
   already handles.
3. If a responder is registered, it is consulted with those three inputs and
   returns zero or more complete response byte sequences.
4. Returned sequences are appended, in order, to the pending response content
   — never overwriting content that has not been drained yet.
5. The existing drain returns all pending bytes and empties the slot. No new
   exit route is added.

Boundary conditions this task owns:

- **Unregistered core**: nothing is consulted, nothing is produced, and every
  existing behavior is byte-for-byte what it is today.
- **Existing device responses** (the identification / status-report family)
  keep their current production and drain behavior; they only gain the
  accumulation guarantee, never a change of content or timing.
- **Layering**: the seam is expressed purely in terms `term_core` already
  owns (numeric code, payload text, terminator kind, byte sequences). It
  cannot name a theme, a color type from the GUI layer, or any GUI concept.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: An OSC string terminated by the BEL form reports the BEL
      terminator kind at the dispatch boundary, and one terminated by the ST
      form reports the ST kind; the classification of a non-terminated string
      is deterministic and asserted.
- [ ] AC-2: A responder registered through the seam is consulted for every
      dispatched OSC with the code, the raw payload and the terminator kind,
      and the byte sequences it returns appear verbatim, in returned order, in
      the pending response content.
- [ ] AC-3: With no responder registered, OSC handling produces no response,
      does not panic, and every pre-existing `term_core` test passes
      unchanged.
- [ ] AC-4: Several responses produced within one parse pass all survive to
      the next drain, in production order; a drain returns all pending bytes
      and leaves the slot empty; the existing device-response behavior is
      unchanged.
- [ ] AC-5: The existing color-response formatter remains the only formatter,
      and its inline tests cover boundary components 0x00, 0x7f and 0xff,
      asserting the 8-bit-to-16-bit expansion and the `rgb:rrrr/gggg/bbbb`
      text shape (TS-1).
- [ ] AC-6: `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path crates/term_core/Cargo.toml --lib`
      passes, `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features`
      passes, and `crates/term_core`'s manifest gains no GUI-layer,
      app-crate, or platform-specific dependency (TS-17, TS-18).
- [ ] AC-7: The report states which case SPEC assumption A6 turned out to be:
      the parser already retained the terminator, or retention was added here.

## Test Notes

All tests are inline unit tests inside `crates/term_core`, driven by feeding
byte sequences through the parser — no GUI crate is involved.

- AC-1, AC-2, AC-4: drive both terminator forms through the parser with a
  test-local responder that records its inputs and returns fixed byte
  sequences; assert the recorded inputs and the drained content.
- AC-3: the same drive path without registering a responder.
- AC-5: extend the formatter's existing inline tests rather than adding a new
  test module.
- AC-6 is verified by running the two commands; it is not a code-level test.
- Edge case worth covering: a payload the responder declines (returns
  nothing) must leave the pending content untouched, including when earlier
  content is already pending.
