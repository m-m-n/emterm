# Task Plan: task0006 — Bounded response fan-out for chained color queries

## Provenance

- source: review
- source_ids: [ecb0d586e27282de]
- review_round: 1

## Goal

A single untrusted OSC payload can no longer turn one control sequence into
an unbounded number of response allocations: the number of answers one
dispatch may produce, and the volume of pending response bytes that may
accumulate before a drain, are both capped by declared budgets, and the
remainder is dropped before it is allocated.

## Requirements

FR2, FR4, FR10

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/render/theme.rs` — the palette dispatch that produces one
  response per query token: stop producing once the per-dispatch budget is
  reached, dropping the remaining tokens' answers before allocating them.
- `crates/term_core/src/osc_handler.rs` — the seam that appends responder
  output to the pending response content: enforce the accumulation budget
  there as the second line of defence, so a payload spread across several
  dispatches cannot exceed the total by staying under the per-dispatch cap
  each time.

## Design

Normative background is IMPLEMENTATION.md SC-2, SC-3 (as amended by the
fan-out budget), SC-4, SC-8 and D10. Those are not restated here.

**The amplification.** The OSC payload length limit is large, and a palette
payload may repeat the query token indefinitely within it. Each token
produces its own freshly allocated answer, and nothing drains the pending
content until the whole parse pass finishes. One sequence from any process
writing to the PTY — including a remote host over a forwarded session —
therefore converts a single bounded input into a multiple-of-input transient
allocation and a correspondingly long stall on the thread doing the parse.
This is newly reachable: before the feature, query tokens on this code were
skipped and only small fixed-size device replies could accumulate.

**Where the cap goes.** At the production site, because dropping after
allocation does not remove the amplification — the allocation is the cost.
The producer counts the answers it has emitted for the dispatch in hand and
stops emitting past the budget; the tokens beyond it are consumed by the
existing payload walk exactly as before, they simply produce no answer.

**Why a second budget at the seam.** The per-dispatch cap alone is bypassable
by splitting a payload into many dispatches inside one parse pass. The seam
that owns the pending content is the only place that sees the total, so it
carries a byte budget: once the pending content reaches it, further responses
are dropped rather than appended. This narrows SC-3's accumulation
postcondition, which is why SC-3 is amended rather than silently contradicted.

**Set semantics are untouched.** The budget governs answers only. Every set
element in the payload is applied exactly as today, in payload order,
including elements that appear after the budget is exhausted. A payload that
stays within the budget behaves identically to today in output, in order and
in visible-change reporting.

**Silent by design.** Dropping is not an error condition and is not logged:
the bytes come from an untrusted stream and logging them is itself an
amplification channel (IMPLEMENTATION.md Conventions, "Inert invalid input").

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A single palette dispatch whose payload carries more query tokens
      than the declared per-dispatch budget produces exactly the budget's
      number of answers; the tokens beyond it produce no answer and no
      allocation of an answer.
- [ ] AC-2: Pending response content accumulated at the seam never exceeds
      the declared byte budget within one parse pass, including when the
      producing payload is split across several dispatches each individually
      within the per-dispatch budget.
- [ ] AC-3: A payload within both budgets is unchanged in every observable
      respect: the same answers, in the same payload order, with the same
      terminator, and the same visible-change reporting as before this task.
- [ ] AC-4: Every set element of a payload is applied in payload order
      regardless of whether the answer budget is exhausted, and a query-only
      payload still reports no visible change.
- [ ] AC-5: A pathological chained payload built at the OSC payload length
      limit completes with the pending content bounded by AC-2's budget and
      the answer count bounded by AC-1's budget; the test constructs that
      payload rather than asserting on a small one.
- [ ] AC-6: Both budgets are named constants at their definition sites and
      the tests assert against those constants rather than against literals,
      so changing a budget does not silently void the tests.
- [ ] AC-7: The `term_core` side acquires no GUI-layer dependency and the
      CLI-only build check still passes (NFR4, NFR5).
- [ ] AC-8: Dropping beyond either budget emits no log output and produces no
      error value on the dispatch path.

## Test Notes

- Inline unit tests in each module under test, matching the project's
  existing pattern.
- AC-1 and AC-4 are theme-side unit tests on the dispatch entry point: build
  a payload mixing sets and queries around the budget boundary and assert
  both the answer count and the resulting theme state.
- AC-2 is a seam-side test in `term_core` driven by a test-local responder
  that returns fixed-size byte sequences; it needs no theme and therefore
  runs in the `term_core` crate's own test command.
- AC-5's payload is large; build it programmatically and assert on counts and
  lengths, never by comparing whole byte strings.
- Boundary cases worth covering: exactly at the budget (all answered),
  one past it (last one dropped), zero query tokens (no change from today),
  and a budget-exhausting payload followed by a drain and a fresh small query
  (the budget resets with the pending content, so the later query is
  answered).

## Out of Scope

- Changing the OSC payload length limit itself.
- Any change to which values a query reports or to the answer format.
- Any change to the coalescing gate or the drain sites (task0004).
- Reporting, logging or surfacing a dropped answer to the user.
- The responder carry-over across the off-thread swap (task0005).
