# Task Plan: task0001 — Correct the stale line-523 prose in the ring-push-blank-row-scope test record

## Goal

The two prose passages in the ring-push-blank-row-scope test record that
currently claim, in the present tense, that line 523 of the term_core ring
buffer test file is the survivor-row assertion are rewritten so a reader
re-running the AC-4 / AC-6 mutation reaches the post-scroll survival assertion
directly, while the record's verbatim evidence and YAML structure stay intact.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `test-docs/ring-push-blank-row-scope-test/task0001.tests.yaml` — the two folded-scalar prose passages inside the record's AC-4 and AC-6 entries are rewritten; nothing else in the file changes

## Design

Read IMPLEMENTATION.md first: decisions D1 (hybrid anchoring), D2 (the
protected transcript is a content region), D3 (line numbers re-derived at edit
time) and D4 (prose checks read the parsed scalar) govern this task and are
not restated here.

### Naming

The record's own acceptance criteria are named AC-1..AC-7 and this plan's
criteria are also named AC-n. Throughout this task, the record's entries are
written as "the record's AC-4 entry" and "the record's AC-6 entry".

### What the corrected prose must convey

Two passages change, and each must end up carrying all of the following:

1. The failure location as it was observed at the time of that run — the
   number 523 remains present, but bound to that run rather than to the file's
   present state.
2. An identification of the assertion that survives future line drift: its
   expression, qualified as the **post-scroll survival** assertion so it is
   not confused with the textually identical **pre-scroll anti-vacuity**
   guard that appears earlier in the same test.
3. Optionally, the assertion's current line number — and if one is written, it
   is the number read out of the working tree during this edit (D3), not a
   number copied from this plan, from SPEC.md, or from the originating bug
   report. Those three sources disagree with each other, which is precisely
   the failure this task exists to stop repeating.

The two passages are:

- **The record's AC-6 entry, closing sentence** (FR1): currently states that
  the failing line (523) is a survivor-row assertion and that this matches the
  requirement that the failure not land on a recycled-row assertion. The
  "matches the requirement …" half is still true and is preserved; only the
  identification of the assertion is rewritten.
- **The record's AC-4 entry, `red_reason` prose** (FR2): currently reports the
  failed assertion together with a `path:line:column` location. This
  occurrence is prose, not protected transcript — the classification is
  explicit in SPEC.md — and is corrected the same way as FR1.

### What must not change

- The fenced `cargo test` transcript inside the record's AC-6 entry, including
  its `panicked at …:523:5` line: byte-identical, line for line, in order
  (FR3, D2). This is the evidence of the past run; the 523 in it is correct
  as-is precisely because it is a quotation.
- Every other key of the document: `task_id`, `baseline_failures`,
  `final_failures`, the record's AC-1, AC-2, AC-3, AC-5 and AC-7 entries, and
  every `tests:` and `red_confirmed:` field (FR6).
- The file's YAML shape: it parses as valid YAML after the edit, the folded
  scalars stay folded scalars, and the existing 6-space continuation
  indentation is kept (FR6).
- Every other file in the repository, `crates/term_core/src/ring_buffer/tests.rs`
  above all — it is read-only input to this task (FR7).

### Editing flow

1. Read the current post-scroll survival assertion's line number and its
   pre-scroll twin's line number out of the working tree's term_core ring
   buffer test file. Record both; they are inputs to steps 3 and 5.
2. Capture the pre-change content of the record's transcript block so the
   byte-identity check in step 5 has something to compare against.
3. Rewrite the record's AC-6 closing sentence per "What the corrected prose
   must convey".
4. Rewrite the record's AC-4 `red_reason` location reference the same way,
   keeping its surrounding sentences as they are.
5. Re-check: valid YAML, unchanged key structure, transcript block unchanged,
   diff confined to the two folded scalars, and any current line number
   written in steps 3-4 still matching what step 1 read.

## Test Notes

This task produces no compiled code, so its criteria are checked as assertions
about file state rather than as unit tests. That is TDD-awkward but not
TDD-hostile: every criterion below has a genuine red state before the edit and
a green state after, so the checks are written and run first, observed to fail,
and then made to pass.

- **Red-state availability.** AC-1 and AC-2 fail against the pre-change file
  (the present-tense claims are there); AC-3 and AC-4 fail (no qualifier, no
  re-derived number); AC-5, AC-6 and AC-7 pass before the edit and act as
  regression guards that must still pass after it.
- **Parsed value vs raw bytes (D4).** AC-1, AC-2, AC-3 and AC-6 are checked
  against the YAML-parsed document, because folding wraps a single sentence
  across physical lines and a raw line-oriented search for it finds nothing
  even when the sentence is present. AC-5 and AC-7 are checked against the raw
  file and its diff, because they are byte-level claims.
- **AC-4 procedure.** Re-read the assertion's line number from the working
  tree and compare it against every current-tense number in the new prose.
  Treat a match against a number quoted in this plan or in SPEC.md as no
  evidence at all — the check is against the file.
- **AC-3 and AC-1/AC-2 judgment component.** Whether a qualifier reads as
  "historical" is a wording judgment. Reduce it mechanically first: enumerate
  every occurrence of 523 in the changed file, then classify each as (a)
  inside the protected transcript, or (b) carrying an explicit
  at-the-time-of-that-run qualifier. Any occurrence in neither class fails.
- **No build or test run is required.** No compiled file changes, so the
  term_core build and test commands are not part of this task's evidence; the
  test record for this task states that explicitly rather than reporting an
  unrun command as passed.
