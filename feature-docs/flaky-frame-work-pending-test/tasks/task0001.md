# Task Plan: task0001 — Eliminate the restart-flag order dependence in the `--lib` suite

## Goal

Confirm and record why
`app::tests::timing::frame_work_pending_true_when_restart_flag_raised_and_consumes_nothing`
fails only at cargo's default `--lib` parallelism, eliminate that contention at its
source without weakening or hiding the test, and leave the diagnosis and the chosen fix
side as a durable feature document.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `feature-docs/flaky-frame-work-pending-test/DIAGNOSIS.md` — the record required by FR3 /
  AC-04 / AC-05, in the shape IMPLEMENTATION.md D2 fixes.

### Files to Modify
- `src-tauri/src/self_exec.rs` — owner of the process-global restart-required state, of
  the consuming read / non-consuming peek pair, and of the test-only setter seam; also
  holds its own inline test module, which is one of the contending parties.
- `src-tauri/src/app/tests/timing.rs` — holds the failing test and its sibling tests that
  clear the same state; the app-side contending party.
- `src-tauri/src/app/tests.rs` — the app test-module root; the place a shared app-side
  test helper would be declared if the chosen fix needs one.
- `src-tauri/src/app/mod.rs` — holds the frame pending-work predicate that performs the
  non-consuming observation; touched only if the fix takes the production-side direction.
- `src-tauri/src/app/timing.rs` — holds the per-frame consuming read that arms the restart
  toast; touched only if the fix takes the production-side direction.

Not every file listed above must change: the list is the permitted envelope for either
fix direction (IMPLEMENTATION.md D1), not a checklist. Needing a file outside this set is
a reportable plan deviation.

## Design

### Subject

The frame pending-work predicate is true when any of four terms holds: a toast is already
up, the SFTP progress channel is non-empty, the SFTP duplicate-check result channel is
non-empty, or the restart-required state is raised. The failing test constructs a fresh
App (so the first three terms are false by construction), raises the restart-required
state, and asserts the predicate is true — i.e. it asserts on the fourth term alone.

The restart-required state is **process-global**: it lives in the restart-signal layer
(`src-tauri/src/self_exec.rs`) as one process-wide flag shared by every test in the
`--lib` binary. Its test-only setter's own documentation asserts that "the suite runs
single-threaded", which is false for the default `--lib` invocation — that assumption is
the seed of the defect.

### Starting hypothesis (to confirm, not to assume)

Several parties in the same test binary mutate that one state:

1. the failing test itself raises it, then observes it;
2. three sibling tests in the same app-side test module clear it as their own
   precondition;
3. one further app-side test clears it as its precondition;
4. two tests in the restart-signal layer's own inline test module raise it, then clear it
   — one of them by way of the consuming read, which clears as a side effect of reading.

Candidate mechanism: between the failing test's raise and its assertion, a concurrently
scheduled party clears the state; the observation then returns false, and because the
fresh App makes the predicate's other three terms false, the predicate returns false and
the assertion fails. Under a single test thread no party can interleave into that window,
so the test passes.

**FR1 requires this to be established as fact, not carried as a plausible story.** The
investigation must (a) enumerate every party in the `--lib` binary that raises, clears or
consumes the state — including any indirect raise through the spawn-failure notification
path, which must be checked rather than assumed inert — and (b) establish the mechanism
concretely enough that the record explains why the observation flips, not merely that it
does. If the evidence contradicts the hypothesis above, the record states what the real
contended state is; the hypothesis carries no authority over the evidence.

### Investigation-to-fix flow

1. On the unmodified base state, run the approved default-parallelism `--lib` command and
   record the failure verbatim: command, failing test path, assertion message (TS-02).
   This is the baseline; it must be captured before any source change.
2. Enumerate every party that touches the restart-required state, from the source, and
   classify each as raiser, clearer, consumer or observer.
3. Establish the mechanism connecting an interleaving of those parties to the false
   observation.
4. Choose the fix direction under IMPLEMENTATION.md D1's constraints, and state the
   reason for the choice.
5. Apply the fix so that no party can observe a value it did not itself establish — the
   Shared Components contract in IMPLEMENTATION.md.
6. Land the deterministic regression guard (AC-6).
7. Re-run the approved commands and record the results (AC-3, AC-4, AC-7).
8. Write `DIAGNOSIS.md` (AC-1, AC-2).

### Constraints carried from IMPLEMENTATION.md

- The seam must cover **every** contending party, in both modules (D1).
- The consuming-read / non-consuming-peek distinction is preserved unchanged (D1).
- A panic inside one party's exclusivity span must not convert unrelated tests into
  failures (Shared Components contract).
- The four forbidden resolutions of D3 apply without exception.
- Out-of-scope known flakes are handled per D4.

## Test Notes

- **Approved commands only.** The four commands available to this workflow are the
  whole-suite ones listed in VERIFICATION.md, verbatim; filtered cargo invocations are not
  available. Every step above is expressed so it can be carried out with those commands —
  no step may depend on running a subset of the suite.
- **Baseline first (TS-02).** Capture the failure on the unmodified state before touching
  any source file. Once the fix is in, that evidence cannot be reproduced without undoing
  the work.
- **Diagnosis confirmation (TS-03).** With filtered runs unavailable, the confirmation of
  the diagnosis is carried by two things together: the source-level enumeration of every
  contending party (AC-1) and the deterministic regression guard (AC-6), which must fail
  against the unfixed state. A green suite alone is not evidence that the diagnosis was
  right.
- **Assertion strength (TS-05).** Deliberately break the scenario's precondition, run the
  approved default-parallelism command, observe the target test fail, then revert the
  break and confirm the suite is green again. Record both observations. The break must not
  survive into the final change set.
- **Stability (TS-01) and serial safety (TS-04).** Three consecutive default-parallelism
  runs plus one serial run. Record each summary line. A single green run is not the
  criterion.
- **Feature gate (TS-06).** Run the CLI-only check after the final source state, not
  before — a production-side change is exactly what can break it.
- **New tests are deterministic.** Any test added here that depends on sleeps, timing
  thresholds or thread interleaving would replace one flake with another and fails the
  task's own purpose.
