# Task Plan: task0001 — Redact OSC 9 notification text from both log sites

## Goal

Introduce one module-private redaction renderer (plus its per-run keyed diagnostic ID) in the
callbacks module and rewire both notification log sites to emit only its allow-listed metadata,
so no OSC 9 title or body text ever reaches `emterm.log` while the suppression and dispatch
events stay identifiable and correlatable.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/callbacks.rs` — add the module-private redaction renderer, the diagnostic-ID
  derivation and the process-global per-run hash key; rewrite the rate-limit branch's warn
  record and the dispatch-success branch's debug record to use the renderer. The dispatch-error
  branch and every other statement in the file stay as they are.
- `src-tauri/src/callbacks/tests.rs` — add unit tests for the renderer, the metadata fields and
  the diagnostic ID, and for the marker constant's value. Existing tests in this file are not
  edited.

## Design

### What already exists (do not change it)

- The OSC 9 handler parses the sequence into a (title, body) pair, asks the rate limiter
  whether to emit, and either buffers + dispatches the notification or logs the suppression.
  Every part of that decision flow — the parse, the 1 s dedupe window, the (title, body) key,
  the pending-notification buffering and the sink call — keeps its current behaviour (NFR1).
- The notification sink applies the body-markup escape gate to its two inputs before handing
  them to the OS notification API. That gate, its capability query and its fail-closed
  semantics are not touched (NFR2).
- The release build's warn-and-above file filter lives in the logging module and is out of
  scope; this task relies on it only insofar as the suppression record keeps warn level (FR4).

### What this task adds

Two module-private items, whose contracts are pinned in IMPLEMENTATION.md ("Shared
Components") and whose output shape is pinned in IMPLEMENTATION.md ("Redacted record format").
Implement against those contracts; this plan does not restate them.

1. **Redaction renderer** — takes a (title, body) pair, returns the three-field metadata
   rendering. Pure, total, no I/O, no allocation beyond the returned rendering.
2. **Diagnostic ID derivation** — keyed hash over the pair, rendered as 16 lowercase hex
   characters, under a process-global key created exactly once per run (IMPLEMENTATION.md D3).

### Processing flow after the change

Rate-limit branch:

1. The handler holds the parsed (title, body) pair.
2. The rate limiter reports "suppress".
3. The renderer is called with that pair.
4. One warn record is emitted: the unchanged rate-limit marker constant, a colon and a space,
   then the renderer's output — and nothing else.

Dispatch-success branch:

1. The sink is entered with a (title, body) pair.
2. The renderer is called with those values **before** the escape gate shadows them
   (IMPLEMENTATION.md D2); the rendering is held for later use.
3. The escape gate and the OS notification call run exactly as today.
4. On success, one debug record is emitted: the existing "notify-rust dispatched" literal, a
   colon and a space, then the held rendering — and nothing else.
5. On failure, the existing warn record is emitted unchanged (FR7).

### Constraints the implementation must honour

- Neither new item may be Unix-gated. The escape helpers next to them are; copying that gating
  breaks the Windows build, because the dispatch-success site exists on every platform
  (IMPLEMENTATION.md D4).
- The per-run key is shared by all threads, initialized once, and never logged. Per-call or
  per-thread keying is a defect, not a variant (IMPLEMENTATION.md D3).
- No field may be added to the record beyond the three allow-listed ones, at either site
  (IMPLEMENTATION.md D5).
- No new dependency (NFR4): the keyed hash comes from the standard library's randomly-seeded
  hash-state facility.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A module-private renderer takes a (title, body) pair and returns the metadata
      rendering defined in IMPLEMENTATION.md; for an input pair containing a URL, a token-like
      string and a command line, the returned rendering contains none of those three
      substrings. (TS1)
- [ ] AC-2: The rendering carries the title length and the body length as UTF-8 byte counts for
      a known input pair, in the fixed order, field naming and separator form defined in
      IMPLEMENTATION.md, and carries no fourth field. (TS2)
- [ ] AC-3: The diagnostic ID is 16 lowercase hex characters, is equal for two renderings of
      the same pair within one process run, differs for a pair that differs only in the body,
      and is backed by a key created exactly once per process run that appears in no log
      record. (TS3)
- [ ] AC-4: The rate-limit branch emits, at warn level, the rate-limit marker constant (whose
      value is unchanged) followed by the renderer's output, and binds neither the title nor the
      body into its record. (TS7, TS11)
- [ ] AC-5: The dispatch-success branch emits, at debug level, its existing literal prefix
      followed by a rendering derived from the values the sink received before the escape gate
      transforms them; the dispatch-error branch is unchanged in level and content. (TS10, TS11)
- [ ] AC-6: The existing rate-limiter, OSC 9 parse and body-markup escape tests pass unmodified,
      and `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`
      passes. (TS4, TS5, TS12, TS9)
- [ ] AC-7: `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features`
      passes and no dependency was added to any manifest. (TS8, TS13)

## Test Notes

- Write the renderer's tests first; they are the only mechanical coverage this feature has
  (IMPLEMENTATION.md D6). The two log sites contribute a fixed literal each, so the renderer's
  tests carry AC-1 through AC-3 almost in full.
- New tests belong in a dedicated child module inside `src-tauri/src/callbacks/tests.rs`,
  alongside the existing per-feature test modules, and reach the module-private items the same
  way the existing tests reach the module's other private helpers.
- **Substring assertions**: assert the absence of whole sensitive tokens (the full URL, the full
  token-like string, the full command line). Do not assert per-character absence — a length
  digit or a hex character of the ID will coincidentally match a single character of the input
  and make the test flaky for reasons unrelated to redaction.
- **TS10** (the pre-escape capture premise): render the same body twice, once raw and once in
  the form the escape gate would produce for a body containing markup meta-characters, and
  assert the two renderings differ. This pins *why* the capture point matters; it does not by
  itself prove the site captures at the right point — that part is an AC-5 review check.
- **Not covered by tests, by design**: that the ID is stable across threads (the unit tests run
  the derivation on one thread), and the final text of either log record (no harness captures
  logger output). Both are review/inspection items; do not add a logging harness to close them.
- Keep the existing tests byte-identical. A change to any of them is a signal that behaviour
  moved, which NFR1 forbids.
