# Task Plan: task0001 — Stop hook state を done に変更しテスト期待値を同期

## Goal

The plugin's Stop hook reports state `done` instead of `idle`, and the hook
test suite asserts the new value, so that eMterm's OS notification fires on
response completion and `bun test` stays green against the shipped
`hooks.json`.

## Requirements

FR1, FR2, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

- (none)

### Files to Modify

- `plugins/emterm/hooks/hooks.json` — the Stop entry's `args` value changes
  from `idle` to `done` (currently lines 46-47). No other event entry, and no
  other field of the Stop entry, changes.
- `plugins/emterm/hooks/scripts/notify-status.test.ts` — the `test.each`
  expectation-table row binding the Stop event to `idle` (line 420) changes to
  bind it to `done`. This is the only Stop→`idle` binding in the file; no
  other line changes.

## Design

Behavioural intent: on the Claude Code Stop event, the hook invokes the
existing notify script with the state argument `done` instead of `idle`.
`done` is in eMterm's notification-firing set (Blocked / Done), so the OS
notification becomes reachable; every stage downstream of the state value is
already implemented and is out of scope.

Constraints on the edit (from IMPLEMENTATION.md Conventions):

1. The Stop entry keeps its existing command form — `${CLAUDE_PLUGIN_ROOT}`
   prefix and `timeout 3` (NFR4; the suite's format-validation tests at lines
   424-450 enforce this).
2. The other event bindings are untouched: `UserPromptSubmit` / `PostToolUse`
   / `PostToolUseFailure` stay `working`; `PermissionRequest` /
   `Notification` stay `blocked` (FR1).
3. In the test file, line 175's `ALLOWED_STATES` and line 486's `idle_prompt`
   are unrelated to the Stop binding and are not modified (FR2).
4. Both file edits are one atomic unit (IMPLEMENTATION.md D1): the suite reads
   the real `hooks.json` via its `readHooksJson` helper, so changing only one
   side leaves `bun test` red.

  suite goes red against the still-`idle` `hooks.json` — then change the
  hook definition (AC-1) to bring it green. No new test needs to be written:
  the existing table-driven test reads the shipped `hooks.json`, so it is the
  integration test for this change (VERIFICATION.md TS1).
- AC-3 / AC-4 map to the project's test and build commands; AC-5 is verified
  by inspecting the change set (also covered feature-wide as VERIFICATION.md
  TS3).

  (VERIFICATION.md TS2), not part of this task's automated criteria.
