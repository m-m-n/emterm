# Implementation Plan: benign-edit-test-token-rewrite

## Overview

良性編集の受け入れテストを、プロダクションソーステキストのリテラル複製に依存しない構築方式へ
書き換える。変更は `src-tauri/src/window_host/tests.rs` のインライン `#[cfg(test)]` モジュール
内部に閉じ、プロダクションコードには一切触れない（NFR1 / NFR2）。

本 feature は単一タスク（task0001）で構成される。分割しない判断の根拠は D1 にある。

## Technology Stack

- **Language**: Rust（既存クレート `src-tauri` のインラインテストモジュール）
- **Test runner**: 既存の `cargo test --lib`。新しいテストフレームワークは導入しない。
- **Key libraries**: 追加なし。

### 新規依存のライセンス

本 feature は依存を 1 つも追加しない（NFR1 が proptest / criterion 等の導入を明示的に禁止）。
したがって `project.license: MIT` に対する新たなライセンス制約は発生せず、記録すべき
新規依存のライセンス行も存在しない。

## Layer Structure

`tests.rs` 内部を 3 層として扱い、依存方向を一方向に固定する。

| 層 | 責務 | 本 feature での扱い |
|---|---|---|
| 既存トークンヘルパー層（`call_site_scan`） | ソースのトークン化、呼び出しの探索、実引数 span の分割、トークン列のスプライス、判定 | **無改変で再利用のみ**（NFR1） |
| アンカールーチン層（新規・テストローカル） | ソースバイト上で呼び出しのバイト範囲を構造的に特定し、トークン形状を検証する | 新規追加。`call_site_scan` の内側には置かない |
| テスト関数層 | 良性編集を組み立て、ガードと受け入れをアサートする | 旧テストを置き換える |

依存方向は テスト関数層 → アンカールーチン層 → 既存トークンヘルパー層 の一方向のみ。
逆流（アンカールーチンの機能を `call_site_scan` 側へ追加すること）は NFR1 により禁止する。

各層が依存する既存資産（既存トークンヘルパー群、閉じた集合の定数群、埋め込みソース、判定呼び出しの
アリティ引数）とそれらに対する制約は、単一タスクの内部事項のため task0001 の計画に置く。

## Conventions

### 結合規約（FR1）

- 新規のテストおよびテストヘルパーは、閉じた集合（`run_button_decision`、`handle_mouse_wheel`、
  `mouse_report::apply_outcome_with_held`、`mouse_report::apply_wheel_report_step`、
  `mouse_report::apply_outcome`、`mouse_report_held`）の外側にあるプロダクション識別子を、
  文字列リテラルでも識別子でも名指さない。
- プロダクションのソーステキストを書き写したリテラルを新たに作らない。
- レシーバ識別子は抽出した関数自身の引数集合（`FunctionBody.params`）から取得し、
  ハードコードしない。

### vacuity ガード規約（FR3）

すべての良性編集は、受け入れアサーションを実行する**前に**、自分の入力を実際に変更したことを
アサートする。トークンレベルの編集は「編集後トークン列 != 未編集トークン列」、ソースレベルの
編集は「編集後ソースバイト != 元のソースバイト」で判定する。編集が静かに適用されなかった
場合に緑のままになる経路を作らない。

### 失敗の表出規約（Error Handling）

- アンカー・走査の失敗は、明示的な `Err`、またはテストのアサーション失敗として必ず表面化する。
- 静かに誤ったバイト範囲を返す経路を作らない。
- 入力の想定外（コメント混入、括弧の不均衡）に対してパニックで代替しない。

### テスト規約（NFR3）

- テスト名は `<subject>_<scenario>_<expected>`。
- 決定的かつ並列安全。共有のグローバルフィクスチャを持たず、`include_str!` によるコンパイル時
  埋め込みとローカルな走査器状態のみを使う。`-- --test-threads=1` を必要としない。

### 変更集合規約（NFR2）

- 変更は `src-tauri/src/window_host/tests.rs` のみ。`pointer_routing.rs` / `mouse_report.rs` /
  `event_loop.rs` を含むプロダクションファイルには一切触れない。
- 前 feature の既存テスト（構造テスト群を含む）は緑かつ無改変のまま維持する。

## Design Decisions

### D1: 本 feature を単一タスクとして実装する

**決定**: Class A（ソースバイトに対するアンカー＋スライス編集とアンカールーチン）と Class B
（既存トークンヘルパーによるトークンレベル編集）、および旧テストの撤去を、1 つのタスク
（task0001）に統合する。2 タスクへ分割して並列実装しない。

**根拠**: 分割案（2 タスク並列）と統合案（1 タスク）を比較検討した結果、統合案を採用した。

- 分割案は、Class B が既存ヘルパーと既存定数だけで完結し Class A の成果物を必要としないこと、
  および編集範囲を「旧テストの撤去は Class A 側が単独所有する」「新規テストの挿入点を重ねない」
  という取り決めで分離できることから、並列化の根拠自体はあった。
- しかし両タスクは同一ファイル `src-tauri/src/window_host/tests.rs` を変更するため、上記の
  取り決めは衝突面を縮小するものであって、隣接ハンクのマージが発生する可能性を解消しない。
  衝突リスクが消えたとは判断できない。
- 分割は実装時間を短縮しうるが、衝突時の解消と再確認でその短縮分が相殺される可能性もある。
  各タスクの所要時間の見積もりを持たないため、短縮幅は断定できない。
- 対象が 1 ファイル・合計およそ 160 行という規模であることを踏まえると、不確かな時間短縮より、
  統合の手間と不確実性を減らすことを重く見るべきと判断した。

**帰結**: 分割を前提にしていた取り決め（旧テスト撤去の単独所有、新規テストの挿入点の分離）は
タスク間の契約ではなくなり、単一タスク内部の実装順序の話に降格する。task0001 の Design に
「実装順序の指針」として置き直した。また、複数タスクが同一のコンポーネントを共有する構図が
消えたため、本書の `## Shared Components` 節は不要になり削除した。既存資産に対する制約は
task0001 の Design へ移した。

**トレードオフ**: task0001 の受け入れ条件は 9 件となり、タスク分割の通常の目安（約 7 件）を
超える。これは上記の比較の結果として意図的に受け入れたものであり、目安の見落としではない。
実装時は AC 単位ではなくテストシナリオ単位（TS-5 → TS-6 → TS-7 → TS-3 → TS-4 → TS-1 → TS-2）で
TDD サイクルを回すことで、1 セッション分の作業として扱える粒度に保つ。

**影響**: task0001。

### D2: 撤去と追加を一度の置き換えとして行う

**決定**: 旧テスト `button_path_benign_edits_to_the_real_source_are_still_accepted`
（`tests.rs:6825-6888`）とその 3 つのソースリテラル（`:6832` / `:6859` / `:6860`）、およびそれらを
守る `src.contains(...)` sanity アサーションの撤去は、新しいテスト群への置き換えとして一度の
編集で行う。

**根拠**: 撤去を先行させると、良性編集のカバレッジが一時的に失われた状態がコミット境界に残る。
本 feature の目的は「カバレッジを保ったまま構築方式を書き換えること」であり、カバレッジが欠けた
中間状態を成果物として残さない。

**影響**: task0001。

### D3: 走査モジュールを凍結する（NFR1）

**決定**: `call_site_scan` モジュールに範囲情報を持つ字句走査器を追加しない。Class A の位置決定は
独立したテストローカルのアンカールーチンで行う。既存ヘルパーはシグネチャ・意味論とも無改変で
再利用する。

**根拠**: NFR1 の明示的な制約であり、かつ前 feature のテスト群が既存ヘルパーの現在の意味論に
依存しているため。

**影響**: task0001。

### D4: 新規依存を追加しない

**決定**: 外部依存・テストフレームワーク依存をゼロに保つ。否定テスト（TS-5 / TS-6 / TS-7）は
プロパティテストではなく、メモリ内に組み立てた入力に対する通常のユニットテストで行う。

**根拠**: NFR1 の明示的な制約。加えて依存ゼロであれば `project.license: MIT` に対する
ライセンス互換性の検討そのものが不要になる。

**影響**: task0001。

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| アンカーが意図しない呼び出し箇所に着地し、テストが空虚に緑のまま通る（EC-3） | 中 | 高 | FR4(c) のトークン形状アサーション（呼び出し先パス + トップレベル実引数ちょうど 4 個）を必須とし、TS-5 でガード自体の非空虚性を固定する |
| 良性編集が静かに適用されず、テストが空虚に緑のまま通る | 中 | 高 | 全編集に vacuity ガードを必須化（vacuity ガード規約）し、AC-7 で検証する |
| 括弧深度走査がコメント内の不均衡な括弧で壊れ、誤った範囲を静かに返す（EC-2） | 中 | 中 | 失敗の表出規約に従い明示的な失敗を返す（またはコメント対応の走査とする）。TS-7 で固定する |
| 書き換えの過程で閉じた集合外の新しいリテラルを作り込み、FR1 の目的を再び壊す | 中 | 高 | 結合規約を AC-1 に落とし、verify 時に AC-2（SPEC 側）で再確認する |
| 既存ヘルパーに手を入れて前 feature のテストを巻き込む | 低 | 高 | D3 の凍結決定と変更集合規約。verify 時に既存テストが緑かつ無改変であることを確認する |
| 単一タスクの作業量が 1 セッションに収まらず、途中で息切れする | 低 | 中 | D1 のとおり TDD サイクルを TS 単位で回す。7 本のテストはいずれも独立して緑にできるため、部分的な進捗が失われない |
| 撤去だけが先行し、カバレッジが欠けた中間状態が残る | 低 | 中 | D2 のとおり撤去と追加を一度の置き換えとして行う |
