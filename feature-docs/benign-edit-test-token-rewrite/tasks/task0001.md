# Task Plan: task0001 — 良性編集テストを閉じた集合のみに結合する構築方式へ書き換える

## Goal

良性編集の受け入れテストを、プロダクションソーステキストのリテラル複製に依存しない構築方式へ
全面的に書き換える。4 種の良性編集（実引数リストの再折り返し、コメント挿入、末尾カンマ、
独立した 2 文の並べ替え）を実際に埋め込んだプロダクション本体に対して行使しつつ、vacuity と
mislocation の 2 つのサイレント失敗モードに対するガードを追加する。

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

なし。

### Files to Modify

- `src-tauri/src/window_host/tests.rs` — 旧良性編集テスト
  （`tests.rs:6825-6888`）とその 3 つのソースリテラル（`:6832` / `:6859` / `:6860`）および
  それらを守る `src.contains(...)` sanity アサーションを撤去し、その位置にアンカールーチンと
  Class A のテスト群（TS-3 / TS-4）、アンカールーチンの否定テスト（TS-5 / TS-6 / TS-7）、
  および Class B のテスト群（TS-1 / TS-2）を置く。

## Design

IMPLEMENTATION.md の Layer Structure / Conventions / Design Decisions に従う。ここでは本タスク
固有の内容のみを述べる。本 feature は単一タスクで構成されるため、Class A 経路・Class B 経路・
旧テストの撤去はすべて本タスクの内側で完結する。

### 依存する既存資産と、それらに対する制約

いずれも本 feature の base revision に既に存在する。**無改変で利用する**ことが制約である。

| 既存資産 | 責務 | 本タスクが守る契約 |
|---|---|---|
| 既存トークンヘルパー群（`find_calls` / `contains_token_sequence` / `split_arg_spans` / `splice_tokens` / `judge_call`） | ソースのトークン化・呼び出し探索・実引数分割・スプライス・判定 | シグネチャも意味論も変更しない。前 feature のテスト群から見た振る舞いが本タスク適用後も変わらないこと（NFR1 / NFR2） |
| 閉じた集合の定数群（`HELD_AWARE_BUTTON_CALLEE` / `HELD_FIELD` / `HELD_UNAWARE_CALLEE` ほか、`tests.rs:5992-5999`） | 本 feature が結合してよいプロダクション名の唯一の宣言 | 値を上書き・再定義しない。新規テストがプロダクション名を参照する経路はこの定数群のみとする（レシーバ識別子は例外として、抽出した関数の `FunctionBody.params` から取得する） |
| 埋め込みソース（`include_str!("pointer_routing.rs")`） | 良性編集の対象となる実プロダクション本体 | 良性編集は手書きの代用物ではなく、この埋め込みソースから抽出した本体に対して行使する |
| 判定呼び出しのアリティ引数（`tests.rs:6028-6036` と同一の組） | 編集後の成果物を受理する判定条件 | 未編集本体を判定するときと同じ定数・同じアリティ引数を使う |

### アンカールーチンの責務と契約（Class A 経路）

テストモジュール内のプライベートなルーチンとして実装する。`call_site_scan` モジュールの内側には
置かない（IMPLEMENTATION.md D3）。

**責務**: 埋め込みソース全体・外側の関数名・呼び出し先の名前・期待するトップレベル実引数の個数を
受け取り、その呼び出しのバイト範囲（実引数リストの範囲を含む）を返す。

**事前条件**:
- 与えられたソースは有効な Rust ソーステキストである。
- 外側の関数名と呼び出し先の名前は、閉じた集合の定数から供給される（テスト側でリテラルを
  作らない）。呼び出し先については、可能な範囲で完全修飾パスではなく素のセグメントに
  アンカーする（SPEC の A2 / FR4d。ただし選好であって必須ではなく、閉じた集合の定数を
  上書きしない）。

**事後条件（成功時）**:
- 返されたバイト範囲は、外側の関数の本体の内側にある当該呼び出し **1 箇所** を指す。
- 返された範囲のトークン形状が「呼び出し先パス + トップレベル実引数ちょうど N 個」に一致する
  ことを、返す前に検証済みである（FR4c）。
- 返された範囲から、実引数テキストのバイト範囲を個別に取り出せる。

**事後条件（失敗時）**:
- 明示的な失敗（`Err`、またはテストのアサーション失敗）として表面化する。
- 誤った関数・誤った呼び出し箇所を指す範囲を、静かに成功として返さない。
- パニックを失敗表現の代替として使わない。

### 位置決定の流れ（FR4a）

1. 与えられたソースから、外側の関数名の定義位置を構造的に特定する。`fn` キーワードと関数名の
   対応が壊れている入力（間にブロックコメントが挟まる等）は、誤った関数にアンカーせず明示的な
   失敗にする（EC-1）。
2. その関数本体の内側で、呼び出し先の名前の出現位置を探す。
3. 呼び出し先の名前に続く開き括弧から、括弧深度で対応する閉じ括弧まで走査し、呼び出しの
   バイト範囲を確定する。コメント内の不均衡な閉じ括弧に走査が壊される入力は、明示的な失敗に
   するか、コメントを認識して正しい範囲を返すかのいずれかとする。静かに誤った範囲を返さない
   （EC-2）。
4. 確定した範囲のトークン形状を検証する。ボタン経路では N = 4（FR4c）。

### 編集後ソースの構築（FR4b）

編集後ソースは「元ソースの範囲開始まで」「編集で挿入する前置部分」「元ソースの実引数範囲を
そのまま持ち回した部分」「編集で挿入する後置部分」「元ソースの範囲終了以降」の連結として
構築する。実引数のテキストをテスト側で書き直さない。この構築方式により、実引数の個数・既存の
インデント幅・レシーバ識別子のいずれもテスト側が知る必要がなくなる。

- TS-3（再折り返し）: 実引数の前後の空白・改行のみを差し替える。
- TS-4（コメント挿入）: 呼び出し先と開き括弧の間にブロックコメントを挿入する。同じアンカー・
  同じスライス経路を使う。

構築した編集後ソースを再トークン化し、外側の関数の本体を再抽出したうえで、未編集本体を判定する
ときと同じ定数・同じアリティ引数で判定を行う。結果は `Ok` であること（FR5）。

### トークンレベル編集の流れ（Class B 経路、FR2）

1. 埋め込みプロダクションソースから、外側の関数の本体を抽出する。
2. 抽出した本体のトークン列に対して編集を行う。構築には既存トークンヘルパーを無改変で用いる。
3. 編集後のトークン列をそのまま判定へ渡す。ソーステキストへ戻して描画しない。

- TS-1（末尾カンマ）: held 対応呼び出しを特定し、その実引数リストの末尾にカンマトークンを
  追加したトークン列をスプライスで生成する。末尾カンマが実引数の個数を変えないこと（実引数
  分割から見える個数が依然 4 個であること）をアサートする。これは「編集が主張どおり意味的に
  等価である」ことの確認であり、vacuity ガードとは別物である（FR5 / EC-4）。
- TS-2（文の並べ替え）: 並べ替える 2 文を **構造的に** 選ぶ。ソーステキストの照合で選ばない。
  選択の手がかりはトークン走査から得られるもの（たとえば本体内で隣接するトップレベルの `let`
  文 2 つ）に限り、文の中身に現れるプロダクション識別子をリテラルとして持たない。並べ替え
  対象は互いに独立した 2 文であり、判定対象の held 対応呼び出しではないこと。

### 旧テストの撤去（FR1）

旧良性編集テストと、その 3 つのソースリテラル、およびそれらのリテラルを守るためだけに存在する
`src.contains(...)` sanity アサーションを削除する。置き換えのテストは、IMPLEMENTATION.md の
結合規約に従い、閉じた集合の外側の識別子を新たに名指さない。レシーバ識別子が必要な場合は
抽出した関数の引数集合から取得する。

撤去と追加は、旧テストが占めていた領域を新しいテスト群で置き換える一度の編集として行う。
撤去だけを先に済ませて良性編集のカバレッジが一時的に失われる状態を、コミット境界に残さない。

### 実装順序の指針

並列化のための分割ではなく、手戻りを減らすための順序として次を推奨する。

1. アンカールーチンの否定テスト（TS-5 / TS-6 / TS-7）を先に書き、失敗表現（明示的な `Err` か
   アサーション失敗か）の設計を先に固定する。
2. アンカールーチンの成功経路を通し、Class A のテスト（TS-3 / TS-4）を書く。
3. Class B のテスト（TS-1 / TS-2）を書く。この経路は既存ヘルパーと既存定数だけで完結し、
   アンカールーチンを必要としないため、1・2 と独立に着手してもよい。
4. 旧テストの撤去を、上記の置き換えとして確定する。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: 旧良性編集テストとその 3 つのソースリテラル（`tests.rs:6832` / `:6859` / `:6860`）、
      およびそれらを守る `src.contains(...)` sanity アサーションが `tests.rs` から消えている。
      本タスクが追加したテスト・ヘルパーは、Class A / Class B のいずれについても、閉じた集合の
      6 名の外側にあるプロダクション識別子をリテラルでも識別子でも名指していない。レシーバ
      識別子は抽出した関数の引数集合から取得している。（FR1）
- [ ] AC-2: アンカールーチンが、行番号にも呼び出しテキストの部分文字列照合にも依存せず、
      「外側の関数名 → 呼び出し先の名前 → 開き括弧からの括弧深度走査」の順で呼び出しの
      バイト範囲を返す。（FR4a）
- [ ] AC-3: アンカールーチンが、範囲を返す前にその範囲のトークン形状（呼び出し先パス +
      トップレベル実引数ちょうど 4 個）を検証し、一致しない場合は静かに範囲を返さず明示的な
      失敗を報告する。実引数の個数が異なる／呼び出し先が異なる形状に対して、この検証が実際に
      失敗を返すことをテストで示している。（FR4c、TS-5）
- [ ] AC-4: `fn` キーワードと関数名の間にブロックコメントが挟まる入力、および実引数リスト内の
      コメントに不均衡な閉じ括弧を含む入力のいずれに対しても、アンカールーチンがパニックせず、
      誤った範囲を静かに返さず、明示的な失敗を返す（あるいはコメントを認識して正しい範囲を
      返す）。（FR4、TS-6、TS-7）
- [ ] AC-5: 再折り返し編集とコメント挿入編集が、元ソースバイトのスライス連結で構築されており、
      編集後ソース中の実引数テキストが元の実引数テキストとバイト単位で同一である。（FR4b）
- [ ] AC-6: 末尾カンマ編集と文の並べ替え編集が、埋め込みプロダクションソースから抽出した本体に
      対して既存トークンヘルパー（`find_calls` / `split_arg_spans` / `splice_tokens`）で構築されて
      いる。末尾カンマ編集は実引数の個数が依然 4 個であることをアサートし、並べ替え編集は 2 文を
      ソーステキスト照合ではなくトークン走査から構造的に選ぶ。いずれも編集後のトークン列を
      そのまま判定へ渡し、ソーステキストへ戻して描画する経路を持たない。（FR2）
- [ ] AC-7: 4 種すべての良性編集が、受け入れアサーションの **前** に vacuity ガードを持つ。
      Class A は「編集後ソースバイト != 元のソースバイト」、Class B は「編集後トークン列 !=
      未編集トークン列」で判定し、編集が適用されなければテストが赤になる。（FR3）
- [ ] AC-8: 4 種すべての良性編集の後も、未編集本体を判定するときと同じ閉じた集合の定数・同じ
      アリティ引数で判定が `Ok` を返す。Class A については編集後ソースから外側の関数の本体を
      再抽出できている。閉じた集合の定数を上書き・再定義していない。（FR5）
- [ ] AC-9: `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`
      がパスし、`CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features`
      がパスする。本タスクの差分は `src-tauri/src/window_host/tests.rs` のみで、`call_site_scan`
      の既存ヘルパーと前 feature の既存テストは無改変のまま緑である。テスト名は
      `<subject>_<scenario>_<expected>` に従い、テストは `-- --test-threads=1` を必要としない。
      新しい依存を追加していない。（NFR1、NFR2、NFR3、NFR4）

## Test Notes

- すべてユニットテスト。新しい結合テストのコンパイル単位を追加しない（NFR1）。
- TS-1 / TS-2 / TS-3 / TS-4 は実際の埋め込みプロダクション本体に対して編集を行使する。手書きの
  代用ソースで置き換えない。
- TS-5 / TS-6 / TS-7 はメモリ内に組み立てた入力に対する否定テスト。プロパティテスト用の依存を
  導入せず、通常のユニットテストとして書く（IMPLEMENTATION.md D4）。
- TS-5 は AC-3 のガードが空虚でないこと（実際に失敗を返せること）を示すためのものであり、
  ガードのコードを書いただけでは満たされない。
- vacuity ガード（AC-7）は受け入れアサーションより **前** に置く。順序が逆だと、編集が適用され
  なかった場合に空虚な緑を出す。
- TS-1 の「実引数の個数が変わらない」アサーションは、既存の実引数分割ヘルパーが保証している
  性質の再確認であり、vacuity ガードとは別の観点として独立して書く（EC-4）。
- 文の並べ替えで選ぶ 2 文は互いに独立している必要がある。依存関係のある 2 文を選ぶと「良性編集」
  という前提そのものが崩れる。選択規則を構造的な条件として書き、選べなかった場合は静かに
  スキップせず明示的に失敗させる。
- TDD で書きにくい点: アンカールーチンの成功経路は、否定テストを先に書いてから成功経路を通すと
  失敗表現の設計が先に固まって手戻りが少ない（Design の実装順序の指針を参照）。
- 並列安全性の確認は、テストが共有の可変フィクスチャを持たないことをレビューで担保する。
  `-- --test-threads=1` を前提にしたテストを書かない。
- 本タスクは受け入れ条件が 9 件あり、通常の分割目安（約 7 件）を超える。これは意図的な判断で
  あり、根拠は IMPLEMENTATION.md の D1 にある。TDD のサイクルは AC 単位ではなく TS 単位
  （TS-5 → TS-6 → TS-7 → TS-3 → TS-4 → TS-1 → TS-2）で回すのが扱いやすい。

- 新しいテストフレームワーク依存（proptest / criterion 等）の導入。NFR1 により禁止。
