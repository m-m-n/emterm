# Task Plan: task0001 — Default the mux window list to overlay display

## Goal

A session with no saved preference for the mux window list shows it as an overlay instead of a
persistent right-hand panel, while sessions that explicitly saved the persistent choice keep it.

## Requirements

FR1, NFR3

## Scope

### Files to Create

(none)

### Files to Modify

- `crates/app_settings/src/settings.rs` — the mux settings' display-mode default value and the unit
  tests that pin it
- `src-tauri/src/settings.rs` — the mirrored app-side default and the loader tests that pin it

## Design

The display mode is a single persisted boolean under the mux settings group
(`mux.window_sidebar_overlay`): true selects the floating overlay card, false the always-present side
panel. Two independent definitions of its default exist and must agree:

1. The serde-facing settings schema in the settings crate, whose default is used when the key is absent
   from the settings file.
2. The app-side runtime settings struct's default, which is the starting point the loader overlays parsed
   values onto — the loader treats an explicitly-null value as "not specified", so null must resolve to
   the same default as absent.

Both defaults become "overlay". Nothing else about the field changes: its name, its serialization, its
position in the group, and the settings-panel toggle that edits it all stay as they are. The TypeScript
side carries only the field's type, not a default, so it needs no change.

Existing unit tests assert the previous default in three shapes — missing key, explicit null, and a
round-trip through serialization. Their intent (the default is applied when unspecified; an explicit
value always wins) stays valid and must be preserved; only the expected default value flips. Do not
delete these tests, and keep at least one test per shape.

Behavioral consequence to respect: because the loader distinguishes absent/null from present, a settings
file that stores false continues to select the persistent panel (IMPLEMENTATION.md D3).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Deserializing an empty mux settings object yields the overlay display mode.
- [ ] AC-2: Deserializing the mux settings with the display-mode key explicitly null yields the overlay
      display mode (the loader path, matching AC-1).
- [ ] AC-3: Deserializing the mux settings with the display-mode key explicitly false yields the
      persistent display mode.
- [ ] AC-4: Deserializing the mux settings with the display-mode key explicitly true yields the overlay
      display mode.
- [ ] AC-5: A round trip (serialize the default settings, deserialize the result) preserves the overlay
      display mode, and a round trip of an explicitly-persistent value preserves the persistent mode.
- [ ] AC-6: The whole settings crate test suite and the app-side settings tests pass, with no test
      deleted or weakened to accommodate the new default.

## Test Notes

- All criteria are unit tests in the two files being modified, alongside the existing tests for this
  field; follow their existing arrangement and naming style, updating names that state the old default.
- AC-2 belongs to the app-side loader tests (the null-handling path lives there); AC-1, AC-4, AC-5 belong
  to the settings crate; AC-3 is worth having on both sides since it is the compatibility guarantee.
- No TDD awkwardness: the change is a default value, and every criterion is a direct deserialization
  assertion.

## Out of Scope

- Any change to the overlay's appearance, opacity, or open/close behavior (task0002 owns all of it).
- The initial open/closed state of the overlay card — that is runtime state, not a persisted setting, and
  belongs to task0002.
- Adding, renaming, or removing any settings key; changing the settings panel UI or its translations.
- Touching the TypeScript settings types or their tests.
