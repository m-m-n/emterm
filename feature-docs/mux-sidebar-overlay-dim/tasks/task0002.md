# Task Plan: task0002 — Auto-dim the overlay window list when idle

## Goal

The overlay mux window list is fully legible while the pointer hovers it or just after a window switch,
and fades to a low opacity otherwise so terminal text behind it can be read — with the frame scheduling
needed for those transitions to actually appear, and without any repaint once it has settled.

## Requirements

FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR10, NFR1, NFR2, NFR4

## Scope

### Files to Create

(none)

### Files to Modify

- `src-tauri/src/app.rs` — dim state (hover flag, last-switch instant, fade bookkeeping), the opacity
  resolver, the wait-deadline contribution, the initial open state of the overlay card, and recording a
  window switch in the mux action dispatch and the sidebar-switch event path
- `src-tauri/src/ui/mux_sidebar.rs` — accept an opacity input and apply it to the whole overlay card; the
  persistent variant ignores it
- `src-tauri/src/render/mod.rs` — pass the resolved opacity into the overlay draw call
- `src-tauri/src/window_host.rs` — feed the pointer position into the hover flag, include dim work in the
  frame-skip gate's overlay-work input, arm the wait deadline, and request a redraw when the hover
  predicate changes

## Design

### State and resolution (app layer)

The app owns three pieces of runtime state: whether the pointer is currently inside the overlay card,
when the last mux window switch happened, and enough bookkeeping to interpolate the fade (the opacity the
card had when it started leaving the bright state, and when that transition began). None of it is
persisted.

The resolver is a pure function of that state (IMPLEMENTATION.md D1). Its contract:

- **Precondition**: none; every input may be absent.
- **Postcondition**: returns an opacity clamped to the inclusive range zero-to-one, plus an indication of
  whether a further frame is required to continue an in-flight fade.
- **Bright condition**: the pointer is inside the card, OR a switch was recorded and less than the bright
  hold duration has elapsed since it. Bright resolves to full opacity immediately, with no interpolation
  (D4).
- **Dim condition**: neither of the above. The value interpolates from whatever it was when the bright
  condition stopped holding, toward the idle opacity, over the dim fade duration, and stays at the idle
  opacity afterwards.
- **No switch recorded yet**: treated as "not recently switched" — a freshly started session is dim
  (FR5).
- **Precedence**: hover and hold are independent sufficient conditions; releasing hover inside the hold
  window keeps the card bright for the remainder of the hold (SPEC.md A5).

Three new named constants live next to the resolver (IMPLEMENTATION.md conventions, NFR2): the idle
opacity, the dim fade duration, and the bright hold duration. Their values are given in SPEC.md's
"Concrete values" table. The pre-existing bright fill alpha of the card keeps its current value and its
current location — do not move it and do not change it.

A window switch is recorded (timestamp set to now) in two places: the mux action dispatch, for the
next-window / previous-window / select-window-by-digit actions, and the path that handles a switch
requested by the sidebar itself (a row click). Any later switch overwrites the timestamp, which is what
makes a rapid sequence extend brightness (FR4).

The overlay's runtime open flag starts open rather than closed (FR2), so a default-configured session
shows the list without a toggle press. The toggle action keeps its current behavior untouched (FR9,
verified by not modifying it).

### Deadline contribution (app layer)

Alongside the existing per-concern deadline providers (cursor blink, bell, toast), the app exposes the
next instant at which this feature needs a frame: the hold expiry while a hold is pending, or the next
fade step while a fade is in flight. When the card is settled — no hover, hold expired, fade complete —
or when the overlay is not being shown at all, it contributes nothing (NFR1).

### Rendering (draw layer)

The overlay draw path takes the resolved opacity as an input and applies it once, at the card's container
level, so the fill, row text, badges, icons and elevation shadow all fade together (FR6,
IMPLEMENTATION.md D2). Use the toolkit's own whole-widget opacity facility rather than multiplying
individual colors — the module is forbidden from gaining raw color constructors, and hand-multiplying
would scatter the factor.

At full opacity the rendered result must be indistinguishable from today's overlay: same corner radius,
same fill produced by the same state-layer helper and alpha, same elevation shadow, same geometry. The
persistent variant ignores the opacity input entirely and stays fully opaque (FR10).

### Scheduling (winit host)

Three additive changes (IMPLEMENTATION.md D5):

1. **Hover feed** — the host already tracks the pointer position and already calls the sidebar's hit test
   for press routing and wheel routing; reuse that same hit test, evaluated against the overlay
   placement, to maintain the app's hover flag. The hit test and the click routing must agree on the
   boundary so the two cannot disagree about a pointer exactly on the edge.
2. **Frame-skip gate** — the expression that tells the gate "there is overlay work to do" gains this
   feature's condition: a fade is in flight, or a pending hold has just expired. Without this, frames on
   an otherwise-clean grid are skipped and the fade never appears (FR8).
3. **Wait deadline and redraw** — the deadline computation includes the app's new contribution so the
   event loop wakes for it via the wait-until path; note that the repaint-after request used by the UI
   toolkit does not reach this event loop in release builds, so the wait-until path is the only working
   mechanism. Separately, because bare pointer motion is deliberately excluded from "actionable input", a
   transition of the hover predicate (outside→inside or inside→outside) must itself request a redraw.

### Non-goals inside the touched files

Do not alter the card's geometry, width, placement, row layout, badge content, copy-icon behavior, the
toggle action, or the persistent panel's appearance.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With no hover and no recorded switch, the resolver returns the idle opacity; with hover, it
      returns full opacity regardless of the switch timestamp; with a switch recorded just now and no
      hover, it returns full opacity.
- [ ] AC-2: With no hover and a switch recorded longer ago than the bright hold plus the fade duration,
      the resolver returns exactly the idle opacity; sampled part-way through the fade it returns a value
      strictly between the idle opacity and full opacity; entering the bright state returns full opacity
      immediately with no interpolation.
- [ ] AC-3: A second switch recorded inside the hold window keeps the card bright past the first
      switch's expiry; releasing hover while a hold is still pending keeps the card bright until that
      hold expires.
- [ ] AC-4: The resolver's output is always within the inclusive zero-to-one range for every input
      combination, including a hold or fade origin in the future or far past.
- [ ] AC-5: The deadline contribution is absent when the card is settled (no hover, hold expired, fade
      complete) and when the overlay is not shown, and present while a hold is pending or a fade is in
      flight.
- [ ] AC-6: Each of the next-window, previous-window and select-window-by-digit actions records a switch
      timestamp, and so does the sidebar-originated switch path.
- [ ] AC-7: The overlay's runtime open flag is open on a freshly constructed app state.
- [ ] AC-8: At full opacity the overlay card's appearance is unchanged — the existing expectations for
      its corner radius and fill alpha still hold — and the persistent variant renders fully opaque no
      matter what opacity value is supplied.
- [ ] AC-9: The frame-skip gate's overlay-work input is true while a fade is in flight on an otherwise
      clean grid and false once settled; a hover-predicate transition requests a redraw.
- [ ] AC-10: The module-level source constraint of the sidebar module is still satisfied (no raw color
      constructors), the full library test suite passes, and the no-default-features build still checks
      cleanly.

## Test Notes

- AC-1 through AC-5 are pure unit tests over the resolver and the deadline provider: construct the state
  directly with chosen instants rather than sleeping. Derive the "far past" instants by subtracting the
  constants, so the tests stay correct if the constants are retuned.
- AC-6 and AC-7 are unit tests over the app's action dispatch and its initial state; follow the existing
  test arrangement for mux action dispatch in that file.
- AC-8 extends the sidebar module's existing rendering tests; keep the current pinned expectations intact
  and add the persistent-ignores-opacity case rather than rewriting them.
- AC-9 is best tested at the level of the gate's and deadline's input functions rather than by driving a
  real event loop: the host's skip-gate and deadline helpers are plain functions taking their inputs.
- Boundary cases worth explicit tests: exactly at the hold expiry, exactly at fade completion, pointer
  exactly on the card boundary (shared hit test), and the overlay closed while a fade was in flight
  (resolving to a defined value with no stale fade left armed).
- TDD-awkward area: the actual on-screen fade cannot be asserted automatically. Everything decidable is
  pushed into the resolver and the two host helper functions so the untestable remainder is a single
  parameter hand-off; visual confirmation is left to the manual section of VERIFICATION.md.
