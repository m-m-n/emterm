# Task Plan: task0001 — 通知シンクにおける body-markup ケイパビリティ連動のマークアップエスケープ

## Goal

`NotifyRustSink::send` が notify_rust の `.body()` に本文を渡す直前で、通知サーバーが `"body-markup"` ケイパビリティを報告する場合に限りマークアップメタ文字（`&` `<` `>`）をエスケープし、OSC 0/2 由来タイトルによるマークアップインジェクションを全通知経路で防ぐ。

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3

## Scope

### Files to Create

- なし

### Files to Modify

- `src-tauri/src/callbacks.rs` — `NotifyRustSink::send`（:145）にケイパビリティ判定とエスケープ適用を追加。エスケープ変換とケイパビリティ結果解釈の 2 つの純関数ヘルパーを同ファイル内（`NotifyRustSink` 近傍）に追加
- `src-tauri/src/callbacks/tests.rs` — 純関数ヘルパーのユニットテスト（TS1〜TS5 相当）を追加

## Design

実装位置の決定（案 (b)）と、その理由・キャッシュ方針・純関数分離は IMPLEMENTATION.md の D1 / D2 / D3 を参照。本タスクはそれを次の 3 コンポーネントで実現する。

### コンポーネント 1: マークアップエスケープ変換（純関数）

- 入力: 任意の文字列。
- 処理: `&` → `&amp;` を**最初に**置換し、その後 `<` → `&lt;`、`>` → `&gt;` を置換する。
- 事後条件: 出力に生の `<` `>` は存在しない。`&` は変換が生成した実体参照の先頭としてのみ現れる。入力に元々含まれていた `&amp;` は `&amp;amp;` になる（二重エスケープの曖昧さ排除）。
- プラットフォーム: Linux 送出フローからのみ使用するため、既存のゲート規約に従い Unix 側に置く（Windows ビルドに未使用コードを残さない）。

### コンポーネント 2: ケイパビリティ取得結果の解釈（純関数）

- 入力: ケイパビリティ取得の結果（成功時はケイパビリティ名の一覧、失敗はその旨）。
- 出力: `"body-markup"` が確認できたか否かの二値。
- 事後条件: 成功かつ一覧に `"body-markup"` が含まれる場合のみ「確認済み」。取得失敗・一覧に不在の場合は「未確認」（フェイルセーフはエスケープしない側。FR3）。

### コンポーネント 3: `send` 内の適用フロー（薄いアダプタ）

`NotifyRustSink::send` の Linux（Unix）側フロー:

1. notify_rust の `get_capabilities()` を呼び、結果をコンポーネント 2 で解釈する（送出ごとに問い合わせ。キャッシュしない — IMPLEMENTATION.md D2）。
2. 「確認済み」の場合のみ、本文をコンポーネント 1 で変換する。
3. summary（タイトル）は無変更のまま、（必要に応じ変換した）本文を `.body()` に渡して送出する。既存のエラーログ挙動は変えない。

制約:

- Windows 側の送出フローは字面上も無変更（FR5）。notify_rust のケイパビリティ取得 API は XDG プラットフォーム限定のため、判定・エスケープのコードは `#[cfg(unix)]` 配下に置くことがコンパイル上も必須。
- `NotificationSink` トレイトのシグネチャは変更しない（呼び出し元 4 経路すべてに影響しないこと）。
- 本文はシンク到達時点で上流の `sanitize_title` による 100 文字トランケートを終えているため、エスケープは常にトランケート後になる（FR2）。エスケープ結果が 100 文字を超えるのは正当であり、シンクで再トランケートしない。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS1): タイトル `<a href="https://attacker.invalid">Sign in</a>` を含む本文が、「確認済み」時に解釈可能なマークアップを一切含まないエスケープ済みリテラルテキストになる（生の `<` `>` が残らない）。
- [ ] AC-2 (TS2): 既に `&amp;` を含む入力が `&amp;amp;` になる（`&` 先行の置換順序が固定されている）。
- [ ] AC-3 (TS3): 100 文字超で境界付近にメタ文字を持つタイトルを共有パイプライン（`sanitize_title`）に通した後にエスケープすると、実体参照が途中で分断されず完全な形で現れる（結果が 100 文字を超えることは正当）。
- [ ] AC-4 (TS4): 「未確認」（`"body-markup"` 不在、または取得失敗）の場合、本文は入力と同一のまま渡される（`&amp;` が可視化される変換が起きない）。
- [ ] AC-5 (TS5): タブアクティビティ経路の本文（`sanitize_title` + `notification_body`）とエージェント経路の本文（`agent_notification_body`）のいずれも、シンク側のエスケープ判定を通すと「確認済み」時にエスケープされる（両経路が単一チョークポイントで覆われている）。
- [ ] AC-6 (TS6/TS7): `src-tauri/src/notifications.rs` は無変更で、既存の `sanitize_title` / `notification_body` テストを含む `--lib` スイート全体が期待値変更なしで通る（NFR1）。
- [ ] AC-7 (TS8/TS9): デフォルトフィーチャーの check と `--no-default-features` の check が双方通り、ケイパビリティ判定・エスケープのコードが Unix ゲート配下にのみ存在して Windows 送出フローが無変更である（FR5 / NFR3）。

## Test Notes

- AC-1〜AC-4 はコンポーネント 1 / 2 の純関数ユニットテスト（`src-tauri/src/callbacks/tests.rs`）。D-Bus 実接続には依存させない。
- AC-5 は `crate::notifications` の本文組み立て関数と純関数ヘルパーを合成するユニットテスト（結合相当）。両経路の実際の本文フォーマットを入力にする。
- AC-3 は境界ケース: 100 文字目付近がメタ文字になるタイトルを作り、トランケート済み文字列に対する変換結果の末尾に完全な実体参照があることを確認する。
- コンポーネント 3（D-Bus を呼ぶアダプタ本体）はユニットテスト対象外。ゲート配置と適用条件はレビューで検査する（TS9）。
- テストは `--lib` にある（`--bin emterm` は 0 件）。`tabs.rs` の replay テストに既知の非決定性があり、無関係な失敗が出た場合は同じ承認済みコマンドの再実行で判断する。
