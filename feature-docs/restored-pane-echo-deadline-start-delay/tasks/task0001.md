# Task Plan: task0001 — Make the restored_echo_wait deadline tests independent of reader-thread start time

## Goal

The two deadline tests of the test-only helper `read_echo_until_marker` pass
whether or not the helper reader thread delivered its first chunk before
`SHORT_DEADLINE`, while still checking the deadline behavior and the failure
message. A deterministic delayed-start test and a deterministic
failure-message test pin both properties without any CPU load.

## Requirements

FR1, FR2, FR3, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/mux/session/pane/tests.rs` — in the restored_echo_wait module: add a start gate to the scripted reader, add a shared deadline check, relax the two deadline tests, add the delayed-start test and the failure-message test.

## Design

All work is inside the `restored_echo_wait` module of
`src-tauri/src/mux/session/pane/tests.rs`. There is no cross-task contract;
this is the only task of the feature.

### Fixed points (do not change)

| Item | Rule | Source |
|------|------|--------|
| `read_echo_until_marker` | Body and semantics unchanged, including the absolute deadline computed at the start of the call | SPEC A2 |
| `SHORT_DEADLINE` | Stays 200 ms; the `200ms` text check stays | SPEC A1 |
| `GENEROUS_BOUND`, `SCRIPTED_READER_SAFETY_LIMIT` | Values unchanged (3 s, 6 s) | SPEC |
| Names of the two existing deadline tests | Unchanged, so the predecessor feature's test record needs no update | SPEC A4 |
| Dependencies | Standard library only; the module stays platform-neutral (no platform gating added) | NFR2, NFR4 |

### Component 1: start gate on `ScriptedEchoReader`

Chosen option for SPEC A5: a gate before the first chunk on the existing
`ScriptedEchoReader`, not a separate reader type. The delayed-start test then
reuses exactly the withheld-data and trickle scripts of the two deadline
tests.

| Aspect | Contract |
|--------|----------|
| Default | Ungated. Every reader produced by the existing `scripted_reader()` path (used by the existing scripted-reader tests) behaves exactly as before. |
| Construction | A gated reader is produced together with a release handle that the test keeps (a new construction path or option next to `scripted_reader()`; naming is the implementer's choice). |
| First read, gated | Returns no bytes and does not return until either the release handle has been used, or `SCRIPTED_READER_SAFETY_LIMIT` has elapsed since reader construction. |
| After release | The reader continues with its script unchanged: the scripted chunks, then the configured after-chunks behavior (`Withhold`, `Trickle`, ...). |
| Never released | When the safety limit is reached, the reader ends the same way the existing safety limit ends it, so a broken helper fails an assertion instead of hanging (NFR3). |
| Waiting | Blocking only: a timed wait on a standard-library synchronization primitive, or short sleeps between flag checks. No spin loop and no busy thread (NFR1). |
| Release | Idempotent. Releasing before the first read makes that read proceed without waiting. |

### Component 2: shared deadline check

A test-local helper used by both deadline tests and by the delayed-start test,
so the FR2 test runs the same deadline checks as the FR1 tests (SPEC A5).

- **Input**: the outcome returned by `read_echo_until_marker`, the measured
  elapsed time of that call, and the expected collected-bytes shape of the
  script used.
- **Shapes**:
  - withheld-data shape: collected bytes are empty, or exactly `restored-`;
  - trickle shape: collected bytes are empty, or `restored-` followed by zero
    or more `.` bytes and nothing else.
- **Checks** (all must hold):
  - (a) the outcome is Missing with reason
    `MissingReason::DeadlinePassed(SHORT_DEADLINE)`;
  - (b) elapsed time < `GENEROUS_BOUND`; no lower bound is checked;
  - (c) the collected bytes match the shape;
  - (d) the `describe_missing_echo` text for the returned missing-echo value
    contains `deadline`, `200ms`, and the rendering of the bytes actually
    collected. The expected rendering is derived inside the check from the
    collected bytes, never read back from the text under test.
- **Output**: the collected bytes, so a caller can add a stricter per-test
  assertion.
- **Diagnostics**: each failing check states which of (a)-(d) failed and shows
  the collected bytes, so a failure is diagnosable from the test log alone.

### Changes to the two existing deadline tests

| Test | Script | Change |
|------|--------|--------|
| `read_echo_until_marker_reports_the_deadline_with_the_collected_bytes` | Unchanged (prefix chunk, then `Withhold`) | The equality check on the whole missing-echo value and the fixed `"restored-"` text check are replaced by the shared check with the withheld-data shape. |
| `read_echo_until_marker_deadline_is_absolute_while_non_marker_bytes_trickle_in` | Unchanged (prefix chunk, then `Trickle`) | The unconditional prefix check on the collected bytes and the fixed text check are replaced by the shared check with the trickle shape. |

### New test: delayed start (FR2)

1. Construct a gated reader with the withheld-data script and keep its release
   handle.
2. Call `read_echo_until_marker` with `SHORT_DEADLINE`, measuring the elapsed
   time of the call.
3. Release the gate right after the call returns and before any assertion, so
   a failing assertion never leaves the reader gated.
4. Run the shared check with the withheld-data shape, then additionally check
   that the collected bytes are empty.
5. Repeat steps 1-4 with the trickle script and the trickle shape.

Whether the two cases are one test or two is the implementer's choice; the
test name(s) state that the reader start is delayed.

### New test: failure message (FR3)

Build a missing-echo value directly (no reader, no thread) with reason
`DeadlinePassed(SHORT_DEADLINE)` and collected bytes `restored-`. Check that
the `describe_missing_echo` text contains `"restored-"` including the double
quotes, `deadline` and `200ms`. This pins the concrete rendering independently
of scheduling and of the derivation used in the shared check.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): `read_echo_until_marker_reports_the_deadline_with_the_collected_bytes` keeps its name and script and, through the shared deadline check, asserts reason `DeadlinePassed(SHORT_DEADLINE)`, elapsed < `GENEROUS_BOUND`, collected bytes empty or exactly `restored-`, and a failure text containing `deadline`, `200ms` and the rendering of the bytes actually collected. It no longer requires the prefix to have arrived before the deadline.
- [ ] AC-2 (FR1): `read_echo_until_marker_deadline_is_absolute_while_non_marker_bytes_trickle_in` keeps its name and script and, through the same shared deadline check, asserts reason `DeadlinePassed(SHORT_DEADLINE)`, elapsed < `GENEROUS_BOUND`, collected bytes empty or `restored-` followed only by `.` bytes, and a failure text containing `deadline`, `200ms` and the rendering of the bytes actually collected. It no longer requires the prefix to have arrived before the deadline.
- [ ] AC-3 (FR2, NFR1, NFR3): A delayed-start test uses a gated scripted reader whose first read returns nothing until the test releases it, and the test releases it only after `read_echo_until_marker` has returned. For both the withheld-data script and the trickle script it passes the shared deadline check with `DeadlinePassed(SHORT_DEADLINE)` and empty collected bytes. The gated wait blocks without spinning and ends no later than `SCRIPTED_READER_SAFETY_LIMIT` after reader construction when never released.
- [ ] AC-4 (FR2): Red evidence: with the strict pre-change collected-bytes rules in the shared check (collected equal to `restored-`; collected unconditionally starting with `restored-`), the delayed-start test fails on the collected-bytes check. It passes once the shapes of the shared check are relaxed.
- [ ] AC-5 (FR3): A deterministic test builds a missing-echo value with reason `DeadlinePassed(SHORT_DEADLINE)` and collected bytes `restored-` without any reader or thread, and checks that the `describe_missing_echo` text contains `"restored-"` (with the double quotes), `deadline` and `200ms`.
- [ ] AC-6 (NFR2, NFR4): Under `src-tauri/`, only `src-tauri/src/mux/session/pane/tests.rs` changes; `Cargo.toml` and `Cargo.lock` are unchanged and no dependency is added. The body of `read_echo_until_marker` and the values of `SHORT_DEADLINE`, `GENEROUS_BOUND` and `SCRIPTED_READER_SAFETY_LIMIT` are unchanged, the existing scripted-reader tests use the ungated default unchanged, and `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml` exits 0.
- [ ] AC-7 (NFR1, NFR3): `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib` passes with every `restored_echo_wait` test passing, and no new or changed test uses busy-loop threads, spin loops, stress tools or core-count parallel work.

## Test Notes

- AC-1 / AC-2: the two existing tests are rewritten in place. Under normal
  scheduling they still observe the prefix; both outcomes (prefix collected
  or nothing collected) are accepted by the shapes.
- AC-3: deterministic regardless of scheduling, because the reader cannot
  deliver anything before the release, and the release happens after the
  call has returned at `SHORT_DEADLINE`. The never-released path (a full 6 s
  wait) gets no dedicated test; it is checked by inspection that the gated
  wait uses the same construction-relative limit as the existing safety
  limit.
- AC-4: TDD red step. Write the delayed-start test first against the shared
  check with the strict pre-change rules, run it, confirm it fails on the
  collected-bytes check, and record that run as the red evidence. Then relax
  the shapes and confirm the test, AC-1 and AC-2 pass.
- AC-5: pure unit test with no threads; it is the coverage the deadline tests
  used to give for the `"restored-"` rendering.
- During TDD, run only the module with the `restored_echo_wait` test-name
  filter appended to the `--lib` command; run the full `--lib` suite once at
  the end for AC-7.
- Never confirm the fix by loading the CPU: no busy-loop helpers, stress
  tools, or one-process-per-core runs (NFR1).
