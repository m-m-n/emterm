# Task Plan: task0001 — Rewrite the target record's AC-2 red_reason to the observed count

## Goal

The AC-2 entry of `test-docs/ac7-red-confirmed-unobserved/task0001.tests.yaml`
stops claiming that none of the four required elements were present before the
edit it describes: its `red_reason` states that three of the four were missing
and that the fourth — the linkage to the described record's AC-2 repository-wide
count explanation — was already in the base text and was kept, with the red
verdict and everything else in the file unchanged.

## Design

Read IMPLEMENTATION.md first. Convention C1 (naming disambiguation) defines

### Why this correction exists

The target-record AC-2 entry justifies its `red_confirmed: true` by describing
what a scripted check found in the described-record AC-7 `red_reason` before and
after the edit that the ac7-red-confirmed-unobserved feature made. Its
before-half currently makes two claims:

1. that none of the four required elements were present, naming three of them in
   a parenthetical; and
2. that the text made no direct connection to the described record's AC-2 count
   explanation.

The three named in the parenthetical were genuinely absent. The fourth — the
count linkage — was already in the base blob, so claim 1 overcounts and claim 2
is false. Three absent elements are still enough to have made the criterion red,
so the verdict is not revised (FR5); only the justification is.

### The evidence read that comes first (IMPLEMENTATION.md D2)

Before writing any text, read the described record as it stood at revision
`9eee6161` out of git history, find its AC-7 entry, and confirm that its
`red_reason` there already carries the linkage explaining why the described
record's AC-2 repository-wide count stands at 6 rather than 7.

- **If the linkage is there**: proceed. The rewritten text may state that the
  fourth element pre-existed, because the read supports it.
- **If it is not there**: stop and report. Assumption A-1 has failed, the
  premise of the whole correction is gone, and writing the text anyway would
  violate NFR4 by asserting an unobserved state — the same defect class this
  task exists to remove. This is a plan deviation to surface, not something to
  improvise around.

Record what the read returned; it is the evidence the rewritten text cites, and
it is what the task's own record reports.

### The one region that changes

Located by content, never by line number (IMPLEMENTATION.md D5): find the
target record's `acceptance_tests` mapping, match the AC-2 key, and rewrite that
entry's `red_reason` scalar. Its key set, its key order, its `tests` value and
its `red_confirmed` value are not touched.

The rewritten scalar, written in the record's existing voice and inside its
existing folded block scalar, states all of:

- **the corrected count** — that before the edit the scripted check found three
  of the four required elements absent from the described-record AC-7
  `red_reason`, rather than none of the four present;
- **the three that were absent** — the "invariant guard" phrase, the mention of
  the described record's AC-6 entry, and the "no observable pre-state" phrasing,
  named as they are named today;
- **the fourth, and its provenance** — that the linkage to the described-record
  AC-2 repository-wide count explanation was already present in the base text
  and was preserved by the edit rather than introduced by it. What is asserted
  is the presence of that linkage's substance, in the terms the base blob
  actually supports — not that any particular sentence was identical;
- **the accurate post-edit half, in substance** — that after the edit the same
  scripted check finds all four elements present in the rewritten
  described-record AC-7 text and finds no "confirmed by" / "observed"
  red-observation language in it.

It asserts nothing else about the pre-edit state. Any statement about what the
base text did or did not contain has to be something the evidence read above
actually returned.

### What the rewrite must not disturb

`task_id`, `baseline_failures`, `final_failures`, the target record's AC-1 and
AC-3 through AC-7 entries (including their own `red_confirmed` values and reason
texts), the target-record AC-2 entry's `tests` and `red_confirmed` values, and
the trailing `notes` block all stay byte-identical. The described record is not
opened for writing at all — it is read from history as evidence only.

### The trap in this task

Two different entries in two different files are both called "AC-2", and the
scalar being rewritten is one of them while the other is the subject it talks
about. A sentence that says the entry explains its own repository-wide count
would create a second record/reality gap of exactly the class this task closes.
Convention C1's qualifiers exist for this sentence; use them in the rewritten
text as well, so the reader can tell which AC-2 is meant without opening a
second file.

**Red observability, decided here rather than while writing the record**
(IMPLEMENTATION.md D3; convention C2 is the substance of this feature, so its
own record is held to it). Before writing the per-task test record, classify
each criterion above:

| AC-2 | Yes — the scalar currently claims the opposite about the fourth element | red confirmed, with the observed failure noted |
| AC-3 | No — the three absent elements and the post-edit half are already in the scalar; this criterion guards against losing them | NOT red-confirmed: invariant guard, no observable pre-state |
| AC-4 | No — the flag already reads `true` and the record is already English | NOT red-confirmed: invariant guard, no observable pre-state |

Writing `true` for any of the bottom five would ship the exact defect this task
removes, in a third file.

**How each criterion is checked.** AC-1, AC-2 and AC-3 are assertions on the
PARSED scalar, never on raw line content — the folded scalar re-wraps on
rewrite, so line-oriented assertions are unreliable (SPEC.md edge case). Load
the record with a YAML parser, read `acceptance_tests['AC-2']['red_reason']`,
and assert on the resulting string: both the positive statements and the
negative one (the "none of the four" claim is gone). AC-2's evidence half is a
read of the described record out of git history at revision `9eee6161`, done
before the rewrite, whose result is captured in the task's record. AC-4 and AC-5
are a parse of the file plus an inspection of the loaded key set, followed by a
read of the raw text to confirm the block-scalar indicators and indentation
survived. AC-6 is a read of the file's own diff. AC-7 is a listing of the change
set plus a fixed-string check for the identifier, assembled at check time from
the described record's own header-comment fragments and never written back into
any file.

**TDD shape.** AC-1 and AC-2 are the red-to-green cycle: state each as a
concrete check against the parsed scalar, observe it fail on the base revision,
make the edit, observe it pass. The remaining five are run before and after —
they must hold in both states — and are recorded as guards, not as transitions.

**Edge cases worth covering.** A rewrite that satisfies AC-1 but silently drops
the parenthetical enumeration or the post-edit half is the most likely failure;
run AC-3's check immediately after rewriting, not only at the end. A rewritten
scalar at the wrong indentation can still parse while folding into a
neighbouring key's value — after parsing, read the loaded value back and
confirm it reads as its own complete text, and that the entry count is still
seven.

**TDD-awkward item.** AC-2's evidence half concerns an immutable historical
blob, so it has no red state and cannot be driven by a failing test; it is a
precondition read whose result gates the rewrite (IMPLEMENTATION.md D2). Run it
first and record what it returned.
