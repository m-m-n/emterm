model update intact.

## Design

### Why the test currently leaks

The test builds an app with the production notification sink still in place,
then feeds it a wire-level agent-status update whose state is "blocked" and
pumps. Inside the pump, the agent-status transition drain evaluates the
transition and fires a notification when all of the following hold — and in this
test all of them do:

1. the new state is a notification-eligible one (blocked / done),
2. the pane is not visible (the OS window starts unfocused, and the pane has no
   corresponding tab),
3. both notification settings are enabled (their defaults),
4. the rate limiter permits the first notification for that pane key.

So the only variable that decides whether an OS notification actually goes out
is which sink the app holds.

### The change

Obtain the app from the test module's capturing-sink helper, which returns both
the app and a handle to the capturing sink. The handle is not needed here — this
test's subject is the model update, not the notification — so bind it in a way
that makes the intent explicit rather than asserting on it.

Preconditions the helper already enforces: both notification settings are at
their enabled defaults. Postcondition relied upon: nothing the app sends reaches
the OS notification service.

Everything else in the test body — spawning the initial tab, constructing the
wire-level update for pane 42 with revision 7, routing it as a control message,
pumping, and the assertions on the model entry — stays exactly as it is.
