# Task Plan: task0001 — Remove mux status bar across all Rust layers

## Goal

Remove the mux-sourced status bar from the Rust side end-to-end — GUI
state/render path, daemon `StatusBarEngine`, the `StatusUpdate` (0x16) /
`RequestStatusUpdate` (0x17) protocol messages, and the `mux.statusbar`
settings schema on both Rust mirrors — while relocating `detect_osc7_cwd`,
preserving the general app status bar, and tolerating stale peers and stale
settings files.

## Design

### Removal flow (one pass, single worktree)

1. Relocate `detect_osc7_cwd` + its unit tests from statusbar.rs into
   pty_spawn.rs, keeping the function's observable behavior identical
   (contract below). Keep `Pane.cwd` updates in the PTY reader; drop the
   statusbar-registry updates.
2. Remove GUI usage top-down: ui/status_bar.rs mux rendering → runtime.rs
   mux parameter/branch → app.rs projection → tabs.rs field + latch/clear +
   any `RequestStatusUpdate` sender.
3. Remove daemon usage: connection.rs wiring and handler,
   `register_session_pane_cwds`; delete statusbar.rs and its module
   declaration; update the windows_exec.rs doc comment.
4. Remove protocol definitions: `StatusUpdateMsg`, both message types, their
   round-trip tests; add the reserved-opcode comment; confirm the
   unknown/retired-opcode decode path is non-fatal.
5. Remove settings schema on both Rust mirrors; add stale-settings
   tolerance tests.

### Contracts (this task)

- **Retired-opcode tolerance** (IMPLEMENTATION.md D2): precondition — a raw
  frame carrying opcode 0x16 arrives at the GUI mux-message receive path, or
  0x17 at the daemon connection receive path. Postcondition — the frame is
  discarded; at most one warn-level log; the connection stays up; tab /
  session state is unchanged. Tests construct raw frames and assert the
  observable outcome without naming the retired types (they must stay valid
  after the type deletion).
- **Relocated `detect_osc7_cwd`**: signature, inputs and outputs unchanged;
  given PTY output bytes containing an OSC 7 sequence, it yields the
  detected cwd exactly as before; its existing unit tests move verbatim and
  pass at the new location.
- **Stale-settings tolerance** (Shared Components, "Settings mirror
  shape"): JSON input containing a populated `mux.statusbar` object loads
  without error on both Rust loaders; the obsolete key is ignored.
- **Grid-height invariant** (FR5): the status bar's visible row count, the
  bottom inset derived from it, and therefore the terminal grid rows are
  functions of window size and general (non-mux) status-bar state only; mux
  attach/detach is not an input.

### Preservation boundary

IMPLEMENTATION.md D4 applies in full: general status bar (osc_dispatcher.rs,
callbacks.rs, `statusbar_*` settings, App Line 1/2,
status-bar-section.ts), ResizeSettler / inset machinery, and tab bar /
sidebar / agent status surfaces are untouched.

## Test Notes

- TDD fit: AC-3's tolerance tests fail before removal (the current handler
  mutates the tab / responds to the request), making them natural
  red-first tests. AC-2's mux-independence tests are written against the
  post-removal signatures, so they start red at compile level.
- AC-4's tolerance tests may pass pre-removal too (the key currently
  deserializes into a real field); they are regression anchors, not
  red-first tests — keep them anyway.
- AC-3 tests must build **raw frames** (byte-level opcode 0x16/0x17) and
  assert observable outcomes only, never naming the retired protocol types
  (IMPLEMENTATION.md Conventions) — this keeps them valid in this worktree
  and after integration.
- mux_ipc crate: removing the round-trip tests for the two retired messages
  is part of the deletion; add a decode-level test that a retired-opcode
  frame yields the non-fatal skip path.
- Run the integration test exactly as
  `cargo test --test mux_hot_upgrade -- --test-threads=1` (workflow.yaml
  command); tabs.rs replay tests are known to be nondeterministic under
  parallel execution — that flakiness is pre-existing and out of scope.
