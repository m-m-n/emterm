# Task Plan: task0003 — Discard replay-generated device responses in the off-thread core-swap path

## Goal

Make the off-thread core-swap path discard device responses synthesized
during snapshot replay before the swapped-in core goes live, restoring
parity with the synchronous replay path's existing discard so stale
replay responses are never delivered to the PTY after a window switch or
reattach.

## Requirements

FR1, FR2, FR3

## Provenance

- source: review (round 1)
- source_ids: 8bebc1e532a1b597 (medium)

The synchronous replay path explicitly discards responses generated while
replaying stored bytes; the off-thread swap path installs the
worker-built core without that discard. The gap predates task0001, but
task0001's promotion of the drain to the sole delivery route makes the
documented invariant ("replay never produces delivery") false on exactly
one path. Distinct root cause from the multi-query loss family, so it is
a separate task; the two tasks share only the drain contract pinned in
IMPLEMENTATION.md (D5).

## Scope

### Files to Create

- none

### Files to Modify

- `src-tauri/src/tabs.rs` — the off-thread swap application site: after
  the worker-built core replaces the live core, drain the pending device
  responses and discard the result, mirroring the synchronous replay
  path's existing discard; inline invariant test.

## Design

- Contract dependency: only the shared drain contract (IMPLEMENTATION.md
  Shared Components / D5) — "a drain whose result is discarded removes
  every pending response". That postcondition holds under both the
  pre-rework single-slot buffer and the reworked ordered store, so this
  task is implementable independently of any concurrent rework task's
  internals and merges cleanly in either order.
- Placement: the discard happens at the swap application site,
  immediately after the worker-built core is installed as the live core
  and before any subsequent PTY write-back drain can observe
  replay-generated responses.
- No other behavioral change: queries arriving in live PTY output after
  the swap are answered and delivered exactly once through the unchanged
  write-back sites.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: An inline `--lib` test drives the off-thread swap application
      path with a worker-built core whose replayed snapshot bytes embed at
      least one in-scope device query (e.g. DA1) and asserts that no
      response bytes are subsequently delivered toward the PTY (the
      outbound sink contains no replay-generated response). The test fails
      against the pre-fix code (demonstrated in the implementer report).
- [ ] AC-2: The synchronous replay path's existing discard-after-replay
      invariant tests stay green unmodified.
- [ ] AC-3: A query arriving in live output AFTER an off-thread swap is
      answered and delivered exactly once (post-swap query handling
      unaffected by the discard).
- [ ] AC-4: The full `--lib` suite passes and the `--no-default-features`
      check passes.

## Test Notes

- AC-1 maps to the new TS9 scenario; AC-2 is the existing regression
  floor; AC-3 guards against over-discarding.
- The existing off-thread swap tests in `tabs.rs` (callback/OSC-9999

  construct and apply a worker-built core in a test; reuse that seam.

  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`;
  the `tabs.rs` replay tests may need `-- --test-threads=1`.
