# Task Plan: task0001 — Root-cause and fix the tmux-startup device-query response leak

## Goal

Identify the mechanism that makes tmux-startup device-query responses appear
as visible pane text, fix it so every synthesized response is delivered to
the querying application's PTY input exactly once (never rendered, never
stored in scrollback or snapshots), and pin the mechanism with inline
`--lib` regression tests covering both runtime contexts (plain tab and mux
pane) and the generalized response set.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

- none

## Design

### Phase A — bounded root-cause identification (do this first)

Deliverables before any fix is written:

1. A unit test (or tests) that reproduces the leak mechanism at byte level
   and FAILS on the current code.
2. A root-cause statement (which path delivered the visible bytes, and why
   twice) in the implementer report.

Investigative leads — these are leads, not conclusions:

- **Lead 1 (assumption A3, sharpened)**: the leaked pixel response
  `4;816;1656` equals a 207-col x 51-row grid at term_core's DEFAULT cell
  metrics (8x16 px). The core's cell-metrics setter has NO call site
  anywhere in `src-tauri` — every GUI-side core constructed via `new`
  carries the defaults. Discriminator: a snapshot-REBUILT core carries
  cell metrics of ZERO (`crates/term_core/src/snapshot.rs`) and would have
  answered `4;0;0` — so the responder was a `new`-constructed core at the
  real grid size, most plausibly the tab's own live core. This points at
  the DELIVERY of legitimately synthesized responses, not at a rogue
  second parser with wrong dimensions.
- **Lead 2 (duplicate parse/delivery)**: the same outer bytes may be
  parsed more than once, each parse synthesizing and writing back its own
  response copy. Candidate pairs: live parse vs `apply_queued_live_output`
  replay around a pending tab switch (a fresh tab IS a switch); coalesce
  flush vs per-frame `apply_mux_message` arm; GUI core vs any other
  consumer of the same stream. The reported "displayed twice" fits a
  duplicated delivery whose extra copies reach tmux's stdin when tmux no
  longer expects them and forwards them to the pane shell as input.
- **Lead 3 (mis-timed or mis-routed write-back)**: `write_device_response`
  in the mux context targets the pane that is ACTIVE at write time, which
  is not necessarily the pane whose bytes produced the response; in the
  plain-tab context, delivery timing relative to tmux's raw-mode/query
  window decides whether tmux consumes or forwards the bytes.
- **Lead 4 (single-slot overwrite)**: synthesis OVERWRITES the 64-byte
  single-slot buffer (last query in a chunk wins). The observed leak
  string concatenates THREE responses — establish how three survived
  delivery (separate chunks? an appending path?). If the slot loses
  responses when one chunk carries several queries, FR2 (every response
  delivered exactly once) is at risk independently of the leak, and the
  fix must preserve all responses, not merely deduplicate.
- **Lead 5 (daemon side, mux context)**: confirm whether the daemon's
  vt100 shadow parser synthesizes device responses at all; if it does,
  its copies also carry default metrics and need routing/stripping.

Bound: if the reproduction test cannot be built from these leads, write
the byte-trace findings into the implementer report and stop before
changing behavior — do not commit a speculative fix.

### Phase B — fix

Whatever the mechanism, the fix must establish these invariants:

- **I1 (exactly-once)**: each synthesized response reaches the PTY input
  of the application that issued the query exactly once — no duplicates,
  no drops, across coalesce, queued-replay, switch, and reattach paths.
- **I2 (never visible)**: response bytes never enter the visible grid,
  the scrollback, or any snapshot/replay store in either context.
- **I3 (pass-through)**: byte streams that merely resemble queries or
  responses inside ordinary application output are untouched (NFR3).
- **I4 (floors hold)**: per-tab-grid-size behavior and the
  mux-snapshot-device-query-strip strip/keep sets are unchanged or
  strictly extended with documentation (FR6, NFR4).
- **I5 (hot-path neutrality)**: no added per-byte work for non-query
  traffic; classification stays per-frame/chunk (NFR1,
  IMPLEMENTATION.md D4).

### Phase C — generalized regression tests

For each in-scope response type — DA1, DA2, DSR status, CPR, XTWINOPS 14,
16, 18, DECRPM (FR5 resolution) — and for each context (plain-tab path,
mux-pane path), an inline test drives the query through the relevant parse
path and asserts I1 + I2 on the observable sinks (bytes written toward the
PTY / control frames vs grid contents and scrollback). Reuse the existing
test seams: `tabs.rs` already unit-tests `process_outer_via_core` /
mux-message application with known buffers, and `csi_device.rs` tests
response synthesis directly.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A unit test reproducing the identified leak mechanism exists,
      fails against the pre-fix code (demonstrated in the implementer
      report), passes after the fix, and its doc comment states the root
      cause.
- [ ] AC-2: For every in-scope response type (DA1, DA2, DSR status, CPR,
      XTWINOPS 14, 16, 18, DECRPM), a `--lib` test on the plain-tab path
      asserts the response is delivered toward the querying PTY exactly
      once and appears nowhere in the grid or scrollback.
- [ ] AC-3: The same delivery/visibility assertions hold on the mux-pane
      path, including that pending-switch queued-output replay and
      snapshot/reattach replay produce no additional delivery and no
      visible bytes.
- [ ] AC-4: A negative test shows query- and response-lookalike byte
      sequences embedded in ordinary output reach the grid unchanged, and
      sessions without queries behave byte-identically (NFR3).
- [ ] AC-5: The full `--lib` suites of `src-tauri` and `crates/term_core`
      pass, with all pre-existing per-tab-grid-size and
      mux-snapshot-device-query-strip tests green; any modified existing
      assertion carries a justification comment.
- [ ] AC-6: `cargo check` and the `--no-default-features` check both pass;
      GUI-only code touched stays behind the `gui` feature gate.
- [ ] AC-7: The non-query output path gains no per-byte work (stated with
      reasoning in the implementer report); if the scrollback strip
      predicate changed, its existing `#[ignore]` 2 MiB bench still meets
      the documented threshold.

## Test Notes

- All automated tests are inline `#[cfg(test)]` modules run via the
  approved commands (see VERIFICATION.md); the `tabs.rs` replay tests may
  need `-- --test-threads=1` (known parallel flake).
- AC-1..AC-4 map to unit tests (TS4, TS5); AC-5 is the regression gate
  (TS7); AC-6 is the build gate (TS6); AC-7 is review-plus-bench.
- TDD-awkward part: the on-screen symptom itself (TS1–TS3) is manual-only
  — the project has no E2E infrastructure. The unit tests therefore assert
  the byte-level sinks (PTY-bound writes vs grid/scrollback contents), not
  rendered pixels.
- Follow `test/README.md`: construct cores explicitly per test, drive
  input via the PTY-data entry points, assert observable contracts only.

## Out of Scope

- Wiring real font metrics into term_core cores so XTWINOPS reports true
  pixel values — the wrong VALUES are an investigative lead, not the bug;
  fix visibility/routing, not cosmetics (unless the investigation proves
  metrics are load-bearing for the leak, which is then a reported
  deviation).
- Any new E2E infrastructure or scripted tmux automation.
- Performance improvements beyond the NFR1 non-regression bar.
- Extending the strip predicates beyond what the root cause requires.
- tmux-side configuration or behavior changes.
