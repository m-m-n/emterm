## Goal

## Design

### What the test observes

The unit under test is the blank-row push entry point `ring_push_blank` of the
terminal core, taken with scrollback enabled so that the compress branch runs.
Two crate-visible tables carry the state being asserted:

| Table | Key | Meaning for this test |
|---|---|---|
| `overflow` | column and absolute row | the overflow-bound content of one cell |
| `overflow_ridx` | absolute row | the set of columns that row has overflow content in |

They are asserted **independently** — one is never used as a proxy for the
other (IMPLEMENTATION.md, Conventions).

### Fixture

Keep the existing terminal-core construction (10 columns, 3 rows, scrollback
capacity 2) — the row count is what makes a single push evict exactly one row
while leaving another one live. Place overflow-bound content, via the cell
writer `set_cell`, on two distinct viewport rows:

| Role | Viewport row before the push | Why |
|---|---|---|
| Recycled row | the row the first push evicts (viewport row 0) | its entries MUST disappear |
| Survivor row | a row the first push does not evict (viewport row 1) | its entries MUST remain |

The content must be a grapheme cluster long enough to exceed the inline
per-cell capacity, so that it is genuinely stored in the overflow tables rather
than inline. The baseline form named by SPEC.md (a four-person family emoji
sequence, written at column 0 of the recycled row and column 1 of the survivor
row) is a starting point, not a constraint: exact coordinates and the exact
string may be adjusted, provided the anti-vacuity pre-assertions below still
hold. Note that the cell writer takes the column before the row.

### Row identity across the push

The ring head rotates on every push, so a viewport-relative index does not
denote the same absolute row before and after a push. Both rows' **absolute**
row numbers are therefore obtained through the absolute-row accessor
`viewport_abs` **before** the first push and reused verbatim in every later
assertion.

### Processing flow

1. Build the terminal core with the fixture dimensions above.
2. Write the overflow-bound content to the recycled row and to the survivor row.
3. Capture the absolute row numbers of both rows.
4. Pre-assert non-vacuity: for the recycled row and for the survivor row,
   independently in `overflow` and in `overflow_ridx`, the row's overflow-bound
   content is present. This subsumes or strengthens the current
   "overflow_ridx is not empty" assertion — the weaker form is not kept
   alongside a strictly stronger one.
5. Push one blank row.
6. Post-assert row scope, as four independent assertions: the recycled row's
   `overflow` entry is gone; the recycled row's key is gone from
   `overflow_ridx`; the survivor row's `overflow` entry is still present; the
   survivor row's `overflow_ridx` membership is still present.
7. Push four more blank rows (five in total, the pre-existing count).
8. Assert, unchanged from the current test, that `overflow` is empty and that
   `overflow_ridx` is empty.

Step 6 is placed at the one-push point deliberately: at three pushes the
survivor row is itself evicted, and the survival assertions would then be
unsatisfiable for a correct implementation (IMPLEMENTATION.md D3).

### Doc comment

The test's doc comment states three things, in the phrasing style of the
sibling test `test_ring_push_blank_clears_recycled_row_overflow_entries`:

1. **Proved**: the compress branch does not sweep away overflow entries of rows
   other than the evicted one.
2. **Not proved**: that the compress branch's own clear site fired.
3. **Why (2) is unattainable**: `ring_push_blank` has three clear sites — the
   compress branch, the scrollback-disabled branch, and the unconditional clear
   of the new viewport's bottom row. Within one push the new bottom absolute row
   always equals the evicted absolute row, independent of the row count, so the
   eviction-time clear and the unconditional bottom-row clear necessarily target
   the same absolute row and no fixture can distinguish them.

## Test Notes

- **The deliverable IS the test.** The usual TDD ordering is inverted in shape
  but not in spirit: the "red" step is AC-5's mutation run (the strengthened
  assertions must fail against a deliberately broken implementation), and the
  "green" step is AC-6's unmutated run. Do the mutation run first, on the
  finished assertions, before declaring the task done — a strengthened test that
  was never observed red proves nothing.
- **Anti-vacuity is the main hazard.** If the chosen content does not exceed the
  inline per-cell capacity, every post-assertion of the form "the entry is gone"
  passes for the wrong reason. AC-2's pre-assertions exist precisely to convert
  that silent pass into a failure; verify by construction that they fire on the
  fixture actually chosen, not on the baseline one from SPEC.md.
- **Do not merge the two tables' assertions.** Four separate assertions after
  the push, not two combined ones — a regression that drops the row-index table
  while keeping the content table (or the reverse) must still be caught.
- **Determinism.** The fixture owns its terminal core instance and touches no
  global or shared state, so the test must pass under the crate's default
  parallel run; if it appears to need a single-threaded run, that is a defect in
  the fixture, not a reason to restrict the run.
- **Scope of formatting.** Format only the changed file. A crate-wide formatting
  sweep would dirty unrelated files and is out of scope (NFR4).
- **No implementation skill is assigned to this task** (the registry's explicit
  empty-list fallback): its output is test assertions over existing core
  behavior, not new production logic, so no layer skill applies. The
  implementer's preloaded discipline skills are sufficient.
