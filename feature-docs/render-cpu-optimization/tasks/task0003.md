# Task Plan: task0003 — Dirty-row-driven rendering + persistent instance buffer

## Goal

Frame preparation cost becomes proportional to the number of dirty rows: clean
rows reuse a per-row CPU-side instance cache, and instance data is uploaded
into a persistent, grow-on-demand GPU buffer instead of a freshly created one
every frame. A rows-rebuilt perf counter makes the savings observable.

## Requirements

FR3, FR4, FR6 (rows-rebuilt half), NFR1.

## Scope

### Files to Create

- (none — unless the row cache reads more naturally as a sibling module, in
  which case a new file under `src-tauri/src/render/` is acceptable and must
  be reported as a plan deviation)

### Files to Modify

- `src-tauri/src/render/mod.rs` — restructure cell-input collection so it can
  produce output for a **subset of rows** (the dirty ones) while preserving
  the existing full-grid behavior as the cache-rebuild path; keep the
  existing per-cell semantics (selection, hover, scrollback, fold, preedit)
  bit-for-bit.
- `src-tauri/src/render/terminal_grid_pass.rs` — per-row instance cache keyed
  by screen row; rebuild dirty rows, concatenate cached rows in row order;
  persistent instance buffer (and uniform buffer) created once, grown when
  capacity is exceeded, updated in place; growth policy as a pure function.
- `src-tauri/src/window_host.rs` — pass the frame's dirty-row set (already
  computed for the skip decision) plus the invalidation signals (scroll
  offset change, resize, font/theme change, selection/hover/search change)
  into the prepare path; count rebuilt rows behind `EMTERM_RENDER_PERF=1`.

## Design

- Cache unit: one entry per screen row holding that row's ready-to-upload
  instance data. A frame's instance sequence = rows 0..n in order, each taken
  from cache (clean) or rebuilt (dirty). Postcondition (IMPLEMENTATION.md
  Shared Components): the concatenated sequence is byte-identical to a full
  rebuild of the same state — this is the safety net that TS-4 enforces.
- Invalidation rules are fixed by IMPLEMENTATION.md D3: scroll → all rows
  dirty; resize / font / theme change → full cache drop (row count or cell
  metrics changed); selection / hover / search highlight change → affected
  rows dirty (conservative fallback to all rows is acceptable where computing
  the affected set is not already available); fold layout + selection → all
  rows (matches the app-side fallback). IME preedit overlay mutates inputs
  after collection — a frame with active preedit must not poison the cache
  (rebuild or bypass such rows).
- Persistent buffers: keep buffer + capacity across frames; when required
  size exceeds capacity, create a larger buffer using the growth policy
  (pure function: current capacity + required size → new capacity, with a
  growth factor and a minimum). Shrinking is out of scope. Upload via the
  queue's write-buffer path only.
- Rows-rebuilt counter: same env-gate idiom and logging cadence as
  task0002's frames counter.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Equivalence — for mutation scenarios (write characters, scroll by
  one and by a page, change selection, resize), the instance sequence built
  through the row cache equals a from-scratch full rebuild, exactly.
- [ ] AC-2: Invalidation matrix — mutating exactly one of {selection, hover,
  search highlight, scroll, resize, font/theme change, focus gain/loss}
  invalidates at least the expected rows (per D3) and the following frame's
  equivalence (AC-1) still holds.
- [ ] AC-3: A clean row is not rebuilt: with a stable frame, the
  rebuilt-row count for a frame whose dirty set is empty is zero, and for a
  single-row write it is on the order of one.
- [ ] AC-4: Growth policy pure function — capacity never decreases, always
  covers the required size, and grows geometrically (bounded reallocation
  count under monotone growth).
- [ ] AC-5: With `EMTERM_RENDER_PERF=1`, rebuilt rows are counted and logged
  at warn level; unset → no side effects.
- [ ] AC-6: All pre-existing `collect_cell_inputs` tests still pass
  (full-grid path unchanged in observable behavior).

## Test Notes

- AC-1/AC-2 are the core suite (SPEC TS-4/TS-5): drive a real terminal core
  through the mutations, compare instance sequences structurally. They run
  without a wgpu device — cache and instance building are CPU-side; only the
  final buffer upload needs the device, and that part stays untested at unit
  level (final verify covers it).
- AC-4 (SPEC TS-6): plain pure-function tests.
- Choose test placement next to the code (render module test blocks).

## Out of Scope

- Event-loop / wakeup changes (task0004).
- A separate shaped-run cache (subsumed by the row cache — SPEC §4(b)).
