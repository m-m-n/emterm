## Design

### Why the gate is red on landing

The CI workflow runs the whole repository suite on every push and every pull
request targeting the default branch. Two assertions in that suite are pinned
to a plugin version that both manifests — `plugins/emterm/.claude-plugin/plugin.json`
and `.claude-plugin/marketplace.json` — have since moved past, so the suite exits
non-zero on a clean checkout of the integration branch. Those two failures also
occur on the base branch, and SPEC AC-10 / ASM-4 record them as pre-existing and
out of scope for the three original tasks.

This task's reason for touching them is therefore not the failures in
themselves but what the newly added gate does with them: a status check that is
unconditionally red cannot signal drift, because a drift failure and the known
failure are the same observable outcome, and on a protected branch it blocks
merges outright. That is what defeats FR7 (the viewer entry tests run in CI as a
meaningful signal) and FR8 (drift fails loudly).

### The guard's intent is preserved by re-pinning, not by generalizing

The guard exists to make an unreviewed version change visible. Pinning it to the
version the manifests declare today keeps exactly that property: the next
unreviewed bump fails it again. Deriving the expected value from the manifests
would make the assertion compare a value with itself and remove the guard's
whole reason to exist; that is not the change this task makes.

### The gate's command form is not this task's lever

The CI install-and-test contract is already fixed by IMPLEMENTATION.md's
"CI install path" shared component and by task0003's Acceptance Criteria: a
frozen install followed by a whole-suite run, with the workflow-structure test
asserting the whole-suite form of that command. The gate is therefore made green
by making the suite green — never by narrowing what the gate runs, excluding a
path from it, or relaxing the structure test that pins its shape. An attempt to
express an exclusion in the workflow command has already been made and reverted
during this review round; repeating it would break the structure test's
whole-suite assertion as well as depend on runner argument handling that treats
unrecognized positional arguments as inclusions rather than exclusions.

## Test Notes

- The red state already exists: run the suite first and observe the two failing
  assertions before changing anything, so the transition to green is evidence
  that this change is what produced it.
- AC-2 requires running the whole suite, not only the plugin test file, and from
  a clean frozen install — that is the only run whose result matches what the
  CI gate observes.
- AC-3 is a reversible manual experiment rather than a new automated test:
  adding a permanent test that mutates a manifest would itself become a source
  of suite instability. Record the observed outputs in the task's test record so
  the verify phase can re-run it.
- AC-4 is diff-shaped: compare both CI-owned files against the base commit
  rather than reasoning about them in isolation.
- No new test file is warranted; the guard being re-pinned is the test.

## Out of Scope

- Editing the CI workflow — its trigger, its job structure, or its install and
  test commands — and editing the workflow-structure test that asserts them.
  Both are owned by task0003.
- Redesigning the version guard: deriving its expected value from the manifests,
  relocating it, or replacing it with a different mechanism.
- Changing the plugin manifest, the marketplace entry, or the plugin version
  they declare.
- Any dependency declaration, lockfile, or sanitizer change (owned by task0001
  and task0002).
- The three unresolved medium findings from the same review round, which are not
  part of this task's origin.
