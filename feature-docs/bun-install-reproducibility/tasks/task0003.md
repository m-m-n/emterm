# Task Plan: task0003 — CI のクリーンインストール経路とテスト実行

## Goal

Give CI a clean-checkout path that installs the frozen dependency graph and
runs the bun test suite (including the viewer entry tests), and make every CI
install invocation a frozen-lockfile install so a declaration committed without
a regenerated lockfile fails the run instead of silently resolving a different
graph.

## Requirements

FR7, FR8, NFR3

## Scope

### Files to Create

- `.github/workflows/ci.yml` — the clean-checkout workflow that installs the
  frozen graph and runs the test suite. Created only if the enumeration below
  finds no existing workflow that already runs the suite.
- `ci-workflows.test.ts` — a test that parses the workflow definitions and
  asserts the install and test guarantees this task delivers.

### Files to Modify

- `.github/workflows/release.yml` — its install invocations become
  frozen-lockfile installs; every other step, including the bundle builds, is
  left as-is.

## Design

### Enumerate before deciding where the test step lives

Only one workflow file was visible to the requirements analysis, and it runs no
test command (ASM-5). The first step of this task is therefore to enumerate the
workflow directory and classify each workflow by whether it already runs the
bun test suite:

1. If exactly one workflow already runs the suite, add the frozen-install and
   viewer-entry-coverage guarantees there instead of creating a new workflow,
   and report the substitution as a plan deviation.
2. If none does, add the new workflow file named in Scope.
3. If more than one does, add the guarantees to the one that runs on the
   broadest trigger and report the situation, rather than creating a third.

### What the test path must guarantee

- It starts from a clean checkout, with no dependency directory carried over.
- It installs with the frozen-lockfile form, before any step that consumes the
  dependency graph.
- It runs the bun test suite in a way that includes the viewer entry tests —
  either the whole suite or an explicit path that covers them.
- The install step precedes the test step, so a drifted declaration fails the
  run at install time rather than surfacing as a confusing test failure.
- It never generates or commits a lockfile. The lockfile is a tracked input
  provided by task0002 (IMPLEMENTATION.md CI install path contract); if it is
  missing, the frozen install fails, which is the intended behavior.

### Why every install invocation converts

A single remaining non-frozen install in any workflow is enough to reintroduce
the environment-dependent graph this feature removes (IMPLEMENTATION.md D5). The
release workflow's two install invocations therefore convert as well, even
though that workflow runs no tests.

### Preserving the bundle build path

The release workflow builds the viewer and settings bundles that the Rust GUI
build embeds, on both the Linux and Windows jobs (NFR3). Converting the install
form must not reorder, remove, or otherwise disturb those steps; the only
change to that file is the install form itself.

### Making the guarantees checkable without running CI

The workflow definitions are data, so the guarantees above are asserted by a
test that reads the workflow directory and inspects the parsed job and step
structure. That test is what turns this task's Acceptance Criteria into
something the verify phase can re-run offline; the CI run itself is observed
manually once (VERIFICATION.md TS-8).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Exactly one workflow under the workflow directory runs the bun test
      suite, and its trigger covers pushes to the default branch and pull
      requests targeting it.
- [ ] AC-2: In that workflow, a frozen-lockfile install step precedes the test
      step, and no step before it consumes the dependency graph.
- [ ] AC-3: The test step's command covers `src-tauri/viewer/web/entry.test.ts`
      — either by running the whole suite or by naming a path that includes it.
- [ ] AC-4: Every dependency install invocation across all workflow files uses
      the frozen-lockfile form; no plain install invocation remains.
- [ ] AC-5: No workflow step generates, edits, or commits a lockfile.
- [ ] AC-6: `.github/workflows/release.yml` still runs its viewer and settings
      bundle builds on both the Linux and Windows jobs, with no step removed or
      reordered relative to this task's base commit.
- [ ] AC-7: `ci-workflows.test.ts` asserts AC-1 through AC-5 against the parsed
      workflow definitions and passes.

## Test Notes

- AC-7 is the TDD entry point: write the workflow-structure assertions first,
  watch them fail against the base commit's workflow directory, then make them
  pass by adding and converting the workflow steps.
- AC-6 is a diff-shaped criterion — compare the release workflow against the
  base commit rather than reasoning about the file in isolation. A structural
  assertion that the bundle-build steps are still present is worth adding
  alongside it.
- Parse the workflow files as data rather than matching raw text, so a
  reformatted-but-equivalent workflow does not fail the assertions and a
  commented-out install line does not pass them.
- The workflow enumeration result belongs in the task's completion report,
  including which of the three branches in the Design section was taken.
- This task cannot observe a real CI run; the end-to-end observation is a
  manual verification item at the feature level.

## Out of Scope

- Adding Rust, cargo, packaging, or lint jobs to CI, and any quality gate
  beyond the install-and-test path this feature requires.
- Changing release, packaging, or artifact-upload behavior in any way.
- Creating or committing the lockfile itself — owned by task0002.
- Any dependency version change or sanitizer change — owned by task0001.
- Self-hosted runner, caching, or CI performance work.
