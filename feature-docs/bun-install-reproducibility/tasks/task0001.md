# Task Plan: task0001 — dompurify h1 消失機構の特定と安全なバージョン採用

## Goal

Determine, by observation, which layer causes dompurify 3.4.x to drop the
leading level-1 heading from the markdown renderer's sanitized output, record
that finding durably, and land a dompurify version constraint under which the
viewer entry tests pass without weakening sanitization or touching their
assertions.

## Requirements

FR3, FR4, FR5, FR6, NFR1, NFR2

## Scope

### Files to Create

- `doc/dompurify-h1-sanitization.md` — the findings record: the reproducible
  observation, which of the three candidate layers is responsible, the adopted
  version and the reason behind it, and the adopted version's declared license.
- `src-tauri/web-shared/markdown/renderer.test.ts` — sanitizer-boundary
  regression test pinning the heading-survival behavior. Created if absent;
  extended in place if the project already has this file.

### Files to Modify

- `package.json` — the dompurify version constraint, set to the version the
  investigation concludes is adoptable.
- `bun.lock` — regenerated only when the integrated tree already tracks it and
  the declaration changed on this branch (the sync duty in IMPLEMENTATION.md).
- `src-tauri/web-shared/markdown/renderer.ts` — touched only if the finding
  shows the sanitize invocation itself must change; strictness stays at or
  above its current level.
- `test-setup.ts` — touched only if the finding shows the test DOM environment
  is the responsible layer.

## Design

### Investigation

The sanitize boundary under study is the sanitize call in the markdown renderer
(`src-tauri/web-shared/markdown/renderer.ts:216`), which runs against the
happy-dom environment installed by the repository-root test setup module. Three
candidate layers must be distinguished, per FR4:

1. A behavior change inside dompurify itself between the currently installed
   3.3.x line and the 3.4.x line.
2. An option in the sanitizer configuration object (`PURIFY_CONFIG`) whose
   meaning the 3.4.x line interprets differently.
3. An interaction between dompurify and the happy-dom document it operates on.

The investigation proceeds by holding two of the three fixed and varying the
third, so the observation attributes the loss to exactly one layer:

1. Establish the failing condition: install the 3.4.x line, render a document
   whose first block is a level-1 heading, and observe the sanitized output.
2. Vary only the dompurify version, with the configuration and the DOM
   environment unchanged. A difference here implicates layer 1.
3. Vary only the configuration — reducing it toward the sanitizer's own
   defaults without ever widening it beyond its current strictness — with the
   version and the DOM environment fixed. A difference here implicates layer 2.
4. Vary only the DOM environment (for example, by observing the same sanitize
   input under a different document implementation available to the test
   runner), with the version and the configuration fixed. A difference here
   implicates layer 3.

Each step records its input document, the observed sanitized output, and the
exact conditions, so a third party can rerun it from the findings document
alone. ASM-6 (the two sibling dependencies were already ruled out by the
reporter) means the graph is not re-bisected; the investigation starts at
dompurify.

### Adoption

The finding drives the constraint written into the declaration:

- If the newer line can be adopted with the heading surviving and the
  sanitizer's strictness unchanged, the constraint moves to that line and the
  findings document records what made it safe.
- If it cannot, the constraint stays at a version where the tests pass, and the
  findings document records the blocking mechanism as the pin's stated reason
  (IMPLEMENTATION.md D6). An unexplained pin is not an acceptable outcome.

Either way the findings document also records the adopted version's declared
license, read from that version's own package metadata, so the license review
perspective can cross-check it against the project license.

Any change to the sanitize invocation or the test environment is bounded by the
strictness floor in IMPLEMENTATION.md: no new allowed tag or attribute, no
removed forbid entry, no widened URI pattern.

### Regression coverage

The observation is encoded as a test at the sanitizer boundary — closer to the
sanitize call than the viewer entry tests, so a future version bump names the
sanitizer as the culprit instead of failing an entry-level assertion. It
asserts that a document whose first block is a level-1 heading still carries
that heading, with its text, after the renderer's sanitize step.

### Integration duty

This task shares the declaration and the lockfile with task0002. Per
IMPLEMENTATION.md's Lockfile / manifest sync duty, if the tree this branch
integrates with already tracks the lockfile, the lockfile is regenerated from
the merged declaration before this task commits, so a frozen-lockfile install
exits zero. If the tree does not yet track a lockfile, this task changes only
the declaration and leaves the lockfile untracked.

## Test Notes

- AC-2, AC-5 and AC-6 are ordinary test-runner outcomes and are the TDD spine
  of this task: write the sanitizer-boundary test (AC-5) first, watch it fail
  under the failing condition established in the investigation's step 1, then
  make it pass by the adoption decision rather than by relaxing the assertion.
- AC-3 and AC-4 are diff-shaped criteria: verify them by comparing against the
  base commit, not by re-reading the file in isolation.
- AC-1 is a document criterion; it is verified by reading the findings document
  and re-running its stated procedure.
- Edge case worth covering in the sanitizer-boundary test: a document whose
  first block is a level-1 heading, and a document where the heading is
  preceded by front matter — the reported failures include a front-matter
  bearing fixture, so both entry points into the renderer are exercised.
- TDD-awkward part: step 4 of the investigation varies the DOM environment,
  which the test runner fixes globally. Handle it as a one-off observation
  recorded in the findings document rather than as a permanent test.

- Removing the ignore rule on the lockfile, committing the lockfile for the
  first time, or deleting the npm lockfile — all owned by task0002.
- Any CI workflow change — owned by task0003.
- Version changes to any dependency other than dompurify.
