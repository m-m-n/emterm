# Task Plan: task0002 — 依存グラフの凍結（lockfile のコミットと npm lockfile の削除）

## Goal

Make the JavaScript dependency graph resolve identically in every environment
by tracking the bun lockfile in git, removing the ignore rule that hides it, and
deleting the stale npm lockfile that currently causes a re-migration on every
fresh install.

## Requirements

FR1, FR2, FR3, FR8, NFR4

## Scope

### Files to Create

- `bun.lock` — the generated lockfile, newly tracked by git; the frozen
  resolution of the dependency declaration.

### Files to Modify

- `.gitignore` — the entry under the Bun heading (line 42 at the base commit)
  that currently hides the lockfile is removed.
- `package-lock.json` — deleted from the working tree and from the index; the
  bun lockfile becomes the only JavaScript lockfile.

## Design

### Why the graph drifts today

The lockfile is ignored, so a freshly created worktree has no frozen resolution
to install from. The install falls back to migrating the npm lockfile, and the
migration re-resolves the declaration's version ranges against the registry as
it stands at that moment. Two worktrees created at different times therefore
receive different graphs from the same commit. Removing the ignore rule and
committing the lockfile removes the drift; deleting the npm lockfile removes
the migration source, so no second resolution path remains.

### Ownership boundary

This task freezes whatever the declaration resolves to. It never chooses a
dependency version: the dompurify version decision is expressed solely in the
declaration and owned by task0001 (IMPLEMENTATION.md D1). Concretely, this task
does not edit `package.json`.

### Integration duty

Per IMPLEMENTATION.md's Lockfile / manifest sync duty, if the tree this branch
integrates with carries a changed dependency declaration, the lockfile this
task commits is regenerated from the merged declaration before committing —
never hand-edited, never reconciled by editing entries. The mechanical check is
that a frozen-lockfile install on a clean checkout of this branch exits zero.

### Determinism evidence

Reproducibility is demonstrated, not asserted (NFR4): two fresh worktrees are
created from the same commit of this branch, each installed independently from
the committed lockfile, and the dompurify version each resolves is compared as
a string. The comparison is between two independent installs, not between a
declaration range and an expectation.

### Drift guard behavior

The frozen-lockfile install is what makes drift loud. This task demonstrates
both directions locally: an unmodified checkout installs cleanly, and a
declaration mutated without regenerating the lockfile fails the install with a
non-zero exit. The mutation is performed in a scratch worktree and is never
committed. Wiring that same install form into CI is task0003's.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `git check-ignore -v bun.lock` finds no matching rule, and the
      lockfile is reported by git as tracked rather than untracked.
- [ ] AC-2: `package-lock.json` is absent from the working tree and from the
      index, and no other JavaScript lockfile exists at the repository root.
- [ ] AC-3: A frozen-lockfile install on a clean checkout of this branch exits
      zero — the committed lockfile matches the dependency declaration present
      on the branch.
- [ ] AC-4: Two independent clean installs of the same commit of this branch,
      in two separate freshly created worktrees, resolve dompurify to the
      identical version string.
- [ ] AC-5: Mutating a dependency range in the declaration without regenerating
      the lockfile makes a frozen-lockfile install exit non-zero; the mutation
      is confined to a scratch worktree and is not committed.
- [ ] AC-6: The committed lockfile is the unmodified output of an install run
      against the declaration present on this branch — no hand-edited entries.

## Test Notes

- AC-1, AC-2, AC-3 and AC-6 are single-command shell observations against the
  branch; capture the command and its exit status as the evidence.
- AC-4 and AC-5 need throwaway worktrees. Create them under a temporary
  location, and let them be removed by the environment rather than by a cleanup
  step that could delete the wrong path.
- The lockfile is a generated artifact: there is no unit test to write for it.
  The TDD-shaped part of this task is the pair of install observations (AC-3
  positive, AC-5 negative) — run the negative one first and watch it fail
  loudly before relying on it.
- Do not run the viewer entry suite as this task's own gate: whether those
  tests pass depends on the dompurify version decision owned by task0001, and
  the combined outcome is verified feature-wide (IMPLEMENTATION.md D3).

## Out of Scope

- Choosing or changing any dependency version, including editing `package.json`.
- The dompurify investigation and the sanitizer, in any form.
- CI workflow files — owned by task0003.
- Introducing a lockfile for any other package manager, or a checked-in
  dependency directory.
