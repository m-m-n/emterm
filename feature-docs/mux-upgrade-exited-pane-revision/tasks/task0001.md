# Task Plan: task0001 — Carry exited panes' full agent status through the hot-upgrade refresh

## Goal

After the hot-upgrade refresh, every exited pane's handoff entry holds the
agent state, agent name, revision and OSC 7501 records the pane has at refresh
time, all read at the same instant. A successor restored from that document
then sends the latest record and revision to the GUI when it resyncs.

## Design

### Which panes the refresh updates (unchanged)

The refresh walks every pane entry in the handoff document.

- An entry whose pane id is not found in the session manager is skipped and
  left untouched (FR3).
- A found pane is in the **exited set** when the document records no master
  descriptor for it, or when the manager marks the pane exited. This matches
  the term "終了済みペイン" in REQUIREMENTS.md section 13.
- Every other found pane is **live**.

### Read flow for each found pane

1. Acquire the pane's agent-status lock once. Read four values: the state (in
   wire form), the name, the revision, and the record export. Use the same
   record export the snapshot uses. Release the lock.
2. If the pane is in the exited set, write those four values into the entry's
   agent_state, agent_name, agent_revision and program_records. Leave every
   other field as recorded (FR2): id, cols, rows, cwd, title, exited,
   child_pid, master_fd, scrollback, latch_armed, latch_command_ended,
   latch_generation, alt_screen and alt_screen_dump. Then move to the next
   pane.
3. If the pane is live, also read the latch parts and the alt-screen state,
   exactly as today, and write every field exactly as today (FR3).

Step 1 is intentionally placed before the exited/live split, so both branches
share one read under one lock acquisition. That way the exited branch cannot
slide back to a records-only read or to two separate acquisitions. The live
branch behaves the same as before: its four values still come from one
acquisition, and a pane's exited flag cannot change while the caller holds the
session-manager lock.

### Refresh contract after the change

- **Precondition**: the document came from a snapshot of the same manager in
  this upgrade attempt, and the caller holds the session-manager lock (as the
  daemon's call site does today).
- **Postcondition**:
  - For every found pane, the entry's agent_state, agent_name,
    agent_revision and program_records equal the pane's agent status as read
    in one lock acquisition.
  - In exited-set entries, no other field changes.
  - Live entries are refreshed exactly as before.
  - Entries not found in the manager are untouched.
  - The handoff schema and its version do not change.

manager, the snapshot and restore helpers, and the record helpers. Reports are
applied through the pane's own apply operations (the OSC 7501 report-apply
operation and the OSC 777 event-apply operation), the same paths the daemon
uses, rather than by editing the table or revision directly.

- **Scenario 1 (TS-1)**: a live pane at revision 0 is snapshotted. An accepted

  that asserts AC-2. Its name must say that the refresh carries the
  since-exited pane's agent status, and must not say "untouched".
- **Scenario 3 (TS-3)**: a pane that is already exited at snapshot time, built
  by the exited-pane manager fixture. After the snapshot, an OSC 777 event and
  an OSC 7501 report are applied to it, either in one test or in two. The

- **Scenario 4 (TS-4)**: an async test, shaped like the existing daemon resync
  tests. Take the document from the scenario 1 steps and restore it. Wrap the
  restored manager in the shared handle the resync function takes. Subscribe

  post-snapshot resync. Assert AC-4.
- **ac3_refresh_pulls_in_a_program_record_added_to_an_exited_pane_after_snapshot**:
  keeps its name and still passes, because its setup edits the table directly

## Test Notes

- **Unit tests**: AC-1, AC-2 and AC-3 are synchronous unit tests of the
  refresh. AC-4 is an async unit test, because the resync function is async.
  All of them run under the project's --lib test command (NFR1).
- **Expected red against the current code**:
  - AC-1 fails on the revision (0 instead of 1).
  - AC-2 fails on state, name and revision.
  - AC-3 fails on the OSC 777 part.
  - AC-4 fails because the restored pane keeps revision 0, so the resync sends
    nothing and the receive times out.
- **AC-4 stale-descriptor hazard (must handle)**: the document from the AC-1
  steps still holds the master descriptor number recorded at snapshot time.
  Marking the pane exited closed that descriptor, and in a parallel test run
  the same number may already belong to another test. If the document is
  restored unmodified, restore would adopt that descriptor and later close it,
  which is someone else's descriptor. Before restoring, set the descriptor in
  the copy being restored to "none". Restore then rebuilds the pane as exited
  through its existing recorded-live-without-descriptor path, which logs a
  warning. The fields under test are not touched by this change.
- **AC-5**: compare against the failures already present at the task's base,
  recorded as the test record's baseline_failures. The project has known
  parallel-run flakiness in some tabs replay tests and in a load-sensitive
  thread-CPU-time budget test. Those are not regressions from this task.
- **AC-6**: verified by inspection in review. It cannot be expressed as a
  test; the AC-1 to AC-3 tests cover the values the single read produces.
- **AC-7**: use the --list command quoted in `.claude/rules/test-docs-records.md`.

## Out of Scope

- The descriptor/exited-flag mismatch for a pane recorded live but exited in
  the manager. Its master_fd, child_pid and exited stay as recorded.
- Refreshing the latch or alt-screen state of an exited pane.
- Any change to the handoff schema or its version.
- Behavior changes to the snapshot, restore or resync functions.
- A reader-thread barrier for the residual window between the refresh and
  exec.
- Old-name mentions in predecessor features' feature-docs prose, and in
  red_reason text.
