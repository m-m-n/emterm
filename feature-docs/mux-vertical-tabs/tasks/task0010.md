# Task Plan: task0010 — Route wheel scroll over the sidebar to the list

## Goal

When the pointer hovers the mux sidebar (persistent panel OR overlay
card) and the window list overflows, the mouse wheel scrolls the
sidebar's list — the event must NOT reach the terminal scrollback / PTY
path (2026-07-20 実機バグ報告 — the wheel is consumed by the terminal
while the sidebar shows a scrollbar).

## Requirements

FR2, NFR2

## Scope

### Files to Create
- (none)

### Files to Modify
- `src-tauri/src/window_host.rs` — the winit MouseWheel handler: add a
  sidebar-hover branch that forwards the wheel to egui (like the
  existing tab-bar-strip and profile-selector branches) and skips the
  terminal scroll path
- `src-tauri/src/ui/mux_sidebar.rs` — a pure hit-region helper the winit
  handler queries (single source of truth for "is this point over the
  sidebar", covering both placements), plus its unit tests
- `src-tauri/src/app.rs` — include for safety: the handler needs the
  sidebar visibility/placement state the App already owns
  (`mux_sidebar_visibility` readers); no behavioral change expected here

## Design

Observed defect: the winit `MouseWheel` handler forwards the wheel to
egui only for the profile-selector modal and the tab-bar strip; every
other position goes to the terminal scrollback / AltScreen-arrow / PTY
path. The sidebar's vertical scroll list therefore never receives wheel
input, even though it renders a scrollbar.

Fix shape (the established pattern in the same handler):

1. A pure helper in the sidebar module answers whether a logical point
   lies inside the sidebar's current region, given the placement mode,
   visibility, window logical size, and the top/bottom strip heights the
   terminal area excludes. Persistent = the right-edge panel strip
   (width function's value, terminal area's vertical span). Overlay =
   the floating card rect (16 px insets, same derivation as the draw
   path — reuse one derivation, do not duplicate the numbers).
2. The winit MouseWheel handler, BEFORE the terminal scroll path,
   queries that helper with the current cursor position when the
   sidebar is visible (persistent mode with a mux-attached active tab,
   or overlay mode with the overlay open); on a hit it forwards the
   wheel to egui exactly like the tab-bar branch and returns.

This is the defect class recorded in the round-2 lesson: manual
winit-side geometry guards do not automatically follow egui panels —
the guard must share the sidebar's own geometry derivation.

Constraints:

- Local tabs (no mux) and sidebar-hidden states must be completely
  unaffected: the branch must be a no-op there (NFR2), including the
  existing tab-bar strip, profile-selector, AltScreen arrow-scroll, and
  scrollback behaviors outside the sidebar region.
- No PTY resize, no grid geometry change, no new settings.
- egui-side: the list's scroll container already scrolls on forwarded
  wheel events (same mechanism as the tab strip); no draw-path change
  is expected beyond the shared hit-region derivation.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The hit-region helper returns true exactly inside the
      persistent panel strip when persistent+visible, exactly inside the
      overlay card rect when overlay+open, and false everywhere else
      (boundary points test both edges of each region)
- [ ] AC-2: With the sidebar visible and the cursor inside its region, a
      wheel event is forwarded to egui and the terminal scroll path is
      skipped (no scrollback movement, no AltScreen arrow bytes, no
      alt-scroll accumulator change)
- [ ] AC-3: With the sidebar hidden, on local tabs, or with the cursor
      outside the region, wheel behavior is byte-identical to before
      (scrollback / AltScreen / tab-strip / profile-selector paths
      unchanged)
- [ ] AC-4: The helper's geometry derives from the same constants/
      functions the draw paths use (no duplicated magic numbers) —
      guarded by a test relating helper output to the drawn geometry
- [ ] AC-5: Full lib suite has no new failures beyond the documented
      pre-existing tabs.rs flaky set

## Test Notes

AC-1/AC-4 are pure-function tests against the helper. AC-2/AC-3 follow
the existing wheel-handler test conventions in `window_host.rs` (the
alt-scroll accumulator and strip-band tests show the pattern: feed a
synthetic event state, assert which path consumed it). Actual
scroll-feel is manual (M-4).
