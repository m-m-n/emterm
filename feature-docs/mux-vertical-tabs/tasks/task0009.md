# Task Plan: task0009 — Overlay card follows window resize

## Goal

The overlay floating card tracks the current terminal area on EVERY
window resize: its position and size follow both growth and shrinkage of
the app window (2026-07-20 実機バグ報告 — resizing the app leaves the
overlay at its old geometry).

## Requirements

FR2, FR5

## Scope

### Files to Create
- (none)

### Files to Modify
- `src-tauri/src/ui/mux_sidebar.rs` — overlay variant draw path and its
  unit tests

## Design

Observed defect (real build): after resizing the app window, the overlay
card keeps its previous rect instead of following the new terminal area
and the new width-function value.

Suspected mechanism (verify during implementation): the overlay's
floating surface caches per-id state (size and/or position) from earlier
frames, and the current draw path only supplies the freshly computed
card rect as an initial default / minimum — so a changed window size
never reaches the painted geometry. The fix must make the per-frame
computed card rect fully authoritative over any cached surface state, in
both directions (grow AND shrink).

Constraints carried over unchanged:

- Card rect derivation stays as specified: width = shared width function
  of the CURRENT window width; 16 px inset from the CURRENT terminal
  area's top/right/bottom edges.
- 12 px radius, 92%-alpha fill, elevation-3 shadow, no separator, no
  scrim, no animation; painted rect == computed rect (task0008's
  paint-rect authority).
- Zero grid inset; toggle semantics and click routing unchanged.
- Persistent variant untouched (it participates in normal panel layout
  and already follows resizes).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Rendering two consecutive frames with different screen sizes
      (same egui context, e.g. large → small and small → large) yields a
      painted card rect that matches the SECOND frame's computed rect in
      both cases — position and size, grow and shrink
- [ ] AC-2: The card width follows the width function's value for the
      current window width across the resize (not the first frame's
      value)
- [ ] AC-3: task0008's paint-geometry assertions (painted rect ==
      computed rect, 8/12 px row insets, full inset height with few
      entries) still hold on the post-resize frame
- [ ] AC-4: Rounding, fill alpha, shadow, zero grid inset, toggle
      semantics, click routing, and the persistent variant are unchanged
- [ ] AC-5: Full lib suite has no new failures beyond the documented
      pre-existing tabs.rs flaky set

## Test Notes

AC-1/AC-2/AC-3 use the existing paint-rect test hook across MULTIPLE
frames of ONE context with different screen rects — the single-frame
tests from task0008 cannot catch cached-state staleness, which is
exactly how this bug escaped. Pixel appearance stays manual (M-4).
