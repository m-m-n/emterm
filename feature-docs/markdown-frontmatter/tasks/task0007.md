## Design

### 1. Single theme owner (round-2 finding, confidence 100)

Current state: three copies of "system → matchMedia light/dark" resolution
exist; the two in the shared applier register live `change` listeners, the
new one in `entry.ts` (task0006) writes `data-theme` once and never
updates. Consequence: in system mode a live OS theme flip updates the
`--markdown-*` palette but leaves `data-theme` (and thus the
`--fm-error` parse-error accent) stale.

Outcome: exactly one place resolves the effective markdown theme and it
writes BOTH the `--markdown-*` palette and `data-theme`, initially and on
every live system-theme change. The reviewers' recommended shape: move the
`data-theme` write into the markdown theme applier's palette-application
path (it already has the resolution and the listener); delete the copy in
`entry.ts`. Constraint: the applier is shared — other pages that call it
(fullscreen overlay path) must tolerate the attribute write (it is the
same attribute the settings UI already uses for theming; verify no
conflict with pages that manage `data-theme` themselves before choosing
the exact write target).

### 2. Parse-time node budget (round-2 finding)

Current state: `normalizeValue` copies the entire parsed value tree with
no size cap; `MAX_NODES = 2000` bounds only tree-builder row emission, so
a wide/flat document forces a full-size copy before truncation applies.

Outcome: normalization respects the same budget — a remaining-node counter
decrements as values are visited; once exhausted, remaining content is not
copied and the result carries a truncation signal that ends up in the same
user-visible truncated notice the tree already shows. The budget constant
stays defined in ONE module (currently tree-builder) and is imported, not
duplicated. Cycle guard behavior (`[Circular]`) is unchanged. Per the
updated SPEC (FR5), the budget applies "to normalization at parse time as
well as to tree building".
