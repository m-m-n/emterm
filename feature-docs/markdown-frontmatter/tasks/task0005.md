# Task Plan: task0005 — Renderer/viewer integration + regression

## Goal

Wire the front matter stages into the Markdown viewer pipeline: extract
before marked runs, render the stripped body through the existing renderer,
mount the block element above the body, and pin the no-front-matter
passthrough behavior.

## Requirements

FR7 (plus the integration surface of FR1/FR2/FR6, and NFR4)

## Scope

### Files to Create
- `src-tauri/web-shared/markdown/frontmatter/integration.test.ts` —
  pipeline-level tests (extract → render → block)

### Files to Modify
- `src-tauri/web-shared/markdown/renderer.ts` — pre-processing hook so the
  body passed to marked is the stripped body (keeps its string API,
  IMPLEMENTATION.md D3)
- `src-tauri/viewer/web/entry.ts` — obtain the extraction/parse results,
  mount the block element above the rendered body, import the new CSS
- `src-tauri/viewer/web/entry.test.ts` — extend for the mounted block and
  the passthrough case

## Design

- Flow (SPEC.md Data Flow): source → extractor (task0001) → parser
  (task0002) on hit → existing marked/DOMPurify rendering of the (possibly
  stripped) body → block view (task0004) mounted above the body container
  when front matter was found.
- Split of responsibilities per IMPLEMENTATION.md D3: the renderer's
  contract stays string-in/string-out; the entry owns DOM mounting. The
  exact hook shape (where extraction is invoked so both CLI-delivered and
  future callers benefit) is this task's main design decision — decide it
  against the constraint that `render()` must never receive delimiter
  lines when front matter exists, and document the choice in code
  placement (not comments).
- Passthrough (FR7): when extraction reports "no front matter", the
  string reaching marked is the original source and no block-related DOM
  is created. Rendering output must be unchanged vs. today.
- Error path (FR6): a parse failure still mounts the block (error state)
  and still renders the stripped body.
- The outline panel and Mermaid post-processing operate on the rendered
  body only and must be unaffected.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A YAML-front-matter document renders body HTML containing no
      `hr` / heading artifacts from the delimiters, and the block element
      is present above the body with the YAML badge.
- [ ] AC-2: The same holds for TOML and JSON documents.
- [ ] AC-3: A broken-front-matter document renders the body without the
      block content leaking in, and the mounted block is in the error
      state.
- [ ] AC-4: A document without front matter renders output identical to
      the pre-change renderer for the same input (fixture comparison),
      and no block element is mounted.
- [ ] AC-5: A document that is only front matter renders an empty body
      plus the block.
- [ ] AC-6: Existing viewer tests (entry, outline, mermaid) still pass.

## Test Notes

Integration tests exercise the real extractor/parser/view modules together
(no mocking); covers SPEC.md TS-11, TS-12, plus the front-matter-only edge
case. AC-4 needs a pre-change expected-output fixture: generate the
expected HTML with the unmodified renderer path (no front matter → the
pipeline must be byte-identical by construction) and assert equality.
Performance (NFR4) is not micro-benchmarked; the fast path is structural
(AC-4 reference-passthrough from task0001).
