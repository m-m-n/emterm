# Markdownビューアーのフロントマター対応 - 要件定義書

## 1. 概要

### 1.1 背景

現状、フロントマター処理は未実装であり、フロントマター付きMarkdownファイルを表示すると区切り記号（`---` 等）がそのまま marked に渡り誤描画される。YAMLフロントマターの `---` は罫線（hr）や setext 見出しに化ける。

### 1.2 目的

Markdownビューアーで YAML / TOML / JSON の3形式のフロントマターを正しく解析し、本文への誤描画を防ぎつつ、折りたたみUIで内容を確認できるようにする。

### 1.3 スコープ

- 対象: TS側 `src-tauri/web-shared/markdown/renderer.ts` の前処理（marked に渡す前の検出・パース・除去）と、フロントマター表示UI
- スコープ外:
  - ORG等、YAML / TOML / JSON 以外のフロントマター形式
  - `---json` フェンス等の方言記法
  - CLI（`emterm markdown`）側の変更（ファイル内容をそのまま送るだけなので変更不要）
  - ネイティブデータビューアー（`--data-viewer`）側の変更

## 2. ビジネス要件

### 2.1 ビジネス目標

フロントマター付きMarkdownファイル（静的サイトジェネレーター系ドキュメント等）を eMterm の Markdownビューアーで正しく表示できるようにする。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| eMterm利用者 | `emterm markdown <file>` でフロントマター付きMarkdownを表示するユーザー |

### 2.3 期待される効果

- フロントマターの区切り記号が罫線・見出しに化ける誤描画がなくなる
- フロントマターの内容（メタデータ）を折りたたみUIから確認できる

## 3. ユースケース

### 3.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | フロントマター付きMarkdownの表示 | eMterm利用者 | 高 |
| UC02 | 壊れたフロントマター付きMarkdownの表示 | eMterm利用者 | 高 |
| UC03 | フロントマター無しMarkdownの表示（回帰なし） | eMterm利用者 | 高 |

### 3.2 ユースケース詳細

#### UC01: フロントマター付きMarkdownの表示

**アクター**: eMterm利用者

**事前条件**:
- ファイル先頭に YAML（`---`）/ TOML（`+++`）/ JSON（裸の `{...}`）いずれかのフロントマターを持つMarkdownファイルがある

**基本フロー**:
1. 利用者が `emterm markdown <file>` を実行する
2. Markdownビューアーが開き、本文の上部に折りたたまれたフロントマターブロック（「Front Matter」ラベル + 形式バッジ）が表示される
3. 本文にはフロントマターの区切り記号・内容が描画されない
4. 利用者がヘッダーをクリックして展開すると、パース結果が全展開のツリー表示で確認できる

**代替フロー**:
- フロントマターの中身が壊れている場合 → UC02

**事後条件**:
- 本文が正しくレンダリングされ、フロントマターは折りたたみブロック内に隔離されている

#### UC02: 壊れたフロントマター付きMarkdownの表示

**アクター**: eMterm利用者

**事前条件**:
- 区切り記号は正しいが、中身が不正（不正なYAML等）なフロントマターを持つMarkdownファイルがある

**基本フロー**:
1. 利用者が `emterm markdown <file>` を実行する
2. フロントマターは本文に流さず除去される
3. 折りたたみブロックに解析失敗の旨が表示される
4. 展開すると生テキストが表示され、壊れた箇所に気づける

**事後条件**:
- 本文に `---` 等の誤描画が発生しない

#### UC03: フロントマター無しMarkdownの表示（回帰なし）

**アクター**: eMterm利用者

**事前条件**:
- フロントマターを持たないMarkdownファイルがある（文中に `---` 罫線や setext 見出しを含む場合もある）

**基本フロー**:
1. 利用者が `emterm markdown <file>` を実行する
2. 従来どおり本文がレンダリングされる（フロントマターブロックは表示されない）

**事後条件**:
- 既存の表示と同一の結果になる

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | フロントマター検出・除去 | ファイル先頭の区切り記号で形式判定し、本文から除去する | 高 |
| F02 | フロントマター解析 | YAML / TOML / JSON をパースして構造化データに正規化する | 高 |
| F03 | 折りたたみ表示 | デフォルト閉。ヘッダーに「Front Matter」ラベルと形式バッジを表示する | 高 |
| F04 | ツリー表示 | 展開時、パース結果を常に全展開のツリーで表示する | 高 |
| F05 | 解析失敗フォールバック | パース失敗時は本文に流さず除去し、折りたたみ内にエラー表示 + 生テキスト表示 | 高 |

### 4.2 機能詳細

#### F01: フロントマター検出・除去

**説明**: ファイル先頭に1ブロックだけ置けるフロントマターを、先頭の区切り記号で形式判定して検出し（`---`=YAML / `+++`=TOML / `{`=JSON）、marked に渡す前に本文から除去する。複数形式の同居は不可で、先頭判定による排他分岐とする。

**入力**:
- markdown: string - ビューアーに渡されたMarkdownソース全文

**出力**:
- 本文文字列（フロントマター部分を除去済み）
- フロントマター情報（形式・生テキスト）。検出されなかった場合はなし

**ビジネスルール**:
- ファイル先頭のみ認識する（先頭以外の区切り記号は本文として扱う）
- YAML: 1行目が `---`、閉じは後続の行頭 `---` 行
- TOML: 1行目が `+++`、閉じは後続の行頭 `+++` 行
- JSON: 先頭文字が `{`、対応が取れる `}` まで（Hugo系デファクト）
- 閉じ区切りが見つからない場合はフロントマターとして扱わず、全体を本文として描画する

#### F02: フロントマター解析

**説明**: 検出したフロントマターを形式に応じてパースし、構造化データ（オブジェクトツリー）に正規化する。

**入力**:
- フロントマター生テキストと形式（YAML / TOML / JSON）

**出力**:
- パース済みオブジェクトツリー、またはパースエラー

**ビジネスルール**:
- JSON は組み込み `JSON.parse` を使う
- YAML / TOML はJSライブラリを追加する（ライブラリ選定は実装フェーズで実施）

#### F03: 折りたたみ表示

**説明**: 本文レンダリング結果の上部に折りたたみブロックを表示する。

**ビジネスルール**:
- デフォルトは閉じた状態（ヘッダーのみ表示）
- ヘッダーには「Front Matter」ラベルと形式名バッジ（YAML / TOML / JSON）を表示する
- クリックで開閉できる

#### F04: ツリー表示

**説明**: 折りたたみブロックを展開すると、パース結果のネスト構造をツリーで表示する。

**ビジネスルール**:
- 常に全展開で表示する（ノード個別の開閉トグルは設けない）
- 実装は `legacy/webview` ブランチの旧WebView実装（`src/data-viewer/tree-builder.ts` 等）を参考に、TS側へ新規実装する
- 見た目はネイティブJSON/YAMLデータビューアーのツリー表示に寄せる

#### F05: 解析失敗フォールバック

**説明**: 区切り記号はあるが中身が壊れている場合（不正なYAML等）のフォールバック。

**ビジネスルール**:
- 本文には流さず除去する
- 折りたたみブロックに解析失敗の旨を表示する
- 展開すると生テキストを表示する

**エラーケース**:

| エラー | 条件 | 対応 |
|--------|------|------|
| パース失敗 | 区切り記号は正しいが中身が不正 | 本文から除去し、折りたたみ内にエラー表示 + 生テキスト表示 |
| 閉じ区切りなし | 開始区切りのみで閉じが無い | フロントマターとして扱わず本文として描画 |

## 5. 非機能要件

### 5.1 パフォーマンス要件

- フロントマター前処理が体感できる描画遅延を生まないこと

### 5.2 セキュリティ要件

- 入力検証: フロントマターの値をDOMに挿入する際はエスケープ済みであること（既存ビューアーのXSS防護方針を踏襲）
- 過剰なネスト深度・ノード数に対する上限を設けること（上限超過時は切り詰めを通知表示する）

### 5.3 可用性要件

- 該当なし

### 5.4 保守性要件

- テスト: `bun test`（happy-dom）でユニットテストを整備する

### 5.5 互換性要件

- 子WebView（Linux: WebKitGTK / Windows: WebView2）の両方で動作すること
