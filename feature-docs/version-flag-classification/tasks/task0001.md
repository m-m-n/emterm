# Task Plan: task0001 — Register `--version` in the flag table and usage text

## Goal

`--version` becomes a first-class member of the top-level flag table on both
the `gui` and CLI-only builds: the classifier accepts it at any argument
position, the usage text lists it, and the GUI dispatch loop ignores it
because it has no child window to open.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/arg_dispatch.rs` — add the `--version` entry to both build
  variants of the recognized-flag table; give the entry type a way to express
  "no dispatch target"; add the `--version` line to both build variants of the
  usage text; update the module-level documentation comment to describe the
  non-dispatching case; update and extend the unit tests.
- `src-tauri/src/main.rs` — update the GUI dispatch loop so it only considers
  table entries that declare a child-window target.

## Design

### Recognized-flag entry

The entry type currently carries, on the `gui` build, a mandatory child-window
dispatch target. It must be able to express that a flag has no such target.
The classifier is unaffected by this distinction — it only reads the flag name
and whether the flag consumes the following argument.

Contract:

- Precondition: every entry names a flag the build accepts.
- Postcondition (classifier): a flag whose name appears in the table is never
  reported as unrecognized, at any position in the argument list.
- Postcondition (GUI dispatch): only entries declaring a target are candidates
  for opening a window. An entry without a target is skipped and the scan
  continues to the next entry.

### `--version` entry

- Name: the literal `--version`.
- Consumes a following argument: no. A token after `--version` is classified
  on its own merits (so `emterm --version --typo` still reports `--typo`).
- Dispatch target: none.
- Present in the `gui` table and in the CLI-only table. The CLI-only table,
  previously empty, now holds exactly this one entry.

### GUI dispatch loop

The loop walks the table looking for the first entry whose flag is present in
the argument list, then opens the corresponding window. It must now skip
entries that declare no target before considering presence, so a `--version`
appearing anywhere never causes a window to open on its account, and the loop
falls through to normal terminal startup as it does today when no child-window
flag is present.

### Usage text

Both build variants gain one Options line for `--version`, placed immediately
above the `-h, --help` line and aligned with the existing entries' description
column. The trailing `Run \`emterm <subcommand> --help\` for details.` guidance
line stays exactly where it is.

### What does not change

The binary's pre-logging early exit still inspects only the first argument
(IMPLEMENTATION.md D2). This task does not move, duplicate, or widen it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: On the `gui` build, classifying an argument list containing
      `--version` — alone, or after another recognized flag such as the
      settings flag — yields the "proceed" outcome, not an unrecognized-argument
      outcome.
- [ ] AC-2: On the CLI-only build, classifying an argument list containing only
      `--version` yields the "proceed" outcome.
- [ ] AC-3: `--version` does not consume the following argument: classifying
      `--version` followed by an unrecognized flag reports that unrecognized
      flag.
- [ ] AC-4: The usage text on the `gui` build contains a line describing
      `--version` inside the Options block, and still contains the subcommand-
      help guidance line.
- [ ] AC-5: The usage text on the CLI-only build contains a line describing
      `--version` inside the Options block, and still contains the subcommand-
      help guidance line.
- [ ] AC-6: The table-content tests are updated to assert the new expected
      contents on both builds (they still pin the exact set — no loosening to a
      containment check), and they pass.
- [ ] AC-7: A test asserts that the `--version` entry declares no child-window
      dispatch target, so a future edit that gives it one fails the suite.
- [ ] AC-8: Help still wins: an argument list containing both `--version` and a
      help flag yields the help outcome.
- [ ] AC-9: The five existing `--version` integration tests in
      `src-tauri/tests/cli_subcommands.rs` pass without being modified.
- [ ] AC-10: Both builds compile: the default-feature check and the
      `--no-default-features` check each exit 0.

## Test Notes

- AC-1 through AC-8 are unit tests in the existing test module of
  `src-tauri/src/arg_dispatch.rs`, split across its `gui` and CLI-only
  submodules the same way the current tests are.
- AC-9 is satisfied by running the existing integration test binary; no new
  integration test is required, and the existing ones must not be edited.
- AC-10 is a build check rather than a test assertion; it is covered by the
  two build commands in workflow.yaml `project.components`.
- Write the tests first: every acceptance criterion above except AC-10 maps to
  at least one assertion, and each should fail against the current code before
  the change is made.
- Edge case worth an explicit test: a `--version` supplied as the *value* of a
  value-taking flag must still be consumed as that flag's value and never
  classified. This behavior already exists; a test pins that the new entry did
  not disturb it.

## Out of Scope

- Changing what `--version` prints, or its exit code.
- Making `--version` print the version when it appears at a position other
  than the first argument (IMPLEMENTATION.md D2).
- Adding any other flag to the table.
- The known-flaky `tabs` tests, which fail independently of this change.
