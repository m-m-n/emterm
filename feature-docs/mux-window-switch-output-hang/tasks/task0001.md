# Task Plan: task0001 — Fix daemon connection self-deadlock on pane snapshot delivery under high-volume PTY output

## Goal

Ensure the mux daemon's per-connection task never blocks itself when
delivering a pane snapshot (triggered by a client window/tab switch) while
that pane's shared PTY output channel is at or near capacity, so window
switches and other-pane input keep working while a pane is producing
high-volume output.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2

## Scope

### Files to Modify
- `src-tauri/src/mux/ipc/connection.rs` — per-connection `select!` loop;
  change how pane-snapshot delivery is initiated/sequenced relative to the
  loop's own PTY-output drain arm so the loop can never be the sole blocked
  party on a channel only it can drain.
- `src-tauri/src/mux/ipc/handlers.rs` — `handle_request_pane_snapshot`;
  change how the snapshot chunk reaches the client so it does not perform a
  blocking send against a channel that is only drained by the very task
  executing this handler.
- `src-tauri/src/mux/session/pane.rs` — pane output channel definitions
  (`PTY_CHANNEL_CAPACITY`, `pane_output_tx`/`rx` types); adjust only if the
  chosen resolution requires a structural change here (e.g. an additional
  channel or an explicit ordering primitive). Do not change
  `PTY_CHANNEL_CAPACITY`'s value unless the chosen approach requires it —
  if changed, state the new value and why in this task's own notes at
  implementation time.

### Files to Create
None expected. If the chosen resolution introduces a small new internal
type (e.g. an ordering token or a dedicated forwarding helper), keep it
in one of the files above rather than a new file, unless doing so would
make an existing file unreasonably large — if so, note the deviation.

## Design

### Problem being fixed

The per-connection `select!` loop in `connection.rs` has two arms sharing
one bounded `pane_output_tx`/`pane_output_rx` channel (capacity 256, shared
across all panes in the session): the client-message-dispatch arm (which can
invoke `handle_request_pane_snapshot` via `route_message`) and the
PTY-output-drain arm (`pane_output_rx.recv()`, forwarding queued output to
the client). `handle_request_pane_snapshot` currently enqueues the snapshot
chunk onto that same channel with a blocking send. When the channel is full
(sustained high-volume PTY output faster than the socket drains it), that
blocking send suspends the connection task — but only that same task's own
drain arm can free capacity, and it cannot run while the task is suspended
inside the send. The task self-deadlocks: no further client messages are
processed for the whole connection, and no further PTY output for any pane
on the connection is forwarded, until the stall is broken (which today it
is not).

### Required behavior after the fix

- A pane-snapshot request MUST be satisfiable (the client eventually
  receives the snapshot chunk) without ever requiring the connection's own
  `select!` loop to be the entity that frees capacity in a channel it is
  itself blocked sending into.
- While a snapshot delivery is in flight/pending for one pane, the
  connection's `select!` loop MUST remain available to process incoming
  client messages (e.g. `PtyInput` for a different pane) and to drain
  already-queued PTY output for all panes — i.e. the loop must keep making
  progress on its other arms regardless of snapshot delivery state.
- The snapshot chunk for a pane MUST be observed by the client positioned
  in FIFO order relative to PTY output chunks that were already queued for
  that SAME pane at the moment the snapshot was requested (chunks queued
  for the pane AFTER the snapshot request may follow the snapshot; the
  guarantee is only about chunks already queued before the request).
- The mechanism chosen MUST keep an equivalent bound on in-flight/queued
  data (no unconditionally unbounded channel introduced as the sole
  backpressure mechanism) — a full or near-full condition should still be
  observable (e.g. via existing/adjusted backpressure logging) rather than
  silently absorbed by unbounded growth.
- Existing behavior for a closed/gone channel (e.g. the connection ending
  while a send is pending) must continue to be handled the same way it is
  today — no new panic or unhandled error path.

### Audit note (mandatory before considering the fix complete)

Before finishing, confirm (and record the confirmation as a one-line note in
this task's implementation, e.g. a code comment or PR-facing note — not a
new doc) that no other code path reachable from `route_message` performs a
blocking send on `pane_output_tx` (or whatever channel replaces/supplements
it) from within the same connection task without a way for that task's own
drain arm to make progress concurrently. If another such path is found,
apply the same resolution pattern there instead of only for
`handle_request_pane_snapshot`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With the pane output channel filled to capacity by simulated
      high-volume PTY output for pane A, issuing a snapshot request for pane
      A (the same pane) still results in the connection task processing a
      subsequently-arriving client message (e.g. `PtyInput` for pane B)
      within a bounded, short time — the connection does not hang.
- [ ] AC-2: Same setup as AC-1 but the snapshot request targets a different
      pane B while pane A is the one producing high-volume output; the
      connection continues to process messages and forward pane A's queued
      output.
- [ ] AC-3: When a snapshot is requested for a pane that already has N PTY
      output chunks queued ahead of it, the client observes those N chunks
      before the snapshot chunk, in the same relative order they were
      queued (FIFO preserved for that pane).
- [ ] AC-4: The channel/queue used for pane output (including snapshot
      delivery) still has a finite, inspectable bound after the fix — no
      test or code path relies on unconditionally unbounded queuing to pass.
- [ ] AC-5: Existing mux/tabs test suite (`cargo test --lib`, run with
      `--test-threads=1`) passes with no new failures beyond the
      pre-existing, unrelated failures already documented in project memory
      for this test suite (if any are still present, they must be
      independently reproducible on unmodified `main`, not introduced by
      this task).

## Test Notes

- AC-1/AC-2/AC-3 are best covered as unit or narrow integration tests
  against the connection task's channel-handling logic directly (constructing
  a full daemon+client harness is not required if the `select!` loop's
  channel interaction can be exercised at a lower level); if the existing
  test infrastructure has no such harness, add the minimal one needed —
  prefer extending existing test utilities for `connection.rs` /
  `handlers.rs` / `pane.rs` over inventing a new one.
- AC-4 can be a straightforward assertion/inspection of the channel's
  declared capacity or an explicit backpressure-triggering test that
  confirms bounded behavior (e.g. a full channel still applies backpressure
  rather than growing without bound).
- AC-5 is the standard regression gate; run with `--test-threads=1` per
  project convention for `tabs.rs` off-thread-worker test determinism.
- Write tests FIRST per the tdd-testing discipline skill, confirm they fail
  against the current (buggy) behavior, then implement until they pass.

## Out of Scope

- Client-side snapshot handling (`src-tauri/src/tabs.rs` off-thread replay)
