# task0002: Rework — bound and sequence the deferred delivery mechanism introduced by task0001

Synthesized by the orchestrator from review round 1 residual critical/high
findings (batch-mode.md "Rework task synthesis"). Not produced by the planner.

## Why this is ONE task instead of one-per-file

The synthesis rule is "one task per affected file". It is deliberately not
followed here, and the deviation is recorded in the batch report.

All nine residual findings describe **one** defect class: task0001 replaced a
blocking `send().await` with "spawn a detached task that waits for capacity",
and that single mechanism appears in two places —
`pane::enqueue_pane_output_chunk` (chunk send) and
`handle_set_visibility`'s Full arm (permit reserve). Both call sites must adopt
the *same* replacement design (a bounded, order-preserving deferred path). Two
concurrent implementers on two worktrees would each pick a design
independently, and the parent-side-adoption conflict protocol would resolve the
textual conflict without resolving the design divergence. One task keeps the
mechanism coherent.

## Findings to resolve (verbatim from reviews/round1.yaml)

### F1 — `src-tauri/src/mux/ipc/handlers.rs:821` (high, comprehensive)
**遅延 visibility-resume が後続の SetVisibility(false) を無視し、隠れたペインを Connected に戻す**

handle_set_visibility の `TrySendError::Full` 分岐で spawn される遅延タスクは、
permit 取得後に `visible_state` を再確認しない。(1) visible=true・チャネル満杯で
pane P の resume を遅延 spawn、(2) 遅延タスクが走る前に visible=false が届く。隠れ
エッジは `evaluate_output_target(pane, false, false, ..)` を呼ぶだけで、P は既に
`Detached{HiddenByVisibility}` なので `EvalResult::Unchanged` となり、保留中の遅延
resume はキャンセルされない。(3) 遅延タスクが後で走ると reason は依然
`HiddenByVisibility` なので `resume_pane_with_permit` 内の `clear_hidden()` が None を
返し、スナップショットを送って `Connected` にスワップしてしまう。

影響は 2 つ。(a) hidden を宣言済みのクライアントへ PTY 出力が流れ続ける。(b) より
深刻なのは次の visible→true エッジで、P は既に `Connected` なので
`resume_pane_with_permit` が `NoChange` を返しスナップショットが一切送られない →
ウィンドウ再表示時に画面が古いまま/欠落したままになる。これは本 feature が潰そうと
している症状そのもの。handlers.rs:727-731 の doc の主張する安全網は存在しない。

**Suggestion**: spawn 前に `visible_state` を clone して渡し、`session_manager.lock().await`
の後に `visible_state.load(Ordering::Acquire)` を確認して false なら permit を drop
して return する。可視フラグの読みを manager ロック取得後に置くのが要点 — 隠れエッジは
`visible_state.swap(false)` を先に済ませてから同じ manager ロックを取るため、ロック
取得後に load すれば競合が閉じる。doc も実態に合わせて訂正する。

### F2 — `src-tauri/src/mux/ipc/handlers.rs:804` (high, architecture)
**遅延された visibility-resume が状態権威 visible_state を再検証せず、hidden のまま Connected に戻し得る**

同じ欠陥をアーキテクチャ観点から。状態遷移を、その状態を所有する権威
(`visible_state`) の外側へ非同期に持ち出したことが構造的な原因。

**Suggestion**: permit 取得後・pane 解決後に `visible_state` を再検証する。より根本的
には、可視性判定を `resume_pane_with_permit` / `evaluate_output_target` 側の eligibility
判定に組み込み、resume の適用可否をこの状態機械の内側だけで決められるようにして、
遅延パスが独自に前提を持たなくて済む形にする。

### F3 — `src-tauri/src/mux/ipc/handlers.rs:821` (high, spec)
**遅延 visibility-resume が再 hide を無視して pane を Connected に戻す（SPEC Edge case 2）**

SPEC.md「Test Scenarios / Edge Cases → Edge case 2: Multiple rapid window switches
while output is ongoing」が壊れる。`handle_set_visibility` 先頭の `prev == visible`
ガードにより、その後の `SetVisibility(false)` は早期 return するため、pane は次の
show→hide サイクルまで hidden のまま `Connected` で live PTY 出力を流し続ける

### F4 — `src-tauri/src/mux/session/pane.rs:393` (high, comprehensive)
**enqueue_pane_output_chunk の遅延パスは FIFO を保証しない（doc の主張と実挙動が乖離）**

doc は「tokio's bounded mpsc channel wakes waiting senders in the order they started
waiting ... before any producer that only starts waiting later (FR3 preserved)」と書く
が、後半は成立しない。spawn したタスクが待機列に登録されるのは呼び出し時点ではなく
ランタイムが最初にポーリングした時点で、その間に他のプロデューサが割り込める。PTY
リーダースレッド（pty_spawn.rs:795 付近）は同じ `pane_output_tx` に `try_send` →
満杯なら `blocking_send` している。spawn したタスクが未ポーリングの間に drain が
スロットを空ければ、スナップショット採取後に取り込まれたバイト X が先に着き、
connection.rs:389 の drain が Snapshot を `MessageType::Snapshot` として送るため
クライアントの全面再構築で X が丸ごと消える。満杯中に 2 回呼ばれると spawn 2 本の
登録順は不定で、新しいスナップショットの後に古いものが着地して画面が巻き戻ることもある。

**追加所見（同一サイトに統合）**: `pub fn enqueue_pane_output_chunk` は非 async だが
Full 分岐で `tokio::spawn` を呼ぶため、tokio ランタイムコンテキスト外から呼ぶと panic
する。panic するのは満杯という稀パスのみで通常運用では露見しない。将来リーダー側の
送信をこの共通ヘルパーに寄せると「高負荷時だけリーダースレッドが panic する」障害になる。

### F5 — `src-tauri/src/mux/session/pane.rs:486` (high, architecture)
**新公開ヘルパーが保証できない FIFO 契約を doc で宣言し、両呼び出し元がそれに依存している**

`handle_request_pane_snapshot` (handlers.rs:579-581) と connection.rs の audit note が
その契約を前提に書かれている。抽象の公開契約が実装で担保できていないため、将来の
呼び出し元も同じ誤前提で書かれる。

**Suggestion**: (a) connection が所有する順序付きステージングに積み、connection 自身が
順序権威を持つ。(b) 遅延パスでも pane の `output_target` ロック経由で reader スレッドと
同じ順序ロックを共有する。(c) 順序保証を提供しないと割り切り、doc から FR3 preserved の
記述を削除してスナップショットに世代番号を持たせ、クライアント側で古いものを破棄できる
ようにする。

### F6 — `src-tauri/src/mux/session/pane.rs:396` (high, performance)
**スロットパスの tokio::spawn 遅延キューが無制限でバックプレッシャを無効化する**

この遅延キューには一切の上限が無く、生成数も保持バイト数も追跡されていない。capacity=256
の bounded channel が「同時に in-flight にできるバイト数の上限」として機能しなくなる。
`encoded_snapshot` は scrollback 全体（`DEFAULT_SCROLLBACK_CAPACITY` = 2 MiB）+ shadow
parser のスクリーンダンプで、`MAX_SNAPSHOT_FRAME_PAYLOAD` まで許容される。チャンネルが
満杯になるのは「pane が大量出力していて client 側 drain が追いついていない」状態であり、
その間 spawn したタスクは完了しない。高速にウィンドウ/タブを切り替えれば切り替え回数ぶんの
RequestPaneSnapshot が発行され、その一つ一つが数 MiB の Vec を保持したまま常駐する。

**Suggestion**: (a) 遅延中チャンク数 / 合計バイト数を `Arc<AtomicUsize>` で数え、上限
超過時は spawn せず warn してドロップする（Snapshot は完全な再構成なので落としても後続
要求で回復でき部分欠損にならない）。(b) pane ごとに「未完了の遅延 Snapshot は 1 個まで」に
制限し、新規 spawn 前に古いハンドルを `abort()` して差し替える。

### F7 — `src-tauri/src/mux/session/pane.rs:406` (high, performance / codex)
**Full-channel snapshots escape the channel's memory bound**

Every failed `try_send` spawns a task that retains the entire chunk until capacity
becomes available. Snapshot chunks can approach 2 MiB, and the connection select loop
prioritizes inbound messages over draining output. A slow outbound client issuing
repeated snapshot requests can accumulate an unbounded number of multi-megabyte
buffers and tasks outside the nominal 256-item channel, eventually exhausting daemon
memory.

**Suggestion**: Keep overflow state bounded and connection-owned — retain at most one
pending snapshot per pane and coalesce newer requests, or use one dispatcher backed by
a strictly bounded pending-byte budget. Reject, drop, or disconnect on excess work
instead of spawning one task per chunk.

### F8 — `src-tauri/src/mux/session/pane.rs:393` (high, architecture / codex)
**Overflow tasks bypass the bounded backpressure boundary**

This directly violates the bounded-memory contract; a test only asserting the channel
constant remains 256 cannot detect this secondary unbounded queue.

**Suggestion**: Keep overflow state in a connection-owned, explicitly bounded queue or
coalesce pending snapshot requests. Add a test that repeatedly submits requests while
the channel remains full and verifies the total pending backlog is bounded.

### F9 — `src-tauri/src/mux/session/pane.rs:396` (high, spec — claude + codex agreement, confidence 100)
**FR4「等価な上限」なしに deferred send タスクが無制限に積み上がる**

SPEC FR4: "The fix MUST NOT introduce unbounded memory growth as a replacement
backpressure mechanism (e.g. an unbounded channel is not an acceptable unconditional
replacement for the bounded channel without an equivalent bound elsewhere)". 本 diff は
bounded channel 自体は 256 のまま残すが、その手前に個数無制限の副キューを作っており、
"equivalent bound elsewhere" に相当する上限がない。旧実装ではブロッキング send が
backpressure として機能しメモリは有界だった。FR4 に対する唯一のテスト（AC-4 →
`pty_channel_capacity_is_finite_and_unchanged`）は定数 256 を assert するだけで、新設した
遅延機構の有界性を一切検証していない。同じパターンは visibility-resume fallback
(handlers.rs:804-848) にも現れる。

## Acceptance Criteria

- **AC-1 (F1/F2/F3)**: 遅延 visibility-resume は permit 取得後に可視状態を再検証し、
  その時点で hidden なら pane を `Connected` に戻さない。回帰テスト: visible=true で
  チャネル満杯 → `SetVisibility(false)` → 容量解放 → pane が `Detached { HiddenByVisibility }`
  のままであること。あわせて handlers.rs:727-731 の doc から誤った安全網の記述を除く。
- **AC-2 (F4/F5)**: 遅延パスを通ったチャンクが、スナップショット構築後に生成された同一
  pane の PTY チャンクに追い越されない。回帰テスト: 満杯状態で snapshot を enqueue →
  遅延中に reader 相当の並行プロデューサから追加チャンクを送る → 受信順で Snapshot が
  先であること。順序を構造的に保証できない設計を選ぶ場合は、pane.rs / handlers.rs /
  connection.rs の doc と SPEC FR3 の双方から成立しない FIFO 主張を除き、クライアント側で
  古いスナップショットを破棄できる手段（世代番号等）を伴うこと。
- **AC-3 (F6/F7/F8/F9)**: 遅延機構の保留量に明示的な上限がある（チャンク数またはバイト数）。
  回帰テスト: チャネルが満杯のまま N 回連続で enqueue しても、保留中のチャンク数
  （またはバイト数）が定めた上限を超えないこと。上限到達時の挙動（drop + warn / coalesce /
  detach 経路への合流）がコード上で明示されていること。同じ上限が deferred visibility
  resume にも適用されること。
- **AC-4**: `enqueue_pane_output_chunk` の tokio ランタイム前提が機械的に守られている
  （`pub(crate)` 化 / `Handle::try_current()` フォールバック / `Handle` 引数のいずれか）。
  ランタイム外から Full 分岐を踏んだときの挙動を固定するテストがあること。
- **AC-5**: task0001 が満たした FR1/FR2（self-deadlock 解消・接続の応答性維持）が引き続き
  成立する。既存の 7 テスト（pane.rs 4 + handlers.rs 3）が緑のままであること。
- **AC-6**: `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib -- --test-threads=1`

## Notes for the implementer

- The three defect groups are one mechanism. Decide the replacement design ONCE
  (bounded + order-preserving deferred delivery, connection-owned) and apply it to
  both `pane::enqueue_pane_output_chunk` and `handle_set_visibility`'s Full arm.
  The architecture reviewer's medium finding (handlers.rs:786) asks for the duplicated
  reserve → resolve → resume block to be factored out; doing so is the natural way to
  make one mechanism serve both call sites.
- Do NOT reintroduce a blocking `send().await` / `reserve().await` on the connection
  task — that is the original self-deadlock (FR1/FR2) task0001 fixed and AC-5 guards.
- `PTY_CHANNEL_CAPACITY` stays 256; the bound this task adds is for the deferred path.
