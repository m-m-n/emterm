## G1 (the only code change) — `defer_chunk` must not drop the snapshot reply

`reviews/round5.yaml`: `4043ee676f69ca15` (comprehensive, high),
`1c8d86389ab4bf40` (architecture, claude+codex, high), plus the spec-side mediums
`defer_chunk の VisibilityResume 併存時ドロップは FR3 が列挙しない第3の破棄経路`.

task0005 added: if a `VisibilityResume` for the same pane is already queued, drop the
incoming snapshot `Chunk` entirely. The stated premise is that the resume's flush
always builds a fresh snapshot. It does not. `resume_pane_with_permit` returns
`NoChange` **without sending anything** when the pane is already `Connected`, when the
owner does not match, when `reason.clear_hidden()` still yields `Some` (a NetworkDetach
bit survives), or when the snapshot exceeds the single-frame limit. `flush_deferred_output`
also discards a resume outright when `visible_state` went false, and
`resolve_pane_and_resume` sends nothing when the session or pane is gone.

And these are not exotic: `handle_set_visibility` queues a `VisibilityResume` for
*every* non-exited pane in the session on a visible edge without checking whether that
pane is actually detached-hidden, so resumes that will no-op are the normal case.

Concrete loss: channel saturated → resume for pane P queued → a later hide/show edge
resumes P directly (dedupe does not remove the already-queued stale entry) → window
switch issues `RequestPaneSnapshot(P)` → the reply is dropped here → at flush the
queued resume sees P already `Connected` and returns `NoChange` → **no snapshot ever
reaches the client** for that request. The tab stays stale until the next output. That
is the symptom this whole feature exists to remove.

**Fix (three reviewers converged on this one):** instead of dropping, `insert` the
`Chunk` immediately **before** the queued `VisibilityResume` for that pane. Flush order
becomes `Chunk(built at defer time)` → `Resume(fresh at flush time)`, so:
- the newest content still wins (the resume's fresher snapshot lands last), which is
  what task0005's change was trying to achieve, and
- the request is still answered even when the resume no-ops.

Then:
- Update the existing test `deferred_output_queue_drops_redundant_chunk_when_visibility_resume_already_queued_for_same_pane`
  — it currently pins the wrong behaviour and only checks queue length. Assert
  **delivery**, not length: with the resume no-opping (e.g. pane already `Connected`),
  the client still receives a snapshot.
- Correct the `defer_chunk` doc at `pane.rs:562-568` / `603-613`: drop the
  "a Resume's flush always builds a FRESH, current snapshot" claim.

## G2 (documentation/records only — no behaviour change)

1. **SPEC FR3 lead sentence** (`SPEC.md:55-58`): it says both exceptions "discard a
   snapshot reply that no longer reflects the pane's current state rather than the
   client's newest request". That is true of same-pane coalescing and **false** of
   distinct-pane eviction — eviction discards the evicted pane's *only, newest* queued
   reply, so that pane receives nothing. Restate the two exceptions with their actual,
   different justifications: coalescing drops a superseded reply (guarantee intact);
   eviction is an explicit carve-out that really does lose a delivery, justified only by
   FR4's memory bound plus client-driven recovery.
2. **`handlers.rs:2387-2394`** repeats the same faulty reasoning ("so this is not a
   dropped delivery under that guarantee") about eviction. Replace it to match (1).
3. **`connection.rs:2082-2086`** test doc claims a three-part revert experiment;
   `task0005.tests.yaml` AC-1 records that only the wait-loop match arm was reverted and
   that the strict same-moment ordering dimension could not be forced red. Make the doc
   say exactly what the record says.
4. **`connection.rs:2287-2301`**: the doc claims `output_flowed_before_snapshot` closed
   the "output may have been buffered before the request" weakness. It does not — the
   flag only proves *some* PANE_A output frame preceded the snapshot frame, and the
   pre-request saturation guarantees that trivially. Either weaken the doc to what the
   assertion proves, or tag payloads pre/post-request and strengthen the assertion.
   **Prefer weakening the doc** — it is the smaller, lower-risk change and this task is
   scope-limited.
5. **`task0005.tests.yaml:27-33`**: says "+9 new tests" but lists 3+4+1 = 8, and there
   are 8 in the diff. The "arithmetic doesn't reconcile / descriptive, not load-bearing"
   note is itself wrong: 2964 + 8 + 1 (ts7 flip) = 2973 matches the reported count
   exactly. Fix the count and delete the note.
