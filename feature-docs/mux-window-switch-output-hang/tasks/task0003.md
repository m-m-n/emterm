# task0003: Rework — make the bounded deferral lossless, unstarvable, and covered at the connection level

Synthesized by the orchestrator from the verify phase's `failed_items`
(batch-mode.md "Rework task synthesis", verify branch). Not produced by the planner.

The verify failures SC-1 and SC-2 are the same defects review round 2 recorded as

## What round 2 CONFIRMED as fixed (do not undo)

task0002's bounded, connection-owned `DeferredOutputQueue` genuinely closed four
round-1 defects. Preserve all of them:

- The unbounded `tokio::spawn` backlog is gone; `push` is the only growth path and
  enforces `MAX_DEFERRED_ITEMS`.
- `visible_state` is re-validated at flush time, so a stale resume cannot reconnect
  a hidden pane.
- The duplicated reserve → resolve → resume block is factored into
  `resolve_pane_and_resume`.
- `enqueue_pane_output_chunk` no longer calls `tokio::spawn`, so it no longer
  depends on an active tokio runtime.

Also preserve FR1/FR2: no blocking `send().await` / `reserve().await` on the
connection task. That is the original self-deadlock.

## Findings to resolve

### G1 — Overflow policy discards work that has no recovery path (high)
`reviews/round2.yaml`: `4999311c8becf7eb` (comprehensive, pane.rs:482),
`ff58ab6fd17542f4` (architecture, pane.rs:478, claude+codex, confidence 100),
`ac1d20218d320b08` (spec, pane.rs:478, claude+codex, confidence 100),
`1d648d947b4dea8b` (spec, handlers.rs:820).

`DeferredOutputQueue::push` drops the **newest** item once 8 mixed
`Chunk`/`VisibilityResume` items are queued. Two consequences:

- **Visibility resumes are lost permanently.** `handle_set_visibility`'s visible
  edge defers one item per candidate pane (every non-exited pane in the session).
  Past the cap the surplus is dropped with only a warn, and the pane stays
  `Detached { HiddenByVisibility }`. The `prev == visible` early-return at the top
  of `handle_set_visibility` means a repeated `SetVisibility(true)` is a no-op, so
  the pane never recovers until the user hides and re-shows the window. That is
  the "output stops flowing" symptom this feature exists to remove. The doc claim
  "a dropped snapshot/resume recovers via the next request" is true for `Chunk`
  and false for `VisibilityResume`.
- **Snapshot replies are lost.** The client's `request_pane_snapshot` is
  fire-and-forget with no retry (and NFR2 keeps the client out of scope), so a
  dropped reply leaves that tab blank/stale. Dropping the *newest* is also the
  worst choice: it discards the snapshot for the window the user just switched to
  while still delivering eight older ones.
- `push` also does not de-duplicate by pane id, so a toggling visibility can let
  one pane's resumes crowd out every other pane's.

### G2 — flush is structurally starved by the PTY reader thread (high)
`reviews/round2.yaml`: `7e47bd5fe31dc720` (comprehensive, handlers.rs:898),
`2aec511b92102c24` (performance, handlers.rs:898), plus `849329675807abbc`
(performance/codex, connection.rs:424).

`flush_deferred_output` retries with `try_send` / `try_reserve` only. The PTY
reader thread in `pty_spawn.rs` parks on `blocking_send` against the same channel.
tokio's bounded mpsc hands a freed permit directly to the head of its waiter
queue, so while any reader thread is parked, `try_send` observes zero capacity
essentially always — a systematic priority inversion, not an occasional race. The
failure mode is precisely this feature's target scenario: during sustained output
the deferred snapshot is never sent, the connection stays alive but the switched-to
window never repaints, and once the backlog reaches the cap the snapshots start
being dropped by G1. The drain arm's ordering makes it worse: it feeds and awaits
`framed.flush()` *before* calling `flush_deferred_output`, and the reader thread
refills the freed slots during that await.

Note for the implementer: task0002's doc claims this exposure "existed in
equivalent form even before task0001". That is wrong and should be corrected —
the original `send().await` enqueued the caller into the waiter queue at await
time, so it was FIFO-fair against the reader thread (it deadlocked for a different
reason).

### G3 — the mandatory connection-level FR2 scenario is still untested (high)
`reviews/round2.yaml`: `dda847f76f68fea7` (spec, connection.rs:463), plus
`9361b9b42c69fb92` (spec/codex, task0002.tests.yaml:117). Round 1 raised this too;
it is the only finding that has now survived two rounds untouched.

SPEC's Unit Test 1 and Integration Test 1 both require driving the connection's
`select!` loop. Every test added by task0001 and task0002 calls handlers directly
and invokes `flush_deferred_output` by hand, so the actual wiring is unverified:
that flush only runs inside the `if let Some(first) = chunk` block, that it sits
after the send-error `break`, and how it combines with the defensive flush at the
top of `route_message`.

### G4 — the AC-2 ordering test does not exercise the production flush (medium, but it invalidates G2's evidence)
`reviews/round2.yaml`: `6574d4221dcb5efe` (comprehensive, pane.rs:3891).

`enqueue_pane_output_chunk_full_channel_defers_without_blocking_preserves_fifo`
re-implements the flush loop inline rather than calling
`handlers::flush_deferred_output`, so the production `Chunk` arm (Full →
`requeue_front` + `break`, Closed → `clear()`) has zero coverage.

## Related medium findings (same mechanisms — resolve together where the design allows)

- pane.rs:366 (performance) — the cap counts items only; 8 × `MAX_SNAPSHOT_FRAME_PAYLOAD` is ~128 MiB/connection. Add a byte budget.
- handlers.rs:518 (performance) — a full queue still builds the whole snapshot (scrollback copy + encode) before discarding it; check enqueue-ability first.
- connection.rs:924 (comprehensive) — the defensive flush at the top of `route_message` can never make progress (capacity is only freed by the drain arm, which already flushes); either delete it or correct the doc.
- pane.rs:576 (architecture) — the queue/Sender pairing is unenforced across three modules; consider a `PaneOutputSink { tx, deferred }` owning both, with `flush` as an inherent method.
- handlers.rs:846 (architecture) — `resolve_pane_and_resume` collapses "session gone" and "pane gone" into `NoChange`, and both call sites discard the value, so the original early abort was lost.
- connection.rs:924 (architecture/codex) — deferred items are not scoped to an attach/session epoch; after `Attach` changes `active_session_id`, an old-session snapshot can be delivered against the new session.
- pane.rs:443 (spec) — the narrowed FIFO guarantee is not reflected in SPEC FR3, and the "equivalent form before task0001" justification is factually wrong.

## Acceptance Criteria

- **AC-1 (G1)**: No deferred visibility resume is ever silently lost. Regression test:
  with the channel full and more candidate panes than the cap, every pane that
  should resume is resumed once capacity frees — none is left
  `Detached { HiddenByVisibility }`. De-duplicate resumes by pane id.
- **AC-2 (G1)**: Snapshot replies are not silently dropped in favour of older ones.
  Either coalesce per pane (newest wins) or drop oldest — never drop the newest.
  Regression test: N > cap snapshot requests against a full channel, then drain;
  the most recent request for each pane is delivered.
- **AC-3 (G2)**: A deferred item cannot be starved indefinitely while the PTY reader
  thread is producing. Whatever mechanism is chosen (a `reserve_owned` future polled
  as a `select!` arm, a dedicated priority channel drained ahead of `pane_output_rx`,
  splicing deferred items into the drain batch, or a pre-reserved permit), the
  connection task must still never block. Regression test: with a producer thread
  holding the channel saturated the way `pty_spawn.rs` does, a deferred snapshot is
  delivered within a bounded time.
- **AC-4 (G3)**: A connection-level test drives `handle_connection`'s `select!` loop
  over a duplex stream: saturate `pane_output_tx`, send `RequestPaneSnapshot`, then
  send `PtyInput` for a different pane, and assert within `tokio::time::timeout` that
  the input is processed and output forwarding continues. `mux/daemon.rs` around
  line 3364 already spawns `handle_connection` in a test and is the model to copy.
- **AC-5 (G4)**: The AC-2/FIFO ordering tests call the production
  `flush_deferred_output` rather than an inline copy, and the Full-requeue and
  Closed-clear arms are covered.
- **AC-6**: Documentation matches what the code guarantees. Correct the false
  "equivalent form before task0001" claim, and either close the cross-thread
  ordering gap or state the narrowed guarantee in BOTH `pane.rs` and SPEC.md FR3
  (SPEC.md may be edited for this — it is the SSOT and currently asserts a
  guarantee the implementation does not provide).
- **AC-7**: The four round-1 fixes listed at the top of this document still hold,
  FR1/FR2 still hold, and
  `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib -- --test-threads=1`
  shows no failures beyond the 7 pre-existing `tabs::tests::*` ones (2945 passed /
  7 failed is the current baseline; `tabs.rs` and `app.rs` are untouched by this
  feature).
