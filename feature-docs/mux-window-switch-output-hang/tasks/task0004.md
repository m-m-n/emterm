# task0004: Rework — close the residual deadlock, starvation, and spec-contradiction findings from review round 3

Synthesized by the orchestrator from `reviews/round3.yaml` residual critical/high
findings. Round 3 exists because task0003's ~1400 lines had never been reviewed.

## What rounds 1-3 CONFIRMED as fixed (do not undo)

- The unbounded `tokio::spawn` deferral backlog (round 1) — replaced by a bounded,
  connection-owned queue.
- Stale visibility resumes reconnecting a hidden pane (round 1) — `visible_state` is
  re-validated at flush time.
- The `try_send`-only flush losing every permit race to the PTY reader thread
  (round 2) — replaced by a fair `reserve_owned()` reservation that joins tokio's
  FIFO waiter queue. **This is the right mechanism; G2 below fixes only where its
  `select!` arm sits, not the mechanism itself.**
- Drop-newest overflow discarding the snapshot the user just asked for (round 2) —
  replaced by per-pane coalescing + drop-oldest.
- The missing connection-level test (rounds 1-2) — one now exists; G4 fixes its
  composition, it does not need to be written from scratch.

Hard constraint, unchanged since task0001: **never reintroduce a blocking
`send().await` / `reserve().await` on the connection task.**

## G1 — EOF branch self-deadlock (high, `22251d51cc98261e`)

`pty_spawn.rs:624-629` holds the `output_target` std mutex guard across a
`blocking_send`:

```rust
{
    let target = output_target.lock().unwrap();
    if let PaneOutputTarget::Connected(ref tx) = *target {
        let _ = tx.blocking_send(PtyOutputChunk::pty_output(pane_id, Vec::new()));
    }
}
```

The data path in the same file (`pty_spawn.rs:784`) carries an explicit
`// IMPORTANT: release lock before blocking_send to avoid deadlock` comment. The EOF
path does not honour it.

task0003 made this reachable from the connection task: `apply_fair_permit_to_front_deferred_item`
→ `resolve_pane_and_resume` → `resume_pane_with_permit` takes the same
`pane.output_target.lock().unwrap()` (`pane.rs:1061`). Sequence: pane A saturates the
channel → pane B's shell exits and its reader thread parks in `blocking_send` while
holding B's `output_target` (B's `exited` flag is not set yet, so the
`.filter(|p| !p.exited)` guard still admits it) → a deferred visibility resume for B
wins a fair permit and blocks on `output_target.lock()` → the connection task stops,
so the drain arm never runs, so capacity never frees, so the reader never wakes.

`connection.rs:1027-1031`'s audit note asserts the opposite ("blocks that native OS
thread only, not this connection task"). That assertion is false for the EOF path.

**Note:** `pty_spawn.rs` was not in this feature's changed-file set, which is why the
fix is scoped in here explicitly rather than left to a follow-up.

## G2 — the fair reservation is still starvable by an earlier `select!` arm (high, `dd23cfc388062939`, `5c01ffb8d53dc9f7`)

Actual arm order in `handle_connection`:

```
biased;
msg = framed.next()                 // 1st
kick_result = kick_fut              // 2nd
pending_deferred_reserve            // 3rd  <- task0003's fair arm
chunk = pane_output_rx.recv()       // 4th  <- drain
```

task0003's in-code comment argues only that the reserve arm must precede the **drain**
arm. It does not account for `framed.next()` preceding both. Under `biased`, a client
that continuously supplies buffered messages keeps arm 1 ready every iteration, so
arms 3 and 4 are never polled: the reservation future never even registers as a
semaphore waiter, capacity is never freed, and both the deferred snapshot and all
queued PTY output starve indefinitely. SPEC FR2 requires output forwarding to
continue; FR3 (as task0003 rewrote it) forbids indefinite starvation.

This one needs a design decision, not a mechanical move. Arm 1's placement is
deliberate and documented ("prioritize client messages (PtyInput) over PTY output" —
input latency). Simply hoisting the reserve arm above it inverts that policy. State
which invariant wins and why in the code comment, whichever way you resolve it. A
quota / round-robin between the three concerns is also acceptable if you can keep
input latency acceptable.

## G3 — overflow eviction contradicts the FR3 MUST that task0003 itself wrote (high, `b4eee6700d643640`)

task0003 rewrote SPEC FR3 to say the snapshot chunk "**MUST** still be delivered to
the client, and **MUST NOT** be silently dropped or starved indefinitely" — the
narrowing applied to *ordering* only, and *delivery* was actually strengthened
(the old FR3 had no explicit delivery clause).

The same diff then made `defer_chunk` evict the oldest distinct-pane snapshot once
more than `MAX_DEFERRED_ITEMS` panes are pending, and pinned that behaviour with
`handle_request_pane_snapshot_drops_oldest_distinct_pane_never_the_newest`
(`pane.rs:4133-4157`) asserting the evicted panes "get nothing". The client's
`request_pane_snapshot` is fire-and-forget with no retry and NFR2 keeps the client out
of scope, so an evicted reply means that tab stays blank until the user switches to it
again. A daemon warn log is not client-visible delivery.

Pick one and make SPEC and code agree:
- **(a)** Add the carve-out to FR3 (bounded backlog may evict the oldest distinct-pane
  snapshot; recovery is the user's next switch to that pane), and keep the code.
- **(b)** Make the queue lossless: store `SnapshotRequest(PaneId)` instead of a built
  `Chunk` and build the snapshot at flush time. This satisfies FR3 literally while
  keeping FR4's bound, makes the delivered snapshot reflect flush-time state, and
  incidentally resolves the medium findings about per-connection bytes being unbounded
  (`8 × MAX_SNAPSHOT_FRAME_PAYLOAD`) and about building a multi-MiB snapshot only to
  discard it. **(b) is the recommended direction** — it collapses four findings at once
  — but (a) is acceptable if (b) turns out to be structurally harder than it looks.

## G4 — the connection-level test does not drive SPEC's Unit Test 1 (medium, but it is the evidence for G2/FR2)

`connection.rs:1800-1849`: the saturating pane is A, but both the
`RequestPaneSnapshot` and the `PtyInput` target pane B, so "input to a *different*
pane keeps flowing while pane A's snapshot is pending" is never exercised. The
assertions also only check captured input *after* both the output and the snapshot
were already observed, so a build that processes input only after snapshot delivery
still passes, and the output flag can be satisfied by traffic buffered during the
pre-request saturation window.

## Related medium findings (same mechanisms — resolve where the chosen design allows)

From `reviews/round3.yaml`:

- `pane.rs:560` — `defer_chunk`'s coalesce does `remove(pos)` + `push_back`, moving the
  item to the tail and breaking the FIFO invariant the queue's own doc declares. With
  `[Chunk(P), VisibilityResume(P)]` queued, a second request for P reorders them so the
  resume's fresh snapshot is overwritten by the older built chunk. Fix: assign in place.
- `handlers.rs:976` — `apply_fair_permit_to_front_deferred_item` has no direct test, and
  the `AnyPermit::Owned` arm is never executed by any test.
- `handlers.rs:976` (architecture, claude+codex) — the two executors disagree on stale
  handling: `flush_deferred_output` skips a stale resume and continues, the fair path
  drops the permit and returns, so K stale resumes cost K+1 reservation cycles.
- `pane.rs:515` / `handlers.rs:976` — queue type still lives in the session layer while
  every invariant lives in ipc; consider moving it to `mux/ipc/deferred.rs` and making
  `pop_front`/`requeue_front` private behind a single `apply_next`-style method.
- `handlers.rs:851` — `resolve_pane_and_resume` still collapses session-gone / pane-gone /
  exited / declined into `NoChange`, and all three call sites discard it. No log line on
  the silent paths, which matters because this project debugs via `emterm.log` only.
- `pane.rs:1056` — `AnyPermit` is not bound to the sender whose ownership is validated;
  a permit from channel A with sender B would send to A and then install `Connected(B)`.
- `pane.rs:604` — visibility-resume dedupe is a linear scan with no ceiling across
  distinct pane ids (O(n²) insertion, no lifecycle-based removal).
- `connection.rs:446` — one permit services exactly one item, so with resumes now
  cap-exempt, N panes need N drain cycles; and candidates are not filtered to panes that
  actually need resuming.

## Acceptance Criteria

- **AC-1 (G1)**: No code path holds `output_target` across a blocking send. Regression
  test: a pane whose reader thread is at EOF while the channel is saturated does not
  block a connection-task resume for that pane. Correct `connection.rs`'s audit note.
- **AC-2 (G2)**: A deferred item is serviced within a bounded number of loop iterations
  **even while client messages arrive continuously**. Regression test: saturate the
  output channel, stream client messages continuously, and assert the deferred snapshot
  is still delivered within a timeout. The chosen priority policy is stated in a comment
  at the `select!`.
- **AC-3 (G3)**: SPEC.md FR3 and the queue's behaviour agree. If (b): no snapshot reply
  is ever discarded — regression test with > `MAX_DEFERRED_ITEMS` distinct panes pending
  shows every pane eventually receives a snapshot. If (a): SPEC carries the carve-out and
  the existing eviction test's name/doc reflects that it encodes a spec-sanctioned policy.
- **AC-4 (G4)**: A connection-level test drives SPEC Unit Test 1 as written — snapshot
  requested for the **saturating** pane A, `PtyInput` sent for pane B, and the assertion
  proves B's input was processed *while* A's snapshot was still pending (not merely
  afterwards).
- **AC-5**: `defer_chunk`'s coalesce preserves queue position (FIFO invariant holds as
  documented), with a regression test over `[Chunk(P), VisibilityResume(P)]`.
- **AC-6**: `apply_fair_permit_to_front_deferred_item` has direct unit tests covering the
  empty-queue, front-`Chunk`, front-stale-`VisibilityResume`, and front-live-`VisibilityResume`
  cases, and the `AnyPermit::Owned` arm is executed by at least one test.
- **AC-7**: Everything listed under "What rounds 1-3 confirmed as fixed" still holds, FR1/FR2
  still hold, and `cargo test --lib -- --test-threads=1` shows no failures beyond the 7
  pre-existing `tabs::tests::*` ones (baseline: 2955 passed / 7 failed / 3 ignored).
