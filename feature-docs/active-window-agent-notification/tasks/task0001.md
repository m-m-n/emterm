# Task Plan: task0001 — Visible-pane notification setting and gate (Rust)

## Goal

The visible-pane suppression of agent status notifications becomes a persisted
setting: with `agent_notify_visible_pane` ON (default) a blocked/done
transition in a visible pane fires a desktop notification; with it OFF the
pre-feature suppression applies — end-to-end on the Rust side (persisted
schema → runtime settings → pure gate → app wiring).

## Design

Field contract: see IMPLEMENTATION.md Shared Components
(`agent_notify_visible_pane`) and decision D3 (mirror completeness) — this
task owns every Rust layer of that mirror.

### Gate change (`should_fire_agent_notification`)

The pure function gains one boolean input, `notify_visible_pane` (the value of
the new setting). Postcondition — it returns `true` exactly when ALL of:

1. the new state is a qualifying target (blocked or done; Working/Idle never
   qualify),
2. the pane is not visible OR `notify_visible_pane` is on (decision D2 —
   this is the only conjunct that changes),
3. the master toggle (`agent_status_notifications`) is on,
4. the global toggle (`notification_enabled`) is on,
5. the event-type toggle matching the new state (`agent_notify_on_done` /
   `agent_notify_on_blocked`) is on,
6. the caller-supplied rate-limit check passed.

Purity is preserved (NFR2): no side effects, no GUI types, the rate-limit
check stays a caller-supplied boolean.

### Wiring (`maybe_notify_agent_transition`)

Reads the new field from the runtime settings alongside the existing gate
inputs and forwards it. Everything else is unchanged:

- the rate limiter is still recorded only when the decision is fire — so a
  visible-pane fire consumes the pane's shared 30 s window exactly like a
  non-visible fire (FR5 / TS-3),
- the drain loop in `pump_all` stays unconditional, so the transition queue
  cannot grow while notifications are disabled (NFR4),
- Clear transitions (no new state) are still skipped before the gate is
  consulted (TS-2),
- `mark_seen` / badge behaviour and the rate-limit key derivation are not
  touched.

### Existing-test impact (deliberate)

Tests that assert "a visible pane never fires under default settings" now
assert the opposite (the default is ON). Update them to pin the new default,
and keep the legacy behaviour pinned by an explicit setting-OFF case. Do not
modify any tab-activity notification test (FR6).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS-4, FR2): `AppSettings` resolves the new field to `true` when
      the key is missing or null; an explicit `false` survives a
      serialize/deserialize round-trip; the crate default is `true`.
- [ ] AC-2 (FR2, NFR1): the GUI runtime settings mirror the same resolution —
      constructor default `true`, flat key `false` applied by the loader,
      null keeps the default.
- [ ] AC-3 (TS-1, FR1): gate truth table — with the setting ON, a blocked/done
      transition in a visible pane fires when all existing gates pass; with
      the setting OFF, a visible pane is suppressed; a non-visible pane's
      outcome is identical whether the setting is ON or OFF.
- [ ] AC-4 (TS-1, FR5): with the setting ON and the pane visible, each of —
      global toggle off, master toggle off, matching event-type toggle off,
      rate-limit exhausted — still suppresses the notification.
- [ ] AC-5 (TS-2, FR1): a Clear transition (no new state) never notifies even
      with the setting ON; Working/Idle transitions never notify.
- [ ] AC-6 (TS-3, FR5): a notification fired for a visible pane records that
      pane's shared rate-limit window — a second qualifying transition for
      the same pane within 30 s is suppressed.
- [ ] AC-7 (TS-7, TS-8, TS-9, FR6, NFR3, NFR4): non-regression — the CLI
      build check (`--no-default-features`) passes; the drain loop still
      drains unconditionally while notifications are disabled; no
      tab-activity notification test or gate is modified.
