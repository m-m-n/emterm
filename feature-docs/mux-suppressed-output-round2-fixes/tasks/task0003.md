# Task Plan: task0003 — Write-filter parity, pending exclusion and carried-over completions

## Goal

The scrollback write filter tracks the client's parse state across reads and
across removed screen-switch sequences, so it never holds or re-sends bytes the
client already closed or consumed as a designator. The replacement output
excludes only the chunk bytes that correspond to pending, and delivers
sequences that were carried over in pending and completed in the suppressed
chunk. Findings `ae48e7cd98084c19` (FR3), `b600645f1fa94686` (FR4),
`f8b600bcc0ed55da` (FR5) and `03ccd5c7702db8db` (FR6).

## Requirements

FR3, FR4, FR5, FR6, NFR3, NFR4, NFR5

## Scope

## Design

### 1. Awaiting-designator state (FR3)

- The filter keeps an "awaiting designator" flag, separate from pending.
- The flag is set when the fed stream ends right after `ESC (` or `ESC )`
  outside any held string. Inside a held OSC/DCS/APC these bytes are string
  data and set nothing.
- On the next feed, the first byte is consumed as the designator
  unconditionally, even when it is ESC, and the flag clears.
- Everything else stays as it is:
  - the pending retention rules (an incomplete OSC/DCS/APC, or a trailing
    lone ESC, held from its opening ESC);
  - the pending postcondition;
  - the 512 KiB cap and its strip-filtered flush;
  - the dims attribution rules.
- **Split invariance.** For any input split into consecutive feeds that stay
  below the cap, the concatenated emitted bytes and the final pending equal
  the single-feed result.

### 2. Cuts from removed screen switches (FR4)

- A **cut** is a fed-coordinate position where extraction removed a
  47/1047/1049 `h`/`l` sequence. The client saw that sequence's ESC; the
  filter did not.
- A new cut-aware feed takes the fed bytes, the dims and the ascending cut
  positions for this read. Positions may repeat, and may equal 0 or the fed
  length. At each cut the filter does what the client did at that ESC:
  - an in-progress OSC/DCS/APC, or a held lone ESC, is closed and emitted
    through the existing strip, exactly as an ESC-aborted string is today;
  - the awaiting-designator flag is cleared. The client consumed the
    switch's ESC as the designator (as-08), and extraction and the shadow
    parser stay unchanged.
  Processing then continues from ground with the next fed byte.
- The existing feed entry keeps its parameters and results and means "no cut
  in this read", so existing tests keep their call sites.
- **Postcondition.** After every feed, pending holds only the single
  incomplete string, or lone ESC, at the end of the fed stream after its
  last cut. It never holds a sequence closed by a cut, nor any byte after
  one.
- **Reader cut derivation** (non-fallback path only). The reader derives
  cuts from the span list extraction returned:
  - a cut at fed 0 when the first span starts after chunk offset 0;
  - a cut at every boundary between consecutive spans (fed offset = total
    length of the preceding spans);
  - a cut at the fed end when the last span ends before the chunk end.
  Empty spans are valid and yield repeated positions.
- The reader invokes the cut-aware feed also when the fed range is empty but
  a cut exists (for example a chunk that starts with a switch to the
  alternate screen), so pending and the flag are closed.
- The fallback path, where the scan result disagrees with the shadow parser,
  derives no cuts and keeps its current behavior.

### 3. Carried-over completion (FR6)

- **Definition.** A sequence whose opening ESC was held in pending when the
  feed started, and that reaches its terminator (BEL for OSC, or ST) within
  this feed before any cut.
- At most one exists per feed. It is recorded inside the existing boundary
  scan, with no extra pass (NFR3).
- The cut-aware feed reports it with its result for that call:
  - the complete sequence bytes, from its opening ESC through its
    terminator;
  - the fed offset just past its terminator.
- The reader keeps the report for the current read only, so a report from an
  earlier read can never be used.
- Nothing is reported when the carried sequence:
  - is aborted;
  - is closed by a cut;
  - stays incomplete;
  - or when the feed took the overflow flush.
- The reader maps the fed offset of the sequence's final byte to chunk
  coordinates through the span list (span start plus offset within the
  span), then adds one. The result is the completion's end position in chunk
  coordinates.
- The reader passes the report into the replacement request's carried-over
  completion field (IMPLEMENTATION.md Shared Components), and only for a
  suppressed chunk.

### 4. Overflow flush (TM-2)

- When the pending run exceeds the cap, the flush keeps its current behavior
  and memory bound.
- After it, pending is empty and no carried-over completion is reported.
- The awaiting-designator flag equals the client-parity state at the end of
  the flushed run. This is a single bounded pass that runs only on the
  overflow path.

### 5. Replacement assembly (FR5, FR6)

1. The request's D4 rule is unchanged. The pending run is the tail when
   pending is non-empty and the chunk ends inside a ring-written range.
2. **Excluded pieces (FR5).** When the pending run is the tail, the excluded
   region is the chunk-coordinate pieces that make up the last
   min(pending length, total fed length of this read) bytes of the
   concatenated ring-written ranges.
   - The region is computed piecewise and never includes the gaps
     (alternate-screen ranges and removed switch sequences) between ranges.
   - With FR4 in place, the region is always a suffix of the last range.
   - The single cut position and its helper are removed.
3. The client-parity scan walks the whole chunk and does not report an item
   that overlaps an excluded piece. When pieces are excluded it reports no
   tail, because pending is the tail. Items before and between the excluded
   pieces are reported, including those in alternate-screen ranges.
4. **Carried-over completion (FR6).** When the request carries one, the
   builder recovers its body through the delivery-side entry points
   (IMPLEMENTATION.md Shared Components) and classifies it.
   - It becomes an item only when it is a color query or a deliverable
     viewer launch. DCS/APC sequences and non-deliverable OSCs are dropped.
   - The item's bytes are the sequence verbatim; its key is its end position
     in chunk coordinates.
5. **Dedup.** A scan item with the same chunk end position is the same
   sequence, re-detected through the retained window, and is emitted once.
   Items with identical content but different end positions are distinct and
   are all emitted.
6. **Order.** Items are emitted by ascending chunk end position (raw-stream
   order), then the tail.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR3, TM-1, registry): `round2_ae48e7cd_awaiting_designator_is_carried_across_feeds`
      covers `ESC ( ESC ]11;?tail` at two levels:
      - fed in two calls split right after `ESC (`, it emits the same bytes
        and leaves the same (empty) pending as one call;
      - through the reader (split input, second read suppressed, then the
        replacement output, then BEL), it produces no color-query response.
      The same test body fails on the pre-fix code. A companion test checks
      every split position of inputs mixing designator chains, strings, lone
      ESCs and UTF-8, and gets identical concatenated output and final
      pending.
- [ ] AC-2 (FR4, TM-1, registry): `round2_b600645f_removed_screen_switch_closes_the_pending_string`:
      on the main screen, a suppressed chunk holding `ESC ]11;?`,
      `ESC [?47h`, `ESC [?47l` and one space, with BEL sent after the
      replacement output, produces no response. After the feed, pending holds
      no closed OSC. The 1047 and 1049 forms behave the same. The same test
      body fails on the pre-fix code. Further tests cover three more cases:
      - a held lone ESC before a removed switch is closed;
      - the awaiting-designator flag clears at a cut;
      - an empty fed range with a cut still closes pending.
- [ ] AC-3 (FR5, registry): `round2_f8b600bc_pending_exclusion_keeps_alt_screen_queries`
      calls the builder with ring-written ranges whose pending suffix spans
      two ranges around an alternate-screen range holding `ESC [6n`. The CSI
      6n is delivered once, and nothing inside the excluded pieces is
      reported. The same test body fails on the pre-fix code, where the
      single cut drops the query. At reader level (TS-5):

- [ ] AC-4 (FR6, TM-1, registry): `round2_03ccd5c7_carried_over_viewer_launch_is_delivered_once`:
      an OSC 777 emterm markdown longer than 256 bytes is split across reads,
      and the completing chunk is suppressed. The launch is delivered exactly
      once after the snapshot. The same test body fails on the pre-fix code
      (zero deliveries). Further tests cover:
      - a short launch whose start is in the window, split the same way, is
        delivered once, never twice (dedup, TM-1);
      - two identical-content launches are delivered twice;
      - order relative to alternate-range queries and launches follows the
        raw stream;
      - a carried-over color query that completes in the suppressed chunk is
        answered once;
      - a carried launch that completes in the main range of a chunk ending
        on the alternate screen is delivered once;
      - consecutive suppressed chunks deliver once after each snapshot;
      - a run flushed by the cap is never reported.
- [ ] AC-5 (SPEC AC-2): The FR3, FR4, FR5 and FR6 cases above are each run
      with varied split positions. In each run, a term_core client fed the
      snapshot (real assembly output via `reset_and_replay_segments`,
      responses discarded), then the replacement output, then the following
      chunks, matches a reference client fed the raw stream once. Screen,
      cursor, response bytes and displayed characters are compared. No
      continuation byte or U+FFFD is displayed.
- [ ] AC-6 (TM-1, TM-2, NFR3): Adversarial inputs finish within the test time
      budget and do not panic:
      - long designator chains;
      - repeated switch sequences with incomplete introducers;
      - carried sequences near the cap;
      - inputs forcing the overflow flush.
      After an overflow flush, pending is empty, no completion is reported,
      and the awaiting flag matches the client. An empty replacement is
      never sent. The non-suppressed reader path gains no pass over the
      chunk: added work there is limited to state recorded inside the

## Test Notes

- Write-filter unit tests (AC-1 split invariance, AC-2 cut rules, AC-6
  overflow) sit next to the existing feed tests in `pty_spawn/tests.rs`.
- Reader-level tests reuse the existing scripted-reader harness and the
  output-capture pause hooks, which place a snapshot between a chunk's
  capture step and its forward decision. They also reuse the reference
  comparison helpers already used by the visible-reattach tests.
- Registry tests go through the existing four-parameter builder or the
  reader harness, so the same body can be run against the pre-fix sources.
  The AC-3 registry test isolates FR5 by giving the builder a pending whose
  suffix spans two ranges, a shape the pre-fix filter produced.
- To place a sequence's start before the retained window (AC-4), make the
  carried-over run longer than 256 bytes before the suppressed read.
- Known nondeterministic existing tests (e.g. `tabs` replay tests in a
  parallel run) are re-run single-threaded before being treated as failures.
