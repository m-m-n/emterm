## Design

Line numbers refer to the base revision, before any comment line is added. Each
replacement is made in place: the list entry keeps its position, indentation and list
marker; only the test path string changes.

The pairing follows the capability case — body markup present in a successful list /
absent from a successful list / fetch failure — not the true/false words, because the
predicate was renamed with inverted polarity (`body_markup_confirmed` →
`body_markup_absence_confirmed`). All four current names are defined in
`src-tauri/src/callbacks/tests.rs` at the base revision (SPEC A-1); that file is read-only
for this task.

### Supersede notes (FR3)

Target blocks: summary AC-2, summary AC-5, body AC-4. No other AC block gets a note.

Each note:

- is one or more new comment-only lines inside the target AC's block — after the AC key
  line and before the next sibling AC key — indented to the block's child level. No
  existing line is extended with a trailing comment, so existing lines stay
  byte-identical (FR4).
- states that this AC's fetch-failure expectation — when `get_capabilities()` fails, the
  title/body are left unescaped — is superseded by
  `feature-docs/notification-markup-fail-closed/SPEC.md` FR1/FR3 (fail-closed: escape on
  fetch failure).
- states that the listed current fetch-failure test pins the new behavior.
- is scoped to the fetch-failure expectation only: the block's other entries (for
  example summary AC-2's unconfirmed-capability-list entries) still hold as written.
- is written in English, like the rest of the records.

`red_confirmed` and `red_reason` stay as recorded. `red_reason` is the pre-implementation
observation; body AC-4's `red_reason` keeps its mentions of the old
`body_markup_confirmed_*` names (NFR2).

### Preservation invariants (FR4, NFR2)

- The only textual differences from the base revision are the seven replaced path strings
  and the added comment-only lines. All other lines — keys, values, list order, the inline
  comments on lines 2–3 of the body record, blank lines, the trailing newline — are
  byte-identical.
- After parsing, each record equals its base-revision data with the replaced path strings
  substituted: `task_id`, `baseline_failures`, `final_failures`, every `red_confirmed` /
  `red_reason`, and every list order are unchanged.
- The records are edited as text. A parse-and-rewrite round trip is not used: it drops
  YAML comments and can reformat untouched lines.

### References kept as history

Line-number references elsewhere (for example `line: 14` in
`feature-docs/notification-markup-fail-closed/reviews/round1.yaml`) no longer match once
comment lines are added. They are historical records and are not updated (NFR2).
