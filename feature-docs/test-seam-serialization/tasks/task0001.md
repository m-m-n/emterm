### Part B — Structural send-site check (FR6)

Flow of `every_progress_and_result_send_site_routes_through_the_wake_helpers`
after the change:

1. Read the module's own source file (same source location as today).
2. Locate the start of the `mod tests` item: its declaration line together
   with the `#[cfg(test)]` attribute directly above it. Use the first such
   declaration, anchored to the item rather than to free text, so a prose
   mention of `mod tests` in a doc comment does not count. If no such
   declaration is found, the check fails with a message saying the
   boundary is missing.
3. The scanned region is everything before that point: all production items
   plus the `#[cfg(test)] impl SftpService` seam block.
4. Search the region for the two forbidden shapes (a direct send call on
   the progress sender, and one on the result sender). Either found → fail
   with a message naming the helper to use instead.

Steps 2–4 form a detection routine that takes source text as input and
returns what it found. Both the real check (fed the real file) and the
red-case test (fed synthetic text) call it. The routine lives inside
`mod tests`, the excluded region, and keeps assembling the forbidden shapes
from parts, so the file never spells a forbidden shape verbatim.

Red-case test (new, in `mod tests`), fed synthetic module texts:

- (i) a `#[cfg(test)] impl` block placed before `mod tests` that contains a
  bare progress send → the routine reports a progress violation;
- (ii) the same with a bare result send → the routine reports a result
  violation;
- (iii) the same bare send placed only inside a `mod tests` body →
  the routine reports no violation, which pins the exclusion boundary;
- (iv) text with no `mod tests` declaration → the routine reports a missing
  boundary.

Update the check's explanatory comment. The scanned region is production
source plus test seams. Only the `mod tests` body is excluded, because it
spells the forbidden shapes as data. The job-queue send stays a separate,
intentionally untouched channel, as today.

### Part C — Restart-flag audit (FR7) and preservation (FR1–FR3)

- **Touch set** (FR1's definition):
  - direct references to `RESTART_REQUIRED`;
  - `restart_pending` and `restart_required`;
  - `App::frame_work_pending`, `next_toast_deadline`, `pump_toasts` and
    `pump_restart_toast`;
  - every function whose call chain reaches one of the above. Expand
    callers repeatedly until no new function appears.

  The raise path (`note_spawn_failure` and its callers such as
  `spawn_self`) is included too. For a hit reachable only through the
  raise path, record whether the test binary can actually raise the flag
  there. It raises only when a self-exe baseline is recorded, and
  `self_binary_missing_false_without_baseline` pins that the test process
  records none.
- **Search scope**: all test code under `src-tauri/src` (`#[cfg(test)]`
  modules and `app/tests/`), excluding `self_exec.rs` and
  `app/tests/timing.rs`, which already comply.
- **Disposition per hit**: a test that does not already hold a
  `RestartFlagTestGuard` from before its first touch until after its last
  observation gets one for that span. Nothing else in the test changes.
- **Zero hits**: no code change for Part C.
- **Record**: the touch set, the search method and scope, every hit, and
  its disposition go into the task's test record and the implementer
  report.
- **Preservation**: the guard, its lock, its doc comment in `self_exec.rs`,
  and the nine guards in `app/tests/timing.rs` are not modified.

## Test Notes

- **TDD order for Part B/A**: widen the scan region first. The real check
  then fails against the current bare seams; that failure is the SPEC TS-2
  red, observed on the actual file (record it for AC-4). Then reroute the
  seams (Part A) and the check turns green.
- **AC-1**: unit test in `service.rs` `mod tests`. Construct a service,
  call each seam once, and assert the matching receiver yields exactly one
  event with the FR4 field values and then nothing more. The `timing.rs`
  callers need no change.
- **AC-3/AC-4**: unit tests over the detection routine. Build the synthetic
  inputs from parts so they do not add a verbatim forbidden shape to the
  file. They sit inside `mod tests` anyway, but building them from parts
  keeps them harmless if the boundary ever regresses.
- **AC-5**: this is an audit, not a unit test. Its evidence is the recorded
  search result; any guard added to a found test is exercised by that
  test's own run under the parallel `--lib` command.
- **AC-6**: run the parallel `--lib` command above. Known unrelated flakes
  (e.g. the `tabs.rs` replay test, `test/README.md:40`) are rerun and
  recorded, never silently excluded.
- **Formatting**: check each modified file individually (e.g.
  `rustfmt --check --edition 2024 src-tauri/src/sftp/service.rs`). Never
  run crate-wide `cargo fmt`.
