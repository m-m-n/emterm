# Task Plan: task0001 — Store only length-valid capacity bodies for reconnect resend

## Goal

The mux bridge retains a ClientScrollbackCapacity frame body for its
reconnect resend only when the payload is a valid capacity payload (exactly
4 bytes), so a length-invalid report no longer displaces the last valid one,
while every capacity frame is still forwarded to the daemon unchanged. A
regression test proves that the sequence valid report, length-invalid
report, upgrade-driven reconnect resends the valid value.

## Requirements

FR1, FR2, FR3, NFR1, NFR2

## Scope

### Files to Create

None.

### Files to Modify

- `src-tauri/src/mux/bridge/mod.rs` — the capacity capture helper returns a body for storage only for a length-valid capacity payload; its doc comment states that condition; the protocol crate's capacity payload type is imported for the check
- `src-tauri/src/mux/bridge/tests.rs` — unit tests for the helper's length rule, a forwarding-loop test for the no-prior-valid case, and a Unix integration test for valid report, length-invalid report, reconnect

## Design

### Component: capacity capture helper (capture_if_capacity, bridge module)

Responsibility: decide whether a frame read from the bridge's standard input
replaces the retained reconnect capacity.

Contract:

- Input: a parsed mux message and its serialized frame body.
- Postcondition: returns a copy of the frame body if and only if (a) the
  message type is ClientScrollbackCapacity and (b) the message payload is
  accepted by the protocol crate's existing capacity payload decoder, which
  accepts exactly 4 bytes. Returns nothing in every other case: any other
  message type, or a capacity message whose payload length is not 4.
- The value carried by an accepted payload is never inspected: any 4-byte
  payload, including value 0, is accepted as is, with no clamping or
  substitution (FR3).
- Validity is decided by the protocol crate's decoder — the same rule the
  daemon applies — rather than by a length constant maintained separately in
  the bridge.

Unchanged collaborators (read-only for this task):

- The stdin-to-daemon forwarding path in the bridge's forward module keeps
  calling the helper and keeps writing every frame, including length-invalid
  capacity frames, to the daemon socket byte-identically (FR2). When the
  helper returns nothing, the retained value is left as it was.
- The reconnect path (reconnect_and_reattach) keeps resending whatever body
  is retained: capacity first, then Attach.

Flow, per frame on the stdin-to-daemon path:

1. The bridge parses a mux message from standard input and serializes its
   frame body.
2. The capacity capture helper evaluates the message. Valid capacity: the
   retained capacity is replaced by this body. Otherwise: the retained
   capacity is unchanged (the previous valid body, or empty if no valid
   report has arrived yet).
3. The frame body is forwarded to the daemon socket unchanged, whatever the
   outcome of step 2.
4. On an upgrade-driven reconnect, the retained body (the last valid capacity
   report) is resent first after the reconnect handshake.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR3, TM-1): The capacity capture helper returns nothing for a ClientScrollbackCapacity message whose payload is 0, 3 or 5 bytes long, and returns a body identical to the frame body for a 4-byte payload of value 0 and for a 4-byte payload of a non-zero value.
- [ ] AC-2 (FR1): The capacity capture helper still returns nothing for non-capacity messages (a PTY input message and an Attach request).
- [ ] AC-3 (FR1): When the bridge's forwarding loop receives a length-invalid capacity report with no prior valid report, the retained capacity is still empty after the loop ends.
- [ ] AC-4 (FR1, FR2): When the forwarding loop receives a valid capacity report (5 lines) followed by a length-invalid capacity report, both frames reach the daemon side byte-identical to what was sent, in that order, and the retained capacity equals the valid report's frame body.
- [ ] AC-5 (FR1, TM-1): Continuing from AC-4's retained state on Unix, a reconnect against a stand-in daemon resends, as the first frame after the reconnect handshake, a ClientScrollbackCapacity frame whose payload decodes through the protocol crate's capacity payload decoder to 5 lines — the length-invalid report never displaces the last valid one.
- [ ] AC-6 (NFR1, NFR2): The existing bridge tests (capture_if_capacity_captures_capacity_and_only_capacity, forward_loop_forwards_and_captures_capacity_frame_unchanged, forward_loop_capacity_capture_replaces_and_is_unaffected_by_other_messages, and every reconnect_and_reattach_* test) pass unchanged; the bridge test module passes; the CLI-only (no default features) cargo check succeeds; no source file outside the two files in Scope is modified.

## Test Notes

- AC-1, AC-2: synchronous unit tests on the helper, alongside the existing
  capture_if_capacity test. Length-invalid capacity messages are built
  directly with a raw payload of the chosen length; the frame body is
  produced the same way the existing tests produce it. AC-2 is already
  covered by the existing helper test and stays green.
- AC-3, AC-4: async tests on the forwarding loop with in-memory duplex
  streams, following the existing capacity forwarding tests. The
  length-invalid frame is fed through the bridge's stdin parser (the APC or
  EMUX plaintext encoding of a message carrying a raw payload of the wrong
  length) so the real parse, capture and forward path is exercised. The
  daemon side reads exactly the number of frames sent; the loop ends at
  stdin EOF.
- AC-5: Unix-only, because the reconnect function and the stand-in daemon
  helpers exist only on Unix. Reuse the existing stand-in daemon helpers
  (accept and handshake, blocking frame read, no-more-frames assertion). Use
  the retained capacity produced by AC-4's forwarding-loop run — not a
  hand-set value — so one test covers the whole reproduction sequence (SPEC
  AC-2, TS-2). With no Attach retained, the capacity frame is the only frame
  expected after the handshake. AC-4 and AC-5 may be one test.
- The stand-in daemon runs on a plain thread and listens on a socket under a
  temporary directory, as in the existing reconnect tests; each new test uses
  a distinct socket file name.
- The project's test command runs this crate with a single test thread; the
  new tests must not depend on parallel execution or shared global state.
- AC-6: run the bridge test module and the CLI-only check (commands in
  VERIFICATION.md).

## Out of Scope

- Changes to the bridge's forward module, reconnect_and_reattach, the daemon,
  or the mux_ipc protocol crate (NFR1).
- Dropping, rewriting or logging length-invalid capacity frames on the
  forwarding path; they are still forwarded unchanged (FR2).
- Interpreting, clamping or range-checking the capacity value (FR3).
- Sender-side changes: the in-tree sender already sends exactly 4 bytes.
