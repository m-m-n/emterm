## Design

### Edit 1 — Test Scenarios table name cells (FR2)

The table has one row per target-document TS ID (`TS-1` … `TS-6`, then `TS-M1`).
Each `TS-1` … `TS-6` row's Scenario cell opens with one backticked identifier —
a name that was never written into `tests.rs` — followed by an em-dash
description. Replace that identifier with the canonical name(s) of that scenario
(IMPLEMENTATION.md, "Canonical test-name assignment"):

| Target-document TS | Names the row carries |
|---|---|
| TS-1, TS-2, TS-3, TS-6 | the one canonical name of that scenario |
| TS-4 | all 18 canonical names |
| TS-5 | all 3 canonical names |

**Row set stays as it is** — one row per TS ID, in the existing order, with the
existing columns (NFR3). A row carrying several names enumerates them inside the
Scenario cell, each in its own backtick span, one per rendered line (the
repository already uses HTML line breaks inside table cells for this). The
em-dash description and the Expected Result cell of each row keep their existing
wording, which already reads as a collective statement for the scenario. The
`TS-M1` row is untouched.

The TS-4 entry for `sanity_the_fake_callee_pattern_matches_a_real_unquoted_call`
carries the role note required by IMPLEMENTATION.md's scaffold role-note
contract, in this document's English (NFR3).

### Edit 2 — the count claim (FR2)

The "Test Verification" Expected line currently promises that "the six new
`window_host::tests` entries below appear in the run". Six is wrong: the
implementation added 25. State the real count, keep the rest of the line's
meaning (exit code 0; no pre-existing test changes its result), and leave the
Coverage-target and Known-caveat bullets alone. The string "six new" must not
survive anywhere in the document.

### Edit 3 — the AC-1 verification cell (FR2)

The Success Criteria table's AC-1 row tells the reader to "confirm exit 0 and
that TS-1 … TS-6 appear in the run". TS IDs never appear in `cargo test` output.
Rewrite the cell so that what is confirmed in the run is the **named test
functions** listed in the Test Scenarios table. The AC-1 criterion text itself,
every other row of the table, and the Functional Requirements Coverage table are
unchanged.

### Edit 4 — the Code Quality naming inspection item (FR3)

Replace the item that currently demands the test names "match the TS names in
this document character for character" — unsatisfiable, and one-way in the wrong
direction — with an item stating a two-way (bijection) check that names
`src-tauri/src/window_host/tests.rs` explicitly as the side of truth. The revised
item states all of:

1. every test name listed in this document's Test Scenarios table exists
   verbatim as a `fn <name>()` in `src-tauri/src/window_host/tests.rs`;
2. every test function that feature added to that file appears in exactly one TS
   row of the table — no added test undocumented, no documented name absent from
   the file. "Added" is the set defined by IMPLEMENTATION.md decision D2: the
   functions carrying a test attribute between the `AC-3/TS-1` section marker
   and end of file (25 of them); the fixture/helper functions in that span carry
   no test attribute and are not part of it;
3. each of those names follows the repository's `<subject>_<scenario>_<expected>`
   convention — the target document's own NFR3, per `test/README.md` "Test
   Naming Conventions".

The item also states the direction of authority: the file is normative and the
document follows it. The surrounding inspection items (runtime types, manifests,
scan scope, closed name set) and the Format / Static-analysis bullets stay as
they are. The string "character for character" must not survive in the document.

wrapped across lines inside the identifier (NFR2 forbids it) and that the table
cells still parse as a single table; and confirm the stale-name check is done
set-wise (decision D6) rather than by re-typing the names being removed.
