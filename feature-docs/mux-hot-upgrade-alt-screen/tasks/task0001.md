# Task Plan: task0001 — Private per-user group exemption in the path-writability check

## Goal

A daemon started from a umask 002 dev build accepts its own 0o775
binary/parent paths in the NFR3 path-writability check when — and only
when — the path's owning group is the owner's private per-user group,
keeping every other rejection (including world-write) exactly as today,
fail-closed.

## Requirements

FR1, FR2, NFR1, NFR2

## Scope

### Files to Create

(none)

### Files to Modify

- `src-tauri/src/mux/identity.rs` — the group-write branch of the
  entry-validation rule table (`validate_entry`, around line 455), the
  entry-attribute capture, the new private per-user-group predicate, and
  its inline `#[cfg(test)]` unit tests.

## Design

Current behavior: any entry whose mode has the group-write or world-write
bit set is refused. New rule table for the write-bits step, evaluated for
BOTH roles (upgrade candidate and its parent directory), in this order:

1. World-write bit set → refuse unconditionally (FR2), regardless of any
   group facts.
2. Group-write bit set → refuse UNLESS the private per-user-group
   predicate (below) accepts (FR1).
3. Neither bit set → this step accepts (unchanged).

Private per-user-group predicate (FR1): given the entry's owning group and
the entry's owner, accept only when ALL three conditions hold:

- (a) the group's member list contains no name other than the owner's user
  name (an empty member list satisfies this — primary membership is not
  listed in the member list);
- (b) the owner's primary group id equals the entry's owning group id;
- (c) the group's name equals the owner's user name.

Fail-closed (NFR2): if any fact needed by (a)–(c) cannot be obtained
(lookup failure, missing record), the predicate rejects. Refusal reasons
keep the existing convention: human-readable, naming the first failed rule.
The threat model is unchanged: the daemon `execve()`s the accepted path;
parent directories stay in scope; the entry-kind and owner rules are
untouched.

Structure — extend the file's existing testability pattern (pure decision
over captured attributes, capture separated out):

- `EntryAttributes` additionally captures the entry's owning group id, via
  the same non-following stat that already provides uid and mode.
- A pure predicate decides over captured "identity facts" (group name,
  group member names, owner user name, owner primary group id), so every
  FR1 branch is table-testable without privileged fixtures or real
  users/groups — mirroring how `validate_candidate` is already tested.
- A capture wrapper obtains those facts with exactly one group-by-id
  lookup (`getgrgid`) and one user-by-id lookup (`getpwuid`) per entry
  decision (NFR1); it never enumerates the passwd database (no
  `getpwent`). The lookups must be safe under concurrent use from daemon
  threads (reentrant lookup forms or an equivalent guarantee). A capture
  failure yields "facts unavailable", which the predicate treats as reject
  (NFR2).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A 0o775 entry whose owning group satisfies all three FR1
      conditions is accepted, in both the candidate role and the
      parent-directory role.
- [ ] AC-2: Each of the following is refused, each pinned by its own test:
      a group with an extra name in its member list; a group whose id
      differs from the owner's primary group id (e.g. gid 100 "users" as
      primary); a group whose name differs from the owner's user name;
      unavailable identity facts (failed lookup); any entry with the
      world-write bit set (regardless of group facts).
- [ ] AC-3: Every pre-existing accept/reject behavior is preserved:
      owner-writable-only modes still accept; wrong entry kind, foreign
      owner, and world-write rows still refuse, with reasons naming the
      first failed rule.
- [ ] AC-4: The fact-capture path performs at most one group lookup and
      one user lookup per entry decision and contains no passwd-database
      enumeration; the pure predicate is fully covered by table tests
      (every FR1/FR2 branch appears in the inline test module).

## Test Notes

- All tests are unit tests inline in `identity.rs` (`#[cfg(test)]`),
  following the file's existing table-test style: FR1/FR2 branches test
  the pure predicate with synthesized identity facts — no real users,
  groups, or privileged fixtures.
- The system-lookup capture wrapper is deliberately thin; its correctness
  is carried by the pure-predicate tests plus the manual AC-2 scenario in
  VERIFICATION.md, which exercises the real lookups on a umask 002
  machine.
- Keep the Unix gating intact: this is Unix-only surface, and the CLI-only
  (`--no-default-features`) build must keep compiling.
