## Design

Follow the harness's established structure (its module header documents
it): isolated `XDG_RUNTIME_DIR` per scenario, real daemon child process,
raw mux wire-protocol frame helpers, bounded waits that name the stuck
step, RAII cleanup guard.

Scenario flow:

1. Spawn the daemon, connect, create a window/pane, and prove the shell
   round trip (existing helpers).
2. Print a distinctive PRE-ALT marker through the shell, so it lands in
   the scrollback / main screen.
3. Drive the pane onto the alternate screen: have the shell emit the
   alternate-screen-enter control sequence followed by a distinctive ALT
   marker (a shell print of the raw escape bytes is sufficient — the
   daemon's shadow parser tracks pane output regardless of what any
   client renders); wait until the pane output confirms it.
4. Trigger the hot-upgrade over the wire and wait for the daemon to come
   back (existing helpers).
5. Reconnect and reattach; capture the reattach snapshot.
6. Assert the post-restore observable contract: the snapshot's visible
   screen content reflects the alternate screen (the alt-enter sequence /
   ALT marker present as current screen content), and the PRE-ALT marker
   does not surface as the visible screen where the TUI's screen should
   be.

Expected-to-fail status (IMPLEMENTATION.md D2): in this task's own
worktree the daemon does not yet carry alt state, so the new scenario
fails at its named assertion or bounded wait. Do not weaken the scenario
to pass locally; document the status where the file header already
documents the same convention for its original scenarios.

Feasibility fallback (IMPLEMENTATION.md D2, SPEC TS4, REQUIREMENTS.md
14.2): if, while building it, the wire-visible surface turns out unable
to express the step-6 assertion at all (not merely "it fails because the
behavior has not landed"), stop forcing it: report the concrete blocker
as a plan deviation, and record the fallback (task0002's unit-level
fixation + manual AC-2/AC-5) in the harness header and `test/README.md`.
