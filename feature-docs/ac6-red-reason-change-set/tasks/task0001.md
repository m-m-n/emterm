## Design

### Target of the edit

The record's `acceptance_tests` mapping holds seven entries, AC-1 through AC-7.
Only the AC-6 entry's `red_reason` scalar is touched, and within it only the
closing clause — the one asserting that a `git status --porcelain` taken over
the whole change set lists just that one YAML file. Everything before that
clause stays as written.

### What the replacement clause must say

Three assertions, and nothing beyond them (IMPLEMENTATION.md D-2):

1. The change set consists of YAML documentation records only, naming both
   records explicitly: the record that the ac7 task edited
   (`test-docs/stale-test-name-refs/task0001.tests.yaml`, identifiable from the
   record's own AC-1 entry) and that task's own per-task test record
   (`test-docs/ac7-red-confirmed-unobserved/task0001.tests.yaml`, the file
   being edited here).
2. The change set contains no Rust file and no TypeScript file.
3. The workflow-generated documents under
   `feature-docs/ac7-red-confirmed-unobserved/**`, together with the
   `test-docs/` record tree, are an expected carve-out of the change set and do
   not affect assertion 2.

### What the replacement clause must not say

- No file count, in any form — not "one file", not "two files", not an
  exhaustive enumeration presented as the complete list.
- No claim that any particular file is the sole entry of `git status --porcelain`
  or of any other change-set listing.
- No claim whose re-checking would require the working-tree state that existed
  while this edit was made (IMPLEMENTATION.md convention C-4). Every assertion
  must be re-checkable from the record plus the ac7 task's own commit.

### What must survive the edit unchanged

Within the AC-6 entry: `red_confirmed: false`, the "Invariant guard, not a
red->green criterion" framing, the clean pre-state observation, the two-hunk
`git diff` observation, and the list of untouched keys (header comment,
`task_id`, `baseline_failures`, `final_failures`, record AC-1 through record
AC-6).

Elsewhere in the file: acceptance entries AC-1 through AC-5 and AC-7, the
`task_id`, `baseline_failures` and `final_failures` values, the trailing
`notes` block, and the top-level key order — all byte-identical.

### Formatting

The `red_reason` keeps its `>-` folded block-scalar indicator, the file's
2-space indentation, and the file's existing line-wrap width
(IMPLEMENTATION.md convention C-5). The resulting diff reads as a same-style
revision, not a reformat.

### Blocking precondition

If `test-docs/ac7-red-confirmed-unobserved/task0001.tests.yaml` does not exist
on the branch this task is implemented from, stop and report it as a plan
deviation. Do not create the record, and do not redirect the edit to another
path — either action would fabricate evidence for a task that did not run here
(IMPLEMENTATION.md Risk Assessment, first row).

## Test Notes

All assertions run as ad-hoc commands, not as committed test files
(IMPLEMENTATION.md D-3). Record the commands and their observed output in the
implement phase's own test record under
`test-docs/ac6-red-reason-change-set/`.

- **Red-then-green criteria**: AC-2 and AC-4 have an observable pre-state. Run
  them against the record before editing — AC-2's occurrence count is 1 and
  AC-4's carve-out mention count is 0 — then again after. These are the two
  criteria that demonstrate the fix.
- **Invariant guards (no observable red)**: AC-1, AC-5, AC-6, AC-7, AC-8 and
  AC-9 hold before the edit as well; they guard against collateral damage.
  Record them as invariant guards with `red_confirmed: false` and say so
  plainly rather than inventing a red state.
- **Parse assertions** (AC-1, AC-5, AC-6): use a YAML safe-load and compare
  loaded structures, not raw text — that is what makes them insensitive to
  wrapping.
- **Raw-text assertions** (AC-7): read the file as text; a YAML load discards
  the block-scalar indicator and key order, so it cannot verify NFR2.
- **AC-6's comparison** takes the pre-edit version from git history rather than
  from a saved copy, so the check stays reproducible after the fact.
- **AC-8 is a human-judgment check**: read the rewritten clause and confirm
  each assertion names a durable source (the record, the ac7 commit). It has
  no mechanical form; state the judgment and its basis in the test record.
- **Edge case worth covering**: a rewrite that removes the offending clause but
  substitutes an exhaustive "the change set is exactly these two files"
  enumeration still fails AC-2, because an exhaustive enumeration is a count
  claim. Check for that shape explicitly.
