# Task Plan: task0001 — Code-owned rate-limit key derivation for mux panes

## Goal

A mux pane's agent-notification rate-limit key becomes a pure function of its
connection scope and wire pane id, the derivation stops accepting the
daemon-learned identifier map entirely, and the doc comments and app-layer tests
are corrected to state and pin that contract.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR7, FR8, FR9, FR10, NFR2, NFR4

## Scope

### Files to Create

None — every file this task touches already exists.

### Files to Modify

- `src-tauri/src/app/agent_status.rs` — the derivation itself, its doc comment, and the two call sites in this file (the closed-mux-pane loop and the transition-drain loop)
- `src-tauri/src/app/tab_lifecycle.rs` — the close-tab call site and the ordering comment above it
- `src-tauri/src/app/mod.rs` — the reaped-exited-tab call site, the ordering comment above it, and the rate-limiter field's doc comment
- `src-tauri/src/app/tests/agent_status.rs` — every app-layer test that asserts the retired key form, passes the learned-id map, or documents the retired ordering

## Design

### The derivation

The derivation takes exactly one input: a reference to the pane identity value.
It produces, for a tab pane, the literal prefix `tab:` followed by the tab id;
for a mux pane, the literal prefix `mux:`, the connection scope's numeric value,
a colon, and the wire pane id. There is no third form and no branch on whether
an identifier was ever learned for the pane. The full pre/postcondition is
pinned in IMPLEMENTATION.md Shared Components — implement against that, do not
restate it in code comments as a second, drifting copy.

Removing the map parameter is the load-bearing part of the change (CD-2): the
security property "no daemon-supplied byte reaches the key" is then readable off
the signature, and any call site the plan failed to anticipate fails to compile
rather than silently keeping the old behaviour.

### The four production call sites

All four sites already hold the pane identity value they need; each simply stops
threading the learned-id map through. None of them changes what it does with the
derived key.

| Site | Flow | What changes |
|---|---|---|
| closed-mux-pane loop | A daemon batch reports panes that went away | Drops the map argument; keeps discarding the derived key and keeps removing the scoped learned-id entry |
| transition-drain loop | Agent-status transitions are drained and evaluated | Drops the map argument |
| close-tab | A tab is closed by the user | Drops the map argument; keeps the discard and the learned-id removal |
| reaped-exited-tab loop | An exited tab is reaped | Drops the map argument; keeps the discard and the learned-id removal |

### The retired ordering constraint

Three of those sites currently derive the key BEFORE removing the scoped
learned-id entry, and say so in comments, because the derivation used to read
that map. It no longer does, so the obligation is gone. The map removal stays;
the comments asserting the ordering are corrected so the source stops describing
a constraint that does not exist. If a site still has a genuine reason for its
current statement order, the comment states that reason instead.

### What is deliberately retained

The learned-id map and its public accessor are kept exactly as they are — they
serve the sidebar's copy-to-clipboard row, which is an identifier concern, not a
throttling one. Learning on a daemon status update stays; removal on pane close,
tab close and tab reap stays. Every close-time discard call site stays.

### Doc comments

Two doc comments are part of the deliverable: the derivation's own, rewritten
from three mutually disjoint forms to the two live ones; and the rate-limiter
field's, which must stop describing a daemon-learned identifier wrapped behind a
namespace prefix and instead state that no daemon-supplied byte ever reaches a
key.

### Test corrections

The app-layer test suite currently encodes the old contract in three ways, each
handled differently:

1. **Call-site-only updates** — tests that merely pass the map keep their intent
   and lose the argument.
2. **Assertion updates** — tests that assert the retired form assert the
   code-owned form instead.
3. **Premise-removed restatements** — two tests exist to prove that a
   daemon-controlled string cannot collide with another pane's or a tab's key.
   Their premise (that the string reaches the derivation at all) is gone. They
   are restated as guards that seeding the learned-id map with a value
   byte-identical to another key leaves the derived key unchanged, with the
   stronger reason that the derivation cannot read the map. They are not deleted.

One further test names the identity it checks but arms and probes an unrelated
raw string, so its rate-limit assertions currently pass vacuously. It is
corrected to obtain its key from the derivation, so that its pre-detach
assertion genuinely proves the window is armed and its post-detach assertion
genuinely proves it was released.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: For any connection scope and any wire pane id, the derivation yields
      the prefix `mux:`, the scope's numeric value, a colon and the wire pane id
      — identical whether an identifier was never learned for that pane, was
      learned, or was learned and then re-minted to a different value. Two
      connections holding the same wire pane id derive different keys.
- [ ] AC-2: A tab pane still derives the prefix `tab:` followed by its tab id,
      unchanged from before this task.
- [ ] AC-3: The derivation accepts only the pane identity value; no production
      call site and no test passes it a learned-id map, and the crate compiles —
      which is the whole check, since a value the function cannot accept cannot
      reach the key.
- [ ] AC-4: The retired prefix appears nowhere in the four files this task owns
      — neither emitted, nor asserted, nor described as a producible form — and
      no comment in those files asserts the derive-before-removal ordering.
- [ ] AC-5: The learned-id map, its learning site, its three removal sites, its
      public accessor's behaviour (the learned string verbatim for a learned
      pane, nothing for an unlearned or released one) and every close-time
      discard call site are all unchanged in behaviour.
- [ ] AC-6: The two premise-removed tests still exist as guards proving a
      learned value byte-identical to another pane's or a tab's key cannot reach
      that key, and the previously-vacuous detach test derives the key it arms
      and probes from the derivation itself rather than from a raw literal.
- [ ] AC-7: The library test command and the CLI-only check command from
      VERIFICATION.md both pass from this task's worktree.

## Test Notes

TDD order: update the tests first — the signature change makes every stale call
site a compile error, so the corrected tests define the target shape before the
derivation is touched.

| Scenario | Kind | Focus |
|---|---|---|
| TS-1 | Unit | The derivation for a learned pane, an unlearned pane, a tab, and a second scope's same-numbered pane. Rename it: there is no preference step left to name |
| TS-2 | Unit (edge case) | A learned value byte-identical to a tab's key cannot reach that tab's key |
| TS-3 | Unit (edge case) | A learned value byte-identical to another pane's key cannot reach that pane's key |
| TS-4 | Unit | Scoping: the map and the derived keys stay per-connection; the accessor's two assertions stay |
| TS-5 | Integration | Detach releases the model entry, the learned identifier and the rate-limit identity — now probing the real derived key |
| TS-6 | Integration | Detach on one tab leaves a second tab's identically-numbered pane untouched; the before/after equality now holds trivially, which is the point |
| TS-7 | Integration | Tab close, exited-tab reap and mux-pane exit each leave the closed pane's key absent, so an immediate re-report fires |
| TS-8 | Unit | Comment-only correction: the header example must cite the code-owned mux form, not a daemon identifier |

Edge cases worth explicit coverage: an empty learned value (the historical
aliasing case) must not change any derived key; and a pane whose identifier is
re-minted between two derivations must yield the identical key both times.

TDD-awkward: AC-3 is a compile-time property, so its "test" is that the crate
builds with no call site passing a map. Treat a successful build of the test
target as the evidence, and do not add a runtime assertion that pretends to
check it.
