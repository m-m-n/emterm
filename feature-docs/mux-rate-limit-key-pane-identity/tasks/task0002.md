# Task Plan: task0002 — Expiry eviction in the agent-notification rate limiter

## Goal

The rate limiter's record operation drops every entry that can no longer affect
any decision, so the limiter's live-entry count stays bounded over a
long-running session while every observable throttling decision stays exactly
as it is today.

## Requirements

FR6, FR7, NFR1, NFR3, NFR4

## Scope

### Files to Create

None — the limiter and its tests already live in one file.

### Files to Modify

- `src-tauri/src/notifications.rs` — the record operation gains expiry eviction; the read-only check and the close-time discard stay as they are; two tests are added beside the existing limiter tests

## Design

### What changes

The limiter keeps one entry per key: the instant that key last fired. Today the
record operation only inserts. After this task it also drops every entry whose
elapsed time relative to the instant being recorded is at least the cooldown
constant. The full pre/postcondition is pinned in IMPLEMENTATION.md Shared
Components — implement against that.

Ordering between the insert and the eviction sweep is unconstrained, because the
entry being recorded carries an elapsed time of zero and therefore can never be
its own sweep's victim. Choose whichever produces the clearer single pass.

### What must not change

- The read-only check keeps shared access and performs no mutation. It is not
  the pruning site. A suppressed attempt — one where a gate other than the rate
  limit rejected the notification, so nothing is recorded — must leave the
  limiter's contents byte-identical.
- The close-time discard and its contract stay. Expiry is additive: only the
  close-time discard prevents a key reused shortly after its pane closed from
  inheriting an unexpired cooldown (IMPLEMENTATION.md CD-4).
- The limiter stays generic over its key type and must not inspect, parse or
  branch on a key's textual shape, including inside the sweep (CD-5).
- No new public item, no new dependency, no change to the feature split.

### Why the threshold must be the read check's own

The sweep uses the same threshold and the same comparison the read-only check
uses (IMPLEMENTATION.md CD-3). That is what makes pruning provably
decision-neutral: an entry the sweep drops is by construction one the read check
would have answered "allowed" for, so dropping it cannot change any answer. A
different threshold, a grace multiplier, or a size-based trigger would break
that argument and is out of scope.

### Accepted limits

Two properties are accepted, recorded, and must not be engineered around here:
pruning is lazy, so a limiter with no further fires keeps its entries
indefinitely; and removing entries does not shrink the map's allocated capacity,
so expiry bounds live entries rather than the allocation high-water mark.

### Observing the limiter in tests

Entry presence and absence must be observable to the tests without widening the
limiter's public surface — the read-only check alone cannot distinguish "absent"
from "present but expired", since both answer "allowed". Use the access the
tests already have by virtue of living beside the limiter. Adding a public
accessor purely for test convenience is a surface change and is forbidden by
this task's criteria.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: After a fire is recorded for a key at some instant, a record for any
      key at an instant at least one cooldown period later leaves the first key
      absent from the limiter.
- [ ] AC-2: A record at an instant less than one cooldown period after a
      previous key's fire leaves that previous key present, with its original
      instant unchanged — a still-unexpired sibling is never collateral damage.
- [ ] AC-3: The read-only check performs no mutation: repeated calls at an
      instant arbitrarily far past the cooldown period leave the limiter's
      contents unchanged, and never arm a window for a key that never fired.
- [ ] AC-4: Close-time discard still removes exactly the named key and nothing
      else, so a key reused immediately after its pane closed fires rather than
      being suppressed; the existing discard regression test passes unmodified.
- [ ] AC-5: The eviction predicate uses the same threshold and comparison as the
      read-only check, so no throttling answer differs from the pre-task
      behaviour for any key that has not expired.
- [ ] AC-6: No public item is added, no dependency is added, and the limiter
      never branches on a key's textual shape.
- [ ] AC-7: The library test command and the CLI-only check command from
      VERIFICATION.md both pass from this task's worktree.

## Test Notes

TDD order: write the eviction and decision-neutrality tests first against the
current insert-only behaviour, watch them fail for the right reason (the expired
entry still present), then add the sweep.

| Scenario | Kind | Focus |
|---|---|---|
| TS-9 | Unit | Expiry: record one key, record a second key a full cooldown period later, then assert the first is gone while the second is present and throttled |
| TS-10 | Unit | Decision neutrality and read-purity: repeated read-only checks well past the cooldown leave contents unchanged, and a record inside the window does not evict a still-unexpired sibling |
| TS-11 | Unit (existing, unchanged) | Regression guard that close-time discard survives the addition of expiry. Keep it as it is; do not fold it into the expiry tests |

Both new tests drive time by offsetting a single captured instant rather than by
sleeping, matching how the existing limiter tests are written. Boundary case
worth pinning: an elapsed time exactly equal to the cooldown period counts as
expired, matching the read-only check's own boundary.

## Out of Scope

- Every change under `src-tauri/src/app/` — the key derivation, its call sites
  and the app-layer tests belong to another task and must not be edited here.
- Making the read-only check a pruning site, or pruning anywhere other than the
  record operation.
- Keying the limiter by the pane identity value instead of a formatted string.
- A hard entry cap or a global token bucket against adversarial bursts.
- Shrinking the map's allocated capacity, or any other mitigation of the
  accepted limits above.
