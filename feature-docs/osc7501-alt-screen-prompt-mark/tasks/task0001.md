# Task Plan: task0001 — Keep alternate-screen OSC 133 marks out of the OSC 7501 feed

## Goal

On a plain tab, an OSC 133 mark dispatched while the alternate screen is active
never enters the ordered OSC 7501 feed, so a main-screen OSC 133 A that follows
a report in the same processing unit discards that report's working / blocked /
idle record.

## Requirements

FR1, FR2, FR3, NFR1, NFR2

## Design

Cross-task contracts: IMPLEMENTATION.md SC-1, SC-2, D1, D2, D3.

### Parser core

Per dispatched OSC, the order stays:

1. The registered OSC responder is consulted (unchanged).
2. The existing native handling runs (OSC 8 hyperlink, OSC 133 live-mark gate,
   fold-mark capture, OSC 22) unchanged.
3. The callbacks are notified once through SC-1 with the action id, the payload
   and the alternate-screen state read at this point.

No callbacks installed: no notification, as today. The state is read at
dispatch time, so it is correct across the parser's buffer-switch interrupts
inside one resumed parse call.

| Bytes processed by this core before the OSC | "alternate screen active" |
|---------------------------------------------|---------------------------|
| none, or the last switch was `?1049l` / `?1047l` / `?47l` | false |
| the last switch was `?1049h` / `?1047h` / `?47h` | true |
| a RIS after the last switch | false |

### Host callbacks

| Notification | Screen | 7501 feed | Latch feed | Other state |
|--------------|--------|-----------|------------|-------------|
| OSC 133 with a recognized kind | main (SC-1 with false, or the existing notification called directly) | one prompt-mark item, as today | one candidate, as today | as today |
| OSC 133 with a recognized kind | alternate (SC-1 with true) | nothing | one candidate, as today | as today |
| OSC 133 with an unrecognized kind | either | nothing | nothing | as today |
| any other action | either | as the existing notification | as the existing notification | as the existing notification |

Each notification is handled once: the override does not both run its own
OSC 133 handling and forward the same notification to the existing one.

### Tab output pipeline

No logic change. The reproduction bytes after the change: the 7501 feed holds
the working report followed by one prompt start; the live marks hold one
prompt start. The report records working, the prompt start matches the only
live mark and discards the record, and the pending summary changes are
working followed by absence.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): With callbacks that override SC-1 and record every
  notification, an OSC dispatched after `?1049h`, `?1047h` or `?47h` is
  reported with "alternate screen active" true; an OSC dispatched before the
  switch, after the matching `l` within the same parse call, or after a RIS
  issued on the alternate screen is reported with false. Each dispatched OSC
  yields exactly one notification, in byte order.
- [ ] AC-2 (FR3, NFR2): Callbacks that implement only the existing OSC
  notification receive the same sequence of (action id, payload) for a byte
  stream mixing main-screen and alternate-screen OSCs as before this change,
  and the existing tests in `crates/term_core/src/callbacks.rs` and
  `crates/term_core/src/osc_handler.rs` pass unchanged.
- [ ] AC-3 (FR1, FR3): `NativeCallbacks` given an OSC 133 `A` through SC-1 with
  "alternate screen active" true adds nothing to the 7501 feed and exactly one
  prompt-mark candidate to the latch feed. Given it through SC-1 with false, or
  through the existing notification, it adds exactly one prompt-mark item to
  each feed. Any other action delivered through SC-1 leaves the same callback
  state as the existing notification, on either screen.
- [ ] AC-4 (FR1, FR2; TS-1): Feeding ESC `[?1049h`, OSC `133;A` (BEL),
  ESC `[?1049l`, OSC `7501;id=job:state=working` (BEL), OSC `133;A` (BEL) to a
  plain tab in one `process_combined` call leaves the record table empty, and
  the pending summary changes are `[Some(working), None]`.
- [ ] AC-5 (FR1; TS-2): The AC-4 sequence with the alternate-screen switch done
  by `?1047` gives the AC-4 result, and so does the sequence done by `?47`.
- [ ] AC-6 (FR1, FR2; TS-3, TS-4): In one `process_combined` call each:
  (a) main-screen OSC 133 A, `?1049h`, OSC 133 A, `?1049l`, a working report,
  main-screen OSC 133 A leaves the record table empty; (b) `?1049h`, two OSC 133
  A marks, `?1049l`, a working report, main-screen OSC 133 A leaves the record
  table empty.
- [ ] AC-7 (FR3, NFR1, NFR2; TS-5, TS-6): The existing osc7501 /
  program_status_feed tests in `src-tauri/src/tabs/tests/output_pipeline.rs`
  and `src-tauri/src/callbacks/tests.rs`, and the existing agent-status latch
  tests, pass with names and expectations unchanged; the `src-tauri` `--lib`
  suite, the `term_core` `--lib` suite, the `src-tauri` check and the CLI-only
  (`--no-default-features`) check all pass.

## Test Notes

- AC-1 and AC-2: `term_core` unit tests. The existing recording doubles in the
  `callbacks.rs` tests show the shape; one double overrides SC-1, another
  implements only the existing notification.
- AC-3: `src-tauri/src/callbacks/tests.rs` with the default harness, calling
  SC-1 and the existing notification directly and asserting both feeds.
- AC-4 to AC-6: byte-level tests through `process_combined` on the plain test
  tab, reusing the existing OSC 7501 helpers of that test module.
- Red before the change: AC-4 is the reported bug (the record stays); AC-5 and
  AC-6 fail the same way; AC-1 to AC-3 fail because SC-1 does not exist yet.
- Edge case worth a test: a RIS issued on the alternate screen, followed by a
  working report and a main-screen OSC 133 A in the same call, leaves the record
  table empty.
- The replay tests under `src-tauri/src/tabs/tests/` can fail
  non-deterministically when run in parallel; re-run a suspicious failure there
  with one test thread before treating it as a regression.
