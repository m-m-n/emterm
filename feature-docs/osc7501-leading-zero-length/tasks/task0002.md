# Task Plan: task0002 — Mux path: shared-rule ingestion, received length and FR9 records

## Goal

A mux pane ingests OSC 7501 and OSC 133 by the shared recognition rule, applies
the 4096-byte limit to the received bytes, keeps non-canonical OSC 133 marks
away from the OSC 777 inferred-clear latch, and ends in the same OSC 7501
state as a plain tab; the FR9 test rename and its predecessor record are

## Design

Cross-task contracts used here: SC-1, SC-2, SC-3 (consumer; D4 applies),
SC-4, D1–D5 in IMPLEMENTATION.md. `Z(n)` below is the SC-4 notation for n
ASCII `0` bytes.

### osc_identify

- Add one allocation-free entry that returns an OSC string's number under
  SC-1 (none above the u16 range): a single forward pass, no panicking
  arithmetic or indexing.
- The existing zero-allocation identity takes its number from the same entry
  or stays provably equal to it; its allocation-free test and its
  equivalence with the reference recovery over the existing corpus keep
  passing.
- `recover_osc` stays the reference for SC-1 data.

### Feed scanner commit (FR3, FR6)

For each completed OSC body, in this order:

1. A body starting with the canonical OSC 777 agent-status prefix gives the
   report item, as today (canonical-only, predecessor FR18).
2. Otherwise the number comes from the osc_identify entry — never from a
   scanner-local accumulation. Number 7501 gives an OSC 7501 item,
   regardless of live spans, carrying the SC-1 data decoded the way
   term_core decodes it (D3), the SC-2 received length (the raw body
   length) and the terminator. The former one-byte substitution of
   non-ASCII bytes goes away.
3. Number 133 with its terminator inside a live span: a canonical mark (the
   body starts with `133;` and the first segment after it is one valid kind
   byte) gives the existing mark item, as today. Otherwise, when the first
   `;`-separated segment of the SC-1 data is the single prompt-start kind
   byte, it gives the new non-canonical prompt-start item. Other kinds give
   nothing.
4. Anything else gives nothing.

The carry bound, the RIS tracking, the terminator state machine and the
byte-order guarantee are unchanged.

### Feed item, pane and daemon

- The OSC 7501 item carries the received length next to the body and
  terminator.
- The new item means "apply the OSC 7501 prompt start only". It never
  reaches the OSC 777 exit latch.
- The pane gains an operation that applies only the OSC 7501 prompt start
  under the same lock and revision rule the existing mark operation uses for
  that part (the revision moves only when a record was removed) and does not
  touch the exit latch.
- The daemon task calls SC-3 with the item's received length, and handles the
  new item in the same single ordered loop: find the pane, apply the
  operation, broadcast one update through the existing builder when the
  revision moved. Unknown panes are dropped as today.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR3, FR6, FR7, NFR3, TM-3, TM-4): The feed scanner yields exactly
  one OSC 7501 item for each of `07501;state=idle`, `x7501;:state=clear`,
  `7501` and `7501;state=idle`, whose body is the SC-1 data and whose
  received length is the raw byte count between `ESC ]` and the terminator,
  with BEL and with ST. It yields no OSC 7501 item for `7500;x`, `7502;x`,
  `750;state=idle`, `17501;x`, `75010;x`, `65536;x` and
  `655367501;state=error`, and no report item for
  `0777;emterm;agent-status;v=1;state=working`. The existing byte-order,
  split-read and carry-bound tests pass with the new item shape.
- [ ] AC-2 (FR1, FR3, TM-3): Through the real reader and daemon task: after
  `OSC 7501;state=working BEL`, `OSC 07501;state=clear BEL` leaves no record
  (repro 2); SC-4 rows P4 and P6 are accepted and P5 and P7 are rejected;
  P8 is accepted and P9 rejected; a query of any spelling or length changes
  nothing and broadcasts nothing.
