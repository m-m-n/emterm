# Task Plan: task0001 — Plain-tab path: received length and saturating OSC number

## Goal

A plain tab measures every OSC 7501 report by the bytes it actually received
and never routes an above-range OSC number to any code: term_core counts the
received OSC-string length and saturates the OSC number, and the plain-tab
responder applies the 4096-byte rule to that count through SC-3.

## Design

Cross-task contracts used here: SC-1, SC-2, SC-3 (this task owns it), SC-4,
D1–D3, D5 in IMPLEMENTATION.md.

### term_core: received length (FR2)

- The parser keeps one received-length counter per OSC string. It starts at
  zero when `ESC ]` opens a string and on a parser reset.
- Every byte the OSC string state consumes, except BEL and the `ESC` that may
  begin ST, adds one with saturation: digits accumulated into the number, the
  first `;`, non-digit bytes before it, data bytes, and data bytes beyond
  `MAX_OSC_LEN` that the buffer drops.
- For a string cut short by `ESC` + another byte (unterminated), the `ESC`
  and the following byte are not counted.
- The dispatched OSC action carries the counter value; the dispatch boundary
  receives it alongside the number, data and terminator kind.

### term_core: saturating number (FR7)

- The OSC number accumulates with saturation on both the multiply and the
  add. Once above the u16 range it stays at 65535 for the rest of the
  string's number digits.
- 65535 maps to no native handler; the host registers no 65535 app param
  (A5), so a saturated number reaches no code.

### term_core: responder seam (FR2, NFR2)

- The responder trait gains one provided method with the same inputs as the
  existing method plus the received length. Its default forwards to the
  existing method unchanged and ignores the length.
- term_core calls the new method — never the existing one directly — once per
  dispatched OSC, at the same position the existing call has today (before
  the screen-aware notification, including the OSC 8 early-return site).
- term_core gains no knowledge of 7501. Its tests use neutral OSC numbers.
- The screen-aware notification and `on_osc` are unchanged.

### program_status: SC-3

- Add `parse_received` per SC-3. The query check comes first; the length
  check uses 2 + received length + terminator length with saturation.
- `parse` and `parse_bytes` become thin forms of `parse_received` with the
  canonical length (5 + body bytes); their results do not change.

### Plain-tab responder

- The plain-tab responder implements the new responder method: for OSC 7501
  it runs the existing program-status handling with `parse_received` and the
  delivered length; every other code goes to the existing method.
- The existing method keeps its current OSC 7501 behavior (canonical length)
  for direct callers.
- Unterminated strings still get no answer and no feed item; queries are
  answered once with their own terminator; nothing is logged.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR2, NFR3, TM-1): For a dispatched OSC, term_core reports a
  received length equal to the bytes between `ESC ]` and the terminator,
  counting leading zeros, digits, non-digit bytes before the first `;`, the
  first `;` and every data byte once, with invalid UTF-8 bytes counted before
  replacement; BEL, ST and the unterminated form all exclude the terminator
  bytes; the count starts from zero for each string (consecutive strings, a
  string reopened by a new `ESC ]`, after a parser reset). A string of
  `MAX_OSC_LEN` + 100 data bytes reports its full received count while its
  data stays capped at `MAX_OSC_LEN`. A 1 MiB OSC string is dispatched
  within 2 seconds.
- [ ] AC-2 (FR7, NFR3, TM-2): term_core dispatches `65535;x` with number
  65535, and `65536;x` and `655367501;state=error` with 65535; `6553652;x`
  is dispatched with 65535 and is not handled as OSC 52; a host-registered
  app param is not reached by a saturated number; a number of one million
  digits is dispatched within 2 seconds. These tests run in the debug test
  build without a panic.
- [ ] AC-3 (FR2, NFR2): A responder that implements only the existing method
  receives the same calls in the same order as before (every existing
  term_core responder test and every existing src-tauri responder test
  passes unchanged). A responder that implements the new method receives the
  received length with the code, payload and terminator, exactly once per
  dispatched OSC, before the screen-aware notification. Searching
  `crates/term_core/src` for `7501` finds only the existing `osc7501-`
  feature-name mentions in comments.
- [ ] AC-4 (FR1, FR5, FR8, TM-1): `parse_received` meets SC-3: with BEL and
  with ST, a received length giving a whole sequence of 4096 bytes is
  accepted and 4097 is `Ignored`; a body whose replaced text is longer than
  4096 bytes is accepted when its received length gives 4096 or less; a body
  of exactly `?` is `Query` for every received length, including one above
  `MAX_OSC_LEN`. Every existing program_status test passes unchanged.
- [ ] AC-5 (FR1, FR2, TM-1): Through a plain tab's live output path, seeded
  per SC-4: repro 1 (row P3, 4115 bytes) leaves the table unchanged; rows P4
  and P6 are accepted and P5 and P7 are rejected; rows P8 and P9 give the
  SC-4 results; an OSC 7501 report whose OSC string exceeds `MAX_OSC_LEN`
  registers no record.
- [ ] AC-6 (FR8): Through a plain tab's live output path, rows P18 and P19
  and the BEL form of P19 each get exactly one answer `ESC ] 7501;?` with
  the query's own terminator and change no record; an unterminated
  leading-zero query longer than 4096 bytes gets no answer.
- [ ] AC-7 (FR4, FR5, NFR1, NFR4): Every SC-4 row fed to a plain tab ends in
  the row's final table and answer. Every existing term_core and src-tauri
  test passes; the `--no-default-features` check succeeds; the change adds
  no log call on any path that rejects, ignores or does not recognize input.

## Test Notes

- AC-1, AC-2: unit tests at the parser level (the parser tests file) plus
  dispatch-level tests in the OSC dispatch module through a recording
  responder. Run with the term_core test command; the default test profile
  keeps overflow checks on, so a non-saturating add would panic there.
- AC-2's OSC 52 case: assert through the callbacks that no notification with
  the clipboard action is produced and through a recording responder that
  the code is 65535.
- AC-3: the existing term_core test doubles implement only the existing
  method; they are the regression guard. Add one double that implements the
  new method.
- Existing parser tests compare whole dispatched actions; update their
  expected values with the received length rather than renaming them.
- AC-4: program_status unit tests. Build boundary bodies from the received
  length, not from the canonical-introducer helper.
- AC-5, AC-6, AC-7: the output-pipeline tests over the live output path,
  following the existing OSC 7501 tests there; build SC-4 rows
  programmatically and assert on table contents and outbound writes. The
  `MAX_OSC_LEN` row is large; build it once and assert on the table only.
- Responder-level cases for the new method in the callbacks tests: length
  just under and over the limit, a query with a huge length, unterminated.
