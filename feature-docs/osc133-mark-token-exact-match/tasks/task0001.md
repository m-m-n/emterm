# Task Plan: task0001 — Exact first-token match for plain-tab OSC 133 mark candidates

## Goal

`NativeCallbacks::handle_semantic_prompt` pushes an OSC 133 mark candidate to the
OSC 7501 feed and the agent-status latch feed only when the payload's first
`;`-separated token is exactly `A`, `B`, `C` or `D` — the criterion term_core's
`parse_osc133_mark` already applies to live marks — so a malformed token such as
`133;AB` no longer consumes a later well-formed mark's live mark.

## Requirements

FR1, FR2, FR3, NFR1

## Scope

### Files to Create

None.

### Files to Modify
- `src-tauri/src/callbacks.rs` — the semantic-prompt handler decides the mark kind by exact first-token match; its doc comment states that criterion.
- `src-tauri/src/callbacks/tests.rs` — unit tests for malformed tokens, well-formed tokens and edge cases on both feeds (TS-2, TS-3, TS-5).
- `src-tauri/src/tabs/tests/output_pipeline.rs` — plain-tab output-pipeline test with the reproduction bytes (TS-1).

## Design

### Kind decision (FR1)

The kind decision inside `handle_semantic_prompt` has this contract:

- Input: the OSC 133 payload as delivered to the callback (the text after
  `133;`).
- Output: an optional prompt-mark kind.
- Postcondition: a kind is returned if and only if the payload's first
  `;`-separated segment (the whole payload when it holds no `;`) is exactly one
  of the single characters `A`, `B`, `C`, `D`. `A` maps to prompt start, `B` to
  command start, `C` to command exec, `D` to command end. Segments after the
  first never affect the result (`D;0`, `D;42`, `D;x`, `A;aid=1` are
  recognized). Every other first segment — longer than one character (`AB`,
  `Ax`, `Bx`, `Cx`, `Dx`, `D0`), empty (payload `""`, payload `;A`), or a
  character outside the four — yields no kind.
- The single-character-to-kind step reuses the existing byte-level mapping on
  the prompt-mark kind type in `src-tauri/src/prompts.rs`, unchanged. The
  segment-length check (exactly one character) is the new part and lives in
  `callbacks.rs`.

### Processing flow (FR2, FR3)

1. Alternate screen active → push nothing (unchanged).
2. Main screen and the kind decision yields a kind → push one candidate of that
   kind to the latch feed and one to the OSC 7501 feed, under the same single
   lock acquisition and in the same order as today (unchanged).
3. Main screen and the kind decision yields no kind → push nothing to either
   feed.
4. The existing debug log line is kept for every payload.

Both entry routes — the existing `on_osc` notification for action 133 (counted
as main screen) and the screen-aware `on_osc_with_screen` — already reach this
one method exactly once; their routing does not change.

### Why the criterion is mirrored locally

term_core's parser is private to term_core, and NFR1 keeps term_core
unchanged, so the callback applies the same exact first-token rule itself. The
mux write filter (`src-tauri/src/mux/ipc/pty_spawn/write_filter.rs`, OSC 133
item recognition) already applies an exact first-segment rule in the same
crate; this task brings the plain-tab callback in line with it.

### Doc comment

The `handle_semantic_prompt` doc comment states that a kind is recognized only
by an exact first-token match, names term_core's `parse_osc133_mark` as the
criterion it matches, and states that an unrecognized kind pushes nothing to
either feed on either screen.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS-1; FR1, FR2): On a fresh plain test tab, one output-pipeline call with the bytes `\x1b]133;AB\x07\x1b]7501;id=job:state=working\x07\x1b]133;A\x07` leaves the tab's OSC 7501 record table empty (no `job` record).
- [ ] AC-2 (TS-2; FR1, FR2): For each first token `AB`, `Ax`, `Bx`, `Cx`, `Dx`, `D0`, an OSC 133 delivered through the screen-aware notification with the alternate screen inactive, and again with it active, leaves both `pending_program_status_feed` and `pending_latch_feed` empty; the same tokens delivered through the existing `on_osc` notification also leave both feeds empty.
- [ ] AC-3 (TS-3; FR3): `A`, `B`, `C`, `D`, `D;0`, `D;x` and `A;aid=1`, each delivered on the main screen to a fresh harness, push exactly one candidate to each feed, of the matching kind (`A` and `A;aid=1` prompt start, `B` command start, `C` command exec, `D`, `D;0` and `D;x` command end).
- [ ] AC-4 (TS-5; FR1, FR2, FR3): Payloads `""` and `;A` leave both feeds empty on either screen; `D;42` on the main screen pushes exactly one command-end candidate to each feed; `D;42`, `D;x` and `A;aid=1` on the alternate screen leave both feeds empty.
- [ ] AC-5 (NFR1): The feature diff contains no path under `crates/term_core/`, and the existing tests `osc_133_every_recognized_kind_follows_the_screen_rule_and_an_unrecognized_one_pushes_nothing`, `program_status_feed_preserves_true_order_of_reports_marks_and_resets`, `test_parse_osc133_mark_kinds` and every `osc7501_prompt_start_*` test are neither modified, renamed nor removed.
- [ ] AC-6 (TS-4; NFR1, FR3): `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib` and `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path crates/term_core/Cargo.toml --lib` pass, and `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features` compiles.

## Test Notes

- AC-1 is an output-pipeline test in `src-tauri/src/tabs/tests/output_pipeline.rs`,
  built like the module's existing OSC 7501 tests (fresh plain test tab, the
  whole byte string in ONE call — the defect needs the malformed candidate and
  the well-formed mark in the same processing unit). It fails before the fix:
  the `AB` candidate is matched against the only live mark (the trailing `A`),
  so the trailing `A` finds no live mark and the `job` record survives.
- AC-2, AC-3 and AC-4 are unit tests in `src-tauri/src/callbacks/tests.rs`,
  using the module's default harness; use a fresh harness per token and screen
  state so one case cannot mask another. Assert on both feeds in every case.
- Red expectations: AC-1, and the main-screen and `on_osc` halves of AC-2, fail
  before the fix. The alternate-screen half of AC-2, AC-3 and AC-4 pass before
  the fix; they are regression guards for FR3 and the edge cases, not red
  tests.
- AC-5 is checked against the diff and the test listing, not by a new test.
- No existing test is renamed, so the test-docs record rename duty does not
  apply.

## Out of Scope

- Any change under `crates/term_core/` (NFR1): `parse_osc133_mark`,
