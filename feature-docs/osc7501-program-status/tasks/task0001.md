# Task Plan: task0001 — Program Status core module (parser, record table, summary)

## Goal

Deliver the build-agnostic Program Status core (IMPLEMENTATION.md SC-1): it
turns an OSC 7501 body into a validated report or a query, keeps one record
table per terminal under the protocol's replacement, clear, inheritance, cap
and lifecycle rules, and exposes the table's aggregate summary plus a
re-validating export/import. Every other OSC 7501 task consumes this module.

## Requirements

FR2, FR3, FR4, FR5, FR6, FR7, FR10, NFR1, NFR2, NFR5

## Design

The public contract is SC-1 in IMPLEMENTATION.md; this section fixes the
task-internal rules the contract leaves open. D2 (rank) and D9 (title
sanitization) in IMPLEMENTATION.md apply.

### Parsing flow

Input: the OSC body text that follows `7501;`, plus the terminator kind
(BEL or ST). Callers never pass an unterminated sequence.

1. A body that is exactly `?` is a Query. Nothing else is a query.
2. Whole-sequence length = 7 introducer bytes (ESC, `]`, `7501`, `;`) + the
   body's byte length + the terminator length (1 for BEL, 2 for ST). A
   length above 4096 discards the report.
3. The body is split on `:` into pairs; each pair splits at its first `=`.
   A pair is skipped when it has no `=`, when its key is not one or more
   lowercase ASCII letters, or when its value holds a byte outside
   `A-Z a-z 0-9 _ . , + / = -`. Unknown keys are ignored. For a repeated key
   the last surviving occurrence wins.
4. `title` and `msg`: the encoded value is checked against its cap (256 /
   2732 bytes), then decoded as base64 with the standard alphabet (padded
   and unpadded forms both accepted). A decode failure, a decoded size above
   its cap (192 / 2048 bytes), a decoded result that is not UTF-8, or one
   that contains a control character (C0, DEL, C1) discards the whole
   report. An empty decoded value counts as absent.
5. `state` is required and must be one of the six words; otherwise the
   report is ignored.
6. `id` is optional (absent = root). A present value must be 1 to 8
   `/`-separated segments, each 1–32 characters of `A-Z a-z 0-9 _ . + -`,
   128 bytes at most in total; otherwise the report is ignored. An empty
   `id=` value is invalid. Step 3 runs first: an `id` pair that fails the
   pair grammar is skipped, which leaves the report addressed to the root
   (the literal reading of FR2 then FR3).
7. `kind`: kept only when state is `blocked` and the value is `permission`,
   `question` or `auth`; any other value leaves it absent.
8. `progress`: decimal digits only, value 0–100, otherwise the pair is
   skipped (A5); kept only when state is `working` or `blocked`.
9. `app`: kept when it matches `[A-Za-z0-9_.+-]{1,32}`, otherwise absent.

Discard (steps 2 and 4) and ignore (steps 5 and 6) both mean "nothing
changes". The parser is pure and side-effect free.

### Record table

- Keyed by id; the root (no id) is its own key and is an ancestor of every
  id. The ancestors of `a/b/c` are `a/b`, `a` and the root.
- A non-clear report fully replaces its id's record (omitted keys
  disappear) and makes it the most recently updated record.
- `clear` with an id removes that id and every id that starts with it
  followed by `/` (`a` clears `a/b`, never `ab`). `clear` without an id
  removes every record. A clear that removes nothing is still an accepted
  report.
- Inserting a new id while 256 records exist first removes the least
  recently updated record. Updating an existing id never evicts.
- Every accepted report counts as accepted, whether or not the stored data
  changed (the daemon bumps its revision per accepted report, SC-1).

### Lifecycle operations

- Prompt start: removes every `working`, `blocked` and `idle` record; keeps
  `done` and `error`; reports whether anything was removed.
- Reset: removes every record; reports whether anything existed.

### Summary

- None for an empty table.
- Deciding record: the highest record by the D2 rank (blocked > working >
  error > done > idle); ties go to the most recently updated record (A13).
- The summary carries the deciding record's state, its title after D9
  sanitization (absent when missing or empty after sanitization), and its
  effective app: its own app, or else the app of its nearest ancestor
  record present at summary time.

### Export / import

- Export lists every record, least recently updated first, with id, state
  word, kind, progress, app, decoded title and decoded msg as plain values.
- Import takes such a list (oldest first) and rebuilds a table with the
  same update order. Each record is re-validated against the same id, app,
  kind, progress, title and msg rules (decoded caps and control-character
  rule); an invalid record is dropped. When more than 256 valid records
  remain, the most recently updated 256 are kept.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Parsing (FR2, FR4, FR5): malformed pairs are skipped, unknown keys ignored, a repeated key resolves to its last valid occurrence; each of the six state words is recognized; `kind` is kept only for `blocked`, `progress` only for `working`/`blocked` and only as an integer 0–100 (a non-integer or out-of-range value skips the pair); an invalid `app` value is absent; a body that is exactly `?` yields a Query and no other body does.
- [ ] AC-2: Discard and ignore conditions (FR3, TM-1, TM-3): with both terminators, a whole sequence of exactly 4096 bytes is accepted and 4097 is discarded; title above 256 encoded or 192 decoded bytes, msg above 2732 encoded or 2048 decoded bytes, invalid base64, a decoded value that is not UTF-8 or that contains a C0, DEL or C1 control character each discard the whole report; a missing or unknown state, and an invalid id (bad segment, more than 8 levels, more than 128 bytes, empty value) each ignore it — in every case the table is unchanged.
- [ ] AC-3: Table mutations (FR4, FR6, TM-1): a non-clear report fully replaces its id's record (omitted keys disappear); `clear` with an id removes that id and its descendants on segment boundaries only; `clear` without an id removes every record; inserting a 257th distinct id evicts the least recently updated record; re-reporting an existing id refreshes its recency and evicts nothing.
- [ ] AC-4: Lifecycle (FR7): prompt start removes `working`, `blocked` and `idle` records, keeps `done` and `error`, and reports whether it removed anything; reset removes every record and reports whether any existed; neither alters the surviving records' fields or relative update order.
- [ ] AC-5: Summary (FR5, FR10, A13): an empty table has no summary; otherwise the state is the highest across root and all descendants by blocked > working > error > done > idle, title and app come from the deciding record with ties broken by the most recent update, and a record without app takes the app of its nearest ancestor record present at summary time (the root counts as an ancestor).
- [ ] AC-6: Title sanitization for names (NFR5, TM-3): control characters and invisible formatting characters (at least U+00AD, U+061C, U+200B–U+200F, U+2028–U+202E, U+2060–U+2064, U+2066–U+2069, U+FEFF) are removed and the result is truncated to 80 characters; title and msg are kept as plain text and never interpreted.
- [ ] AC-7: Export/import (FR17 support, TM-7): export lists records oldest-updated first with all fields; importing an export yields a table equal to the original, including which record the next eviction removes; import drops a record that violates any id, app, kind, progress, title or msg rule and keeps at most the 256 most recently updated records.
- [ ] AC-8: Build (NFR1): the module depends only on always-built crates and compiles in the `--no-default-features` build.

## Test Notes

- Unit tests only (TS1, TS2, TS3 table level), in `program_status/tests.rs`.
- AC-1 / AC-2 are table-driven; compute boundary inputs so each limit is
  hit exactly (sequence length per terminator, encoded and decoded title /
  msg sizes, id segment length, segment count and total bytes).
- AC-3 eviction: fill 256 ids, touch one, insert a new id, assert which id
  disappeared.
- AC-7 eviction parity: export, import, insert one more id into both the
  original and the imported table, compare the results.
- AC-8 is verified by the `--no-default-features` check (VERIFICATION.md
  TS10); the task runs that command before finishing.
- NFR2: write the parser from the SPEC text only; consult no external
  implementation's code.
