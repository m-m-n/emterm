# Threat Model: osc7501-program-status

## Verdict
threats-identified

## Rationale
Inspected SPEC.md and REQUIREMENTS.md (FR1–FR19, NFR1–NFR5, A1–A14) at the
`full` tier. The feature's inputs are bytes written by any program running in
a terminal (including programs on remote hosts reached over SSH), which reach
a new parser on two paths: the plain-tab GUI path (task0003 over task0001) and
the mux daemon path (task0004 over task0001). Derived text flows into desktop
notifications and the status bar (task0002, task0005). The terminal also
writes a response into the program's input for the `?` query, and the mux
daemon replays recorded output to the GUI (task0003, task0006). The hot
upgrade hands records from one daemon binary to another through a file
(task0007). Depth is deep for every boundary: input-handling drives TB-1 and
TB-2, data-persistence drives TB-3. The task decomposition was re-checked
against the Boundary files lines: every task declaring input-handling
(task0001, task0003, task0004, task0006) or data-persistence (task0007) has
its boundary-handling files listed below. Spoofing of the reporting program
itself is not analysed: the protocol carries no identity, and the SPEC asks
for none. The daemon-to-GUI channel is not a separate boundary: both ends run
the same version (A8) and the title it carries is already sanitized at TB-1.

## Trust Boundaries

### TB-1: Program output → OSC 7501 parsing, record state and derived text
Crossing: bytes from any program in a tab or mux pane (untrusted, possibly
remote) enter eMterm's OSC 7501 parser and per-tab / per-pane record table;
the record's title then becomes the name in desktop notifications, and the
aggregate state becomes the status bar value.
Boundary files: src-tauri/src/program_status.rs, src-tauri/src/callbacks.rs, src-tauri/src/tabs/output_pipeline.rs, src-tauri/src/mux/ipc/pty_spawn/write_filter.rs, src-tauri/src/mux/daemon/tasks.rs, src-tauri/src/notifications.rs, src-tauri/src/status_bar/providers/agent_status.rs
Depth: deep (input-handling)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Denial of service | Oversized sequences, oversized title or msg payloads, deep or long ids, or an unbounded number of distinct ids exhaust memory and CPU in the GUI pump or the daemon (FR3, FR6) | TM-1 | Whole-sequence 4096-byte cap, encoded and decoded caps on title and msg, id segment/depth/length caps, and a 256-record table cap that evicts the least recently updated record; every report's cost is bounded by these caps | task0001 AC-2, task0001 AC-3 | VERIFICATION.md Performance / Security Verification: TM-1 |
| Denial of service | An unterminated or over-long OSC 7501 makes the daemon's agent-status scanner retain bytes without bound (FR1, FR14) | TM-2 | OSC 7501 recognition uses the scanner's existing bounded carry; an over-long or unterminated body yields no item and the retained bytes stay within the existing bound | task0004 AC-2 | VERIFICATION.md Performance / Security Verification: TM-2 |
| Spoofing | A title carrying bidirectional controls or invisible characters makes a notification misstate which agent or what text it reports (NFR5, FR12) | TM-3 | A decoded title containing a control character discards the report; the name taken from a title has control and invisible formatting characters removed and is cut to 80 characters; the daemon sends only the sanitized title | task0001 AC-2, task0001 AC-6, task0004 AC-3 | VERIFICATION.md Performance / Security Verification: TM-3 |
| Tampering | Title or msg content is interpreted as markup in the desktop notification, or terminal-supplied text reaches the status bar template (NFR5, A9) | TM-4 | The title enters the notification body as plain text and goes through the existing escape-on-send path; msg is never displayed; `{agent_status}` holds only a state word or the empty string | task0002 AC-7, task0005 AC-4 | VERIFICATION.md Performance / Security Verification: TM-4 |

### TB-2: Terminal-generated bytes into a program's input, and recorded output replayed into the GUI
Crossing: eMterm writes a query response into the PTY input of whatever
program currently reads it (the shell or another program); the mux daemon
replays recorded PTY output into the GUI's parser on reattach, snapshot and
window switch.
Boundary files: src-tauri/src/callbacks.rs, src-tauri/src/tabs/output_pipeline.rs, src-tauri/src/mux/osc_identify.rs, src-tauri/src/mux/scrollback_filter.rs, src-tauri/src/mux/ipc/pty_spawn/client_parity_scan.rs
Depth: deep (input-handling)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Tampering | A recorded query or report is replayed at reattach, so the GUI writes a response into the program now reading the pane's input (for example a shell prompt) or re-applies stale records (FR15, FR8, FR14) | TM-5 | OSC 7501 reports and queries are stripped from the daemon's scrollback ring and snapshots; the GUI discards 7501 state parsed from mux inner content; state resyncs only through replay-derived messages | task0006 AC-2, task0003 AC-6 | VERIFICATION.md Performance / Security Verification: TM-5 |
| Tampering | A crafted query makes the terminal write attacker-chosen bytes, or many responses, into the program's input (FR8) | TM-6 | The response is the fixed sequence ESC ] 7501;? plus the query's own terminator, produced only for a body of exactly `?` terminated by BEL or ST, once per query, within the existing responder byte budget | task0003 AC-2 | VERIFICATION.md Performance / Security Verification: TM-6 |

### TB-3: Handoff file from the old daemon binary into the new daemon
Crossing: the handoff document written to disk by the old daemon process is
read by the new daemon binary during a hot upgrade; its record lists
originate from untrusted program output and may come from a binary with
different validation.
Boundary files: crates/mux_ipc/src/handoff.rs, src-tauri/src/mux/upgrade.rs, src-tauri/src/program_status.rs
Depth: deep (data-persistence)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Denial of service | A malformed or oversized record list in the handoff document installs records beyond the protocol limits in the new daemon (FR17, FR3, FR6) | TM-7 | Version-gated decode as today; restored records go through the core import, which re-validates every field against the FR3/FR5 rules, drops invalid records and keeps at most the 256 most recently updated | task0001 AC-7, task0007 AC-4 | VERIFICATION.md Performance / Security Verification: TM-7 |
