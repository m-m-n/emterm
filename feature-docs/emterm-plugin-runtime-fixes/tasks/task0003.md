# Task Plan: task0003 — Hook state-machine completion (rework)

## Goal

Close the two state-machine holes found in review round 1: the badge never leaves `blocked` after a permission prompt is answered, and it sticks on `working` when an API error ends the turn. Both are fixed by wiring hook events that are currently unwired.

## Requirements

FR4, FR5 (both extended by this task — see Design). Round-1 findings `cm-no-blocked-recovery` (high) and `cm-stopfailure-unwired` (medium).

## Scope

### Files to Modify

- `plugins/emterm/hooks/hooks.json` — add two hook entries.
- `plugins/emterm/hooks/scripts/notify-status.test.ts` — update the event-set assertions and add coverage for the new entries.
- `feature-docs/emterm-plugin-runtime-fixes/SPEC.md` — FR4's event list, TS-6's expectations, and the M-1 manual scenario.
- `feature-docs/emterm-plugin-runtime-fixes/VERIFICATION.md` — TS-6 and M-1.

### Files to Create

None. The hook script itself does not change — it already accepts every state this task needs.

## Design

### F1 (from finding cm-no-blocked-recovery, high) — recover from `blocked`

Today the state machine only ever enters `blocked` and waits for `Stop`:

```
UserPromptSubmit -> working
Notification(permission_prompt) -> blocked
   user approves; Claude resumes work   <-- nothing clears blocked here
Stop -> idle
```

Add a `PostToolUse` hook with no matcher and args `["working"]`. It fires right after each tool call completes, so the first tool that runs after an approval returns the badge to `working`. `blocked` then covers only the actual wait.

Rationale for `PostToolUse` over `PreToolUse`: a `PreToolUse` firing is followed by the permission prompt for that same call, so `blocked` would overwrite the `working` it just set. `PostToolUse` is strictly after the wait ends.

Cost: one `sh` fork per tool call. The script has no subprocess, no file I/O, and no timer (NFR1), so this is a few milliseconds and does not warrant a matcher to narrow it.

### F2 (from finding cm-stopfailure-unwired, medium) — `StopFailure`

Claude Code fires `StopFailure` **instead of** `Stop` when a turn ends due to an API error (rate limit, auth failure, and similar). Because `idle` is wired only to `Stop`, that path leaves the badge on `working` indefinitely.

Add a `StopFailure` hook with no matcher and args `["idle"]`.

Caveat to record, not to solve here: the documentation states that `StopFailure` hook output and exit codes are ignored. Whether `terminalSequence` is still honoured on that event cannot be settled from the docs, so M-1 gains a step that exercises it on a real API error. If the live check later shows it is not honoured, the follow-up is a README known-limitation line, not a code change.

### Resulting event map

| Event | Matcher | State |
|---|---|---|
| `UserPromptSubmit` | none | `working` |
| `PostToolUse` | none | `working` |
| `Stop` | none | `idle` |
| `StopFailure` | none | `idle` |
| `Notification` | `^(permission_prompt\|elicitation_dialog\|agent_needs_input)$` | `blocked` |

Still no `SubagentStop` entry. All entries stay in exec form (`command` + `args`, `timeout: 3`) per FR4.

### Document updates

SPEC.md FR4 currently enumerates exactly three hooks; it must enumerate five, keeping the exec-form and `timeout: 3` requirements and the "no `SubagentStop`" statement. TS-6 in both SPEC.md and VERIFICATION.md must expect the five-entry set. M-1 gains two steps: confirm the badge returns to `working` after approving a permission prompt, and exercise the `StopFailure` path.

## Test Notes

- AC-5 is the regression guard that matters: the existing assertion enumerating three events will fail once the entries are added, and updating it to five is the point. Do not weaken it to a subset check.
- The new entries need no new script behaviour, so there is nothing to unit-test beyond the manifest shape — `working` and `idle` are already covered by the existing per-state output tests.
- M-1's `StopFailure` step is manual and may be hard to trigger on demand; note in the scenario that it can be exercised by forcing a rate limit, and that an inconclusive result should be recorded rather than silently passed.
