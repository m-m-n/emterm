## Design

### F1 (from finding sp-fr7-contradicts-impl, high) — amend FR7 to match reality

FR7 currently requires the path to be passed "as a single argv element through a no-shell
invocation" and forbids instructing the model to "interpolate the path into a shell command
string". Round 1 established that a Claude Code skill has no no-shell execution surface — the Bash
tool is the only way to invoke `emterm` — so the requirement as written can never be satisfied by
a correct implementation. The four display skills were therefore rewritten to a Bash-first form,
and `skills.test.ts` now pins that form.

Rewrite FR7 so the implemented design is the specified design:

- The single-quoted path placed after the `--` end-of-options delimiter is the REQUIRED form.
- The `'\''` escaping rule for embedded single quotes MUST be documented.
- A bare unquoted path MUST NOT appear as the canonical example.
- An argv-array invocation MAY be mentioned as an equally safe alternative where a caller has a
  no-shell exec path.

Then update the two places that repeat the old framing:

- **Security Considerations** — the bullet claiming FR7 "extends the argv-based invocation
  requirement from mux-send ... closing the last documented shell-string-interpolation path".
  That is doubly wrong now: the requirement is no longer argv-based, and mux-send itself still
  carries the old wording (task0006 fixes mux-send; this task must not claim it is already done).
- **TS-10** — "document argv-based invocation" must become the Bash-first wording.

Do not change the four display SKILL.md files here. They already implement the amended FR7;
task0006 extends them further.

### F2 (from finding sp-fr6-delete-vs-replace, medium) — resolve FR6's self-contradiction

FR6 says both `notify-status.ts` and `notify-status.test.ts` "MUST be deleted", while the File
structure section of the same SPEC annotates the test file as "replaced in place". The
implementation replaced it in place, which is the sensible outcome. Amend FR6 to require deleting
`notify-status.ts` and REPLACING the contents of `notify-status.test.ts`, so the normative
requirement and the file-structure section agree with each other and with the tree.

### F3 (from finding cm-readme-hook-drift, medium) — README wiring line

README's "What gets wired" still says three hooks with an unrestricted `Notification`. Update it
to name all five (`UserPromptSubmit` → working, `PostToolUse` → working, `Stop` → idle,
`StopFailure` → idle, `Notification` → blocked) and state that `Notification` fires only for
`permission_prompt` / `elicitation_dialog` / `agent_needs_input`, so an ordinary idle notification
cannot overwrite the `idle` that `Stop` just set.

Add a `skills.test.ts` assertion that ties this README text to the hooks.json event-key set, so
the two cannot drift apart again. That coupling is the point — the drift happened because README
was one task's scope and hooks.json was another's, with nothing spanning them.

### F4 (disclosure for sc-prose-escaping-fallible and cm-minversion-args-stopfailure)

Two round-2 findings resolve as disclosure rather than code change:

- **Prose-escaping residual risk.** Codex correctly observes that injection prevention rests on
  the model applying the quoting rule correctly, which is prose rather than an enforced
  serialization boundary. Its proposed remedy (mandate an argv-array execution path) is not
  implementable while Bash is the only surface. State the residual risk plainly in SPEC's Security
  Considerations and as a README known limitation, so the dependency is disclosed rather than
  implied.
- **Minimum-version basis.** The stated v2.1.141 floor derives from `terminalSequence` alone,
  while the plugin now also relies on the `args` exec form and the `StopFailure` event. A check of
  the hooks documentation found no min-version marker on either (13 such markers exist elsewhere
  on that page), so there is no evidence of a version window where `terminalSequence` works but
  `args` does not. Note in the README that the floor covers `terminalSequence` and that the exec
  form and `StopFailure` are assumed available at that version — do not invent a higher number.
