# Task Plan: task0009 — Hook wiring corrected to actual platform behaviour (rework)

## Goal

Stop claiming hook behaviour the platform does not provide. Remove the StopFailure entry whose output Claude Code discards, wire PostToolUseFailure so `blocked` also clears when a tool fails, and make README, SPEC, and both test files agree with the result.

## Requirements

## Design

Both findings come from the same root: hook events were wired from a reading of the documentation, without a live check. Two are wrong in opposite directions — one event cannot deliver, another does not fire when we assumed it would.

### F1 (from finding cm-stopfailure-noop, high) — remove the StopFailure entry

The hooks documentation states twice that StopFailure's "Output and exit code are ignored". `notify-status.sh` transports state exclusively through the `terminalSequence` field of its stdout JSON, so the entry added in round 2 is a no-op. When a turn ends on an API error the badge stays `working` until the next prompt, because `Stop` does not fire — StopFailure runs instead of it.

Remove the entry. The alternative — keeping it on the chance the documentation is wrong about this particular field — is what produced this finding in the first place: the task0003 plan flagged exactly this risk, deferred it to a live M-1 check, then shipped the wiring plus a README claim before that check ran. Do not repeat that; a claim the platform documents as impossible should not ship on the hope that it works.

Because M-1 will be executed shortly after this task, add a step there to observe what actually happens on an API-error turn ending. If that live run shows the sequence IS honoured, reinstating the entry is a small, evidence-backed follow-up. That ordering — remove now, reinstate on proof — is the opposite of what was done before and is the point of this task.

Record the resulting behaviour as a known limitation: a turn ending on an API error leaves the badge on `working` until the next prompt.

### F2 (from finding cm-posttooluse-failure-unwired, medium) — wire PostToolUseFailure

PostToolUse "Runs immediately after a tool completes successfully". Failures fire PostToolUseFailure; permission denials fire neither (PreToolUse only). Of the three outcomes after a permission prompt sets `blocked`, only approve-and-succeed currently recovers. Approve-then-fail is routine — any non-zero exit from a Bash call — and leaves the badge stuck.

Add a `PostToolUseFailure` entry with no matcher and args `["working"]`, matching the PostToolUse entry's shape and `timeout: 3`.

The permission-denied path has no event to hook, so it stays a known limitation alongside the existing `PostToolUse` precedence note.

### Resulting event map

| Event | Matcher | State |
|---|---|---|
| `UserPromptSubmit` | none | `working` |
| `PostToolUse` | none | `working` |
| `PostToolUseFailure` | none | `working` |
| `Stop` | none | `idle` |
| `Notification` | `^(permission_prompt\|elicitation_dialog\|agent_needs_input)$` | `blocked` |

Five entries again, but a different five. No `SubagentStop`, no `StopFailure`. All in exec form with `timeout: 3`.

### F3 — move every dependent claim in the same change

README's hook list, SPEC FR4's enumeration, TS-6 in both SPEC and VERIFICATION, the event-set assertion in `notify-status.test.ts`, and the README-to-hooks.json consistency assertion in `skills.test.ts` all encode the current five-event set. They must move together — that consistency assertion exists precisely to make a partial update fail, and it will.

VERIFICATION.md M-1 also needs updating: its step 4 asks the reader to observe recovery after approving a permission prompt, which should now also cover the approve-then-fail case; its step 5 currently exercises StopFailure as an informational check and should become an observation of the removed-entry behaviour instead.
