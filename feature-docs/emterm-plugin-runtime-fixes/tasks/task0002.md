# Task Plan: task0002 — Documentation and display-skill hardening

## Goal

Bring the plugin's user-facing documentation in line with the new transport (no `bun`, no `/dev/tty`, a Claude Code minimum version), and close the display-skill argument-injection gap that was deferred from the previous feature's review round 2.

## Requirements

FR7, FR8, FR9.

## Scope

### Files to Modify

- `plugins/emterm/README.md` — prerequisites and known limitations.
- `plugins/emterm/skills/display-markdown/SKILL.md` — argv-based invocation guidance.
- `plugins/emterm/skills/display-json/SKILL.md` — same.
- `plugins/emterm/skills/display-yaml/SKILL.md` — same.
- `plugins/emterm/skills/display-image/SKILL.md` — same.
- `plugins/emterm/skills/skills.test.ts` — extend the static scan to cover the new guidance (only if the existing assertions do not already cover it).

### Files to Create

None.

## Design

### README changes (FR8)

Five edits:

1. **Remove `bun` from prerequisites.** The hook is POSIX sh now; nothing in the plugin needs a Bun runtime.
2. **State the Claude Code minimum version.** The agent-status hook depends on the `terminalSequence` JSON output field, which requires Claude Code v2.1.141 or later. On older versions the field is ignored and no state is reported — harmless, but it must be documented.
3. **Narrow the `emterm` prerequisite.** `emterm` on `PATH` is now required only for the display and mux skills. The agent-status hook does not invoke it. Say so explicitly, because the previous wording implied the hook needed it.
4. **Drop two now-obsolete known limitations**: the "`/dev/tty` may not reach the eMterm PTY" caveat (that path is gone) and the "up to 3 s per prompt" caveat (there is no subprocess and no Bun cold start anymore).
5. **Keep the mux-agent-status-api drain-wiring caveat.** That limitation is unchanged by this feature.

Keep the existing tone: present tense, second person, no marketing language, code blocks for commands.

### Display-skill hardening (FR7)

The four display skills currently direct the model to substitute `<file>` into a shell-form command string. A contributor-controlled path such as `report.md; touch PWNED` would then execute the appended command. `mux-send/SKILL.md` already carries hardening for exactly this class of problem; **read it first and mirror its structure** rather than inventing a new format.

Each of the four skills gains:

- A required-safety section stating that the file path must be passed as a single argv element through a no-shell invocation, never interpolated into a shell command string.
- A statement that if a shell is unavoidable, the path must be shell-quoted and an end-of-options delimiter used where the command supports it.
- At least one adversarial example showing a path with shell metacharacters and contrasting the safe form (path arrives at `emterm` as literal data) with the unsafe form (shell executes the injected fragment).

The invocation contract itself does not change: each skill still calls the same `emterm markdown|json|yaml|image` subcommand, and `display-image` still documents `--protocol kitty|sixel`. These are additive guardrails.

### Version (FR9)

`marketplace.json` and `plugin.json` must keep `"version": "0.1.0"`. This task does not modify either file; the requirement is listed here so the acceptance criteria can assert it as a regression guard.

## Test Notes

- AC-6 through AC-8 are static content assertions; fold them into `skills.test.ts` alongside the existing scan rather than adding another test file.
- AC-9 is a two-line JSON parse assertion — cheap regression protection against an accidental version bump, which is the one thing this feature must not do.
- The README criteria (AC-1 to AC-5) are prose checks. Simple substring assertions in the test file are acceptable if they are robust to wording changes (assert on the distinctive token, e.g. `2.1.141`, rather than a whole sentence); otherwise leave them to review and the verify phase's manual read.
