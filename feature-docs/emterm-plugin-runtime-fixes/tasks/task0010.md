## Design

### F1 (from finding sc-stagefile-unspecified, high) — specify how the staging file is written

Round 4 made `emterm mux send --pane <id> --stdin < '<file>'` the required form for untrusted text, justified by "nothing derived from the text ever enters the command line". That holds for the send command and nothing else: the skill never says how the file gets written. Via the Bash tool, `cat > f <<'EOF' ... EOF`, `printf '%s' '<text>' > f`, or an interpolated variable redirect all put the whole untrusted blob back on a shell command line — and the heredoc route reproduces the round-3 delimiter-collision hole one step upstream, on a body that is arbitrary-length and arbitrary-byte rather than a single path. The skill's own text pushes toward that route: it forbids the shell-variable form, calls heredocs "never used for untrusted text in this skill" in a context readable as being about `--stdin` supply only, and never mentions the Write tool.

Require a non-shell write. The file MUST be created with the Write tool, which takes the content as a parameter and never constructs shell text. State explicitly that Bash-based creation — heredoc, `printf`, `echo`, or redirecting an interpolated variable — is forbidden for untrusted text. Narrow the "nothing derived from the text enters the command line" claim so it says what is true: it holds provided the file itself was written without a shell. Extend the adversarial example that rejects heredocs so it covers file creation, not only `--stdin` supply.

### F2 (from finding sc-redirect-path-unruled, medium) — put rules on the redirect path

The path in `--stdin < '<file>'` is the only shell-interpreted token in the form, and the skill merely observes that it is "the file path, which you chose". That is an assumption, not a requirement, and it breaks the moment a caller says "send the contents of ~/notes/draft.txt to pane 2". mux-send has neither of the rules the display skills adopted for this: no `'\''` splice rule for the redirect path (it covers `--text` only), and no resolve-`~`-first rule.

Make it a requirement: the redirect target MUST be a path the model chose itself — absolute, under a temp directory, no `~`, no bytes derived from untrusted input. If a caller-supplied path must be redirected instead, apply the display skills' rules verbatim: resolve `~` to an absolute path first, single-quote the whole path, splice embedded quotes as `'\''`.

### F3 (from finding sc-invariant-contradicts-escape, medium) — make the invariant include its own splice

The display skills state the invariant absolutely — "no byte derived from an untrusted path ever appears outside the single quotes" — while the `'\''` rule two bullets later places exactly such a byte outside them. A model handed a path containing a quote cannot satisfy both, and one available way out is double quotes, which the same file forbids because command substitution expands inside them. This is a contradiction in the rule, not imprecision in its expression.

Restate it so the splice is part of the invariant rather than an exception to it: every byte of the path is either inside a single-quoted span or is part of the fixed four-character `'\''` splice, and nothing else path-derived appears outside the quotes. Put the `~` bullet and the splice bullet adjacent so neither reads as contradicting the other in isolation. Apply to all four display skills and update the assertion that pins the old wording.

### F4 (from finding sc-consent-vs-invoke-as-is, medium) — stop the closing line cancelling the consent rule

mux-send now says the destination pane executes what it receives and that sending untrusted text to a shell pane needs the user's consent — then ends with the unconditional "Invoke the command as-is and report the result back to the user." A model takes the closing line as the operative instruction, so the consent requirement is decorative. The skill also never says how consent is obtained or what to do if refused.

Make the closing instruction conditional: when the text is untrusted and the destination pane is running a shell, show the user the exact bytes to be sent and get explicit approval before invoking. Say what happens on refusal. Add an assertion that the closing instruction is not the unconditional form — the current test only checks that the consent phrase appears somewhere.

### F5 (from findings cm-heredoc-guard-too-narrow and cm-matcher-test-missing-type, medium) — widen two guards to match their claims

The heredoc regression guard rejects the two characters that open a QUOTED delimiter while its comment claims it blocks any heredoc. An unquoted `cat <<EOF` passes, and is strictly more dangerous: besides the same delimiter-collision termination, it also expands command substitution, backticks, and parameter expansion in the body. Widen both assertions to reject the bare heredoc operator regardless of delimiter quoting, and align the comment. Prose that must mention heredocs should use the word, not the operator. mux-send currently contains neither form, so widening is safe.

The Notification matcher test says it evaluates "the seven notification-type names" but the documented namespace has eight; `agent_completed` is missing from the negative set. The current anchored matcher is unaffected, but loosening it to something like a prefix match would set `blocked` when a background agent COMPLETES — the opposite of a wait — with no test failing. Add `agent_completed`, fix the count, and note that the list tracks the documented types.

### F6 (from finding sp-text-example-unbalanced, medium) — fix the `--text` example

FR10 requires `--text` to follow the single-quote-plus-`'\''` rule, but the embedded-quote example shows the splice without its surrounding quotes, which is an unbalanced shell token. Show the complete value including outer quotes, ideally in the full command. Strengthen the TS-10 assertion to require the complete quoted form rather than the splice substring.

### F7 (from findings sp-sc4-bun-absolute, sp-nfr3-path-absolute, sp-verification-dollarparen-grep, medium) — retire three absolute claims in the SSOT

Three statements are true of no file in the tree:

Scope SC-4 to shipped artifacts (the script, `hooks.json`, the SKILL.md files, README) and state that the test files use Bun as a development-time tool.

Scope NFR3 to shipped config (`hooks.json`) and exempt development-time test files.
- **VERIFICATION.md's NFR2 note** credits TS-8 with a command-substitution check TS-8 does not contain, leaving one of NFR2's three prohibitions unguarded while the record says otherwise. Add the check to TS-8 and to the source-hygiene block so all three are mechanical.

## Verification before writing

Every form documented here must be run against the real `emterm` CLI before it goes into a file, under the CLI-safety constraints below. At minimum: the redirect form delivers the file's bytes unchanged; a file whose body contains a bare `EOF` line is delivered as data with nothing executed; a single-quoted path containing a spliced quote resolves to the intended file.

## CLI-safety constraints

`~/.claude/rules/process-termination.md` applies in full. `kill`, `pkill`, and `killall` are forbidden — no patterns, no `kill $(pgrep ...)`, no negative PIDs. Never kill an ancestor; the terminal emulator and `claude` itself are ancestors of you. Anything long-running goes through `run_in_background: true` and `TaskStop`. A process that seems hung is REPORTED, not tidied away.

Prefer invocations that cannot start the GUI: `markdown` / `json` / `yaml` / `image` write to stdout and exit. Do NOT run a bare `emterm`, and do NOT run `emterm --version` — a previous attempt found that `--version` launches the terminal GUI instead of printing a version and hanging around. Verifying `mux send` needs a live mux pane; if none is available, say so in the report and verify what you can (for example that the redirection delivers bytes byte-for-byte to a command that reads stdin) rather than starting a terminal to create one. Fixtures go under `/tmp/` and stay there.
