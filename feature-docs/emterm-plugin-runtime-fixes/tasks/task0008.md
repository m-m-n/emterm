### F1 (from finding sp-mux-send-unspecified, medium) — give mux-send a requirement

Nothing in the SSOT authorises mux-send's rework: no FR mentions it, the File structure section omits it, and TS-10 covers only the four display skills. Worse, Security Considerations still asserts "mux-send/SKILL.md still carries the argv-based primary MUST as of this task; that file is out of scope here (task0006)" — written truthfully by task0005 about a file task0006 then rewrote, and false ever since.

Add a functional requirement for mux-send covering what task0007 builds:

- The file-redirection form `emterm mux send --pane <id> --stdin < '<file>'` is the required form for text from an untrusted source, on the grounds that nothing derived from the text enters the command line.
- No heredoc form is documented (it fails on delimiter collision, and its mandatory trailing newline is an Enter in the destination pane).
- `--text` remains for short trusted strings under the single-quote plus `'\''` rule.
- Pane-ID validation is retained.
- Adversarial examples must describe the destination pane's actual behaviour, including that it executes what it receives.

Then: add `skills/mux-send/SKILL.md` to the File structure section, extend TS-10 from four skills to all seven, and rewrite the stale Security Considerations sentence to describe the post-rework state.

### F2 (from finding sp-fr7-missing-tilde-and-doublequote, medium) — close the FR7 gap

FR7's five MUSTs cover neither the `~` handling nor the double-quote warning that the display skills now carry, and the `~` form as built in round 3 actually deviated from FR7's pinned shape by putting part of the argument outside the single quotes. Tests enforce both additions, so the SPEC and the tests currently disagree.

task0007 removes the `~` exception rather than qualifying it: the model resolves `~` to an absolute path before quoting, and no byte derived from an untrusted path appears outside the single quotes. That restores FR7's single invariant, so FR7 needs:

- The resolve-before-quoting rule for `~`, stated as reinforcing the single-quote invariant rather than as an exception to it.
- The double-quote requirement: state that double quotes are not a substitute because `$(...)`, backticks, and `${...}` expand inside them, and require at least one adversarial example that discriminates on quote TYPE rather than quote presence.

Mirror both in TS-10.

### F3 (from finding sp-ts8-contradicts-fr3, medium) — make TS-8 satisfiable

TS-8 requires notify-status.sh to contain "no reference to … `emterm` …" while FR3 requires that same script to emit the literal `emterm;agent-status;`. The two cannot both hold; the test resolves it by stripping the payload before asserting, which verifies a different (and correct) claim. The task0001 implementer flagged this in its completion report and it was not acted on.

Reword TS-8 to the claim actually verified: no `/dev/tty`, `bun`, `eval`, or backticks, and no invocation of the `emterm` binary, with the FR3 payload literal as the sole permitted occurrence of the string. The test needs no change.

### F4 (from finding sp-fr3-raw-esc-byte, medium) — remove the raw control byte from FR3

FR3's closing sentence contains a literal 0x1B, so it reads "escape the two control bytes as <ESC>" — self-referential, and unsatisfiable as written since a raw control byte cannot appear in a JSON string. The implementation's choice has no clause backing it.

Replace with a control-byte-free statement: escape each ESC (0x1B) as the six characters `backslash u 0 0 1 b`, and the trailing backslash as a doubled backslash. Write the escape sequences as inline code spans containing only printable ASCII.

Then verify no raw control bytes remain anywhere in SPEC.md — `grep -P '[\x00-\x08\x0b-\x1f]' SPEC.md` must return nothing. Note the same trap caught the round-3 review record itself, which became unparseable YAML for exactly this reason; check VERIFICATION.md too while you are there.

### F5 — record the PostToolUse precedence gap

task0007 adds a README known-limitation line for `cm-posttooluse-overwrites-blocked` (an unmatched `PostToolUse` can clear `blocked` while a permission dialog is still open). Record the SPEC side: state the intended precedence in FR4 or the Edge Cases section as a known deviation, note that the proper fix is a precedence rule in eMterm's agent-status (out of scope — `src-tauri/`), and add a VERIFICATION.md note that no test covers state-transition ordering today.
