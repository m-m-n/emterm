## Design

### F3 (from finding sc-display-hardening-wrong-path, medium ×2 perspectives) — Bash-first safe form

The current hardening section makes "pass the path as a single argv element through a no-shell invocation (e.g. `Bun.spawn` array form)" the primary MUST. A Claude Code skill can only reach `emterm` through the Bash tool, which always goes through a shell — so the primary MUST names a path that does not exist here, and only the hedged "If a shell is unavoidable" fallback is ever in force. Meanwhile the canonical usage example at the top of each file still shows the bare unsafe form.

Restructure each of the four files so the shell-safe form is the norm:

1. **Replace the top-of-file canonical example** with the safe form. The path goes in single quotes, after an end-of-options `--`, with any options before the `--`:
   - `display-markdown` → `emterm markdown -- '<path>'`
   - `display-json` → `emterm json -- '<path>'`
   - `display-yaml` → `emterm yaml -- '<path>'`
   - `display-image` → `emterm image --protocol kitty -- '<path>'` (and the `--protocol` documentation stays, with the option before the `--`)
2. **Make the quoted-and-delimited form the primary MUST**: always single-quote the path and place it after `--`; never embed a bare path in the command line. State the `'\''` escaping rule for paths containing a single quote.
3. **Drop the "where the command supports it" hedge** on `--`. eMterm's CLI is clap-based and accepts `--` on these subcommands; this was verified during review (`emterm markdown -- '/tmp/poc; touch PWNED.md'` exits 0 and creates no `PWNED` file).
4. **Demote the argv-array wording** to a short note for callers that do have a no-shell exec path.
5. **Rewrite the adversarial example** so its "safe" side is a command the model can copy verbatim, e.g. contrasting `emterm markdown -- 'report.md; touch PWNED'` (path arrives as literal data) with the unquoted form (shell executes the injected fragment).

`mux-send/SKILL.md` already does this correctly — it gives a copy-pastable shell-safe form. Read it and keep the four display skills symmetric with it.

The invocation contract is unchanged: same subcommands, and `display-image` still documents `--protocol kitty|sixel`.

### F4 (from finding cm-wire-drift-undetected, medium) — make the SPEC claim true

`canonicalSequence()` in `notify-status.test.ts` hardcodes the expected sequence, and its own comment says the literal is pinned by SPEC.md rather than derived at test time. But SPEC.md's "Wire-format duplication" paragraph claims a Rust-side format change that is not mirrored here "shows up as a failing test rather than silent drift". That is false today: bumping `WIRE_VERSION` or changing `PAYLOAD_PREFIX` in `src-tauri/src/agent_status.rs` would leave this test green while the hook emits an obsolete sequence.

Make the claim true. In `notify-status.test.ts`, read `src-tauri/src/agent_status.rs` and extract the four constants that define the format — `OSC_INTRODUCER`, `PAYLOAD_PREFIX`, `WIRE_VERSION`, `ST` — then build the expected sequence from them instead of from a hardcoded literal. This is read-only access to `src-tauri/`, so it does not violate the no-source-changes constraint.

Contract for the extraction: it must fail loudly (a failing test, not a skip and not a fallback to the old literal) if any of the four constants cannot be found. A silent fallback would reproduce exactly the blind spot being fixed.

Keep the name handling in mind: the Rust builder percent-encodes `name`, but `claude-code` is entirely URI-unreserved so the encoding is the identity. The derived expectation may treat `name=claude-code` as a literal; note why in a comment so a future reader does not mistake it for an oversight.

If the extraction proves impractical, the fallback is to correct SPEC.md's "Wire-format duplication" paragraph to state plainly that drift is not automatically detected and must be synced by hand. Do not leave the false claim standing either way.

### SPEC.md update

Whichever route F4 takes, the "Wire-format duplication" paragraph must end up describing what the tests actually do.
