# Task Plan: task0001 — Detach releases the mux group's agent-status state

## Goal

A tab that leaves mux mode through a daemon-confirmed detach releases the
departing connection's agent-status entries, scoped public-pane-id mappings
and notification rate-limit state, so a later attach on the same tab shows
only the new connection — and the connection-scope documentation describes
the lifetime the code actually provides.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None. This task modifies existing files only.

### Files to Modify

- `src-tauri/src/tabs/mux_link.rs` — the daemon-confirmed detach handler queues the departing group's wire pane ids onto the closed-pane latch before the group is cleared; every other step of that handler, and the pane-exit handler, are left as they are
- `src-tauri/src/agent_status_model.rs` — the connection-scope doc comment is corrected to describe the implemented lifetime; no type, field or behaviour changes
- `src-tauri/src/tabs/tests/mux_link.rs` — tab-layer scenarios for the drain after a detach frame and for the pane-exit sequence that empties the group
- `src-tauri/src/app/tests/agent_status.rs` — application-level scenarios for the detach teardown, the re-attach, the surviving plain-tab entry and the two-tab isolation case

## Design

IMPLEMENTATION.md owns the cross-cutting decisions this task implements (D1
through D6) and the contracts of the closed-pane latch, the closed-panes
teardown and the connection scope value. This section states only what is
specific to carrying them out.

### Behavioural change

One behavioural change is made, at one site: the daemon-confirmed detach
handler in the tab layer. Before it drops the window group, it reads the wire
pane ids that group holds and pushes each onto the tab's closed-pane latch.
The rest of that handler — clearing the group and session name, resetting the
frame extractor, superseding any pending replay, resetting the displayed
frame — keeps its current order and content.

Nothing in the App layer changes. The drain, the tagging with the owning
tab's stable id, the ordering of rate-limit resolution against mapping
removal, and the three removals are all reached unchanged; discovering that
they need modification is a plan deviation to report, not a licence to edit
them.

### Documentation change

The connection-scope doc comment currently claims the scope is constant for
the tab's whole lifetime "including across detach and re-attach", which reads
as a promise that the entries it keys survive that transition. It is
rewritten to state both true facts: the scope VALUE is constant for a given
tab, and the entries it keys are released when the tab leaves mux mode and
re-minted on the next attach.

### Properties the tests must pin

1. The detach handler's queueing happens while the group is still reachable —
   asserted indirectly by the drain returning the group's ids.
2. The drain is single-shot: a second drain in the same pump returns nothing.
3. The teardown reaches all three stores for each discarded pane: the model
   entry, the scoped public-pane-id mapping and the notification rate-limit
   identity.
4. The teardown reaches mux-pane keys only: the tab's own plain-tab entry and
   its inferred-clear latch keep reporting.
5. The teardown is confined to the detaching tab's scope: a second tab whose
   group holds the same wire pane id is untouched.
6. The pane-exit path still yields each removed pane id exactly once.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Applying a daemon-confirmed detach frame to a tab that holds a
      seeded mux group makes the tab's closed-agent-status-pane drain return
      exactly that group's wire pane ids; an immediately following second
      drain returns an empty list. (SPEC AC-1; TS-5)
- [ ] AC-2: A pane-exit sequence that removes every window of a group yields
      each removed wire pane id exactly once from the drain — the detach-side
      queueing does not add a second copy of an id the pane-exit path already
      queued. (SPEC AC-1; TS-6)
- [ ] AC-3: After a mux-attached tab has reported a pane state and learned
      that pane's public id, delivering a detach frame through the
      application's mux-message entry point and pumping once leaves the tab's
      aggregated badge reporting nothing for that pane, leaves the
      public-pane-id lookup for (that tab's scope, that wire pane id)
      returning nothing, and releases the pane's notification rate-limit
      identity so a later report of the same public id is not suppressed by
      the previous connection's record. (SPEC AC-1, AC-3; TS-1)
- [ ] AC-4: After that detach, a fresh attach on the SAME tab that reuses the
      same wire pane id leaves both the tab's aggregated badge and the
      per-pane badge reporting nothing — no state and no agent name from the
      previous connection — until the new connection's first status update
      arrives. (SPEC AC-2; TS-2)
- [ ] AC-5: A detach on a tab whose own plain-tab key holds a state leaves
      that entry reporting its state after the pump, and leaves the per-tab
      inferred-clear latch intact. (SPEC AC-4; TS-3)
- [ ] AC-6: With two tabs whose groups both hold wire pane id 1, detaching
      the first leaves the second tab's model entry, its public-pane-id
      mapping and its derived notification rate-limit key unchanged. (SPEC
      AC-5; TS-4)
- [ ] AC-7: The connection-scope doc comment no longer claims that the
      entries it keys survive detach and re-attach; it states that the scope
      value is constant for the tab while those entries are released at
      detach and re-minted on the next attach. (SPEC AC-6)

## Test Notes

- **All seven criteria are unit-testable** against the existing in-crate test
  fixtures; no integration harness and no new test file are needed. Write the
  tests first: each criterion above is red before the one-site behavioural
  change and green after it, except AC-2 (green before and after — it is a
  guard against the change introducing a double push) and AC-7 (a
  documentation assertion, verified by reading the corrected comment, with no
  test of its own).
- **AC-1 / AC-2 are tab-layer tests**: construct a tab, seed a group through
  the existing attach-message fixture, apply the frame under test, and assert
  on the drain. Mirror the shape of the existing pane-exit drain assertion in
  the same file rather than inventing a new fixture style.
- **AC-3 through AC-6 are application-level tests**: build an app with a mux
  group using the direct group-seeding construction already used by the
  scoping tests in the same file, deliver messages through the app's
  mux-message entry point, and pump. For the re-attach half of AC-4, build
  the attach message locally in this test module in the same shape as the
  attach fixture used by the mux-overlay tests; do not widen another test
  module's private helper to reach it.
- **AC-3's rate-limit half** is the subtle one: assert on the identity that
  is released, not merely that some map shrank. Resolve the pane's rate-limit
  key before the detach, then assert the record for that key is gone after
  the pump. This is the assertion that catches a reordering of resolution
  against mapping removal.
- **Edge cases worth explicit coverage** inside the scenarios above: a
  detached pane that never received a status update (no learned public id —
  the release must be a safe no-op); a detach on a background, non-active
  tab (the pump drains every tab's latch, so teardown must still run); and a
  group holding several windows (every pane is released, not only the active
  one).
- **Determinism**: this project's `--lib` suite is run single-threaded by the
  configured test command because some replay tests are order-sensitive.
  Write these scenarios so they pass under that command; do not rely on any
  cross-test ordering.
- **Nothing TDD-awkward** remains except AC-7, handled as noted above.

## Out of Scope

- Any attach-generation counter or other change to how the connection scope
  value is derived (IMPLEMENTATION.md D3).
- Any edit to the App-layer drain, the batch apply's closed-panes arm, the
  tab-close path or the reaped-tab loop. They already satisfy the release
  obligation; needing to change them is a plan deviation to report.
- Any change to the mux wire protocol crate, to daemon behaviour, or to
  user-visible settings.
- Any change to the render or UI layer. The badge and sidebar are expected to
  show less, purely as a consequence of the state release.
- Refactoring the pane-exit handler to share a code path with the detach
  handler (IMPLEMENTATION.md D5) — it would double-push the removed pane ids.
- Performance work. The release reuses the pump's existing traversal and adds
  no new one.
