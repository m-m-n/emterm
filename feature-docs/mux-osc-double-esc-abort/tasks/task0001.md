# Task Plan: task0001 — Mux feed scanner: cut rule, unit tests and the mux half of the parity corpus

## Goal

The mux daemon's `AgentStatusFeedScanner` ends an OSC string as term_core does
when an in-body `ESC` is followed by a byte other than `\`, so that for the
same bytes a mux pane ends in the same OSC 7501 table, OSC 777 state and OSC
133 D→A inferred-clear result as a plain tab. Regression tests pin the rule at
the scanner and through the real reader and daemon task.

## Design

### Reference behavior

term_core's OSC escape state (`crates/term_core/src/parser/osc.rs`, read only)
is the reference: after an in-body `ESC`, `\` dispatches the string as ST;
any other byte dispatches it as unterminated and is then processed as the
byte after an `ESC`. The plain-tab callbacks drop an unterminated OSC 7501 and
apply an unterminated OSC 777 / OSC 133 (SPEC A5). See IMPLEMENTATION.md D1.

### Scanner contract (unchanged interface)

- The scanner's constructor, its per-read feed operation (a read chunk plus
  that read's live spans in, the items found in byte order out) and its
  test-only retained-length query keep their signatures.
- The item type and the program-status terminator type keep their shapes. A
  cut string never produces an OSC 7501 item, so no "unterminated" terminator
  value is needed and the daemon task needs no change.

### Handling the byte after an in-body ESC

| Byte | Behavior |
|---|---|
| `\` | Completes the string as ST — unchanged, including the live-span check at the `\` for an OSC 133 mark. |
| Any other byte | 1. Cut the string (below). 2. Handle the byte as the byte after an `ESC`: `ESC` → wait for the next escape byte; `]` → start a new OSC with an empty body; any other byte → idle. The Reset of `ESC c` still comes from the existing RIS tracking, unchanged. |

Cutting a string classifies its body with the existing recognition order:

1. Body starts with the canonical `777;emterm;agent-status;` prefix → the same Report item its BEL / ST form gives (canonical-only stays).
2. Otherwise the shared recognition rule's number decides: 7501 → no item (no record change, no broadcast, no revision move, no answer); 133 → the existing OSC 133 classification (canonical kind → mark item; shared-rule prompt start → prompt-start-only item, which never reaches the OSC 777 latch; other kinds → nothing), emitted only when the string-end liveness (below) is live; anything else → no item.
3. The body is cleared in every case (retained length 0).

### Ordering (FR5)

For the byte that cuts a string, the cut item comes before every item that
byte or any later byte produces — the Reset of `ESC c` included. The scanner
currently advances its RIS tracking ahead of its OSC decode state for each
byte; the cut item must still be appended first.

### String-end liveness (FR4, FR6)

- A cut OSC 133 string is live when the last byte the string itself consumed
  before its in-body `ESC` (the last body byte; the introducer `]` for an
  empty body) lay inside one of the live spans passed with the read that
  carried that byte. The in-body `ESC` and the cutting byte do not decide it:
  when that `ESC` starts a switch to the alternate screen, the live spans
  exclude it, yet the mark is a main-screen mark (SPEC A6, corpus row K15).
- The liveness is kept as O(1) scanner state recorded while the string's bytes
  arrive, so the in-body `ESC` and the cutting byte may arrive in later reads.
  It is never derived by looking back from the cutting byte's position (a read
  can begin with the in-body `ESC` or the cutting byte — TM-3).
- BEL / ST completion keeps judging liveness at its completing byte (FR8).

### Unchanged (FR8)

BEL and `ESC \` completion, the received-length / 4096-byte rule, the 8 KiB
carry bound and its one-shot warning, the RIS tracking, the canonical-only
OSC 777 agent-status rule, the shared recognition rule, the main-buffer span
extraction and the reader's call into the scanner.

### Threat-model mitigations carried by this task

- TM-1: a cut OSC 7501 string yields no item (AC-1, AC-2, AC-6).
- TM-2: a cut OSC 133 string yields an item only when the string's own last byte was live; alternate-screen strings yield nothing (AC-3, AC-5, AC-6).
- TM-3: O(1) forward-recorded state, body cleared on every cut, carry bound kept, no panic (AC-1, AC-5).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1; TM-1, TM-3): After an in-body `ESC`, `\` completes the string as ST exactly as before, and every other byte ends the string unterminated and is then handled as the byte after an `ESC`: `ESC ] 0;t ESC ESC ] 133;A BEL` yields the live PromptStart mark, `ESC ] 0;t ESC ] 133;A BEL` yields the live PromptStart mark, `ESC ] 0;t ESC c` yields exactly one Reset, and `ESC ] 0;t ESC x ] 133;A BEL` yields nothing. The scanner's retained length is 0 right after every cut.
- [ ] AC-2 (FR2, FR3; TM-1): For each cut form — `ESC ESC \`, `ESC [0m`, `ESC ] 0;t BEL` (a new OSC that yields nothing) and `ESC c` — a cut OSC 7501 string spelled `7501;state=clear`, `07501;state=clear`, `x7501;:state=clear` or `7501` yields no OSC 7501 item; a cut string starting with `777;emterm;agent-status;v=1;state=working` yields exactly one Report equal to the one its BEL form yields; a cut `0777;emterm;agent-status;v=1;state=working` or other OSC 777 body yields no Report. The `ESC c` form additionally yields its one Reset.
- [ ] AC-3 (FR4; TM-2): A cut OSC 133 string is classified as its BEL form is — `133;A` / `133;D` give the mark of that kind, `0133;A` gives only the prompt-start-only item, `133;E` and `0133;B` give nothing — and yields its item only when the string's own last byte lay in a live span. With live spans taken from the main-buffer span extraction of the stream, a cut string on the alternate screen yields nothing and `ESC ] 133;A ESC [?1049h` yields the main-screen PromptStart mark. For each canonical `133;A` case — main screen, alternate screen, and the `ESC [?1049h` cut — the scanner yields a mark item exactly when term_core records a prompt mark for the same bytes.
- [ ] AC-4 (FR5): The items of a cut string come before every item of the cutting byte and later bytes: `ESC ] 777;emterm;agent-status;v=1;state=working ESC c` yields the Report then the Reset; `ESC ] 133;A ESC ] 7501;state=error BEL` yields the PromptStart mark then the `state=error` OSC 7501 item; `ESC ] 7501;state=error ESC ESC ] 7501;state=clear BEL` yields only the `state=clear` OSC 7501 item.
- [ ] AC-5 (FR6, NFR1; TM-2, TM-3): For one stream holding every case of AC-1 to AC-4 (alternate-screen cases included), with each byte's liveness fixed by the whole stream's live spans, splitting the stream into two feeds at every single offset and feeding it one byte at a time yield the same items as one feed. A cut OSC 133 string whose last body byte, in-body `ESC` and cutting byte arrive in three separate feeds yields its mark when only the first feed marks that byte live, and yields nothing when only the later feeds mark their bytes live. A stream of at least 1 MiB made of repeated cut strings (OSC 7501, OSC 777 and OSC 133, every cut form) finishes within 2 seconds in the test build without panic, and the retained length never exceeds the 8 KiB carry bound.
- [ ] AC-6 (FR7, FR9; TM-1, TM-2): Through the real `pty_reader_loop` and the daemon agent-status task, every row K1–K15 of the IMPLEMENTATION.md SC-1 corpus, fed with the row's seed and every delivery the row names, ends in the row's final OSC 7501 table and final OSC 777 state; K1–K4 cause no `AgentStatusUpdate` broadcast and leave the revision unchanged; K5 causes exactly one broadcast and one revision step.
- [ ] AC-7 (FR8, NFR2, NFR3, NFR4, NFR5): Every existing test passes with its assertions unchanged — among them the program_status_feed module (the term_core RIS oracle test included), the daemon leading_zero_length module and the designator-slot scanner tests. `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path src-tauri/Cargo.toml --no-default-features` succeeds. The diff adds no log call on a cut, discard or reject path, no platform-gated code, and no change under `crates/term_core/`.

## Test Notes

- AC-1 to AC-5 are scanner unit tests in the program_status_feed module, next
  to the existing feed tests and their helpers (the whole-chunk-live feed, the
  OSC builders). Write them first; the cut 7501 `ESC ESC \` case, the `ESC [0m`
  777 / 133 cases, AC-4's Report-then-Reset order and K15's mark are red on the
  current code.
- AC-3's term_core comparison follows the existing designator-slot mark test:
  feed the same bytes to a fresh term_core and compare its recorded prompt
  marks with the scanner's mark items, using the span extraction over the
  whole stream for the scanner.
- AC-5's fixed liveness: compute the live spans once over the unsplit stream,
  then hand each piece the part of those spans that falls inside it, rebased to
  the piece. The three-feed case sets the spans by hand. This pins the
  scanner's own carry; the reader's span derivation is covered by AC-6.
- AC-5's time bound mirrors the existing 2-second robustness tests; build the
  1 MiB input by repetition, not by hand.
- AC-6 extends the daemon leading_zero_length module: its drive helper feeds
  one read through a cursor, so split deliveries need a test-local reader that
  hands out one chunk per read (the pattern already exists as private copies
  in the pane and IPC handler test modules). Seeds S-W and S-ALL map onto the
  module's existing seed helpers; S-0 is the empty seed. The corpus rows are
  data in the test, one row per SC-1 entry, so a failure names the row.
- K14 / K15 cut-point deliveries are exactly the offsets SC-1 names; do not
  split inside the enter switch of K14 (IMPLEMENTATION.md Open Questions).
- The existing daemon test that keeps a non-canonical prompt start away from
  the OSC 777 latch stays as it is; it is not a parity row (IMPLEMENTATION.md
  SC-1, last paragraph).
- AC-7: run both full `--lib` suites and the `--no-default-features` check.
  `tabs` replay tests can fail nondeterministically in parallel; rerun a
  failing one with a single test thread before treating it as a failure.
