# Task Plan: task0001 — Injectable timer tick source and deterministic timer tests

## Goal

The status-bar TimeProvider timer loop gets its ticks from a replaceable tick
source. The three timer tests and a new delayed-tick regression test drive
ticks manually and assert exact counts without depending on real time. The
production timer path behaves exactly as before.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4

## Design

All shared contracts — tick source, production source, manual
source/controller, shared helper, manual constructor, runtime internal
constructor and builder — are pinned in IMPLEMENTATION.md "Shared
Components". Decisions D2–D5 there apply. This section covers only how this
task applies them.

### Timer loop flow (both sources)

1. While stop is not set: ask the tick source for the next tick outcome.
2. On *Stop*, or if the stop flag is set after the outcome returns: leave the
   loop without bumping or waking.
3. Otherwise bump `version` by one, then call `wake()`.
4. Tell the tick source *tick done*, then repeat from 1.

### Drop flow

1. Set the stop flag.
2. Notify-all on the provider's existing pair (unchanged).
3. *Interrupt* the tick source (IMPLEMENTATION.md D3).
4. Take the join handle, if any, and join the timer thread (unchanged).

### Test behaviours

- **`time_provider_timer_thread_calls_wake_on_interval`** (FR5): manual
  source, counting `WakeFn`. The wake count is 0 before any delivery. The
  test delivers N ticks one at a time: hold one, then the shared helper with
  n = 1 and the updated baselines. At the end the wake count equals N
  exactly.
- **`time_provider_timer_thread_bumps_version_per_tick_without_get_value`**
  (FR6): manual source. The test records v0 without calling `get_value`,
  delivers N ticks through the shared helper, and checks that the version
  equals v0 + N exactly. `get_value` is never called.
- **New drop-while-parked test** (FR4): manual source. The test waits until
  the timer thread is parked and keeps its own handle to the provider's
  version counter. After drop returns, the controller reports *closed*, and
  the wake count and version are unchanged. A tick held and released after
  the drop reports zero completed, returns without blocking, and causes no
  wake or version bump.
- **New delayed-tick regression test** (FR8): IMPLEMENTATION.md D4. The test
  waits until the timer thread is parked, holds N ticks, and checks
  immediately (no sleep) that the wake count is 0 and the version is
  unchanged. It then calls the shared helper with n = N. Its doc comment
  states the regression property: replacing the helper's handshake with a
  fixed real-time window makes this test fail.
- **`runtime_time_provider_timer_fires_wake`** (FR7): builds the runtime
  through the test-only builder with a counting `WakeFn`, a cwd source that
  returns none, no custom commands, and a long `git_branch` interval. It
  delivers N ticks through the shared helper, using the runtime's
  TimeProvider version as the version reader, and checks that the wake count
  equals N exactly. The rewritten comment drops the claim that the git-branch
  worker fires an initial wake when the cwd source returns none. It states
  that the git worker's cache clear wakes only when a branch or status was
  cached before.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The timer loop gets its ticks from the tick source contract.
  `TimeProvider::with_wake` and `StatusBarRuntime::new` use the production
  source. That source does one timed wait for `RefreshConfig.interval` on the
  provider's existing pair per tick, and every tick bumps `version` before
  calling `wake()`. The signatures of `TimeProvider::new`,
  `TimeProvider::with_wake`, `TimeProvider::set_format`, `RefreshConfig` and
  `StatusBarRuntime::new` are unchanged, and no added item is `pub` (only
  `pub(crate)` or `cfg(test)`). (FR1, FR2, NFR4)
- [ ] AC-2: With the manual source, before any delivery the wake count is 0
  and the version is unchanged. As soon as the controller's *release and
  wait* returns for k released ticks, the wake count and the version have
  each advanced by exactly k. (FR3)
- [ ] AC-3: Dropping a provider whose timer thread is parked in the manual
  source returns. The controller then reports *closed*, and the wake count
  and the retained version counter are unchanged. A tick released after the
  drop reports zero completed, does not block, and causes no wake or version
  bump. (FR4)
- [ ] AC-4: `time_provider_timer_thread_calls_wake_on_interval` and
  `time_provider_timer_thread_bumps_version_per_tick_without_get_value` keep
  their names, drive ticks through the manual source and the shared helper,
  and assert exact equality: wake count = N, version = v0 + N. Neither
  contains a thread sleep or a fixed real-time window, and the second never
  calls `get_value`. (FR5, FR6, NFR2)
- [ ] AC-5: `runtime_time_provider_timer_fires_wake` builds the runtime
  through the test-only builder, which shares the production `WakeFn` wiring
  of `StatusBarRuntime::new` and swaps only the time tick source. The test
  asserts wake count = N exactly after N ticks through the shared helper and
  contains no thread sleep. Its comment no longer says the git-branch worker
  fires an initial wake when the cwd source returns none. (FR7, NFR2)
- [ ] AC-6: A new delayed-tick regression test in providers/time.rs holds N
  ticks while the timer thread is parked and asserts that wake and version
  are unchanged, with no sleep. It then passes through the same shared helper
  used by AC-4 and AC-5. Its progress depends only on the helper's *release
  and wait* handshake (IMPLEMENTATION.md D4). (FR8, NFR2)
- [ ] AC-7: Every other status_bar test passes with its assertions
  unchanged, including `time_provider_drop_joins_timer_thread`,
  `time_provider_version_is_pure_load`,
  `time_provider_without_timer_does_not_spawn_thread` and
  `provider_set_format_bumps_version`. The two `cargo check` runs (default
  features and `--no-default-features`) succeed with no new warnings from
  the two modified files. `src-tauri/Cargo.toml` and `Cargo.lock` are
  unchanged, and the status_bar tests pass repeatedly both in parallel and
  with `--test-threads=1`. (FR2, NFR1, NFR3, NFR2)

## Test Notes

- TDD order: write the drop-while-parked test, the regression test and the
  three rewrites against the contract first. They fail to compile until the
  seam exists. Then build the seam until they pass.
- AC-2 and AC-3 map to the new time.rs unit tests. AC-4 and AC-6 are the
  tests themselves. AC-5 is the runtime-level test. AC-1 and AC-7 are checked
  by the existing tests passing unchanged, the two `cargo check` runs, and
  diff inspection.
- Awkward to test: a handshake defect shows up as a hang, not as a failure.
  Run tests with the Bash tool's `timeout` parameter. Do not add a deadline
  or a timeout to the handshake (NFR2).
- AC-6's "fails under a fixed real-time window" property is checked once by
  a temporary change during the verify phase (VERIFICATION.md TS-4). The
  implementer does not commit any such change.
- Before relying on exact counts in AC-5, confirm by reading the git-branch
  and cwd providers that neither wakes in the FR7 setup. If one does, report
  it as a plan deviation. Do not loosen the assertion to a lower bound.
- Run tests from the project root with `CARGO_TARGET_DIR=src-tauri/target`
  and `--manifest-path src-tauri/Cargo.toml --lib`. The tests live in the
  library target.
