# Task Plan: task0001 — Reject unknown top-level flags and add `--help`

## Goal

`emterm` rejects any unrecognized `-`-leading top-level argument with a usage
message on stderr and exit code 2, and prints its usage on stdout with exit 0
when given `--help` or `-h`, on both the default (`gui`) and
`--no-default-features` builds.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3

## Scope

### Files to Create
- `src-tauri/src/arg_dispatch.rs` — the argument classifier, the
  recognized-flag table, the usage text, and their unit tests.

### Files to Modify
- `src-tauri/src/lib.rs` — declare the new module in the roster, outside the
  `#[cfg(feature = "gui")]` block so it exists in both builds.
- `src-tauri/src/main.rs` — call the classifier after the bare-word subcommand
  dispatch and before `logging::init()`; perform the stdout / stderr / exit
  side effects; make `run_gui`'s flag branches agree with the recognized-flag
  table; replace the CLI-only fallthrough message with the shared usage text.

## Design

See IMPLEMENTATION.md for the cross-task contracts (Shared Components) and
decisions D1–D5. This task implements all of them; nothing is deferred.

**Classification flow** (operating on the argument list excluding the program
name, reached only when the bare-word subcommand match declined):

1. Scan the arguments left to right.
2. If the current argument is the long or short help flag, the outcome is
   *help requested* — this wins regardless of anything already seen (D3).
3. If the current argument is a recognized value-taking flag, skip the next
   argument without evaluating it and continue (D4).
4. If the current argument is a recognized valueless flag, continue.
5. If the current argument begins with a dash and none of the above matched,
   remember it as the candidate unrecognized argument if no candidate has been
   remembered yet, and continue scanning (so that a later help flag can still
   win).
6. Otherwise continue.
7. After the scan: *help requested* if a help flag was seen; otherwise
   *unrecognized argument* carrying the remembered candidate if there is one;
   otherwise *proceed*.

**Binary side effects** (in `main`, per D1):

- *help requested* → write the usage text to stdout, exit 0.
- *unrecognized argument* → write one line naming the argument verbatim, then
  the usage text, both to stderr; exit 2.
- *proceed* → continue into the existing path unchanged (`logging::init()`,
  then `run_gui` on the `gui` build, or the CLI-only fallthrough).

**CLI-only fallthrough**: the existing message at the end of `main` for the
non-`gui` build is replaced by the shared usage text on stderr with exit 2, so
that a single usage string serves all three sites (help, unknown flag,
CLI-only fallthrough) and FR4's guidance line is not duplicated.

**Drift guard** (D2, NFR3): the recognized-flag table is the only definition of
which flags exist. `run_gui`'s existing branches must be expressed in terms of
that table — or, if they stay as literal comparisons, a test must assert that
the table's contents and `run_gui`'s accepted flags are the same set, and fail
when one changes without the other.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Classifying an argument list containing only `--help`, or only
      `-h`, yields the *help requested* outcome; `main` writes the usage to
      stdout and exits 0.
- [ ] AC-2: Classifying `--typo` yields *unrecognized argument* carrying
      `--typo`; `main` writes an error line naming `--typo` plus the usage to
      stderr, writes nothing to stdout, and exits 2.
- [ ] AC-3: Classifying an empty argument list yields *proceed*; `emterm` with
      no arguments still reaches the existing GUI startup path.
- [ ] AC-4: On the `gui` build, each of `--viewer <path>`, `--image-viewer
      <path>`, `--data-viewer <path>`, `--html-viewer <path>` and `--settings`
      yields *proceed*, and a value beginning with a dash (e.g. `--viewer
      --weird`) still yields *proceed*.
- [ ] AC-5: An argument list containing both an unrecognized flag and a help
      flag, in either order, yields *help requested*; an argument list with two
      unrecognized flags reports the left-most one.
- [ ] AC-6: `-` alone and `--` alone each yield *unrecognized argument*.
- [ ] AC-7: On the `--no-default-features` build, `--settings` yields
      *unrecognized argument*, and the CLI-only fallthrough prints the same
      usage text to stderr with exit 2.
- [ ] AC-8: The recognized-flag table and `run_gui`'s accepted flags are the
      same set, asserted by a test that fails if either side changes alone.
- [ ] AC-9: `CARGO_TARGET_DIR=src-tauri/target cargo check --manifest-path
      src-tauri/Cargo.toml` and the same command with `--no-default-features`
      both succeed, and `src-tauri/tests/cli_subcommands.rs` passes unchanged.

## Test Notes

- AC-1 through AC-8 are unit tests on the classifier and the flag table, in the
  library crate, reached by `cargo test --lib`. Write them first.
- The feature-dependent criteria (AC-4, AC-7) need tests that compile under the
  respective configuration — gate the `gui`-only assertions and the CLI-only
  assertion on the `gui` feature so both `cargo test --lib` and `cargo test
  --lib --no-default-features` are meaningful.
- The `main`-side behavior (which stream, which exit code) is not reachable
  from the test harness because the binary target has no tests. Keep `main`'s
  branch arms trivial enough that reading them verifies the mapping, and cover
  the decision itself through the classifier tests.
- AC-9 is a build/regression check, not a new test.

## Out of Scope

- Implementing `--version` — owned by the separate `version-flag` feature
  (SPEC.md Assumption A2). Do not add it to the recognized-flag table.
- Validating arguments that bare-word subcommands parse themselves, including
  anything after `emterm mux`.
- Treating non-dash stray arguments (e.g. `emterm foo`) as errors.
- Introducing an argument-parsing dependency.
