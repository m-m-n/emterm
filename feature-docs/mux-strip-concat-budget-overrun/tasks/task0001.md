# Task Plan: task0001 — Measure the target test's cost and bring it within its budget

## Goal

Find, by measurement, which entry and which shape dominate the thread CPU time of
`strip_concat_alternations_and_chains_finish_within_the_budget` (the target test)
and whether that cost is linear, record the result, and make the target test pass
on a debug build with a measured total of 5 s or less: by shrinking the test's own
workload when the cost is linear, or by fixing the non-linear production path when
it is not.

## Requirements

FR1, FR2, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `src-tauri/src/mux/ipc/pty_spawn/tests/strip_concat_query.rs` — the target test: its input sizes, its cap assertions, its verdict output, its doc comment and the FR1 record
- `src-tauri/src/mux/scrollback_filter.rs` — non-linear verdict only: the non-linear path of the strip pass, with byte-identical output
- `src-tauri/src/mux/ipc/pty_spawn/write_filter.rs` — non-linear verdict only: the non-linear path of the write filter, with byte-identical output

## Design

Cross-task rules that apply here: IMPLEMENTATION.md D1 (the linearity
criterion), D2 (the measured production entries keep their contract), D3 (file
ownership) and Conventions (measurement, no intentional CPU load, frozen shared
definitions). This plan does not restate them.

### Step 1 — FR1 measurement

The measured entries, as the target test calls them today:

| Entry | Measured calls |
|---|---|
| E1 | `strip_pty_output_for_scrollback_write` |
| E2 | `strip_replayable_rich_content` |
| E3 | `ScrollbackWriteFilter::feed`, one call (the overflow flush) |
| E4 | `ScrollbackWriteFilter::feed`, unit-aligned reads |
| E5 | `ScrollbackWriteFilter::feed`, 64 KiB reads |
| E6 | The ESC chain block: its strip, its one call and its 16 KiB reads |

The shapes are the open CSI and the lone ESC for E1 to E5, and the ESC chain for
E6, each for every `TARGETS` entry.

Measurement conditions:

- Each (entry, target, shape) cell is measured through its own `CpuMeter`, in a
  run of the target test alone, single-threaded, on a debug build.
- Two sizes of the same unit per target and shape, N and 4N. At both sizes every
  one-call input is longer than `SCROLLBACK_FILTER_PENDING_CAP`, so E3 takes the
  overflow flush at both.
- One run per size. The larger run's total stays at or below the current
  workload's total (the 27 s the failure reports).
- Instrumentation used only for the measurement does not stay in the final test:
  the final test measures every call through one `CpuMeter` judged against
  `BUDGET`, as today.

Verdict (IMPLEMENTATION.md D1): linear when every cell's 4N / N ratio is below 8.
Otherwise non-linear, and the cells at 8 or more name the path to fix.

The FR1 record is written in English in the target test's doc comment and holds:

- the measurement conditions (build, single thread, `CpuMeter`, the two sizes);
- for each entry E1 to E6 and each shape, the thread CPU time summed over the
  targets at N and at 4N, and their ratio;
- the largest per-cell ratio and the cell it belongs to;
- the verdict and the branch taken (Step 2a or Step 2b);
- the target test's total after the change, measured the same way.

### Step 2a — linear verdict: shrink the target test's own workload

- E3, for each target and shape: the input is the smallest whole number of units
  whose length exceeds `SCROLLBACK_FILTER_PENDING_CAP`. The test asserts that the
  length exceeds the cap before it feeds the input.
- E1, E2, E4 and E5: a smaller input made of the same unit, long enough to span
  at least three reads of the read size the entry uses, so constructs are held
  and split across reads.
- E6: a chain that may be shorter than today's 100,000 ESC bytes and spans at
  least three 16 KiB reads.
- Kept as today: every `TARGETS` entry, both shapes, the three feed modes, both
  strips, the ESC chain block and every output assertion (exact expected bytes
  for E1 to E4 and for the chain's strip and one call, the present checks of E5
  and of the chain's reads, the carried CSI state checks).
- The doc comment states the new input sizes and that they depart from the
  100k scale named for mux-strip-concat-query-closure AC-7, as this feature's
  SPEC records (its Workload Change Record, A8).
- No production file changes.

### Step 2b — non-linear verdict: fix the production path

- Fix the path the cells at 8 or more point to, in the strip pass or in
  `ScrollbackWriteFilter`. Signatures and output bytes stay the same for every
  input (NFR3, THREAT-MODEL.md TM-1).
- The workload stays as today, except that a one-call input that is not longer
  than the cap is raised to just above it, with the cap assertion of Step 2a.
  Today that is the lone ESC + csi query cell: 500,000 bytes against 524,288.
- Re-measure the cells that were at 8 or more, at N and 4N: each ratio is now
  below 8 (THREAT-MODEL.md TM-2). The FR1 record gains these numbers.
- When the total, with the workload unchanged, still exceeds 5 s after the fix,
  stop and report it as a conflict between FR2's non-linear branch and SPEC
  AC-2. Do not shrink the workload in this branch.

### Step 3 — verdict output

On success the target test writes its verdict line (the total against the
budget, the same text the failure message shows) to the test output, so a run
that shows test output reads the total.

### Flow

1. Measure every cell at N and 4N (Step 1).
2. Decide the verdict by D1.
3. Linear: Step 2a. Non-linear: Step 2b.
4. Write the FR1 record, the post-change total included.
5. Add the verdict output (Step 3).
6. Run the target test alone and then `mux::ipc::pty_spawn::tests`, each
   single-threaded.

- [ ] AC-1 (FR1, NFR1, NFR2): The target test's doc comment holds the FR1 record:
      the measurement conditions, the thread CPU time of each entry E1 to E6 per
      shape at N and at 4N with their ratio, the largest per-cell ratio and its

      passes on a debug build.
- [ ] AC-3 (FR2, NFR1): The target test passes every measured call through one
      `CpuMeter` judged against the unchanged 10 s `BUDGET`, reads no wall clock,
      and writes its verdict line to the test output on success. The
      post-change total in the FR1 record is 5 s or less.

      one-call input is longer than `SCROLLBACK_FILTER_PENDING_CAP`, and every

      doc comment states its input sizes and their departure from the 100k scale

      non-linear cell's 4N / N ratio below 8 (TM-2).
- [ ] AC-7 (FR2): `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib mux::ipc::pty_spawn::tests -- --test-threads=1`
      passes, the target test included.

## Test Notes

- AC-2, AC-3 and AC-4 are checked by the target test itself. Red: the
  reproduction command fails today (27 s against the 10 s budget), and the new
  cap assertion fails on today's lone ESC + csi query one-call input (500,000
  bytes, below the cap).
- AC-1 and AC-5 are document and diff checks with no executable red; record them
  with the rule for criteria without an executable check.
- AC-6, linear branch: a diff check against the base commit. Non-linear branch:
  the existing strip and write-filter suites, unchanged, plus the re-measurement.
- AC-7: the module run single-threaded; the scaling-ratio tests of the parallel
  task may or may not be present in it.
- Every run is a single-threaded run of the target test or of the module
  (NFR2). Noise is not averaged by repeated runs.
