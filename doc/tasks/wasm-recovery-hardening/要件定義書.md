# WASM自動復旧の堅牢化 - 要件定義書

## 1. 概要

### 1.1 背景

長時間運用・多ペイン・大量スクロールバックの環境で、WASM が「死んだ」まま自動復旧されず、ユーザーが手動でアプリを再起動する事象が発生した。2026-06-02 のログ調査（`tmp/wasm-recovery-failure-investigation-2026-06-02.md`）で、以下が判明した。

- 設計上存在する WASM 自動復旧（`reinitWasm`）が、`ReferenceError: Can't find variable: heap` で必ず失敗する。
- 失敗の原因は、ビルド時パッチ `scripts/patch-wasm-bindgen.sh` が注入する `__wbg_reset` が、現行 wasm-bindgen 生成物に存在しない `heap` / `heap_next` 変数を参照していること。
- 復旧フローの起点は、WASM リニアメモリが約 99MB で頭打ちになった状態での `RuntimeError: Out of bounds memory access`。99MB は明示的な上限設定ではなく、実行時に `memory.grow` が拒否された頭打ちである。
- 同種の復旧失敗は 2026-05-27、2026-06-02 07:46 にも発生しており、再発性がある。

### 1.2 目的

WASM が一度クラッシュしても、手動再起動なしに自動復旧が機能する状態へ戻す。あわせて、復旧の起点となるメモリ枯渇（Out of bounds）の発生頻度を、スクロールバック総量の制御によって低減する。

### 1.3 スコープ

本タスクの対象:

- P0: `scripts/patch-wasm-bindgen.sh` が注入する `__wbg_reset` から、存在しない `heap` / `heap_next` 参照を除去する。
- P0補強: パッチ適用後、注入コードが参照する識別子が生成物に実在するかをビルド時に検査するガードを追加する。
- P2: WASM 復旧の入口判定 `tryRecoverFromWasmCrash` が、exports 消失型 `TypeError` を WASM クラッシュとして検知できるようにする。
- P1: 全ペイン合計のスクロールバック総量にグローバル上限を設け、超過時は最古の行から破棄して、メモリ枯渇（Out of bounds）を予防する。

対象外:

- WASM リニアメモリの最大サイズの明示設定による上限引き上げ（実行環境のメモリ圧が要因のため効果が見込めない）。
- 復旧フロー自体の再設計（既存の二段構え recreateWasmCore → reinitWasm を維持する）。

## 2. ビジネス要件

### 2.1 ビジネス目標

ターミナルの可用性を維持し、長時間運用中の予期しない手動再起動をなくす。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| eMterm 利用者 | 多ペイン・長時間運用で大量出力を扱うユーザー（AI コーディングツール併用を含む） |

### 2.3 期待される効果

- WASM クラッシュ時に自動復旧が機能し、手動再起動が不要になる。
- スクロールバック総量制御により、メモリ枯渇起因のクラッシュ頻度が下がる。
- 将来の wasm-bindgen 更新で同種のパッチズレが再発した場合、ビルド時に検出できる。

## 3. ユースケース

### 3.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | WASM クラッシュからの自動復旧 | システム | 高 |
| UC02 | exports 消失型クラッシュの検知 | システム | 高 |
| UC03 | スクロールバック総量上限による破棄 | システム | 中 |
| UC04 | パッチズレのビルド時検出 | 開発者 | 中 |

### 3.2 ユースケース詳細

#### UC01: WASM クラッシュからの自動復旧

**アクター**: システム（フロントエンド復旧機構）

**事前条件**:
- WASM が `RuntimeError: Out of bounds memory access` または exports 消失型 `TypeError` でクラッシュした状態。

**基本フロー**:
1. 復旧入口 `tryRecoverFromWasmCrash` がクラッシュを検知する。
2. Step1: `recreateWasmCore()` を試みる。
3. Step1 が失敗した場合、Step2: `reinitWasm()` で WASM モジュールを再初期化する。
4. `reinitWasm()` 内の `reset()` が `ReferenceError` を出さずに完了する。
5. 新しい WASM インスタンスへ差し替わり、描画が復帰する。

**代替フロー**:
- Step1 で `recreateWasmCore()` が成功すれば Step2 をスキップする。
- 既定の最大試行回数を超えた場合は `wasmUnrecoverable` とし、復旧を諦める（既存挙動を維持）。

**事後条件**:
- 手動再起動なしにターミナルが操作可能な状態へ復帰する。
- `emterm.log` に復旧成功の記録（`WASM module reinitialized — terminal recovered`）が残る。

#### UC02: exports 消失型クラッシュの検知

**アクター**: システム

**事前条件**:
- WASM exports オブジェクト（バンドル後の `d0`）が `undefined` になり、`TypeError: undefined is not an object (evaluating 'd0.terminalcore_*')` が発生する状態。

**基本フロー**:
1. 描画・フォーカスプローブ・リサイズ等の経路でクラッシュが顕在化する。
2. `tryRecoverFromWasmCrash` がエラーメッセージに `terminalcore_` を含む `TypeError` を WASM クラッシュとして分類する。
3. UC01 の復旧フローへ流す。

**事後条件**:
- exports 消失型クラッシュが復旧フローの起点として扱われる。

#### UC03: スクロールバック総量上限による破棄

**アクター**: システム

**事前条件**:
- 多ペイン環境でスクロールバックが蓄積している。

**基本フロー**:
1. PTY 出力でスクロールバックが増加する。
2. 全ペイン合計のスクロールバック総量がグローバル上限を超える。
3. 最古の行から破棄して総量を上限以下に保つ。

**事後条件**:
- メモリ枯渇（`memory.grow` の Out of bounds 到達）が予防される。

#### UC04: パッチズレのビルド時検出

**アクター**: 開発者

**事前条件**:
- wasm-bindgen のバージョン更新等で生成物の内部変数構成が変わる。

**基本フロー**:
1. `bun run build:wasm` がパッチを適用する。
2. ガードが、注入した `__wbg_reset` の参照識別子が生成物に実在するか検査する。
3. 未宣言の識別子があればビルドを失敗させる。

**事後条件**:
- パッチと生成物のズレが、ランタイムではなくビルド時に検出される。

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| FR1 | reset の heap 参照除去 | `__wbg_reset` から存在しない `heap`/`heap_next` 参照を除去 | 高 |
| FR2 | パッチのビルド時ガード | 注入コードの参照識別子の実在を検査しビルド失敗で通知 | 中 |
| FR3 | exports 消失型クラッシュ検知 | `terminalcore_` を含む TypeError を復旧対象に追加 | 高 |
| FR4 | スクロールバック総量制限 | 全ペイン合計の総量上限と最古行破棄 | 中 |

### 4.2 機能詳細

#### FR1: reset の heap 参照除去

**説明**: `scripts/patch-wasm-bindgen.sh` の `RESET_FN` から、現行 wasm-bindgen 生成物に存在しない以下4行を除去する。

```
heap.length = 128;
heap.fill(undefined);
heap.push(undefined, null, true, false);
heap_next = heap.length;
```

残す状態リセットは、生成物に実在が確認済みの `wasm`、`cachedDataViewMemory0`、`cachedUint16ArrayMemory0`、`cachedUint8ArrayMemory0`、`WASM_VECTOR_LEN` のみ。

**ビジネスルール**:
- `wasm/pkg/` は生成物であり直接編集しない。必ずパッチスクリプト側を修正し、`bun run build:wasm` で再生成して反映する。

**エラーケース**:

| エラー | 条件 | 対応 |
|--------|------|------|
| ReferenceError: Can't find variable: heap | 修正前の `reset()` 呼び出し | FR1 で参照除去し解消 |

#### FR2: パッチのビルド時ガード

**説明**: パッチ適用後、注入した `__wbg_reset` 本体が参照する識別子が生成物 `emterm_wasm.js` に宣言・定義されているか検査する。未宣言があればパッチスクリプトを非ゼロ終了で失敗させ、メッセージを出力する。

**バリデーション**:

| 項目 | ルール | エラーメッセージ |
|------|--------|------------------|
| 参照識別子の実在 | `__wbg_reset` が参照する各識別子が生成物に存在する | どの識別子が未宣言かを示してビルド失敗 |

#### FR3: exports 消失型クラッシュ検知

**説明**: `src/terminal-app/pty-handler.ts` の `tryRecoverFromWasmCrash` 入口判定に、`error instanceof TypeError && msg.includes("terminalcore_")` を WASM クラッシュ条件として追加する。バンドル後に変わる `d0` ではなく、wasm-bindgen の安定プレフィックス `terminalcore_` で判定する。

**ビジネスルール**:
- 復旧入口は単一に集約されているため、入口1箇所への条件追加で全経路（描画失敗・フォーカスプローブ・リサイズ・グローバルハンドラ）に効く。

#### FR4: スクロールバック総量制限

**説明**: 全ペイン合計のスクロールバック総量にグローバル上限を設ける。上限を超えた場合は最古の行から破棄して総量を上限以下に維持する。これにより `memory.grow` が Out of bounds に到達する前にメモリ消費を抑える。

**ビジネスルール**:
- 上限の具体値（総バイト数 / 総行数）と破棄単位は実装計画で根拠とともに決定する（Open Questions 参照）。
- 既存の個別ペイン上限（10000 行）と整合させる。

**エラーケース**:

| エラー | 条件 | 対応 |
|--------|------|------|
| RuntimeError: Out of bounds memory access | メモリ枯渇 | FR4 で予防、FR1/FR3 で発生時も自動復旧 |

## 5. 非機能要件

### 5.1 パフォーマンス要件

- スクロールバック総量チェックは PTY 出力のホットパスに有意なオーバーヘッドを与えないこと。

### 5.4 保守性要件

- 復旧の成功・失敗が `emterm.log` の warn / error レベルで追跡できること。
- パッチと生成物のズレがビルド時に検出できること。

### 5.3 可用性要件

- WASM クラッシュ（Out of bounds / exports 消失）から手動再起動なしに自動復旧すること。

## 9. 制約条件

### 9.1 技術的制約

- 対応プラットフォームは Linux / Windows（macOS 非対応）。Linux の WebView は WebKitGTK。
- DevTools は使用不可。検証は `emterm.log`（warn 以上）とユニットテストで行う。
- 99MB のメモリ頭打ちは実行環境のメモリ圧によるもので、最大メモリ設定の引き上げでは解決しない。

## 10. 想定される課題とリスク

### 10.1 技術的課題

| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| パッチで残す状態変数名が将来の wasm-bindgen で再び変わる | 中 | FR2 のビルド時ガードで検出 |
| スクロールバック破棄でユーザーの履歴が失われる | 中 | 上限値を十分大きく取り、破棄は最古行からに限定 |
| reinit 後も exports 消失が再発するケース | 低 | FR3 で起点検知、既存の最大試行回数で無限ループを防止 |

## 12. テストシナリオ

### 12.1 テスト観点

- [ ] 正常系: `reset()` → `init()` で新しい WASM インスタンスが得られる。
- [ ] 正常系: 復旧フロー（recreate 失敗 → reinit 成功）が通る。
- [ ] 異常系: exports 消失型 TypeError が復旧対象として分類される。
- [ ] 境界値: スクロールバック総量が上限ちょうど／上限超過の場合の破棄挙動。
- [ ] 回帰: 既存のユニットテスト（`pty-handler.test.ts`、`canvas-renderer-recovery.test.ts`）が壊れない。

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| exports 消失型クラッシュ | WASM exports オブジェクト（バンドル後 `d0`）が `undefined` になり、メソッドアクセスが `TypeError` になる失敗モード |
| reinit | `reinitWasm()` による WASM モジュールの再初期化（`reset()` → `init()`） |
| 総量上限 | 全ペイン合計のスクロールバックに設けるグローバルな上限 |
