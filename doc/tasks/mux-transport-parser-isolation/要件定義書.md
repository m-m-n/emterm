# mux トランスポート/コンテンツ パーサー分離 - 要件定義書

## 1. 概要

### 1.1 背景

mux セッション内で `emterm image <file>` を実行すると、インライン画像が表示されず、
端末に base64 のような文字列が漏れる。タブを切り替えて戻すと（snapshot 再描画で）消える。
mux 外の通常タブでは正常に画像表示される。mux 内でのみ発生する。

根本原因は、mux タブが 1 個の `term_core` パーサー（`Tab::core`）を、2 つの独立した
ストリームに多重利用しているため、ストリーム境界でパーサー状態が混ざることである。

- 外側（トランスポート）: PTS に来る `emterm-mux;` APC を剥がして `MuxMessage` を抽出
  （`pump` → `core.process_pty_data_fully`、`tabs.rs:1457`）
- 内側（コンテンツ）: `PtyOutput` の中身＝リモート pane の生ターミナル出力を描画
  （`apply_mux_message` PtyOutput アーム → `core.process_pty_data_fully`、`tabs.rs:945`）

daemon は PTY を 64KB 単位で読むため、Kitty の各チャンク（約4KB）は PtyOutput 境界で
頻繁に APC 途中分断される。内側パースが分断チャンクの途中でパーサーを ApcString 状態の
まま残し、次の pump で外側パースが同じパーサーで割り込むことで、分断チャンクが壊れ、
後半が Ground 状態で base64 としてテキスト印字される（＝画面への漏れ）。

### 1.2 目的

外側トランスポートのパースと内側コンテンツのパースで、パーサー状態を完全に分離し、
mux セッション内での画像表示（Kitty / SIXEL）と通常コンテンツ表示を正常化する。

### 1.3 スコープ

- 対象: mux クライアント側（GUI）の PTS バイトのパース経路
- 対象外: mux daemon・mux_ipc プロトコル・ブリッジ（不変）
- 対象外: 非mux 経路（不変）
- 対象外: WebView 側（`src/`、廃棄予定・一方向マージ方針）

採用方針: **案A（専用トランスポート抽出器、mux 確立後に切替）**。

## 2. ビジネス要件

### 2.1 ビジネス目標

mux を tmux 代替として実用に足るものにする。リッチコンテンツ表示（画像・Markdown）は
eMterm の中核的な強みであり、mux 内で機能しないと mux の採用を妨げる。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| mux 利用者 | eMterm の mux 機能でセッションを多重化して使う利用者 |
| AI コーディングツール利用者 | mux 内で画像出力を伴うツール（`emterm image` 等）を使う利用者 |

### 2.3 期待される効果

- mux セッション内でインライン画像（Kitty / SIXEL）が正しく表示される
- base64 文字列の画面漏れが解消される
- `self.core` が「内側コンテンツ専用」に純化され、外側トランスポートのパーサー汚染が無くなる

### 3.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | mux 内で画像を表示する | mux 利用者 | 高 |
| UC02 | mux 内で大きい画像を表示する | mux 利用者 | 高 |
| UC03 | mux 内で SIXEL 画像を表示する | mux 利用者 | 中 |

### 3.2 ユースケース詳細

#### UC01: mux 内で画像を表示する

**アクター**: mux 利用者

**事前条件**:
- mux セッションに attach 済み（`mux_session_name.is_some()`）

**基本フロー**:
1. 利用者が mux タブで `emterm image <file>` を実行する
2. CLI が Kitty シーケンスを stdout に出力する
3. daemon がリモート pane の出力を PtyOutput として配信する
4. GUI が PtyOutput の中身を内側パースして画像を組み上げる
5. インライン画像が表示される

**代替フロー**:
- Kitty チャンクが PtyOutput 境界で分断されても、内側パーサー状態が保たれ正しく組み上がる

**事後条件**:
- インライン画像が表示され、base64 文字列の漏れが無い

#### UC04: mux 内で通常コンテンツ（テキスト・TUI・Markdown）を使う

**アクター**: mux 利用者

**事前条件**:
- mux セッションに attach 済み

**基本フロー**:
1. 利用者が mux タブで通常テキスト出力・TUI（vim 等）・Markdown ビューアを使う
2. 外側分離後も従来どおり描画される

**事後条件**:
- 外側分離の副作用による表示崩れが無い

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | 専用トランスポート抽出器 | mux 確立後の PTS バイトから `emterm-mux;` APC / OSC フレームを独立状態で抽出 | 高 |
| F02 | self.core の内側コンテンツ専用化 | mux 確立後、`self.core` を内側パース専用にする | 高 |
| F03 | mux 確立前後の経路切替 | Welcome ハンドシェイクを境に処理経路を切替 | 高 |
| F04 | detach 時の復帰 | detach 時に PTS 処理を `self.core` に戻す | 中 |
| F05 | DIAG ログ撤去 | 調査用に仕込んだ一時ログを撤去 | 中 |

### 4.2 機能詳細

#### F01: 専用トランスポート抽出器

**説明**: mux 確立後のタブの PTS バイトを、`self.core` ではなく専用の APC/OSC 抽出器
（独立したパーサー状態）に通して `emterm-mux;` フレームだけ取り出す。

**入力**:
- coalesce 済み PTS バイト列: `&[u8]`

**出力**:
- mux APC ペイロード列: `Vec<Vec<u8>>`（既存の `partition_apc_for_mux` → `apply_mux_message` 経路へ）

**ビジネスルール**:
- 抽出器は `ApcDispatch` / `OscDispatch` だけ拾い、Print 等は捨てる
- 抽出器は APC（`ESC _ emterm-mux; ... ESC \`）と OSC フォールバック（`ESC ] 9999; ...`）の両方を扱う
- 外側ストリームはグリッドに描画するものが無い（APC はコールバック dispatch のみ・印字しない）ため、
  `self.core` から外しても描画上の損失は無い

#### F02: self.core の内側コンテンツ専用化

**説明**: mux 確立後、`self.core`（グリッド＋パーサー）はリモート pane の画面＝内側コンテンツ
専用にする。`apply_mux_message` の PtyOutput アームのみが `self.core` を駆動するため、
内側 Kitty チャンクが PtyOutput 境界をまたいでもパーサー状態が保たれる。

#### F03: mux 確立前後の経路切替

**説明**: Welcome ハンドシェイクの状態に応じて処理経路を切り替える。

**処理フロー**:
- Welcome 到達前（通常タブ）: 従来どおり `self.core` で PTS を処理（任意のコマンドが動きうる）
- Welcome の APC は `self.core`（pre-mux）で 1 個パースされる（クリーンな単発 APC なので無害）
- `apply_mux_message` が Welcome を処理して `mux_session_name` がセットされた次の pump 以降、
  抽出器に切替
- 切替時、`self.core` のパーサーは直前の内側パースが残した状態のまま（以降は内側のみが駆動）

**ビジネスルール**:
- 切替判定は `mux_session_name.is_some()` を使う
- 抽出器に切替えた後も Welcome 二重送信（既知）に対応できること

#### F04: detach 時の復帰

**説明**: detach（`mux_session_name` クリア、`tabs.rs:1364`）時に PTS 処理を `self.core` に戻す。

#### F05: DIAG ログ撤去

**説明**: 調査用に仕込んだ一時ログを撤去する。

**対象**:
- `crates/term_core/src/terminal_core.rs`: `parser_mid_sequence()` アクセサ
- `src-tauri/src/tabs.rs`: `apply_mux_message` PtyOutput アームの `DIAG mux PtyOutput ...`
- `src-tauri/src/tabs.rs`: `drain_and_decode_images` の `DIAG drain ...`
- `src-tauri/src/tabs.rs`: `reset_frame_for_replay` の `DIAG reset_frame_for_replay ...`
- `src-tauri/src/mux/apc.rs`: `try_decode_emterm_mux` 失敗時の `DIAG mux APC decode failed ...`
  （元の簡易 warn に戻す）

## 5. 非機能要件

### 5.1 パフォーマンス要件

- `pump` の coalesce / フレーム予算（`FRAME_BUDGET_MS = 12ms`、`COALESCE_CAP = 1MB`）の
  既存挙動を損なわないこと
- 抽出器の追加によるスループット低下を最小限にする

### 5.2 セキュリティ要件

- 該当なし（既存の APC/OSC パースの範囲内で完結）

### 5.4 保守性要件

- ログ出力: 調査用 DIAG ログは撤去し、`apc.rs` の失敗時ログは元の簡易 warn に戻す
- `term_core` 側に `Parser` を standalone で使える公開 API が無ければ、最小限の公開窓口を足す
  （例: APC/OSC ペイロードだけ返す `MuxApcExtractor`）

### 5.5 互換性要件

- mux daemon・mux_ipc プロトコル・ブリッジは不変
- 非mux 経路は不変
- WebView 側（`src/`）は対象外

## 9. 制約条件

### 9.1 技術的制約

- ブリッジは APC と OSC（`ESC] 9999;` フォールバック）両方を使いうる（`mux/bridge.rs` の transport 検出）
- mux はインバンドプロトコルであり、受信側は本質的に 2 層のパースが必要（トランスポート / コンテンツ）

## 10. 想定される課題とリスク

### 10.1 技術的課題

| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| 抽出器が APC/OSC 両方の途中分断を正しく扱えるか | 高 | term_core の Parser を独立インスタンスで使う or 専用スキャナを慎重に実装 |
| detach 後の経路復帰漏れ | 中 | detach 経路（`tabs.rs:1364`）で `self.core` 復帰を確認するテスト |
| Welcome 二重送信時の切替タイミング | 中 | `first_welcome` ガードと組み合わせて検証 |

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| 外側パース（トランスポート） | PTS バイトから `emterm-mux;` APC を剥がして `MuxMessage` を抽出する処理 |
| 内側パース（コンテンツ） | `PtyOutput` の中身（リモート pane の生ターミナル出力）を `self.core` で描画する処理 |
| 抽出器 | 外側パース専用の独立パーサー状態（案A で新設） |
| PtyOutput 境界 | daemon が 64KB 単位で読むことで生じる PtyOutput メッセージの分断点 |
