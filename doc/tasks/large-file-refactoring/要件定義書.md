# 大規模ファイル分割リファクタリング - 要件定義書

## 1. 概要

### 1.1 背景
コードベース内に1000行を超えるファイルが複数存在し、単一クラスに多数のメソッドが集中している。特にTypeScriptフロントエンドの3ファイル（canvas-renderer.ts、state.ts、terminal-app/index.ts）は1400〜1900行に達しており、保守性・可読性の低下が顕著。

### 1.2 目的
1000行超の大規模ファイルを責務ごとに分割し、各モジュールの凝集度を高める。既存の動作を維持しつつ、コードの保守性と可読性を向上させる。

### 1.3 スコープ
- 高優先度: TypeScript 3ファイル（canvas-renderer.ts、state.ts、terminal-app/index.ts）
- 中優先度: TypeScript 2ファイル + Rust 1ファイル（unified-buffer.ts、layer.ts、terminal_core.rs）

## 2. ビジネス要件

### 2.1 ビジネス目標
コードベースの保守性を向上させ、今後の機能追加・バグ修正の効率を上げる。

### 2.2 対象ユーザー
| ユーザータイプ | 説明 |
|----------------|------|
| 開発者 | コードベースを保守・拡張する開発者 |

### 2.3 期待される効果
- ファイルの責務が明確になり、変更箇所の特定が容易になる
- コードレビューの効率が向上する
- 並行開発時のコンフリクトが減少する

## 5. 非機能要件

### 5.1 パフォーマンス要件
- リファクタリングによるランタイムパフォーマンスへの影響なし

### 5.2 保守性要件
- 各分割先ファイルは400行以下を目安とする
- 関数ベースのモジュール分割（サブクラスではなく純粋関数）
- 元ファイルからの re-export で外部 import パスを維持

### 5.3 互換性要件
- 既存の public API に変更なし
- 外部からの import パスに変更なし（re-export で維持）

## 9. 制約条件

### 9.1 技術的制約
- TypeScript の分割は関数ベースモジュールとする（既存の renderer-utils.ts パターンに準拠）
- Rust の分割は impl ブロック分割による別ファイルへの切り出し
- WASM バインディングへの影響なし

### 9.2 ビジネス上の制約
- 機能的な変更を含まない純粋なリファクタリングであること

## 10. 想定される課題とリスク

### 10.1 技術的課題
| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| private メンバーへのアクセス | 中 | 関数引数で必要な状態を渡す、またはアクセサメソッドを追加 |
| 循環依存の発生 | 中 | 依存方向を単方向に保つ設計 |
| TypeScript の this バインディング | 低 | 関数に必要なコンテキストを明示的に渡す |

### 10.2 ビジネスリスク
| リスク | 発生確率 | 影響度 | 対応策 |
|--------|----------|--------|--------|
| リグレッション | 低 | 高 | 既存テスト全通過を確認 |

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| 関数ベース分割 | クラスのメソッドを外部の純粋関数モジュールに切り出し、元クラスから呼び出すパターン |
| re-export | 分割先で定義した関数・型を元ファイルから `export { ... } from './split-file'` で再公開すること |
