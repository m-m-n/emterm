# detach 中の pane exit を daemon で reap する - 要件定義書

## 1. 概要

### 1.1 背景

mux の「Ctrl+D でシェル終了 → pane/タブがクリーンアップされず残る」バグ修正
（`fix(mux): reap exited panes ...`, commit 0966e67）は、GUI が attach 中
（`output_target == Connected`）の経路のみをカバーしている。**detach 中にシェルが
死んだ場合**は依然として daemon の `SessionManager` に zombie pane が残り、
「全 session 空 → auto-shutdown」の不変条件が成立しない。

PTY reader スレッドの EOF 処理は `Connected` のときだけ空チャンク（exit シグナル）を
送る。daemon 側の reap（`connection.rs` の PTY 出力 select! ループで空チャンク →
`handle_destroy_pane`）はこの空チャンクが起点なので、`Detached` のときは reap が一切
走らない。

### 1.2 目的

「PTY が死んだら attach/detach に関係なく必ず pane が reap される」という単一の権威を
daemon に成立させ、zombie session の発生をなくす。これにより detach 中の自然終了でも
`mux kill` / 自動シャットダウンが正しく機能するようにする。

### 1.3 スコープ

対象（修正する）:

- **(A) 純粋な detach 経路**: reader スレッドが `Detached` 状態で EOF を迎える経路。
  空チャンクが出ないため現状の変更では拾えない。
- **(B) 接続断レース**: クライアント切断と最終シェル終了が同時に起き、
  `detach_session_panes`（`connection.rs:494`）経由で pane が `Detached(NetworkDetach)`
  に切り替わるだけで remove されない経路。skip-guard は `pane.exited` を見るが EOF 経路は
  それを立てないため stranding する。

対象外:

- WebView（旧 `src/`）側の挙動。本タスクは native mux daemon のみを対象とする。
- mark_exited を起点とする既存の graceful shutdown / 明示 kill 経路の仕様変更。

## 2. ビジネス要件

### 2.1 ビジネス目標

mux daemon が「全 session 空 → 自動終了」の不変条件を attach 状態に関わらず常に満たし、
zombie daemon / zombie session を残さない。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| eMterm 利用者 | mux を detach して放置し、その間にシェルが終了するケースに遭遇する |
| 開発者 | `mux kill` / 自動シャットダウンの不変条件に依存するコードを書く |

### 2.3 期待される効果

- detach 中にシェルが死んでも pane が確実に reap される
- 接続断レースで pane が stranding しない
- `mux kill` / 自動シャットダウンが効かない zombie session が生じない

## 3. ユースケース

### 3.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | detach 中の最終シェル終了で daemon が自動終了する | 利用者 | 高 |
| UC02 | detach 中の非最終 pane 終了で当該 pane だけ reap される | 利用者 | 高 |
| UC03 | 接続断レースで pane が stranding しない | 利用者 | 高 |

### 3.2 ユースケース詳細

#### UC01: detach 中の最終シェル終了で daemon が自動終了する

**アクター**: 利用者

**事前条件**:
- mux daemon が起動中で、GUI クライアントは detach 済み（接続なし）
- 残り pane は1つだけ

**基本フロー**:
1. detach 状態でシェルが終了する（exit / Ctrl+D / プロセス死）
2. PTY reader スレッドが EOF を検知する
3. reader が attach 状態に関係なく daemon へ pane exit を通知する
4. daemon が当該 pane を reap し、空 window/session を除去する
5. 全 session が空になったため daemon が自動シャットダウンする

**事後条件**:
- `SessionManager` に zombie pane が残らない
- daemon プロセスが終了している

#### UC02: detach 中の非最終 pane 終了で当該 pane だけ reap される

**アクター**: 利用者

**事前条件**:
- detach 状態で複数 pane が存在

**基本フロー**:
1. detach 状態で1つの pane のシェルが終了する
2. reader EOF → daemon へ通知 → 当該 pane を reap
3. 空 window/session があれば除去する

**事後条件**:
- 当該 pane のみ除去され、他 pane は存続
- 全 session が空でないため daemon は終了しない

#### UC03: 接続断レースで pane が stranding しない

**アクター**: 利用者

**事前条件**:
- GUI クライアント切断と最終シェル終了がほぼ同時に発生

**基本フロー**:
1. クライアント切断で `detach_session_panes` が走り、pane を `Detached(NetworkDetach)` に切り替える
2. ほぼ同時に reader が EOF を検知し daemon へ pane exit を通知する
3. daemon の reap は `output_target` の状態に関わらず pane_id で除去する

**代替フロー**:
- reap が先に走った場合: `detach_session_panes` は当該 pane を見つけられず no-op

**事後条件**:
- pane が `Detached(NetworkDetach)` のまま残存しない（必ず reap される）

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | attach 非依存の pane exit 通知 | reader EOF で attach 状態に関係なく daemon へ通知 | 高 |
| F02 | daemon 側 reap 受信タスク | 通知を受けて `handle_destroy_pane` を呼ぶ単一の権威 | 高 |
| F03 | Connected 経路の client teardown 保持 | Connected 時は従来どおり空チャンクを client へ送る | 高 |
| F04 | reap の冪等性 | 既に除去済みの pane への reap を安全な no-op にする | 高 |
| F05 | 両プラットフォーム対応 | Unix socket / Windows named pipe の両 run ループで配線 | 高 |

### 4.2 機能詳細

#### F01: attach 非依存の pane exit 通知

**説明**: `pty_reader_loop` の `Ok(0)`（EOF）アームで、`output_target` の状態
（Connected/Detached）に関係なく、専用チャネルへ `pane_id` を送出する。

**入力**:
- pane_id: `PaneId` - EOF を迎えた pane

**出力**:
- 専用 pane-exit チャネルへの `pane_id` 送出

**ビジネスルール**:
- Connected のときは F03（空チャンク送出）も併せて実行する
- 送出失敗（受信側 drop = daemon 終了中）は無視してよい

#### F02: daemon 側 reap 受信タスク

**説明**: daemon が専用チャネルの受信タスクを spawn し、受信した `pane_id` ごとに
`handle_destroy_pane(pane_id, &session_manager, &shutdown_tx)` を呼ぶ。これにより
「PTY 死亡 → reap」が attach 状態に依存しない単一の権威になる。

**処理フロー**:
```mermaid
flowchart TD
    A[reader EOF Ok(0)] --> B{output_target}
    B -->|Connected| C[空チャンクを client へ送出]
    B -->|Detached| D[（client teardown なし）]
    C --> E[pane-exit チャネルへ pane_id 送出]
    D --> E
    E --> F[daemon reap 受信タスク]
    F --> G[handle_destroy_pane]
    G --> H{全 session 空?}
    H -->|Yes| I[shutdown_tx.send(true)]
    H -->|No| J[終了せず継続]
```

**エラーケース**:
| エラー | 条件 | 対応 |
|--------|------|------|
| pane が見つからない | 既に reap 済み（Connected 経路が先行） | warn ログのみ・no-op（F04） |

#### F03: Connected 経路の client teardown 保持

**説明**: Connected のときは従来どおり空チャンク（`PtyOutputChunk { data: Vec::new() }`）を
client へ送出し、GUI 側の UI teardown（`PtyExited`）を維持する。

#### F04: reap の冪等性

**説明**: `handle_destroy_pane` は対象 pane が見つからない場合 warn ログを出して return する
（既存挙動）。Connected の空チャンク reap（`connection.rs`）と F02 の daemon reap が同一 pane に
対して両方走っても二重 free やパニックを起こさない。

#### F05: 両プラットフォーム対応

**説明**: 専用チャネルの生成・受信タスクの spawn・`handle_connection` への配線を、
Unix socket daemon（`daemon.rs` の Unix run）と Windows named pipe daemon（同 Windows run）の
両方で行う。

## 5. 非機能要件

### 5.1 パフォーマンス要件

- pane exit 通知は EOF 検知時に1回だけ送出する軽量操作。定常出力経路（`Ok(n)`）には影響を与えない。

### 5.2 セキュリティ要件

- 該当なし（プロセス内チャネル。外部入力なし）。

### 5.3 可用性要件

- reap の単一権威化により「全 session 空 → daemon 終了」の不変条件が attach 状態に関係なく成立する。

### 5.4 保守性要件

- ログ: EOF 検知・reap 通知・reap 実行の各地点で既存方針（`log::info!` 以上）に従いログを残す。
- 専用チャネルは既存の `(PaneId, String)` 通知チャネルとは別に切る（型・用途の混同を避ける）。

### 5.5 互換性要件

- 既存の `mux-kill-shutdown`（明示 kill）/ `close-window-on-shell-exit`（shell exit → tab close）の
  挙動を壊さない。本タスクは「detach 中の自然終了でも reap」要件として両者の中間を埋める。

## 9. 制約条件

### 9.1 技術的制約

- reader スレッド（`pty_reader_loop`）は `output_target` / `scrollback` 等は持つが
  `shutdown_tx` / `session_manager` は持たない。よって reader 自身は reap できず、
  daemon 側の受信タスクが reap を担う必要がある。
- 既存の `NotificationSender = mpsc::Sender<(PaneId, String)>` は GUI への OSC 通知転送用で
  型・用途が異なるため流用しない。
- cwd マップ（`pane_cwd_map`）は接続単位（`connection.rs`）で持つため daemon 受信タスクからは
  触れない。detach 中は接続がなく当該マップも存在しないため、daemon reap での cwd 掃除は不要。

## 10. 想定される課題とリスク

### 10.1 技術的課題

| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| Connected 時の二重 reap | 中 | reap を冪等にする（F04）。`handle_destroy_pane` の既存 no-op 挙動で吸収 |
| 接続断レースの順序非決定性 | 中 | reap は `output_target` 非依存・pane_id ベース。`session_manager` の async Mutex で直列化（F02/UC03） |

## 12. テストシナリオ

### 12.1 テスト観点

- [ ] 正常系: detach 中の最終 pane EOF → reap → 全 session 空 → shutdown シグナル
- [ ] 正常系: detach 中の非最終 pane EOF → 当該 pane のみ reap、daemon 継続
- [ ] 異常系（レース）: `detach_session_panes` で `Detached(NetworkDetach)` 化された pane も reap される
- [ ] 冪等性: 同一 pane への二重 reap が安全（no-op）
- [ ] 手動: detach → Ctrl+D → daemon プロセス終了を実機で確認

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| reap | 終了した pane を `SessionManager` から除去し、空 window/session を片付ける処理 |
| attach / detach | GUI クライアントが daemon の session に接続している / していない状態 |
| stranding | 終了済みなのに `Detached` 状態で `SessionManager` に残り続ける pane |
| 単一の権威 | 「PTY 死亡 → reap」を attach 状態に依存せず1経路で扱う設計 |
