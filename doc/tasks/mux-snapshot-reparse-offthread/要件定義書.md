# mux 切替時 snapshot 再パースコストの計測と判断 - 要件定義書

## 1. 概要

### 1.1 背景

mux-scroll-isolation（commit `e8e538f`）の FR1 により、オンデマンド `RequestPaneSnapshot`
の応答に pane の scrollback（最大 `DEFAULT_SCROLLBACK_CAPACITY` = 2MiB、実履歴量に比例）を
載せるようになった。クライアントはこの snapshot を受信すると `reset_and_replay`
→ `process_pty_data_fully` で **payload 全バイトを同期 VT 再パース**する。この処理は
`Tab::pump` → `App::pump_all` の中で走り、`App::pump_all` は winit イベントループ
（UI/描画スレッド）から駆動される。

FR1 以前のオンデマンド snapshot は「画面のみ（数KB）」で切替は軽かったが、現在は
pane/window を切り替えるたびにその pane の全履歴（最大 2MiB）を描画スレッドで毎回
パースし直す。`Ctrl+B n n n` のような高速切替では毎キーで走り、入力/再描画が詰まる
懸念がある。

この再パース CPU コストは SPEC（mux-scroll-isolation）の NFR2（転送量の免除）では
カバーされていない。設計メモ `tmp/perf-snapshot-reparse-offthread-plan.md` に対策案
（案a: off-thread replay）が記録されているが、メモ自身が「後でタスク化（実装はしていない）」
かつ「§4: まず計測してから案a を実装するか判断する」というゲートを置いている。

### 1.2 目的

- 近満杯（~2MiB）の scrollback を `process_pty_data_fully` に通す再パース所要時間を、
  決定的・再現可能な形で計測する。
- 計測結果にしきい値を当て、案a（off-thread replay）の本実装を行うか否かを判断・記録する。
- 計測ゲートとは独立に、daemon 側 `handle_request_pane_snapshot` の scrollback
  ロックスコープ（現状すでに read_all コピー区間のみ）を明示化・回帰テスト化して
  将来のリファクタで広がらないようガードレール化する。

### 1.3 スコープ

**本 feature に含む**:
- 再パースコスト計測ハーネス（FR1）
- 計測の実行・記録と go/no-go 判断の文書化（FR2）
- handlers のロックスコープのガードレール化（FR3）

**本 feature に含まない（follow-up feature へ繰り延べ）**:
- 案a（off-thread replay）の本実装。計測で go と判断された場合に、別 SDD feature として
  起票する。方針は案a で確定済み（後述）。
- 案c（pane 毎の常駐 core）。非採用。
- 直近 K pane の LRU キャッシュ（折衷案）。本 feature では採用しない。

## 2. ビジネス要件

### 2.1 ビジネス目標

mux の pane/window 高速切替で UI が詰まらない応答性を保つ。ただし対策の複雑さに
見合うコストかを計測で確認してから実装判断する（過剰最適化の回避）。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| eMterm 利用者 | mux で複数 pane/window を高速に切り替えるユーザー（特に履歴の多い pane） |

### 2.3 期待される効果

- 切替レイテンシのボトルネックが「再パース CPU」かどうかを数値で確定する。
- 実装の要否を事実ベースで判断でき、不要なら複雑な off-thread 化を回避できる。
- handlers のロックスコープを明示化・回帰テスト化し、計測結果に依らず snapshot
  応答の tight なロック区間を将来も維持できるようにする。

## 3. ユースケース

### 3.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | 再パースコストを計測する | 開発者 | 高 |
| UC02 | 計測結果から案a の要否を判断する | 開発者 | 高 |
| UC03 | snapshot 応答のロックスコープをガードレール化する | 開発者 | 中 |

### 3.2 ユースケース詳細

#### UC01: 再パースコストを計測する

**アクター**: 開発者

**事前条件**:
- term_core クレートがビルド可能。

**基本フロー**:
1. 開発者が計測ハーネス（`#[ignore]` テストまたは bench）を実行する。
2. ハーネスは ~2MiB の代表的な合成 scrollback を生成する。
3. `process_pty_data_fully` に通し、`std::time::Instant` で所要時間を測る。
4. 所要 ms とスループット（MiB/s）を標準エラー/ログへ出力する。

**事後条件**:
- 再パース所要時間の数値が得られる。

#### UC02: 計測結果から案a の要否を判断する

**アクター**: 開発者

**事前条件**:
- UC01 の計測値がある。

**基本フロー**:
1. 計測値を §4 のしきい値（後述 11.1）に当てる。
2. go/no-go を判断する。
3. 判断と根拠（計測値・実運用での 2MiB 到達頻度の考慮）を記録する。
4. go の場合は案a 実装を follow-up feature として起票する旨を記す。

**事後条件**:
- 判断結果が `VERIFICATION_RESULT.md`（または決定メモ）に残る。

#### UC03: snapshot 応答のロックスコープをガードレール化する

**アクター**: 開発者

**事前条件**: なし

**基本フロー**:
1. `handle_request_pane_snapshot` の `scrollback.lock().unwrap().read_all()` は、
   現状すでにガードを文末で drop し、assembly/log/send より前にロックを解放している
   ことを確認する。
2. drop 点を明示化する（所有 `Vec` を返すスコープブロック＋不変条件を述べるコメント）。
3. snapshot 出力バイトが不変であることを回帰テストで担保する。

**事後条件**:
- ロックは read_all コピー区間のみ保持される（現状維持）ことが明示・テスト化され、
  将来のリファクタで assembly/send まで広がらない。出力は変わらない。

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| FR1 | 再パースコスト計測ハーネス | ~2MiB scrollback の `process_pty_data_fully` 所要を決定的に計測 | 高 |
| FR2 | go/no-go 判断の記録 | しきい値判定と判断・根拠の文書化 | 高 |
| FR3 | handlers ロックスコープのガードレール化 | daemon 側 snapshot 応答の copy-only ロックスコープを明示化＋回帰テスト化（出力不変） | 中 |

### 4.2 機能詳細

#### FR1: 再パースコスト計測ハーネス

**説明**: term_core 内に、決定的・再現可能で、かつ `pump_all` の flaky 経路に依らない
純粋な計測ハーネスを設ける。通常の `cargo test` を遅く/不安定にしないため `#[ignore]`
（またはそれに準ずる手段）でゲートし、明示実行時のみ走らせる。

**入力**:
- 合成 scrollback バイト列: ~2MiB（`DEFAULT_SCROLLBACK_CAPACITY` 相当）。プレーンテキスト
  に一部 SGR/改行を混ぜた、scrollback として代表的な内容。

**出力**:
- 再パース所要時間（ms）とスループット（MiB/s）を標準エラーまたはログへ出力。

**ビジネスルール**:
- 入力は固定生成（乱数・時刻に依存しない）。
- 計測対象は `process_pty_data_fully`（= `reset_and_replay` の支配的コスト）。

#### FR2: go/no-go 判断の記録

**説明**: FR1 の計測値を 11.1 のしきい値に当て、案a 実装の要否を判断し記録する。

**ビジネスルール**:
- 判断は計測値と「実運用で 2MiB まで貯まる頻度」の両方を考慮する。
- go の場合のみ案a 実装を follow-up feature 化する（本 feature では実装しない）。

#### FR3: handlers ロックスコープのガードレール化

**説明**: `handle_request_pane_snapshot`（`src-tauri/src/mux/ipc/handlers.rs`）の
scrollback ロックスコープは現状すでに `read_all()` コピー区間のみ（ガードは文末で
drop 済み）。本要件はそれを明示化（所有 `Vec` を返すスコープブロック＋不変条件コメント）
して将来のリファクタで assembly/send まで広がらないよう固定し、snapshot 出力バイトの
不変を回帰テストで担保する。ロック保持時間の短縮ではない（O(n) コピーはリングバッファ
再設計なしには短縮不能で、本 feature の対象外）。

**ビジネスルール**:
- snapshot 出力バイトは現状と同一（振る舞い不変）。
- 既存の mux reattach/snapshot テストを壊さない。

**エラーケース**:
| エラー | 条件 | 対応 |
|--------|------|------|
| ロック取得失敗（poison） | mutex poisoned | 現状の `unwrap()` 挙動を踏襲（本 feature で挙動変更しない） |

## 5. 非機能要件

### 5.1 パフォーマンス要件

- FR1 の計測は決定的で、同一マシン上で再現可能（実行間のばらつきが判断を覆さない程度）。
- FR3 はロックスコープを copy-only に固定（現状維持の明示化＋回帰テスト）。回帰なし。

### 5.2 セキュリティ要件

- 該当なし（既存の「snapshot は要求元の attach 中セッションの pane のみ」認可は変更しない）。

### 5.3 可用性要件

- 該当なし。

### 5.4 保守性要件

- 計測ハーネスは恒久的に残し、将来の回帰計測にも使えるようにする。
- ログ出力は warn 以上で残す必要はない（計測は明示実行＝開発時のみ）。

### 5.5 互換性要件

- Linux / Windows 両対応（term_core はプラットフォーム非依存）。CLI-only ビルドを壊さない。

## 6. UI/UX要件

該当なし（ユーザー可視の UI 変更は無い。FR3 は内部最適化）。

## 7. データ要件

該当なし（永続データの追加・変更は無い）。

## 8. 外部連携

該当なし。

## 9. 制約条件

### 9.1 技術的制約

- ビルド/テストは `CARGO_TARGET_DIR` を `src-tauri/target` に固定し、プロジェクトルートから
  `--manifest-path` 経由で実行する（build-location ルール）。
- crate 全体の `cargo fmt` は走らせない（フォーマットは PostToolUse hook が担当）。
- `App::pump_all` に非同期を持ち込まない（FR1 は term_core 単体の純粋計測に留める）。

### 9.2 ビジネス上の制約

- リリースビルドはユーザーの明示指示時のみ。本 feature で勝手に `cargo build --release` しない。

### 9.3 スケジュール制約

- 特になし。

## 10. 想定される課題とリスク

### 10.1 技術的課題

| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| 計測値がマシン依存で判断がぶれる | 中 | しきい値に幅（<5ms / 5–50ms / 50ms+）を持たせ、グレー域は別途協議 |
| 合成入力が実 scrollback と乖離 | 中 | プレーンテキスト＋SGR/改行混在で代表性を確保 |
| FR3 のスコープ明示化で snapshot バイトが変わる | 高 | 出力バイト一致をテストで担保 |

### 10.2 ビジネスリスク

| リスク | 発生確率 | 影響度 | 対応策 |
|--------|----------|--------|--------|
| 計測の結果 case が軽く案a を作らない判断になる | 中 | 低 | それが本 feature の目的（過剰最適化回避）。判断を記録すればよい |

## 11. 成功基準

### 11.1 受け入れ基準

- [ ] FR1: ~2MiB の scrollback で `process_pty_data_fully` の所要時間を計測・出力できる。
- [ ] FR1: 計測ハーネスは決定的で、通常の `cargo test` を遅く/不安定にしない。
- [ ] FR2: 計測値を以下のしきい値に当て、判断と根拠を記録する。
  - `< 5ms`: 案a の複雑さに見合わない可能性 → 案a 見送り（FR3 のみ）
  - `5–50ms`: グレー域 → 計測値を添えて別途判断
  - `50ms+`: 案a を本実装（follow-up feature 起票）
- [ ] FR2: go の場合、案a（off-thread replay, コアのみ・LRU 無し）の follow-up feature を起票する旨を記す。
- [ ] FR3: handlers の scrollback ロックスコープが明示化される（スコープブロック＋
      コメントで read_all コピー区間のみと固定）。
- [ ] FR3: snapshot 出力バイトが変わらない（既存テスト green）。
- [ ] `cargo test`（default, single-thread）green、CLI-only `cargo check` green。

## 12. テストシナリオ

### 12.1 テスト観点

- [ ] 正常系: 合成 scrollback の計測が完走し数値が出る。
- [ ] 境界値: 空 scrollback（0B）でハーネスが panic せず 0 近傍を返す。
- [ ] 回帰: FR3 適用後も snapshot 出力バイトが一致する（既存 reattach/snapshot テスト green）。
- [ ] CI 非汚染: 通常 `cargo test` に計測が含まれない（`#[ignore]` 等）。

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| 案a | 重い VT 再パースをワーカースレッドで行い完成 core をメインで差し替える方式 |
| 案c | pane 毎に常駐 core を持ち切替を描画向き先変更のみにする方式（非採用） |
| snapshot | オンデマンド `RequestPaneSnapshot` の応答バイト（`ESC[H ESC[2J + scrollback + screen`） |
| go/no-go ゲート | §4 の計測しきい値に基づく案a 実装の要否判断 |
