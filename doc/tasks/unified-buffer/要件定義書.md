# 統合バッファ (Unified Buffer) - 要件定義書

## 1. 概要

### 1.1 背景

現在のeMtermは、ターミナルバッファを「スクロールバック（`scrollbackBuffer: Line[]`）」と「画面バッファ（`ScreenBuffer.lines: Line[]`）」に分離して管理している。この設計にはリサイズ時に以下の問題がある:

- reflowが画面バッファ（`ScreenBuffer`）内のみで実行され、スクロールバック行と分断される
- reflow後に行数が画面行数を超えた場合、下端から切り捨てられ、カーソル付近のコンテンツが失われる
- カーソル位置がreflow後の行再配置を反映せず、単純クランプのみで補正される
- シェルのSIGWINCH応答がreflow後のカーソル位置と不整合を起こし、表示が崩れる

### 1.2 目的

分離されたバッファを統合リングバッファに移行し、リサイズ時のreflowとカーソル追跡を正しく行うことで、ターミナルリサイズ時の表示崩れを根本的に解決する。

### 1.3 スコープ

- `ScreenBuffer` クラスを新しい `UnifiedBuffer` クラスに置き換え
- `TerminalState` の `scrollbackBuffer` を `UnifiedBuffer` に統合
- プライマリバッファとalternateバッファの両方を統合バッファ化
- reflow対象をバッファ全体（スクロールバック含む）に拡大
- reflow中のカーソル位置追跡を実装
- 既存テスト（1712件）の互換性を維持

## 2. ユースケース

### 2.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | ターミナル幅の縮小 | ユーザー | 高 |
| UC02 | ターミナル幅の拡大 | ユーザー | 高 |
| UC03 | スクロールバック閲覧 | ユーザー | 高 |
| UC04 | Alternateスクリーン切替 | アプリケーション | 中 |

### 2.2 ユースケース詳細

#### UC01: ターミナル幅の縮小

**事前条件**: ターミナルにコマンドと出力が表示されている

**基本フロー**:
1. ユーザーがウィンドウ幅を縮める
2. バッファ全体がreflowされ、長い行が折り返される
3. カーソル位置が論理行内オフセットから再計算される
4. 余剰の空行が下端から削除される
5. それでも余剰があれば上端行がviewport外（スクロールバック領域）に移動する
6. PTYに新サイズが通知される

**事後条件**: カーソル付近のコンテンツが保持され、シェルの再描画と整合する

#### UC02: ターミナル幅の拡大

**事前条件**: 折り返されている行がバッファ内に存在する

**基本フロー**:
1. ユーザーがウィンドウ幅を広げる
2. バッファ全体がreflowされ、wrappedな行が結合される
3. 行数が減少した分、スクロールバックから行が可視領域に戻る
4. カーソル位置が再計算される

#### UC03: スクロールバック閲覧

**事前条件**: スクロールバック行が存在する

**基本フロー**:
1. ユーザーがスクロールアップする
2. viewportが統合バッファの上方向にスライドする
3. 統合バッファの該当範囲が表示される

## 3. 機能要件

### 3.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | UnifiedBuffer クラス | リングバッファによる統合バッファ | 高 |
| F02 | バッファ全体reflow | スクロールバック含む全行のreflow | 高 |
| F03 | カーソルreflow追跡 | reflow中の論理行オフセット追跡と物理座標再計算 | 高 |
| F04 | viewport管理 | 末尾N行を可視領域とするviewport制御 | 高 |
| F05 | Alternateバッファ統合 | alternateスクリーンもUnifiedBuffer化 | 中 |
| F06 | 既存インターフェース互換 | TerminalStateAccessor等の既存APIを維持 | 高 |

### 3.2 機能詳細

#### F01: UnifiedBuffer クラス

**説明**: `ScreenBuffer` を置き換える新しいバッファクラス。リングバッファでスクロールバックと画面行を統合管理する。

**データ構造**:
- 内部: 固定容量のリングバッファ（`Line[]` + head/tail ポインタ）
- 容量: `scrollbackLines + rows`（プライマリ）、`rows`（alternate）
- 可視領域: 末尾 `rows` 行

**主要メソッド**:
- `getLine(row)`: 可視領域の行を取得（row 0 = 画面先頭）
- `getScrollbackLine(index)`: スクロールバック行を取得
- `scrollUp(count)` / `scrollDown(count)`: スクロール領域内でのスクロール
- `resize(cols, rows, cursorRow, cursorCol)`: reflow + viewport調整
- `push(line)`: 行をバッファ末尾に追加（容量超過時は先頭を破棄）

#### F02: バッファ全体reflow

**説明**: 幅変更時にバッファ全行（スクロールバック + 画面行）を一括してreflowする。

**アルゴリズム**:
1. 全行をドレインし、wrappedフラグで論理行を復元
2. 各論理行を新しい幅で再分割
3. 末尾の空行を優先的に刈り取り
4. 結果をバッファに書き戻す

**alternateバッファの扱い**: reflowしない（WezTermと同じ）。幅変更時はリサイズのみ。

#### F03: カーソルreflow追跡

**説明**: reflow処理中にカーソルの論理行内オフセットを累積追跡し、再分割後に物理座標(x, y)に逆変換する。

**アルゴリズム** (WezTerm方式):
1. 論理行結合時: カーソルが現在の物理行にある場合、`logical_cursor_x = cursor_x + 結合済み行のセル数`
2. 再分割時: `new_row = logical_cursor_x / new_cols`, `new_col = logical_cursor_x % new_cols`
3. 結果を新しいカーソル位置として返す

#### F04: viewport管理

**説明**: 統合バッファ内でviewportの位置を管理する。

- 通常時: バッファ末尾 `rows` 行がviewport
- スクロール時: viewportが上方向にスライド
- `getVisibleLines()`: viewport内の行を返す
- `getScrollbackLength()`: viewport外の行数を返す

#### F05: Alternateバッファ統合

**説明**: alternateスクリーンもUnifiedBufferで管理するが、スクロールバック容量は0、reflowは行わない。

#### F06: 既存インターフェース互換

**説明**: `TerminalStateAccessor` や `TerminalState` の公開APIを維持し、ハンドラーやレンダラーへの影響を最小化する。

変更が必要なAPI:
- `TerminalState.resize()`: カーソル位置をreflow結果から更新
- `getVisibleLines()`: 統合バッファのviewportから取得
- `getScrollbackBuffer()` / `getScrollbackLength()`: 統合バッファから算出

変更不要なAPI（互換維持）:
- `getActiveBuffer().getLine(row)`: 可視領域のアクセスは同じ
- `getActiveBuffer().setCell(col, row, cell)`: セル書き込みは同じ
- `getActiveBuffer().scrollUp()` / `scrollDown()`: スクロール動作は同じ

## 4. 非機能要件

### 4.1 パフォーマンス要件

- reflow処理: スクロールバック10,000行 + 画面行の全体reflowが100ms以内
- セルアクセス: `getLine(row)` が O(1)
- リングバッファ先頭削除: O(1)（ポインタ移動のみ）

### 4.2 メモリ要件

- 統合バッファの最大容量: `maxScrollbackLines + rows`
- セル圧縮は今回のスコープ外（将来対応可能な設計とする）

### 4.3 互換性要件

- 既存テスト1712件が全て通過すること
- `TerminalStateAccessor` インターフェースの変更を最小限にすること
- レンダラー（`canvas-renderer.ts`）の変更を最小限にすること

## 5. 制約条件

### 5.1 技術的制約

- TypeScript（Vanilla）での実装（フレームワーク不使用）
- 既存の `Line` / `Cell` データモデルは変更しない
- `wrapped` フラグは行レベル（`Line.wrapped`）を維持（セルレベルへの変更はスコープ外）

### 5.2 設計上の制約

- alternateバッファはreflowしない（WezTermと同様、フルスクリーンアプリとの干渉を避ける）
- スクロールバック上限超過時は先頭（最も古い行）から破棄
