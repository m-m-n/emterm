# 要件定義書: mux を独立 cargo feature に分割し CLI ビルドで mux daemon を使えるようにする

## 1. 概要

eMterm の `mux` サブコマンド（multiplexer daemon / bridge / CLI 管理）は現在 `gui` cargo feature の中に閉じ込められている。そのため `--no-default-features` でビルドした CLI 専用バイナリでは `emterm mux daemon` が「This build does not include mux support」と返して exit する。SSH 越しのリモートサーバで mux daemon だけを立てて、ローカルの GUI 版から bridge で接続するというユースケースが阻害されている。

本タスクでは `mux` を独立した cargo feature として切り出し、CLI 専用バイナリでも `mux` を有効化したサブセットビルドが作れるようにする。

## 2. 背景・課題

### 2.1 現在のビルド構成

| ビルド | コマンド | 含まれる機能 | deb パッケージ |
| --- | --- | --- | --- |
| GUI フル | `cargo build --release`（既定） | terminal + mux + CLI subcommands | `emterm` |
| CLI のみ | `cargo build --release --no-default-features` | markdown / json / yaml / image サブコマンドのみ | `emterm-cli` |

CLI 専用バイナリは GUI 依存（winit / wgpu / wry / GTK / WebKitGTK）を完全に排除しており、libc6 のみに依存する。これにより SSH 越しのヘッドレスサーバでもインストールでき、CLI 経由でのリッチコンテンツ表示（`emterm markdown <file>` 等）に利用されている。

### 2.2 課題

`emterm mux daemon` は `[features].gui` の中にネストされているため、`--no-default-features` 環境では使えない。

- `src-tauri/src/main.rs`：`emterm mux …` dispatch が `#[cfg(feature = "gui")]`
- `src-tauri/src/lib.rs`：`pub mod mux;`、`pub mod pty;` が `#[cfg(feature = "gui")]`
- `Cargo.toml`：`tokio`、`tokio-util`、`portable-pty`、`term_core`、`mux_ipc`、`vt100`、`anyhow`、`hostname`、`chrono`、`futures` がすべて `gui` の依存にまとめられている

リモート Linux サーバに CLI ビルドを置いて mux daemon を立てるという設計上自然なユースケースが取れない。

### 2.3 目的

`mux` 機能を `gui` から切り出して独立した cargo feature にする。これにより：

- 既定の GUI ビルドは従来通り mux を含む（`gui` が `mux` を要求）
- `--no-default-features --features mux` で「CLI + mux daemon」ビルドが取れる
- `--no-default-features` のままなら従来の CLI のみビルド

## 3. スコープ

### 3.1 含むもの

- `mux` を独立した cargo feature として `Cargo.toml` に追加
- `mux` 専用の依存パッケージ群を新しい feature に集約
- `gui` feature が `mux` feature を必須要求するように依存関係を組み直す
- `lib.rs` / `main.rs` の `cfg(feature = "gui")` を、mux 関連のみ `cfg(feature = "mux")` に書き換え
- mux モジュールが GUI 側に張っている依存（`viewer::REPLAYABLE_VIEWER_KINDS`、`scroll::ScrollPosition` 等）を CLI でもビルドできる位置に移動する
- `make` ターゲットおよび `scripts/build-dpkg.sh` に CLI+mux ビルドを追加
- CLI+mux 用の deb パッケージを新規追加（パッケージ名: `emterm-mux`）

### 3.2 含まないもの

- `mux` daemon / bridge / CLI 自体のロジック改変（feature 化のための gate 書き換え以外は触らない）
- mux プロトコルの変更
- GUI 側 mux UI（タブバー、prefix、ダイアログ等）の改変
- macOS 対応
- `emterm-cli`（既存の CLI のみ deb）の構成変更

### 3.3 影響を受けるパス

- `src-tauri/Cargo.toml`
- `src-tauri/src/lib.rs`
- `src-tauri/src/main.rs`
- `src-tauri/src/mux/`（モジュール本体）
- `src-tauri/src/pty/`（mux が依存）
- `src-tauri/src/viewer/mod.rs`（`REPLAYABLE_VIEWER_KINDS` の移動）
- `src-tauri/src/scroll.rs`（`ScrollPosition` の移動 or feature gate 調整）
- `src-tauri/src/mux/tmux_import.rs`（GUI 専用 `settings_store::save_patch_to` を使うため `mux` feature ではビルドできない → 別 gate）
- `Makefile`
- `scripts/build-dpkg.sh`

## 4. ユースケース

### UC1: SSH 越し Linux サーバで mux daemon を立てる

**前提**：
- リモートサーバはヘッドレスで libwebkit2gtk / libgtk-3 が入っていない
- ローカルマシンでは GUI 版 eMterm が動作している

**手順**：
1. 開発者がリモートサーバ向けに「CLI+mux」ビルドの deb を取得（`make mux-dpkg` で生成された `emterm-mux_<ver>_<arch>.deb`）
2. リモートサーバに `sudo dpkg -i emterm-mux_<ver>_<arch>.deb` でインストール
3. SSH ログインして `emterm mux daemon` で daemon を起動
4. 別シェル（あるいはローカルからの SSH 接続）から `emterm mux attach` で bridge 接続

**期待結果**：daemon が起動し、bridge から attach できる。GUI 版と同じ mux プロトコルで通信できる。

### UC2: 既存の GUI フルビルドが従来通り動作する

**前提**：開発者がローカル開発機で従来通り GUI 版を使う

**手順**：
1. `make build` あるいは `cargo build --release` を実行
2. `emterm` を起動
3. terminal 内から `emterm mux daemon` 等を使う

**期待結果**：従来の挙動と完全に一致する（mux feature は gui が自動で引き込む）

### UC3: CLI のみビルド（mux 無し）が従来通り動作する

**前提**：mux 不要な軽量 CLI が欲しい

**手順**：
1. `make cli-build` あるいは `cargo build --release --no-default-features` を実行
2. `emterm markdown <file>` 等を使う
3. `emterm mux daemon` は従来通り「使えません」とエラー終了する

**期待結果**：従来の `emterm-cli` deb の挙動と完全に一致する

## 5. 機能要件

### FR1: `mux` cargo feature の新設

`src-tauri/Cargo.toml` の `[features]` セクションに `mux` を追加する。

- `default = ["gui"]` は維持
- `gui = ["mux", ...]` のように `gui` が `mux` を必須要求する形にする
- `mux` 単独で有効化したビルドは PTY サブシステム、mux daemon、mux bridge、mux CLI が動作する状態

### FR2: 依存パッケージの再分類

以下を `gui` から `mux` feature に移し替える（`gui` から見れば `mux` を介して間接的に有効化される）：

- `tokio`、`tokio-util`、`futures`
- `chrono`、`anyhow`、`hostname`
- `vt100`
- `portable-pty`
- `term_core`、`mux_ipc`

これらは mux daemon / bridge / PTY が消費する依存。`gui` 固有の依存（winit / wgpu / wry / swash / zeno / fontdb / resvg / rodio / arboard / notify-rust / 等）は `gui` に残す。

`term_images` は GUI 描画パス（Kitty / SIXEL inline 表示）でのみ使うため `gui` に残す。

### FR3: モジュール gate の書き換え

`src-tauri/src/lib.rs` で：

- `pub mod mux;` を `#[cfg(feature = "mux")]` gate に変更
- `pub mod pty;` を `#[cfg(feature = "mux")]` gate に変更（PTY は mux daemon が消費するため `mux` feature で必要）
- それ以外の `#[cfg(feature = "gui")]` モジュールは現状維持

ただし `mux::tmux_import` は GUI 専用の `settings_store::save_patch_to` に依存しているため、`tmux_import` 単独で `#[cfg(feature = "gui")]` gate に保つ（mux feature ビルドではこのサブモジュールは無効、GUI ビルドだけで有効）。GUI 起動時の auto-import 経路（`main.rs` の `mux::tmux_import::import_tmux_conf_if_needed()`）はそのままで OK。

### FR4: main.rs の dispatch gate 書き換え

`src-tauri/src/main.rs` の `if sub == "mux"` 分岐：

- 現在 `#[cfg(feature = "gui")]` / `#[cfg(not(feature = "gui"))]` で振り分けている部分を `#[cfg(feature = "mux")]` / `#[cfg(not(feature = "mux"))]` に変える
- `mux` feature 無効ビルドのエラーメッセージは「CLI-only build」表記をやめ、「This build does not include mux support」のような中立的な表現にする

### FR5: GUI ↔ mux 間で共有されている定数・型の移設

mux モジュールが現在 GUI 専用モジュールに参照している以下のシンボルを CLI/mux でもビルドできる位置に移す：

- `crate::viewer::REPLAYABLE_VIEWER_KINDS`（`viewer/mod.rs:40`）→ CLI 共有モジュール（例: `crate::viewer_kinds` のような小モジュール）に移す。`viewer` モジュール側は移動先から `pub use` で再公開する
- `crate::scroll::ScrollPosition`（`scroll.rs`、23 行の小さな enum）→ CLI/mux でも参照できる位置に移す（モジュール自体を mux feature の gate に変更するか、CLI 共有モジュールに昇格する）

設計上の選択は実装計画で確定するが、要件としては「mux feature 単独ビルド時にこれらの参照がコンパイル可能であること」。

### FR6: pty モジュールの gate 変更

`src-tauri/src/pty/` 配下は mux daemon が直接使うため、`#[cfg(feature = "mux")]` gate でビルドする。

- `pty::input` は現在 GUI のキー入力エンコーダで使われている（`window_host`、`ime/*`）。これは GUI 経路でも必要なので `mux` feature 経由で有効化される（`gui = ["mux", ...]` なので問題ない）
- `pty::passthrough_scanner`、`pty::visibility`、`pty::ring`、`pty::mod`（`PtySession` 等）は mux/GUI 共通で使う

### FR7: ビルドコマンドおよび deb パッケージング

`Makefile` に新規ターゲットを追加：

- `make mux-build` — `CARGO_TARGET_DIR=src-tauri/target-host cargo build --release --no-default-features --features mux --manifest-path src-tauri/Cargo.toml`
- `make mux-dpkg` — CLI+mux ビルドで deb を作成

`scripts/build-dpkg.sh` を拡張：

- 環境変数 `EMTERM_MUX_ONLY=1` で CLI+mux モードを検知
- パッケージ名は `emterm-mux`
- バイナリは `--no-default-features --features mux` でビルド
- `.desktop` ファイル、icon、postinst の GTK cache 更新はスキップ
- DEBIAN/control の Depends は `libc6` のみ
- Description は「CLI + mux daemon for remote/headless use」のような内容

既存の `EMTERM_CLI_ONLY=1`（CLI のみ deb）の挙動は変更しない。

### FR8: ビルド成果物の動作要件

| ビルド | `emterm`（GUI 起動） | `emterm markdown <file>` 等 | `emterm mux daemon` | `emterm mux attach` |
| --- | --- | --- | --- | --- |
| `gui`（default） | ✔ | ✔ | ✔ | ✔ |
| `mux`（CLI+mux）| ✘（GUI 無効でエラー） | ✔ | ✔ | ✔ |
| なし（CLI のみ） | ✘ | ✔ | ✘（使えませんエラー）| ✘ |

`mux` feature だけで GUI を起動しようとした場合は、現状の CLI ビルドと同じく「This build does not include the GUI」相当のエラーで exit する。

## 6. 非機能要件

### NFR1: 後方互換性

- `make build`、`cargo build --release`、`make dpkg` の出力（GUI deb）は本タスク前後で機能差分ゼロ
- `make cli-build`、`cargo build --release --no-default-features`、`make cli-dpkg`（既存 CLI deb）の出力は本タスク前後で機能差分ゼロ
- 既存テスト（`cargo test` 全モード、`bun test`、`bun run typecheck`、`./scripts/run-e2e-docker.sh`）は全て pass し続ける

### NFR2: ビルド時間

`mux` feature 単独ビルド（CLI+mux）は GUI フルビルドより速いこと。具体的には winit / wgpu / wry / swash / zeno / fontdb / resvg / GTK / WebKitGTK の link を回避できているため、コンパイル時間とバイナリサイズはどちらも CLI のみ < CLI+mux < GUI フル の順になる。

### NFR3: feature 直交性

`--no-default-features --features gui` と `--no-default-features --features mux,gui` の両方が有効ビルドであること（`gui` は単独でも `mux` 経由でも `mux` を有効化する）。

## 7. 制約

### C1: portable-pty / tokio のリンクが入る

CLI+mux ビルドは libc6 だけでなく PTY と非同期ランタイムを含むため、CLI のみビルドより重い（バイナリサイズが大きくなる）。

### C2: cfg gate の細粒度

`mux::tmux_import` は GUI 専用のため `#[cfg(feature = "gui")]` のままになる。それ以外の `mux/*` は `#[cfg(feature = "mux")]` で統一する。この差は実装計画と SPEC で明示する。

## 10. リスク

- mux モジュールが GUI 専用シンボルに依存している箇所が（今回特定した 3 箇所以外に）潜在的に残っている可能性。`cargo check --no-default-features --features mux` で実際に compile error を一つずつ潰す形になる。
- 既存テストで `#[cfg(feature = "gui")]` 経由でしか走らないものを `feature = "mux"` で走らせるべきか、現状維持か、ケース毎の判断が要る。

## 11. 用語

- **GUI ビルド**：`--features gui` を有効化したビルド。winit + wgpu + wry を含むフルパッケージ
- **CLI のみビルド**：`--no-default-features` のビルド。markdown/json/yaml/image サブコマンドのみ
- **CLI+mux ビルド**：`--no-default-features --features mux` のビルド。CLI サブコマンド + mux daemon/bridge/CLI
