# terminal/state.ts リファクタリング - 要件定義書

## 1. 概要

### 1.1 背景
`src/terminal/state.ts` は約1200行のモノリシックなクラスで、ターミナル状態管理とすべてのシーケンスハンドラーが混在している。コードの可読性・保守性・テスト容易性の向上が必要。

### 1.2 目的
TerminalStateクラスをデータ指向アプローチでリファクタリングし、ハンドラーを機能カテゴリ別に外部関数として分離する。

### 1.3 スコープ
- TerminalStateクラスの内部実装のリファクタリング
- ハンドラー関数の外部モジュールへの分離
- 対応するテストファイルの分割
- 既存の公開APIは維持

## 2. ビジネス要件

### 2.1 ビジネス目標
- コードの保守性向上
- テスト容易性の向上
- 新しいシーケンス追加時の開発効率向上

### 2.2 対象ユーザー
| ユーザータイプ | 説明 |
|----------------|------|
| 開発者 | コードベースを保守・拡張する開発者 |

### 2.3 期待される効果
- 機能別にファイルが分離され、変更箇所の特定が容易になる
- テストが機能単位で実行でき、問題の切り分けが容易になる
- 新しいシーケンスの追加が体系的に行える

## 3. 機能要件

### 3.1 機能一覧
| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | データ構造の分離 | TerminalStateを純粋なデータ構造として定義 | 高 |
| F02 | ハンドラーの外部化 | シーケンスハンドラーを外部関数として分離 | 高 |
| F03 | テストの分割 | ハンドラーごとに対応するテストファイルを作成 | 高 |
| F04 | パース/バリデーション分離 | パース処理とミューテーションを分離 | 中 |
| F05 | シーケンスセマンティクス一元化 | デフォルトパラメータ、クランプ等を一元管理 | 中 |

### 3.2 機能詳細

#### F01: データ構造の分離

**説明**: TerminalStateクラスを純粋なデータ構造として再定義し、ビジネスロジックを含まないようにする。

**現状の構造**:
- TerminalStateクラスがデータとロジックを両方保持
- private メソッドとしてハンドラーが実装されている

**目標の構造**:
- TerminalStateはデータ（バッファ、カーソル、モード等）のみを保持
- processAction は外部ハンドラーにディスパッチ

#### F02: ハンドラーの外部化

**説明**: 各シーケンスハンドラーを機能カテゴリ別の外部関数として分離する。

**ディレクトリ構造**:
```
src/terminal/
├── handlers/
│   ├── index.ts           # エクスポート集約
│   ├── csi_cursor.ts      # カーソル移動 (CursorUp, CursorDown, CursorPosition等)
│   ├── csi_screen.ts      # 画面操作 (EraseInDisplay, EraseInLine, EraseCharacters)
│   ├── csi_edit.ts        # 編集操作 (InsertLines, DeleteLines, InsertCharacters, DeleteCharacters)
│   ├── csi_scrolling.ts   # スクロール操作 (ScrollUp, ScrollDown, SetScrollRegion)
│   ├── csi_char_attrs.ts  # 文字属性 (SGR)
│   ├── csi_modes.ts       # モード設定 (SetMode, ResetMode)
│   ├── csi_device.ts      # デバイス応答 (DeviceStatusReport, DeviceAttributes)
│   ├── esc_handlers.ts    # ESCシーケンス (SaveCursor, RestoreCursor, Index等)
│   ├── osc_handlers.ts    # OSCシーケンス (SetTitle, Hyperlink等)
│   ├── c0_handlers.ts     # C0制御文字 (CR, LF, BS, HT等)
│   └── print_handler.ts   # 文字出力処理
├── state.ts               # TerminalStateクラス（データ + ディスパッチ）
├── cursor.ts              # 既存（維持）
├── modes.ts               # 既存（維持）
├── sgr.ts                 # 既存（維持）
└── ...
```

**ハンドラー関数のシグネチャ**:
```typescript
// 状態を受け取り、変更を適用する純粋関数スタイル
function handleCursorUp(state: TerminalState, count: number): void;
function handleEraseInDisplay(state: TerminalState, mode: EraseMode): void;
```

#### F03: テストの分割

**説明**: ハンドラーごとに対応するテストファイルを作成する。

**テストファイル構造**:
```
src/terminal/handlers/
├── csi_cursor.test.ts
├── csi_screen.test.ts
├── csi_edit.test.ts
├── csi_scrolling.test.ts
├── csi_char_attrs.test.ts
├── csi_modes.test.ts
├── csi_device.test.ts
├── esc_handlers.test.ts
├── osc_handlers.test.ts
├── c0_handlers.test.ts
└── print_handler.test.ts
```

既存の `state.test.ts` は統合テストとして維持するか、各ハンドラーテストに分解する。

#### F04: パース/バリデーション分離

**説明**: パース処理とミューテーション（状態変更）を分離する。

**現状**:
- handleCsi内でパラメータ解析と状態変更が混在

**改善**:
- パラメータのパースとバリデーションを独立した関数に
- ミューテーションは検証済みパラメータを受け取る

**例**:
```typescript
// パース関数
function parseCursorPosition(data: { row?: number; col?: number }): { row: number; col: number };

// ハンドラー関数（検証済みパラメータを受け取る）
function handleCursorPosition(state: TerminalState, row: number, col: number): void;
```

#### F05: シーケンスセマンティクス一元化

**説明**: ANSIシーケンスのセマンティクス（デフォルト値、クランプ処理等）を一元管理する。

**管理項目**:
- デフォルトパラメータ値（0/1変換等）
- パラメータのクランプ（画面範囲への制限等）
- 1-indexed から 0-indexed への変換

**実装アプローチ**:
```typescript
// defaults.ts または semantics.ts
export const CSI_DEFAULTS = {
  CursorUp: 1,
  CursorDown: 1,
  CursorPosition: { row: 1, col: 1 },
  // ...
};

export function clampToScreen(col: number, row: number, cols: number, rows: number): { col: number; row: number };
export function toZeroIndexed(value: number): number;
```

## 4. 非機能要件

### 4.1 パフォーマンス要件
- リファクタリング後もパフォーマンス劣化なし
- 関数呼び出しオーバーヘッドは無視できるレベル

### 4.2 互換性要件
- 公開API（processAction, resize, extractText等）は維持
- 既存テストが全てパス

### 4.3 保守性要件
- 各ファイルは200-300行以内を目安
- 明確な責務分離
- 一貫した命名規則

## 5. 制約条件

### 5.1 技術的制約
- 既存モジュール（cursor.ts, modes.ts, sgr.ts）はそのまま維持
- TypeScript のみ（JavaScript不可）
- Bun test との互換性維持

### 5.2 設計上の制約
- TerminalStateの公開メソッド・プロパティは変更不可
- クラスベースの構造は維持（完全な関数型への移行は行わない）
