# WASM TerminalCore (Grid + State Data Layer) - 要件定義書

## 1. 概要

### 1.1 背景

Sprint 0でUnicode幅計算のWASM化に成功し、2.23倍の性能改善を達成した。次のステップとして、ターミナルのデータ層（Cell, CellAttributes, CursorState, TerminalModes, Grid）をRust/WASMのlinear memoryに移行する。これにより:
- JSヒープのGC圧迫を軽減
- Cell/Lineオブジェクトのアロケーション/デアロケーションコストを排除
- 後続Sprint（ハンドラ移行）の基盤を構築

### 1.2 目的

ターミナルのビューポートグリッド（rows×cols）と関連ステートをWASM linear memoryに移行し、JS GC負荷を軽減する。

### 1.3 スコープ

**対象:**
- Cell構造体（文字、幅、属性）
- CellAttributes（色、スタイルフラグ）
- CursorState（位置、属性、保存/復元）
- TerminalModes（autoWrap、originMode等）
- ビューポートグリッド（rows×cols）
- TabStops
- Dirty行トラッキング

**対象外:**
- スクロールバック/リングバッファ（Sprint 5）
- ハンドラ移行（Sprint 2-5）
- ANSIパーサー/Binary IPC（Sprint 6）
- Renderer移行（Sprint 7）

## 2. ビジネス要件

### 2.1 ビジネス目標

ターミナルの内部データ構造をWASMに移行し、後続Sprintの基盤を確立する。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| eMterm利用者 | メモリ使用量の改善とGCポーズの削減を体感 |
| Sprint 2-7の開発者 | WASMのGrid/State APIを使ってハンドラを移行 |

### 2.3 期待される効果

- ビューポートCellデータがlinear memoryに移行（GC対象外）
- 後続Sprintでハンドラ移行時にGrid書き込みがWASM内完結可能に
- Cell/Lineオブジェクト生成コスト削減

### 3.1 ユースケース一覧

| UC06 | リサイズ | TerminalState | 中 |

### 3.2 ユースケース詳細

#### UC01: Cell読み書き

**アクター**: TSハンドラ（print_handler等）

**基本フロー**:
1. ハンドラがTerminalStateのgetActiveBuffer()経由でWASM APIを呼び出す
2. WASM TerminalCoreがlinear memory上のCellを更新
3. 対象行がdirtyとしてマークされる

#### UC04: ビューポート描画データ取得

**アクター**: Canvas Renderer

**基本フロー**:
1. RendererがDirty行リストを取得
2. 各dirty行のCellデータをWASMから読み取り
3. TextSpanへのグループ化を実行し描画

## 5. 非機能要件

### 5.1 パフォーマンス要件

- setCell/getCell: 1回あたりのJS-WASM境界コスト < 100ns
- ビューポートデータ取得: 80行×120列を < 1ms
- メモリ使用量: 80×120ビューポートで < 500KB（WASM linear memory）

### 5.2 互換性要件

- 既存の全テスト（1779件）がパスすること
- RendererがWASM Gridから正しく描画できること
- 既存ハンドラのAPI変更は最小限

### 5.3 保守性要件

- Rustコードに`#[cfg(test)]`インラインテストを含む
- TypeScriptグルーレイヤーは薄いラッパーに留める

## 6. データ要件

### 6.1 データモデル概要

```
TerminalCore (WASM)
├── ViewportGrid
│   └── Cell[] (rows × cols, linear memory)
│       ├── char_data (inline UTF-8)
│       ├── width (0, 1, 2)
│       └── PackedAttrs (fg, bg, style flags)
├── CursorState
│   ├── position (col, row)
│   ├── attrs (PackedAttrs)
│   └── saved (optional snapshot)
├── TerminalModes (bitfield)
├── TabStops (Vec<bool>)
└── DirtyRows (bitset)
```

## 7. 制約条件

### 7.1 技術的制約

- wasm-bindgenの型制約（構造体の直接返却不可、プリミティブ型推奨）
- WASM linear memoryはJSから直接読み取り可能だがレイアウト依存
- Cellの文字データは可変長（ASCII 1byte〜emoji 25+ bytes）

### 7.2 スコープ制約

- スクロールバックはTS側のUnifiedBufferに残す
- ハンドラは引き続きTS側で動作（Sprint 2以降で移行）
- Rendererは変更最小限（APIアダプタ層で吸収）

## 8. 想定される課題とリスク

| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| Cell文字データの可変長対応 | 高 | インラインバッファ + ヒープフォールバック |
| JS-WASM境界の呼び出しコスト | 中 | バッチAPI（getViewportRow等）で軽減 |
| 既存テストとの互換性 | 高 | 段階的置換、TSテスト全パスを各段階で確認 |
| Rendererとのインターフェース | 中 | アダプタ層で既存APIを維持 |
