# WASM Renderer Zero-Copy + Carry-over - 要件定義書

## 1. 概要

### 1.1 背景
Sprint 6でANSI Parser + Binary IPCが完了し、PTY → WASM → 画面更新の直通パイプラインが実現した。しかし、WASM → Renderer間のデータ転送にはまだ最適化余地がある。現在のRendererは`LineAccessor`インターフェース経由でセルごとに4+回のWASM呼び出しを行っており、80列の場合1行で320回以上のWASM境界越えが発生している。

### 1.2 目的
1. Renderer描画パスで`get_row_packed()`を直接パースし、JS中間オブジェクト生成を回避
2. WasmLineProxyのdirtyフィールドをWASM bitsetのgetter委譲に変更
3. Kitty Graphics Protocolのimage_id照合を実装し、複数画像同時転送の信頼性を向上

### 1.3 スコープ
- CanvasRendererのviewport/scrollback描画パスの最適化
- WasmLineProxy.dirtyのgetter委譲化
- Kitty image_id生成とレスポンス照合
- 既存のJS fallbackパスは維持（WASM初期化失敗時用）

## 2. ビジネス要件

### 2.1 ビジネス目標
WASM化ロードマップの最終Sprint。描画パフォーマンスの最適化とcarry-over項目の完了。

### 2.2 対象ユーザー
| ユーザータイプ | 説明 |
|----------------|------|
| eMtermユーザー | ターミナルを日常使用するユーザー全般 |
| emterm image CLI利用者 | 画像表示CLIコマンドの利用者 |

### 2.3 期待される効果
- dirty行の描画パフォーマンス向上（WASM呼び出し回数: cols×4+ → 1回/行）
- JS GC圧力低減（Cell/CellAttributes/Lineオブジェクト生成回避）
- 複数画像同時転送時のレスポンス照合の信頼性向上

### 3.2 ユースケース詳細

#### UC01: 通常のターミナル操作

**アクター**: ユーザー

**事前条件**:
- WASMが正常に初期化されている

**基本フロー**:
1. PTYデータがWASMで処理され、dirty行が記録される
2. Rendererがdirty行のpacked binary dataを取得
3. バイナリデータをインラインパースしてspan構築
4. Canvas 2D APIで描画

**事後条件**:
- dirty行が2ms以内に描画完了

#### UC02: 大量出力のスクロールバック閲覧

**アクター**: ユーザー

**基本フロー**:
1. ユーザーがスクロールアップ
2. Rendererがスクロールバック行のpacked dataを取得（`get_scrollback_row_packed()`）
3. packed dataをインラインパースして描画

#### UC03: 複数画像の連続表示

**アクター**: ユーザー

**基本フロー**:
1. `emterm image img1.png && emterm image img2.png` を実行
2. 各コマンドがユニークなimage_idで画像データを送信
3. ターミナルがimage_idを照合してレスポンスを返信
4. CLIがレスポンスのimage_idを確認して正常終了

## 4. 機能要件

### 4.1 機能一覧
| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | Packed Row描画パス | get_row_packed()の直接パースによるspan構築 | 高 |
| F02 | Scrollback Packed描画 | スクロールバック行のpacked描画対応 | 高 |
| F03 | Dirty描画最適化 | render()のdirty行処理をpackedパスに統合 | 高 |
| F04 | ForceRender最適化 | forceRender()の全行描画をpackedパスに統合 | 高 |
| F05 | WasmLineProxy dirty getter | dirtyフィールドをWASM bitset getter委譲に変更 | 中 |
| F06 | Kitty image_id生成 | ユニークimage_idのatomicカウンタ生成 | 中 |
| F07 | Kitty response照合 | CLIがimage_id付きレスポンスを照合 | 中 |

### 4.2 機能詳細

#### F01: Packed Row描画パス

**説明**: `get_row_packed(row)` が返すUint8Arrayをインラインでパースし、Cell/Line/CellAttributesオブジェクトを生成せずにTextSpanを構築する。

**入力**:
- packed: Uint8Array（バイナリフォーマット: cell = char_len(1) + char_data + width(1) + fg(4) + bg(4) + flags(2 LE)）
- cols: number

**出力**:
- TextSpan[]（既存のrenderSpanText()互換）

**処理フロー**:
1. Uint8Arrayを先頭から順次読み取り
2. 各セルのchar, width, fg, bg, flagsをバイナリからデコード
3. 前セルとの属性比較（10バイト: fg 4 + bg 4 + flags 2）
4. 属性が同じならspan継続、異なればspan確定 → 新span開始
5. 完成したTextSpan[]を返却

#### F05: WasmLineProxy dirty getter

**説明**: `dirty`フィールドをES getter/setterに変更。`get dirty()`はWASM coreの`is_row_dirty(row)`を呼び出す。

#### F06: Kitty image_id生成

**説明**: `generate_kitty_sequence()`でAtomicU32カウンタから生成したユニークimage_idを使用。

#### F07: Kitty response照合

**説明**: `wait_for_kitty_response()`がimage_id付きレスポンス`ESC _G i={id};OK ESC \`をパースし、送信したimage_idと照合。

## 5. 非機能要件

### 5.1 パフォーマンス要件
- 1 dirty行の描画パス（データ取得→パース→Canvas描画）が2ms以内
- JS中間オブジェクト（Cell, Line, CellAttributes）の生成数がゼロ（packed描画パス使用時）
- WASM境界越え: 1行あたり1回（get_row_packed）

### 5.2 互換性要件
- WASM初期化失敗時はJS fallbackパス（既存のLineAccessor経由）が動作
- 既存のテスト全パス維持
- WASMバイナリサイズ 80KB未満

### 5.3 保守性要件
- packed描画パスとJS fallbackパスの切り替えはTerminalState.getWasmCore()のnullチェックで判定
