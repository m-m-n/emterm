# キー入力パフォーマンス改善 - 要件定義書

## 1. 概要

### 1.1 背景
eMtermのキーリピート速度が他のターミナルエミュレータ（WezTerm, Alacritty等）と比較して遅い。特に英字キーの長押し時に顕著であり、操作体感に影響を与えている。

### 1.2 目的
キー入力パイプライン全体を最適化し、他のターミナルエミュレータと同等のキーリピート速度を実現する。

### 1.3 スコープ
- キー入力パイプラインの最適化（フロントエンド → IPC → バックエンド → PTY）
- 対象外: PTY出力（読み取り側）の最適化、レンダリング最適化

## 2. ビジネス要件

### 2.1 ビジネス目標
ターミナルエミュレータとしての基本品質（入力応答性）を他のモダンターミナルと同等にする。

### 2.2 対象ユーザー
| ユーザータイプ | 説明 |
|----------------|------|
| ターミナルユーザー | 日常的にシェル操作やエディタを使用するユーザー |

### 2.3 期待される効果
- キーリピート速度が他のモダンターミナルと同等になる
- 長押し操作時のストレスが解消される

## 3. ユースケース

### 3.1 ユースケース一覧
| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | 文字キーの長押し入力 | ユーザー | 高 |
| UC02 | 矢印キー・BackSpaceの長押し | ユーザー | 高 |
| UC03 | IME使用中のキー入力 | ユーザー | 高 |
| UC04 | 単打キーの即時応答 | ユーザー | 高 |

### 3.2 ユースケース詳細

#### UC01: 文字キーの長押し入力

**アクター**: ユーザー

**事前条件**:
- ターミナルセッションが開始されている
- IMEがオフの状態

**基本フロー**:
1. ユーザーが英字キー（例: `a`）を押し続ける
2. OSのキーリピート設定に従い、keydownイベントが連続的に発生する
3. 各keydownイベントがPTYに書き込まれる
4. 文字が高速に連続表示される

**事後条件**:
- 他のターミナルと同等の速度で文字が入力される

#### UC02: 矢印キー・BackSpaceの長押し

**アクター**: ユーザー

**事前条件**:
- ターミナルセッションが開始されている

**基本フロー**:
1. ユーザーが矢印キーまたはBackSpaceを押し続ける
2. keydownイベントが連続的に発生する
3. エスケープシーケンスまたは制御文字がPTYに書き込まれる
4. カーソル移動・文字削除が高速に実行される

#### UC03: IME使用中のキー入力

**アクター**: ユーザー

**事前条件**:
- IMEがオンの状態

**基本フロー**:
1. ユーザーがIMEで日本語入力を行う
2. 変換候補の選択、確定操作を行う
3. 確定されたテキストがPTYに送信される

**事後条件**:
- IMEの動作に一切影響を与えない
- 変換・確定が正常に動作する

#### UC04: 単打キーの即時応答

**アクター**: ユーザー

**事前条件**:
- ターミナルセッションが開始されている

**基本フロー**:
1. ユーザーが単一のキーを押す
2. 即座にPTYに書き込まれる

**事後条件**:
- 単打キーの入力レイテンシが現行と同等以上

## 4. 機能要件

### 4.1 機能一覧
| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | IPC最適化 | Tauri invokeのオーバーヘッド削減 | 高 |
| F02 | シリアライゼーション最適化 | JSON経由のバイト配列変換コスト削減 | 高 |
| F03 | ロック競合削減 | Rust側のMutex取得回数・コスト削減 | 高 |
| F04 | IME互換性維持 | 最適化によりIME動作が影響を受けないこと | 高 |

### 4.2 機能詳細

#### F01: IPC最適化

**説明**: 現在のTauri invoke（リクエスト-レスポンスモデル、JSON経由）を最適化し、キー入力のIPCオーバーヘッドを削減する。

**現状の問題**:
- 各キー押下で `invoke("pty_write", { sessionId, data: Array.from(bytes) })` が呼ばれる
- invokeはリクエスト-レスポンス型で、レスポンス待ちのオーバーヘッドがある
- fire-and-forgetパターン（awaitしない）は採用済みだが、invoke自体のセットアップコストが残る

**改善方針**:
- Tauri Channelやevent等、より軽量なIPCメカニズムの検討
- バイナリ転送の活用（JSON変換の回避）

#### F02: シリアライゼーション最適化

**説明**: `Array.from(bytes)` によるUint8Array→number[]変換とJSONシリアライズを回避する。

**現状の問題**:
- `Array.from(bytes)` でTyped ArrayをプレーンなJavaScript配列に変換
- JSONシリアライザがnumber[]を文字列化
- Rust側でVec<u8>にデシリアライズ

**改善方針**:
- バイナリIPCの活用（プロジェクトではWASM連携で既に使用実績あり）

#### F03: ロック競合削減

**説明**: Rust側でのセッションロック取得を最適化する。

**現状の問題**:
- pty_writeコマンドハンドラで毎回:
  1. async RwLock でPtyManagerからセッション取得
  2. async Mutex でPtySession取得
  3. sync StdMutex でwriter取得
- キーリピート時に高頻度でロック取得が発生

**改善方針**:
- ロック回数の削減（セッションハンドルのキャッシュ等）
- より軽量なロック戦略の検討

#### F04: IME互換性維持

**説明**: すべての最適化がIME（日本語入力）の動作に影響を与えないことを保証する。

**制約**:
- EditContext API（Chromium/WebView2）の動作を維持
- Textarea fallbackモードの動作を維持
- IME composition中のキーイベントフィルタリングを維持

## 5. 非機能要件

### 5.1 パフォーマンス要件
- キーリピートスループット: WezTerm/Alacrittyと同等
- 単打キーレイテンシ: 現行と同等以上（劣化させない）
- CPU使用率: キーリピート時の増加を最小限に抑える

### 5.2 互換性要件
- IME（日本語入力）: 完全互換
- マルチタブ: 既存のタブ切り替え・入力分離を維持
- 既存のキーバインド: 全てのショートカットが正常に動作

### 5.3 保守性要件
- コードの複雑さを不必要に増加させない
- 既存のテストが通り続けること

## 6. 制約条件

### 6.1 技術的制約
- Tauri v2のIPC機構の範囲内で最適化する
- portable_pty crateのAPI制約
- WebView2/WebKitGTKのイベントモデル制約

### 6.2 設計上の制約
- 単打キーのレイテンシを増加させないこと（バッファリングによる遅延を許容しない）
- IMEの動作に影響を与えないこと
