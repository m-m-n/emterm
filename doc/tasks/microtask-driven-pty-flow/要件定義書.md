# 要件定義書: Microtask 駆動の PTY パース処理

## 1. 概要

eMterm のフロントエンドにおいて、 PTY 出力データを WASM パーサに流す処理 (`processPendingData`) は現在 `requestAnimationFrame` (rAF) でスケジュールされている。 WebKitGTK は visibility=hidden / window occlusion / ワークスペース切替時に rAF を停止するため、その間 WASM パースが止まり、ack を返さなくなり、 backend の `in_flight` が溜まり、 reader thread が `wait_for_drain` でブロックされる。

本機能では xterm.js が採用している方式に倣い、 WASM パース処理の駆動を rAF から **MessageChannel / queueMicrotask 系** に切り替え、 visibility 状態に左右されずに PTY データの消費が継続するようにする。

## 2. 背景

### 2.1 直近の事象

- 2026-05-08 00:48:46 (JST) に PTY バックプレッシャーで eMterm が固まる事象が発生
- backend `in_flight` 8.4MB が 107 分間ドレインされず、 PTY 出力が完全停止
- 直接原因は WebKit の rAF 停止により、フロントの WASM パースが止まったこと
- 既存の保険機構 (rAF heartbeat / visibility-aware streaming) は対症療法として動作するが、 rAF 駆動という構造そのものは脆弱なまま

### 2.2 既存の関連実装

- `visibility-aware-pty-streaming` (FR1〜FR16): visibility=hidden 時の backend 一時停止と shadow snapshot 機構
- `visibility-raf-heartbeat`: rAF stall を検知して hidden 状態を強制発火する保険
- `visibility-render-recovery`: focus 戻り時の WASM 健全性プローブ
- 既存 ack 機構: `pty_ack` Tauri コマンドと `SessionBackpressure::{add_sent, ack, wait_for_drain, hidden_wake, force_wake}`、 `ACK_FLUSH_BYTES` / `ACK_FLUSH_INTERVAL_MS` によるコアレッシング送信

ack のコア機構は既に揃っているが、その ack を送る `processPendingData` が rAF でしか起動されないため、 rAF 停止下では ack が出ず backend が詰まる、というのが本件の本質。

### 2.3 xterm.js の方式

- パース処理は内部キューに enqueue し、 `MessageChannel.postMessage` で次の microtask に処理を譲る
- メインスレッドをブロックしない
- visibility=hidden でも microtask は走るので処理が止まらない
- 完了通知を呼び出し側に返してフロー制御を組ませる

## 3. 用語定義

- **microtask 駆動**: `MessageChannel` の `port.postMessage` ハンドラまたは `queueMicrotask` を用いて次のイベントループターンで処理関数を呼ぶ方式
- **rAF 駆動**: `requestAnimationFrame` のコールバックで処理関数を呼ぶ方式 (WebKitGTK ではタブ非表示などで停止する)
- **process 関数**: `pty-handler.ts` の `processPendingData(trigger)` を指す
- **ack**: backend `SessionBackpressure.in_flight` を減算する `pty_ack` Tauri 呼び出し
- **rAF heartbeat**: `visibility-raf-heartbeat` 機能で導入された rAF stall 検知ロジック

## 4. 目的

- visibility=hidden / window occlusion / ワークスペース切替でも PTY パース処理を継続する
- 結果として ack が継続的に送られ、 backend の `in_flight` が溜まらないようにする
- 構造的に脆弱な rAF 依存を取り除き、保険機構 (rAF heartbeat / visibility-aware streaming) に頼らずとも基本動作が壊れない実装にする
- 既存の保険機構は本機能と併存し、別目的 (visibility hidden 時の backend 帯域節約や WASM 健全性プローブ) として機能し続ける

## 5. スコープ

### 5.1 含むもの

- `pty-handler.ts` の `scheduleProcessing` を rAF から microtask 駆動に切り替える
- microtask 駆動下で既存 ack コアレッシングが正しく動作することの確認と必要な調整
- microtask 駆動と Canvas レンダリング (rAF 駆動のままで可) の責務分離
- 単体テスト / 既存 E2E の継続成立確認

### 5.2 含まないもの

- backend → frontend の **新規** ack イベント (現状 ack は frontend → backend の片方向で十分機能している)
- Canvas レンダリング自体の microtask 化 (描画は rAF タイミングが妥当)
- visibility-aware streaming / rAF heartbeat / visibility-render-recovery の機能変更 (併存維持)
- mux 経路の APC `SetVisibility` 等プロトコルの変更

## 6. 利用シナリオ

### 6.1 主なユーザーストーリー

#### US1: ワークスペース切替中の AI セッション継続

ターミナル常用ユーザーとして、 Claude Code を eMterm で動かしたまま別ワークスペースに移動し、長時間後に戻ってきても eMterm がフリーズしていないことを期待する。

**受け入れ基準:**
- ワークスペースから外れて rAF が停止しても、 PTY データの WASM パースが継続する
- backend `in_flight` が `HIGH_WATER` を超えない
- 復帰時に追加の操作なしで最新画面が描画される

#### US2: ウィンドウ最小化中のビルド継続

開発者として、 ウィンドウを最小化したまま長時間ビルドを走らせても、 復帰時に出力が完全に処理済みで終了行まで表示されていることを期待する。

**受け入れ基準:**
- 最小化中も PTY ストリーミング (visibility-aware で hidden 時は backend 抑制、 visible 中は microtask 経路) が機能する
- 復帰時に未処理データが残ったままフリーズしない

#### US3: 通常入力時の打鍵レイテンシ無回帰

ユーザーとして、 microtask 駆動になっても通常入力 (キー押下→画面反映) のレイテンシが体感で変わらないことを期待する。

**受け入れ基準:**
- 通常 streaming 中の打鍵レイテンシが既存比で有意に劣化しない (実測 ±10% 以内)
- 連続出力 throughput が既存比で有意に劣化しない (実測 ±10% 以内)

## 7. 機能要件

### FR1: WASM パース処理の microtask 駆動化

`pty-handler.ts` の `scheduleProcessing` を以下のように変更する。

- 第一選択: `MessageChannel` を 1 つだけ用意し、 `port2.onmessage` ハンドラで `processPendingData("microtask")` を呼ぶ。 `port1.postMessage(0)` でスケジュールする
- フォールバック: `MessageChannel` が利用できない環境では `queueMicrotask` を使用する
- どちらも利用できない環境では `setTimeout(fn, 0)` を最終フォールバックとする
- `rafScheduled` 相当の重複スケジュール抑止フラグは保持し、名称を意味に合わせて `processScheduled` 等にリネームする
- `scheduleToken` による古いスケジュール無効化機構は維持する

`requestAnimationFrame` は本処理経路から削除する。

### FR2: Canvas レンダリングの rAF 維持

`processPendingData` の中で行われる Canvas 再描画 (例: `forceRender` / `paintIfDirty`) は、 microtask で実行された後でも視覚更新は次の rAF タイミングで行われるよう、 既存の Canvas レンダラ呼び出し方式を変更しない。 つまり「データ消費は microtask、 描画は rAF」の責務分離を行う。

なお WASM 側 grid の dirty flag に基づく差分描画は既存通り rAF 経路で起きてよい。 microtask 駆動が止まらない限り、 dirty flag は正しく更新されるため、 visibility=hidden 中に視覚更新がなくとも内部状態は最新化される。

### FR3: ack コアレッシングの継続動作保証

既存の ack 送信ロジック (`pendingAckBytes` / `ACK_FLUSH_BYTES` / `ACK_FLUSH_INTERVAL_MS` / `ackFlushTimer`) を microtask 駆動下でも正しく動作させる。

- microtask が連続して発火しても `ackFlushTimer` の `setTimeout` が時間ベースで flush することを保証する
- `ACK_FLUSH_INTERVAL_MS` は現状値を維持する
- microtask 連発で `pendingAckBytes` が `ACK_FLUSH_BYTES` を頻繁に超える場合の挙動を回帰テストで確認する

### FR4: backend reader との整合性維持

backend 側 `SessionBackpressure::wait_for_drain` は `LOW_WATER` まで in_flight が減少するまで block する。 microtask 駆動で ack が継続的に送られれば、 visible 中は wait_for_drain が ack で wake し reader が再開する。

- 本要件で backend 側のコードを変更しない
- ただし microtask 駆動で hidden 中も ack が走り続けるため、 `visibility-aware-pty-streaming` の `hidden_wake` 経路や `pty_set_visibility(false)` の動作に副作用が出ないことを確認する

### FR5: 既存保険機構との併存

以下の機構は本機能の実装後も維持する。

- `visibility-raf-heartbeat`: rAF stall を検知して `setVisibility(false)` を発火する仕組みは維持する。 rAF 停止が microtask 駆動の停止を意味しない構造になるため、 hidden 通知の意味が「描画が止まっている」程度に弱まるが、 backend の帯域節約 (visibility-aware streaming) のトリガとして引き続き有効
- `visibility-aware-pty-streaming`: hidden 時の backend 抑制 / shadow snapshot は維持
- `visibility-render-recovery`: focus 戻り時の WASM 健全性プローブは維持

### FR6: スケジューリング統計の観測性

診断のため、 `scheduleProcessing` の経路別呼び出し回数を内部で記録し、既存の `processPendingData` 開始時のログ (`trigger` 引数) で確認できるようにする。 `trigger` の値域から `"raf"` を削除し、 `"microtask"` / `"timer"` (timer fallback 用) を追加する。

### FR7: rAF 経路の完全削除

`scheduleProcessing` 内の `requestAnimationFrame` / `cancelAnimationFrame` 呼び出しは削除する。 `rafHandle` / `rafScheduled` 等の状態変数は意味に合わせてリネームする (例: `pendingHandle` / `processScheduled`)。

`pty-handler.ts` 内の他箇所で rAF を使っている経路 (例: 描画再開トリガ) はそのまま残す。

## 8. 非機能要件

### NFR1: visibility=hidden / window occlusion での処理継続

- ウィンドウが hidden / occluded / 別ワークスペースの状態でも、 PTY データを受信した時点で WASM パースと ack が継続する
- 30 分間 hidden 状態を維持しても backend `in_flight` が `HIGH_WATER` (`8 MiB`) を超えない (visibility-aware streaming が hidden 時に backend 送信を抑止するため、 そもそも in_flight は積まれないが、 visibility 通知失敗時の保険としても microtask 駆動が機能する)

### NFR2: パフォーマンス無回帰

- 連続出力 throughput (`yes | head -c 100M` 相当) が既存比 ±10% 以内
- 打鍵から画面反映までのレイテンシが既存比 ±10% 以内
- microtask の連発による CPU 使用率増が現実利用ケースで 1% 以内

### NFR3: 既存テスト・機構との互換性

- `bun test` の既存全テストが pass
- `cargo test` の既存全テストが pass
- 既存 E2E specs (`./scripts/run-e2e-docker.sh test`) が回帰なく pass
- `visibility-raf-heartbeat` / `visibility-aware-pty-streaming` / `visibility-render-recovery` の各 SPEC の挙動が変わらない

### NFR4: 観測性

- microtask 駆動への切替で生成される `[DIAG-*]` 系ログ形式は既存と互換にする
- `trigger` ラベルが `"microtask"` 主体に変わることだけが観測上の差分になる

### NFR5: クロスプラットフォーム

- Linux (WebKitGTK) / Windows (WebView2) の両方で動作する
- どちらの WebView でも `MessageChannel` は標準で利用可能

## 9. 想定される利用シーン

| シーン | 期待動作 |
|--------|----------|
| 常時可視で AI セッションを使う | rAF 駆動時と同等の応答性で動作する |
| ワークスペース切替で長時間離席 | hidden 中も microtask は走る。 visibility-aware streaming が backend 抑制を引き受けるが、 通知失敗等で抑制が効かなくとも microtask により ack が送られ in_flight が積まれない |
| ウィンドウ最小化中のビルド完了待ち | 同上 |
| 多数タブ並列稼働 | 各タブの microtask は独立してスケジューリングされる。 1 タブが処理に時間を要しても他タブの microtask は次の event loop で走る |

## 10. 制約

- 後方互換性は最優先しない (新規ブランチ `fix/freeze` での破壊的改修許可済み)
- backend / mux daemon / mux IPC プロトコルへの変更は行わない
- WASM パーサ本体 (`wasm/src/`) への変更は行わない

## 11. リスクと対策

| リスク | 対策 |
|--------|------|
| microtask 連発でメインスレッドの input event 処理が遅延する | 1 microtask あたりの処理上限 (既存の `WASM_TIME_BUDGET_MS` 相当) を維持し、 タイムバジェット超過時は次の microtask に繰り越す |
| `MessageChannel` 経由のメッセージ配送オーバーヘッドが累積する | `MessageChannel` は再利用し、 ハンドラを 1 度だけ登録する。 1 schedule あたりの postMessage は 1 回 |
| `queueMicrotask` フォールバックでスタック深さが増える | `queueMicrotask` は新しい microtask スコープを作るためスタックは伸びない。 念のため処理量バジェットで打ち切る |
| ack コアレッシングの `setTimeout` が visibility=hidden で throttle される | `ACK_FLUSH_BYTES` 経由のサイズトリガが効くため、 タイマ throttle 下でも一定量で flush される。 hidden 中は backend が抑制するため不足は表面化しない (visibility-aware streaming の責務) |
