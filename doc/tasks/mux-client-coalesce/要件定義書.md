# mux client coalesce (phase1) - 要件定義書

## 1. 概要

### 1.1 背景

mux ウィンドウでの大量出力スループットが、通常タブに比べ著しく低い。

- mux ウィンドウで `seq 1 10000000` が 2% CPU・2分26秒（通常タブは 96% CPU・3.8秒）
- daemon 直結 E2E（bridge/GUI 描画を含まない、term_core パース込み）の実測:
  - N=10,000,000 → 84.77 MiB / 124,233 フレーム / 29.75s = 2.85 MiB/s
  - N=1,000,000 → 7.52 MiB / 13,958 フレーム / 3.15s = 2.39 MiB/s
- 85 MiB が約 12 万フレーム（≈700 B/フレーム）に分割されており、フレーム数の多さがオーバーヘッドの核心
- `pump()` はバイトを最大 1 MiB まで coalesce する（`COALESCE_CAP`）が、coalesce 後も mux 経路では各 mux APC フレームごとに `process_pty_data_fully` が走る
- 律速はパース起動回数。1 MiB ÷ 700 B ≈ 1400 フレーム/pump、各フレームごとに parse が走る

### 1.2 目的

client(GUI)側で、1回の pump 内に届いた連続する同一アクティブペイン宛の `PtyOutput` フレームの inner payload を連結し、`term_core` へのパース起動を 1 回にまとめることで、mux ウィンドウの大量出力スループットを改善する。

### 1.3 スコープ

- 対象: `src-tauri/src/tabs.rs` の mux 確立時の出力処理経路（`process_combined` の抽出フレームループ）
- 本タスクは mux 性能改善の phase1（client側 PtyOutput inner payload の coalesce）のみを対象とする。phase2/3 は別タスク
- daemon 側・bridge 側・transport 層・WebView 版（`src/`）は変更しない

## 2. ビジネス要件

### 2.1 ビジネス目標

AI コーディングツール（Claude Code 等）が大量出力を流す利用形態で、mux ウィンドウが通常タブに迫るスループットを示すこと。

### 2.2 対象ユーザー

| ユーザータイプ | 説明 |
|----------------|------|
| mux ウィンドウ利用者 | tmux 風多重化を使い、大量出力を伴うコマンド／ツールを実行するユーザー |

### 2.3 期待される効果

- 1 pump 内の `process_pty_data_fully` 起動を ~1400 回 → 数回（連続 PtyOutput 区間ごとに 1 回）に削減
- CPU 効率向上 → backpressure 緩和 → PTY read / 1 フレームの大型化 → フレーム数自体の減少という好循環

## 3. ユースケース

### 3.1 ユースケース一覧

| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | mux ウィンドウで大量出力を表示する | mux 利用者 | 高 |

### 3.2 ユースケース詳細

#### UC01: mux ウィンドウで大量出力を表示する

**アクター**: mux ウィンドウ利用者

**事前条件**:
- mux 接続が確立している（`process_combined` 経路がアクティブ）
- アクティブペインが存在する

**基本フロー**:
1. アクティブペインから大量の出力が PTY に流れる
2. daemon が出力を多数の `PtyOutput` mux APC フレームに分割して client へ送る
3. client の `pump()` が 1 MiB まで coalesce し `process_combined` に渡す
4. `process_combined` が連続するアクティブペイン宛 `PtyOutput` の inner payload を連結バッファに溜める
5. 制御メッセージ境界またはループ終端で、連結バッファを 1 回だけ `process_pty_data_fully` に渡す
6. 画面に出力が反映される

**代替フロー**:
- 非アクティブペイン宛 `PtyOutput`: 連結対象に含めず drop（従来どおり）
- `pending_switch`（off-thread replay 中）: 連結対象外。従来の個別経路（`live_queue` 積み）を維持
- 制御メッセージ（`Welcome` / `PaneCreated` / `Detached` / `PtyExited` 等）: 処理前に連結バッファを flush し、順序を保つ

**事後条件**:
- 連結==分割の出力結果が一致（純粋な性能変更であること）

## 4. 機能要件

### 4.1 機能一覧

| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | 連続 PtyOutput の連結 parse | 連続するアクティブペイン宛 `PtyOutput` の inner payload を連結し parse を 1 回にまとめる | 高 |
| F02 | 制御メッセージ境界での flush | `PtyOutput` 以外のメッセージ処理前に連結バッファを flush し順序保証 | 高 |
| F03 | バッチ後の副作用処理 | `take_response` / `drain_marks` / 内側画像 APC/DCS drain を連結バッチ後に 1 回行う | 高 |
| F04 | pending_switch 中の従来経路維持 | off-thread replay 中はバッチ対象外とし `live_queue` 積みを維持 | 高 |

### 4.2 機能詳細

#### F01: 連続 PtyOutput の連結 parse

**説明**: `process_combined` の抽出フレームループで、連続するアクティブペイン宛 `PtyOutput` フレームの inner payload を連結バッファに溜め、即時 parse しない。次のいずれかで連結バッファを 1 回だけ `process_pty_data_fully` に渡す（flush）:
- `PtyOutput` 以外の制御メッセージが来たとき、その処理の前
- ループ終端

**ビジネスルール**:
- 非アクティブペイン宛 `PtyOutput` は連結対象に含めない
- `pending_switch` 中は連結対象外（F04）

#### F02: 制御メッセージ境界での flush

**説明**: 制御メッセージ（`Welcome` / `PaneCreated` / `Detached` / `PtyExited` 等）を処理する前に必ず連結バッファを flush し、出力と制御の順序を保つ。

#### F03: バッチ後の副作用処理

**説明**: `process_pty_data_fully` 後の `take_response`（device response 書き戻し）、`drain_marks`（OSC 133）、内側画像 APC/DCS の drain は、連結バッチ後に 1 回行う。

#### F04: pending_switch 中の従来経路維持

**説明**: off-thread replay 中（`pending_switch` が Some）の `PtyOutput` は連結対象外とし、従来の個別経路（`live_queue` への push）を厳守する。

## 5. 非機能要件

### 5.1 パフォーマンス要件

- 1 pump 内の `process_pty_data_fully` 起動回数: ~1400 回 → 数回（連続 PtyOutput 区間ごとに 1 回）
- daemon 直結 E2E スループット: before 2.85 MiB/s（N=10M）から大幅短縮
- daemon 直結 E2E フレーム数: before 124,233（N=10M）から減少
- 最終ゴール（phase1〜3 共通）: 実環境 `time seq 1 10000000`（mux ウィンドウ）を 10 秒弱以内（ストレッチ 7.6 秒）。現状 146 秒。本 phase1 単独でこの最終ゴール到達を必須とはしない（到達可否は phase2/3 着手判断の材料）

### 5.4 保守性要件

- 連結==分割の正しさを保証する既存契約テストを green に維持する

## 9. 制約条件

### 9.1 技術的制約

- daemon / bridge / transport / WebView 版（`src/`）は変更しない
- 既存の `PtyOutput` アームの相互作用（pane filter / `pending_switch` / device response / 内側 Kitty 画像の APC 境界）を連結経路で正しく再現する

## 10. 想定される課題とリスク

### 10.1 技術的課題

| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| `PtyOutput` アームの相互作用を連結経路で再現 | 高 | pane filter / pending_switch / device response / 画像 APC 境界を連結経路へ正しく持ち上げる |
| Kitty 画像チャンクが `PtyOutput` 境界をまたぐ | 中 | 連結により境界が消えるため安全側。ただし制御メッセージ区切りで必ず flush し順序保証 |
| pending_switch 中の挙動退行 | 高 | pending_switch 中はバッチ対象外（従来経路）を厳守 |

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| coalesce | 連続する複数フレームの payload を連結し parse 起動を 1 回にまとめること |
| pump | 描画フレームごとに 1 回呼ばれる、受信バイトの取り込み処理 |
| inner payload | mux APC フレームの内側に入っている、ペイン宛の生 PTY バイト列 |
| pending_switch | off-thread replay 中の状態。ウィンドウ切替時の replay 待ち |
| drain_marks | OSC 133 等のマーク収集処理 |
