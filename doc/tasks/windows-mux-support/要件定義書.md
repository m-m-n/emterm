# Windows mux機能対応 - 要件定義書

## 1. 概要

### 1.1 背景
eMtermのmux機能は現在Linux専用で実装されており、Windowsでは全CLIコマンドがエラーを返して終了する。eMtermはLinuxとWindowsの両プラットフォームをサポートしているため、mux機能もWindowsで利用可能にする必要がある。

### 1.2 目的
WindowsでeMtermのmux機能（デーモン、ブリッジ、セッション管理、ウィンドウ操作、再接続）を利用可能にする。

### 1.3 スコープ
**対象:**
- デーモン起動・停止（Named Pipes経由）
- ブリッジ接続（Windows Console API raw mode）
- セッション管理（ls, kill）
- ウィンドウ操作（new-window, switch-window）
- デタッチ・再接続（reattach/detach）

**対象外:**
- send-keys
- ステータスバー

## 2. ビジネス要件

### 2.1 ビジネス目標
WindowsユーザーがeMtermのmux機能を利用できるようにし、プラットフォーム間の機能格差を縮小する。

### 2.2 対象ユーザー
| ユーザータイプ | 説明 |
|----------------|------|
| Windows開発者 | Windows上でeMtermを使用し、muxによるセッション永続化を必要とするユーザー |

### 2.3 期待される効果
- Windowsユーザーがmux機能でセッションを永続化できる
- ターミナル終了後もプロセスが維持される

## 3. ユースケース

### 3.1 ユースケース一覧
| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | muxセッション開始 | Windowsユーザー | 高 |
| UC02 | muxセッション再接続 | Windowsユーザー | 高 |
| UC03 | ウィンドウ作成・切替 | Windowsユーザー | 中 |
| UC04 | セッション一覧表示 | Windowsユーザー | 中 |
| UC05 | セッション終了 | Windowsユーザー | 中 |

### 3.2 ユースケース詳細

#### UC01: muxセッション開始

**アクター**: Windowsユーザー

**事前条件**:
- eMtermがインストールされている
- Windows 11

**基本フロー**:
1. ユーザーが `emterm mux` を実行
2. デーモンが起動していなければNamed Pipe経由でデーモンを起動
3. ブリッジプロセスがデーモンに接続
4. ターミナルがraw modeに切り替わり、双方向通信が開始

**代替フロー**:
- デーモンが既に起動済みの場合、既存デーモンに接続

**事後条件**:
- muxセッションが確立され、シェルが利用可能

#### UC02: muxセッション再接続

**アクター**: Windowsユーザー

**事前条件**:
- デーモンが起動中で、デタッチ済みセッションがある

**基本フロー**:
1. ユーザーが `emterm mux` を実行
2. デーモンに接続し、既存セッションに再接続
3. バッファされた出力が送信される

**事後条件**:
- 以前のセッション状態が復元される

#### UC03: ウィンドウ作成・切替

**アクター**: Windowsユーザー

**基本フロー**:
1. `emterm mux new-window` で新規ウィンドウを作成
2. `emterm mux switch-window` でウィンドウを切替

#### UC04: セッション一覧表示

**基本フロー**:
1. `emterm mux ls` でセッション・ウィンドウ一覧を表示

#### UC05: セッション終了

**基本フロー**:
1. `emterm mux kill` でデーモンを終了

## 4. 機能要件

### 4.1 機能一覧
| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | Named Pipeデーモン | Named Pipe上でリッスンするmuxデーモン | 高 |
| F02 | デーモンプロセス分離 | DETACHED_PROCESS + CREATE_NEW_PROCESS_GROUPでデーモンを起動 | 高 |
| F03 | ブリッジ接続 | Named Pipe経由のブリッジ（Windows Console API raw mode） | 高 |
| F04 | セッション管理CLI | ls, kill コマンドのWindows対応 | 中 |
| F05 | ウィンドウ操作CLI | new-window, switch-window コマンドのWindows対応 | 中 |
| F06 | reattach/detach | セッションのデタッチ・再接続 | 中 |

### 4.2 機能詳細

#### F01: Named Pipeデーモン

**説明**: Unix版の`UnixListener`に相当するNamed Pipeサーバーをデーモンとして起動し、クライアント接続を受け付ける。

**Named Pipeパス**: `\\.\pipe\emterm-mux-default`

**処理フロー**:
1. Named Pipeサーバーを作成
2. クライアント接続を待機
3. 接続ごとに`handle_connection`をspawn
4. Ctrl+Cで graceful shutdown
5. 全セッション空で自動終了

**エラーケース**:
| エラー | 条件 | 対応 |
|--------|------|------|
| Pipe作成失敗 | 権限不足またはパス競合 | エラーログ出力して終了 |
| 接続受付失敗 | システムリソース不足 | エラーログ出力して継続 |

#### F02: デーモンプロセス分離

**説明**: `CREATE_NEW_PROCESS_GROUP | DETACHED_PROCESS` フラグでデーモンを起動し、親ターミナル終了後も生存させる。

#### F03: ブリッジ接続

**説明**: Named Pipeクライアントとして接続し、stdin/stdout ↔ Pipe間の双方向転送を行う。Windows Console APIでraw modeを設定する。

**処理フロー**:
1. Named Pipeに接続
2. `GetConsoleMode`で現在のモードを保存
3. `SetConsoleMode`で`ENABLE_VIRTUAL_TERMINAL_INPUT`に設定
4. stdin → Pipe、Pipe → stdout の双方向転送
5. 終了時に`SetConsoleMode`で元のモードを復元

#### F04: セッション管理CLI

**説明**: `emterm mux ls` と `emterm mux kill` のWindows対応。Named Pipe経由でデーモンと通信。

#### F05: ウィンドウ操作CLI

**説明**: `emterm mux new-window` と `emterm mux switch-window` のWindows対応。Named Pipe経由でデーモンと通信。

#### F06: reattach/detach

**説明**: セッションのデタッチ・再接続。バッファされた出力の再送信を含む。

## 5. 非機能要件

### 5.1 パフォーマンス要件
- Named Pipe通信のレイテンシ: Unix版と同等
- ブリッジのスループット: PTY出力をリアルタイムで転送

### 5.2 セキュリティ要件
- Named Pipeのアクセス制御: 現在のユーザーのみアクセス可能
- PIPE_REJECT_REMOTE_CLIENTSフラグによるリモートアクセス拒否

### 5.3 可用性要件
- デーモンはターミナル終了後も生存し続ける
- 異常終了時はstale pipe検出と再起動が可能

### 5.4 保守性要件
- ログ出力: Unix版と同じログ形式
- プラットフォーム固有コードは`#[cfg(windows)]`で分離

### 5.5 互換性要件
- 最低OS: Windows 11
- IPCプロトコル: Unix版と同一のメッセージフォーマット（codec/protocol層は共通）

## 6. UI/UX要件

### 6.1 画面設計要件
CLIインターフェースのため画面設計は不要。コマンド体系はUnix版と同一。

### 6.2 画面遷移
該当なし（CLI）

### 6.3 レスポンシブ対応
該当なし

## 7. データ要件

### 7.1 データモデル概要
Unix版と同一のセッション/ウィンドウ/ペインモデルを使用。

### 7.2 データ項目
変更なし（既存のセッション管理構造を共有）

### 7.3 データ保持期間
該当なし（メモリ上のセッション状態のみ）

## 8. 外部連携

### 8.1 連携システム
| システム名 | 連携方法 | データ |
|------------|----------|--------|
| Windows Named Pipes | `\\.\pipe\emterm-mux-default` | IPCメッセージ |
| Windows Console API | `windows-sys`クレート | コンソールモード制御 |
| portable-pty | 既存依存 | PTYセッション（既にWindows対応済み） |

### 8.2 API仕様要件
IPCプロトコルはUnix版と同一。トランスポート層のみNamed Pipeに変更。

## 9. 制約条件

### 9.1 技術的制約
- `tokio::net::windows::named_pipe`を使用（tokioの`net`featureが必要）
- `windows-sys`クレートでConsole APIを呼び出し
- Named PipeはUnixソケットと異なりステートフル（接続/切断のセマンティクスが異なる）

### 9.2 ビジネス上の制約
- Unix版の既存動作を一切変更しない

### 9.3 スケジュール制約
- 特になし

## 10. 想定される課題とリスク

### 10.1 技術的課題
| 課題 | 影響度 | 対応策 |
|------|--------|--------|
| Named PipeとUnixSocketのAPI差異 | 中 | トランスポート抽象化層の設計 |
| Named Pipeの同時接続ハンドリング | 中 | tokioのnamed_pipe APIで非同期処理 |

## 13. 用語定義

| 用語 | 定義 |
|------|------|
| Named Pipe | Windowsのプロセス間通信機構。`\\.\pipe\{name}`形式のパスでアクセス |
| DETACHED_PROCESS | Windowsのプロセス作成フラグ。親コンソールから分離される |
| CREATE_NEW_PROCESS_GROUP | Windowsのプロセス作成フラグ。新しいプロセスグループを作成 |
| bridge | デーモンとターミナルの間を中継するプロセス |
